# Workflow 검토

산출물은 관점별 지적과 근거이고 수용·반려는 작성자가 결정한다. CI 정책의 재설계 제안은 별도 요청 범위다.

## 1. 입력과 실행 코드의 출처

workflow YAML 전부(트리거가 서로 참조한다), 호출하는 스크립트 본문, 실행/생략 조건의 정본(판정 스크립트·정책 테스트), required·배포 정책(branch protection 설정·결정 문서), 실제 run 증거(run URL·SHA·결론)를 확보한다. YAML의 주석·이름이 아니라 스크립트와 설정이 하는 일을 기준으로 판정한다.

검토 대상의 ref·SHA를 고정해 적고, 이벤트별로 **어느 ref의 코드가 실행되는지** 먼저 확인한다 — `pull_request`는 PR merge 결과, `workflow_run`은 default branch, 재사용 workflow는 호출 시점의 핀이다. 같은 파일이 브랜치마다 다르면 어느 계보를 검토했는지 명시한다. 빠진 입력은 그 관점을 **미검토**로 표시하고 확보된 범위만 검토한다.

## 2. 다섯 관점

| 관점 | 확인할 것 |
| --- | --- |
| 병합 방어 | branch protection의 required 목록과 실제 job 이름이 일치하는가. 필요한 검증의 실패·취소·예상 밖 생략이 required 실패로 전파되는가. `always()`·`!cancelled()`·`continue-on-error`가 실패를 삼키는 경로는 없는가. |
| concurrency | group 키에 무엇이 들어가는가 — PR 취소는 허용하되 main push·배포가 서로를 취소하거나 대기에서 밀려 탈락하는 경로가 없는가. 배포처럼 직렬화가 필요한 job의 queue 정책. |
| 캐시·path filter | 캐시 키가 입력 변경을 따라가는가, 잘못된 hit이 검증을 약화시키지 않는가. 필터 밖 경로 변경이 검증 대상 동작을 깨는 반례. 미분류 경로의 기본값(안전한 쪽인가). API 목록 잘림·조회 실패의 검출. |
| required와 생략 | 조건부 skip이 required와 만나 pending·침묵 통과로 남지 않는 구조인가. 생략 **결정**과 실제 **outcome**을 대조하는 장치가 있는가. 정상 생략과 조건 버그 생략을 출력·summary에서 구별할 수 있는가. |
| 최소 권한·secrets | job별 `permissions` 명시와 최소화. 쓰기 권한·secrets가 있는 job에서 PR head의 코드·설치 스크립트·훅을 실행하지 않는가. `pull_request_target` 부재. secrets가 로그·산출물·fork로 새는 경로. 외부 fork의 처리. |

## 3. 실행 상태와 동일 SHA 대조

실패·취소·정상 생략·0개 실행·미완료를 구별한다. 각 상태 주장에는 run URL과 SHA를 붙인다. "테스트가 돌았다"는 선택 개수·통과 개수를 기대값과 대조하는 장치까지 확인한다 — 0개 선택 성공을 실행으로 세지 않는다. timeout·재시도 소진·게시 실패는 지적 없음·성공과 구별해 표시되는지 본다.

검증한 SHA와 그 결과를 소비하는 곳(required 판정·PR 코멘트·배포)이 **같은 SHA**를 가리키는지 대조한다. 늦게 끝난 과거 run이 최신 결과를 덮는 경로와 그 방어를 확인한다.

run 증거 없이 "이 조건에서 반드시 실행된다"고 판정할 수 없으면 **보류**로 보고하고, 무엇을 실행하면 확인되는지 적는다.

## 4. 보고와 작성자 결정

지적마다 위치(파일·줄 또는 run)·관점·근거·확신도를 남기고 확실한 사실과 추정을 구별한다. 기존 결정 문서가 있는 정책은 문서를 인용해 **기존 결정**으로 보존하고, 새 판단이 필요한 항목만 **작성자 결정 대기**로 남긴다. 검토 완료는 다섯 관점 각각에 지적 또는 "확인함(근거)"이 있고 미검토·보류 목록이 정리됐을 때다.
