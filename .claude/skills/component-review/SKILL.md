# /component-review 컴포넌트 관심사 리뷰

React 컴포넌트 리팩토링 결과를 발제 기준으로 검토하는 스킬.
이 스킬이 답하는 질문은 하나다 — **이 화면을 무엇으로 나눌 것인가.** "잘게 쪼갰는가"가 아니라 읽고 싶은 관심사를 한 번에 읽을 수 있는 구조인지 본다.

---

## 절차

1. 분리하기 **전** 요청이면 사전 모드, 변경한 **뒤** 요청이면 리뷰 모드로 진행한다. 사전 모드는 대상 컴포넌트와 사용처를, 리뷰 모드는 `git diff`와 변경 파일 목록을 확인한다.
2. 관련 컴포넌트, hook, service, utils 파일을 읽는다.
3. `AGENTS.md`, `CONVENTIONS.md`, 관련 과제 문서가 있으면 함께 읽는다. 대상 파일에 걸리는 `.claude/rules/*.md`도 읽는다 — 화면 컴포넌트는 `rendering.md`, 성능을 이유로 든 변경은 `performance.md`가 판정 기준이다.
4. 아래 관점으로 구조와 기록을 검토한다.
5. 사용처, 측정 자료, 작성자가 정한 의도처럼 없는 입력은 추측으로 채우지 않는다. 필요한 자료와 함께 미검토 범위로 보고한다.
6. 문제는 심각도순으로 보고하고, 분리하지 않아도 되는 부분은 억지로 분리하라고 하지 않는다.

---

## 리뷰 관점

### 0) 분리 전 책임 분류 (사전 모드)

- 지금 이 파일이 지고 있는 책임을 UI 렌더링 / 화면 상태 / 서버 데이터 / 도메인 규칙으로 나눠 표로 적는다. 파일의 모든 코드가 어느 행에는 속해야 한다.
- 책임마다 **변경 이유**를 적는다. 변경 이유가 다르면 분리 후보, 같은 이유로 함께 바뀌면 붙여 둔다.
- 분리 제안의 근거는 변경 이유뿐이다. 줄 수와 props 개수는 근거가 아니다.
- 분리하지 않을 후보와 그 이유도 같은 비중으로 낸다. 상태도 effect도 없는 계산은 Hook이 아니라 순수 함수가 맞다.
- 출력은 후보와 근거까지다. 무엇을 분리할지는 작성자가 정한다.

### 1) 레이어 분리

- Components는 JSX 렌더링, 이벤트 바인딩, 스타일, 작은 표시 파생값에 집중하는가?
- Hooks는 상태 관리, 필터/정렬/검색, 서버 상태 조합, 도메인 흐름을 담당하는가?
- Services는 endpoint, request params, response 형태, 공통 에러 변환만 담당하는가?
- Utils는 외부 상태에 의존하지 않는 순수 함수인가?
- 컴포넌트 파일만 보면 화면이 그려지고, Hook 파일만 보면 기능 흐름이 잡히고, Service 파일만 보면 API 스펙이 보이는가?
- 구현과 조합의 추상화 레벨이 한 파일 안에서 섞이지 않는가?
- 중복보다 잘못된 추상화가 더 위험하다. 세 번째 반복 전에는 성급한 공통화를 경계한다.
- 공통 UI의 공개 API 설계(props 조합 · slot · 제어권 · 합성)는 `analyze-component`가 본다. 여기서는 화면을 무엇으로 나눌지만 판단한다.

### 2) 상태 3분할

- 서버 상태, 클라이언트 상태, 파생값을 구분했는가?
- 서버 상태를 로컬 state로 복제하지 않았는가?
- props, URL search param, 서버 응답에서 계산 가능한 값을 state로 복사하지 않았는가?
- 필터/검색/페이지처럼 공유·새로고침되어야 하는 상태는 단일 출처가 명확한가?
- 렌더링 중 구할 수 있는 값에 불필요한 `useEffect`를 쓰지 않았는가?

### 3) Custom Hook 책임

- 각 Hook을 한 문장으로 설명할 수 있는가?
- 한 문장에 "그리고"가 여러 번 들어가면 분리 후보로 본다.
- 같은 상태 + 로직 조합이 반복되거나, 한 흐름으로 응집되어 있는가?
- Hook이 JSX나 스타일을 반환하지 않는가?
- Hook이 `fetch`/`axios` 구현체에 직접 묶이지 않고 service 함수에 의존하는가?
- Hook 이름이 역할을 충분히 설명하는가? (`useData` 같은 이름은 지적)
- Hook이 자기 안에서 만든 상태(`useState` 등)는 호출할 때마다 새로 생기고, 외부 store·Query를 구독하는 Hook은 반대로 공유된다. 사용처가 기대하는 쪽과 맞는지 확인한다.
- deps에 매 렌더 새로 만들어지는 객체·함수가 들어가 effect가 계속 다시 도는 경로가 있는가?

### 4) API / 서버 상태

- 컴포넌트에서 API 호출 코드가 제거되었는가?
- query key, loading/error/refetch, placeholder data 같은 서버 상태 정책이 한 곳에서 일관되게 관리되는가?
- service가 TanStack Query 옵션, UI 표시 모델, 카드 뱃지 같은 화면 규칙까지 알게 되지 않았는가?
- query option은 사용처가 하나면 hook 내부 private 함수로 둬도 된다. prefetch, loader, 여러 hook 공유가 생기면 `queries/` 분리를 제안한다.

### 5) 도메인 규칙과 파생값

- 서버 응답 형태 자체를 바꾸는 변환과, 화면 표시용 파생값을 구분했는가?
- 할인율, 상태 라벨, 뱃지 조건처럼 도메인 판단은 JSX 안에 인라인으로 흩어져 있지 않은가?
- 서버 데이터만으로 계산되는 표시 파생값은 순수 함수로 분리할 수 있는가?
- 클라이언트 상태가 필요한 값(예: 위시 여부, 검색어 하이라이트)은 너무 이른 레이어에서 계산하지 않았는가?

### 6) useEffect 정당성

- `useEffect`가 외부 시스템 동기화인지 확인한다.
- 서버 요청, localStorage, URL, DOM API, 구독처럼 외부 시스템과 연결되면 effect가 정당할 수 있다.
- 파생값 계산, 상태 라벨 포맷팅, props/state 복사는 effect 제거 후보로 본다.
- 변경 경로가 여러 개인 화면 정책(예: URL 직접 진입, 뒤로가기, 클릭 모두에서 page 변경)은 effect가 더 자연스러울 수 있다.
- 외부 시스템에 연결하는 effect에는 구독 해제·요청 취소 같은 cleanup이 있는가?

### 7) 규칙 파일에 위임하는 범위

각 파일을 열어 그 조항으로 판정한다.

- 오류 처리 위치, 초기/재조회/빈값/오류/취소 전환, 로딩 자리와 접근성: `.claude/rules/rendering.md`
- 성능을 이유로 든 변경: `.claude/rules/performance.md`
- 타입 침묵, 기존 유틸 재사용, 입력 신뢰 경계: `self-review`가 diff 전체에서 본다. 컴포넌트 안에서 눈에 띄면 지적하되 전수 검사는 하지 않는다.

## 결과 형식

```
## Component Review 결과

**판정: PASS / NEEDS_WORK**

### 잘 된 점
- {분리나 기록이 잘 된 부분}

### 지적 사항
- [blocker] {파일:줄} — {문제} → {수정 제안}
- [major] {파일:줄} — {문제} → {수정 제안}
- [minor] {파일:줄} — {문제} → {수정 제안}

### 분리하지 않아도 되는 부분
- {억지 추상화를 피해야 하는 부분과 근거}

### 미검토 범위
- {입력이 없어 판단하지 않은 것과 그에 필요한 자료}

### 질문
- {사람 리뷰어에게 확인하면 좋은 설계 질문}
```

사전 모드에서는 "지적 사항" 대신 아래 표를 낸다.

```
### 책임 표
| 책임 | 지금 있는 위치 | 변경 이유 | 분리 후보 / 유지 | 근거 |
| --- | --- | --- | --- | --- |
```

---

## 판정 기준

- blocker: 동작이 깨지거나 과제 필수 조건을 충족하지 못함
- major: 책임 경계가 흐려 변경 비용이 커질 가능성이 큼
- minor: 이름, 위치, 기록 밀도, 추상화 수준을 다듬으면 좋아짐
