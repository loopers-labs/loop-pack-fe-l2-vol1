# Test Review — 층 · 격리 · 경계 · 자가검증 · 비용

> **용도: 테스트가 "무엇을 지키는지"가 또렷한지 점검.** 프레임워크·도구와 무관한 판단 기준을 담는다.
> 이 레포의 도구(MSW·Stryker·Playwright·vitest)는 원칙을 보여주는 **예시로만** 든다 — 다른 스택에도 그대로 적용한다.

한 질문으로 관통한다: **무엇을 우리가 짜서 검증하고, 무엇을 라이브러리·프레임워크 몫으로 믿고 넘기나.** 커버리지·점수가 아니라 이 경계가 또렷한지가 좋은 테스트의 기준이다.

---

## 점검 실행 순서

1. **대상 읽기** — 인자로 받은 파일(없으면 대상을 묻는다)과 연관(구현·목/픽스처·공통 setup)을 함께 읽는다.
2. **층 판별** — 원칙 1로 이 테스트가 어느 층인지 정한다. 층을 잘못 고른 것 자체가 첫 리뷰 포인트.
3. **원칙별 점검** — 아래 원칙을 대상에 해당하는 것만 적용한다(조건부). 위반으로 보이면 **정당한 예외** 표에 해당하는지 먼저 확인한다 — 조건을 충족하면 통과다.
4. **자가검증** — 이 테스트가 실제 결함을 잡는지 본다.
5. **게이트** — 검증 명령이 통과하고 기존 테스트가 유지되는지.
6. **리포트** — 파일은 고치지 않고 후보만 제안한다.

---

## 원칙 1 — 무엇을 어느 층에서, 어떤 시나리오로 지킬지 먼저 정한다

테스트를 층(단위·통합·E2E)에 배치하는 건 감이 아니라 세 질문으로 정한다.

| 질문                                                      | 예 → 층       |
| --------------------------------------------------------- | ------------- |
| 함수 호출·상태 조회만으로 확인되나                        | 예 → **단위** |
| 렌더·실제 경계(네트워크·저장)가 있어야 드러나나           | 예 → **통합** |
| 실제 브라우저에서만 나타나나(뒤로가기·새로고침·화면 이동) | 예 → **E2E**  |

- [ ] 층을 올바로 골랐는가 — 한 테스트에 여러 층 관심사를 욱여넣지 않았는가
- [ ] 애매한 항목은 "그 상태에 닿는 유일한 경로가 무엇인가"로 갈랐는가
  - _예(이 레포): 빈 결과 화면은 컴포넌트가 스스로 조회해 닿으므로 단위가 아니라 통합으로 뒀다._
- [ ] 해피 패스만이 아니라 **계약으로 시나리오를 설계했는가** — 구현 전에 사전조건(빈·초기 상태), 사후조건(결과·상태 전이), 불변식(경계·초과·경합)을 적었는가
  - _예: "재고 0이면 담기 불가"는 사전조건, "담으면 개수 +1"은 사후조건, "같은 것을 두 번 담아도 한 줄"은 불변식이다._

## 원칙 2 — 우리가 짠 것만 검증하고, 경계는 믿고 넘긴다

- [ ] 라이브러리·프레임워크가 보장하는 동작을 다시 테스트하려 들지 않는가 — 그건 우리 결함이 아니라 그들의 계약이다
  - _예: 상태 라이브러리의 저장, 서버 상태 라이브러리의 재시도, URL 라이브러리의 기본값 처리는 믿고 넘긴다._
- [ ] 우리 코드가 그 경계를 **올바로 호출했는지**(설정을 걸었는지)만 좁게 단언하는가

## 원칙 3 — 목은 경계에서, 내부에서 가로채지 않는다

- [ ] 내부 함수를 바꿔치기하는 대신 **가장 바깥 경계**(네트워크 등)에서 가로채는가 — 그래야 URL 조립·직렬화 같은 중간 단계가 실제로 돈다
  - _예(이 레포): `fetch` 스텁 대신 MSW로 네트워크 경계에서 가로챈다. 정의 안 한 요청은 곧장 실패로 드러내고(`onUnhandledRequest:"error"`), 실패·빈·지연은 테스트마다 덮은 뒤 되돌린다._
- [ ] 목 도구의 버전 API를 맞게 쓰는가(예: MSW v2 `http`·`HttpResponse`·`setupServer`)

## 원칙 4 — 구현이 아니라 관찰 가능한 동작을 단언한다

무엇을 단언하느냐가 유지보수 비용을 가른다. 내부 구현에 붙으면 리팩터마다 깨지고, 관찰 가능한 동작에 붙으면 리팩터에도 살아남는다.

- [ ] 동작을 바꾸지 않는 **리팩터에도 이 테스트가 살아남는가** — 내부 호출·스파이 호출 수·구현 세부가 아니라 관찰 가능한 결과(반환·화면·상태)를 단언하는가
  - _예(이 레포): E2E 셀렉터를 역할·이름 기반으로 두는 것도 이 원칙의 한 조각이다 — 마크업 구조가 바뀌어도 살아남는다._
- [ ] **이 테스트가 실패할 수 있는가** — 단언 없는 렌더나 항상 참인 단언은 초록이어도 아무것도 지키지 않는다
- [ ] **실패 이유가 하나로 좁혀지는가** — 한 테스트가 무관한 여러 가지를 단언하면 실패 리포트만 보고 원인을 짚기 어렵다(순서가 곧 동작인 시퀀스 테스트는 예외 → 원칙 5)

## 원칙 5 — 순서 의존인지 먼저 가리고, 각각 맞게 격리한다

**먼저 이 테스트가 순서에 무관해야 하는지, 순서가 곧 검증 대상인지 가른다.** 둘은 반대 요구라 처리도 다르다.

- [ ] **분류했는가** — 각 테스트가 독립된 사실을 확인하나(순서 무관), 아니면 순서 자체가 검증 대상인가(예: 담기 → 같은 것 다시 담아 무시 → 빼기)
- **순서 무관(대다수):**
  - [ ] 각 테스트가 시작 상태를 스스로 세우고, 전역·모듈 싱글턴·저장소에 남은 값을 물려받지 않는가(공통 `afterEach` 등에서 리셋)
  - [ ] 실행 순서를 섞어(shuffle) 순서 무관을 확인했는가
- **순서가 곧 동작(소수):**
  - [ ] 시퀀스를 **한 테스트가 처음부터 끝까지** 수행하고 중간·최종 상태를 단계별로 단언하는가 — step을 여러 테스트로 쪼개 "A 먼저 돌아야 B 통과"라는 **테스트 간 의존**을 만들지 않았는가
  - [ ] 그 테스트 **자체는 여전히 다른 테스트와 격리되는가** — 순서는 이 한 테스트 _안에서만_ 의미가 있고, 시작·끝에서 자기 상태를 세우고 지운다. 순서 의존이 테스트 _사이로_ 새면 안 된다
- [ ] **flaky를 노이즈로 넘기지 않았는가** — 코드가 그대로인데 결과가 오가면 대개 타이밍·순서 의존·비결정 값이며, 숨은 결합의 신호다
  - _예(이 레포): 순서를 섞자 싱글턴 래치에 의존하던 게이트 테스트가 깨졌고, spy + 복원으로 각 테스트가 자기 상태만 보게 끊었다._

## 원칙 6 — "통과"가 아니라 "결함을 잡는지"를 검증한다

- [ ] **커버리지를 검증으로 착각하지 않는가** — 커버리지는 그 줄이 *실행됐음*을 셀 뿐, 결함을 잡는 *단언이 있는지*는 세지 않는다
- [ ] **스냅샷으로 기능 검증을 대체하지 않는가** — 스냅샷은 출력이 *이전과 같은지*만 보지 *맞는지*는 보지 않는다. 틀린 출력이 기준선이 되면 그 결함을 영영 못 잡으니, 무엇이 왜 맞는지는 명시적 단언으로 짚는다
- [ ] 구현을 한 곳씩 일부러 깨 빨간불을 확인하고, 실험 코드는 원복해 커밋에 남기지 않았는가
- [ ] "깰 곳을 사람이 골랐다"는 편향을 메우려 순수 로직은 전수 변형(뮤테이션 테스트)으로 훑었는가
- [ ] 픽스처가 **동작을 그 변형과 구별할 최소 다양성**을 갖췄는가
  - _예(이 레포): 항목이 하나뿐이면 "그것만 제거"와 "전부 제거"가 같은 빈 결과라 결함이 숨는다 — 둘로 늘려 구별되게 했다._
- [ ] 살아남은 변형을 **"진짜 문제인가"로 판정**했는가 — 바꿔도 동작이 같은 것(equivalent)·성능·SSR·신뢰 경계는 그대로 두고, 우리 판단만 보강
- [ ] 단일 총점에 흔들리지 않고 항목별 신호를 쓰는가 — _총점은 실행 환경에 흔들릴 수 있다(예: 타임아웃이 잡힘으로 집계돼 부하가 클수록 높게 나옴). 가장 보수적인 실행값을 신뢰한다._
- [ ] 전수 변형은 매 커밋이 아니라 순수 로직을 크게 손볼 때·병합 전에만 돌리는가(비싸므로)

## 원칙 7 — 비싼 테스트(E2E)는 값하는 곳에만 붙인다

E2E는 느리고 UI 변경에 잘 깨진다. 개수가 아니라 **가치/비용**으로 붙일 곳을 정한다.

- [ ] 붙일 곳을 근거(빈도·실패 비용)로 골랐는가 — "많이 지나가니까"만으로 정하지 않았는가(이미 싼 층이 덮고 있을 수 있다)
- [ ] 값비싼 셋업(로그인 등)을 1회 만들어 재사용하는가 — 단, **그 흐름 자체를 검증하는 테스트는 재사용분을 쓰지 않는가**(이미 통과 상태로 시작하면 흐름이 깨져도 통과)
- [ ] 병렬 실행에서 무엇을 갈라 격리했는가(계정·데이터·저장소·브라우저 상태)
- [ ] **시간 기반 대기가 없는가**(`sleep`·`waitForTimeout`), 조건 기반 대기만 쓰는가 — 만료 같은 서버 상태는 시간이 아니라 재현 가능한 신호(쿠키 등)로 만든다
- [ ] 셀렉터가 역할·이름 기반인가
- [ ] 실패 증거(trace 등)를 남기고, **설정만 넣는 데 그치지 않고 한 번 직접 열어봤는가**
- [ ] 워커 수를 바꿔도, 반복해도 결과가 같은가
- [ ] 개발 서버가 아니라 **실배포에 가까운 빌드 위**에서 도는가 — 번들·라우팅·CSS가 dev와 달라질 수 있다
- [ ] 자동 생성·자동 수정(healer)된 테스트라면, "셀렉터 안 맞음"이 **의도된 변경인지 구현이 깨진 것인지 사람이 diff를 읽고 판정**했는가
  - _예(이 레포): 기존 E2E는 `playwright.config`의 `pnpm build && pnpm start` 위에서 돌고 셀렉터는 `getByRole`·`getByLabel`이라, 위 원칙들은 이미 실물로 뒷받침된다. auth 특화 패턴(storageState 재사용·워커별 계정·시나리오 쿠키)만 이번 주 4단계에서 실물이 된다._

## 정당한 예외 — 규칙을 우회해도 되는 자리

원칙을 어긴 것처럼 보여도 아래에 해당하면 정당하다. **단, 우회에는 각 항목의 조건이 붙어야 한다(대개 이유 주석) — 조건 없는 우회는 그냥 위반이다.**

| 원칙 | 우회해도 되는 자리                                                                                         | 정당한 조건                                         |
| ---- | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| 2    | 라이브러리 몫이라도 **우리가 주입한 판단**(커스텀 `retry` 조건·zod `.catch` sanitize·transform)은 검증한다 | 그 로직을 우리가 짰을 것                            |
| 3    | **비결정 근원**(시간·랜덤·UUID)은 근원에서 고정, 외부 SDK는 **provider 인터페이스**에서 대체               | 네트워크가 아니라 통제 불가한 비결정·외부 의존일 때 |
| 4    | **호출 자체가 관찰 계약**이면 그 호출을 단언(분석 이벤트 이름·props, 주입 콜백, `aria-*`)                  | 그 호출이 산출물·계약일 때(내부 구현이 아니라)      |
| 5    | **읽기 전용·워커 단위** 공유 셋업(`beforeAll` 불변 픽스처·워커별 `storageState`)                           | 공유분에 변이·오염이 없을 것                        |
| 6    | **검토된 기준선**의 구조적 출력 스냅샷(직렬화·생성 설정)으로 변경 감지                                     | 기준선을 "맞다"고 검토했을 것(캡처만은 X)           |
| 7    | **저빈도·고비용**(막히면 뒤가 다 막힘) 경로는 E2E를 붙인다                                                 | 실패 비용이 빈도를 이길 것(예: 인증)                |
| 7    | **부정 단언**("재요청 없음" 등)은 유계 시간 대기가 불가피                                                  | 이유 주석 + 유계(무한정 대기 X)                     |
| 7    | role·name이 없으면 `getByTestId`                                                                           | 접근 가능한 role·name이 정말 없을 것 + 이유         |

## 관통 프레임 — 설계로 없애고, 남은 것만 감당하되 포기 목록을 남긴다

문제를 만나면 **먼저 설계로 없앨 수 있는지** 본다(격리로 원인 제거). 못 없앤 것만 폴백·마스킹·재시도로 감당하되, **무엇을 포기했는지 기록**해 "이건 왜 안 잡혔지"를 나중에 추적할 수 있게 한다. "덜 정확한 다수 vs 정확한 소수"에서는 정확한 소수를 택한다.

## 게이트

프로젝트의 검증 명령(이 레포: `pnpm check` — test·lint·typecheck·중복검사·build)이 통과하고, **기존 테스트가 그대로 유지**되며, 비활성화(`it.skip`·주석)된 테스트가 없어야 한다.

## 리포트 형식

- **층 판별 결과** — 잘못 골랐으면 그 지적을 첫 항목으로.
- **원칙별 위반 후보** — 어긋난 곳과 **근거 한 줄**. 해당하는 원칙만.
- 파일은 수정하지 않고 후보만 제안한다.
