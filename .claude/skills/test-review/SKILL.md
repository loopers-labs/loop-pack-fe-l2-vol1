# /test-review 테스트 검증 스킬

테스트가 **공개 동작**을 붙잡고 있는지, 초록불이 거짓말하지 않는지 확인한다.
테스트를 고칠지 구현을 고칠지는 사람이 정한다. 이 스킬은 그 판정 재료를 만든다.

---

## 절차

### 1. 범위와 의도 확보

**범위** — 호출자가 파일 목록을 넘겼으면 그것. 단독 호출이면 `git diff main...HEAD --name-only`와 `git status --short`에서 고른다. 여기서 정한 **대상 실행 테스트** 목록이 3·4단계의 단위다.

- 실행 테스트: Vitest `{scripts,src,tests}/**/*.test.{ts,tsx}` · Playwright `e2e/**/*.spec.{ts,tsx}`
- 지원 파일: `{tests,e2e}/**` 중 실행 테스트가 아닌 것 (헬퍼 · MSW 핸들러 · 픽스처). 바뀌었으면 바뀐 export를 참조하는 실행 테스트를 대상에 더한다 (`setupFiles` 경유 포함)
- 하네스: `vitest*.ts` · `playwright*.ts`. 바뀌었으면 `pnpm vitest list --filesOnly` · `pnpm test:e2e --list`가 찾은 파일이 실행 테스트 패턴에 맞는 파일 전부인지 본다. 빠진 파일이 있으면 `[blocker]`

각 테스트가 검증하는 구현도 같이 읽는다.

**의도** — 무엇을 지키기로 했는지의 출처. 대상 테스트나 그 구현을 직접 언급하는 문서만 인정한다.

1. 사용자가 명시한 것
2. `docs/rfc/*test-plan.md`의 검증 표
3. `specs/*.spec.md`의 완료 조건 중 공개 동작인 것 (정적 검사 · 문서 · 수동 확인 조건은 제외)
4. 없거나 하나로 못 정하면 구현에서 공개 동작 후보를 표로 뽑아 AskUserQuestion으로 확인

확인된 의도가 없으면 2단계의 의도 표 대조만 건너뛰고(린트는 항상 돌린다) 보고에 "의도 출처 없음 — 누락 검사 생략"을 적는다.

### 2. 누락 검사

먼저 `pnpm lint`를 돌린다. `.skip` · `.only` · 주석 처리 · 단언 없음 · truthiness 단언은 린트가 잡으며 에러 하나가 `[blocker]` 하나다.

**린트가 닿지 않는 파일이 있다.** 실제 범위는 `eslint.config.mjs`의 테스트 블록이 정본이고, 오늘 기준 `scripts/**` · `e2e/**`에는 어느 조항도 걸리지 않는다(`src/app/api/**`는 truthiness만 빠져 있다). 그 파일들은 같은 항목을 이 스킬이 눈으로 대조해 같은 심각도로 올린다. 린트 통과를 그 파일들의 통과로 적지 않는다.

그다음 diff에서 삭제된 테스트 선언을 찾는다. 삭제는 그 행의 마지막 대응 테스트가 사라졌을 때만 `[blocker]`.

의도 표의 행마다 대응하는 테스트를 찾는다. 없는 행은 `[blocker]`.

### 3. 테스트별 진단

대상 실행 테스트에서 추가·수정된 테스트마다 한 문장을 적는다: **"이 테스트가 빨간불이 되면 나는 무엇을 알게 되나?"**

답이 "코드가 잘 돈다" · "컴포넌트가 렌더된다" · "누가 구조를 바꿨다" 류면 지적한다. 원인은 셋 중 하나다.

- 구현 세부사항 단언 — 스토어 필드, 훅 내부 상태, 함수 호출 여부. 판별: 이걸 바꿨을 때 사용자가 알아차리나?
- 무의미 단언 — `toBeTruthy` · `length > 0` · 단언 없음
- 이름 — 조건과 결과가 없음

심각도는 고정이다: 무의미 단언·단언 없음 `[blocker]`, 구현 세부사항 `[개선]`, 이름 `[nit]`. 답이 불명확한 테스트만 보고한다.

### 4. 거짓 초록불 검사

통과해도 아무것도 지키지 않는 단언을 찾는다. 표의 모든 행을 대상 테스트 전부에 대조하면 끝. 관찰 자체가 불가능한 레이아웃 · CSS와 검증 대상 mock은 `[blocker]`, 나머지는 `[개선]`.

| 거짓말    | 신호                                                                          | 왜                                                                                                      |
| --------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 레이아웃  | jsdom에서 `toBeVisible`로 가려짐·잘림·화면 밖을 판정                          | jsdom은 레이아웃을 계산하지 않는다. `display:none`·`hidden`까지만                                       |
| CSS       | Vitest/jsdom에서 클래스로 준 스타일을 단언                                    | Vitest `css: false` — 클래스 스타일은 적용되지 않는다                                                   |
| 낡은 mock | 핸들러·픽스처가 실제 응답 타입에 묶이지 않음 · 공용 응답·엔티티를 테스트마다 리터럴로 다시 씀 (시나리오별 override는 정상) | 서버가 바뀌어도 초록불. 타입으로 먼저 걸리게 하고, 픽스처는 `tests/msw/fixtures.ts` 한 곳         |
| 불가능한 값 | 실제 서버가 보낼 수 없는 조합을 픽스처·핸들러가 만듦 | 그 값으로 통과한 화면은 현실에서 검증된 적이 없다. 타입만 맞으면 통과하므로 사람이 한 번 훑는다 |
| 검증 대상 mock | 지키기로 한 동작을 담은 모듈 자체를 `vi.mock`으로 대체 (프레임워크·브라우저 API 대체는 정상) | 남은 것은 mock이 mock을 확인하는 테스트다 |
| 시간      | `vi.setSystemTime` 없이 `new Date()` · `Date.now()`를 읽음                    | 어느 날 이유 없이 깨진다. `now`를 인자로 받는 쪽이 낫다                                                 |
| 타임존    | `Intl.DateTimeFormat` 직접 사용 · `getHours`류 지역 시간 접근자로 비교 · 포맷터가 고정한 표시 타임존이 화면 의도와 다름 | 로컬과 CI(UTC) 결과가 다르다. **`toLocale*` 호출 자체는 린트가 막으므로 다시 지적하지 않는다** (5단계 승격) |
| 순서      | 앞 테스트가 남긴 스토어·localStorage에 기댐                                   | 단독 실행하면 깨진다. 리셋은 jsdom에서만 `vitest.setup.ts`가 한다                                       |
| 비동기    | 고정 시간 대기, 같은 전이의 단언을 전부 `waitFor`로 감쌈                       | 전이마다 대표 조건 하나만 기다린다 — 등장 `findBy` · 제거 `waitForElementToBeRemoved` · 비-DOM `waitFor` |

### 5. 실행 환경별 추가 검사

대상에 `e2e/**`나 `scripts/**`가 있을 때만 돈다. 없으면 이 단계를 건너뛰었다고 적는다.

조항의 정본은 `.claude/rules/testing.md`의 「E2E」·「검사기 테스트」다. 아래 표는 **무엇을 신호로 보고 어떤 심각도로 올릴지**만 정한다.

**E2E (`e2e/**`)**

| 확인할 것 | 지적 조건 |
| --- | --- |
| 시작 경계 | 테스트가 `page.goto` 없이 앞 테스트가 남긴 화면에서 시작한다 → `[blocker]` |
| 최종 결과 단언 | 토스트 문구·로딩 표시·URL만으로 성공을 판정한다. 주문 번호·목록 항목 같은 결과가 없다 → `[개선]`, 그 단언이 유일하면 `[blocker]` |
| storageState | 로그인 자체를 검증하는 테스트가 저장된 세션으로 시작한다 → `[blocker]`. 그 테스트는 `test.use({ storageState: { cookies: [], origins: [] } })`로 빠져나온다 |
| 계정·데이터 격리 | 워커별 계정을 쓰지 않거나, 남이 만든 데이터에 기대는 단언(전체 개수 등)을 쓴다 → `[blocker]` |
| 조건 대기 | `waitForTimeout`·`setTimeout` 고정 대기, 시계에 의존하는 재현(TTL 단축) → `[blocker]` |
| flaky 대응 | 재시도·대기 시간 증가·단언 약화로 초록불을 만든 흔적 → `[blocker]`. 원인과 trace 근거를 요구한다 |
| 선택 기능 | 시각 회귀·탐색형 에이전트·healer의 산출물인데 마스킹으로 줄어든 범위와 바뀐 단언의 기록이 없다 → `[개선]`. 이 행은 그 산출물이 대상에 있을 때만 적용한다 (도구 도입 권고가 아니다) |

**검사기 (`scripts/**`)**

| 확인할 것 | 지적 조건 |
| --- | --- |
| 공개 동작 | 함수 반환값만 보고 실제 명령의 **종료 코드·진단 출력**을 단언하지 않는다 → `[blocker]` |
| 실패 종류 | 통과 · 위반 · 입력 없음(미측정) 중 실행하지 않은 경우가 있다 → `[blocker]`. 둘이 같은 종료 코드를 쓰는데 무엇으로 갈리는지 단언하지 않는다 → `[개선]` |
| 진단 | 출력에 원인을 특정하는 값(초과량 · 누락 대상 이름)이 없다 → `[개선]` |
| CI 연결 | 테스트가 부르는 명령이 workflow가 실제로 부르는 명령과 다르다 → `[blocker]` |

### 6. 뮤테이션 검수

**대상은 하나다** — 새로 추가된 대표 테스트, 또는 3단계에서 답이 불명확했던 테스트. 해당하는 것이 없으면 하지 않았다고 적는다.

그 테스트가 진짜로 무엇을 잡는지는 구현을 깨뜨려 봐야 안다. 그것이 지킨다고 주장하는 구현을 **한 줄** 되돌리고 그 테스트 파일만 실행한다.

- 빨간불이면 통과. 초록불이면 그 테스트는 아무것도 지키지 않는다 → `[blocker]`.
- 깨뜨린 자리 · 실행 명령 · 결과를 보고에 적고 **원복한 뒤 다시 초록불을 확인한다.** 그 확인까지가 이 단계다.
- 전수 확인이 필요하면 `pnpm test:mutation`(Stryker, 느림)을 별도로 돌린다.

## 지적의 근거

지적의 근거는 **직접 읽은 파일에서 인용해 확인한 것만** 쓴다. 다른 파일·문서에서 본 명령·설정·값을 대상 파일의 사실로 옮기지 않는다 — CI 실행 명령은 workflow에서, 실행 옵션은 그 도구의 설정 파일에서 직접 읽는다. 확인하지 못한 전제는 지적으로 만들지 말고 미검토 범위에 적는다.

## 결과 형식

```
## Test Review 결과

**판정: PASS / FAIL** (blocker가 하나라도 있으면 FAIL)

### 의도 출처
- {사용자 명시 | docs/rfc/... | specs/... | 사용자 확인 | 없음 — 누락 검사 생략}

### 실행한 검사
- 린트: {통과/에러 수} — 하네스 밖(`scripts/**` · `e2e/**` · `src/app/api/**`)은 눈으로 대조
- 환경별 추가 검사: {E2E · 검사기 · 해당 없음}
- 뮤테이션 검수: {깨뜨린 자리 → 결과 → 원복 확인 | 하지 않음}

### 누락
- {의도 표 행} — 테스트 없음
(없으면 "없음")

### 지적 사항 (심각도순)
- `[blocker]` {파일:줄} — {문제} → {고칠 방법}
- `[개선]` {파일:줄} — {문제} → {고칠 방법}
- `[nit]` {파일:줄} — {문제} → {고칠 방법}
(없으면 "없음")

### 미검토 범위
- {돌리지 못한 검사, 대상 테스트가 닿지 않는 경로}
(없으면 "없음")
```
