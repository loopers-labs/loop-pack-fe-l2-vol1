# test-design-review

테스트에는 층이 둘이다. **의도**(무엇을 지킬 것인가 · 단언의 내용 · 모킹 경계)와 **실행**(셋업 · 픽스처 · 핸들러 · 셀렉터). 이 스킬은 의도만 다룬다. 의도를 정하지 않고 테스트를 맡기면 현재 동작이 버그까지 포함해 정답으로 굳는다.

**출력은 후보 · 검증 층 · 제외 이유까지다.** 무엇을 단언할지와 어디까지 모킹할지는 작성자가 정한다.

## 입력 — 셋 중 무엇으로 와도 된다

| 들어온 것 | 후보를 어떻게 얻나 |
| --- | --- |
| 시나리오·스펙 | 준 대로 쓴다 (구현 전) |
| 파일·기능 지정 | 그 코드의 진입점에서 사용자가 겪는 결과를 뽑는다 — 화면 전이 · 저장 · 요청 · 종료 코드 |
| 아무것도 없음 | `git diff`의 변경에서 이 변경이 새로 만들거나 바꾼 동작만 뽑는다 |

코드에서 뽑았으면 후보에 근거(파일:줄)를 적는다. 작성자가 준 의도와 코드가 다르면 둘 다 적고 어느 쪽이 맞는지 묻는다. 스펙의 완료 조건 중 **정적 검사 · 문서 · 수동 확인** 항목은 후보가 아니다.

셋 다 비면 — 아직 코드도 스펙도 없는 기능이면 — 후보를 지어내지 않는다. 「입력 부족」에 필요한 자료를 적고 끝낸다: 그 기능이 성립하는 조건, 끝났을 때 사용자가 보는 것, 실패했을 때 할 수 있는 일.

## 절차

1. `.claude/rules/testing.md`를 읽는다. 픽스처 · 격리 · E2E 조항은 그 파일이 정본이다.
2. 공개 동작 후보를 뽑는다. 기준은 하나다 — **이게 깨지면 사용자가 알아차리는가.** 스토어 필드 · 훅 내부 상태 · 함수 호출 여부는 후보가 아니다.
3. 후보마다 층을 정한다. 아래 표에서 **그 결과를 실제로 관찰할 수 있는 가장 싼 층**을 고른다.
4. 후보마다 제외 이유나 보류 이유를 적는다. 빈도가 아니라 관찰 가능성과 실패 비용으로 가른다.
5. 작성자가 정할 것을 질문으로 남긴다 — 단언 문구, 모킹 경계, 붙이지 않을 흐름.

후보마다 층과 그 층이 못 보는 부분이 채워지고, 제외·보류마다 이유가 달리고, 단언 문구와 모킹 경계가 작성자 몫으로 남으면 검토가 끝난다.

## 층 판정 — 그 층이 못 보는 것으로 정한다

| 층 | 실제로 보는 것 | 못 보는 것 |
| --- | --- | --- |
| unit-node (`*.test.ts`) | 순수 함수 · parser · store 액션의 입출력과 경계값 | 화면, 사용자의 조작 순서 |
| unit/integration-jsdom (`*.dom.test.{ts,tsx}`) | 렌더 결과 · 조작 · 상태 전이 · MSW 경계까지의 요청 | 레이아웃 · 클래스로 준 CSS · 실제 네비게이션 · 쿠키/미들웨어 |
| Playwright (`e2e/**/*.spec.ts`) | 실제 브라우저의 이동 · 쿠키 · 미들웨어 리다이렉트 · 서버 렌더 HTML | 싼 값이 아니다. 여기 올린 만큼 CI 시간과 유지비를 낸다 |
| 검사기 (`scripts/**/*.test.ts`) | 실행한 명령의 **종료 코드와 진단 출력** | 그 스크립트를 부르는 workflow의 실제 조건 |

- 브라우저가 있어야만 성립하는 것(쿠키 · 리다이렉트 · 초기 HTML)만 E2E에 올린다. 통합 테스트가 이미 보는 결과는 통합에 둔다.
- 후보를 싼 층으로 내릴 때 줄어드는 관찰 범위를 적는다. 그것이 **포기 목록**이다.

## 후보를 찾는 자리

- **경계값**: 0 · 1 · 최댓값 · 빈 문자열 · 목록의 마지막 페이지. 갈리는 지점마다 양쪽.
- **실패 경로**: 요청 실패 · 권한 없음 · 빈 결과. 사용자가 다음에 무엇을 할 수 있는지까지가 동작이다.
- **되돌리기**: 잘못 넣은 값이 저장되지 않고 무엇으로 복원되는가.
- **격리**: 로그인 · 로그아웃 · 다른 계정 · 새로고침에서 남는 것과 사라지는 것.
- **불가능한 조합**: 실제 서버가 절대 보내지 않는 값은 후보가 아니다 (`testing.md` 「픽스처와 핸들러」).

## 결과 형식

```
## Test Design Review 결과

### 의도 출처
- {사용자 명시 | specs/... | git diff | 없음 — 후보만 제시}

### 공개 동작 후보
| 후보 | 이게 깨지면 사용자가 겪는 일 | 층 | 이 층이 못 보는 부분 | 근거 |
| --- | --- | --- | --- | --- |

### 제외·보류
| 후보 | 제외/보류 | 이유 |
| --- | --- | --- |

### 작성자가 정할 것
- 단언 문구: {무엇으로 확인할지의 선택지}
- 모킹 경계: {어디까지 실제로 돌릴지의 선택지}
- 붙이지 않을 흐름: {포기 목록 후보}

### 입력 부족
- {받지 못해 판단하지 못한 것과 필요한 자료}
```

## 하지 않는 것

- 테스트 코드 · 픽스처 · 핸들러를 쓴다 → 의도가 확정된 뒤의 일이다. 작성된 결과 검수는 `test-review`.
- 단언 문구와 모킹 경계를 대신 확정한다 → 선택지와 각각이 지키는 범위만 적는다.
- 커버리지 숫자를 목표로 후보를 늘린다 → 후보는 관찰 가능성과 실패 비용으로만 는다.
- E2E 포함·제외를 로그 빈도로 판정한다 → 세션 비율과 관측 한계는 `e2e-scope-review`가 본다.
