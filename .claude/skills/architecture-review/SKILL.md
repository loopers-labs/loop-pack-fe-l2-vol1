# architecture-review

폴더 구조와 import 그래프를 FSD 기준에 비춰 점검하는 스킬.
**출력은 진단과 근거까지다. 코드 수정안(diff, 구현 지시, 이동 목적지)은 제시하지 않는다.**

## 판단 기준: FSD 레이어와 나누는 질문

레이어는 위에서 아래로 `app → pages → widgets → features → entities → shared`이며, **자기보다 아래 레이어만 import할 수 있다.**

| 레이어 | 정의 | 이 파일이 여기 있어도 되는가를 묻는 질문 |
| --- | --- | --- |
| app | 앱 전역 관심사: 라우터, providers, 전역 스토어 초기화, 전역 스타일. 슬라이스 없이 세그먼트로 구성 | 앱 전체에 딱 한 번 존재하는 설정인가? |
| pages | 라우트 하나에 대응하는 화면 단위. UI 구성과 데이터 연결 | 이 코드는 특정 화면에서만 의미가 있는가? |
| widgets | 여러 페이지가 재사용하거나 페이지 안에서 독립적인 큰 UI 블록 | 둘 이상의 페이지가 이 조합 블록을 그대로 쓰는가? |
| features | 사용자가 수행하는 주요 상호작용. 모든 것이 feature일 필요는 없다 | 사용자의 행위인가? 표현만 있는 것은 아닌가? |
| entities | 비즈니스가 쓰는 용어 그대로의 실세계 개념(상품, 장바구니 등). 데이터 형태, 검증, 조회, 표현 | 이 코드가 답하는 질문이 "X가 무엇인가"인가? |
| shared | 도메인을 모르는 기반: HTTP 클라이언트, 범용 UI, 유틸. 슬라이스 없이 세그먼트로 구성 | 비즈니스 용어를 하나도 몰라도 성립하는 코드인가? |

**import 규칙**

1. 하위 레이어는 상위 레이어를 import하지 않는다. entities가 features를, shared가 무엇이든 도메인 코드를 알면 위반이다.
2. 같은 레이어의 다른 슬라이스를 직접 import하지 않는다. 두 슬라이스가 협력해야 하면 상위 레이어에서 조합한다.
3. 다른 슬라이스는 Public API(슬라이스 루트 진입점)로만 import한다. 내부 파일 직접 참조(딥 import)는 캡슐화 위반이다. 같은 슬라이스 안에서는 상대 경로를 쓴다.

**세그먼트**는 목적(ui, model, api, lib, config)을 드러내야 하며, components, utils처럼 파일 종류를 반복하는 이름은 냄새다.

## 이 프로젝트의 매핑 (공인 결정, 위반으로 판정하지 않는다)

- pages 레이어 폴더는 `src/_pages`(Next 예약어 회피). widgets는 쓰지 않기로 결정했고, `_pages`는 조합 전용으로 제한한다(상태, 파서는 features에).
- entities 간 참조는 `@x` 공인 통로로만 허용된다. `@x`를 entities 밖에서 쓰면 위반이다.
- shared는 index 없이 파일 경로로 직접 import한다.
- 루트 `tests/`는 레이어 밖 통합 테스트 자리다. 레이어 규칙을 적용하지 않는다.
- `src/app/api`는 mock 백엔드(네트워크 건너편)라 점검 대상이 아니다. 단, 프론트 코드가 이를 import하면 위반이다.
- features 슬라이스 이름은 기능이 다루는 도메인 대상(product, cart, wishlist)으로 짓는다.

## 절차

1. 실제 구조를 수집한다: `src/` 트리, `@/` alias import 전수, 레이어 경계를 넘는 상대 경로 import, 동적 `import()` 전수.
2. `pnpm lint`의 하네스 경고를 확인한다. 하네스가 잡은 것은 결과만 인용하고 재분석하지 않는다.
3. 위 판단 기준으로 아래 항목을 점검한다.
4. 보고 형식대로 출력한다.

## 점검 항목

- **레이어 적합성**: 각 파일에 위 표의 질문을 적용했을 때 현재 레이어가 맞는가. 이름은 중립인데 내용이 특정 도메인이나 특정 화면을 아는 경우까지 본다.
- **import 방향**: 하위가 상위를 아는 경로가 있는가. entities가 features를 render props나 children으로 받는 척하며 실질적으로 전제하는 설계 포함.
- **슬라이스 격리**: 같은 레이어 슬라이스 간 직접 의존. 협력이 필요하면 상위 조합으로 풀었는가.
- **Public API**: 진입점이 선별 수출인가 전부 재수출(barrel)인가. 딥 import가 있는가. 미사용 index.ts, 빈 폴더가 있는가.
- **shared 오염**: 비즈니스 용어를 아는 코드가 shared에 있는가.
- **응집**: 한 기능을 지우려면 몇 개 슬라이스를 건드리는가. 함께 바뀌는 코드가 흩어져 있지 않은가.

## 보고 형식

```markdown
## 위반
- {파일}: {어긴 기준} — {구조 관점에서 왜 문제인가}

## 회색 지대 (기준으로 판정 불가)
- {대상}: {가능한 해석 A/B} — {판단에 필요한 질문}

## 구조 냄새 (위반은 아님)
- {대상}: {관찰} — {방치 시 커지는 비용}
```

- 각 항목에 파일 경로를 명시한다. 추측으로 위반을 만들지 않는다(불확실하면 회색 지대로).
- 수정 방법, 이동 목적지, 코드 예시는 쓰지 않는다. 어떤 기준과 어떻게 충돌하는지까지만.
- 위반이 없으면 "위반 없음"과 확인한 범위를 말한다.
