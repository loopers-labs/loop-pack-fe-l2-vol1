# Architecture Review

코드의 폴더 이름을 평가하지 말고 실제 import, 소비자, 상태 소유권, 변경 반경을 평가한다.
자동 검사 결과를 사실의 출발점으로 삼되 설계 판단을 대신하게 하지 않는다.

## 절차

1. `pnpm architecture:evidence`를 실행해 현재 트리의 결정적 검사 결과와 수동 검토 항목을 수집한다. 커밋 직전에는 `pnpm architecture:check:staged`로 Git index 스냅샷도 확인한다.
2. `git diff --cached --stat`과 `git diff --cached`를 읽는다. staged 변경이 없으면 작업 트리 diff를 읽고 그 사실을 밝힌다.
3. 변경된 코드의 직접 소비자와 import 경로를 `rg`로 확인한다. 파일명이나 RFC 주장만으로 소비 범위를 추정하지 않는다.
4. 변경이 인용하는 RFC 결정과 구현을 양방향으로 대조한다. 문서→코드뿐 아니라 코드→문서의 누락도 찾는다.
5. `references/review-rubric.md`의 순서로 검토한다.
6. 재현 가능한 지적만 finding으로 작성한다. 추정은 질문 또는 확인 필요 항목으로 분리한다.

## 판정 원칙

- 규칙 위반과 설계 트레이드오프를 구분한다.
- 현재 요구사항에서 발생하지 않는 가상 확장성만으로 변경을 요구하지 않는다.
- 줄 수와 파일 수는 독립된 근거일 때만 사용한다. 같은 원인을 다른 숫자로 중복 계상하지 않는다.
- 테스트도 슬라이스 외부 소비자다. 테스트라는 이유로 Public API 우회를 허용하지 않는다.
- 과거 결정 기록과 현재 확정 문장을 구분한다. 번복 이력을 지우지 말되 현재 결론은 한 가지여야 한다.
- 자동 검사가 통과해도 에러 복구 UX, 상태 소유권, 삭제 시나리오는 별도로 판단한다.

## 출력 형식

다음 순서로만 작성한다.

1. **판정**: 승인 / 수정 후 승인 / 차단 중 하나와 한 문장 근거
2. **Findings**: 심각도 순. 각 항목에 파일과 줄, 확인한 사실, 실제 영향, 판정 근거를 포함
3. **잘한 결정**: 코드 증거가 있는 항목만 기록
4. **수동 검증 필요**: 브라우저 재현처럼 정적 검사로 증명하지 못한 항목
5. **커밋 전 명령**: 실제 실행 결과와 실패 여부

finding이 없으면 없다고 명시한다. 코드 수정은 사용자가 요청한 경우에만 수행한다.
