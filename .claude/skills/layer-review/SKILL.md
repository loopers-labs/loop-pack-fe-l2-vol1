# /layer-review — 레이어 분리 검증 스킬

**목적:** 컴포넌트의 관심사가 적절히 분리되었는지, Hook의 역할이 명확한지를 AI가 리뷰한다.
판별만 한다. 수정 여부와 방법은 사용자가 직접 결정한다.

**추측하지 말고 실제 파일을 읽어 확인한다.** 근거 없는 발견을 만들지 않는다.

---

## 절차

1. 경로를 지정하면 해당 경로의 파일을 읽는다. 지정하지 않으면 `src/` 안의 `.ts` · `.tsx` 파일을 모두 읽는다.
2. `CLAUDE.md`를 읽어 프로젝트 규칙을 확인한다.
3. 각 코드 블록의 관심사를 분류한다 (UI / 상태 / 서버 통신 / 도메인 로직).
4. 현재 레이어가 아래 기준에 맞는지 판별한다.
5. Hook이 있다면 책임이 명확한지 추가 검증한다.
6. 결과를 표로 보고한다.

---

## 레이어별 기준

| 레이어 | 있어야 할 것 | 있으면 안 되는 것 |
|--------|------------|----------------|
| `components/` | JSX, 이벤트 바인딩, 스타일, 단순 이벤트 핸들러(setter 직접 호출), 작은 파생값(const 한 줄·이 화면 전용) | API 호출, 복잡한 도메인 규칙, 서버 응답 세부 구조에 직접 접근 (service에서 변환하지 않은 중첩 참조) |
| `hooks/` | 상태 관리, 도메인 로직, 서버 상태 조합, 유효성 검증 결과 상태 | JSX 반환, 통신 구현체(fetch·axios 등) 직접 호출 — service 함수를 통할 것 |
| `services/` | API 호출 함수, 요청/응답 변환, 에러 변환 | React state, UI 코드 |
| `utils/` | 순수 함수 | 상태, 사이드이펙트, React 의존성 |

## Hook 책임 검증

`hooks/` 레이어의 각 Custom Hook에 추가로 판별한다.

- `use`로 시작하는가? (`productFilter` ❌, `useProductFilter` ✅)
- 이름이 역할을 설명하는가? (`useData` ❌, `useProductFilter` ✅)
- 한 문장으로 설명되는가? ("그리고"가 두 번 이상 → 분리 후보)
- 함께 바뀌는 것끼리 같은 hook에 있는가?
- 다른 이유로 바뀌는 것이 한 hook에 섞여 있지 않은가?
- 파생값을 `useState`로 들고 있지 않은가?
- `useEffect`가 외부 시스템 동기화 목적인가?
- JSX를 반환하지 않는가?
- 상태만 있고 도메인 로직·파생값·사이드이펙트가 전혀 없지 않은가? (오버 추상화 후보)

## 분리하지 않은 결정

"여긴 분리 안 한다"는 결정에 한 줄 근거가 있는가?

근거 예시: "한 곳에서만 쓰임", "단순 이벤트 바인딩", "이 화면 전용 UI"

---

## 결과 형식

```
## Layer Review 결과

검토 파일: {N}개

| 위치 | 관심사 | 분리 후보 | 분리 이유 | 분리하지 않을 근거 |
|------|--------|-----------|-----------|-------------------|
```

- 분리하는 것: 분리 후보 + 분리 이유 채움, 분리하지 않을 근거는 —
- 분리 안 하는 것: 분리 후보 —, 분리 이유 —, 분리하지 않을 근거 채움

---

## 판별 정책

- 코드를 자동으로 고치지 않는다. 판별만 한다.
- 통과로 판단한 항목도 반드시 1줄 근거와 함께 적는다.
- 고치지 않기로 한 이슈도 이유와 함께 "보류 판단"에 적는다.
- 이슈가 아닌데 "이슈다"라고 하지 않는다. 근거 없는 발견을 만들지 않는다.
