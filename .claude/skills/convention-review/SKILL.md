# Convention Review

diff 를 이 프로젝트의 합의된 규칙으로 판정한다. **결과물은 위반 판정이지 코드
수정안이 아니다.** 패치나 "이렇게 바꾸세요"를 내지 않는다. "무엇이 어느 규칙을
어떻게 어겼는가"만 낸다.

## 우선순위 (겹치는 스킬과의 관계)

레이어 경계·import 방향·public API 규약은 `architecture-review` 가 맡는다. 여기서
구조를 판정하지 않는다. 반대로 네이밍·훅 사용·상태 관리·주석 같은 코드 레벨 규칙은
이 스킬이 맡는다. 두 축이 겹치는 지적이 나오면 각자 자기 축만 낸다.

## 리뷰 대상

리뷰 대상 diff 안의 **추가·수정된 줄만** 판정한다. 대상이 PR 이면 base 브랜치와
head 사이의 diff 가 대상이다. 어느 브랜치를 base 로 볼지 모르겠으면 추측하지 말고
그 사실을 밝힌다.

- diff 에 없는 파일은 지적하지 않는다. 리뷰가 레포 전체 감사로 번지면 무엇을
  고쳐야 PR 이 통과하는지 알 수 없어진다.
- 판정에 맥락이 필요하면 레포 파일을 읽어도 된다. 다만 **읽은 것은 근거로만 쓰고
  지적 대상으로 삼지 않는다.**
- 삭제된 줄은 지적하지 않는다. 이미 사라진 코드다.

## 판정 기준의 출처

아래 문서를 읽고 **거기 적힌 기준으로만** 판정한다. 규칙 본문을 이 파일에 옮겨
적지 않는다. 문서가 바뀌면 판정도 따라 바뀌어야 하기 때문이다.

- `CLAUDE.md`
- `.claude/rules/code-quality.md`
- `.claude/rules/react.md`

이 세 문서에 근거가 없는 지적은 내지 않는다. 일반적으로 옳은 조언이라도 마찬가지다.

## 규칙 문서에 없는 합의 규칙

아래 셋은 위 문서에 아직 문장으로 없지만 이 프로젝트가 합의한 규칙이다. 문서화가
안 됐을 뿐이므로 동일하게 판정한다.

### URL 상태 동기화

공유·새로고침·뒤로가기에서 살아남아야 하는 화면 상태(필터·정렬·페이지·검색어)는
**URL 을 단일 출처로 둔다.** 같은 값을 URL 과 컴포넌트 state 양쪽에 두고 서로
맞추지 않는다. 출처가 둘이면 어느 쪽이 맞는지 코드로 알 수 없다.

```
URL 에서 읽어 그대로 쓴다                          ✅
URL 값을 useState 초깃값으로 복사하고 양방향 동기화  ❌  출처가 둘
```

### custom hook 분리 기준

컴포넌트가 표현 외의 일(파싱·동기화·구독·여러 상태의 조합)을 들고 있으면 hook 으로
뺀다. **판단 기준은 재사용 여부가 아니라 책임이다.** 한 곳에서만 쓰여도 뺀다.

### 서버 응답을 로컬 상태에 복사하지 않는다

서버에서 받은 데이터를 별도의 로컬 스토어나 state 에 옮겨 담지 않는다. 쿼리
캐시가 이미 단일 출처인데 복사본을 만들면 둘이 어긋나고, 무효화·재요청이 복사본에
반영되지 않는다. 로컬 스토어에는 서버가 모르는 값(선택 여부·열림 상태 등)만 둔다.

## 지적하지 않는 것

아래는 지적 대상이 아니다. 이미 기계가 결정적으로 막고 있거나, 판정 기준이 없다.

- **린터·타입체커·구조 검사기가 막는 것.** 이 저장소는 커밋 전에 lint·typecheck·
  구조 검사를 돌린다. 그 도구가 잡는 항목을 다시 지적하면 통과한 코드에 대해
  틀린 말을 하는 셈이다. 여기서는 **사람이 읽어야만 알 수 있는 위반**만 낸다.
- **일반론.** "가독성을 높이세요", "성능을 고려하세요" 처럼 규칙 문서에 대응하는
  문장이 없는 조언.
- **포맷팅.** 들여쓰기·줄바꿈·따옴표는 포매터가 정한다.
- **테스트가 없다는 지적.** 무엇을 테스트할지는 이 리뷰의 판정 범위 밖이다.
- **취향 차이.** 규칙 문서가 어느 쪽도 정하지 않은 선택지.

## 판정 규율

- **근거 주석이 달린 예외는 존중한다.** 왜 그렇게 했는지 적혀 있으면 판단이 이미
  이뤄진 코드다. 그 근거가 틀렸다고 말하려면 근거를 반박해야지, 규칙 위반으로
  분류하지 않는다.
- **diff 에 안 보이는 것을 추측해서 지적하지 않는다.** "아마 이 함수는 …할
  것이다" 로 시작하는 지적은 내지 않는다. 확인이 필요하면 파일을 읽고 확인한 뒤
  낸다.
- **확신이 없으면 내지 않는다.** 틀린 지적 하나가 맞는 지적 열의 신뢰를 깎는다.
- **같은 규칙의 반복 위반은 하나로 묶는다.** 같은 지적을 파일마다 늘어놓지 않고
  대표 위치 하나에 나머지 위치를 함께 적는다.

## 출력 형식

출력은 PR 코멘트로 그대로 게시된다. 리뷰 결과 본문만 낸다. 무엇을 할 계획인지,
어떤 파일을 읽었는지 같은 진행 보고는 코멘트에 남을 내용이 아니다.

지적이 없으면 "위반 없음" 한 줄만 낸다. 억지로 채우지 않는다. 이 리뷰는 참고용이라
머지를 막지 않으므로, 건수를 채우려고 확신 없는 지적을 보태면 손해만 남는다.

지적마다 아래 네 항목을 모두 적는다. 하나라도 못 채우면 그 지적은 내지 않는다.

```markdown
### N. <한 줄 요약>

- **위치**: `경로/파일.tsx:120` (같은 위반이 더 있으면 여기 함께 적는다)
- **근거 규칙**: `.claude/rules/react.md` > "파생 가능한 값은 계산한다"
  > 인용문 한두 줄
- **판정**: 왜 이 코드가 그 규칙을 어겼는지. 코드가 실제로 하는 일을 짚는다.
- **확신도**: 높음 | 중간 | 낮음
```

**근거 규칙은 반드시 문서의 실제 문장을 인용한다.** 인용할 문장을 못 찾으면 그
지적은 규칙에 근거가 없다는 뜻이므로 내지 않는다.

확신도 기준이다.

- **높음** — 규칙 문장과 코드가 정면으로 어긋나고, 다르게 읽을 여지가 없다.
- **중간** — 규칙에 걸리지만 맥락에 따라 정당화될 수 있다.
- **낮음** — 걸리는 것 같은데 확인 못 한 전제가 있다.

마지막에 요약 한 줄을 붙인다. `총 N건 (높음 a / 중간 b / 낮음 c)`
