# 성능 변경 규칙

위 `paths`는 이 규칙이 자동으로 딸려 오는 자리다. 성능을 이유로 드는 변경이면 경로와 상관없이 이 규칙을 적용한다.

- 순서는 실측 → 관찰 → 가설 → 반증 조건 → 가장 작은 변경 → 같은 조건 재측정이다.
- 지표는 축으로 쪼개고 긴 축에만 개입한다 (LCP = TTFB · 로드 지연 · 다운로드 · 렌더).
- 관찰과 해석을 나눠 적는다. "Hero가 6.14초에 도착했다"는 관찰, "이미지가 LCP를 늦춘다"는 가설이다. 가설에는 무엇이 나오면 틀린 것인지를 붙인다.
- raw는 도구가 주는 최대 정밀도로 남긴다 — Lighthouse는 리포트 화면의 0.1초 단위가 아니라 JSON `numericValue`(ms). 회차별 raw와 중앙값 · 범위를 함께 적는다.
- 판정 기준은 "흔들림 폭보다 큰 변화인가"다. 한 회차 값은 근거가 아니다.
- 빠르다 · 느리다에는 비교 대상을 붙인다. 기준 없는 "충분히 빠름"은 판단이 아니다.
- 비교는 SHA를 뺀 모든 조건이 같을 때만 성립한다. 측정 조건의 정본은 [7주차 측정 절차](../../docs/week-07-performance/measure-protocol.md)다.
- 증거의 종류를 구별한다. 지표(FCP · LCP · CLS)와 사실(요청 URL, 전송 크기, 서버 호출 수, JS 실행 전 HTML)은 서로 다른 것을 증명한다.
- `memo` · `useMemo` · preload · prefetch는 측정 근거와 함께 제안한다. 점수를 올리려고 검증이나 호출을 없애는 변경은 개선이 아니다.
- CI 성능 예산은 새 측정 근거가 있을 때만 움직인다.
- 관찰용 임시 계측은 관찰이 끝나면 지운다.
