# FSD Architecture

먼저 실제 폴더 구조, 경로 별칭, 라우팅 디렉터리를 확인한다. 표준 레이어 이름을 기계적으로 강제하지 말고 프로젝트에서 정한 매핑을 따른다. 이 프로젝트에서는 Next.js의 `src/app`과 FSD App 레이어 `_app`을 구분한다.

## 레이어 책임

위에서 아래 순서로 배치한다.

| 레이어             | 책임                                          |
| ------------------ | --------------------------------------------- |
| `app` / `_app`     | 앱 초기화, 전역 Provider와 설정               |
| `pages` / `_pages` | 라우트 단위 조합                              |
| `widgets`          | 여러 하위 슬라이스를 조합한 독립 UI 블록      |
| `features`         | 사용자의 비즈니스 행위                        |
| `entities`         | 도메인 데이터, 상태와 도메인 UI               |
| `shared`           | 도메인에 종속되지 않은 UI, API 기반, 유틸리티 |

파일 이름이나 현재 소비처만 보지 말고 코드가 소유한 도메인과 책임을 기준으로 배치한다. `shared`에 상품, 회원, 장바구니처럼 특정 도메인 정책이 포함되면 적절한 entity나 feature로 이동할지 검토한다.

## 의존성 규칙

- 상위 레이어에서 하위 레이어만 참조한다.
- 같은 레이어의 다른 슬라이스를 직접 참조하지 않는다.
- 여러 슬라이스의 협력은 공통 상위 레이어에서 조합한다.
- 슬라이스 외부에서는 프로젝트가 정한 Public API만 사용한다.
- Public API는 공개 계약이며, 모든 파일을 다시 내보내는 편의성 barrel과 구분한다.

## Entity 교차 참조

다른 entity의 타입이 꼭 필요할 때만 제공 entity의 `@x/<consumer>` 경로로 필요한 타입을 공개한다. 일반 Public API나 내부 경로로 우회하지 않는다.

- 소비 entity별 파일로 공개 범위를 제한한다.
- 타입만 named export한다.
- UI, store, API 호출 등 런타임 구현은 `@x`로 공개하지 않는다.
- 예외가 늘어나면 `@x`를 확대하기 전에 도메인 소유권이나 조합 위치를 다시 검토한다.

## 리뷰 절차

1. 폴더를 FSD 레이어, 슬라이스, 세그먼트로 매핑한다.
2. import의 출발점과 도착점을 확인해 역방향 및 슬라이스 간 참조를 찾는다.
3. 각 파일의 책임이 레이어 정의와 일치하는지 확인한다.
4. Public API 우회, 과도한 공개, `@x` 오용을 확인한다.
5. 자동화 규칙이 있다면 실제 구조와 같은 정책을 검사하는지 확인한다.

## 결과 작성

- 위반과 설계상 선택을 구분한다.
- 지적마다 파일 근거, 영향, 판단 이유를 제시한다.
- 심각도가 높은 항목부터 정리한다.
- 리뷰 요청에서는 코드를 수정하지 않고 구조적 판단만 제공한다.
- 문제가 없으면 확인한 범위와 남은 위험을 명시한다.
