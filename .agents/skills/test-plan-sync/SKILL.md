# 계획 문서와 코드 동기화

설계 문서를 먼저 쓰고 코드를 나중에 쓰는 작업에서, 둘이 어긋나는 것을 줄이고 어긋났을 때 빨리 찾는다.

문서가 있는데 코드와 다르면 문서는 읽을수록 해롭다. 없는 것보다 나쁘다 — 읽은 사람이 코드를 잘못 이해한 채 판단하기 때문이다.

## 1. 계획 문서를 쓸 때 — 판정 가능한 문장으로 쓴다

각 문장에 대해 **"이 문장을 어긴 코드를 내가 지목할 수 있는가"**를 묻는다. 지목할 수 없으면 다짐이지 계획이 아니다.

| 의도만 쓴 문장 (판정 불가)            | 판정 가능한 문장                                     |
| ------------------------------------- | ---------------------------------------------------- |
| 모킹은 실제 요청 조건을 읽는다        | 서버가 400을 주는 조건은 mock도 400을 준다           |
| 구현 세부사항 대신 사용자가 보는 결과 | `fetch` spy와 라이브러리 콜백 인자를 단언하지 않는다 |
| 접근 가능한 locator를 우선 사용한다   | `getByTestId`를 쓰면 이유를 주석으로 남긴다          |
| 테스트를 적절한 계층에 배치한다       | 같은 단언이 두 계층에 있으면 낮은 쪽만 남긴다        |

특히 **아직 존재하지 않는 코드에 대해 쓴 문장**을 조심한다. mock 핸들러, 테스트 헬퍼, 아직 안 만든 유틸이 여기 해당한다. 짤 때 문장은 만족시키면서 목적은 놓치기 쉽다.

## 2. 코드를 쓸 때 — 항목 번호를 코드에 심는다

계획 문서에 번호가 있으면 대응하는 파일 상단에 남긴다.

```ts
// 계획서 4·5·6·7·8·9·10번 — docs/rfc/week08-test-plan.md
describe('ProductListContent', () => {
```

문서가 코드에서 안 보이면 코드를 고칠 때 문서를 열 계기가 생기지 않는다. 번호가 보이면 근거를 넘어서는 단언을 추가할 때 브레이크가 걸린다.

## 3. 구현 중 결정이 바뀌면 그 자리에서 문서에 적는다

계획서 단계에서는 알 수 없고 코드를 짜야만 드러나는 것이 있다. 그런 판단이 나오면 **구현을 끝낸 뒤 몰아서 대조하지 말고 그때 한 줄 남긴다.**

문서에는 원래 판단을 지우지 말고 **뒤집은 경위**로 남긴다.

```md
**처음 정한 것**: ...
**구현 단계에서 뒤집은 것**: ...
표를 채울 때는 A와 B를 한 덩어리로 봤는데, 짜면서 갈렸다. ...
```

계획 문서를 "코드보다 먼저 커밋하고 끝나는 문서"로 취급하면 갱신할 자리가 사라진다.

## 4. 커밋 전에 대조한다

계획 문서가 있는 작업은 커밋 **전에** 한 번 대조한다. 커밋을 다 하고 나서 찾으면 문서 수정과 코드 수정이 뒤섞인 커밋이 나온다.

대조 순서:

1. 계획 문서의 항목 표를 열고, 각 항목에 대응하는 테스트 파일을 찾는다
2. 항목별로 **문서가 하지 말라고 한 것**을 코드가 하고 있는지 본다 (초과)
3. 항목별로 **문서가 하라고 한 것**을 코드가 안 하고 있는지 본다 (누락)
4. 문서에 없는 판단이 코드에 들어갔으면 그것도 어긋남이다 (파일명, 상수 하드코딩, 헬퍼의 안 쓰는 옵션)

## 5. 어긋났을 때 어느 쪽을 고칠지

**문서를 고친다** — 코드 쪽 판단이 더 정확할 때. 계획서가 알 수 없던 구분이 구현 중에 드러난 경우가 대부분이다. 결론만 갈아끼우지 말고 처음 판단과 뒤집은 경위를 함께 남긴다.

**코드를 고친다** — 문서의 제약이 여전히 옳고 코드가 초과하거나 미달한 경우. "더 꼼꼼해 보여서" 추가된 단언이 여기 자주 걸린다.

**예외로 기록한다** — 코드가 규칙을 벗어나야 할 실제 이유가 있을 때. 이유, 대신 치르는 비용, 그 예외가 성립하는 조건을 함께 적는다.

```md
### 예외 한 곳 — ...

... 대신 치르는 비용이 있다. X가 바뀌면 이 테스트는 초록불인 채로 실제 코드와 어긋난다.
그 회귀는 Y에서 드러나므로, 이 예외는 Y가 함께 있을 때만 성립한다.
```

셋 중 어느 쪽인지는 **작성자가 정한다.** 어긋남을 찾아 선택지와 근거를 제시하는 데서 멈추고, 임의로 한쪽에 맞추지 않는다.

## 6. 판단 근거를 문서에 남길 때

AI가 코드에서 읽어 추정한 근거를 작성자의 판단으로 적지 않는다. 추정이면 추정이라고 적고, 실제 판단이 달랐다면 작성자가 고쳐 쓰도록 남긴다.
