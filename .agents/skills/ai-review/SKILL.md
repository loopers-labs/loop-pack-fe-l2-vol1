# AI 코드리뷰 기준

TRIGGER — AI 리뷰, PR diff 리뷰 요청 시 이 스킬을 로드.

이 스킬은 **지적 목록을 만드는 것까지만** 한다. 무엇을 채택하고 무엇을 기각할지는 작성자가 판단한다.
리뷰 결과는 비결정적이므로 merge를 막는 게이트로 쓰지 않는다(advisory).

## 리뷰 대상

`git diff <base>...<head>` 중 **코드와 설정만** 본다. 문서(`docs/**`, `*.md`, `*.html`)는 제외한다.
문서 표현은 이 기준으로 참/거짓을 가릴 수 없어 지적의 정확도를 떨어뜨린다.

## 기준 — 기존 규칙 재사용

아래 규칙 파일이 이 프로젝트의 합의다. 리뷰 시 그대로 적용한다.

| 파일                                | 범위                                                       |
| ----------------------------------- | ---------------------------------------------------------- |
| `CLAUDE.md`                         | 프로젝트 전반, 네이밍, 검증·완료 기준                      |
| `.claude/rules/code-style.md`       | `any`/`as`/`@ts-ignore`/빈 catch, 기존 유틸 재사용, 네이밍 |
| `.claude/rules/component-design.md` | Client 경계, 파생값 계산, 훅 단일 책임, URL 상태           |
| `.claude/rules/fsd-verification.md` | 레이어 의존 방향, Public API, `entities/@x`                |
| `.claude/rules/testing.md`          | 테스트 계층 선택, role/name locator                        |

## 기준 — CI·workflow (10주차에 추가)

위 규칙은 애플리케이션 코드용이라 workflow를 보지 못한다. 아래를 추가로 묻는다.

### 게이트의 실효성

- 이 PR의 검증으로 **깨진 코드가 base 브랜치에 들어가는 것을 막을 수 있는가**
- 검증 스크립트를 추가했다면 **실제로 빌드·배포하는 명령이 그것을 부르는가**.
  CI step에만 걸려 있고 `package.json`의 `build`에는 없으면 배포 경로는 무방비다
- 조건부 실행이 걸린 check를 required로 두어 **영구 대기(pending)** 하지 않는가
- `continue-on-error`를 쓴 step의 실패가 사람 눈에 보이는 자리에 남는가

### 실행 조건

- `concurrency` 그룹이 **`main`이나 다른 ref의 실행까지 취소하지** 않는가
- path filter가 필요한 검증을 스킵하지 않는가. 분류하지 못한 경로는 안전한 쪽으로 승격되는가
- 감지 job의 실패와 본 job의 실패가 **구분되는가**. 감지가 실패했을 때 조용히 스킵되지 않는가
- step `if` 조건이 단축 평가로 의도하지 않게 항상 참/거짓이 되지 않는가
  (`success()`는 `||`의 오른쪽에 두면 왼쪽이 참일 때 평가되지 않는다)

### 캐시

- cache key가 실제로 hit 될 구조인가. lockfile 해시 등 **변경 주기가 맞는 입력**을 쓰는가
- matrix job이 같은 key를 공유해 한 job의 저장이 다른 job의 hit로 바뀌는 것을 감안했는가

### 권한과 secret

- workflow 또는 job의 권한이 `contents: read` 등 **최소**로 명시돼 있는가
- `pull-requests: write` 같은 쓰기 권한이 **필요한 job에만** 붙어 있는가
- secret 값이 로그, job summary, PR 코멘트에 남을 자리가 있는가.
  **Actions는 모든 step 헤더에 그 step의 `env:`를 나열한다.** 평문 `env:`에 둔 값은 매 step 노출된다
- third-party action이 태그 또는 SHA로 고정돼 있는가
- `pull_request_target`을 쓴다면 fork PR 코드를 checkout해 실행하지 않는가

### 스크립트

- 실패해도 리포트가 남는가. 종료 전에 요약을 먼저 쓰는가
- 외부 호출 실패(API, 파일 없음)가 job 전체를 깨뜨리지 않는가
- 에러를 삼키지 않는가. 조용한 fallback이 실패를 성공처럼 보이게 하지 않는가

## 출력 형식

```
### 🔴 Critical   동작이 깨지거나 게이트가 무력화되는 문제
### 🟠 Major      설계·안전성에 영향을 주는 문제
### 🟡 Minor      코드 품질에 영향을 주는 사소한 문제
```

각 항목은 아래 형식으로 쓴다. **라인 코멘트로 옮길 수 있어야 하므로 파일과 라인이 필수다.**

```
`파일:라인` — 무엇이 문제인가 / 왜 문제인가 / 어떻게 고치는가 (적용한 기준)
```

diff 밖을 짚는 지적은 라인을 달 수 없으므로 `(diff 밖)`으로 표시하고 따로 모은다.

## 하지 않을 것

- 일반론("가독성을 높이세요", "네이밍을 개선하세요")만 있는 지적
- 규칙 파일에 근거가 없는 개인 취향
- 추측으로 "~일 수 있습니다" 수준의 지적. **근거를 코드에서 짚지 못하면 쓰지 않는다**
- 어느 지적이 채택될지 예단하는 서술
