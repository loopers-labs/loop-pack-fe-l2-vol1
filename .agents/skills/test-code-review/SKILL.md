# 테스트 코드 검토

검증하려는 실패를 가장 낮은 비용의 테스트 계층에 배치한다. 파일 종류나 구현 기술이 아니라 테스트의 통과 조건을 기준으로 판단한다.

## 판단 절차

테스트를 작성하거나 검토하기 전에 다음 질문을 순서대로 적용한다.

1. 컴포넌트를 렌더링하지 않고 값이나 상태만 확인해도 되는가?
   - 그렇다면 DOM 없는 단위 테스트를 작성한다.
   - 순수 함수, parser, formatter, validator, Zustand action·selector, reducer, 상태 전이, API 응답 변환이 해당한다.
2. 렌더링된 요소와 상호작용하면 충분한가?
   - 그렇다면 Testing Library와 jsdom을 사용하는 통합 테스트를 작성한다.
   - 텍스트·목록·오류 UI 표시, 폼 입력, 버튼 클릭, 조건부 렌더링, focus, 접근성 상태, hook·store와 화면의 연결이 해당한다.
3. 실제 브라우저의 탐색·렌더링·API가 있어야 재현되는가?
   - 그렇다면 Playwright E2E를 작성한다.
   - 실제 라우팅, URL 변경, 새로고침, 뒤로·앞으로 이동, hydration, 브라우저 API, 네트워크 실패와 복구, 브라우저별 차이, 여러 화면의 핵심 흐름이 해당한다.

React 컴포넌트와 관련된 기능이라는 이유만으로 DOM 테스트를 선택하지 않는다. 내부 계산은 가능한 한 DOM 없이 검증하고, 화면 연결과 사용자에게 보이는 결과만 DOM으로 검증한다.

경계 사례는 사용하는 API 이름이 아니라 검증 범위로 구분한다.

- `localStorage` 데이터의 parser·migration은 DOM 없는 단위 테스트, 저장 결과의 화면 반영은 jsdom 통합 테스트, 새로고침 후 실제 복원은 E2E로 검증한다.
- API 실패에 따른 오류 UI는 요청을 대체한 jsdom 통합 테스트로 검증할 수 있다. 실제 네트워크 지연·요청 취소·페이지 이탈·재시도 흐름이 핵심일 때만 E2E로 올린다.
- 이미지의 속성·대체 텍스트·fallback UI는 jsdom으로 검증하고, 실제 로딩 성공·실패와 브라우저 렌더링은 E2E로 검증한다.
- Clipboard·History 같은 브라우저 API 호출 여부만 보면 mock 기반 통합 테스트를 사용하고, 권한·탐색·브라우저별 동작이 핵심이면 E2E를 사용한다.

## 자율 판단과 질문 기준

- 요구사항, 코드, 기존 테스트에서 검증 경계가 명확하면 질문하지 말고 계층을 선택한다.
- 여러 계층이 가능하더라도 더 낮은 계층으로 같은 실패를 잡을 수 있으면 더 낮은 계층을 선택한다.
- 불확실성이 테스트 계층이나 검증 범위를 실질적으로 바꿀 때만 질문한다.
- 질문하기 전에 관련 코드, 테스트 설정, 기존 테스트와 과제 명세에서 답을 찾는다.
- 질문은 한 번에 하나의 사용자 동작을 묻고 권장안을 함께 제시한다. 테스트 도구를 사용자에게 대신 선택하게 하지 않는다.

좋은 질문:

- “이 기능은 현재 화면의 상태 변경만 검증하면 되나요, 새로고침 후 유지까지 검증해야 하나요? 현재 요구사항만 보면 화면 상태 변경까지만 검증하는 것을 권장합니다.”
- “오류 메시지 표시만 대상인가요, 네트워크 재시도 후 정상 복구까지 대상인가요? 사용자 흐름상 복구까지 검증하는 것을 권장합니다.”

피할 질문:

- “DOM 테스트로 할까요?”
- “Vitest와 Playwright 중 무엇을 쓸까요?”
- 코드와 기존 테스트에서 확인할 수 있는 내용을 다시 묻는 질문

## 작성 및 검토 규칙

- 관련 구현, 테스트 설정, 기존 단위·통합·E2E 테스트를 먼저 확인한다.
- 정상 시나리오와 함께 관련 있는 오류·경계·복구 시나리오를 최소 하나 검토한다.
- 같은 요구사항을 여러 계층에서 중복 검증하지 않는다. 중복이 필요하면 각 계층이 담당하는 실패 경계를 명시한다.
- 구현 세부 사항보다 공개 동작, 사용자에게 보이는 결과, URL, 접근성 상태를 검증한다.
- DOM 테스트는 role과 접근 가능한 이름으로 요소를 찾는다.
- E2E는 실제 브라우저 경계가 핵심인 시나리오만 남기고 테스트 간 상태 의존성을 없앤다.
- 저장소의 테스트 실행 제한과 완료 기준을 따른다. 테스트 실행 권한이 없으면 코드는 작성하되 실행하지 않았음을 보고한다.

## 예시

장바구니 기능은 검증 목적에 따라 다음처럼 나눈다.

- 상품 추가 action이 store 상태를 바꾸는가: DOM 없는 단위 테스트
- 추가 버튼을 누르면 화면의 수량이 바뀌는가: jsdom 통합 테스트
- 새로고침 후 저장된 장바구니가 복원되는가: Playwright E2E

## 완료 보고

- 선택한 테스트 계층과 이유를 한 문장으로 밝힌다.
- 작성하거나 수정한 테스트와 담당 실패 경계를 요약한다.
- 실행한 검사와 결과, 실행하지 않은 검사와 이유를 구분한다.
- 판단에 사용한 가정이나 남은 브라우저 경계 위험이 있으면 적는다.
