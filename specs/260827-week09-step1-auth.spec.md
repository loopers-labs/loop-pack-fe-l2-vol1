# 9주차 1단계 — 인증 구현 스펙

## 목표

스타터 인증 API를 사용해 로그인·로그아웃, 헤더 로그인 상태, 보호 경로 접근 제어, 로그인 후 경로 복원, 세션 만료 처리를 구현한다.

서버가 세션의 원본을 소유하고 초기 HTML부터 로그인 상태를 반영해야 한다. 브라우저에서는 현재 사용자 UI 상태와 서버 데이터 캐시의 책임을 분리하고, 명시적 로그아웃과 세션 만료의 성격에 맞게 계정 데이터와 임시 상태를 정리한다.

## 비범위

- 2단계 이벤트 계측과 `identify()`·`reset()` 연결
- 3단계 E2E 범위 RFC, 4단계 E2E 테스트, 5단계 실험
- 회원가입, 비밀번호 찾기, 토큰 갱신
- 다른 탭에서 발생한 로그인·로그아웃의 실시간 동기화
- `/api/auth/me` 주기적 재조회
- 스타터 API, 인증 시나리오 노브, `src/analytics/` 수정
- 위시리스트 전용 화면, 서버 장바구니, 주문서 임시 저장 API
- 새 외부 의존성 추가

## 확정 목표

### 화면과 접근 범위

| 경로          | 화면       | 접근 정책                          |
| ------------- | ---------- | ---------------------------------- |
| `/login`      | 로그인     | 공개                               |
| `/cart`       | 장바구니   | 공개                               |
| `/my`         | 마이페이지 | 공개, 로그인 상태에 따라 내용 변경 |
| `/orders`     | 주문 내역  | 로그인 필요                        |
| `/orders/new` | 주문서     | 로그인 필요                        |

마이페이지는 보호 경로가 아니다. 비로그인 사용자에게도 마이 메뉴의 구조와 로그인 후 이용할 수 있는 기능을 먼저 보여준다.

- 비로그인: 로그인 안내와 CTA, 공개 장바구니, 로그인 후 사용할 수 있는 주문 내역·계정 정보 진입점
- 로그인: 사용자 이름·이메일과 주문 내역 진입점
- 마이페이지 로그인 CTA: 공통 로그인 URL 생성 규칙을 사용한 `/login?next=/my`

회원가입 API가 없으므로 회원가입 CTA는 만들지 않는다. 위시리스트는 기존 담기·빼기와 헤더 카운트를 유지하지만 별도 화면은 만들지 않는다.

로그인이 필요한 모든 진입점은 같은 복원 규칙을 사용한다. 마이페이지 CTA, proxy의 보호 경로 리다이렉트, 세션 만료 리다이렉트는 돌아갈 경로를 `next`에 담아 로그인 페이지로 보낸다. 기본값은 현재 `pathname + search`다. 장바구니 구매 모달은 구매 시 확정한 주문 예정 목록(checkout draft)을 보존하고 `/login?next=/orders/new`로 보낸다. 로그인 성공 후에는 `next`를 검증하고 원래 경로로 돌아간다.

### 핵심 사용자 흐름

1. 장바구니의 상품 선택(체크)은 장바구니 store가 항목 속성으로 저장해 새로고침 후에도 유지한다. 새로 담은 상품은 기본 선택된다.
2. 사용자가 구매하기를 누르면 선택 상품과 수량을 checkout draft로 확정해 `sessionStorage`에 저장한다.
3. 비로그인 사용자는 로그인 안내 모달의 CTA로 `/login?next=/orders/new`에 이동하고, 로그인 성공 후 주문서에서 checkout draft를 복원한다.
4. 로그인 사용자는 checkout draft를 만든 뒤 상품 ID를 URL에 싣지 않고 `/orders/new`로 이동한다.
5. 미로그인 사용자가 `/orders`에 접근하면 로그인 화면을 거쳐 주문 내역으로 돌아온다.
6. 미로그인 사용자가 `/my`에 접근하면 이동되지 않고 게스트용 마이페이지를 본다. 여기서 로그인하면 `/my`로 돌아와 로그인 사용자용 내용을 본다.
7. 로그인된 사용자가 주문 API에서 401을 받으면 사용자 상태를 정리한 뒤 `/login?reason=expired&next=<직전 경로>`로 이동한다. 로그인 화면에서 만료 이유를 확인하고 다시 로그인하면 직전 경로로 돌아온다.
8. 로그아웃하면 사용자 정보·주문 캐시·checkout draft는 제거되고, 브라우저 소유 장바구니·위시리스트는 유지된다.

## 조사 결과

### 현재 화면과 구조

- 커머스 화면은 홈과 상품 목록뿐이다. 로그인·마이페이지·장바구니·주문 화면은 새로 필요하다 (`src/app/(commerce)`, `src/_pages`).
- 커머스 layout은 서버 컴포넌트이고 헤더에는 상품 링크와 장바구니·위시리스트 카운트만 있다 (`src/app/(commerce)/layout.tsx:7-22`).
- 접근성 동작이 구현된 공용 Compound `Dialog`가 있으므로 로그인 안내 모달에 재사용할 수 있다 (`src/shared/ui/dialog/Dialog.tsx`, `src/app/demos/DialogDemo.tsx`).
- 페이지 조합은 `app → _pages → features → entities → shared` 방향을 사용한다 (`eslint.config.mjs:62-69`).
- `(commerce)/error.tsx`는 예상하지 못한 렌더 오류만 처리하며, 아직 인증 오류 분기가 없다 (`src/app/(commerce)/error.tsx:3-20`).

### 인증 API와 쿠키

- `session` 쿠키는 httpOnly·sameSite=lax이고 로그인 성공 시 1시간 유효한 서명 토큰으로 설정된다 (`src/app/api/auth/login/route.ts:58-68`).
- `readSessionToken`은 토큰 형식, HMAC 서명, `exp`, 사용자 존재를 검증한다 (`src/app/api/_data/auth.ts:96-132`).
- 로그아웃 API는 쿠키를 삭제하고 본문 없는 204를 반환한다 (`src/app/api/auth/logout/route.ts:4-16`).
- `/api/auth/me`와 `/api/orders`는 미로그인과 `expired` 시나리오 모두 같은 401 메시지를 반환한다 (`src/app/api/auth/me/route.ts:28-35`, `src/app/api/orders/route.ts:52-61`).
- `expired` 시나리오는 쿠키를 만료시키지 않고 API 응답만 401로 만든다. 따라서 proxy의 쿠키 검사만으로는 열린 화면의 세션 만료를 처리할 수 없다.

### 클라이언트 상태와 요청 처리

- `apiClient`는 GET만 지원하고 실패 응답의 status를 버린다. 본문 없는 성공 응답도 오류로 처리한다 (`src/shared/api-client.ts:10-37`).
- React Query는 브라우저 요청을 기본 2회 재시도하므로 현재 상태에서는 401도 재시도한다 (`src/shared/get-query-client.ts:3-15`).
- 장바구니와 위시리스트는 각각 모듈 전역 Zustand store이며 localStorage에 저장된다 (`src/entities/cart/model/cart-store.ts:42-73`, `src/entities/wishlist/model/wishlist-store.ts:42-67`).
- `createValidatedStorage`는 저장값을 검증한 뒤 Zustand의 `migrate`에 넘긴다. version 2 validator가 `productIds`를 먼저 버리면 version 1 장바구니를 마이그레이션할 수 없다 (`src/shared/persisted-store.ts:27-41`).
- 5주차 과제는 두 상태를 비로그인 사용자의 로컬 익명 상태로 정의했다 (`docs/assignments/week-05.md:7-13`, `:44-51`).

### 주문과 성능

- 주문 API는 사용자별 메모리 저장소를 사용하고 각 항목에 1 이상의 정수 수량을 요구한다 (`src/app/api/_data/auth.ts:134-152`, `src/app/api/orders/route.ts:67-88`).
- 제공된 주문 API는 최종 주문 생성(`POST`)과 주문 내역 조회(`GET`)만 지원한다. 선택 상품·배송지 같은 주문서 중간 상태를 저장하는 API는 없다 (`src/app/api/orders/route.ts:91-122`).
- 주문 응답에는 상품 ID·수량·주문 시각만 있고 상품명·가격·결제 합계는 없다 (`src/app/api/_data/auth.ts:32-53`). 주문 내역에서 상품 정보가 필요하면 현재 상품 API 응답으로 보강해야 하며, 이를 주문 당시 결제 금액으로 표현할 수는 없다.
- 장바구니는 상품 ID 배열만 저장하고 수량은 없다 (`src/entities/cart/model/cart-store.ts:16-24`).
- 상품 단건 API는 없고 목록 API의 `pageSize`는 최대 24다 (`src/app/api/products/route.ts:47-59`). 장바구니 상품 정보를 표시하려면 목록을 두 페이지 조회해야 한다.
- 인증 API에는 production에서도 기본 500ms mock 지연이 있다 (`src/app/api/_data/auth.ts:163-167`). layout에서 `/api/auth/me`를 호출하면 모든 커머스 페이지의 초기 응답이 늦어진다.
- 7주차 최종 측정값은 홈 FCP 0.3s·LCP 0.8s·CLS 0.006, 상품 목록 FCP 0.2s·LCP 0.6s·CLS 0이다 (`docs/week-07-performance/README.md:9-25`).

## 고민한 지점

### 1. 보호 경로 경계

#### 고민한 문제

주문 화면은 로그인이 필요하지만 장바구니와 마이페이지까지 진입을 막을지는 선택 사항이다. 특히 마이페이지는 비로그인 사용자에게도 메뉴와 로그인 혜택을 안내하는 진입점으로 사용하려 한다.

#### 고민한 대안들

| 선택                             | 판단                                                                                          |
| -------------------------------- | --------------------------------------------------------------------------------------------- |
| 주문서·주문 내역만 보호          | 계정 소유 데이터만 명확하게 보호한다. 장바구니와 마이페이지는 비로그인 경험을 제공할 수 있다. |
| 주문서·주문 내역·마이페이지 보호 | 구현은 단순하지만 `/my` 진입 즉시 로그인으로 보내므로 게스트용 마이 화면을 제공할 수 없다.    |
| 장바구니까지 보호                | 브라우저가 소유하는 익명 장바구니를 보려면 로그인이 필요한 모순이 생긴다.                     |

#### 최종 결정

- **D1: 보호 경로는 `/orders`와 `/orders/new`다.** `proxy.ts` matcher는 `['/orders/:path*']`만 사용한다. `/cart`와 `/my`는 공개한다.
- **D2: `/my`는 인증 상태에 따라 내용을 바꾸는 공개 화면이다.** 비로그인 사용자에게 메뉴 구조와 로그인 CTA를 보여주고, 로그인 사용자에게만 이름·이메일을 표시한다.

### 2. 현재 사용자 상태 — React Query와 Zustand

#### 고민한 문제

인증의 원본은 서버가 검증하는 쿠키다. 서버는 이 값으로 초기 HTML을 만들지만, hydration 이후 헤더와 마이페이지도 로그인 성공·로그아웃·세션 만료에 즉시 반응해야 한다.

이번 사용자 상태는 `/api/auth/me`를 주기적으로 조회하며 서버와 동기화할 데이터가 아니다. 서버에서 받은 최초 사용자 복사본이 세 가지 명시적 이벤트에서만 바뀐다. 이 복사본을 아예 두지 않을지, React Query 캐시에 둘지, Zustand에 둘지 결정해야 한다.

#### 고민한 대안들

| 선택                                     | 장점                                                                    | 이번 요구에서의 비용                                                                                                                           |
| ---------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 서버 props만 사용하고 `router.refresh()` | 별도 클라이언트 상태가 없다.                                            | 상태 변경마다 서버 왕복이 필요하다. API만 401을 반환하는 `expired` 시나리오에서는 쿠키가 여전히 유효해 헤더를 즉시 비로그인으로 바꾸기 어렵다. |
| React Query                              | `/api/auth/me` 재조회, 로딩·오류·재시도·캐시 수명을 함께 관리하기 좋다. | 이번에는 재조회를 하지 않으므로 `setQueryData`·`removeQueries`만 쓰게 되고 Query의 주요 기능을 사용하지 않는다.                                |
| 모듈 전역 Zustand store                  | Provider 없이 가장 간단하다.                                            | 서버 요청마다 다른 `initialUser`를 같은 인스턴스에 넣으면 요청 간 상태가 섞일 수 있다.                                                         |
| 요청별 Zustand Provider                  | 서버 초기값을 바로 넣고 `setUser`·`clearUser`로 즉시 갱신할 수 있다.    | store factory와 Context Provider가 필요하다.                                                                                                   |

#### 최종 결정

- **D3: 인증의 원본은 서명된 httpOnly 쿠키다.** 접근 권한은 proxy와 API가 판단하며 Zustand 값은 UI 렌더링에만 사용한다.
- **D4: 현재 사용자 UI 복사본은 요청별 Zustand Provider에 둔다.** 이 값은 서버 데이터 조회 캐시가 아니라 서버 초기값 이후 로그인 성공의 `setUser`, 로그아웃·인증 필요 API 401의 `clearUser`로만 바뀌는 작은 UI 상태다. React Query의 재조회·로딩·캐시 수명 기능을 사용하지 않으므로 Zustand가 책임에 더 잘 맞는다.
- **D5: commerce layout이 쿠키를 직접 검증해 `initialUser`를 만들고 `SessionProvider`가 `useState(() => createSessionStore(initialUser))`로 요청별 store를 한 번 생성한다.** `/api/auth/me` 호출의 500ms mock 지연을 피하고 JavaScript 실행 전 HTML에도 인증 상태를 반영한다. 모듈 전역 store는 요청 간 공유를 피하기 위해 사용하지 않는다. `persist`는 오래된 사용자를 복원할 수 있고, `useEffect` 초기화는 최초 HTML을 비로그인으로 만들기 때문에 사용하지 않는다. 주문처럼 실제로 조회·재검증·무효화가 필요한 서버 데이터는 계속 React Query가 맡는다.

### 3. 보호 경로 판정과 로그인 후 복원

#### 고민한 문제

proxy가 쿠키의 존재만 볼지 실제 유효성까지 확인할지, 로그인 후 돌아갈 경로를 어떻게 전달하고 외부 주소 이동을 어떻게 막을지 정해야 한다.

#### 고민한 대안들

| 선택                            | 판단                                                                               |
| ------------------------------- | ---------------------------------------------------------------------------------- |
| 쿠키 존재만 확인                | 빠르지만 위조·만료 쿠키를 통과시켜 proxy와 layout의 로그인 판단이 달라질 수 있다.  |
| 쿠키 서명과 `exp` 검증          | 기존 검증 함수를 재사용해 proxy와 layout이 같은 기준으로 판단한다.                 |
| 복원 경로를 쿠키에 저장         | URL은 단순하지만 클라이언트 만료 안내와 별도 구현이 필요하다.                      |
| 복원 경로를 `next` query로 전달 | 모든 로그인 진입점이 같은 방식을 쓰고 테스트하기 쉽지만 외부 주소 차단이 필요하다. |

#### 최종 결정

- **D6: proxy는 기존 `readSessionToken`으로 쿠키 서명과 `exp`까지 검증한다.** 미로그인·위조·만료 쿠키는 로그인 페이지로 보내고 layout도 같은 함수로 사용자를 판정한다.
- **D7: 복원 경로는 공통 함수가 `next` query로 만든다.** 마이페이지 CTA와 proxy 리다이렉트는 현재 `pathname + search`를 사용한다. 세션 만료도 같은 경로를 사용하되 `reason=expired`를 함께 전달하고, 장바구니 구매 모달은 draft를 확정한 뒤이므로 `/orders/new`를 사용한다. 로그인 성공 시 `next`가 `/`로 시작하고 `//`·`/\`로 시작하지 않을 때만 `replace`하며 나머지는 `/`로 대체한다.

### 4. 세션 만료 처리 위치

#### 고민한 문제

미로그인과 세션 만료가 모두 401이지만 로그인 폼의 401은 자격 증명 실패다. 어떤 401을 만료로 볼지와 중복 없이 사용자에게 안내할 위치를 정해야 한다.

#### 고민한 대안들

| 선택                                        | 판단                                                                                |
| ------------------------------------------- | ----------------------------------------------------------------------------------- |
| 화면별 처리                                 | 조회 화면과 주문 mutation마다 같은 분기가 반복된다.                                 |
| React Query 전역 콜백                       | query와 mutation 캐시 양쪽을 설정해야 하고 React Query를 거치지 않는 요청은 놓친다. |
| proxy                                       | 페이지 진입만 처리하므로 `expired` 시나리오와 열린 화면의 만료를 알 수 없다.        |
| `ApiError` + React Query + 라우트 에러 경계 | 인증 필요 query와 mutation의 401을 한 경로로 모아 로그인 이동을 처리할 수 있다.     |

#### 최종 결정

- **D8: 로그인 API의 401은 자격 증명 실패, `/api/auth/me`·`/api/orders`의 401은 세션 만료로 본다.** 로그인 401은 폼에 표시하고 인증 API 401은 공통 만료 흐름으로 보낸다.
- **D9: 인증 필요 API의 401은 `apiClient → React Query → (commerce)/error.tsx` 경로로 처리한다.** `apiClient`는 status를 가진 `ApiError`만 던지고, 서버에서도 사용하는 계층이므로 router·`window` 조작이나 사용자 상태 정리를 하지 않는다. React Query는 query와 mutation의 401을 재시도하지 않고 `throwOnError`로 렌더 단계에서 다시 던져 에러 경계에 전달한다. 로그인 mutation의 401은 자격 증명 실패이므로 `throwOnError: false`로 폼에서 처리한다. 에러 경계는 사용자 store와 주문 캐시를 비운 뒤 `/login?reason=expired&next=<직전 pathname+search>`로 `replace`한다. refresh token처럼 세션 복구 수단이 있다면 복구 후 한 번 재시도할 수 있지만 현재 API에는 없으므로 바로 재로그인을 요청한다.

### 5. 로그아웃 시 클라이언트 상태

#### 고민한 문제

실무에서는 로그인 사용자의 장바구니를 서버가 소유하거나 주문서 초안을 임시 저장하고 `checkoutId`로 다시 조회하는 경우가 많다. 이 구조에서는 로그아웃할 때 계정 범위의 클라이언트 장바구니·checkout 캐시를 지워도 서버에서 다시 복구할 수 있다.

현재 스타터에는 서버 장바구니와 주문서 임시 저장 API가 없다. 장바구니·위시리스트의 localStorage가 유일한 원본이므로 로그아웃 시 지우면 복구할 방법이 없다. 반면 checkout draft는 구매하기를 누른 시점의 주문 예정 목록일 뿐 장바구니 원본이 아니다.

#### 고민한 대안들

| 선택                         | 판단                                                                                |
| ---------------------------- | ----------------------------------------------------------------------------------- |
| 장바구니·위시리스트까지 삭제 | 서버 장바구니나 `checkoutId`가 있다면 적절하지만, 현재는 유일한 로컬 원본을 잃는다. |
| checkout draft까지 모두 유지 | 재선택은 줄지만 다른 계정으로 바꿨을 때 이전 주문 예정 목록이 이어진다.             |
| 원본은 유지하고 draft만 삭제 | 장바구니 데이터는 보존하면서 명시적인 사용자 전환 경계를 지킨다.                    |

#### 최종 결정

- **D10: 로그아웃 API가 204로 성공한 뒤 사용자 상태·주문 캐시·checkout draft를 비운다.** 장바구니·위시리스트는 서버 사본이 없는 브라우저 원본이므로 유지한다. checkout draft는 다른 계정으로 이어지지 않게 제거하고 `/`로 이동한다. 로그아웃 요청이 실패하면 쿠키가 남아 있으므로 클라이언트 상태와 현재 위치를 유지하고 오류를 안내한다. 세션 만료 후 재로그인 흐름에서는 직전 작업 복원을 위해 checkout draft를 유지한다.
- **D11: 주문 query key에는 `userId`를 포함한다.** 로그아웃·만료 때 주문 query 전체를 제거해 다른 계정에 이전 사용자의 주문이 노출되지 않게 한다.
- 로그아웃 API의 204는 본문이 없는 정상 성공이다. `apiClient`는 204에서 `undefined`를 반환하고, JSON을 약속한 다른 성공 응답의 파싱 실패는 오류로 처리한다.

### 6. 장바구니 수량과 주문 상품 전달

#### 고민한 문제

현재 장바구니는 상품 ID만 저장하지만 주문 API는 수량을 요구한다. 모든 상품에 수량 1을 붙이는 최소 구현도 가능하지만, 장바구니와 주문서에서 실제 수량을 변경할 수 있도록 범위를 확장할지 결정해야 한다. 장바구니 선택(체크)은 실제 커머스처럼 장바구니 항목의 속성으로 저장해 새로고침 후에도 유지하고, 구매하기를 누른 뒤에는 주문 예정 목록이 로그인 왕복과 새로고침 뒤에도 유지되어야 한다.

#### 고민한 대안들

장바구니 데이터 형태:

| 선택                                  | 판단                                                                               |
| ------------------------------------- | ---------------------------------------------------------------------------------- |
| ID 배열을 유지하고 항상 수량 1로 주문 | 구현은 작지만 장바구니와 주문서에서 수량을 바꿀 수 없다.                           |
| 상품 ID와 수량을 함께 저장            | 기존 저장값 마이그레이션이 필요하지만 주문 API 계약과 실제 장바구니 동작에 맞는다. |

선택 상품 전달 방식:

| 선택                                        | 판단                                                                              |
| ------------------------------------------- | --------------------------------------------------------------------------------- |
| 구매 시점의 `sessionStorage` checkout draft | 장바구니 선택은 로컬에 두고 확정된 상품·수량만 로그인 왕복과 새로고침에 유지한다. |
| 상품 ID·수량을 query로 전달                 | 별도 상태는 없지만 주문 정보가 URL에 노출되고 주문서 경로가 전달 형식과 결합된다. |
| 서버에 주문서 초안 생성                     | 옵션·수량·쿠폰·배송지를 다루기에 적합하지만 현재 API에 없고 이번 범위를 넘는다.   |

#### 최종 결정

- **D12: 인증 구현의 최소 조건보다 범위를 확장해 장바구니에 `items: { productId; quantity; checked }[]`를 저장한다.** 항상 수량 1로 주문할 수도 있지만, 사용자가 장바구니에서 실제 수량을 확인·변경할 수 있게 하기 위한 제품 결정이다. 주문서는 draft의 상품·수량과 catalog 최신 가격으로 계산한 결제 금액을 확인하는 읽기 전용 화면이며, 수정이 필요하면 장바구니로 돌아가 다시 구매하기를 누른다. 저장 버전을 2로 올리고 version 1의 ID 배열은 수량 1·선택된 항목으로 마이그레이션한다. 공용 저장소가 검증 후 마이그레이션하므로 version 1 형태를 검증 단계에서 보존하거나 버전별 validator를 사용한다. 복원 시 상품 ID 중복을 제거하고 수량은 1 이상의 안전한 정수, checked는 boolean만 허용한다. 수량 변경·선택 토글과 주문 상품 일괄 제거 action을 추가한다. 헤더 카운트는 수량과 무관하게 담긴 상품 종류 수를 표시한다.
- **D13: 장바구니 체크 여부는 장바구니 store가 항목 속성으로 저장하고(새로 담은 상품은 기본 선택), 구매하기를 누를 때 `entities/order`의 `sessionStorage` 기반 checkout draft에 선택 상품·수량을 스냅샷으로 저장한다.** draft store는 시작과 비우기만 제공하며 체크 toggle은 장바구니 store가 소유한다. 비로그인 구매 모달의 CTA는 `/login?next=/orders/new`로 이동하고, 로그인 후 주문서가 draft를 복원한다. 명시적 로그아웃과 주문 성공 때 draft를 비우고, 세션 만료 후 재로그인과 같은 탭 새로고침에서는 유지한다. draft 복원 시 상품 ID와 1 이상의 안전한 정수 수량만 허용하고 중복 상품은 제거한다. 서버 checkout session API가 생기면 이 클라이언트 draft를 대체한다.
- **D14: 주문서는 checkout draft의 hydration을 기다린 뒤 draft 상품을 catalog와 대조해 판매 중인 상품만 남긴다.** 주문서는 cart store를 읽지 않는다. 남은 상품의 draft 수량과 최신 상품 가격으로 주문과 합계를 구성하며 주문 API가 ID·수량을 다시 검증한다. 성공하면 주문한 상품만 장바구니에서 제거하고 draft를 비운 뒤 주문 query를 무효화하고 `/orders`로 이동한다. draft가 없거나 판매 중인 draft 상품이 없으면 빈 상태와 장바구니 CTA를 표시한다.

### 7. 장바구니·주문 상품 정보 조회

#### 고민한 문제

장바구니는 최대 30개 상품을 담을 수 있지만 상품 목록 API는 한 요청에 최대 24개만 반환하고 단건·ID 필터 API가 없다. 주문 응답도 상품명·가격·결제 합계를 보존하지 않는다.

#### 고민한 대안들

| 선택                                  | 판단                                                                 |
| ------------------------------------- | -------------------------------------------------------------------- |
| 장바구니 화면에 페이지네이션 UI 추가  | 사용자가 담은 상품만 보는 화면을 임의로 나누므로 요구와 맞지 않는다. |
| 상품 API에 `ids` 필터 추가            | 가장 효율적이지만 스타터 API 수정이 비범위다.                        |
| 기존 상품 페이지를 내부에서 모두 조회 | API 계약을 바꾸지 않고 최대 30개 상품 정보를 한 번에 구성할 수 있다. |

#### 최종 결정

- **D15: 상품 단건 조회와 ID 목록 필터 API가 없으므로 기존 상품 목록 API를 내부에서 끝까지 조회한다.** `productQueries.catalog()`가 `page=1&pageSize=24`의 `totalCount`로 페이지 수를 계산하고 나머지 페이지를 병렬 조회해 하나의 배열로 합친다. 장바구니·주문서·주문 내역이 이 catalog를 공유하며 화면에 페이지네이션 UI는 만들지 않는다. 단건 조회나 ID 목록 필터 API가 추가되면 필요한 상품만 조회하는 방식으로 교체한다. 주문 내역은 주문 ID·시각·수량과 현재 상품 정보를 표시하되, 현재 가격을 주문 당시 결제 금액으로 표현하지 않는다.

## 구현 구조

- `entities/session`: 사용자·세션 타입, 요청별 session store와 Provider
- `entities/cart`: 수량 포함 장바구니, version 1 → 2 마이그레이션
- `entities/product`: 전체 상품 페이지를 합치는 catalog query
- `entities/order`: 주문 타입, API, userId 기반 query key, `sessionStorage` checkout draft
- `features/auth`: login/logout API와 mutation, 로그인 폼, 로그인 필요 Dialog, 헤더 세션 메뉴, 로그인 화면의 만료 안내, `next` 검증
- `features/order`: 주문 폼
- `shared/persisted-store`: 저장소 대상 선택과 버전별 검증·마이그레이션 지원
- `shared/api-client`: `RequestInit`, `ApiError`, 204 응답 처리
- `shared/get-query-client`: 401 재시도·에러 경계 전달 정책
- `_pages/{login,cart,my,orders,order-new}`: 페이지 조합
- `src/proxy.ts`: 보호 경로 가드
- `src/app/(commerce)/layout.tsx`: 쿠키 검증과 사용자 초기값 전달
- `src/app/(commerce)/error.tsx`: 401 상태 정리와 로그인 리다이렉트

## 완료 조건

### 기능

- [ ] **C1:** 장바구니에서 `p1`, `p3`만 선택한 미로그인 사용자가 구매하기를 누르면 두 상품과 수량이 checkout draft에 저장되고 로그인 필요 모달이 열린다. 모달을 닫으면 화면 선택이 유지되고, “로그인 페이지로 이동” CTA로 로그인하면 `/orders/new`에서 두 상품을 복원한다.
- [ ] **C2:** 미로그인으로 `/my`에 접근해도 리다이렉트되지 않고 로그인 안내·CTA와 마이 메뉴를 볼 수 있다. CTA로 로그인하면 `/my`로 돌아와 이름·이메일을 볼 수 있다.
- [ ] **C3:** 공통 `next` 검증 함수는 `/orders?status=pending` 같은 내부 경로는 유지하고 `https://evil.com`, `//evil.com`, `/\evil.com` 같은 외부 이동 가능 값은 `/`로 대체한다. 로그인 성공도 이 검증 결과만 사용한다.
- [ ] **C4:** 로그인 폼에 잘못된 이메일 또는 비밀번호를 입력해 API가 401을 반환하면 로그인 화면에 자격 증명 오류를 표시한다. 경로와 비로그인 사용자 상태를 유지하며 사용자는 값을 수정해 다시 제출할 수 있다.
- [ ] **C5:** 로그인 쿠키가 있는 초기 HTML에는 사용자 이름이, 쿠키가 없는 초기 HTML에는 로그인 링크가 포함된다.
- [ ] **C6:** 로그인 후 `scenario=expired`로 주문 API가 401을 반환하면 재시도하지 않고 사용자 상태와 주문 캐시를 비운 뒤 `/login?reason=expired&next=<직전 경로와 query>`로 이동한다. 로그인 화면에 만료 안내가 보이고, 다시 로그인하면 checkout draft를 유지한 채 직전 위치로 돌아온다.
- [ ] **C7:** 로그아웃 API가 204를 반환하면 사용자 상태·주문 캐시·checkout draft는 제거되고 `/`로 이동한다. 장바구니·위시리스트 카운트는 유지된다. 통합 테스트에서 로그아웃 요청을 실패시키면 기존 상태와 위치를 유지하고 오류를 표시한다.
- [ ] **C8:** 기존 version 1 장바구니 저장값은 검증 과정에서 버려지지 않고 각 상품이 수량 1에 선택된 version 2 데이터로 복원된다. 사용자가 수량·체크를 변경하면 새로고침 후에도 유지되고 헤더 카운트는 담긴 상품 종류 수를 표시한다.
