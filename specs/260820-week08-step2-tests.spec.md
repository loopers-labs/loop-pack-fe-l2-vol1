# 8주차 2단계 — 검증 항목 구현 스펙

## 목표

1단계에서 배치한 15개 검증 항목을 정한 방법론 그대로 구현한다. 항목마다 정상 케이스와 경계 케이스를 함께 두고, 테스트 이름만 읽어도 무엇이 깨졌는지 알 수 있게 쓴다.

## 비범위

- 3단계(구현을 일부러 망가뜨려 테스트가 잡는지 확인)와 Advanced(Stryker) — 별도 세션
- 커버리지 수치를 올리기 위한 테스트 추가
- 1단계 목록 밖 항목(검색 UI·검색 결과 시나리오, CSS·스타일) — 1단계 문서에서 이미 하지 않기로 판단. 다만 **URL 파서의 `q` 정규화는 항목 2에 포함**된다
- 새 외부 의존성 추가 (`msw`는 0단계에서 이미 들어옴)
- 테스트를 통과시키기 위한 구현 기능 삭제·완화

## 확정 목표

단위 3(node) / 통합 8(jsdom + MSW) / E2E 4(production build)를 구현하고 `pnpm check`를 통과시킨다.

**배치는 1단계가 정한 대로 지킨다.** 구현이 막힌다고 문서를 구현에 맞춰 고치지 않는다. 그렇게 하면 1단계 문서가 사후 정당화가 되고 설계가 틀렸다는 사실이 영영 드러나지 않는다. 막히면 그 자리에서 무엇 때문에 막혔는지를 근거로 남기고, 그래도 배치가 틀렸다는 결론이 나오면 **그 판단 자체를 별도 기록으로 남긴 뒤에만** 문서를 고친다.

## 조사 결과

**환경은 확장자로 갈린다** — `.ts` → node, `.tsx` → jsdom (`vitest.config.ts:26-48`). 예외는 `src/_pages/home/ui/HomePage.test.tsx` 하나. **단위 테스트를 `.tsx`로 만들면 자동으로 jsdom에서 돌아 1단계 배치와 어긋난다.**

**jsdom에만 정리 setup이 걸려 있다** — `vitest.setup.ts`가 `cleanup()` → 스토어 비우기 → `localStorage.clear()`를 한다. node 프로젝트에는 이 파일이 없어, node 단위 테스트가 스토어를 건드리면 **파일 안에서 스스로 초기화해야 한다**.

**MSW 기본 핸들러는 조건을 읽지 않는다** — `tests/msw/handlers.ts:8`의 `*/api/products`가 query와 무관하게 `PRODUCT_LIST_RESPONSE`(`totalCount: 1`, 상품 1개, `pageSize: 12`)를 고정으로 준다. 이대로면 항목 8·9·10에서 조건을 바꿔도 응답이 같고, `totalPages`가 항상 1이라 페이지 경계를 만들 수 없다.

**`NuqsTestingAdapter`는 `hasMemory: true`가 필요하다** — 기본값 `false`면 search param이 초기값에 얼어붙어 조건 변경이 화면에 반영되지 않는다(0단계 문서 2절 실측). 항목 8·9·10의 전제.

**필터는 `<select>` 두 개다** — `ProductListFilters.tsx:20-49`. 접근 가능한 이름은 label의 `카테고리`·`정렬`. 통합·E2E 모두 `selectOptions`로 조작할 수 있다.

**E2E가 만날 실제 숫자** — 시드는 상품 30개, 카테고리마다 6개(`src/app/api/_data/commerce.ts`). `pageSize` 12이므로 `all`은 3페이지(마지막 6개), 개별 카테고리는 1페이지. 항목 10·11의 페이지 경계가 이 숫자 위에서 만들어진다. mock API의 500ms 지연도 production 실행이라 그대로 만난다(`waitForMockApi`는 `NODE_ENV === 'test'`일 때만 0).

**`countTotalPages`가 UI 파일에 있다** — `src/_pages/products/ui/ProductList.tsx:17`의 모듈 지역 함수. 도메인 계산인데 자리가 UI다.

**항목 2의 현재 테스트는 `.tsx`다** — `product-list-params.test.tsx`가 `renderHook` + `NuqsTestingAdapter`로 "서버 loader와 브라우저 hook이 같은 queryKey를 만든다"를 검증한다. 1단계는 항목 2를 단위로 배치했으므로 이 파일은 그대로 둘 수 없다. 그리고 두 경로는 **같은 `conditionParsers` 객체 하나**에서 나온다 — `createLoader(conditionParsers)`와 `useQueryStates(conditionParsers)`. 지금 이 테스트가 실제로 지키는 건 우리 코드가 아니라 nuqs다.

**스토어 테스트 파일이 이미 있다** — `cart-store.test.tsx` / `wishlist-store.test.tsx`(jsdom). 내용은 전부 **저장·복원·저장값 검증**이고 개수 파생은 다루지 않는다. 0단계에서 `localStorage`가 필요해 `.ts` → `.tsx`로 rename된 파일들이다.

**기본 핸들러 응답에 의존하는 테스트는 하나뿐이다** — `tests/products-error.test.tsx`. `api-client.test.ts`·`api-client.browser.test.tsx`도 `*/api/products`를 쓰지만 둘 다 `server.use`로 직접 덮으므로 기본 핸들러를 바꿔도 영향이 없다.

**브랜치는 이미 정해졌다** — `feat/round-8`.

## 결정 사항

- **D1: 항목 2는 loader만 남긴 순수 단위로 교체한다** — `product-list-params.test.tsx`를 지우고 `product-list-params.test.ts`(node)를 새로 쓴다. URL 문자열 → queryKey까지가 순수 함수라는 1단계 판단 A를 그대로 따른다. 없어지는 loader↔hook 대조는 **검증 공백이 아니다**: 서버와 브라우저가 같은 `conditionParsers` 하나를 공유하므로 갈라질 경로가 없고, 그 테스트는 nuqs의 두 API가 같은 파서를 같게 해석하는지를 보고 있었다. 화면까지 이어지는 확인은 항목 11(E2E)이 실제 주소로 들어가는 것으로 한다.

  **항목 2는 파일 둘로 나눈다.** `product-list-params.test.ts`는 주소 → 조회 조건까지(파싱)만 보고, 그 조건이 실제 캐시 키에 실리는지는 `queries.test.ts`가 본다. 한 파일에서 `queryKey`까지 단언하면 파싱 테스트마다 3칸 배열이 딸려와 읽기 나빠지고, 반대로 `queryKey`를 아예 안 보면 **조건이 키에서 빠져 모든 조건이 캐시 한 칸을 공유하는 회귀**를 아무도 못 잡는다. 나누면 둘 다 지켜진다.

- **D2: 기본 핸들러가 조건을 읽어 응답을 만들게 고친다** — 지금 핸들러는 요청을 보지도 않고 늘 같은 응답(상품 1개)을 준다. 그래서 항목 8·9·10에서 카테고리를 바꿔도 화면이 그대로라 "새 응답으로 갈아탔다"를 단언할 수 없다.

  ```ts
  // 지금
  http.get('*/api/products', () => HttpResponse.json(PRODUCT_LIST_RESPONSE));

  // 바꿀 것 — 주소의 조건을 읽어 거르고, 정렬하고, 페이지만큼 자른다 (약 15줄)
  http.get('*/api/products', ({ request }) => {
    const params = new URL(request.url).searchParams;
    ...
  });
  ```

  정렬은 테스트가 실제로 쓰는 것 하나만 구현한다.

  **실제 `route.ts`의 `GET`을 그대로 부르는 안은 택하지 않는다.** 성립하기는 한다 — 핸들러가 `NextRequest`를 만들어 넘기면 되고, `NODE_ENV === 'test'`라 route의 500ms 지연도 0이 된다. 로직 중복도 사라진다. 그러나 그러면 통합 테스트 아래에 진짜 백엔드가 서서 "네트워크에서 자른다"는 모킹 경계가 사실상 사라진다. 과제가 직접 정하라고 못 박은 결정을 route에 넘기는 모양이 되고, route가 깨지면 통합 8개가 함께 빨간불이 된다. 로직이 두 벌이 되는 대가는 감수한다(→ 「감수한 것」).

- **D3: 픽스처는 개수뿐 아니라 "구별 가능성"까지 설계한다** — 세 가지다.

  **첫째, 개수가 만들 수 있는 상황을 정한다.** 지금 픽스처는 상품 1개라 `totalPages`가 항상 1이고, 페이지가 하나뿐이면 "다음 페이지로 이동"이라는 상황 자체가 없다. 상품 25개(`home` **13개**, 나머지 12개)로 둔다.

  | 조건             | 페이지                | 이걸로 만드는 상황                                            |
  | ---------------- | --------------------- | ------------------------------------------------------------- |
  | `all` 25개 ÷ 12  | 3페이지 (12·12·**1**) | 마지막 페이지에서 `다음` 잠김 (항목 10 경계)                  |
  | `home` 13개 ÷ 12 | 2페이지 (12·1)        | 2페이지에서 카테고리를 바꿔도 **여전히 유효한 페이지** (아래) |

  **둘째, `home`을 13개로 둔 이유는 항목 8·9의 경계가 거짓 양성이 되지 않게 하기 위해서다.** `home`이 1페이지뿐이면, `changeCategory`에서 `page: 1`을 지워도 `usePageClamp`가 3페이지를 1페이지로 보정해버려 **화면은 똑같이 `1 / 1`이 된다.** 페이지 초기화가 망가져도 테스트가 통과한다. 바꾼 뒤에도 원래 페이지가 유효하면 clamp가 끼어들지 않아 둘이 갈린다.

  |                                 | 초기화가 동작              | 초기화가 망가짐              |
  | ------------------------------- | -------------------------- | ---------------------------- |
  | `all` 2페이지 → 카테고리 `home` | `1 / 2`, `홈 상품 01` 보임 | `2 / 2`, `홈 상품 13`만 보임 |
  | `all` 2페이지 → 정렬 낮은가격순 | `1 / 3`, 최저가가 맨 앞    | `2 / 3`                      |

  **셋째, 잘못된 구현이 우연히 통과하지 않게 세 가지 불변조건을 건다.**

  - 기본 정렬(latest)의 첫 상품이 **최저가가 아니다** — 아니면 항목 9가 정렬 없이도 통과한다.
  - 페이지마다 이름이 다른 대표 상품이 있다 (`홈 상품 01` / `홈 상품 07` / `홈 상품 13`) — 아니면 항목 10이 페이지가 안 바뀌어도 통과한다.
  - `home` 결과와 전체 결과를 가르는 대표 상품이 있다 (`일반 상품 01`은 `home`에 없다) — 아니면 항목 8이 필터가 없어도 통과한다.

  배열 순서를 `홈01, 일반01, 홈02, 일반02, …, 홈12, 일반12, 홈13`으로 두고 가격을 뒤로 갈수록 싸게 매기면 셋을 한 번에 만족한다. 25개를 손으로 쓰지 않고 기존 `PRODUCT`에서 필요한 필드만 바꿔 생성한다.

  **넷째, 기대값의 출처는 픽스처다.** `총 25개`를 문자열로 박으면 그 25가 어디서 왔는지 알 수 없고 픽스처를 고쳤을 때 조용히 깨진다(0단계 문서 2절).

  ```ts
  // ❌ expect(await screen.findByText('총 25개'))
  // ✅ expect(await screen.findByText(`총 ${PRODUCTS.length}개`))
  ```

- **D4: 단위는 파생, 통합은 구독** — 항목 1(node 단위)은 `toggle`과 `productIds.length`만 본다(렌더 없음). `tests/store.test.tsx`의 `describe('헤더 개수')`는 남기되 이름을 "스토어에 담기면 헤더가 새 숫자를 다시 그린다"로 고쳐 항목 12가 구독·리렌더를 주장하게 만든다. 두 파일이 서로 다른 것을 지킨다.

- **D5: 새 node 단위 파일에 한정어를 붙인다** — `cart-store.count.test.ts` / `wishlist-store.count.test.ts`. 항목 1은 DOM 없이 통과해야 하고 기존 파일은 `localStorage`가 필요하므로 **한 파일로 합칠 수 없다.** 기존 `cart-store.test.tsx`는 그대로 두고, 두 파일 이름이 각각 무엇을 담는지 말하게 한다.

- **D6: `countTotalPages`는 `src/features/product/model/pagination.ts`로 옮긴다** — 도메인 계산이라 UI 파일에 있을 이유가 없다. `constants.ts`에 넣지 않는 이유는 함수가 상수 파일에 있으면 이름이 내용을 속이기 때문이다. `index.ts`에 export를 더하고 `ProductList.tsx`는 import해서 쓴다. **테스트용 export가 아니라 위치 교정**이다.

- **D7: 단위·통합 테스트는 대상 옆에 두고, 레이어를 가로지르는 것만 밖에 둔다** — FSD는 별도 `tests` 레이어를 만들기보다 **코드와 테스트를 함께 두는 쪽**이 기본이다. 항목 4~10의 통합 테스트는 대상이 `ProductList`이므로 `src/_pages/products/ui/` 옆에 둔다.

  |                                    | 자리                                                                                              |
  | ---------------------------------- | ------------------------------------------------------------------------------------------------- |
  | 단위                               | 대상 파일 옆 (`cart-store.count.test.ts`, `pagination.test.ts`)                                   |
  | 슬라이스 통합 (항목 4~10)          | `src/_pages/products/ui/ProductList.*.test.tsx`                                                   |
  | 레이어를 가로지르는 통합 (항목 12) | `tests/store.test.tsx` — entities 둘과 features 둘을 함께 렌더한다. 어느 슬라이스의 소유도 아니다 |
  | E2E                                | `e2e/`                                                                                            |
  | 테스트 인프라 (MSW, 렌더 헬퍼)     | `tests/` — 0단계에서 정한 자리                                                                    |

- **D8: `tests/products-error.test.tsx`는 새 파일로 흡수하고 지운다** — 그 안의 두 테스트가 항목 6·7의 정상/경계와 그대로 겹친다. 남겨두면 같은 주장이 두 곳에 생긴다.

- **D9: E2E 4개는 한 파일에 둔다** — 항목 11·13·14·15가 전부 `/products`에서 시작하고 같은 빌드를 공유한다. `e2e/products.spec.ts` 하나.

- **D10: 항목 14의 경계는 "조건이 몇 개나 살아남느냐"로 잡는다** — **"새로고침 직후 서버 렌더 결과가 조건을 반영하는지"를 따로 증명하는 안은 택하지 않는다.**

  1단계 문서가 항목 14에서 보기로 한 것은 "새로고침했을 때 조건이 URL에서 의도대로 파싱되는가"이고, 서버 렌더는 이 항목을 E2E로 정한 **이유**이지 테스트가 따로 증명할 대상이 아니다. **새로고침 자체가 이미 서버 렌더부터 다시 지난다.** 요청을 끊거나 JS를 꺼서 "이건 서버가 그렸다"를 증명하려면 도구를 억지로 쓰게 되고(JS를 끄면 스트리밍된 목록이 붙지 않아 구현이 멀쩡해도 fallback에 머문다), 같은 것을 두 번 보는 셈이 된다.

  대신 **기본값이 아닌 조건 셋(카테고리·정렬·페이지)을 한꺼번에 걸어두고 새로고침한다.**

  |      | 내용                                          | 잡는 버그                                       |
  | ---- | --------------------------------------------- | ----------------------------------------------- |
  | 정상 | 카테고리를 바꾸고 새로고침해도 같은 목록      | 조건이 새로고침에 살아남지 못한다               |
  | 경계 | 셋을 다 바꾼 뒤 새로고침해도 셋 다 살아남는다 | 하나만 살고 나머지가 조용히 기본값으로 돌아간다 |

  조건 하나만 보면 파서가 나머지를 흘려도 통과한다. 실제 버그는 `page`만 살고 `sort`가 `latest`로 돌아가는 쪽에서 난다. 셋 다 기본값이 아니라서 "파싱 실패 시 조용히 기본값" 경로도 함께 걸린다.

- **D11: 항목 7의 경계는 시간이 아니라 신호로 연다** — "재조회 중에는 다시 시도 버튼이 잠긴다"는 **요청이 아직 안 끝난 순간**에만 참이다. 핸들러가 즉시 응답하면 클릭하자마자 요청이 끝나 단언 시점에는 이미 버튼이 풀려 있다. 흔한 해법인 `delay(100)`은 "100ms면 충분하겠지"라는 **시간 가정**이라, CI가 느리면 이유 없이 깨진다.

  응답 시점을 테스트가 직접 쥐면 시간이 사라진다. 다만 **핸들러가 실제로 시작했는지도 기다려야 한다** — 클릭 직후 핸들러가 아직 안 돌았을 수 있고, 그때 잠금을 단언하면 무엇을 봤는지 알 수 없다. 문(gate) 하나로는 부족하고 둘이 필요하다.

  ```ts
  const requestStarted = Promise.withResolvers<void>();
  const responseGate = Promise.withResolvers<void>();

  server.use(
    http.get('*/api/products', async () => {
      requestStarted.resolve();
      await responseGate.promise;

      return HttpResponse.json(productListResponse());
    }),
  );

  try {
    await user.click(retryButton);
    await requestStarted.promise; // 요청이 핸들러에 도달했다
    expect(retryButton).toBeDisabled(); // 응답은 아직 안 왔음이 보장된다
  } finally {
    responseGate.resolve(); // 단언이 실패해도 요청을 풀어준다
  }

  expect(await screen.findByText(totalCountText)).toBeInTheDocument();
  ```

  `finally`가 없으면 중간 단언이 실패했을 때 요청이 영영 안 풀려 그 파일이 매달린다. 느리든 빠르든 결과가 같고 `sleep`도 없다.

## 감수한 것

해결책이 있는데 안 한 것이 아니라, 다른 선택지의 대가가 더 커서 받아들인 것들이다.

- **필터·정렬·페이지 로직이 두 군데가 된다** (D2의 대가). 진짜는 `route.ts`, 가짜는 MSW 핸들러. 나중에 누가 `route.ts`의 규칙을 바꿔도 핸들러는 옛 규칙 그대로고, 통합 테스트는 가짜를 상대하므로 **초록불인 채로 진짜와 어긋난 걸 모른다.**

  그래도 받아들이는 이유는 통합 테스트가 지키기로 한 것이 그게 아니어서다. 통합의 질문은 "이런 응답이 오면 화면이 제대로 그리는가"이지 "백엔드 필터링이 맞는가"가 아니다. 백엔드는 `src/app/api/products/route.test.ts`가 따로 지킨다. 진짜 route를 부르면 이 중복은 없어지지만 모킹 경계가 함께 없어진다 — 그쪽 대가가 더 크다고 봤다.

- **통합에서는 URL 문자열이 실제로 바뀌는지 보지 못한다** — nuqs 어댑터가 그 층을 대신한다. 1단계 판단 B가 이미 "감수한 위험"으로 적고 항목 11 E2E가 한 번 지나가는 것으로 갈음하기로 했다. 이 스펙은 그 판단을 그대로 잇는다.
- **테스트가 대상 코드에서 멀어진다** (D7의 대가). `tests/` 배치를 유지해 헬퍼 공유와 FSD 예외를 한곳에 모으는 쪽을 택했다.
