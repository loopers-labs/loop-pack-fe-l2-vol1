# 10주차 Step 3 — 예산 게이트와 결과 가시성

> 작성: 2026-09-10. 번들·Lighthouse 임계값과 여유폭은 기준선 측정 후 사용자가 확정한다.
> 선행 조건: 조건부 CI, strict required checks, 배포 전 전체 E2E, 정기 Lighthouse 측정.

## Problem Statement

테스트와 build가 성공해도 초기 JavaScript의 크기 증가나 배포 환경설정 오류를 놓칠 수 있다. 7주차의 성능 개선을 유지하려면 측정에 근거한 예산을 정하고, 성능 회귀와 설정 오류를 main 병합·Production 배포 전에 차단해야 한다.

실패 원인도 PR에서 바로 보여야 한다. 작성자가 원시 로그를 읽지 않고 초과 대상과 초과량을 확인할 수 있어야 한다.

## Solution

기존 Quality CI에 **환경변수 검증 → production build → 크기 예산 검사**를 연결한다. env·예산 검사는 main 병합과 Production 배포의 필수 조건으로 둔다. Lighthouse는 정기·수동 실행에서 임계값을 판정한다.

PR 코멘트에는 핵심 결과를, job summary에는 상세 결과를 표시한다. 실제 예산 초과 PR에서 실패·병합 차단을 확인하고, 원복 후 성공까지 검증해 제출 증거로 남긴다.

## Implementation Decisions

### 실행 범위

| 실행 시점                      | env → build → 예산                     | Lighthouse assertion |
| ------------------------------ | -------------------------------------- | -------------------- |
| 모든 PR — draft·문서 전용 포함 | CI 테스트값으로 실행                   | 생략                 |
| Production 배포 파이프라인     | 격리 검증 + 실제 배포 환경·산출물 검증 | 생략                 |
| 주간·검증용 수동 실행          | 격리된 테스트값으로 실행               | 3회 중앙값           |

기존 build 앞뒤에 검사를 추가하며 setup·install·build를 중복하지 않는다. 모든 PR의 build 뒤 기존 산출물로 서버 env 실행 검사를 수행해 E2E 생략 여부와 무관하게 실제 기동 검증을 유지한다. 예산/env 설정과 검증 스크립트는 기존 변경 필터에서 빌드·검증 입력으로 분류한다. 캐시 hit 여부로 검사를 생략하지 않는다.

### 번들 예산

size-limit의 file 플러그인으로 빌드된 파일을 검사한다.

| 대상                   | 집계 기준                                                                       |
| ---------------------- | ------------------------------------------------------------------------------- |
| 홈·상품 목록의 초기 JS | 화면의 첫 로드에 필요한 클라이언트 JS를 경로별 중복 제거해 합산. 공유 청크 포함 |
| 공유 JS                | 두 화면이 공통으로 로드하는 파일의 교집합. 화면별 합계와 별도로 표시            |
| Hero 원본 이미지       | 압축하지 않은 소스 파일 바이트                                                  |

서버 JS·source map·다른 화면의 청크는 제외한다. 화면별 합계와 공유 합계를 다시 더하지 않는다. 현재 Next.js 산출물의 파일 목록을 브라우저 초기 요청과 대조하고, 해시 파일명을 고정하지 않는다. 대상 목록·파일 누락이나 수집 실패는 검사 실패다.

JS는 같은 압축 방식과 파일별 합산 규칙을 사용한다. 리포트에 단위와 gzip·Brotli·원본 여부를 명시하며, CI의 고정 압축값을 실제 HTTP 전송량과 구분한다. 압축 설정은 [size-limit 공식 문서](https://github.com/ai/size-limit#plugins)를 따른다.

**예산 결정 절차**

1. SHA·Node·lockfile·빌드 명령·환경·측정 도구를 고정해 최소 3회 측정한다.
2. 원자료·중앙값·최솟값·최댓값·범위를 기록한다. 같은 값이 반복되면 범위는 0으로 둔다.
3. 현재 중앙값 C, 범위 R(최대−최소), 여유율 N%로 `C + R + C × N/100`을 제안한다.
4. 사용자가 여유율과 최종 임계값을 결정한다. 선택 이유와 반올림 방식까지 기록한 뒤 게이트를 활성화한다. 초과 PR에 맞춰 예산을 자동 상향하지 않는다.

7주차 Hero 전송량은 최적화 전 7,368 KiB, 최종 기록 약 409 kB다. 원자료에서 단위를 확인해 인용하고, 이 값을 JS나 Hero 원본 예산으로 직접 사용하지 않는다. **7주차 JS 전송량은 원자료 확인이 남아 있다.** 확보하지 못하면 그 한계를 명시하고 현재 측정값으로 보완한다.

### 환경변수 검증

**2026-09-11 변경 합의:** `src/env/validate.ts`에 Zod 규칙과 `validateBuildEnv()`·`validateServerEnv()`를 모은다. import만으로 검증하지 않고 호출 시 실제 환경값을 읽는다. Next.js가 환경 파일을 로딩한 뒤, `next.config.ts`의 개발/프로덕션 빌드 phase에서 빌드용 검증을, `src/instrumentation.ts`의 Node `register()`에서 서버용 검증을 호출한다. `next start`의 config 로딩에서는 빌드용 검증을 반복하지 않는다.

검증 모듈은 설정·서버에서만 import한다. Zod는 기존 버전을 dependencies로 옮겨 서버 배포에도 포함하며 클라이언트 코드에는 넣지 않는다. Next.js 실행 경로는 자체 env 로딩을 사용한다. 별도 env CLI나 dotenv 파서는 두지 않는다. 변수별 규칙은 검증 함수를 직접 테스트하고 Next 설정·서버 실행 연결은 실제 명령으로 검사한다.

| 변수                                 | 사용처                                             | 검증 시점                       |
| ------------------------------------ | -------------------------------------------------- | ------------------------------- |
| APP_ORIGIN                           | 루트 layout의 metadataBase와 요청 시 서버 API 호출 | 개발/빌드 설정 로딩 + 서버 시작 |
| AUTH_SESSION_SECRET                  | 요청 시 세션 서명·검증                             | 서버 시작                       |
| 알려진 비밀 변수의 NEXT_PUBLIC_ 변형 | 공개 번들로의 비밀 노출 방지                       | 개발/빌드 설정 로딩 + 서버 시작 |

현재 사용하지 않는 공개 API URL·CMS·결제 변수는 추가하지 않는다. 공개 변수와 정적 생성에 쓰이는 서버 값은 향후 빌드 검증에, 요청 전용 값은 서버 검증에 추가한다.

| 검사 대상                                 | 실패 조건                                                                                       |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------- |
| APP_ORIGIN                                | 누락·공백·URL 파싱 실패·http/https 외 프로토콜. Preview만 생략 허용, 있으면 같은 형식·주소 검증 |
| AUTH_SESSION_SECRET                       | 누락·공백, 배포 환경에서 기존 데모 기본값 사용                                                  |
| 알려진 서버 비밀 변수의 NEXT_PUBLIC_ 변형 | 해당 이름이 설정됨. 값이 비어 있어도 실패                                                       |
| 환경별 origin                             | Preview가 Production origin을 사용하는 등 대상 환경의 허용 주소와 불일치                        |

정상 공개 변수까지 일괄 금지하지 않는다. 오류에는 변수명과 이유만 표시한다.

로컬·CI에서는 격리된 origin과 테스트용 인증값을 사용한다. Preview·Production 빌드는 각 환경의 빌드용 값을 검증하고, 실제 서버 인스턴스는 요청 처리 전에 서버용 값을 검증한다. 런타임 전용 인증값의 누락·오류는 빌드를 막지 않지만 서버 시작과 후보의 Production 승격을 막는다. 따라서 빌드 성공만으로 운영 서버 설정의 성공이나 정상 기동을 주장하지 않는다. 환경 구분은 VERCEL_ENV를 사용하고, 도메인·비밀값은 환경설정으로 공급한다. Production secrets를 PR·정기·검증용 수동 실행에 전달하지 않는다.

**2026-09-11 변경 합의 — 예산 검사를 build 스크립트에서 분리한다.** `dev`는 `next dev`, `start`는 `next start`, `build`는 `next build`다. Next.js 명령을 직접 실행해도 해당 생명주기의 env 검증이 적용된다. 번들 예산은 `check:budget` 스크립트로 분리하고, 게이트를 강제할 자리에서 명시적으로 호출한다.

분리하는 이유는 두 실패의 성격이 다르기 때문이다. env 오류는 **산출물 자체가 무효**라 build를 막는 게 맞지만, 예산 초과는 산출물이 정상인데 **정책상 크다**는 판단이다. 같은 종료 코드로 묶으면 유효한 산출물을 만드는 일까지 정책이 막는다. 실제로 초과 상태에서 로컬 E2E(`pnpm build && pnpm start`)가 실행되지 않고, 초과 PR은 Preview 배포까지 잃어 "이 증가가 정당한가"를 판단할 화면이 사라진다.

호출 지점은 세 곳이다. CI는 build step 다음의 별도 step에서, 로컬 전체 검증은 `pnpm check`에서, 배포는 Vercel `buildCommand`에서 호출한다. 배포 과정에서 재빌드한다면 게시할 산출물에도 예산을 적용하되, **Production에서만 적용하고 Preview는 리뷰용으로 남긴다**(`VERCEL_ENV` 분기). Preview가 초과로 실패해도 얻는 것은 없다 — 병합은 이미 CI 예산 검사가 막고 있고, 잃는 것은 리뷰어가 볼 화면이다. 검증·배포 SHA를 일치시키며 CI 테스트값의 성공으로 실제 배포 환경 검증을 대신하지 않는다.

### 병합·배포 게이트

fork main의 required는 **기본 checks + PR guard**로 유지한다. 기존 guard에 env·예산 성공 조건을 추가하고, strict 설정에 따라 최신 main 반영 후 새 산출물을 다시 검사한다. 별도 예산 guard는 만들지 않는다.

빌드용 env 실패 시 production build를 시작하지 않는다. 서버용 env 실패 시 요청 처리를 시작하지 않고 Node 서버 프로세스를 종료 코드 1로 중단한다. Next 16.2.10의 register 예외 로깅만으로는 종료가 보장되지 않아 실패를 명시적으로 종료한다. CI에서 필요한 검증의 실패·취소·예상 밖 생략은 guard 성공이나 Production 게시로 이어질 수 없다. 실제 Production은 `--prod --skip-domain`으로 운영 도메인을 연결하지 않은 후보를 만든다. 후보의 동적 인증 API가 기대 상태·본문으로 응답해야 하며, 최신 main SHA를 다시 확인한 뒤 검증한 동일 배포만 promote한다. 실패·취소 시 승격하지 않아 기존 Production을 유지한다. 이 승격 전 기동 확인은 티켓 1의 env 게시 차단 범위다. 결과 출력 과정에서도 원래 종료 상태를 보존한다.

**guard 조건 재계산의 전환 (ADR-12 메모, 2026-09-10 편입)**: 이번 단계에서 guard를 확장하는 김에 핵심 E2E 실행 조건의 중복 계산을 정리한다. ① 실행 조건(main 대상 AND non-draft AND 런타임 변경)을 테스트 가능한 스크립트(예: `decide-e2e-scope.mjs`)로 추출해 workflow가 호출하고, ② main×draft×runtime 8조합의 기대값을 **손으로 적은 진리표**로 고정한 정책 테스트를 unit 집합에 둬 모든 PR에서 실행하며(기대값을 같은 조건문으로 재계산하면 중복이 테스트로 자리만 옮기므로 금지 — 테스트 대상은 CI가 실제 호출하는 그 스크립트), ③ 그 후에 guard의 조건 재계산을 제거한다. guard에는 job 결과 확인, 출력이 정확히 true/false인지 검증, 선언된 결정 대비 실제 outcome 대조가 계속 남는다. **정책 테스트 없이 재계산만 지우지 않는다.**

| 검증                                              | PR required          | 판단                                                               |
| ------------------------------------------------- | -------------------- | ------------------------------------------------------------------ |
| lint·typecheck·unit·관련 integration              | 기본 checks          | 기본 오류와 변경 관련 회귀를 병합 전에 검사                        |
| 변경 판별·build·env·예산·조건에 해당하는 핵심 E2E | PR guard             | 성능·설정 오류와 핵심 흐름 실패를 병합 전에 차단                   |
| 전체 E2E                                          | 제외, 배포 전 필수   | 매 PR의 실행 비용을 줄이되 비핵심 회귀의 Production 배포는 차단    |
| Lighthouse                                        | 제외, 정기·수동 실행 | 반복 측정 비용과 실행 환경에 따른 변동성을 고려해 성능 감시에 사용 |
| AI 리뷰                                           | 제외, 참고용         | 실행 비용과 비결정적 판단을 고려해 사람이 결과 검토                |

제출 문서에는 검증별 **실행 비용·실패 변동성·현재 실패 리스크**를 한 행씩 비교한다. 기존 측정과 신규 step 실측으로 판단을 뒷받침한다. 추가 검증·결과 게시 시간과 전체 run 시간을 구분하고, 검증 집합이 다른 과거 측정과 같은 조건의 속도 개선으로 비교하지 않는다.

### Lighthouse assertion

홈·상품 목록의 정기·수동 측정을 재사용한다. Desktop 조건·URL·시나리오·도구 버전을 기록하고, 각 3회 원자료·지표별 중앙값·범위를 남긴다. assertion도 중앙값으로 집계한다.

| 7주차 측정                | LCP 중앙값 | LCP 범위 | CLS   |
| ------------------------- | ---------- | -------- | ----- |
| 홈                        | 0.8 s      | 0.4 s    | 0.006 |
| 상품 목록 — slow 시나리오 | 0.7 s      | 0.1 s    | 0     |

LCP·CLS 임계값은 위 값과 현재 CI 분포를 비교한 뒤 정한다. 목록의 LCP가 스트리밍 API 대기를 충분히 반영하지 못했던 한계도 기록한다. 서로 다른 조건의 과거 값을 그대로 cutoff로 사용하지 않는다. FCP·TTFB는 함께 보고하며 근거 없는 종합 점수 cutoff는 추가하지 않는다. 설정은 [Lighthouse CI 공식 문서](https://github.com/GoogleChrome/lighthouse-ci/blob/main/docs/configuration.md#assert)를 따른다.

모든 PR이나 주요 화면 PR 대신 정기·수동 실행을 선택한다. 반복 측정 비용과 러너·네트워크 변동에 따른 오탐을 줄이기 위해서다. PR에서는 결정적인 크기 예산으로 증가를 차단하고, Lighthouse는 로딩 성능을 감시한다. 초과 시 정기·수동 검사 실패와 리포트로 드러내되 병합·Production 배포는 차단하지 않는다.

### PR 코멘트와 job summary

두 채널은 같은 검증 결과를 사용한다. 표시를 위해 검사를 다시 실행하지 않는다.

| 채널        | 표시 내용                                                                                                          |
| ----------- | ------------------------------------------------------------------------------------------------------------------ |
| PR 코멘트   | 검사 상태, 예산 대상·단위·측정값·base 대비 증가량·임계값·초과량·초과율, env 오류 이유, 검증 SHA, 상세 summary 링크 |
| Job summary | 전체 측정표, 선택 테스트·생략 이유·flaky, 실패 리포트·trace 링크, run·배포 결과                                    |

실패해도 가능한 결과를 남긴다. 선행 실패로 측정하지 못한 항목에는 미측정과 이유를 표시한다. 배포한 경우에만 해당 SHA의 배포 URL을 연결한다.

PR마다 식별 마커와 봇 작성자로 찾은 코멘트 하나를 갱신한다. 새 push·재실행·실패 복구 때 댓글을 추가하지 않으며, 최신 PR head와 run/attempt를 확인해 오래된 결과가 덮어쓰지 않게 한다. 실행별 기록은 summary에 보존한다. 게시 수단은 기존 GitHub CLI/API로 충분하면 재사용한다.

**2026-09-11 변경 합의 — 게시를 `workflow_run` 워크플로로 분리한다.** `pull_request` 이벤트에서는 workflow 파일과 스크립트가 모두 PR이 고칠 수 있는 코드라, 같은 이벤트 안에서는 "PR 코드를 실행하지 않는 게시 job"을 만들 수 없다. Quality 완료를 받는 별도 `workflow_run` 워크플로가 default branch의 코드만 실행하고, 결과는 Quality가 올린 리포트 artifact와 job 결론 API로 받는다. 코멘트 게시 워크플로에만 pull-requests: write를 두고, Quality의 job에는 주지 않는다. pull_request_target이나 별도 고권한 토큰으로 우회하지 않는다. [GitHub 권한 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions).

이 분리로 외부 fork PR도 코멘트를 받는다. 대신 리포트 파일은 PR 코드가 만든 신뢰할 수 없는 입력이므로, 게시 전에 코멘트 마커 위조와 멘션을 무력화하고 길이를 제한한다. 표는 그대로 렌더링한다.

**base 대비 증가량**은 main push가 남긴 측정값을 캐시로 받아 예산 검사가 직접 계산한다. 기준선이 없으면 열을 생략하고 그 사실을 적으며, 판정 자체는 고정 상한으로만 한다 — base를 다시 빌드하지 않는다.

게시 실패는 summary에 표시하고 기존 검증 결과를 유지한다. 댓글 전송 자체를 required로 만들지 않는다. PR이 없는 main·정기·수동 실행은 summary만 생성한다. `workflow_run`은 default branch의 워크플로만 실행하므로, 게시 동작은 이 변경이 main에 병합된 뒤부터 확인할 수 있다.

## Testing Decisions

주 검증 경계는 실제 Quality CI의 입력부터 PR status·코멘트·summary·병합 및 배포 결과까지다. 내부 함수 호출이나 YAML 문자열 대신 관찰 가능한 동작을 확인한다. 기존 origin 오류·인증 테스트와 fork PR의 실행 증거 수집 방식을 재사용한다.

크기·env 스크립트에는 실제 명령의 종료 코드와 공개 출력을 확인하는 작은 실행 검사를 남긴다. env는 실제 `next build`의 설정 로딩 연결까지 검사하고, 배포 검사는 CLI 진입부터 HTTP 상태·본문 판정과 실패 종료까지 실행한다. 외부 Vercel 요청만 테스트 응답으로 대체하며 인증값 없이도 실패 원인을 읽을 수 있어야 한다. Next 설정 재로딩 때도 검증은 수행하되, 성공 summary는 CI Build 완료 지점에서 한 번만 기록한다. 실패 이유는 검증 지점에서 즉시 기록한다.

| 검증                       | 기대 결과                                                                                                                                                   |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 예산 정상·임계값 동일·초과 | 이하 통과, 초과 실패. 대상 파일 누락·수집 실패도 실패                                                                                                       |
| env 오류                   | origin·비밀 공개 변수 오류는 개발/빌드 전에 실패. 인증값 누락·공백·배포 기본값은 서버 시작 때 실패. 정상 공개 변수 허용·값 비노출                           |
| env 실행 시점              | import만으로 검사하지 않음. 인증값 없이 실제 build 성공, 같은 산출물의 잘못된 서버 env는 시작 실패, 정상 env는 요청 처리                                    |
| 환경 분리                  | CI는 테스트값으로 통과. Preview의 Production origin 오설정과 실제 배포 env 오류는 차단                                                                      |
| PR 조건                    | 문서·draft도 env/build/예산 실행. 기존 E2E 조건 유지. ready·base·main 갱신 후 최신 산출물 검사                                                              |
| 실패 전달                  | 실패·취소·예상 밖 생략이 성공으로 바뀌지 않음. 요약·코멘트 게시가 게이트 결과를 덮지 않음                                                                   |
| 코멘트                     | PR당 하나를 최신 결과로 갱신. 쓰기 불가·게시 실패 시 summary 유지                                                                                           |
| Production                 | 예산/빌드용 env 실패 시 게시 미실행·기존 배포 유지. 서버용 env 실패는 요청 처리 시작·후보 승격 차단 및 기존 Production 유지. 정상 게시 경로는 같은 SHA 검증 |
| Lighthouse                 | 3회 원자료와 중앙값 assertion 일치. 초과 리포트 표시. PR·배포 조건과 분리                                                                                   |

### 빨간불 실험과 복구

1. 소유 fork main을 대상으로 실험 PR을 하나 이상 만든다. 공통 클라이언트 경로에서 실제로 사용하는 코드·자산을 키워 예산을 초과시킨다.
2. **예산 검사 때문에** CI가 실패하고 required가 병합을 막는지 확인한다. 임계값만 낮추거나 압축으로 사라지는 주석을 넣는 것으로 대신하지 않는다. 새 라이브러리 없이 재현할 수 있으면 그 방법을 쓴다.
3. 원시 로그 없이 PR 코멘트에서 대상·측정값·임계값·초과량을 읽고 summary와 대조한다. 불명확하면 출력을 수정하고 같은 실패 상태에서 재실행·재확인한다.
4. 실패 코멘트와 summary 화면을 캡처한다. 성공 결과로 코멘트를 갱신하기 전에 실패 증거를 보존한다.
5. 같은 PR에서 초과 변경을 원복한다. 임계값·검증 조건은 유지하고 새 SHA에서 예산·required 성공과 코멘트의 성공 갱신을 확인한다. 검증 전 PR diff가 사라지지 않도록 필요한 경우 동작에 영향 없는 변경을 남긴다.
6. 성공 화면도 캡처하고 실험 PR은 **머지 없이 닫는다**. 실패·성공 각각의 SHA·run URL·스크린샷과 PR URL을 제출 문서에 연결한다. 예산 검사가 생략된 run은 성공 증거로 인정하지 않는다.

Production 차단은 실제 게시 직전의 검증 경로에서 확인한다. 실패 산출물을 공개하거나 게이트를 우회하지 않는다. 실제 배포 연결을 확인하지 못했다면 미완료로 남긴다.

### 완료 조건과 제출물

기존 CI 기록 문서에 아래 증거를 모으고 최종 제출 PR에서 참조한다.

- [ ] 확정 임계값, 7주차 값 인용, 현재 3회 측정 원자료·범위, 여유폭 산정 이유.
- [ ] 실제 required 설정과 검증별 비용·변동성·실패 리스크에 따른 포함·제외 판단.
- [ ] 초과 PR의 빨간불·병합 차단, **PR 코멘트와 summary의 실패 리포트 스크린샷**.
- [ ] 같은 예산 기준의 원복 후 초록불, 성공 화면, 실패·성공 각각의 SHA·run과 미병합 실험 PR 링크.
- [ ] 실제 배포 환경 검증·Production 차단 증거와 정상 배포의 SHA·run·URL.
- [ ] Lighthouse assertion 근거, 실행 시점 선택 이유, 측정·초과 리포트.
- [ ] 실험 잔재 제거, pnpm check와 새 검증 명령 통과, self-review 완료.

소유 fork 내부 실험 PR에서는 코멘트와 summary가 모두 표시되어야 가시성 완료로 판정한다. 스펙 작성이나 검사 설정만으로 구현 완료를 표시하지 않는다.

## Out of Scope

- 새 화면·업무 기능, 성능 최적화 자체, 모든 페이지·정적 파일의 총량 예산.
- 기존 E2E 실행 정책 재설계, merge queue, 전체 E2E의 PR required 전환.
- AI 리뷰 구현·룰 승격·Docker·최종 회고·승격 후 별도 상시 smoke 기능. 티켓 1의 승격 전 기동 확인은 범위에 포함한다.
- 자동 예산 상향, 별도 리포트 서버·대시보드·상시 실행 봇, 클라이언트에 Zod를 넣는 리팩터링.
