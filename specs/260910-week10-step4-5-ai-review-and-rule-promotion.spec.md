# 10주차 Step 4–5 — 프로젝트 AI 리뷰와 결정적 룰 승격

> 초안 · 2026-09-10. 실행 정책과 스킬 배치의 미결정 사항은 Further Notes에 정리한다.

## Problem Statement

10주간 학습한 기준이 컨벤션·스킬·개별 설계 문서에 나뉘어 있다. 기존 컴포넌트·아키텍처·테스트 리뷰만으로는 상태 설계, 테스트 설계, E2E 범위 판단까지 일관되게 검토하기 어렵다. 필요한 규칙을 명문화하고 실제 AI 리뷰에 연결해야 한다.

AI 리뷰에는 오탐이 있으므로 작성자가 근거로 판별해야 한다. 반복 지적 중 결정적으로 판별할 수 있는 것은 기계에 맡겨 같은 검토를 되풀이하는 비용을 줄인다.

## Solution

1~10주차 학습 기준을 프로젝트의 rule·skill로 정비한다. 설계·측정·테스트 검토에는 필요한 입력과 판단 절차를 갖추고, PR diff 리뷰에는 변경과 관련된 기준을 연결한다.

실제 리뷰에서 유효 지적 1개와 오탐 1개를 판별하고 프롬프트 개선 전후를 비교한다. 이어서 반복 지적 하나를 결정적 게이트로 승격해 위반 차단·정상 통과를 증명하고, 기계·AI·사람의 책임을 기록한다. 4·5단계는 한 스펙으로 진행하며, 승격 대상은 4단계의 증거를 확보한 뒤 선택한다.

## User Stories

1. As a 작성자, I want 주차별 학습 기준의 반영 여부를 확인하기를, so that 빠진 rule·skill을 찾아 보완한다.
2. As a 유지보수자, I want 기존 지침과 새로 필요한 지침을 구별하기를, so that 정본과 적용 범위가 명확해진다.
3. As a 개발자, I want 컴포넌트의 책임과 패턴을 구현 전후에 검토하기를, so that 분리·합성·상태 소유권을 설명한다.
4. As a 설계자, I want 상태 분류의 전제와 로그인 전환을 반박받기를, so that 동기화와 수명의 빈틈을 발견한다.
5. As a 개발자, I want 성능 관련 변경의 측정 근거를 확인하기를, so that 근거 없는 최적화를 걸러낸다.
6. As a 테스트 작성자, I want 시나리오와 검증 경계를 먼저 검토하기를, so that 지킬 동작·단언·모킹 범위를 직접 결정한다.
7. As a 테스트 작성자, I want AI 생성 픽스처와 테스트를 검수하기를, so that 잘못된 계약과 거짓 초록불을 발견한다.
8. As a 테스트 작성자, I want 로그와 통합 테스트의 한계로 E2E 범위를 검토하기를, so that 비싼 검증의 포함·제외를 설명한다.
9. As a 유지보수자, I want workflow와 실행 증거를 함께 검토하기를, so that 필요한 검증의 실행과 실패 전파를 확인한다.
10. As a PR 작성자, I want 고정한 diff에 프로젝트 기준 리뷰를 받기를, so that 변경에 관련된 규칙과 설계 위험을 확인한다.
11. As a 리뷰어, I want 지적의 위치·기준·근거·불확실성을 확인하기를, so that 수용과 반려를 판단한다.
12. As a PR 작성자, I want 설계·리뷰 지침 변경에도 적절한 검수를 받기를, so that 문서 변경으로 분류되어 검토가 빠지지 않는다.
13. As a 관리자, I want AI 실행량·시간·권한을 제한하기를, so that 중복 실행·과금·자격 증명 노출을 통제한다.
14. As a PR 작성자, I want AI 리뷰의 실패와 미완료가 표시되기를, so that 지적 없음이나 결정적 검사 결과와 혼동하지 않는다.
15. As a 작성자, I want 유효 지적과 오탐을 직접 판별하기를, so that 프롬프트 수정의 근거를 남긴다.
16. As a 작성자, I want 같은 diff에서 프롬프트 전후를 비교하기를, so that 오탐 감소와 유효 지적의 유지 여부를 확인한다.
17. As a 유지보수자, I want 실제 반복 지적에서 규칙 하나를 고르기를, so that 반복 리뷰 부담을 결정적 검사로 줄인다.
18. As a 개발자, I want 승격 룰이 위반을 막고 정상·예외를 통과시키기를, so that 신뢰할 수 있는 병합 게이트를 갖는다.
19. As a 작성자, I want 실행·판정·게이트 증거와 책임을 연결하기를, so that 무엇을 AI·사람·기계에 맡겼는지 설명한다.

## Implementation Decisions

### 1. Rule·skill 정비

주차별 학습 목록의 각 항목에 **유지·보완·신규·해당 없음**, 근거, 정본, 적용 시점, 기계 검사 여부를 기록한다. 아래 범위를 실제 지침에 반영하며 세부 출처·예외는 요구사항 감사의 대조표를 사용한다.

| 규칙 영역 | 명문화할 내용 |
| --- | --- |
| 공통·컴포넌트·FSD | 타입/린트 침묵, 기존 유틸 재사용, 입력 신뢰 경계, 책임 분리, props·합성·제어권, Hook의 역할, 레이어·Public API·공인 예외 |
| 상태·데이터 | 원본·수명·공유 범위, API 계층, Query key/옵션/캐시, mutation 취소·복구·재검증, URL parser·이력, selector·persist·migration |
| 오류·렌더링 | 오류 종류별 처리 위치, 복구와 reset, 초기/재조회 상태 전환, 오래된 응답, 로딩 경계·레이아웃 공간·접근성 |
| SSR·성능 | 요청별 격리·hydration, 메타데이터·캐시 정합성, 관측과 가설의 구분, 동일 조건 측정·반증 |
| 인증·계측 | return URL 검증, 비로그인/만료 구별, 사용자 전환 시 캐시·진행 중 응답, 이벤트 계약, 로그의 분모·중복·관측 한계 |
| 테스트·E2E | 공개 동작·단언·모킹 경계, MSW·픽스처 계약, 테스트 무력화 금지, mutation 검수, 계정/상태 격리, 조건 대기·최종 결과 단언·flaky 분석 |
| CI·AI | 실행/생략 조건, required·배포·실패 전파, 캐시·concurrency·권한, 리뷰 입력·실행 한도·판정·룰 승격 |

기존 정본은 보완하고 중복 복사하지 않는다. 최신 사용자 요구와 유효한 프로젝트 결정을 발제의 일반 예시보다 우선하며, 충돌은 보고한다. E2E와 CI 스크립트 테스트까지 검수 범위에 포함하고 실제 lint가 검사하는 범위를 명시한다.

### 2. AI 검토 절차와 연결

각 절차는 입력, 검토 기준, 출력, 사람의 결정 지점을 갖는다. 기존 스킬은 보완하고 독립적인 입력·출력이 필요한 절차는 신규 스킬로 제공한다. 최종 스킬 배치는 Further Notes의 미결정 사항이다.

| 검토 기능 | 입력 → 검토 결과 | 정비 방향 |
| --- | --- | --- |
| 컴포넌트·패턴 | 현 코드·사용처·라이브러리 소스 → 책임 분류, 분리/유지 이유, 제어권·합성 판단 | component-review·analyze-component 보완 |
| 상태 설계 | 상태 분류 표·전환 시나리오 → 성립 전제, 동기화 반례, 미결정 사항 | 신규 절차 |
| 구조 | 현 코드·프로젝트 구조 규칙 → 레이어·의존 방향·Public API 판단 | architecture-review 연결 |
| 테스트 설계 | 사용자 시나리오·스펙 → 공개 동작·검증 경계·단언/모킹 후보 | 신규 절차, 최종 의도는 작성자 결정 |
| 테스트 생성물 | 확정 의도·픽스처·MSW·테스트 → 계약 오류·무력한 단언·격리/대기 문제 | test-review에 E2E·스크립트·mutation 검수 보완 |
| E2E 범위 | 로그·흐름 후보·통합 테스트 범위 → 포함/제외 근거와 관측 한계 | 신규 절차, 최종 범위는 작성자 결정 |
| Workflow | YAML·호출 스크립트·정책·run → 병합 방어, concurrency, 캐시/필터, required/생략, 권한/secrets 검토 | 신규 절차, 3단계 반영 후 최종 리뷰 |
| PR·셀프 리뷰 | spec·고정 diff·관련 지침 → 요구사항 누락·동작/의존성/타입/보안 지적 | code-review·self-review 연결 보완 |
| 룰 승격 | 반복 지적·판정·예외 → 룰 초안·실행 검증·책임 이동 | 아래 5단계 절차를 스킬로 제공 |

상태 설계 검토에는 상태 분류와 전환 시나리오를 제공한다. 입력이 부족하면 필요한 자료와 미검토 범위를 보고한다. 성능 기준은 rule로 명문화해 관련 변경의 리뷰에 적용한다. 로컬/CI 도구가 관련 지침을 실제로 읽는 경로를 연결하며, 변경과 무관한 모든 스킬을 매번 실행하지 않는다.

### 3. PR diff 리뷰와 실행 제어

- 기존 무유도 로컬 리뷰를 유지하고 프로젝트 기준 리뷰를 추가한다. 실행 위치와 트리거는 Further Notes에서 확정한다.
- 시작 시 base·head·merge-base와 프롬프트 버전을 고정한다. diff와 같은 head의 호출부·계약·예외를 읽고, 입력 수집 실패나 잘림은 실패/부분 리뷰로 표시한다.
- 지적에는 규칙 식별자·파일/위치·근거·확신도를 남긴다. 정상 예외와 기계 검사 범위를 반영하고 불확실한 판단은 질문으로 표시한다.
- 자동 리뷰의 기준·도구 설정은 고정한 base에서 읽는다. 최초 도입이나 비교 실험은 작성자가 검토한 프롬프트 버전을 명시한다. PR 내용은 검토 자료로 취급하며 실행 지시로 따르지 않는다.
- AI 리뷰는 **advisory**로 둔다. 비용과 비결정성 때문에 required·PR guard·배포 성공 조건에 넣지 않으며, 실패·timeout·미실행을 지적 없음과 구별한다.
- `max_turns`·timeout·concurrency와 입력/재실행 한도를 정하고 소진 시 중단·미완료 사유를 남긴다. turns·시간 제한을 금액 상한으로 간주하지 않고 선택한 인증/과금 경로의 사용량 제한을 확인한다.
- CI 선택 시 기존 변경 판별을 재사용하되 AI 조건을 핵심 E2E 조건과 분리한다. 일반 문서, 설계 문서, rule·skill·prompt 변경의 검수 경로를 구별한다.
- CI 결과는 대상 SHA·프롬프트 버전·run과 함께 PR 코멘트에 표시한다. 중복/오래된 게시를 막고 게시 실패는 summary나 run 종료 상태에 남긴다.
- CI의 자격 증명과 쓰기 권한은 필요한 작업에만 부여한다. 자격 증명이 있는 실행에서 PR head의 코드·설치 스크립트·Hook을 실행하지 않는다. secrets를 출력하지 않고 외부 fork의 인증 불가를 `pull_request_target`으로 우회하지 않는다.

### 4. 리뷰 판별과 프롬프트 개선

1. 실제 구간 PR을 리뷰한다. 사례가 부족하면 과거 실제 diff를 보조 자료로 사용하고 출처와 SHA를 남긴다.
2. 작성자가 **유효 지적 1개·오탐 1개**를 원문·규칙·코드 근거로 판정한다. 실제 오탐을 확보하지 못하면 미확보로 남긴다.
3. 오탐을 유발한 프롬프트 조항을 수정하고 같은 diff·모델·주요 실행 조건에서 다시 실행한다. 실제 적용한 v1/v2 버전을 기록한다.
4. 유효/오탐/보류 결과와 기존 유효 지적 유지 여부를 비교한다. 개선이 없으면 그대로 기록하며 한 번의 비교를 보편적인 정확도 향상으로 주장하지 않는다.

### 5. 반복 규칙의 결정적 게이트 승격

1. AI 또는 사람이 반복 지적한 실제 사례를 집계한다. 같은 diff 재실행의 중복은 제외하고, 빈도·영향·판별 가능성·예외를 근거로 작성자가 규칙 하나를 선택한다.
2. 검출할 위반·정상·허용 예외와 기존 검사에서 놓치는 범위를 명시한다. 후보를 기존 네 항목으로 제한하지 않으며, 이미 있는 FSD·테스트 단언 규칙을 신규 승격으로 세지 않는다.
3. 작성자가 정한 판정식에 따라 AI가 룰 초안을 작성한다. import·구문은 기존 ESLint 규칙/selector를 우선 검토하고, 파일·구조는 스크립트/CI 검사 등 성격에 맞는 수단을 선택한다.
4. 실제 검사로 위반·정상·경계 사례를 검증한다. 오탐이면 룰을 좁히고 재검증한다. 선택한 검사의 실패를 기존 required와 배포 전 검사에 연결한다.
5. 정확히 승격한 검출 범위를 AI의 반복 검사에서 빼고 아래 책임과 증거를 제출 기록에 남긴다.

| 담당 | 책임 |
| --- | --- |
| 기계 | 기존 검증과 승격한 판정 범위를 반복 검사하고 위반 차단 |
| AI | 설계·컨벤션의 반례/누락 제안, 룰 초안과 검증 보조 |
| 사람 리뷰어 | 설계 대안·변경 위험·맥락 판단 |
| 작성자 | 동작·단언/모킹·E2E 범위·예산/required·리뷰 수용/반려·승격 선택과 최종 검증 |

## Testing Decisions

검증 경계는 **실제 리뷰 도구의 입력/출력과 기존 fork PR의 CI 결과**다. 지침 문구나 YAML 모양 대신 적용된 기준, 지적 근거, 실행 상태, 위반 차단을 확인한다.

승격 룰에는 실제 CI 검사와 같은 설정을 사용하는 작은 회귀 검사를 남긴다. 위반·정상·예외의 종료 상태와 진단을 확인하고, unit-node에서 실행되도록 연결한다. 기존 CI 스크립트 테스트와 fork PR의 실패→복구 기록 방식을 재사용한다.

| 검증 | 완료 조건 |
| --- | --- |
| 학습 기준 반영 | 주차별 항목마다 반영 위치/제외 이유가 있고 합의한 rule·skill이 실제로 변경됨 |
| 검토 절차 연결 | 신규/변경 절차에 대표 입력·정상 예외·입력 부족 사례를 주어 관련 지침 선택과 결과/미검토 범위를 확인함 |
| Diff 리뷰 | SHA·지침 버전·검토 범위가 고정되고 실패/잘림이 전체 리뷰 성공으로 표시되지 않음 |
| 실행 제어 | 한도·중복 취소·인증 불가·timeout이 합의한 정책대로 처리되며 AI 결과가 required에 영향을 주지 않음 |
| CI 선택 시 | 트리거/생략, 지침 변경 검수, 최소 권한, 코멘트 최신성·게시 실패 처리의 실제 run 증거가 있음 |
| 리뷰 판별·개선 | 유효 지적 1·오탐 1의 작성자 판정과 동일 diff의 v1/v2 원문·수정 근거·비교 결과가 있음 |
| Workflow 리뷰 | 3단계까지 반영한 workflow의 5관점 검토와 수용/반려 근거가 있음 |
| 승격 룰 | 위반은 해당 검사로 실패, 정상/예외는 통과. 회귀 검사가 실제 실행되며 룰 제거 시 검출 단언이 실패함 |
| Required 연결 | fork 실험 PR에서 위반으로 병합 차단, 같은 룰을 유지한 원복 커밋에서 복구됨. SHA·run·PR 증거를 보존함 |
| 책임·제출 | 기계로 옮긴 범위와 AI/사람에 남긴 판단, 지침 변경·리뷰·게이트 증거가 연결됨 |

실험 위반은 최종 변경에서 제거하고 main에 병합하지 않는다. 구현 후 관련 검사·프로젝트 전체 검사·self-review를 완료한다. AI 출력의 정확한 문장이나 지적 개수는 자동 통과 조건으로 고정하지 않는다.

## Out of Scope

- RFC 검토와 성능 분석 전용 스킬 생성.
- 여러 후보의 일괄 게이트 승격, 기존 FSD·테스트 규칙의 재구현, 별도 룰 엔진·리뷰 대시보드.
- 맥락 판단이 필요한 상태 복사·추상화·성능 효과를 무조건적인 문법 규칙으로 차단하는 일.
- AI의 자동 수용/반려·수정·머지, 선택한 PR 리뷰 외 신규 유료 API 도입, 선택 전 무인 탐색·시각 회귀·planner/generator 실험 도입.
- 1~3단계 CI 정책 재설계, Docker 실습, 6단계 전체 회고. 승격 룰에 필요한 수정을 제외한 앱 기능 변경.

## Further Notes

**미결정 사항**

| 항목 | 결정할 내용 |
| --- | --- |
| 스킬 배치 | 상태 설계·테스트 설계·E2E 범위·workflow·룰 승격의 신규 스킬과 기존 스킬 확장의 최종 배치 |
| 실행 정책 | 확정: 별도 GitHub Actions의 PR 자동 리뷰·advisory. 코드/설계/지침은 실행, 일반 문서는 사람 검토. 기존 무유도 로컬 리뷰 유지 |
| 도구·한도 | 확정: gpt-5.6-luna·API 별도 과금, 호출 1회·3분·입력 1MiB·출력 6,000토큰, 수동 재실행 1회. 저장소 secret·main 반영·실제 API 응답과 댓글 게시 확인(PR #25), 외부 상태 미검토는 partial로 표시 |
| 선택 기능·자료 | AI 탐색·시각 회귀·planner/generator의 실제 도입 여부. 10주차 발제 원본 확보 후 추가 대조 |

주차별 근거와 상세 후보/예외는 [요구사항 감사](../docs/rfc/week10-ai-review-requirements-audit.md)에 둔다. 확인 범위는 1~9주차 발제, 1~10주차 과제와 4·5단계 요구사항이다. 선택 기능의 검수 기준도 학습 목록에는 남긴다.

2·3단계 CI를 선행 기반으로 사용하며 실제 반영 상태는 구현 착수 시 확인한다. 실행·판정·게이트 증거는 기존 CI 기록에 연결한다.
