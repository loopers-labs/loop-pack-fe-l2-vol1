# 9주차 5단계 — E2E 자가 검증 스펙

## 목표

인증 구현을 한 곳씩 의도적으로 망가뜨려 4단계 E2E가 약속한 동작을 실제로 보호하는지 확인한다. 최소 세 번 실험하고, 그중 하나는 통합 테스트는 통과하지만 실제 브라우저 E2E만 실패하는 사례로 확인한다.

## 비범위

- 주문 등 인증 외 구현을 망가뜨리는 실험
- 한 실험에서 구현을 두 곳 이상 변경
- 망가진 구현을 둔 상태에서 테스트 코드 수정
- 3단계에서 정하지 않은 E2E 시나리오 추가
- 테스트 통과를 위한 애플리케이션 동작 완화
- 외부 의존성이나 테스트 환경설정 변경
- 망가뜨린 구현을 최종 변경에 남기는 것

## 조사 결과

- 미로그인 사용자의 보호 경로 진입과 로그인 후 `/orders/new` 복원은 `e2e/auth.spec.ts`가 실제 브라우저에서 검증한다.
- 세션 만료 후 이유와 원래 경로를 담은 로그인 이동은 `e2e/session-expired.spec.ts`가 검증한다.
- 로그인 API 통합 테스트는 직렬화된 세션 쿠키 헤더를 검사하며, 현재 `Path=/` 단언은 `toContain`이라 `Path=/api`도 통과한다. 헤더 값을 더 정확히 단언할 수는 있지만, 설정된 Path를 브라우저가 실제로 해석해 다음 보호 경로 요청에 쿠키를 보내는지는 실제 앱 E2E가 검증한다 (`src/app/api/auth/route.test.ts`).
- proxy 통합 테스트는 로그인 URL의 `next` 값을 직접 검사하므로 복원 경로 제거를 잡을 수 있다 (`src/proxy.test.ts`).
- 세션 만료 통합 테스트는 `CommerceError`를 직접 렌더해 리다이렉트와 상태 정리를 검사한다 (`tests/session-expired.dom.test.tsx`).
- Playwright는 `pnpm build && pnpm start`로 production build 위에서 실행된다 (`playwright.config.ts`).
- 과제 결과 기록은 PR 본문이 기본 위치이며, 실험마다 변경점·결과·실패 테스트·실패 메시지의 진단 가능성을 남겨야 한다 (`docs/assignments/week-09.md`).

## 결정 사항

- **D1: 실험은 1 · 2 · 3 세 개만 수행한다.** 최소 개수로 쿠키의 브라우저 적용, 보호 경로 복원, 세션 만료 처리를 각각 확인한다.
- **D2: 실험 1은 로그인 응답의 세션 쿠키 `path`만 `/`에서 `/api`로 바꾼다.** 전체 통합 테스트는 통과하고 보호 경로 복원 E2E는 실패해야 한다. 통합 테스트는 쿠키 헤더를 확인하고, E2E는 브라우저가 쿠키 Path를 실제 요청에 적용하는 동작을 확인한다.
- **D3: 실험 2는 proxy가 로그인 URL에 전달하는 `pathname + search`만 `/`로 바꾼다.** 전체 통합 테스트와 보호 경로 복원 E2E가 모두 실패해야 한다.
- **D4: 실험 3은 세션 만료 effect의 `if (!sessionExpired) return`만 `if (sessionExpired) return`으로 반전한다.** 전체 통합 테스트와 세션 만료 E2E가 모두 실패해야 한다.
- **D5: 각 실험은 순차적으로 수행한다.** 변경 전 기준 상태를 확인하고, 구현 한 곳 변경 → 전체 `pnpm test` → 대상 E2E → 결과 기록 → 구현 복구 → 대상 파일 diff 확인 순서를 지킨다. 한 실험의 변경을 다음 실험에 누적하지 않는다.
- **D6: 실험 중에는 기존 테스트 코드를 수정하지 않는다.** 변경이 살아남으면 먼저 구현을 복구하고, 놓친 이유를 기록한 뒤 기존 범위 안에서 최소 단언을 보강한다. 이후 같은 구현 변경을 다시 적용해 실패를 확인하고 다시 복구한다.
- **D7: 대상 E2E는 해당 변경을 지키기로 한 테스트만 실행한다.** 실험은 전체 E2E 파급 범위를 조사하는 작업이 아니므로, 결과에는 실행 범위를 밝힌다. 모든 E2E는 구현을 복구한 최종 `pnpm check`에서 확인한다.
- **D8: E2E를 실행하기 전 포트 3000이 비어 있고 다른 build·Playwright 실행이 없는지 확인한다.** 서버 시작·production build·포트 충돌 실패는 테스트가 구현 결함을 잡은 결과로 세지 않고, 원인을 제거한 뒤 다시 실행한다. 점유 프로세스는 이전 Playwright 실행이 만든 것인지 확인하지 않고 종료하지 않는다.
- **D9: 통합 테스트도 잡은 실험 2와 3은 E2E의 고유 가치를 다시 판단해 기록한다.** 두 테스트 모두 4단계의 필수 인증 시나리오이므로 삭제하지 않는다. 실험 2는 실제 proxy 실행부터 로그인과 보호 화면 도착까지의 연결을, 실험 3은 실제 API 401부터 React Query와 에러 경계를 거친 브라우저 이동을 확인한다. 통합 테스트와 같은 세부 단언이 중복된다면 단언을 줄일지 검토한다.
- **D10: 결과는 PR 본문에 과제 표 형식으로 기록한다.** `결과`에는 통합 테스트와 대상 E2E의 결과를 구분하고, `실패 메시지로 원인을 알 수 있었나`에는 예·부분적·아니오 중 하나와 실제 메시지로 추론할 수 있었던 범위를 함께 쓴다.
- **D11: AI 사용 범위를 PR 본문에 공개한다.** AI는 실험 후보 나열과 스펙 초안 작성에 사용했고, 최종 실험 범위와 기존 E2E의 핵심 단언은 제출자가 검토하고 확정했음을 기록한다.

### 판단

- **E2E만 잡은 항목:** 실험 1에서 `pnpm test`의 46개 파일·389개 테스트는 모두 통과했고 대상 E2E만 실패했다. 통합 테스트는 응답의 `Set-Cookie` 헤더를 확인하지만, 브라우저가 Path를 해석해 `/orders/new` 요청에 쿠키를 보낼지는 확인하지 않는다. 실제 브라우저가 쿠키를 보호 경로에 보내지 않아 proxy가 다시 로그인으로 보낸 동작을 E2E가 잡았다.
- **실험 2의 E2E 유지 이유:** proxy 통합 테스트가 `next` 값을 더 직접적으로 알려줬다. 그래도 E2E는 실제 proxy 실행, 브라우저 리다이렉트, UI 로그인, 보호 화면 도착을 한 흐름으로 확인하는 4단계 필수 인증 시나리오이므로 유지한다.
- **실험 3의 E2E 유지 이유:** DOM 통합 테스트가 `CommerceError`를 직접 렌더해 만료 분기를 정확히 잡았다. E2E는 실제 `/api/orders`의 401이 React Query와 Next 에러 경계를 지나 브라우저의 로그인 이동으로 연결되는지를 확인하는 4단계 필수 인증 시나리오이므로 유지한다.
- **살아남은 변경:** 세 실험 모두 해당 E2E가 잡았으므로 없었다. 테스트 코드를 수정하거나 E2E 범위를 늘리지 않았다.
- **실행 범위:** 각 실험에서 전체 `pnpm test`와 해당 변경을 지키기로 한 대상 E2E만 실행했다. 전체 E2E 파급 범위는 조사하지 않았고, 구현 복구 후 최종 `pnpm check`로 전체 회귀를 확인했다.
- **인프라 판정:** 각 E2E 전에 포트 3000이 비어 있는지 확인했다. 서버 기동·build·포트 충돌 실패는 없었고, 기록한 실패는 모두 테스트 단언 실패였다.
- **실험 후 리뷰 조치:** 세 인증 실험과 구현 복구를 모두 마친 뒤, 기존 다이얼로그 E2E의 조건부 `test.skip`을 제거했다. 환경마다 다른 스크롤바 폭과 padding 구현은 통합 테스트에 두고, E2E에서는 다이얼로그를 열기 전후 콘텐츠의 실제 위치가 같은지만 검증한다. 인증 실험 대상 테스트는 수정하지 않았으며 위 결과는 이 리뷰 조치 전에 확정했다.
- **복구 확인:** 각 실험 직후 세 구현 파일의 대상 diff가 기준 상태와 같은지 확인했다. 최종 상태에서 `pnpm check`가 통과해 Vitest 46개 파일·389개 테스트, lint, typecheck, production build, Playwright 15개 테스트가 모두 통과했다.
- **AI 사용:** AI는 실험 후보 나열, 스펙 초안, 반복 실행과 결과 정리에 사용했다. 최종 실험 범위와 기존 E2E의 핵심 단언은 제출자가 검토하고 확정했다.
