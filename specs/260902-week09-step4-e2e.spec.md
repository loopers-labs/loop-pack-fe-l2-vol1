# 9주차 4단계 — 인증과 주문 E2E 스펙

## 목표

`docs/rfc/week09-e2e-scope.md` C절에서 정한 범위만 production build 위의 Playwright로 검증한다.

- 인증 플로우의 필수 세 갈래: 보호 경로 복원 · 세션 만료 · 잘못된 자격 증명
- 인증 외 선택 경로 한 개: 장바구니 담기부터 주문 내역 반영까지
- 로그인 자체가 검증 대상이 아닐 때만 워커별 `storageState`를 재사용한다.

## 비범위

- 목록 · 필터 · 정렬 · 페이지 이동 E2E 추가
- 주문 실패 UI와 재시도 E2E 추가
- 인증 쿠키나 브라우저 저장소를 직접 만들어 인증 성공을 우회
- CSS 구조 셀렉터, 테스트 전용 id, 시간 기반 대기
- 범용 Page Object 계층과 새 외부 의존성
- 애플리케이션 동작과 `playwright.config.ts` 변경

## 조사 결과

- Playwright는 이미 `pnpm build && pnpm start`로 production build를 실행한다 (`playwright.config.ts`).
- 로그인 성공은 서명된 `session` 쿠키를 `httpOnly`, `SameSite=Lax`로 설정한다 (`src/app/api/auth/login/route.ts`).
- `/orders/:path*`는 `proxy.ts`가 보호하며 원래 경로를 로그인 URL의 `next`에 보존한다 (`src/proxy.ts`).
- `expired`와 `invalid`는 `scenario` 쿠키로 실제 API에서 결정적으로 재현할 수 있다 (`src/app/api/auth`, `src/app/api/orders`).
- 장바구니는 `localStorage`, 주문 draft는 `sessionStorage`를 쓴다. Playwright `storageState`는 draft를 보존하지 않으므로 주문 테스트에서 실제 UI로 draft를 만든다 (`src/entities/cart`, `src/entities/order`).
- 주문 저장소는 사용자별이므로 병렬 실행의 서버 데이터를 워커별 계정으로 격리할 수 있다 (`src/app/api/_data/auth.ts`).

## 결정 사항

- **D1: E2E 대상은 RFC의 두 경로뿐이다.** 인증은 요구된 세 테스트로 나누고 주문 완료는 한 테스트로 만든다.
- **D2: 공통 로그인 동작은 `submitLoginForm` 함수 하나로 공유한다.** 역할과 접근 가능한 이름으로 이메일 · 비밀번호 · 로그인 버튼을 찾는다. 범용 Page Object는 만들지 않는다.
- **D3: 인증 상태가 전제인 테스트는 워커 fixture를 사용한다.** `parallelIndex`에 따라 8개 계정 중 하나를 배정하고, 워커가 UI 로그인을 한 번 수행한 직후의 `storageState`를 `test-results` 아래에 저장한다. 8개를 넘는 워커는 계정 충돌 대신 명시적으로 실패시킨다.
- **D4: 로그인 성공·실패 테스트는 기본 Playwright `test`와 빈 `storageState`를 사용한다.** 저장된 인증 상태를 불러온 뒤 지우는 방식은 사용하지 않고, 쿠키와 origin이 없는 상태를 명시해 실제 로그인 흐름을 검증한다.
- **D5: `scenario`는 각 테스트의 격리된 브라우저 컨텍스트에만 쿠키로 설정한다.** `session` 쿠키는 애플리케이션 로그인 응답으로만 만든다.
- **D6: 주문 완료는 새 주문의 공개 결과를 단언한다.** 주문 요청의 응답에서 이번 주문 ID를 구분한 뒤 `/orders` 화면에서 해당 주문 ID와 처음 담은 상품명이 함께 보이는지 확인한다. 기존 주문이 없다고 가정하지 않는다.
- **D7: 모든 대기는 URL · 접근 가능한 화면 요소 · 실제 응답 조건을 사용한다.** `waitForTimeout`은 사용하지 않는다.

## 완료 조건

- [ ] **C1:** 미로그인으로 `/orders/new`에 들어가면 `/login`으로 이동하고 `next=/orders/new`가 보존된다. UI 로그인 뒤 `/orders/new`로 돌아오며 `session` 쿠키는 `httpOnly=true`, `SameSite=Lax`다.
- [ ] **C2:** 로그인 상태에서 `scenario=expired`로 `/orders`를 조회하면 `/login?reason=expired&next=/orders`로 이동하고 만료 안내가 보인다.
- [ ] **C3:** 인증되지 않은 상태에서 `scenario=invalid`로 로그인하면 자격 증명 오류가 보이고 `/login`에 머물며 `session` 쿠키가 생기지 않는다.
- [ ] **C4:** 로그인 상태에서 상품을 담고 장바구니의 선택 상품으로 주문하면 `/orders`에서 새 주문 ID와 해당 상품명을 볼 수 있다.
- [ ] **C5:** C1과 C3은 인증된 `storageState`를 재사용하지 않고 빈 상태를 명시하며, C2와 C4만 워커별 계정의 인증 `storageState`를 재사용한다.
- [ ] **C6:** `pnpm exec playwright test --workers=4`, `--workers=1`, `--workers=1 --repeat-each=3`이 모두 통과한다.
- [ ] **C7:** 역할과 이름 기반 셀렉터만 사용하고 시간 기반 대기가 없다.
- [ ] **C8:** 의도적으로 단언 하나를 실패시킨 `--trace=on` 실행의 trace를 직접 확인한 뒤 테스트를 원상복구한다.
- [ ] **C9:** `pnpm lint` · `pnpm typecheck` · `pnpm build` · `pnpm test`가 통과한다.
