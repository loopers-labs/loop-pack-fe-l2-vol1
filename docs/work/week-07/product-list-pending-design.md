# 상품 목록 pending · 갱신 · 실패 상태 설계 (7주차 2단계)

> 이 문서는 7주차 2단계에서 확인한 세 가지 불일치의 대응 설계다. 측정 기록과 판단 근거는 [02-list-pending-cls.md](./02-list-pending-cls.md) 2️⃣ 절을, 발제 요구는 [week-07.md](../../assignments/week-07.md) 2단계를 참고한다.

## 결정 요약

**본문 server prefetch를 제거하고, 상품 목록 데이터의 소유권을 클라이언트 `useQuery`로 일원화한다.**

`ProductListPage`의 `await queryClient.prefetchQuery(...)` + `HydrationBoundary`를 걷어내고, 데이터가 없는 최초 진입은 `isPending` 분기가 실제 목록 크기를 예약하는 그리드 스켈레톤으로 담당한다. query key factory와 `staleTime`은 손대지 않는다.

---

## 1. 배경 — 확인된 불일치 세 가지

| # | 상태 | 현재 동작 | 위반한 요구 |
| --- | --- | --- | --- |
| 1 | 데이터 없는 최초 진입 | `ProductListPage.tsx:19`의 `await prefetchQuery`가 문서 응답을 1.5초 통째로 막는다. hydrate 시점엔 캐시가 이미 차 있어 `isPending` 분기(171행 텍스트 한 줄)가 영영 도달하지 않는다 | "실제 목록 크기를 예상할 수 있는 pending UI를 보여줘요" |
| 2 | 이전 데이터가 있는 갱신 | 목록은 유지되지만 표시가 `aria-busy`(167행)뿐이다. 눈으로 보는 사용자에게는 갱신 중과 완료를 구분할 단서가 없다. `isFetching`은 화면 어디에도 쓰이지 않는다 | "기존 목록을 비우지 않고 갱신 중임을 보여줘요" |
| 3 | 갱신 실패 | 168행 `isError` 분기가 기존 `productList` 유무를 보지 않고 무조건 전체 에러 박스로 교체한다 | "기존 목록을 유지한 채 갱신 실패와 다시 시도할 방법을 보여줘요" |

2·3번은 클라이언트 렌더 분기 문제라 데이터 소유권과 무관하게 고칠 수 있다. **1번만 구조 선택이 필요하다.**

## 2. 왜 server prefetch를 제거하는가

### 2-1. 이번 주에 바꿔도 되는 범위인가

| 구분 | 항목 | 근거 |
| --- | --- | --- |
| 재설계 금지 | query key factory, `staleTime` | 멘토 노트 516행 "이번 주에는 query key factory와 `staleTime`을 다시 설계하지 않아요" |
| 재설계 금지 | Route Handler 내부, 누적 FSD 구조 | week-07.md 1단계 note |
| **선택 사항** | `placeholderData`, prefetch, `AbortSignal`, **server prefetch + hydration** | 멘토 노트 419행 "server prefetch와 hydration은 Basic 필수 구현이 아니에요. 적용하지 않았다면 무개입 근거를, 적용했다면 waterfall과 응답 크기의 Before / After를 남겨요" |

server prefetch 제거는 금지된 재설계가 아니라 발제가 명시적으로 열어둔 선택지다. 대신 근거와 Before/After 기록이 요구된다.

### 2-2. week-05가 prefetch로 얻은 것이 되살아나는가

[week-05/ssr-fetch-fix-plan.md](../week-05/ssr-fetch-fix-plan.md) §6 · [server-state-design.md](../week-05/server-state-design.md):25 기준 도입 목적은 네 가지였다.

| 도입 목적 | 제거 시 되살아나는가 | 이유 |
| --- | --- | --- |
| 중복 fetch 제거(서버가 받은 데이터를 클라가 곧장 재요청) | **아니오** | 서버가 본문 조회를 아예 하지 않는다. 서버 0회 + 클라 1회로 오히려 총 호출이 준다 |
| 하이드레이션 역행 깜빡임 제거 | **아니오** | 역행은 "서버가 데이터를 그렸는데 클라가 로딩으로 되돌아가는" 현상이다. 서버가 스켈레톤을 그리면 되돌아갈 대상이 없다. SSR 스켈레톤 → hydrate 후에도 같은 스켈레톤 → 데이터의 단방향 전환만 남는다 |
| week-05 Advanced B 요건("동일 쿼리 팩토리 재사용") | 해당 없음 | 5주차 과제 요건이고, `productQueries.list()` 팩토리 자체는 그대로 유지된다 |
| `staleTime` 20s와의 짝(hydrate 직후 `refetchOnMount` 재요청 방지) | 해당 없음 | hydrate할 캐시가 없으므로 방지 대상 자체가 사라진다. `staleTime` 값은 건드리지 않는다 |

즉 week-05가 비용을 들여 없앤 문제 중 되살아나는 것은 없다.

### 2-3. week-06이 세운 회귀 기준을 의도적으로 넘는다

[week-06/baseline.md](../week-06/baseline.md)에 이 상태가 이미 기록돼 있다.

- 24행: `| 홈 | 로딩 폴백 | 도달 불가 (서버 prefetch로 항상 캐시 hit) |`
- 175행: "회귀 판정 기준: 마이그레이션 후 이 화면이 사용자 경로에서 보이기 시작하면 서버 prefetch 구조가 바뀐 것이므로 원인 확인 필요"

"pending UI 도달 불가"는 이번에 생긴 버그가 아니라 5주차가 의도적으로 만들고 6주차가 baseline으로 확정한 구조다. 이번 변경은 그 회귀 기준을 **의도적으로 넘는 것**이며, 원인은 이 문서다. 목록 pending 화면이 다시 보이기 시작하는 것은 회귀가 아니라 이번 변경의 목표다.

> 범위 주의: 이번 변경은 **상품 목록에만** 적용한다. 홈(`HomePage`)의 server prefetch는 그대로 두고, 홈의 로딩 폴백 도달 불가도 유지한다. 홈은 Hero 이미지가 병목이라는 것이 1단계에서 이미 확인됐고(LCP의 97.3%가 이미지 전송), 목록과 달리 URL 조건에 따라 자주 바뀌는 데이터가 아니다.

### 2-4. SEO 영향은 작다

- **metadata(title·description·Open Graph)는 이 변경과 무관하다.** `generateMetadata`가 서버에서 독립적으로 조회·생성한다.
- 잃는 것은 "초기 HTML 본문에 상품 텍스트가 들어간다" 하나다. 그런데 `ProductCard`(`src/entities/product/ui/ProductCard.tsx`)는 `<article>` + 이미지 + 텍스트뿐이고 **링크가 없다.** 상품 상세 라우트도 존재하지 않는다(`app/` 아래 `products/[id]` 부재). 따라서 크롤 발견(crawl discovery) 이점은 0이고, 남는 것은 상품명·브랜드·가격 텍스트와 `alt`의 색인 정도다.
- 발제가 초기 HTML에 요구하는 "하나의 명확한 `h1`, 페이지 설명, 주요 링크와 구조"는 셸이 담당하며, 이번 변경 후 셸은 오히려 **더 일찍** 초기 HTML에 나온다(현재는 1.5초 대기 후 문서 응답).
- 멘토 노트 628행도 "크롤러가 JavaScript를 실행할 수 있어도 초기 응답에 의미 있는 콘텐츠와 링크가 있으면 더 일찍 이해할 수 있어요"로, 색인 가능 여부가 아니라 이해 시점의 문제로 서술한다.

### 2-5. 감수하는 비용 — 3단계 관찰 대상 축소

발제 3단계는 본문 server prefetch의 존재를 전제로 서술돼 있다.

- "상품 목록은 정규화한 URL 조건과 **본문 prefetch와 같은 query factory**가 조회한 응답의 카테고리명·전체 개수·첫 상품 이미지를 사용해요"
- "같은 render/request에서 URL·options가 모두 같은 native fetch만 memoization 대상이에요"
- 체크리스트: "Browser Network만으로 Route Handler 횟수를 판정하지 않고, **서버 측 계수로** 확인한 뒤 계측을 되돌렸는가"

본문 server prefetch를 없애면 서버 fetch가 `generateMetadata` 1건뿐이라, 같은 요청 안의 동일 fetch가 memoization으로 1회로 합쳐지는 것을 **2→1로 보여줄 관찰 대상이 사라진다.**

**대응**: 3단계에서 memoization은 "본문과 metadata 사이"가 아니라 `generateMetadata` 내부의 동일 조회 경로에서 관찰하고, 서버 호출 계수는 "본문이 서버에서 조회하지 않으므로 요청당 1회"라는 사실 자체를 계수로 확인해 기록한다. `productQueries.list()`라는 같은 query factory·같은 GET URL·같은 options를 쓴다는 요구는 그대로 지킬 수 있다.

### 2-6. 채택하지 않은 대안 — Suspense + prefetch 유지

```
<h1>상품 목록</h1>                            ← 즉시 스트리밍
<Suspense fallback={필터+그리드 공간 예약}>
  <ProductListData/>                          ← async RSC: prefetch → dehydrate
</Suspense>
```

- 장점: 3단계 관찰 대상(서버 호출 계수·memoization) 보존, week-06 회귀 기준 유지, 초기 HTML에 상품 텍스트 유지
- **채택하지 않은 이유**: 필터 컨트롤(검색·카테고리·정렬)이 데이터와 같은 경계 안에 있어 1.5초 동안 함께 늦는다. 상호작용 컨트롤을 데이터 때문에 막는 것이 이번 주의 문제의식("셸은 먼저, 느린 것만 기다리게")과 정면으로 어긋난다. 필터를 경계 밖으로 빼려면 카테고리 옵션이 같은 쿼리에 묶여 있어 구조 변경이 커진다.
- 이 대안은 3단계 진행 중 서버 호출 계수 관찰이 실제로 막히면 다시 검토한다.

## 3. 여섯 가지 상태 대응 설계

`isPending`(캐시에 이 키의 데이터가 아직 없음)과 `isFetching`(요청 진행 중, 데이터 유무 무관)의 역할을 분리하고, 여기에 **기존 데이터 유무**(`productList`)를 곱해 여섯 화면을 가른다.

| 상태 | 판정 조건 | 보여줄 화면 |
| --- | --- | --- |
| 데이터 없는 최초 진입 | `isPending` | 그리드 스켈레톤 12개 (실제 목록과 같은 `.product-grid`) |
| 이전 데이터가 있는 갱신 | `!isPending && isFetching` | 기존 목록 유지 + 상태줄에 `· 갱신 중` + 그리드 흐리게 |
| 성공 + 0건 | `!isPending && !isError && totalCount === 0` | `총 0개` + 빈 결과 안내 (현행 유지) |
| 최초 실패 | `isError && !productList` | 목록 대신 실패 사유 + 재시도 (현행 유지) |
| 갱신 실패 | `isError && productList` | **기존 목록 유지** + 상태줄에 `· 갱신 실패` + 재시도 버튼 + 그리드 흐리게 |
| 취소 | (별도 분기 없음) | react-query가 query key 변경 시 이전 요청을 취소하고 `isError`로 승격하지 않는다 (현행 유지) |

분기 순서가 핵심이다. **`isError`를 최우선으로 두지 않고 보여줄 목록이 있는지를 먼저 본다.**

```
isPending      → 그리드 스켈레톤 (최초 진입)
!shownList     → 전체 에러 (최초 실패 — 보여줄 이전 결과조차 없음)
그 외          → 상태줄 + 목록
                  상태줄이 갱신 중 / 갱신 실패 / 이전 조건의 결과 / 0건을 구분해 표시
                  갱신 중·갱신 실패면 그리드를 흐리게 해 최신 결과가 아님을 알린다
```

### 3-1. `keepPreviousData`는 에러를 덮어주지 않는다 (실측으로 확인)

설계 초안에서는 "판정을 `productList` 존재 여부로 두면 두 경우 모두 안전하다"고 적었으나 **틀렸다.**

`placeholderData: keepPreviousData`는 새 query key의 요청이 **pending인 동안에만** 이전 결과를 내준다. 요청이 에러로 끝나면 그 키에는 데이터가 없고 `data`는 `undefined`가 된다. 브라우저 실측(카테고리 변경 요청에 500 주입)에서 `cards: 0`, 전체 에러 화면으로 확인했다.

즉 갱신 실패에는 두 종류가 있다.

| 종류 | `data` | 현재 분기 |
| --- | --- | --- |
| 같은 key 재요청 실패 | 마지막 성공 데이터가 남음 | 목록 유지 + 인라인 실패 표시로 동작함 |
| **다른 key(필터 변경) 실패** | **없음** | 초안대로면 최초 실패와 같은 전체 에러로 떨어짐 |

이 앱에는 같은 key를 수동 재요청할 UI가 없으므로, 실제로 발생하는 갱신 실패는 대부분 두 번째다.

### 3-2. 채택한 처리 — 이전 결과 유지 + 조건 불일치 명시

실무 커머스에서 목록 갱신 실패를 다루는 방식은 세 가지로 나뉜다.

| 패턴 | 쓰이는 상황 | 이 코드베이스 적합성 |
| --- | --- | --- |
| 전체 에러로 교체 | 목록이 페이지의 전부일 때 | 필터를 한 번 잘못 눌러 네트워크가 튀면 사용자가 보던 결과가 통째로 사라진다 |
| URL 롤백 + 토스트 | 필터가 URL에 없는 앱 | URL을 단일 출처로 삼은 5주차 설계와 충돌한다. 사용자의 선택을 시스템이 되돌리고 재시도 루프 위험이 있다 |
| **이전 결과 유지 + 조건 불일치 명시 + 재시도** | 대부분의 커머스 목록 | **채택** |

react-query 메인테이너(TkDodo)의 에러 핸들링 가이드도 백그라운드 갱신 실패에 대해 "stale 데이터를 작은 에러 표시와 함께 보여주는 편이 아무것도 보여주지 않는 것보다 낫다"고 권한다. 발제문 표("기존 목록을 유지한 채")와 멘토 노트("오래된 결과를 최신처럼 보이지 않게")도 같은 방향이다.

핵심 조건은 **목록은 남기되 화면이 URL에 대해 거짓말하지 않는 것**이다. URL은 `category=fashion`인데 화면이 캐주얼 결과라면 그 사실을 문구로 밝혀야 "현재 URL의 active query와 화면 결과가 일치" 요구와 충돌하지 않는다.

```
갱신 실패 — 아래는 이전 조건의 결과입니다 · 총 6개   [다시 시도]
```

**구현**: 이전 결과를 로컬 상태나 ref로 복사하지 않는다. `findLastSuccessfulProductList(queryClient)`가 query cache에서 가장 최근에 성공한 목록 쿼리를 찾아 그 데이터를 그대로 읽는다. 서버 상태의 소유권은 계속 query cache에 있다. 캐시의 `data`는 `unknown`이고 프로젝트가 타입 단언을 금지하므로 타입 가드로 좁힌다.

> 한계: 렌더 중 캐시를 한 번 읽는 방식이라 캐시 변화에 반응하지 않는다. 이 값을 쓰는 시점이 에러 렌더 직후뿐이라 충분하고, 실시간 반영이 필요해지면 쿼리를 하나 더 두는 쪽으로 올린다.

## 5. CLS를 만들지 않기 위한 조건

교체가 일어나는 지점은 두 곳이고, 둘 다 **교체 전후가 같은 공간을 차지하게** 만든다.

| 교체 | 대응 |
| --- | --- |
| 스켈레톤 → 실제 그리드 | 스켈레톤이 `.product-grid`·`.product-card`·`.product-card-image` 클래스를 그대로 쓴다. 열 수(5/3/2)와 이미지 비율(`aspect-ratio: 1`)이 CSS에서 자동으로 일치한다. 카드 내부도 같은 태그(`p`/`h2`/`strong`/버튼 2개)로 채워 줄 높이를 맞춘다 |
| 상태줄 텍스트 변화 · 재시도 버튼 등장 | 상태줄에 `min-height`로 버튼이 들어갈 높이를 항상 예약한다. `· 갱신 중` 같은 인라인 텍스트 추가는 세로 높이를 바꾸지 않는다 |
| 갱신 중 표시 | `opacity`로만 처리한다. 레이아웃에 영향을 주지 않는 속성이다 |

**측정으로 확인한 잔여 위험**: 상품명(`h2`)이 카드 폭에서 2줄로 접히는 경우가 실제로 있어, 실제 카드와 스켈레톤 양쪽 제목에 `min-height: 2lh`를 주어 1줄이든 2줄이든 같은 공간을 쓰게 했다(이름을 잘라내지 않는다). 이것으로 폴백 교체 CLS는 0이 됐다. 다만 `min-height`는 하한만 잡으므로 이름이 3줄이 되는 카드가 있으면 카드 높이가 달라진다 — §7의 잔여 항목으로 남는다.

측정 조건: production build(`pnpm build && pnpm start`), viewport 1350×940, `PerformanceObserver('layout-shift')`.

| 항목 | 기대 | 실측 |

| SSR ↔ CSR 깜빡임 | 없음 | ✅ **0.** 5회 모두 `skeleton → grid` 단방향 1회 전환(`skeleton@26~50ms → grid@1549~1578ms`). 되돌아가는 전이 0회 |
