## 1️⃣ Hero LCP

**LCP 구간 분해**

Before·After 각각 같은 조건으로 5회 측정한 값의 중앙값이다(실행 원본은 로컬 보관). 재현 조건(쓰로틀링·viewport·production build)은 0단계와 동일하며, After 5회 모두 요청 35건 중 dev 마커 0건으로 production build를 재확인했다.

| 구간                      | Before                  | After                  | 변경                       |
| ------------------------- | ----------------------- | ---------------------- | -------------------------- |
| 서버 응답 대기            | 13.9 ms (0.17 %)        | 13.1 ms (2.44 %)       | -0.8 ms                    |
| 이미지 요청 시작까지 대기 | 166.8 ms (2.0 %)        | 166.1 ms (30.86 %)     | -0.7 ms                    |
| **이미지 전송**           | **8,000.8 ms (97.3 %)** | **319.7 ms (59.41 %)** | **-7,681.1 ms**            |
| 화면에 그려질 때까지      | 33.6 ms (0.41 %)        | 36.9 ms (6.86 %)       | +3.3 ms                    |
| **LCP 합계**              | **8,225.4 ms**          | **538.2 ms**           | **-7,687.2 ms (-93.46 %)** |

회차별 LCP: 519.0 / 538.2 / 534.0 / 538.8 / 541.6 ms (범위 22.6 ms, 중앙값의 4.2 %). 이미지 전송 구간이 8,000.8→319.7 ms로 줄면서 LCP 구성비가 뒤바뀌었다 — 이제는 요청 시작 대기(30.9 %)가 서버 응답 대기(2.4 %)보다 커서, 다음으로 줄일 여지가 있다면 전송이 아니라 발견·요청 시점 쪽이다.

> ⚠️ **이후 단계에서 실측이 바뀐 구간 — 서버 응답 대기**
> 위 After 열은 **1단계 완료 시점**(3단계 커밋 `6f016256` 이전)의 값이다. 3단계에서 `getHome`의 week-05 direct-call 우회를 제거해 서버도 `apiFetch`로 `/api/home`을 실제 HTTP 호출하게 되면서, 최종 SHA `e3fdf8e5`의 같은 조건 재측정에서는 **서버 응답 대기가 13.1 ms → 521.9 ms(LCP 880.9 ms의 59 %)** 로 올라갔다. 증가분은 `/api/home`의 고정 지연 500 ms(`waitForMockApi` 기본값)이며, Hero 이미지 자체의 요청 지연·전송·렌더 지연은 이 표와 같다. 최종 수치는 [baseline-and-regression.md](./baseline-and-regression.md) 4단계를 따른다.
> 이 변화는 아래 "렌더링 경계 선택" 판단의 근거 수치에도 영향을 준다 — 갱신된 근거는 해당 행에 적었다.

**이미지 변경 내역**

|                | Before                                               | After                                                                                      |
| -------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 요청 URL       | `/images/week-07/hero-original.jpg` (원본 직접 서빙) | `/_next/image?url=%2Fimages%2Fweek-07%2Fhero-original.jpg&w=1200&q=75` (`next/image` 경유) |
| 원본 해상도    | 3840×2160                                            | 3840×2160 (원본 파일은 그대로, 요청 시점에 리사이즈)                                       |
| 전송 크기      | 7,545,525 B (7.20 MB)                                | **80,965 B (79.1 KB) — 98.93 % 감소**                                                      |
| 실제 표시 크기 | 1200×675 (`boundingRect`)                            | 1200×675 (`boundingRect`, 동일)                                                            |
| 포맷           | JPEG                                                 | WebP (`next/image` 자동 협상)                                                              |

**포맷 선택 기록 (WebP vs AVIF)** — `next.config.ts`의 `images.formats`만 바꿔 같은 조건으로 2회씩 비교했다(해상도 축소 전, 원본 3840×2160 그대로인 상태).

| 포맷 | 전송 용량         | LCP (2회)           | LCP 중앙값 |
| ---- | ----------------- | ------------------- | ---------- |
| WebP | 409,736 B (400 KB) | 1580.1 / 1263.2 ms | 1421.6 ms  |
| AVIF | 304,373 B (297 KB) | 1437.3 / 1017.2 ms | 1227.3 ms  |

**AVIF가 전송 용량·LCP 모두 더 좋았는데도 WebP를 선택했다.** 당시 기록에 선택 이유가 남아있지 않아, 이 판단은 근거를 다시 세우거나 AVIF로 바꾸는 재검토가 필요한 열린 항목이다.

**판단**

| 항목                                                                   | 내용                                                                                                                                                                                                                                                                                                        |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Hero의 시각적 크기·비율·주요 피사체·문구 유지 여부                     | **유지됨.** 전체 화면 스크린샷 대조에서 Hero 박스 위치·크기, 16:9 비율과 피사체 잘림 없음, 오버레이 문구("이번 주의 발견" · "매일 새롭게 발견하는 취향")와 위치가 Before/After 동일했다. 실제 배송 리소스의 픽셀 크롭 비교에서도 가죽 질감·스티치 라인·음영 그라데이션이 유지되고 블록 노이즈·색 밴딩은 없었다. 표시 크기는 양쪽 모두 1200×675로, 이번 변경은 표시 크기가 아니라 그 크기를 위해 내려받는 리소스 해상도만 맞춘 것이다. 대조에 쓴 스크린샷·크롭 이미지와 상세 판정 기록은 로컬에 보관하고, 판정 결과는 위와 같이 이 문서에 옮겨 적었다 |
| 이미지 요청 우선순위를 높였는가 / 높이지 않았다면 그 근거              | 브라우저는 렌더링을 실제로 막는 리소스(document, 렌더 블로킹 CSS)만 `VeryHigh`로 두고, 그 외엔 아무리 중요해도 그 아래 등급에 묶어둔다. 이미지는 없어도 페이지가 일단 그려지므로 "렌더링을 막는 자원"이 아니라서 최상위 등급 대상이 아니다                                                                  |
| 렌더링 경계 선택 — 홈 데이터를 기다리는 `await` 위치와 `Suspense` 위치 | 변경하지 않았다. **1단계 시점의 근거**: 진단 기록표에서 확인했듯 홈 데이터 대기 비용이 서버 응답 대기 13.1 ms(2.44 %)로 API 병목 자체가 크지 않아, 경계를 나눠 얻는 이득보다 이미지 전송량을 줄이는 쪽이 비용 대비 효과가 훨씬 커서 그쪽을 우선했다.<br>**3단계 이후 정정된 근거**: 위 경고 상자대로 direct-call 우회 제거(`6f016256`) 이후 서버 응답 대기가 521.9 ms(LCP의 59 %)가 되어 "API 병목이 작다"는 근거는 더 이상 성립하지 않는다. 그럼에도 경계를 다시 나누지 않은 이유는 이 521.9 ms가 렌더링 경계가 만든 대기가 아니라 `/api/home`의 고정 지연 500 ms 자체이기 때문이다 — 경계를 나눠도 총 대기는 줄지 않고, 셸이 먼저 나가는 대신 배너·상품 그리드가 그만큼 늦게 채워지는 교환에 그친다. 목록에서 같은 교환(server prefetch 제거, 2단계)을 택한 것은 그 1.5초 동안 검색·카테고리·정렬 컨트롤까지 조작할 수 없었기 때문인데, 홈 셸에는 그 사이 조작할 대상이 없어 같은 이득이 생기지 않는다. 우회 제거 자체를 되돌릴지는 3단계 metadata 실패 재현 요구와 충돌해 미결이다([baseline-and-regression.md](./baseline-and-regression.md) 4단계 "효과가 없었거나 악화된 변경")                                                                               |
| Header·`h1`·페이지 설명이 느린 Hero와 함께 막히지 않았는지 확인 결과   | **추가 검토 필요.** filmstrip 750 ms 프레임에서 Header·`h1`·설명·Hero가 모두 표시된 것은 확인했지만, 이번 변경으로 Hero 자체가 빨라지면서 개별 확인이 무의미해진 것인지 렌더링 경계가 실제로 안전하게 분리돼 있는지는 별도로 검증하지 않았다                                                                |
| Hero fallback의 공간 예약 방식과 Layout shifts track 확인 결과         | CLS 0 (5회 모두, Before와 동일). `next/image`의 `fill`이 `position:relative; aspect-ratio:16/9`인 부모 박스를 그대로 채우는 방식이라 이미지 로드 전후로 공간이 바뀌지 않음                                                                                                                                  |

> `next/image` 사용 여부가 아니라 실제 요청 URL·전송 크기·waterfall·LCP 변화로 판단한다.
