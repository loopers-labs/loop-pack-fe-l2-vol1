Reviewer memo · Week 06

예상 커밋별 리뷰 포인트

현재 히스토리 이후에 예상되는 작업만 대상으로 한다. 구현 방법을 대신 결정하지 않고, 각 커밋이 하나의 논리적 변경인지와 과제·RFC·멘토링 피드백의 경계를 지키는지를 검토한다.

기준 HEAD 99da85d
완료된 결정 Decision 1–4
남은 핵심 결정 Public API · Error Boundary
검증 기준선 134 tests + lint + typecheck + build
리뷰 결론: 지금부터는 폴더를 바로 옮기면 안 된다. Decision 5와 6, 목표 트리, 파일 매핑이 먼저 확정되어야 이후 이동 커밋의 완료 조건을 판단할 수 있다. 멘토의 “경계를 먼저 지키라”는 피드백과도 일치한다.
현재 문서에서 먼저 고칠 사실: Preflight에는 아직 Node 20.19.0에서 확인했다고 적혀 있으나 저장소의 .nvmrc와 실제 재검증 환경은 Node 24.17.0이다. 최종 설계 확정 커밋에 섞지 말고, 기준선 사실 정정으로 명시해야 한다.

예상 커밋 순서

1

Public API 경계 결정

docs

이 커밋의 범위

  • 외부 소비자가 있는 슬라이스만 Public API 필요 여부를 결정한다.
  • cart와 wishlist는 ProductGrid뿐 아니라 Header도 소비자 목록에 포함한다.
  • productListContract의 소비자는 product-list 화면과 mock Route Handler 두 곳임을 반영한다.
  • mock API가 FSD 프론트엔드 레이어 밖 코드라는 경계를 문서화한다.

리뷰 질문

  • Public API가 경로 단축이 아니라 숨길 구현을 실제로 숨기는가?
  • cart/wishlist의 Zustand store와 setter 계약은 외부에서 import할 수 없게 남는가?
  • export * 없이 필요한 값만 명시적으로 공개하는가?
  • 같은 슬라이스 내부 import까지 루트 Public API를 우회하게 만들지는 않는가?
통과 기준: 각 공개 항목마다 실제 외부 소비자를 말할 수 있고, 각 비공개 항목마다 숨겨야 하는 변경 이유를 말할 수 있어야 한다.
2

에러·로딩 경계 결정

docs

이 커밋의 범위

  • 4xx, 5xx, 네트워크, 타임아웃, 예상 밖 렌더링 오류를 표로 분리한다.
  • 현재 ApiError의 status, 서버 message, retry 가능 여부를 Decision 6의 입력으로 사용한다.
  • Query isPending, nuqs를 위한 기존 Suspense, route error.tsx의 역할을 구분한다.
  • 이벤트 핸들러 오류가 Error Boundary 대상이 아님을 기록한다.

리뷰 질문

  • 실패 시 검색 폼과 URL 조건을 유지해야 하는 사용자 흐름이 보존되는가?
  • “5xx이므로 무조건 페이지 전체를 가린다”가 아니라 살아남아야 할 UI 범위로 경계를 정했는가?
  • throwOnError 조건이 에러 처리 표와 정확히 일치하는가?
  • Suspense는 데이터 요청 단위가 아니라 고객이 하나로 인식하는 로딩 경험을 기준으로 정했는가?
통과 기준: 각 실패가 어느 UI를 죽이고 무엇을 남기는지 한 문장으로 설명할 수 있어야 한다. 일반 API 실패와 예상 밖 렌더링 오류를 같은 fallback에 밀어 넣으면 반려한다.

RADIO·목표 트리·파일 매핑 확정

docs

이 커밋의 범위

  • Decision 1–6의 결론만 RADIO 본문과 목표 트리에 반영한다.
  • 현재 위치, 목표 위치, 레이어·슬라이스·세그먼트를 파일별로 매핑한다.
  • 애매한 파일 5개 이상의 최종 결정표를 완성한다.
  • 단계별 이동 순서와 각 단계의 검증 명령을 고정한다.
  • Node 기준선과 문서 내 중복 문장 등 현재 사실 오류를 정정한다.

리뷰 질문

  • 목표 트리에 빈 폴더나 미래용 세그먼트가 없는가?
  • src/app은 Next 진입점만 남고 FSD page는 src/_pages로 구분되는가?
  • Product 타입, API 응답 타입, mock scenario 타입의 소유자를 각각 설명하는가?
  • “shared를 강화”한다는 멘토 피드백을 도메인 코드까지 shared에 넣는 뜻으로 오해하지 않았는가?
통과 기준: 이후 모든 이동 커밋의 대상 파일과 완료 조건이 이 문서만으로 예측되어야 한다. 구현하면서 소유자를 다시 고민해야 한다면 아직 이 커밋은 완료가 아니다.

커밋 분리 원칙

함께 두어도 되는 것 반드시 분리할 것
파일 이동과 그 이동 때문에 필요한 import 경로 수정 구조 이동과 사용자 동작 변경
한 슬라이스의 구현 이동과 같은 책임의 테스트 이동 Decision 문서와 해당 Decision이 정하지 않은 구현
에러 경계 구현과 그 경계를 직접 검증하는 테스트 에러 정책 변경과 unrelated 접근성·스타일 수정
최종 RFC 사실 동기화와 검증 결과 기록 Advanced 기능과 기본 FSD 마이그레이션

리뷰 중 즉시 중단할 신호

소유권 재논의 구현 커밋에서 “이 파일은 어디에 둘까”가 다시 나오면 목표 트리 확정이 덜 된 것이다.
shared의 도메인 창고화 여러 곳이 쓴다는 이유만으로 Product 정책이나 화면 문구가 shared로 내려가면 반려한다.
페이지 전체 붕괴 한 조회 실패가 수정 가능한 검색 조건과 독립 UI까지 지우면 에러 경계를 다시 좁힌다.
숫자만 있는 실측 파일 수·줄 수·삭제 반경이 파일 목록이나 명령 결과 없이 결론의 핵심 근거가 되면 확인을 요구한다.
이 문서는 리뷰 기준만 제시한다. 커밋 생성, 스테이징, 브랜치 변경은 수행하지 않는다.
