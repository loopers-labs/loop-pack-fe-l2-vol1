LOOP PACK · WEEK 09 FEEDBACK

피드백 정리와 변경 계획

멘토 피드백을 현재 저장소와 대조해, 바로 고칠 부분과 판단이 필요한 부분을 구분했습니다.

한눈에 보기

핵심은 사용자가 잘못 이해할 수 있는 세션 만료 화면을 먼저 고치고, 자동 테스트가 놓치는 로그아웃 실패와 이벤트 중복을 고정한 뒤, PR 본문의 수치와 표현을 실제 변경 내용에 맞추는 것입니다.

4 즉시 반영할 항목

무엇부터 고칠까

  1. 세션 만료 안내

    해결 완료 세션 만료를 빈 장바구니나 빈 위시리스트와 구분하도록 수정했습니다.

  2. 로그아웃 실패 테스트

    해결 완료 실패 시 이동하지 않고 오류를 보여주는 정책을 통합 테스트로 고정했습니다.

  3. 목록 조회 이벤트 중복 테스트

    해결 완료 호출 횟수 단언을 추가해 같은 이벤트가 두 번 발생하면 실패하도록 했습니다.

  4. PR 설명 정정

    PR 본문 확인 필요 수정 케이스 수와 테스트 이동 표현을 실제 이력에 맞춰 정정해야 합니다.

변경 계획

사용자 영향 해결 완료

세션 만료를 빈 목록과 구분한다

수정 전 만료 흐름은 다음과 같았습니다.

만료된 쿠키가 존재함
→ proxy.ts는 쿠키가 있다고 보고 보호 경로 통과
→ getSession()은 401을 null로 변환
→ cart, checkout, wishlist는 별도 API 요청 없음
→ mypage는 null을 별도 안내 문구로 처리
→ 전역 401 핸들러가 실행되지 않음
→ 화면마다 빈 목록 또는 별도 문구로 노출됨

/orders만 주문 쿼리가 401을 던져 전역 만료 처리가 실행됩니다. 나머지 네 보호 화면은 공통 서버 세션 가드를 호출합니다. 확인 결과가 null이면 reason=session_expired와 복원 경로를 붙여 로그인 화면으로 보내고, 로그인 폼 위에 만료 안내를 표시합니다.

  • src/_pages/cart/ui/CartPage.tsx
  • src/_pages/checkout/ui/CheckoutPage.tsx
  • src/_pages/wishlist/ui/WishlistPage.tsx
  • src/_pages/mypage/ui/MyProfile.tsx
유지할 결정

getSession()은 401을 계속 null로 반환합니다. 이 함수를 예외로 바꾸면 공개 화면을 방문한 미로그인 사용자까지 세션 만료로 처리될 수 있습니다.

완료 조건

  • 유효한 세션이면 기존 콘텐츠가 보인다.
  • 만료 또는 위조된 세션이면 만료 사유를 붙여 로그인 화면으로 이동한다.
  • 로그인 화면에서 만료 안내와 로그인 폼이 함께 보인다.
  • 만료 상태가 빈 장바구니나 빈 위시리스트로 표현되지 않는다.
해결한 방법

proxy.ts는 쿠키 존재만 확인하고, 보호 페이지가 실제 세션 유효성을 확인하도록 역할을 나눴습니다. 공통 서버 가드 src/entities/session/server.ts가 cookies()와 getSession()을 호출하고, 결과가 null이면 toLoginPath()에 reason=session_expired를 붙여 로그인으로 보냅니다.

Cart와 Checkout은 고정된 복귀 경로를 전달하고, Wishlist는 먼저 entryPoint를 검증해 복귀 경로를 만든 뒤 같은 가드를 호출합니다. Mypage도 ROUTES.MYPAGE를 복귀 경로로 전달해 같은 가드를 사용합니다. 로그인 화면은 전달받은 사유를 role="status" 안내로 표시합니다.

테스트 계층 해결 완료

로그아웃 실패 정책을 테스트로 고정한다

기존 API Route 테스트만으로는 src/features/logout/**의 화면 동작까지 보장할 수 없습니다. Header.test.tsx에서 실패 응답과 팝오버 밖에 표시되는 오류 배너를 연결했습니다.

  1. 로그아웃 API가 500을 반환한다.
  2. 사용자가 로그아웃 버튼을 누른다.
  3. 최상단 NoticeBanner의 role="alert"에 실패 사유가 나타난다.
  4. 팝오버를 닫아도 배너가 남고, 현재 URL에서 이동하지 않는다.
  5. 닫기 버튼을 누르면 배너가 사라진다.
왜 Playwright가 아닌가

여기서 지킬 것은 실제 쿠키 처리보다 실패한 mutation과 오류 UI의 연결입니다. 브라우저 없이 재현할 수 있으므로 Testing Library 통합 테스트가 더 저렴합니다.

해결한 방법

LogoutButton은 버튼 UI만 담당하고, useLogout은 HeaderNav에서 실행하도록 책임을 분리했습니다. 오류 상태를 헤더에서 관리해 팝오버 바깥에 공용 NoticeBanner를 렌더링하고, 사용자가 닫을 수 있도록 mutation의 reset을 연결했습니다.

Header.test.tsx는 MSW로 로그아웃 API에 500 응답을 주고, 로그아웃 클릭 후 오류 배너·이동하지 않음·팝오버를 닫은 뒤에도 배너 유지·닫기 동작을 검증합니다. LogoutButton.test.tsx는 버튼이 전달받은 로그아웃 핸들러를 호출하는지만 검증해 각 테스트의 책임을 나눴습니다.

추가 사항

브라우저를 Offline으로 바꾸면 TanStack Query의 기본 networkMode: 'online' 때문에 mutation이 실패하지 않고 paused 상태로 대기할 수 있습니다. 새로고침 때 보이는 브라우저 에러 페이지는 앱의 API 오류 처리가 아니므로, 이 문제를 별도 범위로 보완했습니다.

  1. src/shared/api/fetch-with-timeout.ts에 공통 timeout 유틸을 추가하고, 기존 AbortSignal과 요청 timeout을 함께 취소하도록 했습니다.
  2. 로그인·로그아웃·주문 생성처럼 사용자가 기다리는 mutation에는 networkMode: 'always'를 적용해 오프라인에서도 오류로 종료하도록 했습니다.
  3. 상품·주문 목록 조회에는 각 API의 signal을 보존한 timeout을 적용해 요청 취소와 timeout을 구분하도록 했습니다.
  4. timeout 유틸 단위 테스트와 로그아웃 통합 테스트를 추가하고, Playwright의 route.abort()·route.fulfill()을 사용하는 e2e/logout.spec.ts를 작성했습니다.

서버 Route의 쿠키 처리와 기존 공용 배너는 수정하지 않고, 클라이언트 API·mutation 계층에서만 보완했습니다. pnpm verify는 통과했으며, 로그아웃 E2E의 Chromium·WebKit 실행은 별도 브라우저 검증으로 남아 있습니다.

회귀 방지 해결 완료

product_list_view 중복을 잡는다

현재 toHaveBeenCalledWith()는 이벤트가 한 번이든 두 번이든 통과합니다. ProductListContent.test.tsx의 직접 진입 케이스에 호출 횟수 단언을 추가했습니다. 

expect(track).toHaveBeenCalledTimes(1)

이 단언이 있어야 lastTrackedViewRef를 삭제했을 때 테스트가 실패합니다. 기존 테스트가 사건의 존재를 봤다면, 수정 후에는 사건의 개수까지 보게 됩니다.

해결한 방법

ProductListContent.tsx에서 목록 조회가 성공한 뒤 page·category·sort 조합으로 viewKey를 만들고, lastTrackedViewRef에 같은 조합이 기록되어 있으면 product_list_view를 다시 발화하지 않도록 했습니다.

ProductListContent.test.tsx의 직접 진입 테스트에 toHaveBeenCalledTimes(1)을 추가해 기대한 이벤트가 존재하는지뿐 아니라 정확히 한 번만 기록되는지도 검증했습니다. Vitest는 29개 파일, 164개 테스트가 통과했습니다.

문서에 반영한 내용

전체 케이스는 96개, 직접·수정 태그와 수정 사유 주석은 각각 7개로 정리했습니다. 헤더 숫자는 기존 Header.test.tsx가 검증하고 있었고, 새로 추가된 것은 add-to-cart.spec.ts의 새로고침 유지 검증이라는 사실도 구분했습니다. PR 본문은 이 문장을 기준으로 별도 수정해야 합니다.

권장 문장

기존 E2E는 전제가 사라져 삭제했습니다. 헤더 숫자 변경은 이미 Header.test.tsx가 검증하고 있어 새로 옮기지 않았고, 새로고침 후 장바구니 유지 검증만 add-to-cart.spec.ts에 추가했습니다. 담기 버튼의 aria-pressed는 add-only 결정으로 제품 동작 자체가 사라져 대체 테스트를 만들지 않았습니다.

해결한 방법

삭제된 테스트가 확인하던 위시리스트 새로고침 유지 시나리오를 e2e/add-to-wishlist.spec.ts로 분리했습니다. 로그인 상태에서 상품을 찜한 뒤 위시리스트 목록과 헤더 숫자를 확인하고, 새로고침 후에도 같은 상품과 숫자가 유지되는지 검증합니다.

헤더 숫자 변경은 기존 Header.test.tsx가, 장바구니 새로고침 유지는 add-to-cart.spec.ts가 담당하므로 각 테스트의 검증 범위를 겹치지 않게 나눴습니다. 새 위시리스트 E2E는 Chromium·WebKit에서 모두 통과했습니다.

피드백에서 헷갈릴 수 있는 부분

“근거가 있는 쪽이 이긴다”는 무슨 뜻일까?

문서와 구현 중 한쪽이 항상 우선이라는 뜻은 아닙니다.

  • 명세나 직접 내린 제품 결정이 근거라면 구현을 고칩니다.
  • 구현하면서 발견한 실제 제약이 더 정확하다면 문서를 고칩니다.
  • 둘 다 근거가 없다면 사용자에게 더 자연스러운 동작을 기준으로 정합니다.
  • 예전 결정이 바뀌었다면 과거 문서를 지우지 않고 변경 이유를 남깁니다.
전제가 깨진 테스트는 왜 고치지 않고 지울까?

테스트는 특정 제품 동작을 지키기 위해 존재합니다. 제품에서 그 동작이 없어졌는데 테스트만 통과하도록 고치면, 이제 무엇을 지키는지 알 수 없는 테스트가 됩니다.

고쳐서 유지

버튼 문구, 접근 가능한 이름, 셀렉터처럼 표현만 바뀐 경우

새 위치로 이전

같은 사용자 동작이 다른 화면이나 더 저렴한 테스트 계층으로 이동한 경우

삭제

제품에서 검증 대상 동작 자체가 사라진 경우

의도적 미검증 기록

동작은 남았지만 위험과 비용을 비교해 자동 테스트 범위에서 제외한 경우

“이미 있던 테스트”와 “옮긴 테스트”는 왜 구분할까?

기존 테스트가 이미 같은 부분을 보고 있었다면 새 검증을 추가한 것이 아닙니다. “옮겼다”고 쓰면 삭제한 모든 단언이 다른 곳에서 새로 이어졌다고 오해할 수 있습니다. 

기존 테스트가 이미 있었다 ≠ 새 테스트를 옮겼다
제품 동작이 사라졌다 ≠ 다른 테스트가 대신 검증한다
의도적으로 검증하지 않는다 ≠ 검증할 대상이 사라졌다
세션 만료인데 왜 401 전역 처리가 실행되지 않을까?

전역 처리는 React Query가 받은 오류만 볼 수 있습니다. getSession()은 401을 오류로 던지지 않고 null로 바꾸고, 장바구니·주문서·위시리스트는 Zustand의 로컬 데이터만 읽습니다. 따라서 전역 오류 처리기에 도착하는 401 자체가 없습니다.

주문 내역은 주문 API 쿼리가 따로 있어서 401이 전역 처리기로 전달됩니다. 같은 보호 경로라도 화면이 어떤 데이터를 요청하는지에 따라 만료 동작이 달라지는 이유입니다.

toHaveBeenCalledWith만으로 왜 중복을 못 잡을까?

이 단언은 조건에 맞는 호출이 하나라도 있는지만 확인합니다. 호출 횟수는 묻지 않습니다. 그래서 같은 이벤트가 두 번 발행돼도 기대한 인자의 호출이 존재하므로 통과합니다. 중복 방지 로직을 지키려면 toHaveBeenCalledTimes(1)이 함께 필요합니다.

실행과 검증 순서

  1. 세션 만료 안내와 관련 통합 테스트를 추가 완료했습니다.
  2. 로그아웃 실패 통합 테스트를 추가 완료했습니다.
  3. product_list_view 호출 횟수 단언을 추가 완료했습니다.
  4. pnpm verify로 단위·통합 테스트, 린트, 타입 검사를 실행 완료했습니다.
  5. PR 본문과 삭제 테스트 설명을 실제 이력에 맞게 정정해야 합니다.
  6. 세션 만료를 포함한 인증 브라우저 시나리오 확인을 완료했습니다.
검증 범위

기본 검증에는 프로덕션 빌드와 Playwright가 포함되지 않습니다. 화면 관련 구현 후 런타임 검증을 요청하지 않았다면 완료 보고에 미검증 사실을 별도로 남깁니다.

검증 결과
  • pnpm verify: Vitest 29개 파일·164개 테스트, 린트, 타입 검사를 모두 통과했습니다.
  • e2e/add-to-wishlist.spec.ts: Chromium·WebKit에서 위시리스트 새로고침 유지 시나리오가 모두 통과했습니다(2 passed).
  • e2e/auth.spec.ts: Chromium·WebKit에서 로그인, 세션 만료, 재시도 시나리오가 모두 통과했습니다(6 passed).
  • 로그아웃 E2E와 전체 Playwright 스위트, 프로덕션 빌드는 이번 범위에서 실행하지 않았습니다.
