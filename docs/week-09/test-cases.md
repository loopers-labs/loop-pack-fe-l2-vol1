# 9주차 테스트 케이스 — 인증과 계측

> 1·2단계로 구현한 화면의 수동 QA 케이스다. 3단계에서 E2E로 올릴 대상을 고를 때, 그리고 4단계에서 단언을 쓸 때 셀렉터와 기대 문구의 출처로 쓴다.
>
> **이 문서는 E2E 대상 목록이 아니다.** 여기 96개 중 무엇을 E2E로 올릴지는 [E2E 범위 설계](../rfc/week09-e2e-scope.md) §C에서 정한다. 대부분은 단위·통합 테스트가 더 싼 항목이고, 그 판단의 재료로 전부 적어 둔 것이다.

## 표기 규칙

| 구분        | 뜻                                                                       |
| ----------- | ------------------------------------------------------------------------ |
| `직접`      | 작성자가 화면을 보며 직접 뽑은 케이스                                    |
| `직접·수정` | 작성자 케이스인데 적힌 값이 구현과 달라 고친 것. 고친 이유를 함께 적었다 |
| `보완`      | 코드와 대조해 빠져 있던 것을 채운 케이스                                 |

기대 결과의 `코드체`는 실제 접근 가능한 이름이나 URL을 그대로 옮긴 값이다. 상품명이 들어가는 이름은 `{상품명}`으로 적었다.

---

## 공통 사전조건

모든 케이스가 전제하는 값이다. 각 표의 "사전조건"은 여기에 더해지는 것만 적었다.

| 항목          | 값                                                                                                                  |
| ------------- | ------------------------------------------------------------------------------------------------------------------- |
| 환경          | `pnpm build` 후 `pnpm start`. 개발 서버가 아니라 프로덕션 빌드에서 확인한다 — 가드와 정적/동적 판정이 빌드 기준이다 |
| 계정          | `looper1@loopers.dev` ~ `looper8@loopers.dev` / 비밀번호 `looper1234`. 없는 계정 예: `wendy@loopers.dev`            |
| 미로그인 상태 | 세션 쿠키 `session` 없음. 케이스 사이에 쿠키와 `localStorage`를 비운다 — 장바구니·위시리스트가 브라우저에 남는다    |
| 보호 경로 5개 | `/cart` `/checkout` `/orders` `/wishlist` `/mypage`                                                                 |
| 공개 경로     | `/` `/products` `/login`                                                                                            |

## 5. 프로덕트 카드 — 찜 · 담기

홈 · `/products` · `/wishlist`가 같은 카드를 쓴다. 세 화면에서 같은 동작을 반복 검증할지, 한 화면에서만 볼지는 아래 「정해야 넘어가는 자리」 ②를 참고한다.

| ID      | 구분      | 사전조건                                | 절차                              | 기대 결과                                                                                                                |
| ------- | --------- | --------------------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| CARD-01 | 직접      | 미로그인 · `/products?category=fashion` | 카드의 [찜]을 클릭한다            | 로그인 화면으로 이동. URL `/login?returnUrl=%2Fproducts%3Fcategory%3Dfashion&entryPoint=product_wishlist&productId={id}` |
| CARD-02 | 직접      | 미로그인 · `/products`                  | 카드의 [담기]를 클릭한다          | 같은 형태, `entryPoint=product_cart`                                                                                     |
| CARD-03 | 직접      | 로그인 · 홈                             | 카드의 [찜]을 클릭한다            | 헤더 `위시리스트 {n}`의 숫자가 1 증가                                                                                    |
| CARD-04 | 직접·수정 | 로그인 · 홈                             | 카드의 [담기]를 클릭한다          | 헤더 `장바구니 {n}`의 숫자가 1 증가                                                                                      |
| CARD-05 | 직접·수정 | 로그인 · 홈                             | [담기]를 클릭한다                 | 확인 창이 뜬다. 문구 `장바구니 페이지로 이동하겠습니까?` · 버튼 `취소` `장바구니 이동`. 기본 포커스는 [취소]             |
| CARD-06 | 직접      | 확인 창이 열린 상태                     | [장바구니 이동]을 클릭한다        | `/cart`로 이동                                                                                                           |
| CARD-07 | 직접      | 확인 창이 열린 상태                     | [취소]를 클릭한다                 | 창이 닫히고 현재 화면 유지. **담긴 상품은 그대로** — 묻는 것은 "담을까요"가 아니라 "지금 갈까요"                         |
| CARD-08 | 보완      | 확인 창이 열린 상태                     | [취소]로 닫는다                   | 포커스가 방금 누른 [담기] 버튼으로 돌아온다 — 연속으로 담을 때 위치를 잃지 않는다                                        |
| CARD-09 | 보완      | 확인 창이 열린 상태                     | Esc를 누른다 / 창 바깥을 클릭한다 | 둘 다 창이 닫히고 화면이 유지된다                                                                                        |

> **CARD-04 수정** — 배지는 **담긴 상품 종류 수**다. 같은 상품을 한 번 더 담으면 수량만 오르고 숫자는 그대로다.
>
> **CARD-05 수정** — 초안의 `장바구니 페이지로 이동하게습니까?`는 오타다.

## 7. 보호 경로 가드와 복원

과제 완료조건 "미로그인으로 보호 경로에 들어가면 로그인 후 원래 경로로 돌아온다"가 걸리는 자리다. 초안에는 헤더 링크로 가는 경로만 있었는데, **주소창 직접 진입은 다른 경로이고 만들어지는 URL도 다르다** — 가드가 만든 URL에는 `entryPoint`가 없다.

| ID     | 구분 | 사전조건                      | 절차                                                              | 기대 결과                                                                    |
| ------ | ---- | ----------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| GRD-01 | 보완 | 미로그인                      | 주소창에 `/checkout`을 직접 입력한다                              | `/login?returnUrl=%2Fcheckout`으로 이동. **`entryPoint`가 붙지 않는다**      |
| GRD-02 | 보완 | 미로그인                      | 보호 경로 5개에 각각 직접 진입한다                                | 다섯 개 모두 로그인 화면으로. 응답 코드는 **302가 아니라 307**               |
| GRD-03 | 보완 | 미로그인                      | `/cart?from=header`로 진입한다                                    | 쿼리까지 실린다 — `returnUrl=%2Fcart%3Ffrom%3Dheader`                        |
| GRD-04 | 보완 | GRD-01 직후                   | 정상 계정으로 로그인한다                                          | `/checkout`으로 돌아온다                                                     |
| GRD-05 | 보완 | 미로그인                      | `/login?returnUrl=https://evil.example.com`으로 들어가 로그인한다 | 외부 주소로 나가지 않고 `/`로 이동                                           |
| GRD-06 | 보완 | 미로그인                      | `returnUrl`에 `//evil.com` · `/\evil.com` · 빈 값을 각각 넣는다   | 세 경우 모두 `/`로 이동. `//evil.com`은 `/`로 시작해 경로처럼 보이는 게 함정 |
| GRD-07 | 보완 | 미로그인                      | `/` · `/products` · `/login`에 진입한다                           | 세 화면 모두 정상 노출. 가드에 걸리지 않는다                                 |
| GRD-08 | 보완 | 로그인 상태에서 로그아웃 직후 | `/cart`에 직접 진입한다                                           | 다시 `/login?returnUrl=%2Fcart`로 이동                                       |

## 14. 세션 만료와 위조 쿠키

완료조건의 뒷문장 "세션이 만료되면 다음에 무엇을 해야 할지 화면에서 알 수 있다"가 걸리는 자리다. 전용 만료 화면은 만들지 않았고 로그인 화면이 그 역할을 한다.

**쿠키를 지우는 방식으로는 이 자리를 볼 수 없다.** 쿠키가 없으면 다음 화면 이동에서 `proxy.ts` 가드가 먼저 잡아 GRD 절과 같은 길이 된다. 만료 처리(`Providers`의 `QueryCache.onError`)가 도는 길을 보려면 가드를 통과할 유효한 쿠키를 남기고 API만 401을 내게 해야 한다. 또한 `/api/auth/me`의 401은 `getSession`이 `null`로 흡수하므로, 만료 이동을 실제로 일으키는 화면은 401에 던지는 쿼리를 가진 `/orders` 하나다.

| ID     | 구분 | 사전조건           | 절차                                                                           | 기대 결과                                                                    |
| ------ | ---- | ------------------ | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| SES-01 | 보완 | 로그인 · `/orders` | 세션 쿠키는 그대로 두고 `scenario=expired` 쿠키를 심은 뒤 `/orders`에 진입한다 | `/login?returnUrl=%2Forders`로 이동. 로그인하면 `/orders`로 돌아온다         |
| SES-02 | 보완 | `/login` 화면      | 이 화면에서 401이 나는 상황을 만든다                                           | **이동하지 않는다** — `/login`에서 `/login`으로 되도는 것을 막는다           |
| SES-03 | 보완 | 위조한 세션 쿠키   | `/cart`에 진입한다                                                             | 가드는 통과해 화면이 뜨지만 **목록이 비어 있다** — 남의 목록이 보이지 않는다 |

## E2E가 쓸 접근 가능한 이름

[9주차 E2E 범위 문서](../rfc/week09-e2e-scope.md)에서 고른 세 시나리오가 실제로 통과하는 요소만 적는다. 아직 E2E를 붙이지 않은 화면은 넣지 않는다 — 쓰지 않을 계약을 유지하게 된다.

**화면 글자와 접근 가능한 이름이 다른 것부터 본다.** 담기·찜 버튼은 `aria-label`을 달고 있어서 화면에는 `담기`라고 보이지만 `getByRole('button', { name: '담기' })`로는 잡히지 않는다. 위 표의 `[담기]` 같은 표기는 화면 글자이고, E2E가 쓸 이름은 아래 표에 있다.

| 3 주문   | 주문내역 항목               | —                     | `주문번호 {주문 id}`                                    | `_pages/orders/ui/OrderList.tsx:55`                                    |

상품명이 세 자리(카드 제목 · 담기 버튼 · 장바구니 행)에 들어간다. 시드 상품명이 바뀌면 세 곳이 함께 깨진다. 유지보수 비용 계산은 [E2E 범위 문서의 「유지보수 비용 추정」](../rfc/week09-e2e-scope.md#유지보수-비용-추정)에 있다.

위 값은 소스를 읽어 옮긴 것이고 브라우저에서 실제 렌더 결과로 확인하지 않았다. 4단계에서 로케이터를 붙일 때 한 번 더 대조한다.

---

## 이 중 E2E가 덮는 것

4단계에서 붙인 다섯 테스트가 위 케이스 중 무엇을 지나가는지다. 나머지는 수동 QA와 아래 계층의 몫으로 남는다 — 이 표는 E2E 대상 목록이 아니라 [범위 설계](../rfc/week09-e2e-scope.md) §C의 판단을 케이스 번호로 되짚은 것이다.

| E2E                            | 덮는 케이스              | 같은 것을 보지만 다르게 단언하는 곳                              |
| ------------------------------ | ------------------------ | ---------------------------------------------------------------- |
| 보호 경로 진입 → 로그인 → 복원 | GRD-01 · GRD-04 · LGN-01 | HDR-07의 "JS 없이도 보인다"를 `/orders`의 로그인 상태로 확인한다 |
| 세션 만료                      | SES-01                   | —                                                                |
| 잘못된 비밀번호와 재시도       | LGN-02                   | 재시도 성공까지 한 테스트에서 본다                               |
| 담기 → 장바구니 이동           | CARD-05 · CARD-06        | 헤더 숫자(CARD-04)는 단언하지 않는다                             |
| 주문 → 주문 내역               | CRT-11 · ORD-01          | ORD-01의 "상품이 보인다" 대신 `주문번호 {방금 만든 id}`로 좁힌다 |

E2E에만 있고 위 표에 대응 케이스가 없는 단언이 둘이다. `login_start`와 `login_fail`이 같은 `flow_id`를 다는 것(위 ① 결정의 결과), 그리고 `/orders`의 초기 HTML에 로그인 상태가 있는 것이다.

반대로 E2E가 확인하지 않는 것도 적어 둔다. GRD-02의 **307이라는 응답 코드 자체**(최종 URL만 본다), CARD-05의 **기본 포커스가 [취소]에 있는 것**, GRD-05·06의 **외부 주소 차단**이다.

## 정해야 넘어가는 자리

여기서 답을 정하지 않았다. 어느 쪽으로 가든 위 표에서 지우거나 더할 케이스가 달라진다.

### ① 계측을 어디까지 볼 것인가 — 정했다

지금 표에는 URL에 드러나는 것만 넣었다.

| 선택지          | 내용                                                                                               |
| --------------- | -------------------------------------------------------------------------------------------------- |
| URL까지만       | ANL 3건 유지. 화면에서 보이는 것만 단언한다                                                        |
| 이벤트 버퍼까지 | `window.__analytics`를 읽어 이름·`flow_id`·프로퍼티를 단언한다. 범위는 넓어지고 구현 세부에 묶인다 |
| TC에서 제외     | RFC §C에 "안 붙인 경로"와 근거로만 남긴다                                                          |

**이벤트 버퍼까지 보되, 인증 시나리오 한 곳으로 제한한다.** E2E는 `login_start`와 `login_success`가 같은 `flow_id`를 다는 것만 단언하고, 나머지 계측 회귀는 `analytics/logger.test.ts`와 `ProductListContent.test.tsx`가 맡는다.

담기·주문 시나리오에서 보지 않는 것은 판단이기 전에 제약이다. `flow_id`는 `sessionStorage`에 살고 Playwright의 `storageState`는 `sessionStorage`를 싣지 않으므로, 로그인을 건너뛴 테스트에는 `flow_id`가 아예 존재하지 않는다. 근거는 [RFC의 「4단계 경계」](../rfc/week09-e2e-scope.md#4단계-경계--격리와-storagestate)에 있다.

### ② 같은 동작을 몇 화면에서 반복할 것인가

찜·담기·확인 창은 홈 · 상품 목록 · 위시리스트에서 **같은 부품**이다. 세 화면에서 다 볼지, 한 화면에서만 보고 나머지는 "같은 컴포넌트"로 근거를 적을지에 따라 케이스 수가 크게 달라진다.

### ③ E2E로 갈 것과 아래 계층에 남길 것

위 표는 **수동 QA 기준**으로 썼다. 이 중 브라우저가 꼭 필요한 것은 가드의 307과 `Location` 헤더, JS를 끈 초기 HTML, 쿠키 속성 정도이고, 나머지 상당수(`returnUrl` 검증, 금액 계산, 소유자 분리, 빈 상태 분기)는 단위·통합 테스트가 더 싸다. 어느 케이스를 4단계 E2E로 올릴지는 [E2E 범위 설계](../rfc/week09-e2e-scope.md) §C의 판단이다.

### ④ 장바구니 수량 상한

지금 코드에 상한이 없어 관련 케이스를 넣지 않았다. 서버가 값을 내려주기로 정해지면 §10에 추가되는 자리다.
