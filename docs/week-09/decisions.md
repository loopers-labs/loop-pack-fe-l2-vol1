## 1. 복원 경로를 어떤 파라미터로 실어 나를 것인가

### 고민

미로그인으로 보호 경로에 들어오면 로그인 후 원래 가려던 곳으로 돌려보내야 한다. 그 경로를 담을 쿼리 파라미터 이름을 정해야 했다.

처음에는 `returnUrl`이 걸렸다. 우리는 `/checkout` 같은 **경로만** 받을 생각인데 이름은 절대 URL을 받을 것처럼 읽힌다. 계약과 이름이 어긋나는 것 아닌가 싶었다.

### 검토한 선택지

1. **`returnUrl`** — 널리 쓰여 처음 보는 사람도 뜻을 짐작한다. 다만 절대 URL을 받는다고 오해할 여지가 있다.
2. **`returnPath` / `next`** — 받는 값의 모양이 이름에 드러난다. 대신 관용적이지 않아 팀에서 다시 설명해야 한다.

### 결정

`returnUrl`로 정했다.

### 판단 근거

오칭이 아니었다. 브라우저 기준으로 `/checkout`도 상대 URL이라 `returnUrl`이 틀린 이름이 아니다.

더 중요한 건 **이름이 안전성을 전혀 책임지지 못한다**는 점이었다. 막아야 하는 값(`//evil.com`, `https://evil.com`)도 전부 유효한 URL이라, 어떤 이름을 붙여도 이름이 걸러 주는 게 없다. 안전성은 전부 검증 함수가 진다.

특히 `//evil.com`은 `/`로 시작해서 경로처럼 보이는데 실제로는 외부로 나가는 프로토콜 상대 URL이다. 이름으로 안전을 표현하려던 생각이 오히려 이 값을 놓치게 만들 뻔했다.

거부 대상은 `//evil.com`, `https://evil.com`, `/\evil.com`(백슬래시 정규화), 빈 값이다. 통과하지 못하면 `/`로 대체한다. 순수 함수라 Vitest 단위 테스트가 가장 싸다.

## 2. 보호 경로를 어디까지로 할 것인가

### 고민

명세는 주문서와 주문 내역만 필수로 정하고, 장바구니·위시리스트·마이페이지는 판단에 맡겼다.

### 검토한 선택지

1. **필수 둘만 보호한다** — 범위가 작다. 대신 장바구니를 미로그인으로 볼 수 있어 "누구의 장바구니인가"가 애매해진다.
2. **사용자 고유 데이터를 보여주는 화면 전부** — 기준이 하나라 화면이 늘어도 판단이 흔들리지 않는다.

### 결정

**사용자 고유 데이터를 보여주는 모든 화면**을 보호한다. 지금은 `/checkout` · `/orders` · `/cart` · `/wishlist` · `/mypage` 다섯이다.

### 판단 근거

목록이 아니라 기준으로 정했다. 화면이 늘 때마다 "이건 보호인가"를 다시 논의하지 않아도 된다.

장바구니를 열어 두면 store를 유지하는 순간 **누구의 장바구니인지 모르는 목록**을 보게 된다. 공용 브라우저에서 앞사람의 목록이 그대로 보이는 모양이라, 화면을 막는 쪽이 자연스러웠다.

`/mypage`는 일관성 이전에 내용이 전부 `GET /api/auth/me`라 세션 없이는 그릴 것이 없다.

## 3. 로그아웃하면 장바구니와 위시리스트를 어떻게 할 것인가

### 고민

명세가 "지울지 남길지 정하고 이유를 적으라"고 한 항목이다. 남기면 다음 사람에게 보이고, 지우면 다시 로그인한 본인이 잃는다.

### 검토한 선택지

1. **지운다** — 다음 사람에게 안 보인다. 대신 본인이 다시 로그인해도 목록이 없다.
2. **남긴다** — 본인은 유지된다. 대신 로그아웃 상태에서 남의 목록이 보인다.
3. **소유자별로 나눠 들고, 미로그인에게는 보여주지 않는다** — 둘 다 만족한다.

### 결정

3번. store가 소유자별로 목록을 나눠 들고, 로그아웃하면 지우지 않되 보여주지도 않는다. 헤더 배지의 숫자도 로그인 상태에서만 붙는다.

미로그인 상태에서는 담기·찜을 할 수 없다. 담기 버튼을 누르면 `/login?returnUrl=...`으로 보낸다.

### 판단 근거

미로그인으로 담을 수 없게 하면 **익명 목록이 아예 생기지 않아** 로그인 시 합치는 문제가 없어진다. 마이그레이션·병합 로직이 통째로 사라지는 게 이 선택의 실질적인 이득이었다.

보호 경로 결정(2번)과도 맞물린다. 장바구니 화면 자체가 막혀 있으니 "로그아웃 상태에서 목록을 본다"는 상황이 애초에 없다.

## 4. 세션 만료(401)를 어디서 받을 것인가

### 고민

명세가 "한 곳으로 정하고 근거를 남기라"고 한 항목이다. 공통 처리니까 상위 레이어로 올려야 한다고 생각했고, 처음에는 `_pages`를 떠올렸다.

### 검토한 선택지

1. **`_pages`** — 상위 레이어이긴 하다. 그런데 라우트마다 하나씩 존재하는 계층이라, 여기 두면 화면 수만큼 복제된다. "한 곳에 모은다"와 정반대다.
2. **`shared/api`에 공통 fetch 래퍼를 신설** — 쿼리를 안 거치는 호출까지 덮는다. 대신 지금은 entity마다 fetch를 직접 쓰고 있어 리팩터 범위가 생긴다.
3. **`_app`의 `QueryClient`에 전역 에러 핸들러** — 모든 클라이언트 쿼리가 지나는 자리이고, 앱 전역 정책의 자리다.

### 결정

3번. `_app/providers/Providers.tsx`의 `QueryClient`에 `QueryCache.onError`를 달아 거기서 받는다.

감지는 `shared/api`가 이미 하고 있다 — `ApiError`가 `status`를 들고 있어(`shared/api/api-error.ts`) 새로 만들 것이 없었다.

### 판단 근거

`_pages`를 떠올린 게 잘못이었다. 방향은 맞았는데 목적지가 한 칸 어긋났다. 레이어를 다시 보니 기준은 "위인가"가 아니라 **"그 레이어가 앱에 몇 개 존재하는가"**였다.

| 레이어                                      | 개수                |
| ------------------------------------------- | ------------------- |
| `_app`, `shared`                            | 앱 전체에 하나      |
| `_pages`, `widgets`, `features`, `entities` | 슬라이스마다 하나씩 |

앱 전역에 하나만 존재해야 하는 정책은 슬라이스가 없는 레이어에 둬야 한다. 이 구분은 6주차에 만든 `eslint/fsd.config.mjs`에 `SLICED_LAYERS`로 이미 들어 있었는데, 그동안 import 방향을 검사하는 설정으로만 읽고 있었다.

`shared`가 아닌 이유는 하는 일이 둘로 갈리기 때문이다. **감지**(응답이 401인 걸 알아채는 것)는 도메인 지식이 필요 없어 `shared`가 맡고, **반응**(만료로 판단해 로그인으로 보내는 것)은 앱 정책이라 `_app`이 맡는다.

### 덧붙임 — 완전히 한 곳은 아니다

클라이언트 쿼리의 401은 `_app`으로 모이지만, Server Component가 세션을 읽는 경로는 그 핸들러를 지나지 않고 `proxy.ts` 가드가 맡는다. 서버와 클라이언트는 애초에 다른 경로라 합쳐질 수 없다. **클라이언트 401은 `_app` 한 곳, 서버 미인증은 가드 한 곳**으로 나뉜다는 것까지가 결정이다.

또 401은 재시도를 꺼야 한다. TanStack Query 기본이 3회라 그대로 두면 만료 화면이 늦게 뜨고 E2E가 타임아웃 난다.

## 5. "로그인 안 함"과 "세션 만료"를 무엇으로 가를 것인가

### 고민

`/api/auth/me`가 둘을 같은 401로 돌려준다. 처음에는 쿠키에 든 토큰의 만료 시각을 같이 보면 되겠다고 생각했다. 실제로 토큰 payload에 `exp`가 있고 `readSessionToken`이 그걸 본다.

### 검토한 선택지

1. **토큰의 `exp`를 읽어 가른다** — 세 가지가 막았다.
   - 쿠키가 `httpOnly`라 클라이언트가 못 읽는다. 401을 받기로 한 자리가 `_app`의 `onError`, 즉 클라이언트다.
   - `maxAge`와 `exp`가 둘 다 1시간이라, 토큰이 만료되는 순간 브라우저가 쿠키도 지운다. "쿠키는 있는데 토큰만 만료된" 상태가 시계 오차만큼만 생긴다.
   - `expired` 시나리오는 **쿠키가 유효한 채로** 401을 준다. 토큰을 열어보면 안 만료됐다고 나오는데 API는 401이다.
2. **엔드포인트로 가른다** — 로그인 요청의 401은 자격 증명 오류, 나머지는 만료. 그런데 홈과 상품 목록이 공개 화면이라, 미로그인 방문자에게도 헤더의 세션 조회 401이 난다. 그걸 만료로 보면 처음 온 사람에게 세션 만료 화면이 뜬다.
3. **요청이 세션을 전제하는가로 가른다** — 같은 주소라도 호출하는 쪽에 따라 뜻이 다르다는 걸 반영한다.

### 결정

3번.

```
클라이언트 401 = 만료.  단, 로그인 mutation은 제외
```

처음에는 6번에서 세션을 서버에서 읽기로 하면서 클라이언트 세션 쿼리가 사라져 기준이 단순해졌다고 적었다. **구현에서는 그렇게 되지 않았다.** 장바구니·위시리스트의 소유자를 맞추려면 클라이언트도 현재 사용자를 알아야 해서, `_app`의 `useSyncCollectionOwner`가 세션을 쿼리로 읽는다(7번).

그래도 규칙은 그대로 성립한다. 이유가 달라졌을 뿐이다 — `getSession`이 401을 예외가 아니라 `null`로 돌려주기 때문에(`entities/session/api/api.ts`) 그 401은 애초에 `QueryCache.onError`에 도달하지 않는다. 공개 화면을 보는 미로그인 방문자에게 만료 화면이 뜨지 않는 것이 이 처리 덕분이고, 그래서 핸들러에 남는 오류는 전부 세션을 전제한 요청의 것이다.

로그인 mutation을 빼는 것은 필수다. 전역 핸들러가 그것까지 잡으면 비밀번호를 틀렸을 때 `/login`에서 `/login`으로 리다이렉트한다. 다만 이건 예외 코드로 막지 않았다 — 핸들러를 `QueryCache`에 달았고 로그인은 mutation이라 애초에 그 자리를 지나지 않는다.

### 판단 근거

1번의 세 번째가 결정적이었다. 실제 서비스에서 관리자가 세션을 끊거나 비밀번호 변경으로 기존 세션을 폐기하면 정확히 그 모양이 된다 — 쿠키는 멀쩡한데 서버가 안 받아준다. 토큰을 믿는 판정은 그걸 못 잡고, 하필 4단계에서 재현해야 할 케이스가 그것이다.

명세 문구도 "**어떤 요청의** 401을 만료로 볼지"였다. 토큰이 아니라 요청의 맥락을 보라는 쪽으로 읽혔다.

`meta: { authRequired: true }` 같은 플래그로 요청을 표시하는 방법도 준비했지만, 세션을 서버에서 읽게 되면서 지금은 필요가 없어졌다. 나중에 세션 조회가 클라이언트로 내려오면 그때 붙인다.

여기서 남은 것은 **클라이언트가 세션에 대해 알 수 있는 게 생각보다 적다**는 점이다. `httpOnly` 쿠키는 있는지조차 확인이 안 되니, 클라이언트가 쥔 정보는 "서버가 방금 401을 줬다"와 "그 요청이 세션을 전제했는가" 정도다.

## 6. 세션을 어떻게 읽을 것인가

### 고민

명세가 요구사항으로 못박은 항목이다 — "서버에서 세션을 읽어 초기 HTML에 로그인 상태를 반영해요. 단 쿠키를 읽는 위치에 따라 정적 생성 범위가 달라지니, 7주차 성능 기준을 다시 깨지 않는지 확인하세요."

"서버에서 읽는다"가 두 가지로 갈렸다.

### 검토한 선택지

1. **Server Component가 `/api/auth/me`를 호출한다** — 제공된 API를 그대로 쓴다. 서버 fetch는 브라우저 쿠키를 자동으로 붙이지 않으므로 `cookies()`로 읽어 `Cookie` 헤더에 실어 보낸다. 대신 `waitForAuthApi`가 매 호출 500ms를 잡는다(`auth.ts`, 테스트 환경만 0). 헤더는 모든 화면에 있으니 **모든 페이지의 서버 렌더가 500ms 밀린다.**
2. **쿠키를 직접 읽고 `readSessionToken()`을 호출한다** — 지연이 없다. 대신 그 함수는 mock 서버의 내부 모듈이라, 실제 백엔드가 분리된 환경에서는 쓸 수 없는 방식이다.

### 결정

1번. 지연을 감수하고 API를 호출한다. 헤더는 `Suspense`로 흘려보내지 않고 껍데기에서 기다린다.

### 판단 근거

두 방식의 차이는 **쿠키를 전달하느냐 해석하느냐**다. 1번은 쿠키를 읽되 그 값을 이해하려 들지 않고, 검증 책임을 API 한 곳에 남긴다. 토큰 형식이 바뀌어도 앱 코드가 바뀌지 않고, 실제 백엔드가 분리돼도 그대로 동작한다.

2번이 빠르지만, 빠른 이유가 mock의 인위적 지연을 우회하는 것뿐이다. 실제 서비스에서는 어차피 네트워크를 타야 하는 호출이라, 지금 지연을 피하려고 실제 구조와 다른 길을 만드는 게 맞지 않다고 봤다.

`Suspense`로 흘려보내지 않은 것은 명세가 "JavaScript 실행 전에도 로그인 여부가 보여야 한다"고 했기 때문이다. 스트리밍하면 헤더가 나중에 붙어 그 요구와 부딪힌다.

### 함께 확인해야 하는 것

- **7주차 성능 회귀가 예상된다.** 7주차에 h1이 566.0ms에 등장하는 것을 문제로 보고 고쳤는데, 껍데기에서 500ms를 기다리면 그 자리로 돌아간다. 명세 118줄이 요구하는 것이 이 확인이다. **측정했고, 실제로 그 자리로 돌아갔다** — 아래 "7주차 지표 재측정" 절.
- **`cookies()`를 부르면 그 라우트가 동적이 된다.** 홈은 이미 `force-dynamic`이라 무관하지만, `/products`는 세그먼트 설정이 없고 `ProductListPage`가 `searchParams`를 받지 않아 지금 정적일 수 있다. 빌드 출력의 Route 목록으로 확인이 필요하다.
- **페이지를 `async`로 만들지 않는다.** `HomePage.tsx`에 같은 실수가 기록되어 있다 — async로 두면 return 전체가 await 뒤로 밀려 Header와 h1까지 데이터를 기다린다. 세션 읽기는 Header를 감싸는 작은 async Server Component로 좁힌다.

## 7. 세션 전용 store를 둘 것인가

### 고민

장바구니와 위시리스트가 각각 `ownerId`·`byOwner`·`setOwner`를 갖게 되니 소유자 전환 코드가 양쪽에 중복된다. "현재 사용자"를 store 하나로 모으면 중복이 사라지지 않을까 싶었다.

### 검토한 선택지

1. **`userStore`를 두고 두 store가 참조한다** — `entities/cart`가 `entities/user`를 부르는 형태인데, 같은 레이어의 다른 슬라이스 참조라 FSD가 막는다. `@x`도 타입만 공개하고 store 같은 런타임 구현은 금지한다.
2. **`userStore`를 두고 소비처가 두 store를 조합한다** — 레이어 위반은 없다. 대신 조합 코드를 어디 둘지가 문제가 된다. 소비처가 `features/add-to-cart`, `features/add-to-wishlist`(features), `widgets/header`(widgets), 그리고 앞으로 생길 화면들(`_pages`)에 걸쳐 있어, **모두가 함께 쓸 수 있는 레이어가 없다.** features에 두면 다른 feature 슬라이스가 못 쓰고, widgets에 두면 features가 못 쓴다.
3. **각 store가 소유자 분할을 직접 든다** — 소비처는 selector만 쓰면 되고 레이어 문제가 없다. 대신 소유자 전환 코드가 양쪽에 남는다.

### 결정

3번. 세션 전용 store는 두지 않는다.

### 판단 근거

2번을 택하면 "현재 사용자의 목록"이라는 규칙이 소비처 넷으로 흩어진다. 한 곳을 빼먹으면 거기서만 남의 목록이 보이는 종류의 버그다. **규칙이 store 안에 한 번 있는 쪽이 몇 줄 중복보다 싸다**고 봤다.

실제로 구현해 보니 중복도 예상보다 적었다. 목록을 파생값으로 만들면서 소유자 전환이 한 줄로 끝났기 때문이다(8번).

## 8. 장바구니 store를 팩토리에서 떼어낼 것인가

### 고민

장바구니와 위시리스트는 `ids` + `toggle`만 필요해서 `shared/lib/create-collection-store` 하나로 찍어 쓰고 있었다. 6주차에 그 파일에 예고를 적어 뒀다.

> 장바구니에 수량 같은 다른 로직이 생기면 그 store만 이 팩토리에서 떼어내 독립 구현으로 교체한다.

`POST /api/orders`가 `{ productId, quantity }`를 요구하니 장바구니에 수량이 필요해졌고, 예고한 조건이 그대로 왔다.

### 결정

팩토리를 버리고 두 store를 각각 독립 구현으로 뒀다. 갈라지는 축이 둘이었다 — **아이템 모양과 연산은 갈라지고, 소유자 분할은 양쪽에 똑같이 필요**하다.

|        | 장바구니                                      | 위시리스트      |
| ------ | --------------------------------------------- | --------------- |
| 아이템 | `items: { productId, quantity }[]`            | `ids: string[]` |
| 연산   | `add` / `remove` / `setQuantity` / `clearAll` | `toggle`        |
| 소유자 | `ownerId` · `byOwner` · `setOwner`            | 동일            |

장바구니에서 `toggle`을 없앤 것은 수량이 생긴 뒤로 "다시 누르면 빠진다"가 성립하지 않기 때문이다. 수량 3인 상품에서 다시 누르면 무엇이 되어야 하는지 정할 수 없다. 제거는 장바구니 화면의 명시적 동작으로 옮겼다. 찜은 켜고 끄는 동작이라 `toggle`이 그대로 맞다.

담기는 누를 때마다 수량을 하나 올린다. 헤더 배지는 담긴 **상품의 종류 수**이고 수량 합이 아니다.

### 판단 근거 — `items`를 필드로 두지 않은 이유

와이어프레임 단계에서는 `items`를 store 필드로 두고 `setOwner`가 보관·복원하는 그림이었는데, 구현하면서 바꿨다. `items`와 `byOwner` 두 벌을 들면 저장 시점에 어느 쪽이 진실인지 갈리고, 모든 변경에서 둘을 맞춰야 한다.

진실을 `byOwner` 하나로 두고 현재 소유자의 목록은 selector로 파생시켰다. 그러자 소유자 전환에 절차가 사라졌다.

```ts
setOwner: (ownerId) => set({ ownerId }),
```

"현재 소유자의 목록"이라는 규칙은 `selectCartItems` 한 곳에 있고, 소비처는 selector만 가져다 쓴다. 7번에서 걱정한 규칙 분산이 여기서 닫혔다.

### 저장 규칙

- **`ownerId`는 저장하지 않는다.** 저장하면 로그아웃한 브라우저가 마지막 소유자의 목록을 계속 보여준다. `partialize`로 `byOwner`만 남기고 `ownerId`는 매 로드마다 세션에서 채운다. **저장된 것은 데이터이고, 지금 누구인지는 세션이 정한다.**
- **기존 저장값은 옮기지 않고 버린다.** `version`을 올리고 빈 `byOwner`로 시작한다. 지금 저장된 목록은 로그인 없이 담긴 것이라 주인을 알 수 없고, 처음 로그인한 사람에게 넘기면 공용 브라우저에서 남의 장바구니를 주는 셈이 된다.
- **`byOwner` 검증 함수를 새로 썼다.** 기존 `readIds`가 하던 역할이다. 손상·조작된 저장값에서 읽을 수 있는 항목만 남긴다.
- **미로그인 상태에서는 변경을 막는다.** 담기 버튼이 로그인으로 보내지만, store가 스스로 막아야 주인 없는 목록이 생기지 않는다.
- **`setQuantity`는 1 이상의 정수만 받는다.** 주문 API가 그렇게 요구한다. 0으로 내리는 것은 수량 변경이 아니라 `remove`의 일이다.

## 9. 8주차 통합 테스트를 어떻게 할 것인가

### 고민

체크리스트에 "8주차 테스트가 그대로 통과하는가"가 있는데, store를 분리하니 `src/widgets/header/Header.test.tsx`의 3건이 실패했다. 전부 담기 버튼의 `aria-pressed` 단언이었다.

### 검토한 선택지

1. **`toggle`을 남겨 테스트를 그대로 둔다** — 체크 항목은 지킨다. 대신 수량 3에서 다시 누르면 어떻게 되는지 정하지 못한 동작이 코드에 남는다.
2. **단언을 새 동작으로 다시 쓴다** — 검증은 유지된다. 다만 담기 버튼에는 이제 읽을 상태가 없어 대체할 단언이 마땅치 않다.
3. **그 테스트를 지우고 이유를 주석으로 남긴다** — 검증 대상이 사라진 것을 인정한다.

### 결정

3번을 섞었다.

- `상품을 담고 다시 빼면…`은 **삭제**하고, 자리에 삭제 이유를 주석으로 남겼다. `aria-pressed`로 "담겼나 / 빠졌나"를 대신 보던 테스트인데 그 상태 자체가 없어졌고, 담김 여부는 장바구니 화면에 목록으로 그대로 보이므로 그 화면이 생기면 거기서 검증한다.
- 나머지 둘은 `aria-pressed` 단언만 빼고 유지했다. `찜을 눌러도 장바구니 개수는 그대로다`(두 store의 격리), `서로 다른 상품을 담으면 헤더 개수가 늘어난다`(배지가 종류 수)를 각각 본다.

`it.skip`이나 주석 처리로 비활성화하지는 않았다. 최종 상태는 120건 전부 통과다.

### 판단 근거

명세가 막으려는 건 "하지 말 것"의 다른 항목들과 함께 읽으면 드러난다 — `it.skip`으로 비활성화하기, **통과시키려고** 가드나 복원 로직을 지우기. 새 작업을 통과시키려고 기존 검증을 무력화하는 것을 막는 조항이다.

이 경우는 제품 동작이 의도적으로 바뀌어 옛 동작을 보던 단언이 무효가 된 것이다. 다만 **이 변경은 명세가 시킨 게 아니라 우리가 정한 것**이라(수량을 넣으면서 `toggle`을 남길 수도 있었다) 근거를 남길 책임이 더 크다고 봤다.

1번을 고르면 8주차 체크 하나를 지키려고 앞뒤가 안 맞는 동작을 코드에 남기게 된다. 이번 주 명세가 요구하는 "결정과 근거" 쪽에서 더 잃는다고 판단했다.

## 10. 가드에서 세션 쿠키를 어디까지 검증할 것인가

### 고민

4번에서 서버 미인증은 `proxy.ts` 가드가 받기로 했다. 그러면 가드가 쿠키를 어디까지 들여다볼지가 남는다.

처음에는 고를 여지가 없다고 적어 뒀다 — `proxy.ts`는 Edge 런타임이라 `node:crypto`를 쓰는 `readSessionToken`을 부를 수 없다고 봤기 때문이다.

**그 전제가 틀렸다.** Next 16에서 `proxy`의 런타임은 `nodejs`이고 설정으로 바꿀 수 없다. Edge를 쓰려면 오히려 `middleware.ts`를 유지해야 한다. 스타터가 `auth-cookies.ts`를 crypto와 분리해 둔 것도 Edge 시절 middleware를 전제한 구성이라, 지금은 그 이유만으로 유지할 근거가 없다.

런타임이 막은 게 아니라 실제로 고를 수 있는 선택지였다.

### 검토한 선택지

1. **존재만 확인한다** — `request.cookies.has(SESSION_COOKIE)`. 가드가 상수 하나에만 의존한다. 위조·만료 쿠키는 화면 껍데기까지 들어온다.
2. **`readSessionToken()`으로 서명·만료까지 검증한다** — 위조·만료를 진입 전에 끊는다. 대신 가드가 mock 서버 내부 모듈(`app/api/_data/auth.ts`)에 묶인다.
3. **가드가 `/api/auth/me`를 호출한다** — 정확하고 실제 백엔드 구조도 유지한다. 대신 보호 경로 진입마다 `waitForAuthApi`의 500ms가 붙는다.

### 결정

1번. 존재만 확인한다.

### 판단 근거

6번에서 이미 같은 갈림길을 지났다. 거기서 고른 것은 **쿠키를 해석하지 않고 전달만 하는 쪽**이었다 — 검증 책임을 API 한 곳에 남기면 토큰 형식이 바뀌어도, 실제 백엔드가 분리돼도 앱 코드가 그대로다. 2번은 그때 거부한 방식(6번 선택지 2, `readSessionToken` 직접 호출)과 정확히 같은 형태다. 가드에서만 예외를 두면 "해석하지 않는다"는 규칙이 한 곳에서 깨진다.

3번은 정확하지만, 6번에서 이미 감수하기로 한 500ms를 보호 경로에 한 번 더 얹는다. 7주차 성능 회귀를 아직 측정도 못 한 상태에서 같은 비용을 늘리는 선택이라 미뤘다.

1번의 대가는 **위조·만료 쿠키를 들고 오면 한 번 더 튕긴다**는 것이다. 화면 껍데기까지 들어오고, 그 화면의 데이터 요청이 401을 받고, 4번의 `_app` 핸들러가 로그인으로 보낸다. 사용자가 보는 결과는 같고 왕복만 한 번 늘어난다. 정상 흐름에는 없는 경로라 받아들였다.

`/cart`·`/wishlist`처럼 API를 부르지 않고 store만 읽는 화면에는 그 두 번째 방어가 걸리지 않는다. 대신 `ownerId`가 세션에서 오므로(8번) 위조 쿠키로 들어와도 목록이 비어 있다. 남의 목록이 보이지는 않는다.

## 11. 서버가 읽은 세션을 클라이언트에 어떻게 넘길 것인가

### 고민

6번에서 세션을 서버에서 읽기로 했는데, 클라이언트도 같은 값을 알아야 한다(7번 — 장바구니·위시리스트의 소유자). 그래서 `_app`의 `useSyncCollectionOwner`가 세션을 쿼리로 다시 읽고 있었고, 그 사이에 창이 하나 생겼다.

`useCurrentUserId()`가 로딩 중에도 `null`을 돌려준다.

```ts
export const useCurrentUserId = (): string | null => useSessionQuery().data?.id ?? null
```

**로딩과 미로그인이 같은 `null`로 표현된 것**이 원인이다. 이 값이 그대로 두 store의 소유자가 되므로, 로그인한 사용자가 화면을 열 때마다 이런 순서가 됐다.

1. 서버가 헤더를 로그인 상태로 그린다
2. 클라이언트가 세션을 **다시** 조회한다 (mock 기준 500ms)
3. 그동안 `ownerId === null` → 헤더 배지가 0으로 떴다가 점프하고, 장바구니 화면은 "비어 있습니다"가 잠깐 보인다
4. 그 창에서 담기를 누르면 `selectHasCartOwner`가 false라 **로그인한 사람이 `/login`으로 튕긴다**

화면당 `/api/auth/me`도 두 번(서버 한 번, 클라이언트 한 번) 나갔다.

### 검토한 선택지

1. **로딩 중에는 `setOwner`를 부르지 않는다** — 잘못된 초기화는 막지만 창 자체는 남는다. 소유자가 없는 동안 배지 0과 담기 차단은 그대로다.
2. **서버가 읽은 세션을 클라이언트 캐시의 초기값으로 넘긴다** — 로딩 상태 자체가 없어진다. 첫 렌더부터 확정된 값이다.
3. **헤더가 이미 받은 `user`로 클라이언트에서 캐시를 시딩한다** — 비용이 가장 싸지만, 위젯이 앱 전역 캐시를 쓰게 되어 층이 어긋난다.

### 결정

2번. `_app/providers/SessionHydration.tsx`(Server Component)가 서버에서 세션을 프리패치해 `HydrationBoundary`로 넘기고, `app/layout.tsx`가 `Providers`의 children 자리에 둔다. `QueryClientProvider` 안쪽이어야 해서 그 자리이고, `Providers`가 Client Component라 async Server Component를 children으로 합성해 넣는다.

미로그인이면 `null`이 캐시에 담긴다. 그것도 확정된 답이라 클라이언트가 다시 묻지 않는다.

### 확인

| 항목                  | 전                   | 후            |
| --------------------- | -------------------- | ------------- |
| 화면당 `/api/auth/me` | 2회                  | **1회**       |
| 첫 렌더의 `ownerId`   | `null` → 500ms 뒤 id | 처음부터 id   |
| `/` TTFB              | 548~560ms            | 548~556ms     |
| `/login` TTFB         | 32~38ms              | **549~553ms** |

다른 화면이 그대로인 것은 헤더가 이미 같은 주소를 부르고 있어 Next가 같은 render의 fetch를 합치기 때문이다. 헤더가 없는 `/login`만 새 비용이다.

### 라우트 그룹으로 `/login`을 빼지 않기로 한 것

`app/(session)/`을 만들어 `/login`만 밖에 두면 그 비용이 사라진다. 검토했고, **하지 않기로 했다.**

그 500ms는 mock이 일부러 넣은 지연이다.

```ts
// app/api/_data/auth.ts:167
export const waitForAuthApi = (requestedDelayMs = 500) =>
  new Promise<void>((resolve) => {
    setTimeout(resolve, process.env.NODE_ENV === 'test' ? 0 : requestedDelayMs)
  })
```

실제 인증 API가 30ms라면 `/login`은 33ms → 60ms대다. **강제 지연 하나를 피하려고 디렉터리 여덟 개를 영구히 옮기는 것은 비용이 맞지 않는다.**

경계도 애매하다. 인증 경계는 이미 `proxy.ts`의 `matcher`가 소유하므로(2번·10번) 그룹으로 또 나누면 보호 경로 목록이 두 벌이 된다. 그룹이 실제로 가르는 것은 "보호/비보호"가 아니라 "헤더가 있느냐"이고, 헤더가 없는 화면은 지금 `/login` 하나뿐이다. 화면 하나를 빼려고 나머지 여덟을 옮기는 모양이 된다.

**추후 문제가 생기면 그때 수정한다.** 다시 볼 조건은 두 가지다 — 헤더 없는 화면이 더 생겨(회원가입, 비밀번호 찾기) "세션이 필요 없는 화면들"이 복수가 되거나, 실제 인증 API의 지연이 로그인 화면에서 체감될 만큼 큰 경우다.

### 주문 내역에 상품 정보를 어떻게 붙일 것인가

`GET /api/orders`의 `items`에는 `{ productId, quantity }`만 있고 상품명과 이미지가 없다.
처음에는 주문 응답에 화면 정보도 함께 내려오는 것으로 이해했지만, 실제 계약을 확인한 뒤
**주문 API는 변경하지 않고 주문 내역 화면이 기존 상품 데이터와 결합**하기로 정했다.

상품 단건 조회 API가 없으므로 `/orders`에서 상품 목록 3페이지를 병렬로 조회하고,
`productId`와 상품의 `id`를 연결해 이미지·브랜드·상품명을 표시한다. 주문 entity와 상품 entity가
같은 레이어에서 서로 의존하지 않도록 조합은 상위 `_pages/orders`가 맡는다. 상품을 찾지 못하면
주문 자체를 숨기지 않고 `productId`를 대체 텍스트로 표시한다.

와이어프레임의 주문 내역 상품 행은 `IMG` 자리와 상품명 영역을 포함하는 것으로 확정한다.

- **가드와 복원 흐름을 `pnpm start`에서 확인했다.** 아래 "프로덕션 빌드 확인" 절에 결과를 적었다.
- **6번의 성능 회귀를 측정했다.** 결론은 "감수하기로 한 비용이 예상대로 왔고, 예상보다 넓게 왔다"이다. 아래 "7주차 지표 재측정" 절에 적었다.
- **헤더가 세션을 읽으면서 정적 라우트 넷이 동적이 됐다.** `Header`의 `cookies()`를 뺀 빌드와 비교해 측정했다.

  | 라우트                                    | 헤더가 세션을 읽기 전 | 지금      |
  | ----------------------------------------- | --------------------- | --------- |
  | `/cart` `/checkout` `/orders` `/wishlist` | ○ Static              | ƒ Dynamic |
  | `/products` `/` `/mypage`                 | ƒ Dynamic             | ƒ Dynamic |

  걱정했던 `/products`는 원래부터 동적이었다 — `generateMetadata`가 `searchParams`를 받기 때문이고, 헤더와 무관하다. 실제로 바뀐 넷은 전부 보호 경로라 어차피 가드를 지나야 하고, 정적으로 미리 만들어 둘 수 있는 화면이 아니었다.

  이후 `/wishlist`는 유입 경로(`entryPoint`)를 `searchParams`로 받게 되면서 헤더와 무관하게도 동적이 됐다. 헤더를 뺀 A/B 빌드에서 `/cart` `/checkout` `/orders`는 ○로 돌아왔지만 `/wishlist`는 ƒ 그대로였다.

- **`/mypage`는 세션을 두 번 읽는다.** `Header`와 `MyProfile`이 각각 `getSession`을 부른다. Next의 요청 memoization이 같은 렌더 안에서 합쳐 줄 것으로 보지만 확인하지 않았다.
- **담기 버튼에 화면 반응이 없다.** 미로그인일 때 로그인으로 보내는 것은 붙었지만(3번), 로그인한 뒤 담았을 때는 여전히 헤더 숫자만 오르고 버튼 쪽에는 변화가 없다. `aria-pressed`가 빠진 자리를 대신할 것이 없다. 담은 뒤 장바구니로 갈지 묻는 확인 창을 붙이기로 했고, 전체 비우기의 확인 창과 같은 부품을 `shared/ui`에 두고 공유한다.
- **`to-login-path.ts`에 테스트가 없다.** 짝이 되는 `to-safe-return-path.ts`에는 있다. 만드는 쪽과 받는 쪽이 같은 파라미터 이름을 쓰는지는 지금 상수 공유로만 보장된다.

## 7주차 지표 재측정

명세 118줄이 요구하는 확인이다. 7주차에 고친 것은 "`h1`이 홈 데이터를 기다리느라 566.0ms에야 등장한다"였고, 고친 뒤에는 `h1`이 전체 46,450 byte 중 1,863 byte 지점, 즉 첫 flush에 들어갔다.

`pnpm build && PORT=3100 pnpm start`에서 홈 문서를 스트리밍으로 받아, `<h1`이 담긴 청크가 도착한 시각을 쟀다. `Header`의 세션 읽기를 뺀 빌드와 5회씩 비교했다.

| 항목      | 세션 읽기 뺀 빌드 | 지금            |
| --------- | ----------------- | --------------- |
| TTFB      | 38.1 ~ 42.0ms     | 546.6 ~ 560.5ms |
| `h1` 도착 | 39.5 ~ 43.5ms     | 550.0 ~ 563.7ms |
| 문서 완료 | 555.2 ~ 559.0ms   | 554.5 ~ 568.1ms |
| `h1` 위치 | 2,244 byte        | 3,169 byte      |

**7주차에 고친 것이 되돌아갔다.** `h1` 등장이 약 42ms에서 약 558ms로 밀렸고, 이는 7주차 Before의 566.0ms와 사실상 같은 자리다. 늦어진 폭 약 516ms는 `/api/auth/me`의 500ms 지연과 일치한다.

`Header.tsx`의 주석은 "async 경계를 이 컴포넌트로 좁혀 페이지가 async가 되지 않으므로 `h1`까지 세션을 기다리지는 않는다"고 적고 있었는데, **측정 결과는 그렇지 않다.** `h1`은 문서에서 `Header`보다 뒤에 있고, Suspense 경계가 없으면 스트리밍은 순서대로 나가므로 첫 flush 자체가 세션을 기다린다. 좁힌 것은 페이지 컴포넌트의 시그니처였을 뿐 flush 시점이 아니었다.

문서 완료 시각이 양쪽 다 약 557ms인 것도 함께 읽어야 한다. 홈 데이터(500ms)가 어차피 그 시각에 끝나므로 **전체 완료는 그대로이고, 잃은 것은 셸을 먼저 내보내는 것**이다. 7주차에 산 것이 정확히 그 셸이었다.

### 되돌리는 방법을 두 가지 재봤다

처음에는 "`h1`을 `Header`보다 앞에 두면 된다"고 적었다. **재보니 틀렸다.**

| 홈 구조                       | `h1` 도착         | `h1` 위치  |
| ----------------------------- | ----------------- | ---------- |
| 지금 (`Header` → `h1`)        | 550.0 ~ 563.7ms   | 3,169 byte |
| `h1` → `Header`로 순서만 바꿈 | 559.9 ~ 569.7ms   | 2,721 byte |
| `Header`를 `Suspense`로 감쌈  | **41.0 ~ 44.8ms** | 1,844 byte |

순서를 바꿔도 그대로다. 문서에서 앞으로 가고 byte 위치도 앞당겨졌는데 **도착 시각은 변하지 않는다.** React의 스트리밍은 Suspense 밖의 셸을 통째로 하나로 다루기 때문이다. 셸 안에 await 하는 컴포넌트가 하나라도 있으면 셸 전체가 그것을 기다렸다가 한 번에 나가고, 그 안에서의 순서는 첫 flush 시각에 영향을 주지 않는다.

7주차에 `h1`을 `HeroSection` 밖으로 꺼낸 것이 통했던 이유도 같은 원리다. 순서를 바꿔서가 아니라 **`h1`을 Suspense 경계 밖으로 꺼냈기** 때문이었다.

그래서 실질적인 선택지는 하나다 — `Header`를 `Suspense`로 감싼다. 그러면 `h1`이 41ms로 돌아온다. 대신 헤더가 스트리밍으로 나중에 붙고, React의 Suspense 공개는 인라인 스크립트가 하므로 **JS가 꺼진 브라우저에서는 fallback이 그대로 남는다.** 명세가 요구한 "JavaScript 실행 전에도 로그인 여부가 보여야 한다"가 정확히 그 자리에서 깨진다.

즉 이 둘은 맞바꿀 수 있는 관계가 아니라 **명세의 두 요구가 서로 부딪히는 자리**다. 어느 쪽을 지킬지는 아직 정하지 않았다.
