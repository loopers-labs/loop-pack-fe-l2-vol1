# 9주차 — 인증과 근거 기반 E2E 범위

## 요약

서버가 httpOnly 세션 쿠키를 읽어 초기 HTML부터 인증 상태를 반영하도록 구현하고, 정제한 30일 이벤트 로그를 근거로 인증 필수 흐름과 주문 완료만 신규 E2E 대상으로 선택했습니다. 기존 8주차 상품 탐색 E2E는 중복 작성하지 않고 같은 production 실행에 포함했습니다.

## 주요 결과

| 검증 | 결과 |
| --- | ---: |
| Vitest 단위·통합 테스트 | 249/249 통과 |
| production Playwright, workers 1 | 16/16 통과 |
| production Playwright, workers 4 | 16/16 통과 |
| production Playwright, workers 4·3회 반복 | 40/40 통과 |
| 인증 변이 | 3개 모두 예상 RED, 원복 후 GREEN |
| 브라우저 적용 단계 Domain 변이 | 현재 빠른 테스트 11/11 통과, E2E 실패 |

최종 원본 상태에서 기록된 Node 22.23.2 검증에 더해, Node 24.17.0에서도 `pnpm check`와 `pnpm format:check`를 다시 통과했습니다. 반복 실행의 40건은 setup 4건을 한 번 실행하고 나머지 12건을 세 번 실행한 결과입니다.

## 결정

### 인증 경계

- 보호 경로는 주문서 `/checkout`과 주문 내역 `/orders`로 한정했습니다. 서버 `proxy.ts`가 미로그인 요청을 로그인으로 보내고 query를 포함한 내부 원래 경로를 `returnTo`로 보존합니다.
- 복원 경로는 `getSafeReturnPath()`가 `/`로 시작하는 동일 origin 내부 경로만 허용합니다. 절대 URL과 `//` 경로는 `/`로 바꿔 외부 이동을 막습니다.
- 화면 사용 중 발생한 보호 API의 401은 `requestProtectedJson()`에서 한 번만 처리합니다. 초기 문서 요청의 유효하지 않은 세션은 서버 페이지가 별도로 로그인 화면으로 보내며, 화면 컴포넌트마다 401 처리를 반복하지 않습니다.
- 로그아웃하면 사용자 식별, 진행 중 주문, 개인 주문 query와 위시리스트를 정리합니다. 장바구니는 로그인 전에도 소유할 수 있는 구매 준비 상태이므로 유지합니다.
- 인증된 홈의 서버 응답 HTML 원문을 직접 검사했을 때 `루퍼1`과 `로그아웃`이 포함되고 로그인 링크는 없었습니다. 이는 클라이언트 JavaScript 실행 전의 서버 인증 반영 증거입니다.

### 로그 정제와 E2E 범위

- 원본 22,427개 이벤트에서 정확 중복 77개를 제거했습니다.
- device가 없고, 세션당 이벤트가 하나이며, 기본 상품 목록 진입이고, 초 단위가 `.000Z`이며, 매일 01:00~01:14 UTC에 집중된 조건을 모두 만족하는 486세션만 자동화 의심 군집으로 제외했습니다.
- 정제 후 21,864개 이벤트·7,514세션이 남았습니다. 제거된 군집이 모두 상품 탐색에 속했지만 상품 탐색과 2위의 차이가 커 경로 순위는 바뀌지 않았습니다.
- 인증은 빈도보다 실패 영향과 브라우저 고유 경계가 커 필수 E2E로 선택했습니다.
- 주문 완료는 419개 시작 세션 중 142개에서 완료 이벤트가 관찰되지 않아 선택했습니다. 이를 실제 실패율이나 원인으로 단정하지 않고, 구매 전환이 끊겼을 때의 비용과 장바구니 메모리 상태, 인증 쿠키, 주문 POST와 주문 목록 GET을 잇는 경계의 복잡도를 함께 판단했습니다.
- 상품 탐색은 7,514세션으로 가장 빈번하지만 기존 8주차 E2E 5개가 URL·history·reload 경계를 이미 검증하므로 재사용했습니다.
- 위시리스트는 480세션으로 주문보다 많지만 독립 화면과 후속 여정이 없고 빠른 store·통합 테스트가 현재 경계를 검증하므로 신규 E2E를 추가하지 않았습니다.

### 이벤트 계측 경계

- 이벤트 이름은 대상과 행동을 함께 나타내고, `sessionId`, `device`, `ts`를 공통 속성으로 적용했습니다. 시드 로그와 현재 앱의 이벤트를 같은 사용자 경로로 비교하기 위한 결정입니다.
- 목록 진입, 장바구니 추가, 로그인 시작·성공·실패와 주문 시작·완료 이벤트를 실제 화면 행동 지점에 연결했고, 로그아웃 성공에는 `reset()`을 연결했습니다. 현재 앱에 없는 상세 화면 이벤트는 이름을 맞추기 위해 새 화면을 만들지 않았습니다.
- 로그인 성공에서 `identify()`, 로그아웃에서 `reset()`을 호출해 익명 세션과 회원 행동의 경계를 맞췄습니다. 초기화는 최상위 provider 경계에서 수행하고 멱등하게 처리해 화면 전환마다 중복 전송되지 않게 했습니다.
- 화면 컴포넌트는 typed event facade만 호출하고 provider 구현을 직접 알지 않습니다. 계측 실패가 사용자 행동을 깨뜨리지 않도록 분석 도구와 화면 로직을 분리했습니다.

### 격리와 진단

- 로그인 자체와 잘못된 자격 증명은 저장 상태 없이 검증합니다. 만료와 주문만 실제 UI 로그인으로 생성한 `storageState`를 재사용합니다.
- setup은 계정 `u1`~`u4`의 상태 파일을 만들고, 실행 테스트는 `parallelIndex`가 가리키는 계정과 파일만 사용합니다. 각 테스트의 browser context는 종료 시 닫습니다.
- locator는 role·label·접근 가능한 이름을 사용했고 `getByTestId`, CSS selector와 시간 기반 sleep은 사용하지 않았습니다.
- 잘못된 로그인 오류 문구를 의도적으로 틀리게 바꿔 trace를 생성하고 실제 Trace Viewer를 열었습니다. 최종 URL, 입력값, 실제 alert와 5초 assertion timeout을 확인한 뒤 단언을 원복해 5/5 통과를 확인했습니다.

## 변이 실험

| 변경 | 결과 | 판별 근거 |
| --- | --- | --- |
| 세션 쿠키 `Path`를 `/api/auth`로 축소 | E2E RED, 기존 route assertion도 같은 속성 계약을 보장 | 보호 문서 요청에 쿠키가 전달되지 않아 주문서가 나타나지 않음. E2E 고유 검출 사례로 계산하지 않음 |
| 체크아웃 `returnTo`를 `/`로 변경 | E2E RED, 빠른 라우트 테스트도 분기 자체를 보장 | 기대한 query 포함 경로와 실제 `/`가 URL 실패 메시지에 표시됨. E2E는 서버 redirect와 브라우저 주소의 연결을 보완 |
| 중앙 만료 조건을 401에서 403으로 변경 | E2E RED, `protectedHttpClient` 테스트도 401 계약을 보장 | 401 응답 대기는 통과했지만 URL이 `/orders`에 머물러 실제 탐색 연결의 단절을 확인 |
| 세션 쿠키에 `Domain=example.com` 추가 | 빠른 테스트 11/11 GREEN, E2E RED | 해당 옵션에서 보호 요청의 서버 인증 상태가 형성되지 않음. heading 실패만으로 옵션 원인까지 특정할 수 없어 cookie 상태와 응답 옵션을 함께 확인함 |

모든 production 변이는 한 곳씩만 변경했고 테스트 코드는 바꾸지 않았습니다. 각 RED를 확인한 직후 원복했으며 최종 production 코드에는 변이가 남아 있지 않습니다. 앞의 세 변이는 빠른 테스트도 계약 일부를 보장하므로 E2E만 잡은 사례라고 주장하지 않습니다. 마지막 Domain 실험은 현재 빠른 route 테스트가 해당 속성을 단언하지 않아 통과했지만, 실제 브라우저의 쿠키 적용 단계에서 E2E가 실패를 검출했습니다. Domain 설정값 자체는 빠른 테스트로도 추가 검증할 수 있으며, 이 실험에서 확인한 E2E의 역할은 쿠키 저장·전송과 서버 인증 화면까지의 실제 연결입니다.

## 검증

- `pnpm check`: Vitest 249/249, ESLint, TypeScript, production build, Playwright 16/16 통과
- `pnpm format:check`: 통과
- workers 1·4 및 3회 반복: 모두 retry 없이 통과
- 비활성화 테스트, 고정 sleep, API 직접 로그인으로 위조한 인증 테스트 없음
- 상세 계산, 선택·제외 근거와 trace·변이 원문은 [Week 9 E2E 범위 RFC](../rfc/week09-e2e-scope.md)에 기록

## AI 사용

AI는 요구사항 구조화, 구현 후보 생성, 테스트 초안, 정상·적대적 리뷰와 반복 검증에 사용했습니다. 어떤 사용자 경로를 단언할지와 어떤 경로에 E2E를 붙이거나 제외할지는 로그와 현재 화면 경계를 검토한 뒤 직접 승인·확정했습니다. AI가 제안한 내용을 그대로 통과로 처리하지 않고 실제 production 실행, 의도적 변이와 원복 후 검증 결과를 기준으로 판단했습니다.

## 알려진 범위

- 이번 제출은 Basic 범위입니다. 시각적 회귀는 Advanced 선택 과제이므로 포함하지 않았습니다.
- `httpOnly`와 `SameSite` 문자열 계약 및 쿠키 발급 설정은 route 테스트가 검증합니다. E2E는 UI 로그인 뒤 브라우저에 형성된 세션이 보호 요청과 서버 렌더링까지 이어지는 결과를 검증합니다.
- 루트 레이아웃의 서버 `Header`가 `cookies()`를 읽으므로 빌드 결과에서 모든 앱 경로가 동적 렌더링으로 표시됩니다. 초기 HTML에 인증 상태를 일관되게 반영하기 위해 선택한 비용이며, 7주차 성능이 유지됐다고 이번 결과만으로 주장하지 않습니다.
- 원격 브랜치를 push한 뒤 PR 화면에서 [Week 9 E2E 범위 RFC](../rfc/week09-e2e-scope.md) 링크가 열리는지 확인합니다.
