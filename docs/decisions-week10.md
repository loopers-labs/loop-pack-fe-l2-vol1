# 10주차 판단 근거

## 판단 기준

검증 위치는 결함을 재현하는 데 필요한 환경으로 나눈다.

| 컷       | 판정 기준                                                     |
| -------- | ------------------------------------------------------------- |
| CI CUT   | 코드·테스트·빌드만으로 참과 거짓을 판정할 수 있음             |
| CD CUT   | 배포 URL·배포 환경 변수·브라우저 환경이 있어야 재현할 수 있음 |
| LIVE CUT | 실제 사용자 장치·네트워크·상호작용 데이터가 있어야 드러남     |

컷은 검증이 끝나는 환경을 정하고, required는 실패했을 때 병합을 멈출 대상을 정한다. 두 축은 별도로 기록한다.

## 결정 1 — 병목과 직접 연결된 최적화만 적용

기존 `quality` workflow는 E2E를 실행하지 않으면서 Playwright Chromium을 매번 설치했다. CI 로그에서 해당 설치 단계가 24~30초로 가장 길게 측정됐다.

Chromium 설치를 `quality`에서 제거하고 E2E workflow로 이동한다. 검증 항목을 삭제하거나 순서를 바꾸지 않는다. `quality`의 동시 실행은 `${{ github.workflow }}-${{ github.ref }}` 그룹으로 묶고, pull request 실행만 취소한다.

Before/After의 cold·warm 측정은 같은 검증 집합으로 유지한다. Chromium 설치 제거는 측정된 병목과 직접 연결되지만, concurrency는 중복 실행을 줄이는 운영 정책이므로 단일 실행 시간 개선으로 해석하지 않는다. job을 검증별로 나누는 방식은 설치 중복과 러너 사용량 증가 가능성이 있어 이번 병목 최적화에서는 채택하지 않는다.

## 결정 2 — 캐시 효과는 로그로 확인하고 추정하지 않음

warm 실행에서 캐시 복원 메시지를 확인하고, lockfile 해시를 바꾸는 별도 실험으로 miss와 install 재실행을 확인한다. 실험은 PR 브랜치 캐시만 대상으로 하며 `main` 캐시는 측정 대상에 포함하지 않는다. 실험 후 lockfile과 캐시 관련 변경은 원상 복구한다.

캐시 hit과 miss의 install 시간 차이는 기록하지만, 의존성 변경으로 인한 작업량 차이와 캐시 효과를 같은 원인으로 묶지 않는다.

## 결정 3 — E2E는 CI CUT에서 조건부 실행

현재 Playwright는 `next build && next start`로 로컬 production 서버를 띄운다. 따라서 배포 URL이 필요한 검증이 아니라 CI CUT에 속한다.

E2E는 모든 PR에서 실행하지 않고, 문서만 변경된 경우 생략한다. 경로 필터는 생략 가능한 경로만 허용 목록에 두며, 분류되지 않은 변경은 실행 대상으로 처리한다.

`changes`가 경로를 판정하고 `e2e`가 실제 테스트를 실행한다. `e2e-required`는 항상 선행 결과를 판정한다.

| 조건                                              | guard 결과 |
| ------------------------------------------------- | ---------- |
| 의도한 문서 변경만 있고 E2E가 skipped             | 성공       |
| 실행 대상이고 E2E가 success                       | 성공       |
| 경로 판정 실패·출력 누락·E2E 실패·예상 밖 skipped | 실패       |

`e2e` 자체를 required로 두지 않고 guard를 required 후보로 둔 이유는 조건부 job이 skipped일 때 required check가 대기 상태에 머무를 수 있기 때문이다.

## 결정 4 — 번들 예산은 진입점별 전송량을 기준으로 함

7주차의 hero 값은 이미지 전송량이므로 JS·CSS 번들 예산에 합치지 않는다. 7주차의 JS 청크 값은 과거 기준선으로 사용하고, 현재 빌드에서는 `/`와 `/products`가 실제로 참조하는 JS·CSS 자산을 gzip 전송량으로 다시 측정한다.

7주차와 현재값은 압축 방식은 같지만 자산 집합이 다르므로 동일 수치의 재현으로 해석하지 않는다. 현재 최대 진입점의 JS+CSS 합계를 기준으로 예산을 정하고, 10% 여유폭은 측정 변동폭이 아니라 소규모 의존성 증가를 허용하기 위한 정책값으로 기록한다.

진입점별 자산 합계를 정확히 계산하는 Node 스크립트를 주 게이트로 사용한다. 도구가 동일한 합산을 표현하지 못하면 서로 다른 기준의 보조 게이트를 required로 추가하지 않는다.

## 결정 5 — 환경 변수는 CI와 CD에서 나누어 검증

CI에서는 URL 형식, 필수 값 존재 여부, 서버 전용 비밀값의 `NEXT_PUBLIC_` 접두사 오용을 검사한다. CI에는 실제 비밀값을 넣지 않고 로그에 남아도 되는 검증용 값을 사용한다.

CD에서는 Preview·Production에 실제 값이 주입됐는지, `APP_ORIGIN`이 배포 URL과 일치하는지, `AUTH_SESSION_SECRET`과 localhost fallback이 사용되지 않는지를 확인한다. 배포 환경이 없으면 CD 검증을 완료한 것으로 기록하지 않는다.

## 결정 6 — Lighthouse와 Web Vitals는 CI required로 올리지 않음

Lighthouse 실험실 점수는 실행 장치·네트워크·캐시 상태에 따라 달라지며 Preview의 단발성 결과가 실제 사용자 성능을 대표하지 않는다. 따라서 Lighthouse assertion은 CI/CD 차단 기준으로 사용하지 않는다.

실제 사용자 장치·네트워크·상호작용 데이터가 필요한 LCP·CLS·INP 판정은 LIVE CUT에 둔다. RUM 수집 경로가 없으면 미측정 상태와 후속 수집 계획을 기록한다.

## 결정 7 — AI 리뷰는 advisory로 유지

AI 리뷰 프롬프트에는 10주간 합의한 컴포넌트 책임 분리, hook 분리, URL 상태, 서버 응답 상태 복사, FSD 경계를 포함한다. lint 대상과 YAML·문서의 적용 범위를 구분하고, 프로젝트 규칙에 없는 단순 네이밍 선호는 지적하지 않도록 제한한다.

AI 리뷰 결과는 유효한 지적과 오탐을 분리해 기록한다. 실행 결과가 프롬프트와 맥락에 민감하므로 required 게이트로 사용하지 않고 로컬 advisory 기록으로 남긴다.

## 결정 8 — 반복 지적 하나를 결정적 CI 룰로 승격

FSD import 경계는 이미 `eslint-plugin-boundaries`의 error 규칙으로 적용되어 있으므로 중복 승격하지 않는다.

대신 추적되는 `docs/rfc/**/*.md`에서 `docs/local/**`을 실제 Markdown·HTML 링크 대상으로 참조하는 경우를 CI에서 실패시킨다. 문자열의 단순 등장 자체를 금지하지 않고, 코드블록·인라인 코드 속 설명은 허용한다. 규칙의 목적이 경로명 설명 금지가 아니라 실행 가능한 문서 참조 차단이기 때문이다.

## 결정 9 — required 상태는 실제 설정과 후보를 분리

`main`과 `feat/week-10`에는 영구 branch protection을 설정하지 않는다. 따라서 현재 영구 required check는 없다.

`quality`와 `e2e-required`를 required 후보로 정하고, 임시 보호 브랜치에서 성공·의도한 skip·실패·머지 차단을 확인한 결과만 근거로 남긴다. 이렇게 하면 `main`에 영향을 주지 않고 required 동작을 검증할 수 있다.

## 결정 10 — 배포하지 못한 항목은 미확인으로 기록

Preview·Production 환경이 없으면 4주차 Preview 동작, 9주차 배포 환경 쿠키·환경 변수, 배포 후 smoke test를 확인하지 못한 상태로 남긴다. 로컬 production build에서 재현되는 4주차·9주차 검증은 CI CUT으로 기록한다.

## 책임 경계

코드만으로 판정할 수 있는 lint·typecheck·test·build·번들·환경 변수 형식·RFC 링크는 CI가 담당한다. 배포 값 주입과 URL smoke test는 CD가 담당하고, 실사용 Web Vitals는 LIVE 수집 대상이다. 설계 의도, 예산·required 배치, AI 지적의 맥락 판단은 사람과 AI 리뷰에 남긴다.

## 검토와 변경 원칙

각 단계는 구현, 성공·실패·경계 검증, 문서 대조, 사람 리뷰 순서로 진행한다. 리뷰가 끝나기 전에는 커밋하지 않는다. 실험 PR은 병합하지 않고 결과 링크와 로그만 증거로 보존한다.

# 실행하며 추가·보정된 판단

위 항목은 실행 전에 세운 기준이다. 아래는 구현·검증 과정에서 새로 정하거나 사실에 맞춰 고친 것이다. 보완 대상 결정 번호를 함께 적는다.

## 11 — 전송량은 브라우저가 받는 양으로 잰다 (결정 4 보완)

`fetch`는 `content-encoding`을 자동으로 해제해 압축 전 크기를 돌려주므로 예산 측정에 쓸 수 없다. `node:http`로 응답 본문의 byte를 그대로 세는 방식으로 바꿨다.

측정 중 작은 자산 세 개가 `content-encoding` 없이 내려오는 것을 확인했다(`.css` 991 B, `.js` 399 B ×2). 서버가 작은 파일을 압축하지 않기 때문이다. 이때 오류로 처리하지 않고 받은 byte를 그대로 더한다. 예산의 기준이 "압축률"이 아니라 "브라우저가 실제로 내려받는 양"이기 때문이다. 파일별 인코딩은 기록해 둔다.

`size-limit`을 쓰지 않기로 한 구체적 근거도 여기서 확정됐다. Turbopack 빌드에는 `app-build-manifest.json`이 없고 `build-manifest.json`만으로는 어느 청크가 어느 진입점에 실리는지 나오지 않아, glob 합산으로는 진입점 단위 예산을 표현할 수 없다.

## 12 — 게이트의 실행 순서는 비용과 의존으로 정한다

같은 job 안에서도 앞뒤가 판정 결과를 바꾼다.

| 순서 | 검증                            | 근거                                                           |
| ---- | ------------------------------- | -------------------------------------------------------------- |
| 1    | RFC 링크 검사                   | 정적 텍스트 검사, 1초 미만, 다른 검증에 기대지 않음            |
| 2    | 환경 변수 형식                  | 설정 오류는 코드 검증을 통과한 뒤에 드러나므로 build 전에 막음 |
| 3    | test → lint → typecheck → build | 기존 순서 유지                                                 |
| 4    | 번들 예산                       | build 산출물을 그대로 사용, 재빌드하지 않음                    |

앞에 둔 검증이 실패하면 뒤 검증은 실행되지 않는다. 그래서 앞선 실패를 고친 뒤에는 한 번 더 돌려야 전체 결과를 볼 수 있다. 이 대가를 감수하는 이유는 실패 회차의 러너 시간을 줄이는 편이 이득이기 때문이다.

## 13 — AI 리뷰 프롬프트의 개정 원칙 (결정 7 보완)

오탐 세 건이 모두 "규칙을 아느냐"가 아니라 "규칙이 어디에 적용되느냐"에서 났다. 그래서 프롬프트에 네 가지 제한을 넣었다.

1. 규칙마다 **적용 범위**를 파일 패턴으로 적는다. 적용 대상이 아닌 것도 함께 적는다.
2. diff에 근거가 없는 것과 근거가 없는 것을 구분한다. 근거가 diff 밖에 있을 수 있으면 `확인 필요`로 분류한다.
3. 목록에 없는 규칙을 새로 만들어 적용하지 않는다. 팀 컨벤션이나 실제 오류와 연결되지 않는 네이밍 선호는 지적하지 않는다.
4. required 배치는 일반론이 아니라 이 프로젝트의 결정을 기준으로 판단한다.

개정마다 교환이 있었다. 적용 범위를 좁히면 오탐은 줄지만, 넓게 남겨 둔 자리에서 가치가 낮은 지적이 늘었다. 규칙마다 범위를 적는 비용을 치러야 신호가 남는다.

## 14 — advisory 근거는 재현성이 아니라 기준 민감도 (결정 7 보정)

처음에는 "실행마다 결과가 달라서" advisory로 둔다고 적었다. 같은 diff에 v4 프롬프트를 3회 돌려 확인한 결과 지적 집합이 같았으므로, 그 근거는 성립하지 않아 취소했다.

대신 두 가지를 근거로 삼는다. 첫째, 프롬프트 한 줄을 바꿀 때마다 지적 집합이 통째로 바뀌었다. required로 두면 기준 문서를 고치는 순간 통과·실패가 바뀐다. 둘째, 오탐을 반증하는 데 쓴 근거(lint 대상 범위, 규칙의 목적 주석, 실행 시간 자료)가 모두 diff 밖에 있었다. 리뷰어가 볼 수 없는 자리다.

재현성 확인은 v4에만 해당한다. v1~v3은 반복 실행하지 않았다.

## 15 — 링크 규칙의 검사 범위와 한계 (결정 8 보완)

검사 대상은 Git이 추적하는 `docs/rfc` 아래 Markdown이다. 코드블록과 인라인 코드 구간을 같은 길이의 공백으로 바꾼 뒤, 남은 본문에서 링크 목적지 네 종류(인라인 링크·이미지, 참조 정의, 자동 링크, HTML `href`/`src`)와 본문에 적힌 맨 경로를 찾는다.

잡지 못하는 것을 함께 적어 둔다. 코드로 표시된 문자열, `docs/rfc` 밖 문서, 추적되지 않는 파일은 의도한 예외다. 다른 무시 대상 경로와 깨진 링크 전반은 이 규칙의 범위가 아니다. 링크 목적지를 여러 줄에 걸쳐 쪼개면 검사를 피할 수 있지만, 그렇게 쓰면 렌더링에서도 링크가 만들어지지 않아 규칙이 막으려던 결과와 같아진다.

리뷰 기준 파일을 `docs/rfc` 밖에 둔 것도 이 규칙 때문이다. 금지 경로를 규칙 문장에 그대로 적어야 하기 때문이다.

## 16 — required 영구 배치는 하지 못했다 (결정 9 보정)

임시 보호 브랜치에서 세 경로(실행·통과, 스킵, 실패)를 확인하고 설정을 지운 것까지는 계획대로다. 이후 fork `main`에 같은 설정을 영구 배치하려 했으나 API 호출이 권한 정책에 막혀 실행하지 못했다.

따라서 현재 상태는 "required 동작을 확인한 후보 두 개(`quality`, `e2e-required`)가 있고 영구 설정은 없음"이다. 문서에는 지정했을 때 막힌다는 사실과 지금은 지정돼 있지 않다는 사실을 나눠 적는다.

## 17 — 동시 실행 정책은 측정과 분리한다 (결정 1 보완)

`quality`의 `concurrency`는 중복 실행을 줄이는 운영 정책이므로 Before/After 수치에 반영하지 않는다.

확인한 것과 확인하지 못한 것을 나눈다. 같은 PR에 연속 push했을 때 이전 실행이 취소되고 이후 실행이 통과하는 것은 실행으로 확인했다. `main` push 실행이 취소 대상이 아닌 것은 `main`에 push하지 않아 재현하지 못했으며, 근거는 `cancel-in-progress` 식이 `push` 이벤트에서 거짓이 되고 그룹 키에 ref가 들어 있어 같은 그룹에 묶이지 않는다는 점뿐이다.

## 18 — 유효 지적의 영향도를 과장하지 않는다

스킵 목록에 남아 있던 경로는 무시 대상이라 일반 PR의 변경 목록에 나타나지 않는다. 따라서 실행 비용이나 검증 누락을 일으켰다고 단정하지 않는다.

정리한 이유는 두 가지다. 스킵 정책에 실제로 사용하는 경로만 남겨야 하고, 커밋 문서의 참조를 금지하는 규칙과 경계를 맞춰야 한다. 기록은 "정책 범위 밖 경로가 남아 설정이 넓어져 있었고, 즉시 검증 누락을 일으킨 사례는 확인되지 않았다"로 남긴다.

## 19 — 실험 흔적을 제출 상태에 남기지 않는다 (검토 원칙 보완)

실험 PR 14건을 모두 닫고 브랜치를 삭제했다. 이전 시도에서 닫히지 않은 채 남아 있던 두 건도 6단계 점검에서 찾아 정리했다. 그중 하나에는 고의로 깨뜨린 E2E 단언이 들어 있었다.

닫기 전에 PR 링크와 Actions run, 결과를 문서에 먼저 옮겼다. 정리로 증거가 사라지면 회고의 주장을 확인할 수 없기 때문이다. 문서가 참조하지 않던 실험도 결과를 남긴 뒤 닫았다.

## 20 — 문서와 실제 상태를 제출 전에 대조한다

회고를 쓴 뒤 인용한 값을 실제 상태와 한 번씩 맞춰 봤다. 커밋 SHA 29개의 존재, Actions run 9개의 결론, PR 14건의 상태와 병합 여부, 인용한 소스 파일의 줄 번호를 확인했다.

이 대조에서 두 가지가 걸렸다. 열려 있던 실험 PR 두 건과, `quality`에 없던 동시 실행 정책이다. 문서에 아직 적지 않은 상태에서 찾았으므로 잘못된 서술이 남지는 않았지만, 대조를 생략했다면 회고가 실제 상태와 어긋났을 것이다.
