# 14 — 주석·정책

## When to read

코드 주석, 문서화, AI 생성 부분 표기, 리뷰 설명을 작성할 때 읽는다.

## Source of truth

- 본 저장소의 문서화 원칙: `AGENTS.md`, `docs/rules/README.md`

## Rules

### 1. 본인이 설명할 수 없는 코드는 제출하지 않는다

- AI가 생성한 코드도 머지하는 순간 작성자의 코드다.
- 코드의 의도, 타입, 상태 전이, 에러 처리, 접근성 영향, 검증 결과를 설명할 수 있어야 한다.

| ✅ 올바른 예                                               | ❌ 잘못된 예                         |
| ---------------------------------------------------------- | ------------------------------------ |
| "이 hook은 URL 변경 시 draft를 재마운트 없이 동기화합니다" | "AI가 만들어서 잘 모르겠어요"        |
| PR 설명에 AI 생성/직접 수정 부분 명시                      | AI 생성 코드를 아무런 설명 없이 머지 |

### 2. AI가 추가한 것은 의도와 검증을 남긴다

- AI가 추가한 의존성, 유틸리티, 상태, effect는 왜 필요한지 검증한다.
- PR이나 리뷰 요청에는 AI가 생성한 부분과 직접 수정한 부분을 명시한다.
- 사용하지 않는 AI 제안은 과감히 버린다.

### 3. 주석은 "왜"를 설명한다

- 주석은 "무엇"이 아니라 "왜"를 설명한다.
- 코드 자체로 의도가 드러나면 주석을 달지 않는다.
- 복잡한 비즈니스 규칙, 의도치 않은 제약, 성능/보안상의 선택에 주석을 단다.

| ✅ 올바른 예                                                    | ❌ 잘못된 예            |
| --------------------------------------------------------------- | ----------------------- |
| `// gcTime이 짧으면 뒤로 가기 시 캐시가 날아가므로 기본값 유지` | `// loop through items` |
| `// 서버 동기화가 생기면 persist를 걷어내야 함`                 | `// set state`          |

### 4. TODO/FIXME는 이슈로 연결한다

- 임시 주석은 최소한으로 남기고, 해결해야 할 항목은 이슈 트래커로 연결한다.
- `TODO`는 본인이 해결할 수 있는 짧은 작업에만 사용한다.
- `FIXME`는 반드시 후속 조치가 있는 경우에만 사용한다.

```ts
// ✅ 올바른 예
// TODO: 로그인·서버 동기화 시 migrate 정책 결정 (#123)

// ❌ 잘못된 예
// FIXME: 이게 맞는지 모르겠음
```

## Verification

- AI 생성 부분의 의도와 검증 결과를 설명할 수 있는지 확인한다.
- 불필요하거나 중복된 주석이 없는지 확인한다.
- TODO/FIXME가 이슈로 연결되어 있는지 확인한다.

```bash
pnpm lint
pnpm typecheck
```
