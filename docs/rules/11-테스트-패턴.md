# 11 — 테스트 패턴

## When to read

단위 테스트, 통합 테스트, mock, 테스트 이름, 테스트 본문 구조, Vitest/MSW/Playwright 설정을 작성하거나 변경할 때 읽는다.

## Source of truth

- Vitest 프로젝트: `vitest.config.ts`
- 테스트 script: `package.json`
- MSW 수명 주기: `tests/setup/msw.ts`, `tests/setup/dom.ts`
- E2E: `playwright.config.ts`, `e2e/`
- CI 단계: `.github/workflows/*`

## Rules

### 1. 테스트는 동작에 대한 계약을 보호한다

- 테스트가 없는 버그 수정은 머지하지 않는다. 버그를 재현하는 테스트를 먼저 추가한다.
- 테스트는 구현细节이 아니라 의도(계약)를 검증한다. 내부 변수명이나 private 함수를 직접 단언하지 않는다.
- 순수 함수와 상태 전이는 단위 테스트로, DOM/라우터/네트워크 순서는 dev 서버나 E2E로 나눈다.

### 2. 테스트 이름: USE 패턴

모든 테스트 이름은 다음 세 요소를 담는다.

- **U**nit of work: 테스트 대상이 되는 메서드나 기능
- **S**cenario: 테스트가 진행되는 상황이나 조건
- **E**xpected behavior: 이 테스트를 통해 얻어야 하는 최종 결과

```ts
// ✅ 좋은 예
test('transferMoney: validAccount -> balancesUpdated', () => { ... });
test('addToCart: duplicateProduct -> count stays at one', () => { ... });
test('parseFilters: emptyQuery -> returns default values', () => { ... });

// ❌ 나쁜 예
// 대상이 없어서 실패 시 무엇을 고쳐야 할지 알 수 없다
test('it works', () => { ... });

// 시나리오와 기대 결과가 없어서 의도가 모호하다
test('transferMoney test', () => { ... });

// 기대 결과가 단언문 그대로라서 동작을 설명하지 못한다
test('addToCart: adds item', () => { ... });
```

### 3. 테스트 본문: AAA + 공백 분리

각 테스트 본문은 Arrange, Act, Assert 세 단계로 구성하고, 단계 사이에 한 줄의 공백을 둔다.

- **Arrange**: 입력, mock, 의존성을 준비한다.
- **Act**: 테스트의 핵심 목적을 단 한 줄로 표현한다.
- **Assert**: 하나의 테스트 메서드에는 하나의 핵심 개념만 검증한다. 부수적인 단언은 헬퍼나 추가 테스트로 분리한다.

```ts
// ✅ 좋은 예
it('cartStore.addToCart: newProduct -> item is added', () => {
  // Arrange
  const store = createCartStore()
  const productId = 'p-1'

  // Act
  store.getState().addToCart(productId)

  // Assert
  expect(store.getState().items).toHaveProperty(productId, true)
})

// ✅ 좋은 예: 한 테스트에 하나의 핵심 개념
it('productFilterParsers: emptyQuery -> returns default values', () => {
  // Arrange
  const emptySearchParams = new URLSearchParams()

  // Act
  const parsed = productFilterParsers.parseQuery(emptySearchParams)

  // Assert
  expect(parsed).toEqual({ q: '', category: 'all', sort: 'latest', page: 1 })
})

// ❌ 나쁜 예: 단계 사이 공백이 없어서 읽기 어렵다
it('addToCart adds item', () => {
  const store = createCartStore()
  const productId = 'p-1'
  store.getState().addToCart(productId)
  expect(store.getState().items).toHaveProperty(productId, true)
})

// ❌ 나쁜 예: Act가 여러 줄이라 핵심 목적이 흐려진다
it('addToCart: newProduct -> item is added', () => {
  const store = createCartStore()
  const productId = 'p-1'
  const before = Object.keys(store.getState().items).length
  store.getState().addToCart(productId)
  const after = Object.keys(store.getState().items).length
  expect(after).toBe(before + 1)
})

// ❌ 나쁜 예: 한 테스트에 여러 핵심 개념이 섞여 있다
it('productFilterParsers works', () => {
  const empty = productFilterParsers.parseQuery(new URLSearchParams())
  expect(empty.q).toBe('')
  expect(empty.category).toBe('all')
  expect(productFilterParsers.page.parse('0')).toBe(1)
  expect(productFilterParsers.page.parse('abc')).toBe(1)
})
```

### 4. 테스트 환경 분리

- `*.test.ts`와 `*.test.tsx`는 `node` 프로젝트에서 실행한다. `*.dom.test.tsx`는 제외하므로 기존 순수 로직 테스트에 jsdom 비용을 더하지 않는다.
- `*.dom.test.tsx`는 `dom` 프로젝트에서만 실행한다. 두 패턴은 겹치지 않는다.
- DOM 프로젝트의 jsdom URL은 `http://localhost:3000`이다.
- Node와 DOM 프로젝트는 MSW 수명 주기를 사용한다. DOM에서만 `@testing-library/jest-dom/vitest` matcher와 Testing Library `cleanup`을 연결한다.
- Vitest globals는 사용하지 않는다.

### 5. MSW는 실제 HTTP 경계를 검증한다

- suite 시작 전 빈 MSW `setupServer`를 `onUnhandledRequest: 'error'`로 시작한다.
- 처리되지 않은 요청은 실패한다.
- handler는 각 테스트가 `server.use`로 등록한다. 전역 기본 handler를 두지 않는다.
- 매 테스트 뒤 `resetHandlers`, suite 종료 뒤 `close`를 실행한다.
- 기존 HTTP 경계 테스트는 transport를 직접 교체하지 않고 실제 요청을 MSW가 가로채는 방식으로 검증한다.
- 실제 HTTP 경계를 통과하지 않고 테스트 대역의 임의 동작만 검증하지 않는다. native fetch의 성공, malformed JSON, schema 오류, HTTP 오류, network `TypeError` 변환과 요청 횟수처럼 공개 계약을 검증한다.

| ✅ 올바른 예                                               | ❌ 잘못된 예                            |
| ---------------------------------------------------------- | --------------------------------------- |
| `ProductRepository` 테스트에서 MSW가 실제 ky 요청을 가로챔 | fetch/ky method를 mock transport로 교체 |
| `server.use(handler)` 후 요청, 테스트 뒤 `resetHandlers`   | 전역 handler를 두고 각 테스트가 덮어씀  |

### 6. Playwright E2E는 사용자 흐름을 검증한다

- `pnpm test:e2e`는 `pnpm build && playwright test`다.
- Playwright는 `e2e/`에서 테스트를 찾고 Chromium만 사용한다.
- `webServer`는 `pnpm start`로 production artifact를 제공하고 `http://localhost:3000` 응답 준비를 기다린다.
- 사용자 흐름은 role/name 같은 공개 접근성 계약으로 검증한다.
- E2E는 의도적으로 `pnpm test`와 `pnpm check`에 포함하지 않는다.
- GitHub Actions는 조건부 Chromium 설치와 `pnpm check`를 유지하고, 그 뒤 별도 `pnpm test:e2e` 단계로 실행한다.

### 7. 테스트 경계

- 단위 테스트는 순수 로직과 타입 계약만 검증한다.
- DOM, React 렌더링, 실제 URL hydration, 페이지 전환 중 상태 유지는 dev 서버를 띄운 뒤 수동으로 확인한다.
- 테스트가 DOM/Next.js 라우터 없이 빠르게 돌도록 경계를 둔다.
- hook이 아닌 순수 객체/함수는 DOM 없이 직접 테스트한다. 필요하다면 훅이 아닌 parser 객체 등을 export해 테스트한다.
- 테스트 파일명과 위치는 Vitest 설정을 따른다.

### 8. 검증 명령

```bash
pnpm test          # vitest run
pnpm test:watch    # watch mode
pnpm test:e2e      # build + playwright
pnpm check         # test + lint + typecheck + build
```

## Verification

- 테스트 이름에 Unit of work, Scenario, Expected behavior가 모두 드러나는지 확인한다.
- Arrange/Act/Assert 단계가 공백으로 분리되고 Act는 한 줄인지 확인한다.
- 한 테스트에 하나의 핵심 개념만 있는지 확인한다.
- handler가 해당 테스트 안에서만 등록되고 테스트 뒤 초기화되는지 확인한다.
- 처리되지 않은 요청이 실패하는지 확인한다.
- HTTP 경계 테스트에서 fetch, ky, API client를 mock transport로 교체하지 않았는지 확인한다.
- 테스트가 실제로 통과하는지 확인한다.
- 수동 검증 항목은 기록으로 남긴다.

```bash
pnpm test
pnpm test:e2e
pnpm check
```
