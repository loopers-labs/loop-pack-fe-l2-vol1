# 13 — 피처·구조 패턴

## When to read

새 기능 폴더를 만들거나, slice/entity/feature 구조를 설계하거나, co-locate/폴더 승격/import 경계를 정할 때 읽는다.

## Source of truth

- FSD 레이어: [`02-디렉토리-구조.md`](02-디렉토리-구조.md)
- Public API, co-location, 직접 import: 본 문서 Rules
- 도메인/API 경계: [`05-API-패턴.md`](05-API-패턴.md)

## Rules

### 1. 기능은 FSD 레이어에 맞춰 배치한다

- 기능은 FSD 레이어(app → views → widgets → features → entities → shared)에 맞춰 배치한다.
- slice 내부에서도 api, model, ui, lib 등 책임별 폴더로 나누되, 작은 기능은 과도하게 나누지 않는다.

| 레이어     | 들어가는 것                       | 예시                          |
| ---------- | --------------------------------- | ----------------------------- |
| `app`      | 라우트, 레이아웃, 글로벌 provider | `page.tsx`, `layout.tsx`      |
| `views`    | 페이지 조합                       | `HomePage`, `ProductListPage` |
| `widgets`  | 페이지 섹션 조합                  | `Header`, `ProductList`       |
| `features` | 사용자 흐름                       | `addToCart`, `filterProducts` |
| `entities` | 도메인 모델                       | `product`, `cart`, `wishlist` |
| `shared`   | 재사용 UI/유틸                    | `ui`, `lib`, `config`         |

### 2. slice 내부는 책임별로 나눈다

- slice 내부 폴더는 `api`, `model`, `ui`, `lib` 정도로 제한한다.
- 너무 세분화하면 파일 탐색 비용이 커진다.

| 폴더    | 책임                                          |
| ------- | --------------------------------------------- |
| `api`   | query function, DTO schema, query key factory |
| `model` | store, selector, parser, business logic       |
| `ui`    | 컴포넌트                                      |
| `lib`   | 순수 함수, helper                             |

### 3. 함께 움직이는 코드는 co-locate한다

- 하나의 기능/화면/도메인 조각을 위해 함께 움직이는 코드는 처음에는 한 파일에 둔다.
- 해당 컴포넌트나 동작에만 쓰이는 타입, 상수, 작은 유틸리티 함수, 하위 표현 컴포넌트는 같은 파일 안에서 가까이 배치해 변경 맥락을 유지한다.
- 상태와 상태를 사용하는 로직이 생기면 같은 파일 안의 private custom hook으로 먼저 분리한다. 훅이 길어지거나 같은 slice 안에서 재사용되면 폴더로 승격해 `model` segment나 해당 컴포넌트 폴더의 hook 파일로 옮긴다.

| ✅ 올바른 예                                                      | ❌ 잘못된 예                                                                                                |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `AddToCartButton.tsx` 안에 타입, 상수, 작은 helper 함께 배치      | `add-to-cart-button.types.ts`, `add-to-cart-button.constants.ts`, `add-to-cart-button.utils.ts`를 모두 분리 |
| 같은 slice 안에서 훅이 재사용될 때 `model/useAddToCart.ts`로 승격 | 처음부터 `model/` 폴더를 만듦                                                                               |

### 4. 폴더 승격 기준

- 파일이 커지거나 책임이 분리되기 시작하면 그때 폴더로 승격한다.
- 승격은 다음 질문으로 정당화한다.

| 질문                                                                           | 승격 신호                  |
| ------------------------------------------------------------------------------ | -------------------------- |
| 파일이 길어져 리뷰에서 한 번에 맥락을 파악하기 어려운가?                       | 한 파일이 200~300줄 이상   |
| 타입, 상수, 유틸리티, 하위 컴포넌트가 서로 다른 속도로 변경되는가?             | 한 파일에서 여러 변경 주기 |
| 상태 전이, effect, 파생값 계산, 이벤트 핸들러가 컴포넌트 본문을 가리고 있는가? | JSX가 코드의 20% 미만      |
| 일부 코드가 같은 slice 안의 다른 파일에서도 재사용되는가?                      | 복사-붙여넣기가 생김       |
| 테스트나 Storybook 등 보조 파일을 같은 단위로 묶어야 하는가?                   | 보조 파일이 3개 이상       |

```txt
src/features/add-to-cart/ui/add-to-cart-button/
  index.ts                       # 선택적 컴포넌트 공개 경계
  add-to-cart-button.tsx
  add-to-cart-button.types.ts
  add-to-cart-button.constants.ts
  add-to-cart-button.utils.ts
```

### 5. 공개 경계는 제한한다

- 이 저장소는 slice root와 entity root에 `index.ts` 배럴 익스포트를 사용하지 않는다.
- slice 외부에서는 모듈의 실제 파일 경로를 직접 import한다.
- 폴더로 승격한 컴포넌트 내부의 `index.ts`만 필요한 named export를 모으는 공개 경계로 선택할 수 있으며, 그 외 모듈은 직접 import한다.
- `export *`는 사용하지 않으며 내부 타입, 상수, 유틸리티, 보조 컴포넌트는 외부에서 직접 import하지 않는다.

```ts
// ✅ 권장
import { AddToCartButton } from '@/features/cart/ui/AddToCartButton'
import { useCartStore, cartSelectors } from '@/features/cart/model/CartStore'
import { productEntity } from '@/entities/product/api/ProductService'

// ❌ 금지
import { AddToCartButton } from '@/features/cart'
import { useCartStore } from '@/features/cart'
```

이유:

- root `index.ts`가 없으면 IDE에서 "Go to Definition"이 실제 파일로 바로 이동한다.
- 트리쉐이킹이 불확실해지는 문제를 피한다.
- 사용하지 않는 export가 번들에 포함되는 것을 막는다.
- slice의 공개 계약이 파일 시스템 구조로 드러나며, 변경 시 import 경로가 명시적으로 바뀌어 영향 범위가 보인다.

### 6. 공용 유틸리티는 namespace로 묶는다

- 공용 유틸리티는 비슷한 동작끼리 namespace class의 static method로 묶는다.
- 외부로 공개되는 유틸리티를 top-level standalone 함수로 흩뿌리지 않는다.
- React custom hook은 예외로 두되, React 규약이 드러나도록 `use[A-Z0-9]...` 이름의 function으로 공개한다.

```ts
// ✅ 올바른 예
export class MoneyUtils {
  private constructor() {}

  static format(value: number): string {
    return new Intl.NumberFormat('ko-KR').format(value);
  }
}

// ❌ 잘못된 예
export function formatMoney(amount: number): string { ... }
export function parseMoney(value: string): number { ... }
export function moneyToNumber(value: string): number { ... }
```

### 7. 비슷한 구현을 먼저 찾는다

- 비슷한 유틸리티, 훅, 컴포넌트를 새로 만들기 전에 기존 구현을 먼저 찾는다.
- 기능이 중복되면 합치거나 위치를 조정한다.

| ✅ 올바른 예                                      | ❌ 잘못된 예                                                       |
| ------------------------------------------------- | ------------------------------------------------------------------ |
| 기존 `shared/lib/date.ts`를 찾아 `DateUtils` 추가 | `formatDate`, `dateFormat`, `toDateString`을 각기 다른 폴더에 생성 |
| `entities/cart`를 재사용                          | `features/order` 안에 자체 cart 로직을 새로 만듦                   |

## Verification

- 새 기능이 기존 slice/entity와 중복되지 않는지 확인한다.
- cross-layer import가 금지된 방향으로 발생하지 않는지 확인한다.
- slice 내부 폴더 구조가 과도하게 세분화되지 않았는지 확인한다.
- 공개되지 않은 다른 slice의 내부 구현을 import하지 않았는가?
- slice/entity root에 `index.ts` 배럴 익스포트를 만들지 않았는가?
- 실제 파일 경로로 import하는가?
- 컴포넌트 폴더의 선택적 `index.ts`가 named export만 명시하고 내부 구현과 `export *`를 노출하지 않는가?
