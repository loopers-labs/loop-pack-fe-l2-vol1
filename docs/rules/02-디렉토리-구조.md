# 02 — 디렉토리 구조

## When to read

새 폴더를 만들거나, 파일을 어디에 둘지 결정하거나, slice/레이어를 나누거나, FSD 배치를 검토할 때 읽는다.

## Source of truth

- FSD 레이어와 slice 배치: 본 문서 Rules
- FSD import와 Public API: [`13-피처-구조-패턴.md`](13-피처-구조-패턴.md)
- Next.js 라우트: `src/app/**`

## Rules

### 1. 함께 움직이는 코드는 같은 파일에 둔다

- 하나의 컴포넌트나 동작만을 위해 함께 움직이는 타입, 상수, 작은 helper는 같은 파일에 둔다.
- 파일이 커지거나 재사용성이 생길 때만 폴더로 승격하고 내부 파일로 나눈다.
- 너무 일찍 폴더를 나누면 탐색 비용만 커진다.

| ✅ 올바른 예                                                                | ❌ 잘못된 예                                                |
| --------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `Select.tsx` 안에 `SelectTrigger`, `SelectList`, `SelectOption`이 함께 있음 | `select/` 폴더에 파일 하나씩 분리했지만 각 파일이 10줄 미만 |
| `useProductFilters.ts` 안에 parser, state, handler가 함께 있음              | 훅, parser, handler를 무조건 분리해서 3줄짜리 파일 생성     |

### 2. FSD 레이어에 맞춰 배치한다

- 기능은 FSD 레이어(app → views → widgets → features → entities → shared)에 맞춰 배치한다.
- 모든 디렉터리를 미리 만들 필요는 없다. 실제 기능이 생길 때 필요한 레이어와 slice만 만든다.

| 레이어     | 책임                                   | 예시                          |
| ---------- | -------------------------------------- | ----------------------------- |
| `app`      | bootstrap, provider, router, 전역 설정 | `page.tsx`, `layout.tsx`      |
| `views`    | route/view 단위 화면 조립              | `HomePage`, `ProductListPage` |
| `widgets`  | 독립적인 화면 블록                     | `Header`, `ProductList`       |
| `features` | 사용자 행동 단위 기능                  | `addToCart`, `filterProducts` |
| `entities` | 도메인 모델과 API/model/UI             | `product`, `cart`, `wishlist` |
| `shared`   | 도메인에 종속되지 않는 공용 코드       | `ui`, `lib`, `config`         |

### 3. 레이어 간 import 방향을 지킨다

- 상위 레이어는 하위 레이어를 import할 수 있지만, 하위 레이어는 상위 레이어를 import할 수 없다.

```txt
app -> views -> widgets -> features -> entities -> shared
```

| ✅ 허용                                                        | ❌ 금지                                              |
| -------------------------------------------------------------- | ---------------------------------------------------- |
| `views`가 `widgets`, `features`, `entities`, `shared`를 import | `shared`가 `features`를 import                       |
| `features`가 `entities`, `shared`를 import                     | `entities/product`가 `features/add-to-cart`를 import |
| `entities`가 `shared`를 import                                 | `features/search`가 `widgets/header`를 import        |

### 4. slice 내부는 책임별 segment로 나눈다

- slice 내부 폴더는 `ui`, `model`, `api`, `lib`, `config` 정도로 제한한다.
- 너무 세분화하면 파일 탐색 비용이 커진다.

| segment  | 책임                                    |
| -------- | --------------------------------------- |
| `ui`     | 컴포넌트와 화면 표현                    |
| `model`  | 상태, selector, reducer, hook           |
| `api`    | API 호출, DTO schema, query key factory |
| `lib`    | slice 내부 유틸리티                     |
| `config` | slice 설정                              |

```txt
src/features/add-to-cart/
  ui/
  model/
  api/
  lib/
```

### 5. Next 라우트는 entry point만 담당한다

- Next entry와 라우트 파일은 `src/app`에, 재사용 가능한 UI와 도메인 기능은 하위 FSD 레이어에 둔다.
- `src/app` 라우트 파일은 프레임워크 entry point다. provider와 라우팅 연결만 담당하고, 화면 조립은 `src/views`, 재사용 UI와 기능은 하위 FSD 레이어에 둔다.
- 상태 전이, API 호출, 도메인 로직을 `App.tsx`나 라우트 파일에 누적하지 않는다.

### 6. 내부 구현은 외부로 노출하지 않는다

- 공개 의도가 없는 내부 구현 파일은 다른 slice나 상위 레이어에서 import하지 않는다.
- FSD slice/entity root에는 `index.ts` Public API를 만들지 않는다. 직접 파일 import 정책과 유일한 컴포넌트 폴더 예외는 [`13-피처-구조-패턴.md`](13-피처-구조-패턴.md)에 정의한다.

| ✅ 올바른 예                                                                       | ❌ 잘못된 예                                                              |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `features/cart/ui/CartButton.tsx`가 `entities/cart/model/useCartStore.ts`를 import | `app/page.tsx`가 `entities/cart/ui/CartButton.internal.tsx`를 직접 import |
| 내부 helper는 같은 slice 내에서만 사용                                             | `shared/lib/date.ts`가 `entities/order`의 내부 타입을 import              |

## Verification

- 파일의 책임이 레이어 이름과 일치하는가?
- 상위 레이어를 하위 레이어에서 import하지 않았는가?
- 컴포넌트가 화면 조립, 도메인 로직, 공용 유틸 책임을 동시에 갖고 있지 않은가?
- 기존 구현을 중복하지 않았는지 확인한다.
- 폴더 승격이 크기, 재사용, 책임 분리로 정당화되는지 확인한다.
- 금지된 cross-layer import가 생기지 않았는지 `eslint.config.mjs` 검사를 통과하는지 확인한다.

```bash
pnpm lint
pnpm typecheck
pnpm build
```
