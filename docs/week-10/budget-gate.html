번들 예산과 환경 변수 게이트를 걸고, 막혔을 때 PR 화면만 보고 원인을 알 수 있게 만든다. 임계값은 7주차 측정값과 현재 값의 범위에 근거해야 한다.

01 · 근거로 쓸 값

7주차 기록에 같은 숫자를 두 가지로 부르는 곳이 있다

과제는 임계값 근거를 “7주차에 잰 실제 전송 크기 + 현재 값의 범위”로 요구한다. 그런데 7주차 측정 기록이 같은 값을 두 이름으로 쓴다.

docs/week-07/measurement.md의 상충하는 두 서술
위치 표기 포함 범위
209행 · Network waterfall 표 178.8KB CSS·JS 청크 14개 — CSS 포함
242행 · 본문 178.8KB JS 청크 합계 — JS만
이 값을 그대로 쓰면 감점 함정에 걸린다

과제는 “적당히 300KB는 감점”이라고 못박았고, 진행표도 전체 페이지 전송량과 JS 번들을 같은 값으로 취급하지 말라고 경고한다. 둘 중 어느 쪽인지 확정하지 못한 숫자를 JS 한도의 근거로 인용할 수 없다.

대신 쓸 수 있는 값

같은 문서 1258행에 리소스 종류별 분해가 있다. 이쪽은 JS만 따로 표기된 유일한 값이다.

JS 전송량 환산 · 백분율이 소수점 첫째 자리라 폭이 생긴다
계산 값

홈(/) 진입점 하나이고, 7주차 코드 기준이다. 이후 8주차 테스트와 9주차 인증이 들어갔으므로 현재 값과 다를 가능성이 크다. 임계값을 정하려면 pnpm build로 현재 값을 먼저 재야 한다.

측정 방식도 다르다. 7주차는 브라우저가 실제로 받은 전송 크기이고, 도구가 재는 값은 빌드 산출물의 압축 크기다. 같은 단위로 비교하려면 어느 쪽 기준을 쓸지 먼저 정해야 한다.

02 · 도구 선택

무엇으로 잴지부터 정한다

과제는 size-limit 또는 동등 도구를 요구한다. 현재 저장소에는 없다.

size-limit

파일 glob에 gzip·brotli 한도를 걸고 초과분을 출력한다. PR 코멘트 액션이 따로 있다. 의존성이 늘어난다.

Next.js build 출력 파싱

pnpm build가 출력하는 First Load JS를 스크립트로 검사한다. 의존성이 늘지 않지만 출력 형식이 바뀌면 깨진다.

.next 산출물 직접 계측

청크 파일을 직접 읽어 gzip 크기를 잰다. 7주차 “전송 크기”와 단위를 맞추기 가장 쉽지만 직접 구현해야 한다.

선택 기준

어느 쪽이든 7주차 값과 같은 단위로 비교되는지가 먼저다. 진입점 범위, 압축 방식, 단위를 맞추지 않으면 임계값 근거가 성립하지 않는다.

정정 · 2026-09-11 · 후보 하나가 성립하지 않는다

위 “Next.js build 출력 파싱” 카드는 실행 가능한 후보가 아니다. Next 16의 pnpm build 출력에는 Size와 First Load JS 컬럼이 아예 없어 파싱할 대상이 없다. 근거는 08절에 있다.

채택 결과는 09절에 있다. 위 카드들은 당시 검토 기록으로 그대로 둔다.

03 · 번들 예산

측정 → 범위 확인 → 임계값 순서로만 정한다

  1. pnpm build로 현재 값을 잰다. 한 번이 아니라 여러 번 재서 범위를 본다. 빌드마다 흔들리는 폭보다 여유폭이 작으면 게이트가 무의미해진다.
  2. 7주차 값과 단위·범위를 대조한다. 다르면 왜 다른지 적는다.
  3. 임계값과 여유폭을 정하고 왜 그 값인지를 함께 남긴다.
  4. 일부러 초과시키는 실험으로 실제로 막히는지 확인한다.
미측정 · 미결정

이 절의 모든 숫자는 아직 없다. 현재 값을 재기 전에는 임계값도, 여유폭도, 대상 진입점도 확정하지 않는다.

04 · 환경 변수 게이트

이 저장소에서는 노출 검사가 실질적인 형태다

과제는 누락, 잘못된 URL, 비공개 값의 NEXT_PUBLIC_ 노출 세 가지를 build 전에 막으라고 한다. 그런데 현재 코드에는 NEXT_PUBLIC_ 변수가 하나도 없다.

현재 사용 중인 환경 변수와 검증 후보
변수 사용처 성격 검증 후보
AUTH_SESSION_SECRET app/api/_data/auth.ts 비공개 누락 시 실패 · NEXT_PUBLIC_ 접두사로 새면 실패

검증 스크립트는 변수 이름과 실패 사유만 출력한다. 값 자체나 그 일부를 로그·PR 코멘트에 남기지 않는다. 과제의 공통 보안 항목이자 실패 리포트가 secret 유출 경로가 되지 않게 하려는 것이다.

위 표의 PORT는 게이트 대상에서 뺐다. 세 변수 중 실제로 사고 경로가 있는 것은 APP_ORIGIN과 AUTH_SESSION_SECRET 둘이다.

노출 검사가 핵심이다. get-api-base-url.ts:4-8에 주석으로만 있던 규칙 — “NEXT_PUBLIC_을 붙이면 서버 내부 origin이 브라우저에 그대로 노출된다” — 을 기계가 지키게 한 것이다. 제출 질문 3번 “Preview 환경이 production API를 바라보면”이 묻는 사고 경로가 이것이다.

5주차 판단을 뒤집었다 · APP_ORIGIN 폴백 제거

getApiBaseUrl()의 ?? http://localhost:${PORT} 폴백을 걷어내 APP_ORIGIN을 진짜 필수로 만들었다. AUTH_SESSION_SECRET은 mock 백엔드라 폴백을 유지하고 노출 검사만 적용한다.

이 폴백은 5주차에 의도적으로 남긴 것이다. docs/week-05/decisions.md:208의 이유는 “배포 환경이 정해지기 전에는 어떤 env를 읽어야 할지 알 수 없다”였고, 배포 설정이 없다는 조건은 지금도 그대로다. 바꾼 근거는 배포 환경이 정해져서가 아니라, 설정 계약을 선언하고 CI가 지키게 하는 것 자체가 이번 과제이기 때문이다. 5주차 기록은 지우지 않는다.

폴백이 있으면 origin을 빠뜨려도 조용히 localhost로 흘러간다. 로컬에서는 통과하고 배포 환경에서만 엉뚱한 곳을 가리키는, 설정 사고 중 가장 늦게 발견되는 형태다.

Actions 검증에서 잡은 것 · 2026-09-11 · 스크립트만으로는 부족했다

빨간불 실험(PR #20)에서 APP_ORIGIN을 not-a-valid-origin으로 바꿔 게이트를 실패시켰다. 값을 비우지 않고 형식을 깨뜨린 이유는 값이 로그에 새는지까지 함께 보기 위해서였다. 그 판단이 문제를 하나 잡았다.

스크립트 출력에는 값이 없었다. 그런데 로그 전체를 검색하니 값이 8번 나왔다.

##[group]Run actions/checkout@...
  submodules: false
  set-safe-directory: true
env:
  APP_ORIGIN: not-a-valid-origin     ← 여기
##[endgroup]

Actions가 모든 step 헤더에 그 step이 받는 env를 나열한다. 성공한 실행에서도 같은 값이 11번 나왔으므로 실패와 무관하고, uses:·run: 양쪽 step 모두에서 나타난다. 다만 이 로깅 동작은 문서에 명시된 것이 아니라 이 저장소의 두 실행에서 관찰한 사실이다.

바로 옆 줄이 대비를 보여준다. token: ***는 마스킹되고 APP_ORIGIN은 그대로다. 공식 문서는 자동 마스킹이 secrets 컨텍스트 값에만 적용된다고 명시하고, 비밀이 아닌 민감한 값은 ::add-mask::로 직접 가리라고 안내한다.

대응 · APP_ORIGIN을 secrets로 옮겼다

http://localhost:3000은 비밀이 아니다. 그런데도 secrets에 넣은 이유는 값을 어디서 가져오느냐가 스크립트가 무엇을 출력하느냐보다 중요하기 때문이다. 평문 env:는 자리 자체가 새는 자리라, 나중에 진짜 비밀을 같은 자리에 넣으면 모든 step 헤더에 그대로 찍힌다. 

env:
  APP_ORIGIN: ${{ secrets.APP_ORIGIN }}

감수하는 것이 하나 있다. fork PR에는 secrets가 전달되지 않아 외부 기여자의 PR에서는 게이트가 “누락”으로 실패한다. 이 저장소는 지금까지 모든 PR이 같은 소유자(im-wen3y)에서 왔으므로 해당되지 않지만, 외부 기여를 받게 되면 다시 판단해야 한다.

정정 · 2026-09-11 · 그 조건은 이미 성립해 있었다

바로 위의 “해당되지 않는다”는 판단은 틀렸다. 기록은 지우지 않고 정정만 덧붙인다. 과제 제출 PR 자체가 fork에서 upstream으로 올리는 PR이라, 외부 기여를 받게 될 미래가 아니라 같은 주에 그 조건을 밟았다. 제출 PR에서 quality, E2E (chromium), E2E (webkit) 세 job이 모두 실패했고, 로그의 APP_ORIGIN은 빈 값이었다.

게이트는 설계대로 동작했고 값 공급만 끊긴 상태였다. 그래서 값을 ${{ secrets.APP_ORIGIN || 'http://localhost:3000' }}로 바꿨다. secret이 있으면 마스킹된 값을 쓰고, 없으면 CI에서 쓸 유일한 값으로 떨어진다. 이 기본값은 getApiBaseUrl()에서 걷어낸 폴백과 자리가 다르다. 그쪽은 애플리케이션이 설정 누락을 조용히 넘기는 자리였고, 이쪽은 CI가 쓸 값이 playwright.config.ts의 baseURL 하나로 고정된 자리다.

조치 후 같은 fork PR에서 Quality와 E2E가 모두 통과해 재검증을 마쳤다. 내 저장소 안의 PR은 secret이 있어 조치 여부와 무관하게 통과하므로 근거가 되지 못한다. 게이트의 동작 조건을 바꾼 변경은 그 조건이 실제로 성립하는 환경에서 확인해야 한다. 같은 로그에서 APP_ORIGIN이 마스킹 없이 평문으로 찍힌 것과, PR 코멘트가 skipped: 코멘트 쓰기 실패 (403)으로 생략된 것도 함께 확인했다. 자세한 내용은 docs/rfc/week10-ci.md의 「secrets 취급」과 「결과 가시성」에 있다.

과제 공통 보안 항목(358행) “secrets를 로그로 찍지 않는다”가 말하는 것이 이것이다. 스크립트가 값을 안 찍는 것만으로는 부족했다.

아직 Actions에서 확인하지 않았다

위는 모두 로컬 실행 결과다. Validate environment가 실제 CI에서 Run production build 앞에 서는지, job summary에 결과가 뜨는지, 빨간불 실험에서 build가 Skipped 되는지는 push 후 확인한다. required 배치도 미결정이다.

이후 확인 · 2026-09-11 — 세 항목 모두 Actions에서 확인했다. 성공 실행(PR #12)에서 Validate environment가 build 앞에서 통과했고 번들은 273.79 kB로 로컬 측정과 정확히 일치했다. 실패 실행(PR #20)에서는 Run production build부터 세 step이 skipped였다. 남은 것은 job summary가 PR 화면에 표로 렌더되는지 눈으로 보는 것과 required 배치다.

이후 확인 · 2026-09-11 · Vercel에서 APP_ORIGIN은 필수가 아니다

위 표는 APP_ORIGIN을 “누락 시 실패”로 적었다. 배포 환경이 생기면서 이 판단이 한 군데에서 바뀐다. Vercel은 배포마다 URL이 달라 고정값을 미리 넣을 수 없고, 대신 VERCEL_URL이 그 배포의 도메인을 프로토콜 없이 담아 준다. 그래서 VERCEL=1이고 VERCEL_URL이 있으면 누락 검사를 건너뛴다. 

if (isOnVercel && process.env.VERCEL_URL) return null

계약이 느슨해진 것이 아니라 공급자가 바뀐 것이다. 절대 origin이 필요하다는 요구는 그대로고, 그 값을 사람이 넣느냐 플랫폼이 넣느냐만 다르다. Vercel 밖(로컬 · CI)에서는 여전히 없으면 실패한다.

검사를 짠 것과 검사가 도는 것은 별개였다

Preview가 다른 환경을 가리키는지 보는 checkSelfReference()는 VERCEL_ENV === 'preview'일 때만 동작한다. 그런데 Vercel이 부르는 pnpm build는 next build 하나였다. 검증은 GitHub Actions의 별도 step에서만 돌고 있었고, Actions에서는 그 조건이 참이 될 수 없다. 즉 이 검사는 어디에서도 실행되지 않는 죽은 코드였다. 

- "build": "next build"
+ "build": "node scripts/validate-env.mjs && next build"

게이트는 “조건이 맞으면 막는가”뿐 아니라 “실제로 빌드하는 명령에 걸려 있는가”까지 확인해야 완성이다. CI에만 붙이면 배포 경로는 무방비다.

제출 질문 3번 실험 · Preview에 Production URL 넣기

Vercel Settings → Environment Variables에서 APP_ORIGIN을 Preview 환경에만 Production URL로 지정하고 재배포했다. 결과는 아래와 같다. 

> node scripts/validate-env.mjs && next build

Preview 변수를 지우고 재배포해 초록불로 복구했다. 복구 후 Preview /products의 서버 응답 HTML에 총 30개가 들어 있는 것으로 VERCEL_URL 분기가 동작함을 확인했다 — 브라우저가 나중에 채운 값이 아니라 서버가 만든 HTML에 이미 있다는 뜻이다.

곁가지 · Deployment Protection이 SSR 자기 호출을 막는다

위 확인에 도달하기까지 Preview가 스켈레톤에서 멈춰 있었다. 브라우저로 API 경로를 부르면 200이었는데, 같은 경로를 curl로 부르니 302로 vercel.com/sso-api에 튕겼다. 브라우저에는 SSO 쿠키가 있고 서버가 스스로 부르는 요청에는 없다. 같은 URL인데 호출 주체에 따라 결과가 갈린 것이다.

Vercel 문서도 Standard Protection에서는 VERCEL_URL로 향하는 fetch를 쓰지 말라고 명시한다. 보호 범위는 Standard(production 제외 전부)와 All Deployments 둘뿐이고, production만 보호하는 선택지는 Enterprise 전용이라 Hobby에서 켤 수 있는 유일한 옵션이 정확히 Preview를 잠그는 옵션이었다. 보호를 끄고 해결했다.

얻은 기준 하나. 접근 제한이 걸린 환경에서 “브라우저에서 200”은 서버도 통과한다는 근거가 되지 않는다. 서버 쪽 요청을 따로 확인해야 한다.

막힌 지점 · $GITHUB_STEP_SUMMARY는 step마다 다른 파일이다

리포트 step에서 vitest가 쓴 요약을 읽어 그대로 올리려 했으나 되지 않는다. step마다 별도 파일이라 다른 step의 요약에 접근할 수 없다. 각 스크립트가 공유 디렉터리에 섹션을 남기고 마지막 step이 모으는 구조로 바꿨다. 

ci-report/10-tests.md    ← report-test-results.mjs
ci-report/20-env.md      ← validate-env.mjs
ci-report/30-budget.md   ← report-bundle-budget.mjs
         ↓
post-ci-comment.mjs  →  PR 코멘트 하나 (표식으로 갱신, 쌓이지 않음)

파일명의 숫자가 코멘트 안 순서다. Post CI summary comment step의 조건은 !cancelled()라, 앞 step이 실패해 섹션이 일부만 모여도 그때까지의 결과는 올라간다.

vitest 요약은 json 리포터를 추가해 만든다. --reporter=default --reporter=github-actions --reporter=json으로 기존 로그 출력과 job summary를 그대로 두고 json만 얹었다. 리포터를 명시하면 github-actions 자동 활성화가 꺼질 수 있어 함께 지정했다.

실패했을 때도 리포트가 남아야 한다

게이트가 실패하면 step이 거기서 끝나 summary 기록까지 건너뛰기 쉽다. 2단계 아티팩트 업로드에서 겪은 것과 같은 구조다. 조건을 “실패했을 때”가 아니라 “측정이 실행됐을 때”로 두어야 실패 리포트가 남는다.

06 · required 배치

비용·변동성·리스크로 나눈다

과제는 required로 둘 check와 제외할 check를 구분하고 이유를 적으라고 한다. 판단 기준은 셋이다.

  • 결정적인가 — 같은 입력에 같은 결과가 나오는가
  • 비용 — 모든 PR에서 돌려도 되는 시간인가
  • 리스크 — 막지 못했을 때 main에 무엇이 들어가는가
미결정

환경 변수 검증은 결정적이고 저렴하며 실패 시 배포 사고로 이어진다. 번들 예산은 임계값을 정하기 전까지 판단할 수 없다. 어느 것을 required로 둘지는 작성자가 정한다. 이 문서에서 확정하지 않는다.

결정 · 2026-09-11 · 번들 예산은 막지 않고 경고만

작성자 판단이다. 번들 초과는 되돌리기 쉬운 문제라 머지를 막을 이유가 약하다. 크기는 나중에 줄여도 되고, 그 사이 다른 작업이 막히는 비용이 더 크다. 환경 변수 검증은 그대로 막는다. 설정 실수는 배포까지 흘러가면 되돌리기가 훨씬 비싸다.

비용 · 변동성 · 리스크로 나눈 판단
게이트 변동성 비용 막지 못하면 배치
환경 변수 없음(결정적) 1초 미만 잘못된 설정이 배포까지 간다 차단
번들 예산 없음(재빌드 편차 0) build 재사용, 수 초 번들이 조용히 커진다. 다만 되돌리기 쉽다 경고
별도 job으로 분리하지 않은 이유

“번들만 required에서 빼기”를 위해 별도 job으로 나누는 방법도 있었다. 그러면 size-limit이 .next를 읽어야 하므로 checkout·setup·install과 build를 한 번 더 돌려야 한다. 1단계 실측 기준으로 약 25~32초가 추가된다.

이는 1단계 체크리스트의 “job 병렬화로 각 job의 install 비용을 중복시키지 않았는가”에 정면으로 걸린다. 1단계에서 Quality의 불필요한 Chromium 설치 24초를 걷어냈는데 비슷한 비용을 도로 넣는 셈이다.

대신 step에 continue-on-error: true를 붙였다. 빌드 중복도, required check 추가도 없이 같은 결과를 얻는다. 

- name: Check bundle budget
  id: budget
  continue-on-error: true
  run: pnpm exec size-limit --json > size-limit-result.json
경고가 묻히지 않게

continue-on-error만 붙이면 quality check가 초록불로 남아 초과를 놓치기 쉽다. 리포트 스크립트가 초과 시 ::warning:: 주석을 함께 남겨 PR 화면에 드러나게 했다. 

::warning title=번들 예산 초과::전체 클라이언트 JS 번들이(가)
한도를 23.79 kB 넘었습니다 (273.79 kB / 250.00 kB)

continue-on-error가 붙으면 step이 실패해도 steps.budget.conclusion은 success가 된다. 리포트 step의 조건은 != 'skipped'이므로 그대로 동작한다. 실제 실패 여부가 필요하면 conclusion이 아니라 outcome을 봐야 한다.

required check 구조

두 게이트는 quality job 안의 step이므로 따로 required로 걸 수 없다. develop의 ruleset merge-required-ci에는 quality, Detect E2E scope, E2E (chromium), E2E (webkit) 네 개가 등록돼 있고, ruleset은 그대로 둔다. 환경 변수 검증이 실패하면 quality가 실패해 머지가 막히고, 번들 초과는 continue-on-error 때문에 막지 않는다.

07 · 빨간불 자가 검증

일부러 넘겨서 막히는지 본다

2단계에서 정상 경로만으로는 수정이 효과 있는지 증명되지 않아 실험 브랜치로 실패 경로를 만들었다. 여기서도 같은 방식이 필요하다. 게이트를 넣어두고 초록불만 보면, 그 게이트가 실제로 막는지는 확인되지 않는다.

부수 발견 1 · 예산은 클라이언트 청크만 잰다

처음에는 “큰 라이브러리를 무의미하게 import”하는 방식으로 실제 번들을 키우려 했다. 클라이언트 컴포넌트(HeaderNav)에 137KB짜리 모듈을 넣었는데 클라이언트 번들이 커지지 않았다. 

.next/server/chunks/ssr/...   ← payload 있음
.next/static/chunks/          ← 없음

'use client' 컴포넌트여도 .length만 참조하니 클라이언트 번들에서는 트리 셰이킹으로 걷히고 서버 번들에만 남았다. 소스를 60KB에서 137KB로 키워도 측정값은 286.28 kB 그대로였다.

이 예산이 무엇을 재는지 확인한 셈이다. .next/static/chunks/**, 즉 브라우저가 실제로 받는 JS만 센다. 서버 전용 코드는 들어가지 않는다. 그래서 한도를 낮추는 방식으로 바꿨다.

실험 PR은 머지하지 않는다

2단계 실험 PR과 같은 규칙이다. 제목에 머지 금지를 적고, 확인이 끝나면 실험 변경이 최종 diff에 남지 않았는지 대조한다.

  • app/(home)/ 아래는 page-*.js 하나뿐이다. 홈이 실제로 받는 11개 중 나머지는 공유 청크로 밖에 있어, 홈 전용 조각은 골라도 홈이 받는 전부는 여전히 못 고른다.
  • webpack 산출물은 40개 324.5KB, Turbopack은 23개 266.9KB로 21% 차이가 난다. 배포하지 않는 번들에 예산을 거는 셈이 되고, 1단계에서 잰 CI 시간 근거도 흔들린다.

따라서 webpack 전환은 채택하지 않는다.

측정 방법을 두 번 고쳤다

처음에는 응답의 content-length로 쟀다. 그런데 압축 응답에는 그 헤더가 없다. chunked로 오기 때문이다. 값이 0이라 압축 해제된 본문 크기로 넘어갔고, 홈 JS가 609KB로 나왔다. 실제 전송량의 3.4배다.

CDP의 Network.loadingFinished가 주는 encodedDataLength로 바꿨다. 7주차가 Chrome DevTools 트레이스에서 쓴 것과 같은 값이다.

폰트가 바이트 단위까지 일치한다. 같은 파일을 같은 방식으로 재고 있다는 근거다. 01절에서 “어느 쪽 기준을 쓸지 먼저 정해야 한다”고 남겼던 항목이 여기서 해소됐다.

JS는 8·9주차에 인증과 테스트가 들어갔는데도 약 6.7KB(3.8%) 증가에 그쳤다.

위 재빌드 3회는 모두 Node 22.14.0에서 잰 값이다. Node 24.17.0으로 올려 다시 재니 값이 달라졌다. 

Node 22.14.0   273,743 B   273.74 kB

Node 24에서도 재빌드 3회 모두 273.79 kB로 동일했다. 즉 같은 Node 안에서는 편차가 0이고, Node 메이저가 바뀔 때만 움직인다. 0.017%는 여유폭 5%에 비해 판정을 뒤집을 크기가 아니지만, 측정 조건에 Node 버전을 함께 적어야 한다.

03절의 전제가 바뀐다

03절에는 “빌드마다 흔들리는 폭보다 여유폭이 작으면 게이트가 무의미해진다”고 적었다. 재빌드해도 바이트가 같으므로 여유폭에 노이즈 흡수분을 넣을 필요가 없다. 여유폭은 순수하게 “앞으로 허용할 증가분”이 된다.

1단계 CI 시간 측정과 대비된다. 그때는 같은 커밋이 58·69·69초로 흔들려 13초 단축을 확정하지 못했다.

전체 번들에 걸되, 근거는 홈 실측에서 끌어온다

작성자가 내린 결정
결정할 것 결정 이유
측정 도구 size-limit + @size-limit/file 과제가 이름으로 지정한 도구이고 관리 포인트가 하나다. 제출물 형식 .size-limit.*도 그대로 맞는다

여유폭 5%의 뜻은 “7주차에서 현재까지 홈이 1.4% 늘었으니, 그 3배쯤 되는 증가 한 번을 허용한다” 이다. 임계값이 7주차 실측(①)에서 출발해 현재 값(②④)으로 이어지고, 단위 대응(③)과 편차(⑤)로 뒷받침된다.

설정

[
  {
    "name": "전체 클라이언트 JS 번들",
    "path": ".next/static/chunks/**/*.js",
    "gzip": true,
    "limit": "287.4 kB"
  }
]

webpack: false는 넣지 않았다. 공식 문서의 Next.js 예시에는 있지만, 그 필드는 @size-limit/webpack 플러그인이 설치돼 있어야 인식된다. 실제로 넣었더니 Config option webpack needs @size-limit/webpack plugin 오류가 났다. @size-limit/file만 쓰면 애초에 번들링을 하지 않으므로 불필요하다.

@size-limit/preset-app도 쓰지 않았다. file에 time이 묶여 있는데, time은 headless Chrome을 띄워 실행 시간을 잰다. 크기만 필요하므로 불필요한 비용이다.

초과량을 23.74 kB로 숫자로 말해준다. 과제가 요구한 “무엇이 얼마나 초과했나”를 도구가 이미 절반 채워준다. 확인 후 설정은 원래 값으로 되돌렸다.

이 예산의 한계 두 가지

1. 홈만의 값이 아니다. 한도는 23개 청크 전체에 걸린다. /checkout이 커져도 걸리고 홈이 커져도 걸린다. 어디서 늘었는지는 한도가 알려주지 않으므로, 걸렸을 때 파일별 출력을 따로 봐야 한다.

2. 홈이 전체의 65.5%라는 비율은 오늘 시점 값이다. 다른 라우트가 커지면 이 비율이 변하고, “전체 한도”와 “홈 근거”의 연결이 느슨해진다. 비율이 크게 움직이면 근거를 다시 세워야 한다.

로컬 Node 버전을 24.17.0으로 올린 이유

측정 도중 로컬이 Node 22.14.0으로 돌고 있다는 것을 확인했다. 두 가지 이유로 .nvmrc의 24.17.0에 맞췄다.

올려야 했던 이유
이유 내용 확인한 것
운영·CI 빌드 환경과 일치 CI는 actions/setup-node가 .nvmrc를 읽어 24.17.0으로 빌드한다. 로컬이 22.14.0이면 임계값의 근거가 되는 빌드가 실제 게이트가 도는 환경과 다른 곳에서 나온다. 실제로 두 버전의 산출물이 47 B 달랐다. 크기는 작지만 “같은 조건에서 쟀다”고 말할 수 없게 된다
새로 추가한 라이브러리 호환성 size-limit@13.0.3의 engines는 ^22.18.0 || ^24.0.0 || >=26.0.0이다. 로컬 22.14.0은 22.18.0 미만이라 지원 범위 밖이었다. .npmrc에 engine-strict가 없어 설치와 실행은 됐지만, 지원하지 않는 버전에서 나온 측정값이었다

@size-limit/file의 engines는 ^20.0.0 || ^22.0.0 || >=24.0.0으로 더 넓지만, peerDependencies가 "size-limit": "13.0.3"으로 정확한 버전에 고정돼 있다. 두 패키지는 항상 같은 버전으로 함께 올려야 한다.

기준선을 CI 쪽 값으로 읽어야 한다

CI가 24.17.0으로 빌드하므로 실제로 게이트가 마주할 값은 273.79 kB다. 위 근거 사슬의 ④는 Node 22에서 잰 273.74 kB이므로, 이후 비교는 24.17.0 기준으로 한다.

한도 287.4 kB는 Node 22 값(273.74)에 5%를 얹어 정한 값이다. CI 기준선 273.79에 대해서는 여유폭이 4.97%가 된다. 287.5 kB로 올리면 정확히 5%가 되지만, 0.03%p 차이라 표기를 맞추려는 목적밖에 없어 올리지 않는다. 게이트 판정이 갈리는 구간이 아니다.

아직 하지 않은 것

CI 연결, $GITHUB_STEP_SUMMARY 노출, 환경 변수 게이트, 07절의 빨간불 실험은 시작하지 않았다. required 배치도 미결정이다. 위 자가 검증은 로컬 실행 결과이며 Actions에서는 확인하지 않았다.

작성자가 정할 것

아래는 에이전트가 대신 확정하지 않는다. 근거를 모아 선택지를 정리하는 데까지가 이 문서의 범위다.
