LOOP PACK · WEEK 10 · BEFORE

캐시가 있을 때와
없을 때를 각각 3번씩

CI가 얼마나 걸리는지 재는 작업입니다. 같은 코드라도 캐시가 있으면 빠르고 없으면 느리기 때문에, 두 상황을 나눠서 각각 3회씩 측정합니다.

이 문서는 실행 순서 안내입니다. Warm 3회와 Cold 3회 측정을 모두 마쳤습니다. 측정 방식의 결정 근거와 기록은 진행표 01 Before 측정과 CI 측정과 개선 기록에 있습니다.

캐시가 뭔가

매번 pnpm install로 의존성을 내려받으면 오래 걸립니다. 그래서 GitHub이 받아둔 store를 보관했다가 다음 실행에서 복원합니다. 이 보관소가 캐시입니다. Quality와 E2E는 actions/setup-node의 cache: pnpm 하나를 공유합니다.

warm · 캐시가 복원됨

보관된 store를 꺼내 쓰므로 Install dependencies가 몇 초에 끝납니다. 평소 개발 중 대부분의 실행이 이 상태입니다.

Cache not found

cold · 캐시가 없음

처음부터 내려받아야 합니다. 캐시가 만료되거나 축출됐을 때, 또는 lockfile이 바뀌어 키가 달라졌을 때 발생합니다.

첫 실행 여부가 기준이 아닙니다

cold와 warm은 대상 캐시가 실제로 복원됐는지로 구분합니다. 정확한 키가 miss여도 fallback 키가 복원되면 완전한 cold가 아닐 수 있으므로 실행 로그를 함께 확인합니다.

왜 6번인가

한 번만 재면 그날 러너가 느렸던 것인지 실제 특성인지 구분할 수 없습니다. 조건별로 3회를 재 중앙값을 쓰고 최소~최대 범위를 함께 적습니다. 그래야 개선 후 줄어든 시간이 측정 흔들림보다 큰지 판단할 수 있습니다.

warm을 먼저 재는 이유는 현재 캐시가 살아 있기 때문입니다. 손대지 않고 3회를 먼저 마치면 캐시 삭제는 cold 회차에만 3번 하면 됩니다.

재현 방법으로 채택하지 않은 것

캐시가 저장된 직후 같은 run을 re-run해 warm을 만드는 방법은 실제 개발에서 재현되는 조건이 아니라고 보아 채택하지 않았습니다. 실제 warm은 이전 실행이 남긴 캐시를 이후 PR이 복원하는 상황입니다.

현재 상태 · 2026-09-10

Before warm 3회를 완료했습니다. Quality workflow는 57초·55초·53초로 중앙값 55초, E2E workflow는 3분 4초·2분 33초·2분 10초로 중앙값 2분 33초였습니다. 세 회차 모두 pnpm dependency cache hit/restored 로그를 확인했습니다.

Cold 3회도 각 실행 전에 캐시를 비우고 cache miss 로그를 확인해 완료했습니다.

00. 한 번만 하는 준비

  1. PR을 엽니다. 두 workflow 모두 pull_request에서 실행되므로 PR이 열려 있어야 커밋마다 자동 실행됩니다. 이번 측정용 PR의 base는 develop입니다. 
    # feat/week-10 브랜치에서
git push -u origin feat/week-10
gh pr create --base develop --title "Week 10 CI 측정" --body "Before 측정용"
  2. 현재 캐시를 확인합니다. 기본 표에는 ref 칸이 없으므로 어느 브랜치의 캐시인지 보려면 --json에 ref를 넣습니다. 
    gh cache list -R im-wen3y/loop-pack-fe-l2-vol1 --limit 100 \
  --json id,key,ref,sizeInBytes,lastAccessedAt
  3. 측정 조건을 먼저 적습니다. 러너 ubuntu-latest, Node 24.17.0, pnpm 10.15.1, 검증 명령, 캐시 대상과 키, 기준 커밋 9859a7c6을 CI 측정 기록에 남깁니다. 6회 내내 이 조건은 바뀌지 않습니다.
정정 이력 · 2026-09-10 · 최종 workflow 확인

E2E browser 설치 오류를 확인하는 과정에서 임시 커밋이 있었지만, 현재 최종 quality.yml과 e2e.yml의 파일 내용은 기준 커밋 9859a7c6과 동일합니다. 따라서 이 문서의 기준 커밋 표기는 그대로 사용합니다.

warm 1회차 실행은 커밋 1c4d8e2ac4169022285e56f944ce492b42bc7625에서 실행됐습니다. Quality Quality와 E2E입니다. 이전 확인용 성공 실행은 참고 기록으로만 유지합니다.

세 회차는 workflow label ubuntu-latest가 해석한 Ubuntu 24.04.4, ubuntu-24.04 image 20260831.293.1, Node 24.17.0 조건에서 실행했습니다. Azure Region은 실행마다 달랐습니다.

warm · 3회

01. 캐시를 그대로 두고 3회

아무것도 지우지 않고 평소처럼 커밋을 밀기만 합니다. 아래를 3회 반복합니다.

git commit --allow-empty -m "chore(ci): Before warm 1회차"
git push

--allow-empty는 파일을 바꾸지 않고 커밋만 만드는 옵션입니다. 트리가 동일해야 6회를 같은 조건으로 비교할 수 있어 사용합니다. 기준 커밋 표기는 9859a7c6으로 유지하고, 각 실행이 동일 트리의 빈 커밋임을 함께 적습니다.

첫 실행에서 캐시가 복원되지 않았다면

그 실행은 warm이 아닙니다. cold 회차로 옮겨 적고 1부를 다시 시작합니다. 캐시가 7일간 접근되지 않아 만료됐을 수 있습니다.

cold · 3회

02. 매번 캐시를 비우고 3회

아래 한 묶음을 3회 반복합니다. 회차마다 삭제가 필요합니다.

# 1) 측정 문서 등 현재 변경을 임시 보관합니다
git stash push -m "cold 측정 문서 임시 보관"
git status --short

# 2) 저장소를 명시해 Actions 캐시를 전부 지웁니다
gh cache delete --all --repo im-wen3y/loop-pack-fe-l2-vol1

# 3) 캐시 목록이 비었는지 확인합니다
gh cache list --repo im-wen3y/loop-pack-fe-l2-vol1

# 4) 빈 커밋을 만들고 push하여 실행합니다
git commit --allow-empty -m "chore(ci): Before cold 3회차"
git push

# 5) 실행이 끝난 뒤 문서 변경을 복원합니다
git stash pop
기본 원격 저장소 오류가 나면

No default remote repository has been set 오류는 --repo im-wen3y/loop-pack-fe-l2-vol1로 저장소를 명시하면 해결됩니다. 기본값을 등록하려면 gh repo set-default im-wen3y/loop-pack-fe-l2-vol1을 한 번 실행합니다.

틀리기 쉬운 것

cold 실행이 끝나면 캐시가 다시 저장됩니다

한 번 지우고 3회를 연속 실행하면 2·3회차는 warm이 됩니다. 다음 cold 직전에 매번 다시 지워야 합니다.

지울 범위는 세 곳입니다

PR 실행이 캐시를 복원할 수 있는 곳은 이 PR, base 브랜치 develop, 기본 브랜치 main입니다. 한 곳이라도 남으면 거기서 복원돼 cold가 성립하지 않습니다. gh cache delete --all은 ref 구분 없이 저장소의 캐시를 비웁니다.

삭제했다는 사실은 cold의 근거가 아닙니다

체크리스트에 “캐시 설정의 존재만 보고 hit이라고 기록하지 않았는가” 항목이 있습니다. 같은 기준으로 cold도 실행 로그에 남은 문구로 판정합니다.

Playwright 브라우저 설치는 캐시 대상이 아닙니다

E2E의 Install Playwright browsers는 warm·cold와 무관하게 매번 실행됩니다. Week 09 참고 실행에서는 47초였습니다. 이 시간은 cold와 warm의 차이에 나타나지 않으므로, E2E의 최장 구간을 지목할 때 구분해야 합니다.

03. 실행마다 남길 것과 집계

Quality와 E2E 각각에 대해 회차마다 기록
항목 내용
run URL Quality와 E2E를 각각 남깁니다.
workflow 전체 / job 두 값을 구분해 초 단위로 적습니다.
step 시간 Set up Node.js, Install dependencies, 브라우저 설치, 각 검증 step
캐시 증거 warm은 복원 문구와 용량, cold는 미복원 문구를 로그 원문으로 남깁니다.

6회 측정 결과를 다음과 같이 정리했습니다.

  • Quality workflow 중앙값: warm 55초, cold 57초. 두 조건의 범위가 겹칩니다.
  • E2E workflow 중앙값: warm 2분 33초, cold 2분 38초. 두 조건의 범위가 겹칩니다.
  • 가장 긴 구간은 Run E2E tests로 warm·cold 중앙값이 모두 57초입니다. 다음은 Install Playwright browsers로 warm 51초, cold 52초입니다.
  • Quality와 E2E가 병렬로 실행되므로 “전체 완료 시간”의 정의를 먼저 적습니다. 두 시간의 합이 아니라 늦게 끝나는 쪽입니다.
측정에 포함하지 않는 실행

검증 step에 도달하기 전에 실패한 실행은 6회에 넣지 않습니다. 대신 원인과 함께 CI 측정 기록의 제외 목록에 남깁니다.

완료 — warm 3회와 cold 3회의 원본 값, 중앙값, 범위, 캐시 로그를 모두 기록했고 가장 긴 구간을 로그 근거로 지목했습니다. 다음은 개선 전략을 정하고 같은 조건으로 After를 측정하는 단계입니다.
