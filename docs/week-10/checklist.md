### 현재 확인한 참고 실행 — Week 09 PR #181

이 값은 cold/warm 여부가 확인되지 않아 Before 3회 측정에는 아직 포함하지 않는다.

| 범위                                  |       값 |
| ------------------------------------- | -------: |
| Quality workflow 전체                 | 1분 23초 |
| quality job                           | 1분 18초 |
| Set up job                            |      1초 |
| Checkout                              |      1초 |
| Set up pnpm                           |      3초 |
| Set up Node.js                        |     10초 |
| Install dependencies                  |      2초 |
| Install Playwright Chromium when used |     24초 |
| Run quality checks                    |     33초 |
| Post Set up Node.js                   |      0초 |
| Post Set up pnpm                      |      1초 |
| Post Checkout                         |      0초 |
| Complete job                          |      0초 |

- Chromium 설치는 `pnpm check`에서 사용되지 않으므로 제거 후보지만, 24초가 곧 확정 단축 시간은
  아니다. 같은 조건의 Before/After로 확인한다.
- Quality도 약 197MB의 pnpm dependency cache를 복원했으므로 pnpm cache 기준 warm이다. Next.js
  build cache는 없었다.
- E2E 참고 실행은 workflow 전체 2분 30초, e2e job 2분 26초였다. 브라우저 설치는 47초,
  `Run E2E tests`는 1분 19초였다. 후자는 production build와 Playwright 실행을 모두 포함한다.
  Playwright는 Chromium·WebKit 30개 테스트를 4 workers로 실행해 1.2분에 모두 통과했다. Next.js
  build cache는 없었고, pnpm dependency cache 약 197MB는 key가 일치해 복원됐다. 따라서 pnpm
  cache 기준 warm 실행이지만 모든 캐시가 warm이었다고 표현하지 않는다.

> 초과해도 `quality`는 pass다(PR #21). 실패 리포트는 PR 코멘트·job summary·`::warning::` 주석 셋으로
> 남았고, 게이트가 실제로 빨간불을 내는 것은 환경 변수 쪽에서 확인했다(PR #20: build 포함 3개 step
> skipped, `quality` failure). 두 동작이 의도대로 갈린 것이지 미충족이 아니다.
>
> **「실험 PR 제거」 확인.** 실험 브랜치와 PR(#17·#18·#19·#20·#21)은 최종 브랜치와 분리된
> 별도 검증용 PR이다. 최종 코드(`feat/week-10`)에는 실험 변경이 없음을 확인했다 — 한도 `287.4 kB`,
> `APP_ORIGIN`은 secrets, 실험 파일 0건.
>
> 이후 `APP_ORIGIN`은 fork PR 대응으로 `${{ secrets.APP_ORIGIN || 'http://localhost:3000' }}`가
> 됐다. 경위는 아래 「하지 말아야 하는 것」의 추가 확인(2026-09-11) 참고.

### 하지 말아야 하는 것

- [x] 근거 없이 `300KB` 같은 임의의 예산을 정하지 않았는가
- [x] 전체 페이지 전송량과 JavaScript 번들 크기를 같은 값으로 취급하지 않았는가
- [x] 실패 원인을 확인하려면 로그를 열어야만 하는 상태로 두지 않았는가
- [x] 실제 secret 값을 코드, 문서, 로그나 PR에 남기지 않았는가

> **두 번째 항목**은 오히려 7주차 기록의 모순을 찾아내는 계기가 됐다. `178.8KB`를 209행은
> 「CSS·JS 청크」, 242행은 「JS 청크 합계」로 부른다. 어느 쪽인지 확정할 수 없어 근거로 쓰지 않고,
> 1258행의 리소스 종류별 분해(JS 6.8%)에서 뽑은 값을 썼다.
>
> **세 번째 항목**은 PR #21을 눈으로 확인하면서 처음엔 미충족이었다. job summary만으로는 대화
> 화면에 `All checks have passed`만 떠서 초과를 놓쳤다. PR 코멘트를 붙여 해소했다.
>
> **네 번째 항목** — 검증 스크립트는 변수 이름과 사유만 출력한다. 실험에 쓴 `not-a-valid-origin`은
> 비밀이 아닌 더미 값이고, 실제 비밀은 다루지 않았다. `APP_ORIGIN`을 secrets로 옮긴 뒤 step 헤더의
> 평문 노출이 11회에서 0회로 바뀐 것을 확인했다.
>
> **추가 확인(2026-09-11) — 위 두 항목은 fork PR에서 성립하지 않는다.** 제출 PR(fork → upstream)에서
> 확인한 내용이다. ① secrets가 전달되지 않아 `APP_ORIGIN`이 폴백 값으로 들어가고, 마스킹 대상이
> 아니므로 step 헤더에 평문으로 다시 찍힌다. 비밀이 아닌 값이라 유출은 아니지만 "평문 `env:`는 새는
> 자리"라는 원칙은 지켜지지 않는다. ② PR 코멘트는 `skipped: 코멘트 쓰기 실패 (403)`으로 생략된다.
> fork PR의 `GITHUB_TOKEN`은 `pull-requests: write`를 선언해도 읽기 전용으로 강등되기 때문이며,
> 그래서 세 번째 항목이 말한 "PR 코멘트로 해소"가 외부 기여 PR에서는 되돌아간다. 두 가지 모두 지금
> 구조에서는 받아들이는 것 외에 선택지가 없어 한계로 남긴다. 근거는
> [`week10-ci.md`](../rfc/week10-ci.md)의 「secrets 취급」과 「결과 가시성」에 있다.

## 4단계 — AI 코드리뷰

### AI에게 맡길 수 있는 범위

- workflow YAML 초안과 기존 workflow의 누락·위험 검토
- size-limit과 환경 변수 검증 스크립트의 골격
- `dorny/paths-filter`, `concurrency`, job summary 같은 설정 초안
- ESLint custom rule, `no-restricted-syntax` selector와 Danger 스크립트 골격
- 10주간 합의한 팀 컨벤션을 리뷰 프롬프트 형태로 정리하는 일
- 현재 PR diff 셀프 리뷰와 설계 냄새 후보 제시
- CI 로그의 step 시간 정리와 병목 후보 분석
- 회고 초안의 구조·문장·근거 누락 검토

도구는 Codex, Claude Code, Gemini CLI, 구독 챗봇과 무료 티어 등 자유롭게 선택할 수 있다. 특정
유료 API 결제는 요구사항이 아니며, AI 리뷰를 GitHub Actions에 통합하는 것도 선택이다.

## 선택 또는 과제 밖

- Lighthouse CI는 선택이다. 도입한다면 7주차 측정값을 임계값 근거로 사용하고 변동성에 맞는 실행
  조건을 정한다.
- AI 리뷰의 GitHub Actions 통합은 선택이다. 로컬 도구로 리뷰해도 된다.
- rollback 심화는 선택이며 이번 주 산출물 밖이다.
- Preview/Production URL 확보는 권장되지만 배포 자체는 이번 주 채점 대상이 아니다.

## 단계별 완료조건

### 1단계 완료조건 — CI 측정·최적화

> miss가 됐다. 이 한계는 RFC와 개인 조사 기록에 명시한다.
