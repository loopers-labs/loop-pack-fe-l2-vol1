LOOP PACK · WEEK 10

E2E 조건부 실행 수정 방향

PR에서 바뀐 경로를 먼저 분류하고, 실제로 영향을 받을 가능성이 있는 E2E만 선택한다. 다만 판단할 수 없는 변경이나 판별 실패는 생략하지 않고 전체 E2E로 보낸다.

현재 상태 · 문서-only E2E 생략 검증 완료, 선택 실행 검증 대기

변경 감지 job과 조건부 테스트 선택을 workflow에 반영했고, 필수 결제·주문 조합과 인증 조합을 로컬 Chromium·WebKit에서 통과시켰다. 실제 PR의 경로 분류·step 생략·required check 상태를 확인했으며, PR #13에서 문서-only 변경의 E2E 준비·실행 step 생략도 확인했다. 다음으로 로직 변경의 선택 spec 실행과 알 수 없는 변경의 전체 실행 fallback을 검증한다.

01 · 결정 요약

Quality는 유지하고 E2E만 조건부로 조정한다

실행

JS/TS 로직 변경이면 Chromium과 WebKit에서 order.spec.ts를 항상 실행한다.

추가 실행

변경된 기능의 spec을 결제·주문 테스트에 더한다.

생략

문서-only와 CSS-only 변경에서는 E2E의 설치·build·테스트를 생략한다.

안전 기본값

분류할 수 없거나 판별에 실패하면 전체 E2E를 실행한다.

Quality의 문서·스타일 조건부 분리는 별도 판단으로 보류했다. 이 문서는 E2E의 실행 범위와 required check 표시 문제만 다룬다.

02 · 판별 신호

변경 감지 job이 다음 값을 만든다

paths-filter로 PR의 변경 경로를 읽고, 뒤의 E2E matrix job이 사용할 boolean 신호를 만든다. 신호는 파일 내용을 해석하는 값이 아니라 경로 규칙의 결과다.

changes job의 출력값
값 true가 되는 경우
run_e2e 문서·CSS-only가 아니거나, 분류 실패·미지의 경로가 있는 경우
all 공통 로직, fixture, 설정, lockfile, workflow, 미지의 변경 또는 판별 실패
auth · cart · wishlist · product 각 기능의 소스 또는 대응 spec이 변경된 경우
오타는 경로만으로 판별하지 않는다

.tsx 안의 문구 오타와 동작 로직 변경을 CI가 안전하게 구분할 수 없다. 따라서 JS/TS 파일 변경은 로직 변경 가능성이 있는 것으로 보고 E2E를 실행한다.

03 · 변경 범위 매핑

필수 결제 테스트에 영향 범위를 더한다

현재 정한 E2E 선택 규칙
변경 경로 실행할 spec 판정 이유
인증 로직 또는 auth.spec.ts order.spec.ts + auth.spec.ts + logout.spec.ts 결제 필수 흐름과 인증 회귀를 함께 확인
장바구니 로직 또는 add-to-cart.spec.ts order.spec.ts + add-to-cart.spec.ts 장바구니에서 주문으로 이어지는 흐름 확인
위시리스트 로직 또는 add-to-wishlist.spec.ts order.spec.ts + add-to-wishlist.spec.ts 변경된 위시리스트 동작과 결제 필수 흐름 확인
상품 목록·검색·필터·정렬 로직 order.spec.ts + state-restoration.spec.ts 상품 상태와 URL·스토리지 복원 회귀 확인
공통 로직, fixture, 설정, lockfile, workflow 전체 E2E 영향 범위를 특정하기 어려움
문서-only 또는 CSS-only 생략 브라우저 동작 로직이 바뀌지 않음
분류 불가 또는 판별 실패 전체 E2E 검증 누락보다 실행 비용을 선택하는 안전 기본값

04-A · fallback 수정 계획

감지 실패는 전체 실행으로 복구하고, 테스트 실패는 그대로 중단시킨다

현재 확인한 문제

changes가 실패한 fallback 경로에서는 각 E2E step의 조건이 계속 참이 될 수 있다. 이 상태에서는 checkout이나 설치가 실패해도 뒤의 build와 test가 이어져 최초 실패 원인이 흐려질 수 있다. 반면 UNKNOWN=true를 all=true로 바꾸는 선택 로직은 같은 입력으로 재현했을 때 정상 동작했다.

구현과 검증 순서
순서 수정 계획 판정 가능한 완료 기준
1 두 경로 감지 step의 실패를 scope finalizer가 확인할 수 있게 하고, finalizer는 if: always()로 실행한다. 감지 step 하나를 실패시켜도 finalizer가 실행된다.
2 감지 실패나 비정상·누락 출력은 run_e2e=true, all=true, 빈 test_files로 변환한다. 감지 실패 로그에 fallback 사유와 tests=all이 함께 표시된다.
3 E2E의 무거운 step 조건에서는 감지 job 실패를 직접 우회하는 식을 제거하고, 확정된 run_e2e 출력만 사용한다. checkout 또는 설치가 실패하면 뒤의 build와 test가 실행되지 않는다.
4 Select test scope가 입력 신호와 최종 all·run_e2e·tests를 일반 로그에도 출력하게 한다. 스크립트 원문을 최종 결과로 오해하지 않고 Detect job에서 판정값을 확인한다.
5 정상 분류, unknown, 감지 실패, 중간 step 실패를 각각 검증한다. unknown·감지 실패는 전체 실행되고, docs/style은 생략되며, E2E 준비 실패는 해당 browser job을 실패시킨다.

04-B · fallback 구현 결과 · 2026-09-11

계획을 구현하며 바꾼 것과 그 이유

앞 절 04-A fallback 수정 계획은 그대로 둔다. 이 절은 실제 .github/workflows/e2e.yml에 반영하면서 계획과 달라진 부분만 덧붙인 기록이다.

계획과 구현의 차이
계획(04-A) 구현 바꾼 이유
감지 실패를 changes job 안에서 흡수해 changes outputs를 확정한다. e2e job의 첫 step Finalize E2E scope에서 흡수하고, 이후 step은 steps.scope.outputs.*만 참조한다. changes job이 실패하면 그 job의 outputs 자체가 생성되지 않는다. 같은 job 안에서는 fallback 값을 만들 수 없어 소비하는 쪽으로 옮겼다.
finalizer를 if: always()로 실행한다. finalizer를 if: ${{ !cancelled() }}로 실행한다. 흡수할 대상은 감지 실패이지 실행 취소가 아니다. always()는 취소된 실행에서도 scope를 확정해 뒤 step의 조건 평가를 남긴다.
무거운 step은 확정된 run_e2e 출력만 사용한다. 조건을 !cancelled() && !failure() && steps.scope.outputs.run_e2e == 'true' 로 통일했다. success()를 쓰지 않았다. e2e job이 if: always()라 success()의 평가 범위를 오해하기 쉽다. !failure()는 이 job의 이전 step 실패만 본다는 점을 식에서 드러낸다.
감지 실패를 fallback 조건으로 삼는다. 감지 job이 success인데 run_e2e 출력이 비어 있는 경우도 같은 fallback으로 처리하고, 사유 문구를 두 경우로 나눠 출력한다. step 조건 때문에 Select test scope가 건너뛰어도 job은 success가 된다. 이때 출력이 비면 조용히 전체 스킵이 되므로 막았다.
최종 scope를 일반 로그에 출력한다. run_e2e=false일 때 tests=(skipped)로 표기한다. 실행하지 않는 test_files 초기값을 그대로 찍지 않는다. 스킵된 실행에서 tests=e2e/order.spec.ts가 보이면 실행 목록으로 오해할 수 있다. 이번 문제 자체가 로그 오독에서 시작했다.

아직 Actions에서 확인하지 않은 것

아래는 로컬 재현으로 대신할 수 없는 항목이다. 실제 PR 실행 로그를 보기 전까지 완료로 표시하지 않는다.

  • !failure()가 if: always() job 안에서 이 job의 이전 step 실패만 보는지. 판정 기준은 Checkout을 의도적으로 실패시켰을 때 Set up pnpm 이후가 모두 Skipped이고 해당 browser job이 Failure인지다.
  • 감지 실패 fallback에서 Finalize E2E scope가 실행되고 이후 step이 모두 도는지. 판정 기준은 E2E fallback: 줄과 scope result: all=true, run_e2e=true, tests=all이 함께 남는지다.
  • 두 matrix job이 독립적으로 결과를 내는지. 판정 기준은 한쪽 browser만 실패했을 때 다른 쪽이 Success로 끝나는지다.

04-D · flaky 대응 정책 · 2026-09-11

재료를 남기고, 메시지가 말하게 한 다음, 재시도를 켰다

조사 시점에 문제가 두 겹이었다. 실패가 흔들림인지 진짜인지 구분할 수 없었고, 구분에 필요한 재료조차 남지 않았다. trace는 retain-on-failure로 만들어지지만 job이 끝나면 사라졌고 retries도 설정되어 있지 않았다.

순서를 뒤집으면 감추는 쪽이 된다

재료가 없는 상태에서 재시도부터 켜면 초록불은 빨리 돌아오지만 원인은 계속 모른다. 과제가 말하는 “retry로 실패를 감추는 게 목적이 아니라 흔들림과 진짜 실패를 구분”하는 것과 반대가 된다. 그래서 증거 → 메시지 → 재시도 순으로 넣었다.

적용한 세 가지
순서 내용 위치
1 · 증거 보존 테스트가 실행된 job은 test-results/를 아티팩트로 올린다(7일). 전부 통과하면 trace가 지워져 디렉터리가 비므로 if-no-files-found: ignore로 아티팩트를 만들지 않는다. .github/workflows/e2e.yml
2 · 실패 메시지 상품 목록은 갱신 실패 시 이전 결과를 유지하고 배너만 띄워, 개수 단언이 “로딩 중”과 “갱신 실패”를 구분하지 못했다. 배너 상태를 실패 메시지에 담는다. e2e/fixtures/product-list-assertions.ts
3 · 재시도 retries: process.env.CI ? 2 : 0. 로컬은 0으로 두어 흔들림을 즉시 보고, CI에서만 2회 재시도한다. 재시도로 통과하면 flaky로 보고되고 최초 실패 메시지도 리포트에 남는다. playwright.config.ts

반복 실패는 재시도로 덮지 않는다. 같은 spec이 계속 flaky로 남으면 trace를 근거로 원인을 고치거나 격리 여부를 판단한다.

자가 검증 — PR #19

testInfo.retry === 0일 때만 실패하는 테스트로 flaky를 결정적으로 재현했다. 무작위가 아니라 매번 같은 결과가 나오므로 관찰이 확실하다. 두 브라우저 모두 같은 결과였다.

확인 항목과 결과
항목 결과
재시도 동작 첫 시도 실패 → retry #1 통과 → 1 flaky 표기, job은 Success
아티팩트 업로드 playwright-chromium-attempt1 2.42MB · playwright-webkit-attempt1 2.25MB
첫 실패 trace 보존 아티팩트에 trace.zip(64 files)과 error-context.md가 있고 최초 실패 사유가 들어 있다
이 검증에서 잡은 결함

첫 시도에서는 업로드 조건이 steps.e2e.conclusion == 'failure'였고 아티팩트가 0개였다. 재시도로 통과한 flaky는 step이 success라 조건에 걸리지 않아, 정작 필요한 첫 실패 trace가 버려졌다. 조건을 != 'skipped'로 고친 뒤 위 결과를 얻었다.

정상 실패는 잡고 flaky만 놓치는 형태였다. 결정적 flaky를 만들어 돌리지 않았다면 실제 flaky가 날 때까지 드러나지 않았을 결함이다.

함께 해소된 미확인 항목

retain-on-failure가 재시도로 통과한 경우 첫 실패 시도의 trace를 지우는지 확인하지 못한 상태였다. 지우지 않는 것으로 확인됐다. trace: 'on-first-retry'로 바꿀 필요는 없다.

workflow는 시작하고, matrix job은 화면에 남긴다

06 · 구현 순서

작은 변경부터 차례로 적용한다

  1. changes job을 추가하고 paths-filter를 커밋 SHA로 고정한다.
  2. 기능·spec·fixture·설정 경로를 필터로 선언하고 outputs를 만든다.
  3. E2E matrix job에 needs: changes를 연결한다.
  4. all이면 전체 테스트, 아니면 필수 order와 영향 spec을 선택한다.
  5. 문서·CSS-only에서는 install, browser install, build, test step을 생략한다.
  6. 알 수 없는 변경과 판별 실패의 fallback을 전체 E2E로 연결한다.
  7. 구현 결과와 실제 PR 로그를 RFC에 기록한다.
다음 검증 항목

e2e.yml에 changes job과 조건부 테스트 선택을 추가했다. 로직·fixture·설정 변경이 포함된 PR의 전체 실행과 develop required ruleset, 문서-only PR의 E2E 생략을 확인했다. 다음 PR에서는 기능 로직 변경 시 필수 order와 영향받은 spec만 선택되는지 확인하고, 알 수 없는 경로는 전체 E2E로 fallback되는지 확인한다.

직접 따라 하는 실행 순서

  1. 먼저 변경 파일과 workflow diff를 확인한다. 아직 문서와 코드가 섞여 있다면 이 단계에서 분리한다. 
git status --short
git diff -- .github/workflows/e2e.yml docs/week-10/e2e-conditional-execution.html
pnpm exec prettier --check .github/workflows/e2e.yml docs/week-10/e2e-conditional-execution.html
git diff --check
  1. workflow 변경이 E2E 명령을 깨뜨리지 않았는지 먼저 로컬에서 확인한다. 이 단계는 GitHub의 paths-filter 결과를 검증하는 것이 아니라, 실제로 선택할 spec 조합이 통과하는지 확인하는 단계다. 
pnpm exec playwright test e2e/order.spec.ts --project=chromium --project=webkit
pnpm exec playwright test e2e/order.spec.ts e2e/auth.spec.ts e2e/logout.spec.ts \
  --project=chromium --project=webkit
  1. 로컬 검증이 통과한 뒤 조건부 workflow와 관련 문서를 stage하고, stage된 파일 목록을 다시 확인한다. 
git add .github/workflows/e2e.yml docs/week-10/e2e-conditional-execution.html \
  docs/rfc/week10-ci.md docs/week-10/action-plan.html
git diff --cached --name-only
git commit -m "feat(ci): 변경 범위별 E2E 실행"
git push
  1. GitHub Actions의 Detect E2E scope job을 먼저 연다. 현재 구현 PR에는 .github/workflows/e2e.yml 변경이 포함되어 있으므로 all=true와 전체 E2E 실행이 정상이다.
  2. 이어서 E2E (chromium)과 E2E (webkit)을 각각 연다. 첫 번째 Report selected scope step에서 선택 범위를 확인하고, Run selected E2E tests step의 실제 명령과 테스트 파일을 기록한다.
  3. 현재 PR의 결과를 기록한 뒤, workflow가 반영된 기준 브랜치에서 문서-only PR을 별도로 만든다. 그래야 workflow 파일 변경이 경로 판별에 섞이지 않는다.
정정 · 2026-09-11 · step 이름이 바뀌었다

위 절차와 아래 표의 Report selected scope는 현재 workflow에 없다. fallback 수정 과정에서 Finalize E2E scope로 바뀌었고, 출력 형식도 scope inputs:와 scope result: all=…, run_e2e=…, tests=… 두 줄이 됐다. Actions 로그를 확인할 때는 새 이름으로 찾는다.

이 절 위쪽의 검증 기록에 남은 Report selected scope는 그 시점 로그를 그대로 인용한 것이므로 고치지 않는다.

PR 화면에서 확인할 로그
PR 유형 Report selected scope 기대 결과
문서-only 또는 CSS-only E2E skipped: docs/style-only... 두 browser job은 생성되고 checkout 이후 무거운 step은 Skipped
인증 로직 또는 auth spec all=false와 order·auth·logout 목록 두 브라우저에서 세 spec 조합 실행
fixture·설정·공통 로직 all=true, tests=all 두 브라우저에서 전체 E2E 실행
분류할 수 없는 경로 또는 감지 실패 E2E fallback 또는 all=true 생략하지 않고 전체 E2E 실행

회차마다 남길 값

  • PR URL과 기준 커밋 SHA
  • Detect E2E scope의 filter 결과와 run_e2e·all 값
  • Chromium/WebKit job URL과 전체 job 시간
  • 각 job의 실제 실행 또는 Skipped step, 선택된 spec 목록
  • required check가 성공·실패·대기로 표시됐는지
문서-only·기능별 선택 실행 검증 완료 · fallback 검증 대기

로컬 Playwright 통과, PR #12의 전체 실행·required 표시, PR #13의 문서-only E2E 생략을 확인했고, PR #14·#15에서 order·auth 기능별 선택 spec 실행도 확인했다. 알 수 없는 경로의 전체 실행 fallback을 실제 PR에서 확인하기 전까지 전체 구현 상태는 fallback 검증 대기로 유지한다.

최종 상태 · 2026-09-11 · fallback 검증 완료

위 「fallback 검증 대기」 판정은 당시 기록으로 그대로 둔다. 남아 있던 두 가지를 모두 확인해 대기 상태를 해제한다.

  • 알 수 없는 경로 — PR #16(public/toggle.svg)에서 all=true, run_e2e=true, tests=all, 15개 전체 실행
  • 감지 실패 — PR #17에서 Detect E2E scope가 failure일 때 E2E fallback: 로그와 tests=all, 15개 전체 실행
  • 중간 step 실패 — PR #18에서 Checkout 실패 후 6개 step Skipped, 두 browser job이 각각 독립 Failure

flaky 대응 정책과 그 자가 검증은 04-D에 있다. 실험 PR #17·#18·#19는 머지하지 않는다.
