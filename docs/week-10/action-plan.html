먼저 기존 CI의 시간을 재세요. 그 기록으로 병목을 고친 뒤, 실행 조건과 예산을 붙이고 실제 실패·성공 증거를 모으면 됩니다.

Before·After warm/cold 측정과 병목 비교는 완료했습니다. 캐시 실험의 부분 cold 한계와 최종 전략 판단은 실행 로그와 기록 문서에서 확인합니다.

준비와 기준 버전

지금은 이 네 가지부터

과제 원문: 1단계 · 0단계 Before 고정 (64–107줄)

  1. GitHub에서 Quality와 E2E 측정값 확인하기. Quality 화면에서 quality · 1m 18s, E2E 화면에서 e2e · 2m 26s 카드를 누릅니다. 각 step의 소요 시간과 캐시 관련 문구를 확인하세요.
    확인 이력 · Week 09 PR #181

    Quality는 전체 1분 23초, quality job은 1분 18초였습니다. E2E는 전체 2분 30초, e2e job은 2분 26초였습니다. 둘 다 성공했습니다. 현재 화면만으로는 cold/warm과 병목 step을 판별할 수 없으므로 참고 실행 1회로만 기록합니다.

    추가 확인 이력 · 2026-09-10

    Quality와 E2E 모두 같은 key의 약 197MB pnpm dependency cache를 복원해 pnpm cache 기준 warm이었습니다. 두 실행 모두 Next.js build cache는 없었습니다. 러너는 Ubuntu 24.04.4와 같은 Image 버전을 사용했지만 Azure Region은 달랐습니다. 변경 전 Week 09 참고 실행이므로 새 기준 workflow의 Before 횟수에는 포함하지 않습니다.

    Before warm 측정 완료 · 2026-09-10

    새 기준 workflow의 warm 3회를 완료했습니다. Quality workflow는 57초·55초·53초, E2E workflow는 3분 4초·2분 33초·2분 10초였습니다. 중앙값은 Quality 55초, E2E 2분 33초이며, 상세 URL·job·step·캐시 로그는 CI 측정 기록에 남겼습니다.

    완료 이력 · 2026-09-10

    기준 workflow에서 Quality는 test → lint → typecheck → build를 별도 step으로 실행하고, E2E는 브라우저별 matrix job에서 install → build → Playwright test를 실행하는 것을 확인했습니다. 세부 근거는 CI 측정 기록에 남겼습니다.

  3. 기록할 문서 만들기. docs/rfc/week10-ci.md에 ‘측정 조건 / Before / After / 캐시 / 실행 조건 / 예산 / AI 리뷰 / 규칙 승격 / 질문 답변’ 제목을 준비합니다.
    완료 이력 · 2026-09-10

    docs/rfc/week10-ci.md에 아홉 개 기록 항목과 Before 표를 준비하고, Warm·Cold와 After 측정값·중앙값·범위를 기록했습니다. 최종 비교 결과와 캐시 실험의 한계도 RFC에 남겼습니다.

    진행 이력 · 2026-09-10

    Quality의 test·lint·typecheck·build와 E2E의 브라우저별 install·build·Playwright test를 각각 별도 step으로 나누고, 두 job에 timeout-minutes: 10을 추가했습니다. pnpm verify는 통과했으며, 기준 커밋과 Before/After Actions run 기록을 남겼습니다.

  • 2번 — Quality와 E2E workflow가 실제로 실행하는 package script와 검증 순서를 대조해 완료했습니다.
  • 3번 — CI 측정과 개선 기록에 아홉 개 기록 항목과 Before·After 표를 준비해 완료했습니다.

현재 기준 workflow

Quality는 test · lint · typecheck · build를 별도 step으로 실행합니다. E2E는 Chromium과 WebKit matrix job에서 브라우저 설치와 production build를 각각 수행하고, 변경 경로에 따라 선택된 Playwright spec을 실행합니다. 판별할 수 없는 변경은 전체 E2E로 보냅니다.

측정 판정 결과

E2E workflow 중앙값은 13초 줄어 사전 기준 30초에는 미달했습니다. 다만 느린 브라우저 job은 42초 줄었고 브라우저별 required check를 확보했습니다. 모든 판단은 Before/After 회차별 기록과 캐시 실험 한계를 함께 봅니다.

branch protection 설정 권한과 Actions 실행 가능 여부를 확인했고, develop 대상 merge-required-ci ruleset에 quality, Detect E2E scope, E2E (chromium), E2E (webkit)을 required로 등록했습니다. PR #12 Merge box에서 네 check의 Required 표시와 전체 통과도 확인했습니다. 기존 Preview/Production URL과 7주차 측정 기록의 JS 전송량 근거는 별도 확인 항목으로 남깁니다. 배포 자체는 채점 대상이 아니므로 새 배포 구성에 시간을 먼저 쓰지 않습니다.

다음으로 넘어갈 기준 — 기준 커밋, 측정 대상 workflow, 시간을 재는 시작·종료 지점, cold/warm 구분을 문서에 적었다.

Before 측정

01. Before 6회 측정하기

과제 원문: 0단계 · Before를 고정해요 (68–107줄)

  1. 러너 종류, Node·pnpm 버전, 검증 명령, 캐시 대상과 키, 기준 커밋을 적습니다.
  2. 대상 캐시가 없는 cold 3회와 복원된 warm 3회를 분리해 실행합니다. cold를 반복하는 방법과 warm 캐시를 준비하는 방법도 기록합니다.
  3. 각 실행이 끝날 때 run URL, 전체 경과 시간, step별 시간, 캐시 복원 여부를 바로 남깁니다.
  4. 각 그룹의 원본 값 3개, 중앙값, 최소~최대 범위를 계산하고 가장 긴 구간을 지목합니다.
결정 이력 · 2026-09-10 · cold/warm 재현 방법

실제 개발 흐름에 가까운 방식을 선택했습니다. warm은 캐시가 살아 있는 상태에서 PR 브랜치에 커밋을 밀어 평소와 같이 3회 실행하고, cold는 매 실행 전 gh cache delete로 캐시 축출 상태를 만들어 3회 실행합니다. 저장 직후 re-run으로 warm을 만드는 방법은 실제로 재현되는 조건이 아니라고 보아 채택하지 않았습니다.

트리 변경 없이 실행만 트리거하기 위해 git commit --allow-empty를 쓰고, 기준 커밋 표기는 9859a7c6으로 유지합니다. 삭제만으로 cold라고 적지 않고 실행 로그의 캐시 미복원 문구를 함께 확인합니다. 삭제로 만든 cold는 러너·이미지 버전까지 달라지는 실제 cold와 다르다는 점을 한계로 남깁니다.

측정용 PR의 base는 develop입니다(develop ← feat/week-10). 따라서 cold를 만들 때 지워야 할 캐시 범위는 이 PR, base 브랜치 develop, 기본 브랜치 main 세 곳입니다.

Warm·Cold 각 3회 기록을 마쳤습니다. 별도 cache 실험에서는 matrix job 간 key 공유로 Quality·WebKit miss와 Chromium hit가 섞였으므로 전체 cold로 단정하지 않고 한계로 기록합니다.

개선과 After 측정

02. 병목을 고치고 다시 재기

실행 안내: 병목 개선과 After 측정 순서

과제 원문: 병목 전략·캐시·After 측정 (109–148줄)

  1. 로그에 따라 전략을 고릅니다. 불필요한 Chromium 설치가 크면 제거를, 독립 검증의 직렬 실행이 크면 병렬화를 검토합니다.
  2. 왜 그 전략을 골랐는지, 다른 전략은 왜 넣지 않았는지 적습니다. 같은 검증이 유지되는지 대조합니다.
  3. concurrency는 workflow와 ref를 구분해 다른 브랜치 실행까지 취소하지 않게 검토합니다. 측정 실행끼리 취소되지 않도록 진행합니다.
  4. After cold 3회·warm 3회를 같은 기준으로 재고 Before와 비교합니다.
  5. 별도 실험 변경에서 유효한 lockfile 변경으로 키 miss를 재현합니다. hit/miss 로그와 install 시간을 남긴 뒤 실험 변경을 복구합니다.
측정 조건을 섞지 않기

After까지 끝낸 뒤 조건부 실행과 예산 게이트를 붙이세요. 캐시 miss 실험도 측정용 코드와 구분합니다. lockfile을 임의로 깨서 frozen install 자체가 실패하면 캐시 설치 시간을 비교할 수 없습니다.

직접 판단할 것: 줄어든 시간이 측정 흔들림보다 큰가? 가장 긴 구간의 감소와 연결되는가? 범위가 겹치면 개선을 확정하지 않고 한계를 적습니다.

업데이트 이력 · 2026-09-10 · After 측정 완료

후보 A는 Chromium과 WebKit을 matrix job으로 분리해 각각 required 검증으로 실행했습니다. 브라우저별 설치·build·E2E 시간을 따로 확인할 수 있었고, 검증 범위는 Before와 동일하게 유지했습니다.

After warm·cold 각 3회를 완료했습니다. warm E2E workflow 중앙값은 1분 46초, cold는 2분 20초였습니다. cold 2회차의 첫 시도는 캐시 hit가 확인되어 집계에서 제외하고 재측정했습니다. 원본 값과 step 시간은 RFC After 기록에 남겼습니다. 캐시 실험은 matrix job 간 공유로 부분 cold가 된 한계를 별도로 기록했습니다.

Before와 After의 중앙값·범위 및 PR 전체 wall-clock 비교 결과는 아래 판정 이력에 정리했습니다.

판정 이력 · 2026-09-10

E2E workflow 중앙값은 13초 줄어 사전에 정한 30초 성능 기준에는 미달했습니다. 다만 느린 브라우저 job은 42초 줄었고 브라우저별 실패를 독립 required check로 확인할 수 있어 후보 A는 유지합니다.

Quality 중앙값 증가는 후보 A 대상이 아닌 workflow의 측정 변동으로 분리합니다. 후보 B concurrency는 반복 push를 줄이는 운영 안전장치로 유지하고, 후보 C pnpm store 캐시는 현재 병목 근거가 부족해 보류합니다.

완료 기준 — Before/After 12회 원본 값, 중앙값·범위, hit/miss 로그, 전략 근거, 실험 복구 기록이 있다.

조건부 실행

03. E2E를 언제 돌릴지 정하기

과제 원문: 2단계 · 조건부 실행 설계 (152–200줄)

  1. lint·typecheck·unit은 모든 PR에서 실행하도록 유지합니다.
  2. E2E 실행/스킵 경로를 표로 씁니다. 시작 후보는 ‘문서만 변경하면 스킵’입니다. 소스·의존성·설정·workflow·E2E 변경과 분류 실패 시 동작까지 검토합니다.
  3. required로 둘 check와 조건부 job의 관계를 설계합니다. guard를 둔다면 실행 대상 E2E의 실패·취소는 막고, 의도한 스킵만 통과시켜야 합니다.
  4. 문서만 바꾼 PR과 실행 대상 경로를 바꾼 PR을 각각 만들어 실행·스킵 로그와 required check 상태를 확인합니다.
  5. CI retry 여부와 반복 실패 처리 정책을 1~2줄로 적습니다. retry로 통과해도 최초 실패 증거를 확인합니다.
