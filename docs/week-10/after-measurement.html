LOOP PACK · WEEK 10 · BOTTLENECK

병목에 맞는 변경만 하고
같은 조건으로 다시 재기

Before에서 확인한 가장 긴 구간을 바탕으로 개선 전략을 직접 선택합니다. 선택한 이유와 선택하지 않은 전략의 이유를 적은 뒤, 검증 항목을 유지한 상태에서 warm·cold를 각각 3회 측정하고 범위가 겹치는지까지 보고 개선 여부를 판단합니다.

과제 기준은 10주차 과제 원문, 원본 수치는 CI 측정 기록, 이전 실행 절차는 Before 측정 안내에 있습니다.

지금 할 일

먼저 개선 전략 하나를 확정합니다

  1. 현재 변경 파일을 커밋해 Before 기록을 고정합니다.
  2. 아래 후보 중 Before 병목과 직접 연결되는 전략을 선택하고 근거를 RFC에 적습니다.
  3. workflow를 수정하되 Chromium과 WebKit, build 등 기존 검증을 제거하지 않습니다.
  4. 한 번 실행해 검증 수와 브라우저 범위가 Before와 같은지 확인합니다.
  5. 변경이 확정된 동일 트리에서 After warm 3회와 cold 3회를 측정합니다.
현재 단계의 완료 기준 — 로그로 병목을 지목하고 후보를 비교한 뒤 선택한 전략과 제외한 전략의 이유를 기록했다. 아직 특정 전략을 정답으로 전제하지 않는다.

01 · 전략 결정

후보와 판단 기준

후보 A

브라우저별 E2E job 병렬화

Chromium과 WebKit 검증을 독립 job으로 나누면 두 브라우저의 실행을 겹칠 수 있습니다. Before의 최장 구간과 연결될 수 있지만 install·build가 중복되는 비용을 함께 확인해야 합니다. 실제 채택 여부는 시험 실행 후 판단합니다.

후보 B

concurrency 그룹

연속 push의 낭비는 줄이지만 한 번의 정상 실행 시간은 줄이지 않습니다. 실제로 중복 실행이 쌓였다는 근거가 있을 때 별도 채택합니다.

후보 C

pnpm store 캐시 추가

이미 setup-node 캐시가 있고 cold install도 5~6초였습니다. 현재 병목 근거만으로는 추가하지 않습니다.

현재까지 내린 결정

  • 개선 목표는 GitHub Actions 사용 시간의 합이 아니라 PR 완료 wall-clock 단축입니다.
  • Safari와 같은 WebKit 계열 사용자의 위험도 main 병합 전에 확인해야 하므로 Chromium과 WebKit 검증을 모두 유지합니다.
  • 두 브라우저 job을 각각 required check로 두어 하나라도 실패하면 병합을 막는 방향으로 설계합니다.
  • 브라우저별 job 분리는 실패 브라우저를 명확히 보여주지만 browser 설치와 build가 중복됩니다. 실제 wall-clock 이득은 시험 실행으로 확인합니다.
아직 확인할 가설

Playwright의 브라우저 프로세스와 context는 분리되지만 테스트 계정, 서버, DB 같은 외부 상태는 공유될 수 있습니다. 기존 테스트의 독립성이 병렬 job에서도 유지되는지는 실제 실행 결과로 확인합니다.

RFC에 남길 문장

“Before에서 ___가 중앙값 ___초로 가장 길었기 때문에 ___ 전략을 선택했다. 예상되는 비용은 ___이고, ___는 병목과 직접 연결되지 않아 적용하지 않았다.”처럼 수치와 선택을 연결합니다.

02 · 구현과 1회 검증

측정 전에 동등성을 확인합니다

  1. .github/workflows/e2e.yml을 선택한 전략에 맞게 수정합니다.
  2. Quality의 test·lint·typecheck·build는 그대로 유지합니다.
  3. E2E는 Chromium 15개와 WebKit 15개, 총 30개가 모두 실행돼야 합니다.
  4. production build도 Before와 동일하게 실행돼야 합니다.
  5. 시험 실행의 job 구성, 전체 시간, 중복 install·build 비용을 확인합니다.
  6. 전략을 채택하거나 되돌린 이유를 RFC에 기록한 뒤 최종 변경을 커밋합니다.
# 변경 파일과 커밋 대상 확인
git status --short
git diff -- .github/workflows/e2e.yml .github/workflows/quality.yml

# 기본 검증
pnpm verify
검증을 줄여서 빨라지면 개선이 아닙니다

브라우저 하나를 빼거나 테스트를 생략하거나 build를 제거하지 않습니다. Before와 After의 검증 항목이 달라지면 시간 비교에서 제외합니다.

03 · After 측정

확정된 같은 트리에서 warm 3회, cold 3회

workflow 변경 커밋을 After 기준으로 고정합니다. 이후 빈 커밋만 사용하고, 측정 도중에는 workflow나 lockfile을 바꾸지 않습니다.

현재 진행 상태

후보 A의 After warm 3회와 cold 3회 측정을 완료했습니다. Warm Quality 중앙값은 57초, E2E workflow 중앙값은 1분 46초이며, 느린 브라우저 job의 중앙값은 1분 37초입니다. Cold Quality 중앙값은 1분 9초, E2E workflow 중앙값은 2분 20초이며, 느린 브라우저 job의 중앙값은 1분 42초입니다. 원본 URL·step 시간은 RFC에 기록했고, 첫 cold 2회차 시도는 캐시 hit로 제외했습니다. 별도 캐시 실험에서 Quality·WebKit miss와 Chromium hit를 확인했고, Before/After 비교까지 완료했습니다.

04 · 캐시 자가 검증

After 측정과 분리해 hit/miss를 증명합니다

  1. warm 로그의 복원 키와 install 시간을 캡처합니다.
  2. 별도 실험 커밋에서 유효한 lockfile 변경을 만들어 캐시 키를 바꿉니다.
  3. miss 로그와 install 시간을 캡처합니다.
  4. 실험 변경을 되돌리고 package 파일과 lockfile이 원래 상태인지 확인합니다.
After 6회에 섞지 않습니다

lockfile 변경은 실행 조건을 바꾸므로 After 반복 측정이 끝난 뒤 별도 실험으로 진행합니다. 파일을 임의로 손상시키지 말고 package manager가 만든 유효한 변경만 사용합니다.

검증 실험 결과 · 2026-09-10

lockfile 변경으로 캐시 키를 바꾼 별도 실험을 실행했습니다. 커밋 91cabde2에서 Quality와 E2E workflow를 확인했고, 실험 변경은 커밋 8fe73a0b에서 복구해 실험 전 상태와 동일합니다.

Quality run · E2E run · 상세 기록은 RFC 캐시 검증에 남깁니다.

Quality와 WebKit은 pnpm cache is not found(install 7초·6초)를 확인했지만, Chromium은 다른 job이 저장한 동일 key를 복원해 hit(install 2초)가 됐습니다. 따라서 이 실험은 모든 job이 cold인 결과가 아니라 부분 cold로 분류합니다.

05 · 비교와 판정

중앙값만 보지 않고 범위를 함께 봅니다

  1. warm과 cold 각각 원본 값 3개, 중앙값, 최소~최대 범위를 계산합니다.
  2. Before와 After의 Quality/E2E workflow 시간을 같은 조건끼리 비교합니다.
  3. 최장 step이 실제로 줄었는지 확인합니다.
  4. Before와 After 범위가 크게 겹치면 유의미한 개선으로 단정하지 않습니다.
  5. 병렬화로 늘어난 install·build 비용과 줄어든 wall-clock을 함께 적습니다.
이번 실험의 성공 기준

가장 늦게 끝난 브라우저 job을 기준으로 PR wall-clock 중앙값이 Before E2E 중앙값 2분 33초보다 30초 이상 줄어 약 2분 이하가 되고, After 범위가 Before 범위 2분 10초~3분 4초와 거의 겹치지 않아야 의미 있는 개선으로 판단합니다.

판정 결과 · 2026-09-10

E2E workflow 중앙값은 Before 2분 33초에서 After 2분 20초로 13초 줄어, 목표로 정한 30초 단축에는 미달했습니다. 따라서 PR 전체 wall-clock의 성능 개선은 유의미하다고 확정하지 않습니다.

대신 느린 브라우저 job 중앙값은 2분 24초에서 1분 42초로 42초 줄었고, Chromium과 WebKit을 독립 required check로 확인할 수 있게 됐습니다. 후보 A는 이 구조적·안전성 개선 때문에 유지하며, 후보 C pnpm store 캐시는 보류합니다.

완료 기준 — Before/After cold·warm 원본 값과 중앙값·범위, 병목 근거, 전략 선택 이유, cache hit/miss 및 install 시간, 실험 복구 기록이 모두 있다.
