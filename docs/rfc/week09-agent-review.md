# 9주차 Advanced B. 에이전트 생성 테스트 검수

## 실행 기록

Playwright agent scaffold는 아래 명령으로 만들었다. 과제 문서에는 `npx`가 나와
있지만, 이 저장소는 `pnpm`만 사용하기로 했으므로 `pnpm exec`를 사용했다.

```bash
pnpm exec playwright init-agents --loop codex --project chromium --prompts
```

이 명령은 Codex용 Playwright agent 설정과 기본 프롬프트를 만든다. 함께 생긴
`e2e/seed.spec.ts`는 테스트 생성을 시작하기 위한 예시 파일이다. 다만 현재
Playwright 설정에서는 `e2e/*.spec.ts`가 실제 실행 대상이다. seed 파일도 그대로
두면 E2E suite에 포함될 수 있었다.

기본 프롬프트는 `add to cart` 예시를 기준으로 되어 있었다. 그대로 쓰면 3단계에서
정한 E2E 범위 밖의 테스트가 늘어날 수 있다. 그래서 9주차 범위에 맞춰 인증
플로우와 주문 플로우만 요청했다. 자동 생성된 테스트를 바로 붙이지 않고, planner와
generator가 만든 결과를 `specs/` 아래에 보관한 뒤 내가 4단계에서 작성한 E2E와
비교했다.

## 생성 산출물

| 파일                              | 역할                                    |
| --------------------------------- | --------------------------------------- |
| `specs/week09-agent-plan.md`      | planner가 만든 E2E 후보 계획            |
| `specs/week09-agent-generated.md` | generator가 만든 테스트 후보 코드       |
| `.codex/agents/*`                 | Playwright agent 실행 설정              |
| `.codex/prompts/*`                | 9주차 범위에 맞춰 다듬은 agent 프롬프트 |

`.codex/`에는 에이전트 실행 설정을 두고, `specs/`에는 에이전트가 낸 계획과 후보
코드를 보관했다. `e2e/`는 실제로 실행되는 테스트만 두는 위치로 구분했다.
`e2e/seed.spec.ts`도 함께 생성됐지만 커밋하지 않았다. 빈 seed 테스트가 실제
Playwright suite에 포함되면 3단계에서 정하지 않은 테스트가 하나 늘어나기 때문이다.

## 내 테스트와 생성 후보 비교

| 항목                    | 에이전트 후보                    | 최종 반영                   | 판단 |
| ----------------------- | -------------------------------- | --------------------------- | ---- |
| 초기 HTML 로그인 상태   | `/order` JavaScript off 검증     | `/order`, `/orders` 검증    | 유지 |
| 미로그인 보호 경로 복원 | `/order` redirect 후 로그인 복원 | 동일                        | 유지 |
| 잘못된 자격 증명        | 틀린 비밀번호 실패 메시지 확인   | 동일                        | 유지 |
| 세션 만료 경계          | `expired` 쿠키로 `/orders` 확인  | 동일                        | 유지 |
| 보호 API 401            | 후보에는 없음                    | `/api/orders` 401 모달 확인 | 보강 |
| 주문 플로우             | 상품 담기부터 주문 내역 확인     | 동일                        | 유지 |
| 상품 탐색 단독          | 후보에 없음                      | 추가하지 않음               | 제외 |
| 위시리스트 단독         | 후보에 없음                      | 추가하지 않음               | 제외 |

에이전트가 만든 후보는 큰 방향에서 3단계 결정과 맞았다. 다만 보호 API가 401을
응답했을 때 현재 화면을 유지하고 로그인 안내 모달을 보여주는 경계는 빠져 있었다.
이 부분은 1단계의 "세션 만료 처리 위치를 한 곳으로 정한다"는 요구와 직접 연결되어
있어서 수동 테스트에 남겼다.

## 지운 단언과 이유

| 생성 후보의 단언/구조           | 최종 처리                 | 이유                                                                                                                         |
| ------------------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 상품 목록 heading 확인          | 별도 단언으로 늘리지 않음 | 주문 플로우의 목적은 상품 탐색 검증이 아니라 구매 전환 확인이다. 상품 목록 준비 여부는 첫 장바구니 버튼으로 충분히 확인한다. |
| 단계별 주석                     | 실제 E2E에는 넣지 않음    | trace와 테스트 이름으로 흐름을 읽을 수 있어 주석을 반복할 필요가 없다.                                                       |
| `newStoredLoginPage` helper     | 쓰지 않음                 | 현재 파일 안의 context 생성 코드가 더 짧고, 재사용 지점도 많지 않다.                                                         |
| `appURL()` helper               | 쓰지 않음                 | Playwright `baseURL`을 이미 쓰고 있어 상대 경로로 충분하다.                                                                  |
| `try/finally` context 정리 패턴 | 일부만 참고               | 수동으로 만든 context는 닫되, 후보 구조 전체를 그대로 가져오지는 않았다.                                                     |

생성 후보를 그대로 붙이지 않은 이유는 이미 작성한 `e2e/auth.spec.ts`,
`e2e/checkout.spec.ts`가 같은 사실을 더 적은 코드로 검증하고 있었기 때문이다.
Advanced B의 목적도 테스트 수를 늘리는 데 있지 않다. 에이전트가 만든 테스트가 내가
정한 E2E 범위와 같은 판단을 하는지 검수하는 쪽에 더 가깝다고 봤다.

## healer를 쓰지 않은 이유

healer는 쓰지 않았다. 이번 과제에서는 에이전트가 만든 테스트를 자동으로 고쳐
통과시키는 것보다, 어떤 단언을 남기고 어떤 단언을 버릴지 직접 판단하는 일이 더
중요했다.

특히 E2E는 3단계에서 정한 범위 밖으로 늘리면 안 된다. healer가 실패한 테스트를
통과시키는 과정에서 selector나 단언을 바꾸면, 내가 의도한 사용자 관찰 결과가 흐려질
수 있다고 판단했다.

## 결론

에이전트가 제안한 인증 플로우와 주문 플로우는 최종 E2E 범위와 대부분 일치했다.
그래서 새 테스트 파일을 추가하지 않았다. 기존 수동 테스트가 같은 경계를 더 짧게
검증하고 있었기 때문이다.

추가로 남긴 판단은 두 가지다.

- 보호 API 401은 생성 후보에 없었지만 세션 만료 처리 위치 검증에 필요해 유지한다.
- 상품 탐색, 담기 단독, 위시리스트 단독 플로우는 3단계에서 제외했으므로 생성 후보가 있더라도
  E2E로 추가하지 않는다.
