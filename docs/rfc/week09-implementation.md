# Week 09 인증·계측·E2E 구현 RFC

## 문서 역할

이 문서는 9주차 전체 작업의 결정과 진행 순서를 설명하는 본문 RFC다.
E2E 범위와 실행 증거는
[E2E 범위 부록](./week09-e2e-scope.md)을 단일 기준으로 사용한다.

| 항목           | 값                            |
| -------------- | ----------------------------- |
| 상태           | 검증 완료                     |
| 현재 단계      | 최종 품질 게이트 통과         |
| 본문 목표 분량 | 330 LOC 전후                  |
| 본문 최대 분량 | 400 LOC                       |
| 과제 명세      | `docs/assignments/week-09.md` |

## 운영 원칙

각 Stage는 다음 순서로 진행한다.

1. 현재 코드와 선택지를 설명한다.
2. 사용자 소유 결정을 확정한다.
3. 이 RFC의 `미결정`을 실제 결정으로 교체한다.
4. 실패 테스트를 먼저 작성하고 최소 구현으로 통과시킨다.
5. 관련 테스트와 실제 사용 표면을 검증한다.
6. 예상 결과를 검증된 결과로 교체한다.
7. 완료 조건을 확인한 뒤 다음 Stage로 이동한다.

이 문서는 작업 일지가 아니다. 최종 결정과 변경 이유만 유지하고, 긴 명령
출력이나 E2E 분석표는 부록 또는 생성된 artifact를 가리킨다.

### Git 체크포인트

각 Stage는 완료 조건과 사용자 확인을 통과한 뒤 atomic commit으로 닫는다. 다음
Stage의 변경을 같은 커밋에 섞지 않는다. Stage 내부 변경이 지나치게 크면 검증
가능한 하위 커밋으로 나눌 수 있지만, 다음 Stage에는 마지막 체크포인트 커밋
이후에만 진입한다.

- Stage 0: 두 RFC 골격과 운영 규칙
- Stage 1: 인증 구현과 검증 결과
- Stage 2: 계측 구현과 부록 A
- Stage 3: 부록 B·C와 E2E 범위 결정
- Stage 4: 승인된 E2E와 부록 D
- Stage 5: 실험을 모두 원복한 최종 코드와 부록 E

Stage 5에서 의도적으로 망가뜨린 중간 상태는 커밋하지 않는다.

## 상태 규칙

| 상태      | 의미                                        |
| --------- | ------------------------------------------- |
| 초안      | 구조만 있으며 결정이 열려 있다              |
| 결정      | 사용자 확인을 거쳐 구현 계약이 확정됐다     |
| 구현 중   | 확정된 계약을 테스트 우선으로 구현하고 있다 |
| 검증 완료 | 완료 조건과 실제 사용 검증을 통과했다       |

## 범위와 불변 조건

### 포함

- 로그인·로그아웃과 서버 초기 인증 상태
- 보호 경로와 안전한 원래 경로 복원
- 중앙화된 세션 만료 처리
- 사용자 행동 이벤트 계측
- 시드 로그 기반 E2E 범위 결정
- RFC에서 승인된 E2E 구현
- E2E 가치 확인을 위한 세 가지 이상 자가 검증

### 변경하지 않을 조건

- `src/app` App Router와 제공된 인증·주문 API를 유지한다.
- 8주차의 Node·jsdom·MSW·production Playwright 경계를 유지한다.
- E2E 범위와 단언은 사용자가 직접 결정한다.
- RFC에 없는 E2E 시나리오는 추가하지 않는다.
- 고정 시간 대기, 비활성화된 테스트, 기능 스냅샷 대체를 허용하지 않는다.
- Basic Stage 1~5를 완료하기 전 Advanced를 시작하지 않는다.

## 기준선

상세 기준선은 Stage 1 시작 전에 실제 명령으로 다시 확인한다.

- 제공됨: 인증·주문 Route Handler, 시나리오 노브, 이벤트 로거, 시드 로그
- 확인 필요: 현재 테스트 수와 결과, production Route 목록, E2E 기준 결과
- 구현 필요: 인증 UI, 보호 화면, 계측 연결, E2E 범위와 테스트

## Stage 1 — 인증

상태: **검증 완료**

### 목표

로그인 상태가 초기 HTML부터 일관되게 보이고, 미로그인·만료·로그아웃 경계에서
사용자가 다음 행동을 알 수 있게 한다.

### 사용자 결정

| 결정                           | 상태                                                  | 선택 근거                                                         |
| ------------------------------ | ----------------------------------------------------- | ----------------------------------------------------------------- |
| 보호 경로 범위                 | `/checkout`·`/orders`와 하위 경로                     | 개인 주문 기능인 과제 필수 범위만 보호                            |
| proxy 쿠키 검증 깊이           | 비어 있지 않은 `session` 쿠키 존재 확인               | proxy는 빠른 진입 차단만 맡기고 서버·API가 서명과 만료를 검증     |
| 안전한 복원 경로 규칙          | 단일 `next` query와 보호 경로 allowlist               | `/checkout`·`/orders` 계열만 query를 보존하고 나머지는 `/`로 대체 |
| 세션 만료 처리 위치            | React Query의 중앙 QueryCache·MutationCache 오류 경계 | `requiresAuth` 요청의 401만 만료로 분류해 로그인 실패와 구분      |
| 로그아웃 시 cart·wishlist 정책 | 둘 다 유지하고 cart는 주문 성공 시에만 비움           | 현재 두 상태는 사용자 ID가 없는 기기 소유 `localStorage`          |

`/`와 `/products`는 공개한다. 현재 별도 화면이 없는 cart·wishlist·mypage는
보호 범위와 이번 주 신규 화면 범위에서 제외한다.

### 작업 순서

1. 기준선과 기존 인증 계약을 다시 확인한다.
2. 인증 응답과 복원 경로 정책을 테스트로 고정한다.
3. 인증 모델과 API 경계를 구현한다.
4. 로그인 UI와 서버 초기 인증 상태를 연결한다.
5. 보호 화면과 proxy를 구현한다.
6. 중앙 세션 만료와 로그아웃 정책을 연결한다.
7. 통합 테스트, build, production 서버에서 검증한다.

### 완료 조건

- 미로그인 보호 경로가 로그인으로 이동한다.
- 로그인 후 안전하게 원래 경로로 돌아온다.
- 외부 복원 경로를 허용하지 않는다.
- 초기 HTML에 로그인 상태가 반영된다.
- 만료와 로그아웃 후 다음 행동이 명확하다.
- 인증·주문 API가 production Route 목록에 존재한다.

### 검증 결과

- 구현 커밋:
  - `5a368bdb` — browser storage와 DOM test harness
  - `77fcbf03` — auth domain, server session, proxy
  - `59cc95bc` — AuthProvider, login·logout UI, 초기 session 연결
  - `5eed380b` — checkout·orders, Header, responsive empty state
- `pnpm check`: 54 files, 377 tests와 lint·typecheck·build 통과
- `pnpm format:check`: 전체 파일 통과
- build Route: 인증 API 3개, 주문 API, `/login`, `/checkout`, `/orders`,
  Proxy 확인
- production 익명 `/orders?status=open`: 원래 query를 담아 로그인으로 307
- 잘못된 자격 증명: 401과 form alert, 보호 경로 복원 없음
- 로그인 성공: httpOnly 쿠키와 초기 HTML의 `루퍼1` 확인 후 원래 경로 복원
- `expired` cookie: 대기 없이 만료 안내가 있는 로그인으로 307
- 주문 생성·목록·로그아웃: 각각 201·200·204와 쿠키 제거 확인
- production session 서명은 `AUTH_SESSION_SECRET`이 없으면 실패하고 테스트와
  Playwright에만 별도 전용 키를 명시
- axe WCAG A·AA: login·checkout·orders 모두 위반 0, 미확인 0
- desktop·mobile 시각·기능 독립 검수: 6/6 PASS

## Stage 3 — E2E 범위 결정

상태: **결정**

### 목표

이벤트 빈도뿐 아니라 이탈과 실패 비용을 근거로 E2E 포함·제외 범위를 결정한다.

### 작업 순서

1. 부록 B에서 노이즈·중복·오류 처리 기준을 결정한다.
2. 이벤트 수가 아닌 고유 세션 기준으로 집계한다.
3. 필터 전후 순위와 이탈·실패 비용을 설명한다.
4. 사용자가 부록 C에서 인증 외 최대 2개 시나리오를 결정한다.
5. 사용자가 포함 시나리오의 단언과 제외 근거를 확정한다.

### 사용자 결정

| 결정      | 상태                                                                                        | 단일 기준 |
| --------- | ------------------------------------------------------------------------------------------- | --------- |
| 정제 기준 | 봇 486세션 제외, 중복 77행 병합, `client_error`는 비용 판단에만 사용                        | 부록 B    |
| 집계 단위 | 고유 세션 7,514. 이벤트 수 기준과 순위가 같음을 확인                                        | 부록 B    |
| 추가 E2E  | 2개. 구매 완료(서버 경계)와 장바구니 지속성(저장소 경계)                                    | 부록 C    |
| 제외 근거 | 빈도 1위 목록 탐색과 60.5% URL 상태는 회복이 쉬워 제외. 주문 실패는 통합 테스트가 이미 단언 | 부록 C    |

빈도와 실패 비용이 어긋난다. 목록 탐색은 100% 세션에서 발생하지만 새로고침으로
회복되고, 주문은 5.6%에서만 발생하면서 시작한 33.9%가 완료 없이 끝난다.

### 완료 조건

- 부록 A~C가 완성됐다.
- E2E 구현자가 추가 범위 판단을 할 필요가 없다.
- E2E 코드보다 부록을 먼저 확정할 수 있다.

## Stage 4 — E2E 구현

상태: **검증 완료**

### 목표

부록 C에 포함된 시나리오만 production build 위에서 결정적으로 검증한다.

### 작업 순서

1. worker별 계정과 storageState 격리를 설계한다.
2. 로그인 자체 테스트는 인증 상태를 재사용하지 않는다.
3. 원래 경로 복원·만료·잘못된 자격 증명을 구현한다.
4. 부록 C에서 선택한 추가 시나리오만 구현한다.
5. workers 1·4와 3회 반복 결과를 비교한다.
6. 실패 trace를 직접 열고 부록 D에 기록한다.

### 완료 조건

- RFC 밖 E2E가 없다.
- 시간 기반 대기가 없다.
- workers 수와 반복 횟수에 따라 결과가 달라지지 않는다.
- trace에서 실패 지점을 설명할 수 있다.

### 검증 기록

- 구현 커밋: `27a9bf36`(인증 3개), `9c9f0591`(추가 2개),
  `71095649`(계정 배정 교정), `c054433f`(worker별 storageState 재사용)
- 부록 C가 정한 3개 범위만 추가했고 기존 `home`·`product-list` 스펙은 이전 주차
  자산이다
- `--workers=1·4·8` 각각 14 passed, `--repeat-each=3`은 1·4 모두 42 passed
- 교정 전 `--workers=4 --repeat-each=3`에서 1건 실패. `workerIndex`가 worker 재시작마다
  증가해 계정 8개를 넘었고, `parallelIndex`로 바꿔 해결했다
- 만료 단언을 일부러 무력화해 trace로 실패 지점을 확인하고 원복했다

## Stage 5 — E2E 가치 확인

상태: **검증 완료**

### 목표

E2E가 통합 테스트만으로 잡을 수 없는 회귀를 실제로 탐지하는지 확인한다.

### 작업 순서

1. 제품 코드 한 곳만 바꾸는 실험을 세 가지 이상 설계한다.
2. 테스트 코드는 수정하지 않고 통합 테스트와 E2E를 실행한다.
3. 잡힘·생존과 첫 유용한 실패 메시지를 기록한다.
4. 매 실험 후 제품 코드를 원복하고 diff를 확인한다.
5. 부록 E에서 E2E 유지 여부를 다시 판단한다.

### 완료 조건

- 세 가지 이상 실험 결과가 있다.
- E2E만 탐지한 항목이 최소 하나 있다.
- 살아남은 변경의 원인과 대응이 기록돼 있다.
- 실험용 변경이 최종 코드에 남아 있지 않다.

### 검증 기록

- 로그인 페이지의 복원 경로 전달과 checkout의 만료 사유 전달을 각각 제거했을 때
  관련 통합 테스트는 47개·17개가 통과했지만 해당 E2E가 실패했다.
- proxy 세션 조건을 반전했을 때 proxy 테스트 2개와 보호 경로 E2E가 함께 실패했다.
- 세 실험 모두 테스트 코드는 바꾸지 않았고, 제품 코드 한 곳만 변경한 뒤 원복했다.
- 인증 플로우 3개는 빈 컨텍스트를 유지하고, 추가 E2E 2개만 worker별 storageState를
  재사용하도록 경계를 조정했다.

### 7주차 성능 경계 재확인

root layout에서 쿠키를 읽어 초기 HTML에 인증 상태를 넣으므로 build의 `/`·`/products`
등 기존 route도 정적 생성 대신 dynamic rendering이 된다. 초기 인증 HTML을 모든
화면의 Header에 일관되게 제공하기 위해 이 범위 변화를 수용하되, 7주차의 실제
사용자 기준인 semantic shell·Hero LCP·CLS가 깨지는지는 production Chrome에서
다시 측정했다.

`/?scenario=slow`를 Chrome stable의 PerformanceObserver로 desktop·mobile 각각 5회
측정했다. 이 값은 7주차 Lighthouse 13.3 simulated 값과 도구가 달라 직접 통계 비교는
하지 않고, 7주차 supporting observed LCP median `1725ms`와 같은 브라우저 관측
계열의 회귀 신호로만 사용한다.

| viewport | TTFB median | FCP median | LCP raw (ms)                 | LCP median | CLS |
| -------- | ----------: | ---------: | ---------------------------- | ---------: | --: |
| desktop  |       7.2ms |       44ms | 1748, 1564, 1560, 1560, 1564 |     1564ms |   0 |
| mobile   |       4.4ms |       48ms | 1648, 1548, 1564, 1564, 1568 |     1564ms |   0 |

slow API가 끝나기 전에 FCP가 발생하고 CLS는 0이며, LCP median도 기존 supporting
관측치보다 높아지지 않았다. 따라서 정적 생성 범위는 줄었지만 이번 로컬 production
측정에서는 7주차 semantic shell·LCP·CLS의 observable regression을 확인하지 못했다.
