# 8주차 — 테스트 검증 계획 (1단계 설계)

> - 이 문서는 AI 보조로 작성했다.
> - AI로 검증 항목들에 대한 파일 위치를 확인 -> 15개 항목 표를 직접 작성 -> AI에게 피드백 -> 검토의 순서로 작성했다.
> - 표를 작성하며 든 의문들에 대한 결정은 AI를 통한 꼬리질문과 대화로 내렸고, 이를 문서에 반영하였다.

---

## 0. 이 문서의 범위

- 2단계에서 **무엇을, 어떻게 검증할지**를 먼저 정한다. **테스트 코드는 이 단계에서 쓰지 않는다** (`week-08.md:121`).
- 커버리지 숫자가 아니라 **"무엇을 지킬 것인가, 그것이 깨지면 무엇을 알게 되는가"**를 고정한다.
- 방법론(단위/통합/E2E)은 **검증 범위**로 정한다 — 실행 환경(node vs jsdom)과 헷갈리지 않는다 (`docs/rfc/week08-environment.md` 참고).

## 2. 항목 3 — 순수 로직 선택 이유 (직접 선정, 2개)

공통 방법론 이유: 둘 다 DOM·네트워크 없이 검증 가능한 순수 매핑 함수라 **단위**로 검증된다.

---

### 2.1 `buildQueryString` (`fetcher.ts:12-24`)

```ts
const buildQueryString = (query?: FetcherOptions['query']): string => {
  if (!query) {
    return '';
  }
  const params = new URLSearchParams();
  for (const [key, value] of Object.entries(query)) {
    if (value !== undefined) {
      params.set(key, String(value));
    }
  }
  const qs = params.toString();
  return qs ? `?${qs}` : '';
};
```

**왜 이것을 골랐는가:**

1. **모든 API 요청 URL이 이 함수 하나를 거쳐 만들어진다.** `apiFetch`(`fetcher.ts:48`)가 이 앱의 유일한 fetch 통로이고, 그 안에서 URL을 조립하는 건 `buildQueryString` 하나뿐이다. 즉 이 함수는 **모든 API 요청이 지나가는 단일 목(chokepoint)**이라 결함의 폭발 반경이 넓다.
2. **undefined 처리와 빈 입력 처리라는 진짜 분기가 있다.** "undefined 값을 스킵한다" / "빈 쿼리는 빈 문자열을 반환한다" / "`?` prefix를 붙인다"는 세 분기를 가져 결함 표면이 진짜이다.
3. **깨지면 넓은 범위가 망가진다.** undefined 스킵이 깨지면 URL에 `?category=undefined`가 박혀 서버가 문자열 "undefined"를 받고 — 필터 오작동, 400 에러, 빈 목록 등 **여러 화면이 동시에 broken**된다.

**검증 시 주의 (분기별로 구체적으로):**

- **undefined 스킵**: undefined 값을 넣었을 때 URL에 `?key=undefined`가 **안** 박히는가
- **빈 입력**: `undefined`나 `{}`를 넣었을 때 빈 문자열이 반환되는가 (`?`만 붙지 않게)
- **정상 케이스**: 값이 있을 때 `?key=value&key2=value2` 형태가 되는가

---

### 2.2 `getFailureReason` (`ProductList.tsx:20-24`)

```ts
const getFailureReason = (error: unknown): string => {
  if (error instanceof ApiError) return error.message;
  if (error instanceof TypeError) return '네트워크 연결을 확인해 주세요.';
  return '상품을 불러오지 못했습니다.';
};
```

**왜 이것을 골랐는가:**

1. **분기가 3개라 결함 표면이 진짜이다.** `isCategoryValue`/`isSortValue` 같은 단순 리터럴 체크(`Array.some`)는 분기가 없어 테스트가 잡을 게 없지만, 이 함수는 들어온 에러 타입에 따라 갈라지는 의미있는 의사결정을 한다.
2. **`TypeError → 네트워크 안내` 매핑은 `fetch`의 브라우저 동작에 의존한다.** 브라우저 `fetch`는 네트워크 단절 시 `TypeError`를 던진다. 이 매핑이 틀리면 사용자가 "네트워크 연결을 확인해 주세요" 대신 모호한 "상품을 불러오지 못했습니다"만 보게 돼 원인을 유추할 수 없다.
3. **사용자에게 직접 보이는 메시지를 만드는 마지막 단계다.** `buildQueryString`이 캐시 정합성에 영향을 미치는 것과 달리, 이 함수의 출력은 화면에 그대로 노출되므로 결함이 사용자에게 즉시 가시적이다.

**검증 시 주의 — 분기 선택 vs 메시지 문구:**

단언은 **"어떤 분기를 탔는가"**에 맞추고, 메시지 문구 자체를 스냅샷처럼 검사하지 않는다. 문구는 UX 카피라 자주 바뀌고, 문구가 바뀐다고 해서 결함이 아니다. 분기 선택(예: `TypeError`를 넣었을 때 "네트워크" 안내가 나오는가)이 깨지면 그게 결함이다.

---

> ⚠️ **2단계 메모 (공통):** 두 함수 모두 현재 **export되어 있지 않다** (`buildQueryString`은 `fetcher.ts`, `getFailureReason`은 `ProductList.tsx`에서 모듈 내부 전용). 단위로 검증하려면 export 추가 또는 `shared/lib/` 별도 파일로 추출해야 한다. 이 리팩터는 2단계에서 한다.

## 3. 애매했던 판단 2개(직접 선정)

### 판단 1 — 항목 8·9·10을 통합으로 할까, E2E로 할까

**배경:** "카테고리/정렬/페이지 변경 → 목록 변경"은 사용자가 조작하면 화면이 바뀌는 **연속된 흐름**이다. 그래서 처음엔 "연속 동작이니 E2E"로 보았다. 하지만 어느 쪽도 가능해 보여 애매했다.

**왜 통합을 골랐는가:** 이 항목들의 핵심은 **"목록이 올바르게 바뀌는가"**(정확한 상품 id, 순서, 개수)이지 **"실제 주소창이 바뀌는가"**가 아니었다. URL 반영은 **항목 11이 맡고 있어서**, 8·9·10이 그것까지 검증하면 **11번과 중복**이 생긴다. 통합(MSW + nuqs adapter)은 상태→데이터→렌더를 결정적이고 빠르게 검증할 수 있고, 카테고리별/정렬별로 정확한 상품을 MSW로 제어할 수 있어 상세 단언이 쉽다.

**다른 쪽(E2E)을 골랐다면 달라졌을 점:** 같은 흐름을 항목 11과 중복 검증하게 된다. 게다가 E2E는 느리므로, 이 패턴으로 비슷한 항목(8·9·10)을 전부 E2E로 보내면 `pnpm test:e2e`가 비대해져 개발 피드백이 느려진다. 핵심 원칙은 **"각 항목이 검증하는 층이 겹치지 않게"**였고, 이 원칙이 통합 선택을 이끌었다.

> 핵심 통찰: **"URL"이라는 단어에 반응해 E2E로 가는 함정**을 피했다. nuqs URL 상태는 `NuqsTestingAdapter`로 통합에서 재현 가능하고, 실제 주소창 동작만 E2E 영역이다.

### 판단 2 — 항목 15를 별도 E2E로 둘까, 4+12로 흡수할까

**배경:** "목록 진입 → 담기 → 헤더 확인"은 4(진입/로딩)와 12(담기→헤더)의 합처럼 보여, "행위가 겹치니 15를 흡수시켜도 되지 않을까"가 합리적인 대안이었다. 실제로 흡수 쪽으로까지 검토했었다.

**왜 별도 E2E로 두었는가:** 핵심은 **12와 15를 같은 층으로 비교하면 중복이지만, 층이 다르면 잡는 결함이 다르다**는 점이었다:

1. **12는 통합(jsdom), 15는 E2E(실제 브라우저 + production build)다.** 같은 행위를 봐도 잡는 결함 클래스가 다르다 — 12는 wiring(toggle→store→selector→Header)을, 15는 전체 조립·hydration·런타임 에러를 잡는다.
2. **15의 `page.goto`는 풀 로드라 hydration이 범위에 들어온다.** 공유 URL/북마크로 진입하는 사용자 시나리오에서 SSR ↔ hydration 불일치를 잡을 수 있는 건 15뿐이다. (전형적인 홈→Link 여정은 hydration이 없지만, 풀 로드 진입도 실제 사용자 경로다.)
3. **"A works + B works ≠ A→B works."** 4와 12가 각각 통과해도, 전체 여정을 한 번에 돌렸을 때만 드러나는 조립 결함이 존재할 수 있다. 이 코드베이스에서 가능한 구체적 사례 3가지:

   | 결함                                                                                                                                                                                                    | item 12 (통합) | item 4 (통합) | item 15 (E2E) |
   | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- | ------------- | ------------- |
   | **Header가 페이지에서 빠짐** — 리팩터 시 `<Header/>`를 `ProductList`에서 실수로 제거. 12는 Header를 **직접 렌더**하니 페이지에 있든 없든 통과                                                           | ❌             | ❌            | ✅            |
   | **hydration으로 헤더 개수 틀림** — persist 복구 타이밍에 `hasHydrated` 처리가 깨지면, 사용자가 담기 누른 시점에 localStorage값이 안 반영되어 count가 0부터 시작. jsdom엔 SSR/hydration 단계 자체가 없음 | ❌             | ❌            | ✅            |
   | **Provider가 production에서 빠짐** — `layout.tsx`에서 `QueryProvider`/`NuqsAdapter`를 실수로 제거. 통합은 테스트가 **직접 provider를 세팅**하니 페이지에 있든 없든 통과                                 | ❌             | ❌            | ✅            |

   공통 패턴: **통합은 "내가 직접 조립한 환경"을 검증**해서 조립 누락·플랫폼 단계를 내가 세팅하니 결함이 안 보임. **E2E는 "진짜 앱이 스스로 조립한 결과"를 검증**해서 조립 누락·플랫폼 결함이 그대로 드러남. 매일 일어나진 않지만 **리팩터·설정 변경 때** 잡히고, 이 코드베이스가 이미 `cart-wishlist.spec.ts:103`에서 hydration 안전성을 따로 검증하는 것도 같은 우려의 증거다.

**다른 쪽(4+12로 흡수)을 골랐다면 달라졌을 점:** E2E 한 건이 줄어 `pnpm test:e2e`는 빨라지지만, **production build에서의 조립·hydration 검증이 사라진다.** 행위 수준의 중복 제거는 얻지만, 층 수준의 검증 다양성을 잃는다. 비용(느린 E2E 1건)보다 이익(층이 다른 결함 1종 추가)이 크다고 판단해 별도 유지를 택했다.

> 핵심 통찰: **"행위가 겹친다"와 "중복이다"는 다르다.** 같은 층에서 같은 결함을 잡을 때만 중복이다. 12(통합)와 15(E2E)는 층이 달라 잡는 결함이 다르므로 둘 다 둔다.

## 4. 목록 밖 — 다음에 할 것(AI 활용) / 앞으로도 안 할 것(직접 선정)

### 다음에 하면 좋겠다 — `useProductList`의 prefetch 로직 (`useProductList.ts:15-19`)

```ts
useEffect(() => {
  if (page >= totalPages) return;
  const nextQuery = { ...query, page: page + 1 };
  queryClient.prefetchQuery(productQueries.list(nextQuery));
});
```

**근거:**

- **변경 빈도: 중간.** 페이지네이션 전략(어디까지 미리 가져올지, placeholderData 정책)을 바꿀 때마다 이 로직이 손된다.
- **실패 비용: 중간.** 깨지면 "다음 페이지" 클릭 시 로딩이 길어져 사용자가 멈칫한다. 치명적이진 않지만 UX 직결.
- **판단:** 변경 빈도 × 실패 비용 둘 다 중간이라 ROI가 양수. 다음 주기에 단위(페이지 → 다음 페이지 쿼리 생성) + 통합(prefetch hit 확인)으로 검증할 가치가 있다.

### 앞으로도 안 하겠다 — `isCategoryValue` / `isSortValue` 타입 가드 (`useProductListFilters.ts:38-42`)

```ts
export const isCategoryValue = (value: string): value is CategoryValue =>
  CATEGORIES.some((candidate) => candidate === value);
```

**근거:**

- **변경 빈도: 낮다.** 카테고리 종류가 바뀔 때만(거의 안 바뀜) 손된다.
- **실패 비용: 거의 0.** 본체가 `Array.some`이라 깨질 결함 표면이 없고, 이미 TypeScript가 `CATEGORIES` 리터럴을 잡는다. 설령 가드가 고장 나도 **호출부의 행위 테스트**(`useProductListFilters.test.tsx:77` — "리터럴에 없는 category/sort는 기본값으로 떨어진다")가 잡는다.
- **판단:** 독자 단위 테스트는 유지비만 낳고 잡는 결함이 없다. **"행위를 테스트하고 구현 원시 요소는 테스트하지 않는다"**는 원칙에 따라 안 한다.

> 과제가 금지하는 "전부 다" 계획이 아님을 밝힌다: 15개 항목은 전부 다루되 12·15는 층(통합/E2E)을 나눠 역할 분담시켰고(섹션 3 판단 2), 목록 밖에서는 안 하겠다는 것을 명시했다.
