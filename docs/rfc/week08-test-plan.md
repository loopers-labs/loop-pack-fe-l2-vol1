# Week8 테스트 계획

## 테스트 레벨 분류 기준

- 유틸 함수·순수 로직처럼 입력 출력만 보려 하는 경우에는 **단위 테스트**
- 컴포넌트+상태+API가 얽혀 사용자가 이걸 하면 이게 보이는가 보려 하는 경우 **통합 테스트**
- 전체 사용자 플로우를 확인하고 싶을 경우 **E2E**

| 7 | 에러에서 재시도로 복구 | 통합 | 재시도로 복구되는지는 응답이 실패에서 성공으로 바뀌고 사용자가 버튼을 누르는 흐름이라 화면으로만 확인되므로 통합으로 판단. | 복구할 수 있는 상황에서 재시도 버튼을 클릭해도 복구되지 않는다 |

| 9 | 정렬 변경 → 순서 변경 | 통합 | 정렬을 바꾸면 화면 순서가 달라지는지는 내부 정렬 함수 호출이 아니라 사용자가 보는 순서로 확인해야 하므로 통합으로 판단. | 정렬을 바꿔도 화면 순서가 그대로. |
| 10 | 페이지 이동 → 목록 변경 | 통합 | 페이지 조작이 목록 교체로 이어지는지는 조작·네트워크·화면이 얽혀야 드러나므로 통합으로 판단. | 페이지를 눌러도 목록이 그대로거나 엉뚱한 페이지가 뜬다. |
| 11 | 조작이 URL 반영 · URL로 재진입 | E2E | 조작이 주소창에 실리고 그 URL로 재진입해 화면이 복원되는지는 실제 주소창·실제 로드에서 이어 확인하는 게 확실하다. 반영만 jsdom 통합으로 뗄 수도 있지만 재진입도 같이 확인해야 하니 한 흐름으로 묶어 E2E로 판단 [애매판단 B](#b-11번-url-반영재진입---통합-vs-e2e) | URL과 화면 상태가 어긋난다 (필터를 바꿨는데 주소가 안 바뀌거나, 그 주소로 들어오면 필터가 초기화됨) |
| 12 | 담기 → 헤더 개수 · 다시 누르면 빠짐 | 통합 | 담기 버튼과 헤더 배지의 연결은 화면으로만 드러나 렌더가 필요하므로 통합으로 판단. (기존에 만들어 둔 테스트로, 배지 숫자를 getByTestId를 이용하여 가져오고 있는 상태이므로 제거할 예정.) | 담아도 헤더 숫자가 안 오른다, 또는 다시 눌러도 안 빠진다. |
| 13 | 뒤로·앞으로 가기로 필터 복원 | E2E | 뒤로/앞으로는 브라우저 히스토리 내비게이션이고, 이 앱에선 popstate 와 Next 라우터, nuqs 재동기화가 함께 도는 동작이다. jsdom 에는 진짜 내비게이션·라우터가 없어 이 조합을 실제처럼 재현하지 못하므로, jsdom 에서 통과해도 브라우저에서 필터가 복원되는지는 알 수 없기 때문에 E2E로 판단 | 뒤로·앞으로 가기 시 필터가 유지되지 않음. |
| 14 | 새로고침해도 필터 상태가 유지 | E2E | reload 후 URL 파싱과 화면 복원은 실제 문서 재로드라야 검증되므로 E2E로 판단. | 새로고침하면 필터가 초기화된다 |
| 15 | 목록 진입 → 담기 → 헤더 확인 | E2E | 목록 로드부터 담기·헤더 반영까지 이어지는 부분은 사용자 전체 플로우 확인이라고 판단하여 E2E 선택 | 사용자의 카트 담기 플로우에 문제가 있다 |

## 세 번째 항목 직접 선택

### buildProductListSearchParams

- 부수효과 없는 순수 함수이고, 이 함수가 조립한 `URLSearchParams` 가 그대로 서버 요청이 된다. 분기가 여러 개다. 빈 `q` 는 아예 빼고, `q` 는 trim 하고, `category=all` 은 "필터 없음"이라 생략하고, 나머지는 기본값을 채운다. 이 규칙 하나만 어긋나도 서버에 잘못된 조회 조건이 나가 목록 전체가 원하는 결과와 다를 가능성이 생김.

### buildProductListTitle

- 검색어·카테고리·페이지·빈결과 4갈래를 조합해 문서 제목을 만드는 순수 함수다. 서버 `generateMetadata` 와 클라이언트 `document.title` 이 같은 규칙을 쓰게 하기 위해 만든 함수. 이 규칙이 어긋나면 탭 제목·OG 공유 카드가 실제 조회 결과와 달라진다.

### isServerError

- 네트워크 단절·5xx 만 첫 로드 에러 경계로 넘기고 4xx 는 화면 안에서 다루게 하기 위해 5xx 에러 또는 네트워크 에러인지 체크하는 함수. 이게 표의 6번(5xx 는 경계 화면 / 4xx 는 인라인)의 분기 규칙 그 자체. 6번은 통합으로 "그 화면이 뜨는가"를 보고, 여기선 단위로 "5xx·네트워크·4xx 를 옳게 구분하는가"를 본다.

## 2. 애매했던 판단

### A. 1번 개수 파생 - 단위 vs 통합

**단위로 결정** 개수가 store 상태에서 제대로 파생되느냐는 순수 로직이라 생각했고, 배지까지 렌더해 보는 경로는 12번(담기 → 헤더 숫자 증가·원복)·15번(목록 → 담기 → 헤더 반영)이 테스트를 해주기 때문.

**통합으로 올렸다면**: hydration 전 placeholder("–") → 복원 후 실제 개수로 바뀌는 부분까지 사용자 관점으로 볼 수 있었다. 그러나 검증 대상인 개수 파생보다 더 넓은 범위이고, 이 검증은 12, 15와 겹친다고 판단.

### B. 11번 URL 반영/재진입 - 통합 vs E2E

**E2E 로 통일** 조작이 주소창에 실리는 반영만 떼면 jsdom 통합에서 빠르게 볼 수 있다. 하지만 "그 URL로 재진입해 복원"은 실제 로드라야 믿을 수 있어 E2E 가 필요하다고 판단했다. 조작 → URL 반영 → 재진입은 사용자의 한 연속 흐름이다. 반영을 통합으로 따로 두면 E2E 재진입 테스트가 그 반영 단계를 어차피 다시 거쳐 중복되고, 어디까지 통합이고 어디부터 E2E인지 경계도 흐려진다. 그래서 11은 반영/재진입을 E2E 하나로 결정.

**반영을 통합으로 쪼갰다면**: 조작 직후 `window.location.search` 로 URL 반영을 빠르게 잡아 E2E 부담을 조금 덜었을 것이다. 하지만 URL 반영/재진입을 검증할 때 통합과 E2E로 jsdom과 실 브라우저로 검증 방식이 갈려서 신빙성이 떨어진다.

## 3. 이 목록 밖은 어떻게 할지

### 다음에는 하면 좋겠다 
1. 홈→목록 prefetch로 이어지는 초기 진입 통합 테스트
  - 홈에서 목록으로 넘어갈 때 `buildDefaultProductListQuery` 로 만든 prefetch key 가 목록 페이지의 `resolveProductListQuery` 결과와 일치해야 "상품 목록 클릭 즉시 캐시 hit"이 성립한다. 이게 어긋나면 초기 진입에서 중복 요청이 조용히 난다. 다만 다시 생각해보니 애초에 두 개의 함수로 따로 나뉘어진 게 잘못이 아닐까 싶기도 하여 이번 테스트에 포함하지 않음.

2. 배지 개수를 testid 없이 role·text 로 가져오기
- 12번은 기존에 추가했던 테스트인데, 헤더 배지 숫자를 `getByTestId("cart-count")` 로 가져오게 만들었다. `cart-count` testid 는 사용자에겐 쓸모없고 오직 테스트를 위해 마크업에 붙인 코드다. 테스트가 앱에 맞춘 게 아니라 앱이 테스트에 코드를 얹은 셈이라, 다음엔 사용자에게도 쓸모 있는 접근성 이름(role·text)으로 짚어 이 군더더기를 없앤다.


### 앞으로도 안 하겠다
1. 스타일, 클래스 같은 표현 세부
- 색상, `className` 같은 표현 세부는 **변경 빈도 높음(디자인 조정마다 바뀜) · 실패 비용 낮음(사용자의 동작은 문제 없음)**. 이걸 테스트로 넣으면 리팩터·디자인 변경마다 무의미하게 실패하여 테스트를 오히려 방해한다.
