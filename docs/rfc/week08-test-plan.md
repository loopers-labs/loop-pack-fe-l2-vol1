## 2. 애매했던 판단 둘

### 판단 A — 2번(URL 조건 → query key): E2E vs 단위

처음에는 E2E로 봤다. 실제 URL에서 query key가 제대로 뽑히는지 확인해야 한다고 생각했기 때문이다.

단위로 내린 이유는 URL 문자열에서 query key가 나오는 데까지가 순수 함수여서다. `loadProductListConditions`는 `createLoader`로 만들어져 렌더가 필요 없고, URL 문자열만 넣으면 key까지 나온다.

```
'?q=%20%20의자%20%20&category=home&sort=popular&page=3'
  → ["products","list",{"q":"의자","category":"home","sort":"popular","scenario":null,"page":3,"pageSize":12}]
```

그리고 여기서 봐야 할 것은 케이스 수다. 기본값, 앞뒤 공백이 붙은 검색어, 알 수 없는 카테고리·정렬, 범위를 벗어난 `page` 같은 조합을 하나씩 훑어야 한다. 단위는 이걸 싸게 반복할 수 있다.

단위에서 케이스를 촘촘히 보면 E2E는 흐름만 확인하면 된다. 실제 주소로 들어갔을 때 그 조건의 데이터가 화면에 보이는지만 보면 되고, 그건 11번이 맡는다.

E2E로 갔다면 케이스마다 페이지를 새로 열어야 한다. 그리고 실패했을 때 파서가 잘못됐는지 화면이 잘못됐는지 구분되지 않는다.

### 판단 B — 8·9·10(조건 변경 → 목록 변경): E2E vs 통합

셋 다 E2E로 고민했다. 실제 동작에서는 필터 변경, 정렬 변경, 페이지 변경이 모두 URL을 바꾸는 작업이다. 그러면 이 흐름 전체를 실제 라우팅 위에서 봐야 하는 것 아닌가 싶었다.

두 대안을 비교해봤다.


|     | E2E                                                          | 통합                                                     |
| --- | ------------------------------------------------------------ | ------------------------------------------------------ |
| 장점  | 조작부터 URL 변경, 네트워크 요청, 화면 반영까지 실제 경로 그대로 본다.                  | 조건 변경 → 어댑터 → MSW → 렌더 흐름을 빠르게 반복한다. 더 다양한 케이스를 보기 쉽다. |
| 단점  | 같은 경로를 세 번 확인한다. 테스트마다 페이지를 새로 열어야 한다. 통합 테스트와 비교해 상대적으로 느리다 | URL 층이 어댑터로 대체된다. 주소가 실제로 바뀌는지는 보지 못한다                 |


**통합으로 정했다.** 먼저 이 흐름이 통합에서 재현되는지 확인했다. nuqs 테스트 어댑터로 조건 변경을 흉내낼 수 있어서, 카테고리를 바꾸면 새 요청이 나가고 화면도 그 응답으로 바뀐다.

세 항목은 setter가 하는 일이 조금씩 다르다. 카테고리·정렬은 `page`를 1로 되돌리고, 페이지는 `scroll: true`를 쓴다. 그래도 nuqs 어댑터부터 렌더까지는 같은 경로를 지난다. 이 구간을 세 번 실제 라우팅으로 확인할 필요는 없다고 봤다. 비용 차이도 크다. 통합은 파일당 jsdom 260-800ms에 MSW 150-180ms가 붙는 정도지만, E2E는 실행당 빌드 6초에 테스트마다 페이지 로드가 얹힌다.

어댑터가 대신한 URL 층은 11번이 E2E로 한 번 지나가는 것으로 확인한다. 두 조각이 각각 맞다고 이어붙인 것도 맞다는 보장은 없어서, 이건 감수한 위험으로 남아 관련 E2E 테스트를 추가하면 보강할 수 있다.

## 3. 이 목록 밖

### 다음에는 하면 좋겠다 — 상품 검색(`q`)

15개 항목은 조건 중 카테고리·정렬·페이지만 다루고 검색은 빠져 있다. 코드로는 검색어를 제출하는 `ProductSearchForm`, 검색어를 다듬는 `normalizeSearchQuery`, 검색하면 `page`를 1로 되돌리는 규칙이다.

- **변경 빈도**: 낮다. 입력을 다듬고 정규화하는 게 전부라 손댈 일이 거의 없다.
- **실패 비용**: 크다. `normalizeSearchQuery`는 `trim()`과 `normalize('NFC')`를 한다. 한글은 입력기에 따라 자모가 분리된 형태로 들어오는데, 이 정규화가 서버와 브라우저에서 갈라지면 눈에는 같은 검색어인데 서로 다른 캐시를 쓴다. `page` 되돌리기가 빠지면 3페이지에서 검색했을 때 결과가 없는 페이지가 열린다.

변경 빈도가 낮은데도 꼽은 이유는 두 실패 모두 **화면이 멀쩡해 보이기** 때문이다. 자주 바뀌지 않는 대신 한 번 어긋나면 오래 모른 채로 남는다. 그래서 안전장치로 하나 두는 편이 낫다고 봤다.

### 앞으로도 안 하겠다 — CSS 클래스와 스타일

화면이 의도한 대로 보이는지. 클래스가 제대로 붙는지, 레이아웃이 깨지지 않는지.

- **변경 빈도**: 높다. 스타일은 이 코드베이스에서 가장 자주 손대는 부분이다.
- **실패 비용**: 작다. 레이아웃이 깨지면 화면에서 바로 보인다.

자주 바뀌는데도 안 하겠다는 이유는 셋이다.

먼저 세 방법론 어디에도 맞지 않는다. 단위는 대상이 아니다. 통합은 테스트를 써도 통과가 아무것도 보장하지 못한다. jsdom에는 스타일이 적용되지 않아 보이는지 아닌지를 판정할 수 없고, CSS Module은 프록시라 CSS에서 이미 지운 클래스를 단언해도 그대로 통과한다. E2E는 스타일이 실제로 적용되지만, 의도대로 보이는지를 단언으로 옮기려면 색이나 위치를 숫자로 박아야 한다. 눈으로 볼 것을 숫자로 옮겨 적는 셈이라 유지 비용만 남는다.

다음으로 테스트가 변경을 막는 비용이 된다. 가장 자주 손대는 부분을 단언으로 고정하면 화면을 바꿀 때마다 테스트를 같이 고쳐야 한다.

마지막으로 눈으로 확인하는 쪽이 싸다. 깨지면 화면을 여는 순간 드러난다. 여러 곳에서 재사용하는 공통 컴포넌트의 스타일이라면 Storybook 같은 시각 회귀 도구가 맡을 일이지, 단위·통합·E2E가 할 일은 아니다.
