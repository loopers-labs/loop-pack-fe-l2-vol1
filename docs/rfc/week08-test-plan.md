# RFC: Week 08 — 테스트 설계: 무엇을 어느 층에서 지킬 것인가

브랜치 `feat/week-08` · 상태: 2단계 구현·3단계 실험 완료 · 작성 2026-08-21

**이 문서의 구성** — §1~§5는 1단계 설계(테스트 코드보다 먼저 커밋됨). 부록 A(3단계 실험 기록)와 부록 B(구현 중 설계 이탈 기록)는 구현·검증 후 추가된 실측 기록이다.

커버리지 숫자가 아니라 **지키기로 한 동작**을 고정한다. 검증 항목 15개를 단위·통합·E2E에 배치하고 근거를 남긴다. 이 문서는 테스트 코드보다 먼저 커밋한다(과제 규칙). 2단계(구현)와 3단계(자가 검증)는 §5의 계획을 그대로 따른다.

**빨리 훑을 때** — 배치표 §2.3, 애매했던 판단 2개 §2.4, 목록 밖 취사선택 §2.5, 공개 동작의 정의 §4, 2·3단계 계획 §5.

## 1. R — Requirements

**지킬 것** — 과제 제공 14개 + 직접 고른 순수 로직 1건(§2.2 — `buildTitle`·`buildDescription`). 15개 전부 이번 주에 구현한다.

**출발점(0단계, 커밋 완료)** — 이 설계는 아래 인프라 위에 선다. 여기서 정한 경계가 §2.3 배치의 전제다.

| 인프라          | 내용                                                                                                                    |
| --------------- | ----------------------------------------------------------------------------------------------------------------------- |
| vitest projects | `node`(기존 5개 + 새 단위) / `dom`(jsdom) 분리. DOM 테스트는 `*.dom.test.tsx` 파일 컨벤션                               |
| MSW             | `setup.dom.ts`에서 `onUnhandledRequest: "error"` — 그물 밖 요청은 조용히 나가지 못한다. 기본 핸들러는 성공 경로만       |
| render 헬퍼     | `renderWithProviders` — 테스트마다 새 `QueryClient({ retry: false })` + `NuqsTestingAdapter(searchParams, onUrlUpdate)` |
| 격리            | `afterEach`: `server.resetHandlers()` · `cleanup()` · cart/wishlist 스토어 리셋                                         |
| E2E             | Playwright chromium, `webServer: pnpm start`(production build 위). `pnpm check`의 마지막 단계                           |

**제약** — 기존 node 테스트 5개 불변 / 단위는 DOM 없이 통과해야 함 / 통합의 네트워크는 MSW로만 가로챔(HTTP 클라이언트 바꿔치기 금지) / E2E는 조건 기반 대기만 / 항목마다 정상 + 경계 케이스.

**하지 않을 것** — 커버리지 목표, 스냅샷 검증, 테스트를 위한 기능 변경. 특히 새로고침 시 찜·담기 초기화는 persist 미사용의 의도된 결과이므로 "지키기로 한 스펙"으로 고정한다(§2.3 15번 경계).

## 2. A — Architecture: 배치와 근거

### 2.1 배치 기준

검증하려는 **사실이 어느 층에 사는가**로 정한다.

1. 사실이 **함수의 입출력**이면 단위. 렌더가 필요했다면 배치가 틀린 것이다.
2. 사실이 **여러 층의 협업**(useQuery 상태 머신 ↔ 컴포넌트 분기 ↔ URL 어댑터 ↔ 스토어 구독)이어야만 성립하면 통합. jsdom + MSW로 재현 가능한 범위까지가 통합의 영토다.
3. 사실이 **브라우저 소유**(히스토리 스택, 진짜 reload, 서버 렌더 → hydration 전 경로)면 E2E. production build + mock 500ms 고정 지연 위라 회당 비용이 가장 크다 — 여기서만 지킬 수 있는 것만 올린다.

같은 항목이 두 층에 걸치면 **아래층으로 최대한 내리고, 위층에는 아래층이 못 보는 사실만 남긴다**. 11·12(통합)와 13·14·15(E2E)의 분담이 이 규칙의 적용례다(§2.4).

### 2.2 순수 로직 선택 — `buildTitle` · `buildDescription`

후보 3개를 두 질문으로 비교했다 — "**15개 그물에 이미 걸리는가**"(회귀가 다른 항목의 빨간불로 관찰될 수 있는가), "**내가 쓴 분기가 얼마나 있는가**"(테스트가 지키는 게 내 로직인가 라이브러리인가).

| 후보                              | 그물 밖인가                                                                                                                                                                                                            | 분기 밀도                                                                                                    | 결정     |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | -------- |
| ⓐ `parseAsPositiveInteger`        | 아니오 — 11번(재진입)이 파싱 결과를 select 값·목록으로 단언하고, 13·14번도 서버 렌더의 `loadProductSearchParams`를 지나며 URL·화면 단언에 걸린다                                                                       | `"0"`·`"-3"`·`"abc"`→null, `"1.5"`→1(parseInt) 등 풍부                                                       | 기각     |
| ⓑ `serializeProductsUrl`          | 예 — canonical 직렬화는 metadata 전용 경로                                                                                                                                                                             | 낮음 — nuqs `createSerializer` 설정 한 줄이라 지키는 건 대부분 라이브러리 동작                               | 기각     |
| ⓒ `buildTitle`·`buildDescription` | **예 — 어떤 테스트도 결과를 단언하지 못한다.** E2E가 production 서버에서 `generateMetadata`를 실행하긴 하지만 title·description 단언이 없고, `page.tsx`의 try/catch가 예외까지 삼켜 **크래시조차 빨간불이 될 수 없다** | trim, `page >= 2` 접미사, 카테고리 id→이름 해석과 fallback, 정렬 라벨 fallback, `totalCount === 0` 문구 분기 | **채택** |

잘못돼도 화면 기능은 멀쩡하고 검색엔진·공유 카드에만 노출되는 로직이라 **사람이 가장 늦게 발견하는 종류의 회귀**다 — 테스트가 아니면 지킬 수 없는 스펙이라는 점이 채택의 핵심 근거다.

**추출 선행** — 두 함수는 현재 `src/app/products/page.tsx`의 모듈 프라이빗이다. `src/_pages/products/lib/metadata.ts`로 옮기고 슬라이스 index에 공개한 뒤 page가 import한다(app→`_pages`는 index로만 진입 — 6주차 딥 임포트 차단 규칙). app 레이어는 라우팅 전용이고 이 함수들은 `ProductSearchState`와 응답 계약을 아는 페이지 소유 로직이라, 테스트를 떠나서도 자리가 lib이 맞다. 동작 보존 이동이며 2단계 단위 테스트 커밋에 선행한다.

| 15  | 목록 진입 → 담기 → 헤더 확인               | E2E    | 핵심 사용자 여정의 스모크(조작은 12번과 같이 찜 버튼 기준). production build 위에서 서버 렌더 → hydration → 스토어 → 헤더의 전 스택을 관통한다. 경계: 새로고침하면 0으로 복귀 — persist 미사용도 지키기로 한 스펙(§1)                                                                                                                                                                | 12번(jsdom)이 초록인데 여기만 빨간불이면 jsdom이 못 보는 구간 — production 번들·서버 렌더→hydration 전환 — 이 깨진 것. 배포를 막아야 하는 신호 |

### 2.4 애매했던 판단 2개

**① 11번 — 통합인가 E2E인가.** "URL"이라는 단어가 주소창을 연상시켜 13·14와 같은 E2E 묶음으로 보내고 싶어지는 항목이다. 그러나 이 항목이 고정하려는 사실은 주소창이 아니라 **컴포넌트 조작과 URL 문자열 사이의 계약**이다 — 반영 방향(카테고리 변경 → `category=casual` + `page` 리셋 직렬화, 기본값 생략)과 재진입 방향(`?category=casual&sort=price-desc` → 파싱 → select 값·목록 초기 상태. ⚠ `casual&page=2` 같은 조합은 금물 — casual은 5개뿐이라 어떤 pageSize에서도 2페이지가 없어 "존재하지 않는 페이지" placeholder가 뜬다). 이 양방향을 `NuqsTestingAdapter`가 `onUrlUpdate`와 `searchParams`로 그대로 재현하므로 통합으로 내렸다. 브라우저만 소유한 사실 — 히스토리 스택(뒤로·앞으로), reload + 서버 렌더 — 은 이 계약 밖이고, 정확히 13·14번의 자리다. 반대로 11번까지 전부 E2E로 몰았다면: production build + 500ms 고정 지연 위에서 경계 케이스(기본값 생략, 재진입 시 select 값·목록 일치)를 늘릴 때마다 회당 비용이 쌓이고 13·14와 시나리오가 중복된다. 통합 선택으로 잃는 것도 있다 — 테스트 어댑터와 진짜 주소창의 간극(nuqs 자체 결함)은 통합이 못 잡는다. 그 리스크는 13·14가 실제 주소창을 한 번씩 지나가며 상쇄한다.

**② 1번 단위와 12번 통합 — 같은 "개수"를 두 번 지키는 게 아닌가.** 겹쳐 보이지만 두 테스트가 고정하는 사실이 다르다. 단위(1번)는 **전이 규칙**(같은 id 두 번 → 제거, 다른 id 두 개 → 2)과 **참조 교체 계약**(toggle 후 `ids`는 이전과 다른 Set)을 지킨다. 특히 참조 계약은 현재 소비처가 전부 원시값 셀렉터(`ids.size`, `ids.has(id)`)라서 **직접 변경으로 깨뜨려도 화면에는 증상이 없다** — Set 자체를 구독하는 미래 소비처가 생기는 순간 터지는 시한폭탄이고, 이걸 단언할 수 있는 층은 단위뿐이다. 통합(12번)은 **구독·표시 경로**를 지킨다 — 스토어가 완벽해도 헤더 셀렉터가 `ids.size`를 읽지 않으면(고정값 렌더, cart↔wishlist 스왑) 단위는 전부 통과한다. 단위를 빼면 참조 계약이 무방비가 되고 실패 시 원인 폭(스토어인가 구독인가 렌더인가)이 넓어지며, 통합을 빼면 "스토어는 맞는데 화면이 틀린" 회귀에 무방비가 된다. 둘은 중복이 아니라 원인 축의 분담이다.

### 2.5 목록 밖 취사선택

**다음에는 할 것 — `ProductSearchInput`의 디바운스·flush·IME 처리** (`src/_pages/products/ui/product-search-input.tsx`). commit·cancel 레퍼런스 관리, Enter의 `flush()`, `isComposing` 가드, 외부 value 동기화(`lastCommittedRef`)가 얽힌 실제로 복잡한 로직인데 이번 15개는 이 경로를 지나지 않는다(8·9·11 모두 select 조작으로 설계했고, E2E도 검색어 타이핑이 없다). 변경 빈도 — 검색 UX는 요구가 자주 바뀌고 타이머·ref가 얽혀 있어 회귀가 잦은 영역. 실패 비용 — 검색이 아예 안 되거나 한글 조합 중 커밋되면 IME 사용자 전원이 겪는다. fake timer가 필요해 대기 규칙(§5.2)이 다른 별도 파일이 되므로 이번 범위에서 제외하고 다음 순번 1위로 둔다.

**앞으로도 안 할 것 — `Placeholder`·`ToggleButton` 단독 렌더 테스트** (`src/shared/ui/`). props를 그대로 그리는 표시 전용 공통 컴포넌트다. 변경 빈도 — 6주차 이후 무변경. 실패 비용 — 틀리면 이들을 실사용 맥락에서 지나는 통합 5·6·12번이 즉시 빨간불이 된다. 단독으로 테스트하면 "렌더된다" 수준의 보장 없는 단언이 되기 쉽고, 프로젝트 규칙상 공통 컴포넌트는 비즈니스 로직을 갖지 않으므로 지킬 분기 자체가 없다.

## 3. D — Data: 모킹 경계와 픽스처

**경계 원칙** — 모킹은 HTTP 한 곳에서만 한다. 앱 코드(`fetchCommerceApi`)는 무수정으로 실제 fetch를 발사하고 MSW가 가로챈다. 스토어·컴포넌트·URL 어댑터는 실물을 쓴다.

| 실물                                  | 테스트에서의 대체물                                                                              | 근거                                                                                                            |
| ------------------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| 네트워크(`/api/products`·`/api/home`) | 통합: MSW. 기본 핸들러는 성공만, 빈·에러·1회 실패는 **그 테스트 안에서** `server.use` 오버라이드 | 예외 상태가 파일 기본값이 되면 다른 테스트가 오염된다. `onUnhandledRequest: "error"`로 그물 밖 요청은 즉시 실패 |

## 4. I — Interface: 공개 동작의 정의

무엇이 공개 동작이고 무엇이 구현 세부인지 — 층마다 계약이 다르다.

**단위의 공개 계약** — export된 함수의 입출력. queryKey는 내부 배열 모양이 아니라 **동등성**만 계약이다(같은 조건 → deep equal, 다른 조건 → 다른 키). 예외 하나: `ids`의 참조 교체는 내부 구현처럼 보이지만 zustand 구독 알림의 전제 계약이므로 단언한다 — 근거는 §2.4-②, 검증은 §5.3 실험 2.

**통합의 공개 계약** — 접근성 트리(role·label·텍스트)와 URL 문자열. 아래 실측 표의 속성만으로 15개가 커버되므로 `getByTestId`는 필요 없다고 예측한다 — 쓰게 되면 왜 다른 방법이 안 됐는지 기록한다(과제 규칙).

**구현 세부(단언 금지)** — 컴포넌트 내부 state·훅 호출 여부, queryFn 호출 횟수, 스토어 셀렉터 함수의 모양, CSS 클래스(`week05-*`), 스켈레톤 내부 구조.

### 5.2 대기·격리 규칙

- **통합 파일의 비동기 대기는 첫 전환 1회가 원칙** — `await screen.findByText(/총 \d+개/)` 이후는 동기 `getBy*`로 단언한다. 모든 검증을 `waitFor`로 감싸지 않는다(과제 규칙). 상호작용 후 목록 교체처럼 새 요청이 발생하는 지점만 `findBy*`를 추가한다.
- **격리** — 단위는 팩토리로 새 인스턴스를 만들고 전역 스토어를 import하지 않는다. 통합은 0단계 `afterEach`(핸들러·DOM·스토어 리셋)와 테스트별 새 QueryClient가 담당한다. 파일 단독 실행과 순서 변경에 결과가 무관해야 한다.
- **E2E** — `sleep`/`waitForTimeout` 금지. `expect(page).toHaveURL/toHaveText`의 자동 재시도가 mock 500ms 지연을 흡수한다.

| E2E    | `header-actions.tsx`        | wishlistCount ↔ cartCount 스왑              | **12번(통합)이 먼저·싸게 잡고** 15번(E2E)도 잡는다 — 목적은 층별 그물 비교와 실패 메시지의 원인 추정력 기록. E2E만의 그물 증명은 위의 push→replace가 담당 |

실험마다 기록: 망가뜨린 곳 / 어떻게 / 잡힘·살아남음 / 실패한 테스트 이름 / 실패 메시지만 보고 원인을 알 수 있었나. 살아남은 변형은 테스트를 보강하고 이유를 남긴다.

사전 분석에서 걸러낸 변형 하나 — `product-list-results.tsx`의 `Math.max(1, …)` 제거는 **equivalent mutant**다: `Math.max`가 효력을 갖는 유일한 입력은 `totalCount === 0`인데 그 경우 빈 결과 분기가 먼저 렌더돼 `totalPages`가 화면 어디에도 쓰이지 않는다. 어떤 테스트도 못 잡는 게 정상이므로 실험 대상이 아니라 §5.4의 "죽일 수 없는 변형" 기록 예시로 둔다.

### 5.4 Advanced — Stryker (선택)

`@stryker-mutator/core` + `@stryker-mutator/vitest-runner`를 쓰되 **mutate 범위를 단위로 분류한 3파일로 한정**한다(`create-selection-store.ts`, `queries.ts`, `metadata.ts`). 통합이 걸리는 컴포넌트를 넣으면 변형 × DOM 렌더의 곱으로 실행이 끝나지 않는다 — 이것이 범위 한정의 근거다. 살아남은 변형 중 의미 있는 것 2개 이상 보강, 못 죽이는 변형(equivalent mutant)은 이유 기록(§5.3에서 사전 식별한 `Math.max` 사례가 첫 항목), 실행 시간과 상시 사용 여부 판단까지 남기면 완료.

**관찰 1 — 살아남은 변형은 0이지만, "쉬운 곳만 골랐다"는 뜻이 아니다.** 실험 2에서 참조 단언 하나를 빼고 보면 **나머지 78개 중 77개(12번 통합 포함)가 전부 통과**했다. 현재 소비처가 전부 원시값 셀렉터(`ids.size`·`ids.has`)라 zustand가 병합 객체를 새로 만들어 항상 notify하고, 셀렉터 결과(원시값)가 달라져 리렌더까지 정상 동작하기 때문이다 — §2.4-②의 예측이 실측으로 증명됐다. 이 변형은 Set 자체를 구독하는 소비처가 생기는 순간 터지는 시한폭탄이고, 설계 단계에서 선제한 참조 단언이 유일한 그물이었다. "살아남을 변형"을 구현 전에 찾아 단언을 심어둔 사례로 기록한다.

**관찰 2 — equivalent mutant는 사전 분석으로 걸렀다.** `Math.max(1, …)` 제거(§5.3 하단)는 실험 전에 관찰 불가능함을 논증하고 제외했다. Advanced에서 Stryker가 같은 변형을 만들어 살아남는지로 이 판정을 교차 확인한다.

**관찰 3 — 실패 메시지의 판독력은 단위 > 통합 > E2E.** 같은 결함(실험 8)에 대해 통합은 어떤 텍스트가 틀렸는지를, E2E는 "요소 없음"만 말한다. 원인 판독이 안 되는 층일수록 테스트 이름이 조건→결과를 정확히 말해야 한다는 §4 규칙의 근거가 됐다. 실험 4의 11번 실패(`expected '2' to be null`)도 이름이 없었다면 판독 불가였다 — 이름 덕에 도달했으므로 단언은 손보지 않는다.

## 부록 B. 구현 중 설계 이탈·발견 기록

1. **NuqsTestingAdapter의 `hasMemory`** — 어댑터는 기본값(`hasMemory: false`)에서 `onUrlUpdate` 콜백만 호출하고 **렌더된 searchParams 상태를 갱신하지 않는다**. 상호작용(8~12번) 테스트 8개가 전부 타임아웃으로 전멸한 원인. 0단계 스모크 테스트는 fetch·URL이 없어 이 미비를 드러낼 수 없었다. `renderWithProviders`에 `hasMemory`를 켜서 해결 — "조작이 URL 상태에 기억된다"가 통합 테스트의 전제라 헬퍼 기본값으로 고정했다.
2. **12번 테스트 파일 위치 정정** — §5.1 초판의 widgets/header 배치는 FSD lint(상위 레이어 import 금지)가 테스트 파일에도 적용돼 불가능했다. 두 슬라이스를 함께 렌더하는 조합 지점은 상위 레이어 몫이므로 `_pages/products/ui/wishlist-header-sync.dom.test.tsx`로 옮겼다(테스트 코드 작성 전 docs 커밋으로 선반영).
3. **7번 경계(갱신 실패 배너)의 트리거** — 같은 queryKey의 배경 재조회 실패는 UI에 트리거가 없어(실사용에선 창 포커스 재조회) `renderWithProviders`가 반환하는 queryClient로 `invalidateQueries()`를 호출해 재현했다. 단언은 화면(배너 role="alert" + 기존 목록 유지)으로만 한다.
4. **E2E 단언은 픽스처 무지 원칙** — E2E는 MSW가 아닌 실제 mock API를 타므로 `casual-1` 같은 픽스처 이름 단언 금지. 개수 텍스트를 조작 전에 캡처해 reload 후와 비교하는 조건 기반 단언으로 대체했다. 모든 상호작용 전에 클라이언트 쿼리 결과(`총 N개`)를 기다려 하이드레이션 경합도 차단.
