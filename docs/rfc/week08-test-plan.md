# Week 08 테스트 설계

## 목표와 선택 기준

이번 과제는 테스트 개수나 커버리지보다, 각 위험을 가장 낮은 비용으로 재현하면서도 실제 사용자 계약을 지키는 방법을 선택하는 데 목적이 있다. 따라서 다음 기준을 순서대로 적용한다.

1. 현재 공개 경계를 테스트 때문에 불필요하게 변경하지 않는다.
2. DOM이나 브라우저가 없어도 동일한 위험을 검증할 수 있으면 더 낮은 단계의 테스트를 선택한다.
3. 통합 테스트는 RTL로 사용자 행위를 재현하고, 실제 HTTP 요청을 MSW가 가로채게 한다.
4. 실제 주소창, 브라우저 history, 문서 reload 또는 production 앱 전체 연결이 위험의 중심일 때만 E2E를 선택한다.

최종 배치는 단위 2개, 통합 9개, E2E 4개다.

## 환경과 모킹 경계

- 일반 `*.test.ts(x)`는 Vitest의 `node` 프로젝트에서 실행한다.
- `*.integration.test.tsx`만 `jsdom` 프로젝트에서 실행한다. DOM이 필요 없는 기존 테스트에 DOM 환경 설정 비용을 부과하지 않기 위해서다.
- RTL 통합 테스트는 `@testing-library/react`, `user-event`, `jest-dom`을 사용한다.
- 네트워크는 제품 코드의 `fetch`를 바꾸지 않고 MSW `setupServer`가 HTTP 경계에서 가로챈다.
- jsdom의 Node fetch만 직접 호출하면 `/api/products` 같은 상대 URL을 해석하지 못하지만, MSW 2가 fetch보다 앞에서 요청을 가로채 현재 jsdom URL 기준의 핸들러로 정상 전달한다. 실제 `fetchProducts` → MSW 통합 테스트로 이를 확인했으므로 별도 fetch 어댑터나 제품 HTTP 클라이언트 대체는 추가하지 않는다.
- 공통 MSW 핸들러에는 성공 응답만 둔다. 빈 결과, 오류, 지연은 해당 테스트에서 `server.use`로 덮어쓴다. 처리되지 않은 요청은 오류로 간주한다.
- 기존 `queries.test.ts`의 `vi.stubGlobal('fetch', fetchMock)` 두 곳은 제거한다. 2번은 query key만 DOM·네트워크 없이 검증하고, 요청 URL과 응답 계약은 MSW 통합 테스트가 담당한다.
- Zustand store는 테스트마다 초기 상태로 복원하고 `localStorage`도 비운다.
- 각 통합 테스트는 새 QueryClient를 만들고 UI 상태 전환 검증에서는 `retry: false`로 둔다. 5xx 재시도 정책 자체는 이 15개 항목의 검증 대상이 아니며, 실제 정책을 흉내 내다가 오류 UI가 늦게 나타나는 비용을 만들지 않는다. QueryClient 인스턴스와 cache는 테스트 간 공유하지 않는다.
- 정렬 MSW 핸들러는 JavaScript `sort`로 백엔드 로직을 복제하지 않는다. 요청의 `sort` 값을 관찰하고 조건별로 미리 정렬된 고정 fixture를 반환한다. FE는 올바른 조건을 보내고 받은 순서를 DOM에 그대로 표시하는지만 검증한다.
- E2E는 별도 `pnpm test:e2e` 명령에서 `pnpm build` 후 production 서버를 시작한다. 느린 E2E를 빠른 개발 루프와 분리하되, 최종 `pnpm check`는 Vitest → lint → typecheck → build → E2E 순서로 연결한다. 깨끗한 checkout에서도 `test:e2e` 단독 실행이 가능해야 한다.

### 현재 기준선과 남은 환경 게이트

- 과제 문서에는 기존 테스트가 5개라고 적혀 있지만 현재 브랜치에는 Vitest 파일 11개, 테스트 53개가 있으며 모두 통과한다. 이후에는 실제 저장소의 11개를 회귀 기준선으로 삼고, 문서와의 차이를 숨기지 않는다.
- Node 22.12.0과 pnpm 10.15.1에서 현재 `pnpm check`의 Vitest, lint, typecheck, production build가 통과했다.
- 환경 비교 당시 동일한 15개 파일·69개 테스트를 분리 환경과 전체 jsdom 환경에서 각 6회 실행했다. 첫 실행은 warm-up으로 제외하고 나머지 5회의 중앙값을 비교했다. 분리 구성은 전체 Duration 3.91초, 누적 environment 4.35초였고, 전체 jsdom은 각각 7.62초와 54.68초였다. 전체 Duration은 약 1.95배였으며 environment는 병렬 파일별 누적값이므로 실제 경과 시간으로 해석하지 않는다. 경계 및 HTTP 계약 보강 후 현재 Vitest 결과는 15개 파일·72개 테스트다.
- `week08-product-list.spec.ts`에는 E2E 방법론 4개 항목을 5개 테스트로 구현했다. `pnpm test:e2e`가 먼저 production build를 만든 뒤 3108 포트의 서버에서 실행되며, 서버 컴포넌트의 내부 fetch도 같은 origin을 사용하도록 Playwright web server에 `APP_ORIGIN`을 전달한다.
- 중첩 worktree 때문에 Next.js가 상위 lockfile을 workspace root로 추론한다는 경고가 있다. 사용자 선택으로 유지한 작업 구조이며, 이 과제만을 위해 제품 설정을 변경해 경고를 숨기지 않는다.

## 애매했던 판단

### 개수 파생을 단위가 아닌 통합으로 둔 이유

`useCartCount`와 `useWishCount`의 내부 계산은 단순하지만 현재 공개 경계는 React/Zustand 훅이다. 단위 테스트를 위해 `ids.length`나 `ids.includes`를 감싼 함수를 새로 노출하면 테스트 배치 때문에 제품 구조를 바꾸게 된다. 통합 테스트에서는 두 토글과 Header만 작은 트리로 렌더링해 장바구니·위시리스트의 개수와 독립성을 검증한다. 반대로 단위를 골랐다면 DOM 없이 빠르다는 장점은 있지만, 사소한 구현을 위한 새 경계와 12번과 별개인 연결 검증이 필요했을 것이다. 12번은 MSW로 불러온 실제 상품 카드에서 토글의 왕복까지 확인하므로 1번의 작은 연결 테스트와 범위가 다르다.

### URL 반영·재진입을 통합이 아닌 E2E로 둔 이유

RTL adapter로 query string 직렬화와 초기 search params 복원은 검증할 수 있다. 그러나 이 항목의 표현은 URL 문자열 계산을 넘어 실제 주소창 변경과 만들어진 URL로 새 문서에 직접 진입하는 계약을 포함한다. 이를 통합 테스트로 재현하면 App Router와 문서 진입을 흉내 내는 모형이 커진다. E2E는 비용이 더 들지만 이 위험을 가장 직접적으로 검증한다. 13번은 history 이동, 14번은 reload, 15번은 홈의 링크를 통한 앱 전체 연결로 각각 실패 원인이 달라 중복으로 보지 않는다.

## 목록 밖 테스트 판단

### 다음에는 하면 좋은 것: 할인 표시 계산

가격과 원가로부터 할인율 또는 할인 표기를 만드는 규칙은 사용자에게 직접 노출되고 계산 오류의 신뢰·매출 비용이 크다. 현재 변경 빈도가 높지 않아 이번 15개보다 뒤로 두되, 가격 정책이 확장되거나 할인 계산이 별도 순수 로직으로 자리 잡으면 단위 테스트를 추가한다.

### 앞으로도 하지 않을 것: 상품 카드 CSS 클래스명

클래스명은 스타일 변경으로 자주 바뀌지만 실패 비용이 낮고 사용자 동작을 보장하지 않는다. role, label, 사용자에게 보이는 텍스트와 결과를 검증하며 Tailwind 또는 스타일 구조 변경만으로 테스트가 깨지게 하지 않는다.

## 구현 원칙

- 단위 테스트 2개는 DOM 없이 통과시킨다.
- 2번 query key 테스트에서는 fetch를 호출하거나 stub하지 않는다. 제품 HTTP 요청을 검증해야 하는 단언은 MSW 통합 테스트로 이동한다.
- 통합 테스트는 role, label, text 순으로 요소를 찾고 `getByTestId`는 대안이 없을 때만 근거를 남긴다.
- 비동기 조회만 `findBy*` 또는 제한된 `waitFor`를 사용하고, 이후 단언은 동기식으로 확인한다.
- 각 테스트는 독립 실행되며 store, QueryClient, MSW handler와 저장소 상태를 공유하지 않는다.
- MSW fixture는 요청에 대한 고정 계약만 표현하며 정렬·검색·페이지네이션 제품 로직을 테스트 안에서 다시 구현하지 않는다.
- E2E는 고정 `sleep` 없이 조건 기반으로 기다리고 production server에서 실행한다.
- `it.skip`, 주석 비활성화, 광범위한 `toBeTruthy()`로 완료를 가장하지 않는다.

## 구현 순서와 완료 게이트

1. 실제 제품 `fetchProducts`의 상대 URL 요청이 MSW까지 전달되는 최소 통합 테스트로 HTTP 경계를 확인한다. MSW가 이미 이를 지원하므로 별도 어댑터는 추가하지 않는다.
2. 기존 query factory 테스트에서 직접 fetch stub을 제거하고 2번의 query key 계약만 남긴다.
3. 단위 2개와 통합 9개를 구현하고 각 테스트 파일의 독립 실행과 전체 Vitest 실행을 확인한다.
4. 분리 환경과 전체 jsdom 비교용 임시 설정으로 6회씩 측정하고, 원본 설정에는 분리 환경만 남긴다.
5. E2E 4개를 구현하고 깨끗한 build 조건에서 `pnpm test:e2e`를 확인한다.
6. `pnpm check`에 E2E를 연결하고 전체 검증을 통과시킨다.
7. 단위·통합·E2E에서 각각 하나 이상 제품 코드만 망가뜨리는 결함 주입을 수행하고 테스트의 실패 메시지를 기록한 뒤 제품 코드를 복구한다.

## 구현 및 결함 주입 결과

- 단위 2개 항목, RTL+MSW 통합 9개 항목, Playwright E2E 4개 항목을 계획한 방법론 그대로 구현했다. MSW HTTP 경계 자체를 확인하는 통합 smoke test 하나도 별도로 둔다.
- 기존 query factory 테스트의 `vi.stubGlobal('fetch')` 두 곳을 제거했다. query key는 Node 단위 테스트가, 실제 요청과 응답은 MSW 통합 테스트가 담당한다.
- 최초 오류에서 다시 시도할 때 오류 영역이 사라지고 스켈레톤으로 바뀌는 결함을 테스트가 발견했다. 재시도 중 오류 영역과 비활성 버튼을 유지하도록 수정했다.
- E2E 첫 실행에서 production 서버 포트 3108과 서버 내부 `APP_ORIGIN` 3000이 달라 홈 요청이 실패하는 문제를 발견했다. Playwright web server의 `APP_ORIGIN`을 3108로 맞춰 production 전체 흐름을 복구했다.
- 적대적 리뷰 뒤 2번의 동일 기본 조건 key, 11번의 2페이지 필터 초기화와 재진입 목록 순서, 13번의 history별 목록 식별, 14번의 필터·검색·정렬·페이지 reload와 유효하지 않은 페이지 보정을 보강했다. E2E 4개 항목은 시나리오를 분리해 5개 테스트로 실행한다.
- 두 번째 적대적 리뷰에서 fetch stub 제거 당시 전체 query parameter와 상품 목록 queryFn이 받은 `AbortSignal`의 전달 검증이 유실된 것을 발견했다. MSW가 받은 실제 URL과 Fetch Request의 signal을 확인하는 HTTP 경계 테스트로 두 계약을 복구했다.

| 방법론 | 임시로 망가뜨린 곳 | 관찰한 실패 | 판정 |
| --- | --- | --- | --- |
| 단위 | `getPageNumbers`의 시작 범위를 `page - 2`에서 `page - 1`로 축소 | 중간·마지막 페이지 기대 배열에서 첫 번호가 빠졌다는 diff와 함께 2개 실패 | 계산 경계를 직접 식별함 |
| 통합 | 갱신 실패 인라인 오류 렌더 조건 제거 | 직전 상품은 남았지만 `목록을 갱신하지 못했습니다` 문구를 찾지 못해 실패 | HTTP 실패와 사용자 UI 연결을 식별함 |
