# 8주차 — 테스트 설계 (week08-test-plan)

## 1. 검증 기준 설명

이 프로젝트는 학습 자료의 테스트 피라미드를 따라 단위/통합/E2E 세 가지로 나눴고, 그 경계는 **"컴포넌트를 렌더(`render()`)해야만 확인 가능한가"**를 기준으로 삼았습니다.

#### 단위(unit)로 분류한 기준

`render()` 없이, 함수 호출이나 store 상태 조회만으로 결과를 확인할 수 있는 함수·로직만 단위 테스트로 뒀습니다. 학습 자료가 "컴포넌트에 대해서는 통합 테스트가 더 가치 있다", "컴포넌트 내부 값을 직접 검증하는 건 구현 세부사항 테스트"라고 한 기준을 따라, 컴포넌트가 관여하는 순간부터는 단위 대상에서 제외했습니다.

- 예: query key 생성(`productsQueries`), 텍스트 조립(`buildProductsMetadataText`), store의 개수 파생 로직

#### 통합(integration)으로 분류한 기준

사용자 행위(클릭·입력) → 화면에 보이는 결과 변화를 RTL+MSW로 확인할 수 있는 경우를 통합 테스트로 뒀습니다. 내부 상태값이 아니라 **"그 계산 결과가 실제로 화면까지 전파되는가"**를 확인합니다. 이렇게 층을 나누면, 테스트가 실패했을 때 계산 로직 문제인지 화면 연결 문제인지 구분할 수 있습니다.

- 예: 카테고리 변경 → 목록 변경, 에러 → 재시도로 복구, 담기 → 헤더 개수 변경

#### E2E로 분류한 기준

여러 페이지에 걸치거나, RTL(jsdom)로는 재현할 수 없는 진짜 브라우저 동작이 필요한 경우를 E2E로 뒀습니다. 참고 자료가 E2E를 "전체 사용자 플로우 검증"이라고 정의한 것과, 실제로 jsdom에는 없는 브라우저 전용 기능(풀 페이지 새로고침, 진짜 history 스택 이동)이라는 두 기준을 같이 적용했습니다.

- 예: 새로고침 후 필터 유지, 뒤로가기로 필터 복원, 목록 진입→담기→헤더까지 이어지는 전체 흐름

## 3. 애매했던 판단

#### 판단 1 — 항목 11 "URL로 재진입"을 어디에 배치할지

항목 11("조작이 URL에 반영 · URL로 재진입")은 사실 방향이 반대인 두 검증을 하나로 묶고 있었습니다.

- **화면 조작 → URL 반영**: 사용자가 필터(카테고리, 정렬 등)를 클릭하면, 그 결과로 URL이 올바르게 바뀌는가를 확인합니다. 화면 조작이 먼저이고, URL 변화가 그 결과입니다.
- **URL 재진입 → 화면 상태**: 이미 특정 조건이 담긴 URL로 들어왔을 때(주소창에 직접 입력, 링크 공유 등), 그 URL이 뜻하는 상태로 화면이 맞춰지는가를 확인합니다. URL이 먼저이고, 화면 상태가 그 결과입니다.

이 두 번째 방향("URL로 재진입")은 항목 13(뒤로가기 복원), 14(새로고침 유지)와 같은 성격으로 판단했습니다. 뒤로가기·새로고침·직접 재진입 모두 "URL이 이미 정해진 상태에서, 그 URL을 보고 화면이 올바르게 복원되는가"를 확인한다는 점에서 동일한 메커니즘으로 봤습니다.

항목 11은 "필터를 조작하면 URL이 갱신되는가"(화면→URL 방향)만 통합 테스트로 남기고, "URL로 재진입"(URL→화면 방향)은 별도 테스트를 새로 만들지 않았습니다. "URL로 재진입"과 "새로고침"은 둘 다 해당 URL을 서버에 새로 요청해서 처음부터 렌더하는 동일한 경로를 타므로, 14번에 자연스럽게 흡수시켰습니다. 반면 13번(뒤로가기)은 브라우저 history 스택 이동이라는 별개의 메커니즘이라, 재진입 검증을 거기 포함시킬 이유는 없었습니다.

**다른 쪽을 골랐다면**

"URL로 재진입"을 독립된 항목으로 유지했다면, 별도의 E2E 테스트를 하나 더 만들어야 했을 것입니다. 그러면 13(뒤로가기)·14(새로고침)에 재진입용 테스트가 추가되어 이 영역만 총 3개의 E2E가 되고, 그중 재진입과 새로고침은 같은 내용(URL을 새로 읽어 화면을 복원하는 것)을 반복 검증하는 셈이 되었을 것입니다.

#### 판단 2 — 항목 12와 15가 겹치는 문제

항목 12("담기 → 헤더 개수 · 다시 누르면 빠짐")와 항목 15("목록 진입 → 담기 → 헤더 확인")는 "담기를 누르면 헤더가 바뀐다"는 동일한 동작을 검증한다는 점에서 중복처럼 보였습니다.

다만 둘의 검증 범위가 다르다고 판단했습니다. 12번은 `ProductCard`와 `Header`를 개별 컴포넌트로 뚝 떼어 렌더해서 "부품 단위 연결"(store를 공유하는 두 컴포넌트 간 상태 반영)을 확인하는 반면, 15번은 실제 페이지 라우팅(목록 진입)부터 시작해 그 페이지 안에서 컴포넌트들이 다 같이 조립된 채로 정상 동작하는지, 즉 "실제 배포 환경에서 전체가 연결되어 작동하는가"를 확인합니다. 12번이 실패하면 부품(store 연결) 문제로, 15번만 실패하면 조립(라우팅·페이지 로드) 문제로 원인을 좁힐 수 있어 목적이 다릅니다.

다만 완전한 중복 낭비를 피하기 위해, 15번(E2E)에서는 담기/헤더 관련 세부 케이스(중복 클릭, 여러 상품 등)는 다루지 않고 "담기 한 번 → 헤더 숫자 반영"이라는 대표 케이스 하나만 확인하기로 했습니다. 세부 케이스는 12번(통합)이 이미 충분히 커버하고 있기 때문입니다.

## 4. 이 목록 밖은 어떻게 할지 정해요

#### 다음에는 하면 좋겠다 — `SIMULATE_METADATA_FAILURE` 환경변수 분기

`getProductsServerData`(`src/entities/product/api/products.ts`) 안에는 다음과 같은 분기가 있습니다.

```ts
if (process.env.SIMULATE_METADATA_FAILURE === 'true') {
  throw new Error('상품 목록 조회 실패 (시뮬레이션)');
}
```

이건 실제 사용자가 마주치는 일반 시나리오가 아니라, 개발자가 의도적으로 환경변수를 켜야만 발동하는 디버깅/시뮬레이션 전용 분기입니다. **변경 빈도**는 거의 없다시피 합니다(평소엔 아무도 이 코드를 건드리지 않습니다). **실패 비용**도 낮습니다(환경변수가 꺼진 상태가 기본값이라, 여기 버그가 있어도 실제 서비스에서는 이 분기 자체가 실행되지 않아 사용자에게 영향이 없습니다). 그래서 이번 주 15개 항목만큼 급하게 다룰 이유는 없지만, `generateMetadata` 실패 시나리오를 검증하는 김에 다음 기회에 함께 다루면 좋겠다고 판단했습니다.

#### 앞으로도 안 하겠다 — Dialog, TextSelect/ThumbnailSelect/SizeSelect 컴포넌트

`src/shared/ui/dialog`, `src/shared/ui/select`(TextSelect, ThumbnailSelect, SizeSelect)는 4주차에 만든 컴포넌트로, 실제로 import해서 쓰는 곳이 현재 코드베이스 어디에도 없습니다(`grep`으로 확인했습니다).

**변경 빈도**는 화면에 연결되어 있지 않으니 지금 당장 바뀔 일이 없다고 판단했습니다. **실패 비용**도 낮습니다(사용자가 실제로 마주치는 화면이 아니므로, 여기서 버그가 나도 서비스에 영향이 없습니다). 또한 4주차에서 이미 훅/컴포넌트 단위로 자체 테스트를 마친 영역이라(`week-04-dialog.md`, `week-04-select.md` 참고), 8주차 범위(목록·카트·필터 흐름)와 무관한 재검증에 시간을 쓰는 것보다 우선순위가 낮다고 판단했습니다.


## 3단계 자가 검증 (실험 기록)

방법론(단위/통합/E2E)마다 구현을 한 곳씩 일부러 망가뜨려서, 2단계에서 작성한 테스트가 실제로 그 문제를 잡아내는지 확인했습니다. 실험이 끝난 뒤에는 모두 원래 코드로 복구했습니다.

#### 실험 기록

| # | 방법론 | 망가뜨린 곳 | 어떻게 바꿨나 | 결과 | 실패한 테스트 |
| --- | --- | --- | --- | --- | --- |
| 1 | 단위 | `src/_pages/product-list/api/products-metadata.ts` | 페이지 번호 표시 문구에서 `- ` 하이픈 제거 (`` `${title} - ${page}페이지` `` → `` `${title} ${page}페이지` ``) | 잡힘 | `buildProductsMetadataText — 경계 케이스 > page가 2 이상이면 title 끝에 페이지 번호가 붙는다` |

#### 실패 메시지로 원인을 알 수 있었는지

**실험 1 (단위)**: 알 수 있었습니다. `Expected: "홈 상품 - 3페이지"` / `Received: "홈 상품 3페이지"`로 하이픈 누락이 원인임이 바로 드러났습니다.

**실험 2 (통합)**: 알 수 있었습니다. `Unable to find an element with the text: 오류가 발생했습니다.` 메시지와 함께 출력된 DOM에 `<section aria-label="상품 검색 결과" class="week05-section" />`만 비어 있는 게 보여서, 에러 UI 자체가 렌더되지 않고 있다는 걸 바로 파악할 수 있었습니다.

**실험 3 (E2E)**: 부분적으로만 알 수 있었습니다. `Received string: "about:blank"`를 보고 "뒤로가기를 눌렀을 때 history 스택에 갈 곳이 없다"는 것까지는 추측할 수 있었지만, 정확히 `history: 'replace'`가 원인이라는 것까지는 메시지만으로는 알 수 없었고 코드를 직접 확인해야 했습니다.

#### 부가 발견 — 실제 버그 수정

3단계 실험과는 별개로, 2단계에서 항목 5(목록 빈 결과)의 경계 케이스 테스트를 작성하던 중 실제 버그를 발견했습니다. `totalCount: 0`일 때 페이지네이션이 "1 / 0"으로 표시되는 문제였고, `useProductFilters.ts`의 `totalPages` 계산에 `Math.max(1, ...)`를 추가해 최소값을 보정했습니다. (커밋: `fix: totalCount가 0일 때 totalPages 최소값 1로 보정`)
