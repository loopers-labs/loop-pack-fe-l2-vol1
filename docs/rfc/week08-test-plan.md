# RFC — 8주차 테스트 설계

> 이 문서는 테스트 코드보다 먼저 커밋한다. 커버리지를 올리는 주가 아니라, 지켜야 할 동작을 먼저 정하고 그것만 고정하는 주다.

## 0단계 — 환경과 모킹 경계

### 환경 분리

`vitest.config.ts`에 `projects` 둘을 두고, 파일명 접미사 `*.dom.test.tsx`로 편입을 가른다.

| 프로젝트 | environment | include | setupFiles |
| --- | --- | --- | --- |
| `node` | `node` | `src/**/*.test.{ts,tsx}` (dom 제외) | 없음 |
| `dom` | `jsdom` | `src/**/*.dom.test.{ts,tsx}` | `vitest.setup.dom.ts` |

접미사로 가른 것은 셋업 파일 때문이다. docblock(`// @vitest-environment jsdom`)은 파일마다 환경을 선언할 수 있지만 셋업을 프로젝트 단위로 나누지 못한다. MSW·jest-dom·store 리셋을 DOM 테스트에만 붙이려면 셋업 파일 안에 조건 분기가 들어온다. 디렉터리(`__tests__/dom/`)로 가르면 테스트가 대상 파일에서 멀어지는데, 이 레포는 테스트를 대상 옆에 두는 관례다. 접미사는 `include`/`exclude` 한 줄로 갈리고, 프로젝트별 `setupFiles`가 파일 단위로 정확히 붙는다.

기존 테스트 6개는 접미사가 없으므로 그대로 `node`에 남는다. `HeroSection.test.tsx`와 `ProductListSkeleton.test.tsx`는 `.tsx`인데도 `renderToStaticMarkup`으로 문자열만 보므로 DOM이 필요 없다. 확장자가 아니라 실제 의존이 기준이다.

### 셋업 시간

`vitest run`의 `environment` 값을 3회씩 재고 중앙값을 썼다. 측정 시점의 DOM 테스트는 환경 확인용 스모크 1개다.

| | environment | setup | Duration(벽시계) |
| --- | --- | --- | --- |
| 분리 (node + dom) | 239ms | ~100ms | 505ms |
| 전부 jsdom | 1,977ms | ~1,180ms | 659ms |

`environment`는 워커 합이라 벽시계와 다르다. DOM이 필요 없는 6개 파일에까지 jsdom을 세우면 그 비용이 파일 수에 비례해 쌓인다. 지금 비율은 1:6이지만, 2단계에서 DOM 테스트가 늘어도 단위 테스트는 계속 `node`에 남는다.

> **이 수치는 지금 재현되지 않는다.** 측정에 쓴 DOM 스모크는 환경 확인용이라 지웠고(이 문서가 테스트 코드보다 먼저 커밋돼야 해서), 비교군인 "전부 jsdom" 설정도 임시 파일이었다. 2단계에서 실제 DOM 테스트가 들어온 뒤 같은 방법으로 다시 재고 라이팅에 최종 수치를 남긴다. 위 표는 분리할 가치가 있는지 판단한 근거이고, 제출 수치로 쓸 것이 아니다.
>
> 재현 절차: (1) `pnpm vitest run` 3회, `environment` 중앙값. (2) 임시 config에 `include`를 `src/**/*.test.{ts,tsx}` 전체로 두고 `environment: "jsdom"`과 dom 셋업을 지정해 `pnpm vitest run --config <파일>` 3회. (3) 임시 config 삭제.

### 모킹 경계

네트워크는 **MSW로만** 가로챈다. 앱 코드의 `fetch`를 바꿔치기하지 않는다. 요청은 실제로 나가고 MSW가 받는다.

애초에 옮길 코드가 없었다. `fetch`를 부르는 곳은 `fetchJson` 하나뿐이고, 그걸 스텁하고 있던 테스트도 없었다. 그래서 이 요구사항은 직접 모킹을 걷어낸 과정이 아니라 처음부터 그렇게 짰다는 사실로 기록한다.

남는 결정은 셋업의 기본값을 어디에 두느냐다.

- `onUnhandledRequest: "error"`. 모킹되지 않은 요청이 조용히 나가면 그 테스트가 무엇을 전제했는지 알 수 없다. 경계를 넘는 즉시 실패로 만든다.
- 기본 핸들러는 성공 경로만 둔다. 실패·지연·빈 결과는 그것을 검증하는 테스트가 `server.use()`로 그 자리에서 덮는다. 기본값에 예외를 섞으면 어떤 테스트가 무엇을 전제했는지 파일을 떠나야 알 수 있다.
- 픽스처는 mock 백엔드의 실제 데이터(`app/api/_data/commerce.ts`)를 쓴다. 별도 더미를 만들면 응답 계약이 조용히 갈라진다.

jsdom에는 origin을 준다(`environmentOptions.jsdom.url`). `fetchJson`은 브라우저 분기에서 `/api/products`를 그대로 넘기는데, jsdom 기본 URL이 `about:blank`면 요청 URL이 만들어지지 않아 MSW가 가로챌 대상 자체가 생기지 않는다.

서버 정렬·필터는 MSW가 대신하지 않는다. 그건 `app/api/products/route.test.ts`가 `node`에서 이미 덮고 있다. 통합 테스트는 "서버가 이걸 주면 화면이 이렇게 된다"까지만 본다. 같은 것을 두 층에서 검증하지 않는다.

### 격리 — 전역 store

필터 유지는 전적으로 URL(nuqs)이 맡고 `localStorage`는 쓰지 않는다. 그래서 격리 대상은 zustand store뿐이다.

store는 모듈 싱글턴이다. `entities/{cart,wishlist}/model/store.ts`는 raw store를 내보내지 않으므로 밖에서 `setState`로 되돌릴 수도 없다. 되돌리지 않으면 테스트 순서가 결과를 바꾼다.

zustand 공식 가이드는 `__mocks__/zustand.ts`로 `create`를 감싸 생성된 store를 등록해 두고 `afterEach`에 일괄 초기화하라고 한다. 프로덕션 코드를 한 줄도 안 건드리는 장점이 있다.

그래도 model에 리셋을 공개하는 쪽을 골랐다. `resetCart()`·`resetWishlist()`를 `model/store.ts`가 내보내고 배럴(`index.ts`)은 공개하지 않으므로, 앱 코드가 쓰는 경로에는 나타나지 않는다.

`create`를 갈아치우면 테스트가 검증하는 store가 출하되는 store와 다른 코드로 만들어진다. 지금은 미들웨어가 없어 차이가 없지만, 붙는 순간 그 차이가 조용해진다. `docs/testing/conventions.md`에 내부 모듈을 `vi.mock`하면 실제 통합을 숨겨 false green이 된다고 적어 뒀는데, zustand는 외부 라이브러리라도 `create`는 내 store를 만드는 함수다. 프로덕션 API가 두 줄 늘어나는 비용을 택하고, 그 두 줄에 왜 있는지 주석을 남겼다.

### E2E는 `pnpm test`에 넣지 않는다

별도 `pnpm test:e2e`로 둔다. `pnpm check`가 `test && lint && typecheck && build` 순서인데, Playwright는 `webServer`에서 자기 `pnpm build && pnpm start`를 돌린다. E2E를 `test`에 넣으면 check의 build보다 먼저 build가 한 번 더 돌아서, 같은 빌드를 두 번 하는 비용을 게이트 전체에 얹게 된다.

CI 쪽은 손댈 것이 없다. 코스가 제공한 `.github/workflows/quality.yml`이 `playwright --version`이 잡히면 Chromium을 자동 설치한다.

## 1단계 — 15개 항목을 어떻게 검증할지

15개 항목 전부 내 구현에 존재한다. 기능이 없어서 넘어가는 항목은 없다.

배치의 원칙은 하나다. E2E는 진짜 브라우저여야만 되는 것만 맡는다. 실제 히스토리 스택, 새로고침, production build. 나머지는 통합에서 더 정밀하고 빠르게 본다.

| # | 검증 대상 | 방법론 | 그렇게 정한 이유 | 빨간불이 되면 알게 되는 것 |
| --- | --- | --- | --- | --- |
| 1 | 장바구니·위시리스트 개수 파생 | 단위 | `countIds`·`toggleId`는 도메인을 모르는 순수 함수다(`shared/lib/idSet.ts`). 개수를 저장하지 않고 파생한다는 5주차 결정이 이 두 함수에 있다. 헤더에 실제로 반영되는지는 12번이 덮으므로 여기서 렌더까지 갈 이유가 없다 | 같은 id를 두 번 담으면 개수가 2가 되거나, 빼도 줄지 않는다. 담김/빠짐 토글 계약이 깨진 것이다 |
| 2 | URL 조건 → query key | 단위 | 입력이 조건 객체, 출력이 `queryKey`인 순수 변환이다. 캐시 동일성은 key 모양 그 자체라 값으로 고정하는 게 가장 직접적이다 | 같은 조건이 다른 key를 만들면 재방문·앞뒤 이동에서 캐시가 안 맞아 매번 재요청한다. 다른 조건이 같은 key를 만들면 카테고리를 바꿨는데 이전 목록이 보인다 |
| 3 | `resolveProductListQuery` (직접 고른 순수 로직) | 단위 | 서버(`generateMetadata`·prefetch)가 URL을 조건으로 좁히는 유일한 경로다. nuqs 파서와 같은 기본값·같은 좁히기를 손으로 한 번 더 쓴 곳이라 어긋나기 쉽고, 방어 분기(`page >= 1`, 배열 `q`, 리터럴 좁히기)가 몰려 있어 경계가 많다 | `?page=0`·`?page=abc`가 1로 정규화되지 않으면 서버는 잘못된 page로 prefetch하고 클라이언트는 1로 읽는다. query key가 갈라져 hydration 직후 재요청이 난다. 없는 category가 통과하면 mock API가 400을 준다 |
| 4 | 목록 로딩 → 성공 | 통합 | pending은 렌더와 네트워크 타이밍이 만드는 상태라 순수 함수로 볼 수 없다. MSW가 지연을 정하므로 그 창을 직접 만들 수 있다. 7주차에 1.5초 pending을 라이브로 재현하지 않았다고 지적받은 것을 여기서 갚는다 | 스켈레톤이 안 뜨고 빈 화면이 나오거나, 데이터가 온 뒤에도 스켈레톤이 남는다. 최초 진입에서 사용자가 무엇을 기다리는지 모르게 된다 |
| 5 | 목록 빈 결과 | 통합 | 0건은 200 응답이라 에러와 완전히 다른 화면이다. `describeQuery`가 만든 문구가 URL 조건을 반영하는지는 렌더 결과로만 보인다 | 0건인데 빈 그리드와 페이지네이션이 그려진다. 또는 왜 0건인지가 문구에 없어 사용자가 조건을 완화할 근거를 잃는다 |
| 6 | 목록 에러 | 통합 | 인라인 에러는 4xx에서만 뜬다(`throwOnError: isServerFault`). 그 경계가 실제로 그렇게 갈리는지는 화면에서 봐야 한다. 400과 500 두 방향을 다 넣는 이유는 아래에 따로 적었다 | 400인데 목록 자리가 비고 재시도가 없으면 조건을 바꿔 빠져나갈 수 없다. 400이 경계로 튀면 필터 UI까지 사라져 사용자가 갇힌다. 500이 인라인으로 내려오면 재시도해도 안 되는 실패에 "다시 시도" 버튼을 주는 것이고, 사용자는 같은 버튼을 반복해 누른다 |
| 7 | 에러 → 재시도로 복구 | 통합 | `refetch()`가 같은 조건을 다시 부르고 화면이 복구되는지 보려면 응답 두 개의 순서가 필요하다. MSW override로만 만들 수 있다 | 재시도를 눌러도 에러가 남거나, 복구됐는데 에러 문구가 함께 남아 성공과 실패가 동시에 보인다 |
| 8 | 카테고리 변경 → 목록 변경 | 통합 | 조작 → `setParams` → 새 요청 → 새 목록이라는 사슬 전체가 계약이다. 특히 `page: 1` 리셋은 단위로는 보이지 않는다 | 3페이지에서 카테고리를 바꿨을 때 page가 3으로 남으면, 그 카테고리에 3페이지가 없어 방금 바꾼 조건이 0건으로 보인다 |
| 9 | 정렬 변경 → 순서 변경 | 통합 | 8번과 같은 사슬. 순서는 서버가 정하므로 테스트가 응답 순서를 정하고 화면이 그 순서를 따르는지만 본다(서버 정렬 자체는 `route.test.ts`가 단위로 덮는다). 핸들러가 호출 순서 대신 `sort`를 읽어야 하는 이유는 아래에 따로 적었다 | 정렬을 바꿨는데 `sort`가 요청에 안 실리면 서버는 기본 정렬을 주고 화면은 다른 순서를 기대한다. 응답 순서를 화면이 재배열하면 서버 정렬을 믿지 않는 중복 로직이 생긴 것이다 |
| 10 | 페이지 이동 → 목록 변경 | 통합 | `totalPages = ceil(totalCount / pageSize)` 경계와 `disabled`가 함께 걸린다. 응답의 `totalCount`를 테스트가 정할 수 있어야 경계를 만든다 | 1페이지에서 "이전"이 눌리면 `page=0` 요청이 나가 400을 받는다. 마지막에서 "다음"이 눌리면 빈 목록으로 나간다 |
| 11 | 조작이 URL에 반영 · URL로 재진입 | 통합 | `NuqsTestingAdapter`의 `onUrlUpdate`가 갱신된 `URLSearchParams`를 그대로 주고, `searchParams` 주입으로 재진입을 만든다. 기본값 생략(`all`·`latest`·`page=1`은 nuqs가 URL에서 지운다)은 키 부재 단언이 필요해 E2E보다 정밀하다. 재진입을 새 마운트로 만드는 이유는 아래에 따로 적었다 | 조작해도 URL이 안 바뀌면 링크 공유와 복원이 죽는다. 기본값이 URL에 남으면(`?category=all&page=1`) URL이 조건의 원본이라는 5주차 규칙이 깨진 것이다 |
| 12 | 담기 → 헤더 개수 · 다시 누르면 빠짐 | 통합 | entity store가 버튼과 헤더라는 두 조각을 잇는다는 게 계약이라 함께 렌더해야 보인다. `aria-pressed`·`aria-label`이 이미 붙어 있어 사용자가 인식하는 방식으로 조회된다 | 담았는데 헤더 숫자가 안 오르면 store와 헤더의 연결이 끊긴 것이다. 다시 눌러도 안 빠지면 토글이 add-only다. 다른 상품을 담았는데 첫 상품 버튼이 담김으로 바뀌면 상품별 포함 여부 계산이 id를 무시한다 |
| 13 | 뒤로·앞으로 가기로 필터 복원 | E2E | jsdom에는 실제 히스토리 스택이 없다. `history: "push"`가 진짜로 히스토리를 쌓는지는 브라우저만 답한다 | 뒤로 가도 필터가 그대로면 `replace`로 바뀐 것이고, 조건을 URL에 둔 이유의 절반인 복원이 사라진다 |
| 14 | 새로고침해도 필터 유지 | E2E | jsdom엔 새로고침이 없다. 이 앱은 필터를 URL에만 두므로 URL이 복원의 유일한 근거다 | 새로고침하면 필터가 초기화된다. URL에 조건을 둔 결정이 실제로는 작동하지 않는 것이다 |
| 15 | 목록 진입 → 담기 → 헤더 확인 | E2E | production build 위에서 layout(Header)·페이지·mock API 500ms 고정 지연이 한 번에 맞물리는 유일한 경로다. 통합은 `layout.tsx`를 렌더하지 않는다(`next/font/google`과 전역 CSS가 딸려 온다) | production에서만 헤더 숫자가 안 오른다. hydration 경계 문제이고, dev와 통합에서는 안 잡힌다 |

### 초록불인데도 깨져 있을 수 있는 세 자리

표를 채운 뒤 항목마다 "이 테스트가 통과하는데도 구현이 틀려 있을 수 있나"를 되짚었다. 세 곳이 걸렸고, 2단계 구현에 그대로 반영한다.

#### 6번 — 400 하나로는 부족하다

400만 검증하면 `throwOnError: (error) => isServerFault(error)`를 `() => false`로 바꿔도 초록불이다. 400은 원래 인라인이라 화면이 그대로 나오기 때문이다. 그러면 이 테스트가 지키는 건 4xx가 인라인이라는 사실 하나뿐이고, 정작 위험한 회귀인 5xx의 인라인 유출은 아무도 안 본다.

그래서 두 방향으로 쓴다. 400은 목록 자리에 실패 문구와 "다시 시도"가 보이는 것으로, 500은 경계로 전파되는 것으로 확인한다. 통합 테스트는 `app/products/error.tsx`를 렌더하지 않으므로 테스트가 직접 React ErrorBoundary로 감싸 fallback이 뜨는 것을 본다. 이때 인라인 문구가 보이지 않는 것까지 `queryBy*`로 함께 단언한다.

3단계 변이와 짝이다. `isServerFault`의 `>= 500`을 `>= 600`으로 바꾸면 500이 인라인으로 새는데, 400만 보고 있었다면 그 변이가 살아남는다.

#### 9번 — 핸들러가 요청을 읽어야 한다

`queryKey`는 `["products", query]`로 조건 객체에서 만들어지고, 요청 URL은 `params.set(...)`으로 따로 만들어진다. 두 경로가 갈라져 있다.

그래서 핸들러를 "첫 호출이면 A 순서, 두 번째면 B 순서"로 짜면 이렇게 된다. `params.set("sort", query.sort)` 줄을 지워도, 정렬 select를 바꾸는 순간 `query.sort`가 바뀌어 key가 갈리고, 재요청이 나가고, 핸들러는 두 번째 응답을 주고, 화면 순서도 바뀐다. **테스트는 통과하고 서버는 기본 정렬을 주고 있다.**

그래서 9번 핸들러는 `new URL(request.url).searchParams.get("sort")`를 읽어 그 값에 맞는 순서를 돌려주고, 값이 없으면 400을 준다. 호출 순서에 의존하지 않는다. 같은 이유로 8·10·11번 핸들러도 `category`·`page`를 요청에서 읽는다.

#### 11번 — 재진입에는 unmount가 필요하다

`renderWithProviders`의 `hasMemory: true`는 같은 마운트 안에서 어댑터가 갱신된 조건을 기억하게 하는 장치다. 이것만으로는 URL로 다시 들어왔다가 아니라 같은 어댑터의 상태가 바뀌었다를 보는 것이 된다.

그래서 재진입은 이 순서로 만든다.

1. 조작하고 `onUrlUpdate`가 준 `queryString`을 캡처한다.
2. `unmount()`로 마운트를 완전히 버린다(store 리셋과 `cleanup`이 뒤따른다).
3. 캡처한 `queryString`으로 `renderWithProviders`를 새로 호출한다.
4. select 값·목록 내용·나간 요청이 캡처 시점과 같은지 확인한다.

기본값 생략은 문자열 포함 검사(`toContain("page=1")`)가 아니라 키 부재를 직접 단언한다. `expect(event.searchParams.has("page")).toBe(false)`. 문자열 검사는 `?page=10`이 `page=1`을 포함해서 통과하는 함정이 있다.

### 애매했던 판단 두 개

#### 2번 — query key를 단위로 고정할까, 통합에서 나간 요청으로 볼까

둘 다 성립했다. 통합으로 가면 MSW 핸들러에서 `request.url`을 받아 조건을 바꾸면 그 조건으로 새 요청이 나간다를 볼 수 있다. 사용자 관점에 가깝고, `queryKey`의 모양을 바꾸는 리팩터에도 깨지지 않는다.

**단위로 정했다.** 두 방법이 서로 다른 것을 보기 때문이다. 통합이 보는 건 요청이 나갔다이고, 내가 지키려는 건 같은 조건이 같은 key를 만들고 다른 조건은 다른 key를 만든다는 캐시 동일성이다. 요청이 나가는 것은 캐시 미스의 결과지 동일성 자체가 아니다. 특히 위험한 방향은 다른 조건이 같은 key를 만드는 쪽인데(카테고리를 바꿨는데 이전 목록이 보인다), 통합에서는 요청이 나가는 것만 보고 이걸 놓친다.

통합으로 갔다면 8·9·10번이 이미 조건을 바꾸면 새 목록이 온다를 덮고 있으니 2번이 사실상 중복이 되고, 캐시 동일성은 아무 테스트도 지키지 않는 상태로 남았을 것이다.

대가는 알고 있다. `queryKey: ["products", query]`의 모양을 바꾸면 이 테스트가 깨진다. 받아들일 대가다. 7주차 문서에 이 key 모양이 바뀌면 캐시 동일성이 깨진다고 적어 뒀고, 바꿀 때 테스트가 같이 깨지는 것이 경고로 작동한다. 구현 세부가 아니라 계약이라고 선언한 값에 붙였다.

#### 11번 — URL 반영을 통합에서 볼까, E2E에서 볼까

E2E가 자연스러워 보였다. 13·14번이 이미 브라우저에서 히스토리와 새로고침을 보고 있으니, 조작하면 주소창이 바뀐다를 같은 자리에서 확인하면 시나리오 하나로 묶인다.

**통합으로 정했다.** 결정적인 이유는 기본값 생략이다. nuqs는 기본값과 같은 값을 URL에서 지운다. 카테고리를 `all`로 되돌리면 `?category=all`이 남지 않고 사라진다. 필터를 바꿀 때 넣는 `page: 1`도 URL에는 `page=1`이 아니라 키 자체가 없는 것으로 나타난다. 7주차 기준선 #7에 적어 둔 실제 동작이다. E2E에서 이걸 단언하려면 주소창에 `page`가 없음을 확인해야 하는데, `onUrlUpdate`가 넘겨주는 `URLSearchParams`를 직접 보는 것이 훨씬 정확하다.

13·14번과 보는 방향도 다르다. 13·14는 브라우저가 URL을 되돌려주면 화면이 복원되는가(브라우저→앱)이고, 11번은 조작이 URL에 어떻게 기록되는가(앱→URL)다. 방향이 반대라 한 시나리오로 묶으면 어느 쪽이 깨졌는지 실패 메시지가 말해주지 못한다.

E2E로 갔다면 테스트 수는 줄었겠지만 기본값 생략은 검증하지 못했고, 실패할 때마다 URL 기록이 틀렸는지 복원이 틀렸는지를 손으로 가려야 했을 것이다.

### 이 목록 밖

15개를 다 하고도 테스트할 만한 것이 남는다. 전부 하겠다는 계획은 계획이 아니므로 하나씩 골라 근거를 적는다.

#### 다음에 하면 좋겠다 — 갱신 실패 때 이전 목록 유지 (`updateFailed` 경로)

15개 목록에 없다. 6·7번은 최초 실패를 다루고, 이건 보고 있던 목록이 있는 상태에서 갱신이 실패하는 경우다.

변경 빈도가 높다. `ProductListPage`의 화면 분기(`isFirstLoad`·`isUpdating`·`updateFailed`·`firstLoadFailed`)를 만질 때마다 닿는다. 7주차에 이 경로를 두 번 고쳤다. `keepPreviousData`를 넣고, 그게 실패 때 버려지는 것을 발견해 마지막 성공 조건만 기억하고 데이터는 캐시에서 읽는 방식으로 다시 고쳤다.

실패 비용도 높다. 깨지면 갱신 실패가 최초 실패처럼 보이고 보고 있던 목록이 사라진다. 조용히 나빠지는 종류다. 에러가 안 나고 화면만 비므로 로그에도 안 남는다.

이번 주에 넣지 않은 이유는 하나다. 이 경로를 통합에서 만들려면 성공 → 조건 변경 → 실패라는 3단 응답 시나리오가 필요하고 `placeholderData`와 `lastLoadedParams`의 타이밍에 의존한다. 15개를 먼저 정확히 세우는 것이 우선이다.

#### 앞으로도 안 하겠다 — `shared/ui/select`·`dialog`의 키보드 상호작용

4주차에 직접 만든 헤드리스 Select(↑↓ 이동·Enter 선택·Esc 닫기·품절 건너뛰기)와 Compound Dialog(Portal·Context 조립)다. 테스트하기 좋은 대상처럼 보인다.

변경 빈도가 0에 가깝다. 4주차 이후 손대지 않았다. 6주차 FSD 전환에서 `components/ui` → `shared/ui`로 경로만 옮겼고 내용 변경은 없다.

실패 비용은 0이다. 이 둘을 참조하는 것은 `src/examples/selectExample.tsx`·`dialogExample.tsx`뿐이고, `examples/`는 어떤 라우트에서도 도달하지 않는다. 깨져도 사용자에게 닿지 않는다.

살아 있는 화면에 다시 들어오는 순간(예: 정렬 `<select>`를 이걸로 교체) 비용이 0에서 올라간다. **그때 한다.** 지금 넣으면 사용자에게 닿지 않는 코드를 리팩터할 때마다 테스트가 발목을 잡는 쪽으로만 작동한다.

## 2·3단계에 무엇이 들어가는지

이 문서만 읽고 예측할 수 있어야 한다는 완료조건에 맞춰 정리한다.

### 2단계

위 표대로 단위 3항목 · 통합 9항목 · E2E 3항목. 항목마다 정상과 경계를 함께 넣는다(10번은 1페이지에서 "이전" disabled, 마지막에서 "다음" disabled). `waitFor`는 첫 대기에만 쓰고 나머지는 동기 단언으로 둔다.

조회 방식은 현재 DOM에 맞춰 항목별로 정한다. `getByRole` 우선이 원칙이지만 이 화면의 모든 대상이 role을 갖고 있지는 않다.

| 대상 | 마크업 | 조회 |
| --- | --- | --- |
| 필터·정렬 | `<label>카테고리<select>` | `getByLabelText("카테고리")` |
| 검색 | `<form role="search">` + `<label>검색<input>` | `getByRole("search")` · `getByLabelText("검색")` |
| 담기·찜 버튼 | `<button aria-label="{상품명} 장바구니" aria-pressed>` | `getByRole("button", { name: /장바구니/ })` + `toHaveAttribute("aria-pressed")` |
| 페이지 이동 | `<nav aria-label="페이지 이동">` + `<button>이전\|다음</button>` | `getByRole("navigation", { name: "페이지 이동" })` → `getByRole("button", …)` + `toBeDisabled()` |
| 갱신 중 알림 | `<p role="status">` | `getByRole("status")` |
| 에러 | `<div role="alert">` | `getByRole("alert")` |
| 최초 로딩 | `<p className="shop-state">`, role 없음. 감싼 `<section aria-busy>`가 상태를 갖는다 | `getByRole("region", { name: "상품 검색 결과" })`의 `aria-busy` + `getByText(/불러오는 중/)` |
| 헤더 개수 | `<span aria-label="장바구니 3개">`, span은 role이 없다 | `getByLabelText(/장바구니 \d+개/)` |
| 스켈레톤 | `aria-hidden="true"` | 조회하지 않는다. 보조기술에 안 보이는 것이 계약이다. 개수는 기존 `ProductListSkeleton.test.tsx`가 단위로 덮는다 |

`getByRole`로 안 되는 자리는 최초 로딩과 헤더 개수 둘이다. 테스트를 위해 `role="status"`를 새로 붙이지는 않는다. 접근성 개선으로는 타당하지만 이번 주에 구현을 바꾸는 이유로 삼기엔 근거가 약하고, `aria-busy`와 `aria-label`이 이미 사용자가 인식하는 경로다. `getByTestId`는 쓰지 않는다.

**구독 범위는 이 설계로 보장되지 않는다.** 12번은 담김/빠짐이 상품별로 맞는가까지만 지킨다. selector가 store 전체를 구독하는지 id별로 좁게 구독하는지는 렌더 결과로 구분되지 않는다. 전체를 구독해도 계산이 id별이면 화면은 정상이다. 그걸 계약으로 잡으려면 렌더 횟수를 세야 하고, 그건 구현 내부에 붙는 테스트다. 5주차에 selector를 나눈 이유(리렌더 경계)는 테스트가 아니라 주석과 배럴 경계로 지킨다.

### 3단계

방법론마다 최소 하나씩 구현을 망가뜨린다. 쉬운 곳을 고르면 의미가 없으므로 경계와 분기에서 고른다.

| 방법론 | 변이 후보 | 무엇을 재는가 |
| --- | --- | --- |
| 단위 | `resolveProductListQuery`의 `page >= 1` → `page >= 0` | 3번이 경계를 실제로 단언하는가 |
| 통합 | `setParams({ category, page: 1 })`에서 `page: 1` 제거 | 8번이 목록이 바뀐다만 보고 page 리셋을 안 보는지 |
| E2E | `useProductListQuery`의 `history: "push"` → `"replace"` | 13번이 진짜 히스토리를 보는가 |

단위 변이가 3번 항목과 겹치는 것은 의도다. 경계를 고른 이유가 곧 변이가 잡힐 것으로 기대하는 이유다. 안 잡히면 3번의 단언이 부족하다는 뜻이 된다.
