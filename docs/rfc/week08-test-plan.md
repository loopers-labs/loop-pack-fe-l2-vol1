## 1. 검증 계획

- 화면 없이 계산할 수 있는 로직은 단위 테스트로 검증한다.
- 화면과 API 응답이 함께 움직이는 기능은 통합 테스트로 검증한다.
- URL, 방문 기록, 새로고침이 필요한 기능은 E2E로 검증한다.
- 검증 명령의 E2E는 기존 로컬 서버를 재사용하지 않고 현재 production build로 새 서버를 시작한다.
- 9주차 확정 범위는 상품 2개, 인증 4개, 장바구니 병합 1개, 주문 1개로 총 8개다.

| 기능 | 방법 | 선택 이유와 검증 범위                                                                              | 실패 시 알 수 있는 것                           |
| --- | --- |-------------------------------------------------------------------------------------------|-----------------------------------------|
| 장바구니·위시리스트 개수 계산 | 단위 | Zustand 상태만으로 서로 다른 상품 수, 중복 상품의 수량과 찜 해제를 계산할 수 있다.                                      | 상품 수와 수량을 잘못 구분하거나 찜 해제가 동작하지 않는다.      |
| 장바구니 소유자별 저장 키 | 단위 | `guest`와 `user:<userId>` 저장 키, store 복원, 전체 비우기의 영속성을 DOM 없이 검증한다. | 의도한 로그인 병합 외에 회원 간 상품이 섞이거나 주문 후 비운 상품이 되살아난다. |
| 장바구니 로그인 병합 | 통합 | Provider를 비회원 → 회원 → 비회원으로 바꾸고 기존 회원 상품과 guest 상품의 수량 합산, guest 정리, hydration 상태를 확인한다. | guest 상품이 유실·중복되거나 로그인 뒤 guest 저장소가 남는다. |
| 장바구니 탭 간 동기화 | 통합 | 활성 owner의 `storage` 변경은 다시 hydrate하고 owner가 바뀌면 새 상태를 읽는지 확인한다. 실제 다중 탭 동기화가 제품의 인수 조건이 되기 전에는 E2E로 올리지 않는다. | 다른 탭의 오래된 store가 비운 장바구니를 되살리거나 회원 상품을 잘못된 owner에 저장한다. |
| 공개 장바구니 빈 상태·전체상품 피드 | 통합 | `/cart` 콘텐츠의 hydration, 빈 상태 문구, `/products` 링크, 피드에서 장바구니로 전환되는 흐름을 확인한다. 피드의 페이지 누적·오류 복구는 같은 hook과 trigger를 사용하는 상품 목록 통합 테스트가 담당한다. | 빈 상태가 깜빡이거나 상품 링크·담기 후 화면 전환이 잘못 동작한다. |
| 장바구니 할인 상품·결제 요약 | 단위·통합 | 상품 가격 정책은 순수 함수로 계산하고, 할인 상품을 담았을 때 상품 행과 결제 요약의 전체 할인액을 화면 문구로 확인한다. | 할인율·원가·상품별 할인금액이 빠지거나 결제 요약의 할인 합계가 판매가와 어긋난다. |
| 주문서 제출 | 통합 | 실제 cart store와 상품 조회 HTTP 경로를 사용하고 주문 POST만 MSW로 가로챈다. 성공 후 장바구니 비움과 주문 내역 이동까지 확인한다. | 주문 버튼이 요청을 보내지 않거나 성공 뒤 장바구니와 화면 전환이 갱신되지 않는다. |
| 주문 제출 → 주문 내역 반영 | E2E | 워커별 로그인 계정과 상품 1개가 든 회원 장바구니를 준비한다. 주문 버튼을 누른 뒤 `/orders`에서 해당 상품을 포함한 새 주문을 확인한다. | 실제 쿠키, 주문 POST·GET, 페이지 이동과 주문 내역 렌더링의 연결이 끊긴다. |
| URL 조건 → 무한 query key | 단위 | 기본값 생략·명시와 검색·카테고리·정렬 조건을 DOM 없이 비교할 수 있다. 페이지 번호는 query key가 아니라 `pageParam`으로 분리한다.                  | 필터가 다른 목록이 같은 캐시를 쓰거나 각 페이지가 서로 다른 목록 캐시로 분리된다. |
| `getProductList` 필터·정렬·페이지 계산 | 단위 | 검색·필터·정렬·페이지 계산이 한곳에 모여 있고 잘못되면 목록 전체에 영향을 주기 때문에 골랐다. DOM과 네트워크 없이 검증할 수 있는 순수 함수이기도 하다. | 필터 결과, 상품 순서, 전체 개수나 페이지 계산이 잘못된다.      |
| 목록 로딩 → 성공 | 통합 | MSW로 응답을 늦추고 로딩 화면이 상품 목록과 전체 개수로 바뀌는지 확인한다.                                              | 응답을 받아도 로딩 화면에서 상품 목록으로 넘어가지 않는다.       |
| 목록 빈 결과 | 통합 | 요청은 성공했지만 상품이 없을 때 전체 개수 0과 빈 결과 안내가 나타나는지 확인한다.                                          | 빈 목록을 계속 로딩 중이거나 에러인 것처럼 보여준다.          |
| 목록 에러 | 통합 | 첫 진입에서 서버가 500을 반환할 때 에러 안내와 재시도 버튼이 나타나는지 확인한다.                                          | 요청 실패를 알리지 않거나 다시 시도할 방법이 없다.           |
| 에러에서 재시도로 복구 | 통합 | 첫 요청이 실패한 경우 재시도로 복구되는지 확인한다. 재시도도 실패하면 에러 화면이 나와야 한다.                                    | 재시도가 새 요청을 보내지 않거나 성공한 뒤에도 에러가 남는다.     |
| 카테고리 변경 → 누적 목록 초기화 | 통합 | 2페이지까지 누적한 뒤 카테고리를 바꾸고 새 조건의 1페이지 상품만 표시하는지 확인한다.                                  | 이전 조건의 상품과 새 필터 결과가 한 목록에 섞인다.            |
| 정렬 변경 → 순서 변경 | 통합 | 가격 정렬 요청과 화면 순서를 확인하고 가격이 같은 상품도 모두 남는지 확인한다.                                             | 정렬 조건이 빠지거나 상품 순서와 개수가 잘못된다.            |
| 목록 끝 도달 → 다음 상품 누적 | 통합 | `더 보기`와 observer가 같은 다음 페이지 동작을 사용하며 마지막 페이지에서 멈추는지 확인한다.                                      | 기존 상품을 교체하거나 같은 페이지를 중복 요청한다.            |
| URL 직접 진입·새로고침 복원 | E2E | 카테고리·정렬이 담긴 URL로 직접 진입하고 새로고침한 뒤에도 선택값과 상품 목록이 같은지 확인한다. | 공유 URL이나 새 문서에서 같은 필터와 목록을 복원하지 못한다. |
| 담기 → 헤더 개수 · 다시 누르면 빠짐 | 통합 | 장바구니에는 같은 버튼을 다시 눌러 제거하는 기능이 없다. 같은 토글 동작을 제공하는 위시리스트와 헤더를 함께 확인한다.                       | 찜 버튼, 위시리스트 상태와 헤더 개수가 함께 바뀌지 않는다.      |
| 뒤로·앞으로 가기로 필터 복원 | E2E | 브라우저의 뒤로가기와 앞으로가기에서 선택값과 상품 목록이 함께 돌아오는지 확인한다.                                            | 방문 기록을 이동해도 이전 필터와 목록이 복원되지 않는다.        |
| 비회원 장바구니 → 로그인 병합 | E2E | 비회원 상품 1개를 준비하고 주문하기 → 로그인 뒤 `/orders/new`에서 같은 상품과 수량이 유지되는지 확인한다. | 실제 쿠키와 사용자별 `localStorage`가 바뀔 때 비회원 상품이 유실된다. |
| 공개 `/cart` → 보호 주문서 | 통합·E2E | 빈 장바구니의 공개 상태와 상품 링크는 통합 테스트로 확인한다. 실제 주문하기 → 로그인 → `/orders/new` 복귀는 guest 병합 E2E에 포함한다. | 장바구니가 불필요하게 보호되거나 주문서 인증 경계를 우회한다. |

### 현재 구현에 없는 동작

장바구니의 `담기`는 같은 상품을 다시 누르면 제거하지 않고 수량을 늘린다. `다시 누르면 빠짐`은 위시리스트의 `찜 → 찜 해제`로 검증하고, 장바구니의 상품 종류와 수량 계산은 단위·통합 테스트에서 확인한다.

상품 목록은 페이지 번호 UI를 제공하지 않는다. API의 `page`는 무한 query가 다음 묶음을 요청하는 전송 규약으로만 사용한다. 사용자가 조작하는 URL에는 검색·카테고리·정렬만 남긴다.

### 구현 전에 고칠 코드

- `productListQueryOptions`는 카테고리 생략과 `category: "all"`에 서로 다른 query key를 만든다. 기본 카테고리를 `"all"`로 정규화한다.

## 2. 애매했던 판단

| 대상 | 결정                                                                 | 다른 방법을 선택했을 때                                         |
| --- |--------------------------------------------------------------------|-------------------------------------------------------|
| 카테고리·정렬·무한 스크롤 | 통합 테스트로 UI·요청·응답과 다음 페이지 계산을 확인한다. URL·방문 기록·새로고침만 E2E로 검증한다. observer가 동작하지 않아도 `더 보기`가 같은 동작을 제공하므로 별도 E2E는 두지 않는다. | 모든 누적 동작을 E2E로 확인하면 요청마다 500ms를 기다려야 하고 실패 원인을 좁히기 어렵다. |
| 위시리스트와 헤더 개수 | 상품 목록과 `HeaderNav`가 같은 Zustand 상태를 보는지 통합 테스트로 검증한다.               | `RootLayout`까지 검증할 수 있지만 장바구니 E2E와 범위가 겹친다.           |
| 회원별 분리와 guest 장바구니 병합 | 저장 키와 수량 병합은 단위, Provider 전환·guest 정리·`storage` 이벤트는 통합, 실제 로그인 뒤 주문서에 상품이 유지되는지만 E2E로 검증한다. | 로그아웃과 다중 탭까지 같은 E2E에 넣으면 인증 필수 시나리오와 중복되고 실패 원인을 좁히기 어렵다. |

## 3. 범위 밖 테스트

| 판단 | 대상과 이유                                                                                                                                       |
| --- |----------------------------------------------------------------------------------------------------------------------------------------------|
| 유지할 것 | 상품 목록이 보이는 상태에서 필터 요청이 실패해도 기존 목록과 오류 안내를 함께 유지하고, 다시 시도하면 새 목록으로 복구하는 통합 테스트를 둔다. 검색·필터 기능을 바꿀 때 영향을 받기 쉽고, 잘못되면 사용자가 보던 목록이 사라지기 때문이다. |
| 추가하지 않을 것 | Tailwind 클래스나 HTML 구조 및 화면 전체 스냅샷은 테스트하지 않는다. 기능은 그대로인데 디자인이나 마크업만 바꿔도 테스트가 실패하기 때문이다. 상품 정보가 보이고 버튼을 사용할 수 있는지만 확인한다.                       |

## 4. 테스트가 실제로 버그를 잡는지 확인하기

| 방법 | 바꿀 코드 | 잡아야 하는 문제 |
| --- | --- | --- |
| 단위 | `getProductList` 페이지 시작 위치에서 `page - 1` 제거 | 1페이지가 두 번째 상품 묶음부터 시작한다. |
| 통합 | 무한 query key에서 카테고리 제거 | 기존 카테고리 상품과 새 필터 결과가 한 목록에 섞인다. |
| E2E | URL history를 `push`에서 `replace`로 변경 | 뒤로가기로 이전 필터를 복원하지 못한다. |
