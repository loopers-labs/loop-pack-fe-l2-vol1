# 8주차 테스트 설계 — 무엇을 지킬지 먼저 정한다

## 먼저 밝힐 것

이 레포에는 이미 테스트 269건이 있다. 15개 검증 대상 중 절반 가까이는 5주차와 7주차에 이미
어떤 형태로든 덮여 있다. 그래서 이번 주에 새로 짜는 것보다 **이미 있는 것을 어느 방법론에
둘지 다시 정하고, 잘못 그어져 있던 경계를 옮기는 일**이 더 크다.

옮겨야 할 경계는 둘이다.

- 기존 테스트 7개 파일이 `vi.stubGlobal('fetch', ...)`로 앱의 전송 계층을 바꿔치기하고 있었다.
  요청이 실제로 나가지 않으니 URL 조립과 상태 코드 해석은 검증 밖이었다.
- 테스트 37개 파일이 전부 jsdom에서 돌고 있었다. 그중 22개는 DOM을 쓰지 않는다.

커버리지 수치는 목표로 삼지 않는다. 이 문서의 판단 근거는 "빨간불이 되면 무엇을 알게 되는가"
하나다. 그 칸을 채울 수 없는 항목은 여기 넣지 않았다.

## 1. 검증 방법

| # | 검증 대상 | 방법론 | 그렇게 정한 이유 | 빨간불이 되면 알게 되는 것 |
| --- | --- | --- | --- | --- |
| 1 | 장바구니와 위시리스트 개수 파생 | 단위 | 담기 규칙과 개수 파생은 React 밖에서 성립하는 순수 규칙이다. 렌더를 거치면 실패가 규칙 탓인지 배선 탓인지 갈리지 않는다. hook이 그 규칙을 실제로 구독하는지는 12번이 화면에서 본다 | 같은 상품을 두 번 눌러도 빠지지 않는다. 개수가 담긴 ID 수와 다른 값을 센다 |
| 2 | URL 조건에서 query key | 단위 | 조건 객체 하나가 key와 요청 URL 양쪽의 원본이다. 순수 조립이라 렌더 없이 비교할 수 있고, 캐시가 갈리는 지점은 화면으로는 오히려 보이지 않는다 | 조건이 다른데 key가 같아 앞 조건의 결과를 현재 결과처럼 보여준다. 서버와 브라우저가 같은 URL에서 다른 key를 만들어 hydration 직후 같은 요청이 다시 나간다 |
| 3 | `describeEmptyResult` (0건 설명 문장) | 단위 | 직접 고른 순수 로직이다. 0건 화면에서 사용자가 무엇을 되돌려야 할지 알려주는 유일한 자리인데, 조건 조합이 16가지로 갈린다. 부수효과가 없어 조합을 화면 없이 전부 밟을 수 있다 | 걸지 않은 필터를 걸었다고 말한다. 건 필터를 빠뜨려 사용자가 지울 것을 못 찾는다 |
| 4 | 목록 로딩에서 성공 | 통합 | 대기 화면과 결과 화면은 서버 응답과 컴포넌트 상태가 만나는 자리다. 어느 한쪽만으로는 확인되지 않는다 | 응답 전에 빈 화면이 보인다. 응답이 온 뒤에도 대기 화면이 남는다 |
| 5 | 목록 빈 결과 | 통합 | 0건도 성공 응답이다. 개수 행과 조건 문장이 성공 경로와 같은 자리에 있어야 하는데, 그 자리는 렌더 결과로만 확인된다 | 0건인데 개수 행이 사라져 화면이 밀린다. 조건에 맞는 상품이 없는 것과 범위 밖 페이지가 같은 화면이 된다 |
| 6 | 목록 에러 | 통합 | 실패의 종류에 따라 화면이 달라야 한다. 상태 코드 해석과 화면 분기가 같이 걸리는 자리라 응답을 네트워크에서 만들어야 한다 | 실패가 화면에 드러나지 않고 대기가 계속된다. 실패 문구만 있고 벗어날 출구가 없다 |
| 7 | 에러에서 재시도로 복구 | 통합 | 재시도는 버튼 클릭에서 새 요청까지 이어지는 행위다. 요청이 실제로 나가야 "무엇을 다시 요청했는가"를 볼 수 있다 | 재시도가 실패한 조건이 아닌 다른 조건을 요청한다. 성공 응답이 와도 오류 화면이 남는다 |
| 8 | 카테고리 변경으로 목록 변경 | 통합 | URL 상태, query key, 요청, 렌더가 한 줄로 이어지는지가 대상이다. 조각으로 나누면 이어지지 않아도 전부 통과한다 | 조건만 바뀌고 요청이 나가지 않아 이전 목록이 남는다. page가 1로 돌아가지 않아 3페이지의 다른 카테고리를 연다 |
| 9 | 정렬 변경으로 순서 변경 | 통합 | 순서는 서버가 정하고 화면이 그린다. 요청까지 내려가지 않으면 "정렬을 보냈다"까지만 확인되고 순서는 확인되지 않는다 | 정렬이 URL과 요청에만 반영되고 화면 순서가 그대로다 |
| 10 | 페이지 이동으로 목록 변경 | 통합 | 표기와 목록이 같은 응답을 따르는지가 핵심이고, 그 어긋남은 전환 중에만 보인다 | 표기 페이지와 실제 목록이 어긋난다. 첫 페이지에서 이전 버튼이 열려 있다 |
| 11 | 조작이 URL에 반영되고 URL로 재진입 | 통합 | 판단이 갈렸다. 아래 2절에 적는다 | 조작 결과를 주소로 공유하면 다른 화면이 열린다. 기본값이 URL에 남아 같은 화면이 두 주소를 갖는다 |
| 12 | 담기로 헤더 개수 변경, 다시 누르면 빠짐 | 통합 | 1번에서 규칙을 잡았으니 여기서는 배선을 본다. 서로 다른 컴포넌트가 같은 원본을 보는지가 대상이라 둘을 함께 렌더해야만 확인된다 | 카드의 상태는 바뀌는데 헤더 숫자가 따라오지 않는다. 위시리스트 토글이 장바구니 숫자를 건드린다 |
| 13 | 뒤로가기와 앞으로가기로 필터 복원 | E2E | 판단이 갈렸다. 아래 2절에 적는다 | 뒤로 갔는데 URL만 바뀌고 화면이 그대로다. 한 번의 조작이 히스토리에 두 번 쌓여 두 번 눌러야 돌아간다 |
| 14 | 새로고침해도 필터 상태 유지 | E2E | 실제 문서 재로드가 필요하다. 서버가 URL 조건으로 먼저 그린 화면과 클라이언트가 이어받은 화면이 같은지는 진짜 재로드에서만 드러난다 | 새로고침하면 조건이 기본값으로 돌아간다. 서버가 그린 목록과 클라이언트가 그린 목록이 달라 화면이 한 번 깜빡인다 |
| 15 | 목록 진입에서 담기, 헤더 확인 | E2E | 조각들이 production build 위에서 이어 붙는지는 조각 테스트로는 알 수 없다. 클라이언트 경계와 번들 분할은 빌드 산출물에만 있다 | 조각마다 통과했는데 실제 빌드에서는 담기 버튼이 눌리지 않는다 |

단위 3개, 통합 9개, E2E 3개다. 15개 모두 지금 구현에 그 기능이 있다.

## 2. 애매했던 판단 두 개

### 11번을 통합에 두고 13번을 E2E에 둔 이유

둘 다 URL과 브라우저 사이의 경계라 같은 칸에 들어갈 것처럼 보인다. 반대쪽으로 갈랐다.

11번이 지키려는 것은 **우리 코드의 계약**이다. 조작이 어떤 query string을 만드는가, 기본값을
URL에서 빼는가, 같은 주소로 다시 들어오면 같은 조건을 읽는가. 전부 우리가 parser와 조립
함수에 적어 넣은 규칙이고, 브라우저가 아니라 우리가 바꾸면 깨진다. 조합도 많다. 검색, 카테고리,
정렬, 페이지가 서로를 어떻게 건드리는지까지 봐야 한다. E2E로 옮기면 한 조합에 수 초씩 든다.

13번이 지키려는 것은 **브라우저의 동작**이다. 우리가 history에 무엇을 얼마나 쌓았는지가
대상이고, 그 결과는 실제 뒤로가기 버튼을 눌러야 나온다. jsdom에도 history가 있지만 그것은
흉내다. 4주차에 디바운스가 히스토리를 오염시켜 뒤로가기가 한 번에 돌아가지 않던 회귀가 있었고,
그때 증상은 브라우저에서 먼저 보였다. 흉내 위에서 초록을 받아도 "브라우저에서 된다"고 말할
근거가 되지 않는다.

다른 쪽을 골랐다면. 11번을 E2E로 올렸다면 조합 검증을 포기하고 대표 한두 개만 봤을 것이다.
지금 통합에서 잡는 "카테고리를 바꾸면 page가 URL에서 사라진다" 같은 경계는 빠졌을 것이다.
13번을 통합으로 내렸다면 실행은 1초 아래로 떨어지지만, 히스토리 항목 수가 틀린 회귀는
그대로 통과했을 것이다. jsdom의 history는 우리가 부른 만큼 쌓이고 그것을 그대로 되돌려주기
때문이다. 즉 이 항목에서는 흉내가 검증 대상 자체를 지운다.

### 1번을 단위에 두고 12번을 통합에 둔 이유

개수 파생은 처음에 통합 후보였다. 사용자가 보는 것은 헤더의 숫자이지 배열의 length가 아니기
때문이다. 그런데 그렇게 두면 두 가지가 한 테스트에 묶인다. 토글 규칙이 맞는가와 헤더가 그
규칙을 구독하는가. 실패했을 때 어느 쪽인지 실패 메시지가 말해주지 않는다.

그래서 규칙을 React 밖으로 꺼냈다. `toggleCartId`와 `cartCountOf`를 순수 함수로 노출하고
store와 hook은 그것을 구독하는 배선만 남겼다. 규칙은 1번이 DOM 없이 잡고, 배선은 12번이
화면에서 잡는다. 실패 메시지만 보고 어디를 열어야 할지 갈린다.

다른 쪽을 골랐다면. 앱 코드를 그대로 두고 12번 하나로 합쳤을 것이다. 테스트 수는 줄었겠지만
"같은 상품을 두 번 담으면 순서가 어떻게 되는가" 같은 경계는 화면으로 확인하기 번거로워
안 적었을 가능성이 높다. 실제로 이번에 경계를 적다가 잘못된 기대(빈 목록에서 토글하면
빈 목록)를 하나 썼고, 순수 함수라 즉시 빨간불로 드러났다.

## 3. 이 목록 밖

### 다음에는 할 것: 홈의 카테고리 링크로 목록에 도착하는 경로 (E2E)

홈에서 목록으로 가는 유일한 진입점이다. 지금은 링크의 `href`가 맞는지까지만 본다. 그 주소로
실제로 이동했을 때 그 카테고리의 목록이 열리는지는 아무도 확인하지 않는다.

근거는 실패 비용이다. 변경 빈도는 낮다. 카테고리 계약이 바뀔 때만 움직인다. 그런데 깨지면
홈에서 상품으로 가는 길이 통째로 끊기고, 홈도 목록도 각자는 멀쩡하니 어느 테스트도 빨간불이
되지 않는다. 비용이 큰데 아무도 감지하지 못하는 조합이라 다음 순번에 둔다.

### 앞으로도 안 할 것: `/playground`와 `/performance-lab` 화면

4주차와 7주차의 실험 화면이다. 여기에 테스트를 늘리지 않는다.

근거는 둘 다다. 변경 빈도가 높다. 실험을 할 때마다 갈아엎는 화면이고, 그때마다 테스트를
따라 고치게 된다. 실패 비용은 낮다. 사용자 동선이 아니라 우리가 무언가를 재보려고 만든
자리이고, 깨지면 그 자리에서 즉시 보인다. 이미 있는 `SizeSelect` 테스트는 4주차의 유산이라
남기지만, 이 영역에 새로 쓰지 않는다.

## 4. 환경 분리 — 확장자가 환경을 선언한다

`.test.ts`는 node에서, `.test.tsx`는 jsdom에서 돈다. vitest projects 둘로 나눴다.

이 규약을 고른 이유는 규약과 실제가 이미 일치하기 때문이다. DOM이 필요한 테스트는 React를
그리고, React를 그리면 JSX를 쓴다. 파일마다 주석이나 별도 접미사를 붙이지 않아도 지금 있는
37개 파일 중 34개가 그대로 맞았다. 나머지 3개는 `renderHook`만 쓰던 파일이었고, 그중 둘은
순수 규칙 테스트로 바뀌면서 node로 갔고 하나(`resetStores.test.tsx`)는 확장자를 바꿔 jsdom에 남겼다.

규약이 문서에만 있으면 조용히 깨진다. 그래서 ESLint가 `**/*.test.ts`에서
`@testing-library/*` import를 막는다. 실수하면 lint가 파일 확장자를 바꾸라고 말한다.

### 측정

`vitest run`의 환경 셋업 시간을 비교했다. 같은 트리에서 3회씩 돌렸다.

| 구성 | 환경 셋업 | 전체 | 결과 |
| --- | --- | --- | --- |
| 분리 (node 22 + jsdom 15) | 9.3s, 12.4s, 13.9s | 2.9s, 3.3s, 3.7s | 37 파일 통과 |
| 전부 jsdom (37) | 21.7s, 23.5s, 23.7s | 4.3s, 4.6s, 4.7s | 36 파일 통과, 1 파일 실패 |

환경 셋업은 절반으로 줄었다. 전체 시간은 1.3초쯤 줄었다. 셋업이 워커에 병렬로 흩어져서
줄어든 시간이 벽시계에 그대로 나타나지는 않는다. 지금 규모에서 이 차이는 크지 않고,
그 사실을 숨기지 않는다. 대신 이 비용은 파일 수에 비례해 붙고, DOM이 필요 없는 테스트가
앞으로도 더 빨리 늘어난다.

더 중요한 것은 마지막 칸이다. 전부 jsdom으로 돌리면 `shared/api/http.test.ts`의 취소 전달
테스트가 실패한다. jsdom의 fetch 구현이 node와 달라서다. 전송 계층은 서버 실행에서도 도는
코드인데, 브라우저 흉내 환경에서만 확인하면 통과 여부 자체가 실제와 달라진다. 느려지는 것보다
이쪽이 크다.

대조군 재현 방법. 아래 설정을 `vitest.alldom.config.ts`로 두고 `pnpm vitest run --config vitest.alldom.config.ts`.

```ts
export default defineConfig({
  plugins: [react()],
  test: {
    name: 'all-dom',
    env: { NODE_ENV: 'test' },
    environment: 'jsdom',
    environmentOptions: { jsdom: { url: 'http://localhost:3000' } },
    setupFiles: ['src/test/setup.dom.ts'],
    include: ['src/**/*.test.ts', 'src/**/*.test.tsx'],
  },
  resolve: { alias: { '@': new URL('./src', import.meta.url).pathname } },
})
```

### 나누다가 드러난 것

node 환경에서 `src/app/api/products/route.test.ts`가 12.4초 걸렸다. jsdom에서는 45밀리초였다.
mock API의 고정 지연 500ms는 `process.env.NODE_ENV === 'test'`일 때만 꺼지는데, jsdom 환경에서는
Vite가 이 표현식을 `'test'`로 치환해 지연이 꺼져 있었고 node 환경에서는 실행 환경의 값
(`development`)이 그대로 남아 지연이 걸렸다. 지연을 끄는 조건이 환경에 따라 다르게 성립하고
있었던 것이고, 전부 jsdom으로 돌리는 동안에는 그 사실이 보이지 않았다.
`vitest.config.ts`에서 `env: { NODE_ENV: 'test' }`를 명시해 두 환경에서 같게 만들었다.

## 5. 모킹 경계 — 네트워크에서 자른다

앱 코드의 `fetch`는 건드리지 않는다. 요청은 실제로 나가고 MSW가 그것을 가로챈다.

바꿔치기하던 곳은 7개 파일이었다. 옮기면서 달라진 것이 셋이다.

- 요청 URL을 mock 호출 인자가 아니라 **실제로 나간 요청**에서 읽는다. 조립 함수만 맞고
  전송이 다른 경로로 나가는 경우를 이제 잡는다.
- 실패를 `Promise.reject(new TypeError())`가 아니라 `HttpResponse.error()`로 만든다.
  전송 계층이 그 실패를 `NetworkError`로 승격하는 경로가 검증 안에 들어왔다.
- 취소를 "신호가 전달되었는가"가 아니라 "진행 중인 요청이 실제로 끊기는가"로 확인한다.
  이 테스트는 node 환경에서만 통과한다. 4절에 적은 그대로다.

핸들러 원칙은 셋이다.

- 기본 핸들러에는 **성공 경로만** 둔다. 실패, 지연, 빈 결과는 그것을 확인하는 테스트 안에서
  `server.use`로 덮고 `afterEach`의 `resetHandlers`가 되돌린다.
- 응답 본문은 route와 **같은 함수**로 만든다. `selectProducts`와 `selectHome`을 mock 백엔드에
  하나만 두고 route와 핸들러가 함께 쓴다. 목록을 각자 만들면 통합 테스트가 통과해도 실제
  응답과 다른 목록을 본 것이 된다.
- 잡히지 않은 요청은 **실패**로 만든다(`onUnhandledRequest: 'error'`). 조용히 나가면 개발 서버가
  떠 있는지에 따라 결과가 달라진다.

격리는 setup에서 잡는다. 전역 store는 `afterEach`마다 비운다. `localStorage`는 이 앱이 쓰지
않는다. 테마는 쿠키에 있고 서버가 읽는다. 그래서 지울 것이 없다는 사실을 여기 적어 둔다.

## 6. E2E는 어느 명령에 두는가

`pnpm test`에는 넣지 않고 `pnpm check`에는 넣는다.

`pnpm test`는 저장할 때마다 도는 루프다. E2E는 production build가 있어야 의미가 있고
build 한 번이 루프를 멈춘다. 반면 `pnpm check`는 커밋과 PR의 게이트이고 이미 build를 돈다.
게이트 밖에 두면 아무도 돌리지 않는 테스트가 되고, 그러면 있으나 마나다.
CI는 이 명령 하나를 그대로 실행하고 chromium을 이미 설치한다.

명령은 둘로 나눈다. build를 누가 맡는지가 다르다.

| 명령 | 무엇을 하는가 | 어디서 쓰는가 |
| --- | --- | --- |
| `pnpm test:e2e` | build한 뒤 E2E | 단독 실행. 산출물이 있는지 신경 쓰지 않아도 된다 |
| `pnpm test:e2e:prebuilt` | 이미 있는 산출물 위에서 E2E | `pnpm check`. 앞 단계의 build를 그대로 쓴다 |

나누지 않고 Playwright 설정이 build까지 맡게 두면 `pnpm check`가 같은 빌드를 두 번 돈다.
실제로 그렇게 두고 재보니 E2E 구간이 8.8초에서 2.5초로 줄었다. 대신 `prebuilt`는 산출물이
없으면 실패한다. 조용히 개발 서버로 내려가는 것보다 낫다고 봤다.

Playwright는 `pnpm build && pnpm start` 위에서 돌린다. 개발 서버로만 통과하는 결과는 인정하지
않는다. 실제로 다른 것이 셋이다. 서버 컴포넌트의 사전 렌더, mock API의 500ms 고정 지연,
번들 분할. 재시도는 0으로 둔다. 대기는 전부 조건 기반이라 흔들리면 그것이 진짜 실패다.

## 7. AI를 어디에 썼는가

설정 파일 초안, MSW 핸들러, 반복되는 픽스처, 확장자 규약을 지키는 ESLint 룰 초안은 AI가 썼다.
단언의 내용과 모킹 경계, 15개 항목의 방법론 배치, 2절의 판단은 직접 정했다.

거부한 제안도 남긴다. 1번 항목을 DOM 없이 돌리는 방법으로 세 가지를 받았다.
store를 zustand vanilla로 바꿔 React 밖에서 직접 조작하는 안, 앱 코드를 그대로 두고 항목을
통합으로 내리는 안, 순수 규칙만 함수로 노출하는 안이다. 첫 번째는 "화면에는 selector 훅만
공개한다"는 기존 경계를 무르는 값이 커서 거부했다. 두 번째는 2절에 적은 이유로 거부했다.
세 번째를 골랐다.
