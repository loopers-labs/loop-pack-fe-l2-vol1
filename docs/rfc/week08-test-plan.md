| URL 조건 → query key                                                                                                                    | 통합     | URL로 진입했을 때 URL의 검색/카테고리/정렬/페이지 조건을 `useProductListParams`가 해석하고, 이 조건이 React Query의 query key에도 동일하게 반영되는지를 검증하는 테스트이다. URL 조건과 query key의 동일 여부를 확인하는 것이기에 단위 테스트가 아니라 통합 테스트로 분류했다. 실제 주소창을 조작하는 사용자 흐름이나 브라우저 기능을 검증하지 않으므로 E2E 테스트로 분류하지 않았다.                                                                                                                                                                                                                                                                                                        | 서로 다른 URL 조건이 같은 캐시 항목으로 취급되거나 조건 일부가 누락되어, 다른 탐색 조건의 캐시 결과가 재사용될 수 있다.                                                                                                     | **정상:** 검색/카테고리/정렬/페이지가 모두 지정된 URL의 조건이 query key에 동일하게 포함된다.<br>**경계:** 조건이 없는 URL에는 기본값이 반영되고, 0이나 음수 페이지는 하한값 1로 보정된다.                                                   | **통합 실험:** `productsQueryOptions`가 query key를 생성할 때 `query` 전체 대신 카테고리를 제외한 조건만 포함하도록 변경한다.<br>**예상:** 서로 다른 카테고리 URL이 같은 캐시 키로 처리되므로 `URL 조건 → query key` 통합 테스트가 실패해야 한다. |

UI 선택 상태나 Header 개수 반영은 이 테스트가 보장하지 않는다.                                                   | **정상:** 없는 상품 ID는 추가하고 있는 상품 ID는 제거하며, 직렬화한 Set을 같은 값과 타입으로 복원한다.<br>**경계:** 빈 Set을 직렬화/복원해도 빈 Set을 유지하고, Set이 아닌 일반 값은 변경하지 않는다.                                        | **단위 실험:** `toggleSetItem`의 상품 존재 여부 조건을 반대로 변경한다.<br>**예상:** 상품 ID 추가/제거 테스트가 실패해야 한다.                                                                                                                    |
| 목록 로딩 → 성공                                                                                                                        | 통합/E2E | 기존 목록이 없는 최초 URL 진입에서는 Next.js의 `loading.tsx`가 로딩 화면을 담당한다. 실제 라우트 진입과 production build의 로딩 화면에서 성공 목록으로 전환되는 과정을 E2E로 검증한다. 기존 목록이 있는 상태에서 필터를 변경하면 `keepPreviousData`와 `ProductListSection`의 갱신 상태가 동작한다. 이 경우에는 MSW로 응답 시점을 제어해 기존 목록을 유지하다가 새 목록으로 교체되는지를 jsdom 통합 테스트로 검증한다. 현재 구현에서 최초 로딩과 목록 갱신 로딩의 담당 경계가 다르므로 통합과 E2E로 나누어 분류했다.                                                                                                                                                                          | 최초 진입에서 로딩 상태를 안내하지 못하거나 성공 후 목록을 표시하지 못할 수 있다. 기존 목록이 있는 갱신에서는 목록이 사라지거나, 성공 후 새 목록으로 전환되지 않을 수 있다.                                                 | **정상(E2E):** 기존 목록이 없는 최초 URL 진입에서 `loading.tsx`의 로딩 화면을 거쳐 성공한 상품 목록이 표시된다.<br>**경계(통합):** 기존 목록이 있는 갱신 요청에서는 응답을 기다리는 동안 기존 목록을 유지하고, 성공 후 새 목록으로 교체한다. | —                                                                                                                                                                                                                                                 |
| 목록 빈 결과                                                                                                                            | 통합     | API의 빈 목록이 상품 목록 페이지에 전달되었을 때 상품 카드 대신 `검색 결과가 없습니다.`라는 문구가 표시되는지 검증한다. 목록의 빈 결과만 확인하므로 전체 사용자 흐름을 검증하는 E2E 테스트가 아니며, MSW로 빈 응답을 만들어 API 요청과 화면 표시의 연결을 확인하므로 단위 테스트도 아니다. 그래서 통합 테스트로 분류했다. 기존 목록이 없는 최초 요청과 기존 목록이 표시된 상태에서의 갱신 요청을 모두 확인한다. 두 경우를 함께 검증하면 최초 요청에서는 빈 결과를 정상 상태로 안내하는지 확인할 수 있고, 갱신 요청에서는 빈 응답이 성공했는데도 이전 상품이 남아 있는 오류를 확인할 수 있다. 같은 빈 응답이 기존 목록의 유무에 따라 올바르게 처리되는지를 함께 보장할 수 있다는 이점이 있다. | 최초 요청의 빈 응답이 로딩/오류 상태로 잘못 표시되거나, 갱신 결과가 비었는데도 이전 상품이 남아 현재 조건에 상품이 있는 것처럼 보일 수 있다.                                                                                | **정상:** 기존 목록이 없는 최초 요청에서 빈 응답을 받으면 빈 결과 안내를 표시한다.<br>**경계:** 기존 목록이 있는 갱신 요청이 빈 응답으로 성공하면 이전 상품을 제거하고 빈 결과 안내로 전환한다.                                              | —                                                                                                                                                                                                                                                 |
| 목록 에러                                                                                                                               | 통합     | 네트워크 연결 실패나 서버의 오류 응답으로 상품 목록을 조회하지 못했을 때 오류 안내와 재시도 수단이 표시되는지 검증한다. MSW를 통해 목록 API의 실패를 발생시키고, React Query의 오류 상태가 화면에 반영되는 연결을 확인하므로 통합 테스트로 분류했다. 응답 형식과 파싱 오류는 `apiResponseResult` 테스트에서 별도로 검증한다. 기존 목록이 없는 최초 실패에서는 상품 목록 대신 전체 오류 메시지와 재시도 버튼을 표시하고, 기존 목록이 있는 갱신 실패에서는 기존 상품을 유지하면서 인라인 오류와 재시도 수단을 표시하는지도 함께 확인한다.                                                                                                                                                      | 최초 실패에서 오류 사실과 재시도 수단을 알리지 못하거나, 기존 목록이 있는 갱신 실패에서 사용자가 보던 상품을 지우거나 실패 사실을 안내하지 못할 수 있다.                                                                    | **정상:** 기존 목록이 없는 최초 요청이 서버 오류로 실패하면 전체 오류 안내와 재시도 버튼을 표시한다.<br>**경계:** 기존 목록이 있는 갱신 요청이 네트워크 오류로 실패하면 기존 상품을 유지하면서 인라인 오류와 재시도 수단을 표시한다.         | —                                                                                                                                                                                                                                                 |
| 에러에서 재시도로 복구                                                                                                                  | 통합     | MSW의 실패 응답을 성공 응답으로 변경해 재요청부터 React Query의 상태 변경과 화면 복구까지의 연결을 확인하므로 통합 테스트로 분류했다. 재시도 버튼 조작은 jsdom에서 확인할 수 있어 실제 브라우저를 사용하는 E2E 테스트까지 필요하지 않다. 기존 목록이 없는 최초 실패에서는 전체 오류 UI가 정상 목록으로 교체되는지 확인하고, 기존 목록이 있는 갱신 실패에서는 유지하던 기존 목록과 인라인 오류가 새 목록으로 교체되는지 확인한다.                                                                                                                                                                                                                                                             | 최초 실패에서 정상 목록으로 진입하지 못하거나, 갱신 실패에서 재요청이 성공해도 인라인 오류와 이전 목록이 남아 새 결과로 복구하지 못할 수 있다.                                                                              | **정상:** 최초 요청 실패 후 재시도 요청이 성공하면 전체 오류 UI가 정상 목록으로 교체된다.<br>**경계:** 기존 목록이 있는 갱신 실패 후 재시도가 성공하면 인라인 오류와 이전 목록이 사라지고 새 목록으로 교체된다.                              | —                                                                                                                                                                                                                                                 |
| 카테고리 변경 → 목록 변경                                                                                                               | 통합     | query key의 내부 구조를 확인하는 테스트가 아니라, 변경한 카테고리 조건이 API 요청에 올바르게 전달되고 해당 요청의 응답 결과가 화면에 표시되는지를 검증한다. MSW로 요청 조건에 맞는 응답을 제공하고, API 요청부터 상품 목록 표시까지의 연결을 확인하므로 통합 테스트로 분류했다. 기존 목록이 없는 초기 렌더와 기존 목록이 있는 상태에서의 카테고리 변경을 모두 확인한다. 실제 주소창 기록과 재진입은 E2E 항목에서 검증한다.                                                                                                                                                                                                                                                                   | 최초 진입이나 기존 목록에서의 조건 변경 후 선택한 카테고리와 화면의 상품 집합이 일치하지 않아 다른 카테고리 상품이 표시될 수 있다.                                                                                          | **정상:** 카테고리 변경 요청에 선택한 조건이 포함되고 해당 카테고리의 상품으로 목록이 교체된다.<br>**경계:** 페이지가 2 이상인 상태에서 카테고리를 변경하면 페이지를 1로 초기화한 조건으로 요청한다.                                         | —                                                                                                                                                                                                                                                 |

## 목록 밖의 테스트 판단

### 다음에는 하면 좋겠다: 검색/필터 조건 초기화 통합 테스트

- 검색어와 카테고리/정렬/페이지 조건을 적용한 뒤 초기화 버튼을 누르면 모든 조건과 URL이 기본값으로 돌아가고, 기본 조건의 상품 목록이 표시되는 흐름을 MSW 기반 통합 테스트로 추가한다.
- **정상 케이스:** 검색어나 카테고리처럼 하나의 조건을 적용한 뒤 초기화하면 해당 조건과 URL이 기본값으로 돌아가고 기본 상품 목록이 표시된다.
- **경계 케이스:** 검색어/카테고리/정렬을 함께 적용하고 2페이지 이상으로 이동한 상태에서 초기화해도 모든 조건과 페이지가 한 번에 기본값으로 돌아간다.
- **자가 검증 후보:** `resetQuery`에서 페이지 초기화를 제거한다. 검색/필터 조건 초기화 통합 테스트가 URL의 페이지 조건과 상품 목록이 기본값으로 돌아가지 않은 것을 확인해 실패해야 한다.
- 현재 15개 항목의 카테고리/정렬/페이지 목록 변경과 URL 관련 테스트가 조건별 요청/목록 반영이라는 일부 연결을 이미 검증하므로 기반 동작은 겹친다. 그러나 기존 항목은 각 조건을 적용하거나 복원하는 흐름이고, 여러 조건과 페이지를 한 번의 초기화 조작으로 모두 기본값에 되돌리는 계약은 직접 보장하지 않는다.
- 실제 브라우저 기능보다 초기화 버튼, URL 상태 훅, 목록 요청과 렌더링의 연결이 핵심이므로 E2E가 아닌 통합 테스트로 검증한다.
- **변경 빈도:** 상품 탐색 기능이 확장되면 필터 항목, URL 파라미터와 `DEFAULT_PRODUCT_LIST_QUERY`의 기본값이 함께 바뀔 수 있다. 초기화 로직은 모든 조건을 한 번에 다루므로 조건 하나를 추가하면서 reset 대상에서 누락하기 쉽다. 새로운 필터가 추가될 때 해당 조건을 초기화 로직에 포함하지 않으면, 초기화 후에도 일부 조건이 남는 오류가 발생할 수 있다.
- **실패 비용:** 초기화 뒤 검색어/카테고리/정렬/페이지 중 일부가 남으면 URL, 필터 UI와 API 요청 조건이 서로 달라질 수 있다. 사용자는 전체 상품으로 돌아왔다고 생각하지만 제한된 목록을 계속 보게 되고, 남은 조건을 직접 찾아 해제해야 하므로 상품 탐색을 방해하는 실패 비용이 있다. 변경 가능성과 사용자 영향을 고려해 다음 테스트 대상으로 정한다.

### 앞으로도 하지 않겠다: Header의 정적 링크를 통한 페이지 이동

- Header 로고를 선택해 홈(`/`)으로 이동하는 흐름과 상품 메뉴를 선택해 상품 목록(`/products`)으로 이동하는 흐름을 위한 별도 테스트는 작성하지 않는다.
- **변경 빈도:** 두 메뉴는 동적 상태나 조건 분기 없이 목적지가 각각 `/`, `/products`로 고정된 Next.js `Link`다. 정보 구조나 핵심 라우트가 개편되지 않는 한 수정될 가능성이 낮고, 변경이 생겨도 링크 선언 한 곳에서 확인할 수 있다.
- **실패 비용:** 링크 하나가 잘못되어도 상품 목록은 홈의 카테고리 링크나 주소로 진입할 수 있고, 홈도 브라우저 탐색이나 주소로 돌아갈 수 있어 서비스의 상품 탐색 전체가 차단되지는 않는다. 또한 홈과 상품 목록 라우트 자체의 정상 동작은 각 화면의 통합 테스트와 `목록 진입 → 담기 → 헤더 확인` E2E가 이미 검증한다.
- 변경 가능성과 실패 비용이 모두 낮고 목적지 라우트 검증과도 중복되므로, Header 링크의 `href`와 클릭 이동을 별도 테스트로 고정해 얻는 신뢰보다 유지 비용이 더 크다고 판단한다.
