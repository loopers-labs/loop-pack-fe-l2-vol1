## 전제 — 계층을 고르는 순서

표의 방법론 칸은 전부 이 기준으로 정했다. 아래 세 질문을 순서대로 묻고, 처음 "그렇다"가 나오는 곳에서 멈춘다.

1. 컴포넌트를 렌더링하지 않고 값이나 상태만 확인해도 되는가? → **단위** (node 환경)
2. 렌더링된 요소와 상호작용하면 충분한가? → **통합** (Testing Library + jsdom)
3. 실제 브라우저의 탐색·렌더링·API가 있어야 재현되는가? → **E2E** (Playwright)

1과 2의 경계는 "검증하려는 결과가 값과 상태인가, 사용자가 보는 화면인가"다.
2와 3의 경계는 "jsdom에 없는 것(라우팅, 실제 렌더링, 뒤로가기, 브라우저별 차이)이 필요한가"다.

같은 동작을 두 계층에서 중복 검증하지 않는다.

## 1. 검증 방법

| #   | 검증 대상                                                                                                        | 방법론                                        | 그렇게 정한 이유                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | 빨간불이 되면 알게 되는 것                                                                                                                                                                                |
| --- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 장바구니·위시리스트 개수 파생                                                                                    | 단위 (vitest, 기존 테스트 활용)               | 컴포넌트를 렌더하지 않고 store에 저장된 ID와 그 개수만 확인하면 된다. 공통 store의 빈 상태·추가·제거·개수 selector는 `create-collection-store.test.ts`가 이미 검증하므로 같은 테스트를 다시 만들지 않는다. 실제 Header 반영은 12번이 맡는다.                                                                                                                                                                                                                                                                                                                                                                                                    | ID 추가·삭제 후 파생 개수가 실제 collection의 ID 수와 달라진다                                                                                                                                            |
| 2   | URL 조건 → query key                                                                                             | 단위 (vitest)                                 | parser와 key 조립 모두 순수 함수라 렌더링이 필요 없다. URL은 사용자가 직접 고칠 수 있는 입력이므로, 정상 범위 밖의 값이 params로 정규화되는지가 검증 대상이다. 특히 직접 작성한 `parseAsPositiveInteger`의 조건은 nuqs가 대신 검증해주지 않는다. 같은 파일의 `getLatestProductList`(캐시에서 가장 최근 목록을 고르고 상품 목록이 아닌 캐시를 걸러낸다)도 같은 성격의 순수 로직이고 자체 단위 테스트가 있다. 과제 목록 밖이라 항목으로 세우지 않고 기존 테스트를 그대로 둔다.                                                                                                                                                                    | 잘못된 URL 값이 그대로 요청에 흘러가서 목록이 안 나온다. 또는 같은 URL인데 매번 다른 key로 취급되어 캐시가 맞지 않는다                                                                                    |
| 3   | 총 페이지 수 계산 (`totalCount`, `pageSize` → `totalPages`)<br>— 과제 표의 "내 코드에서 고른 순수 로직 1개 이상" | 단위 (vitest)                                 | 라이브러리에 위임한 부분이 없는, 직접 작성한 계산식이다. 경계값(0개, 딱 나누어떨어짐, 1개)이 여럿이고 페이지네이션은 off-by-one이 생기기 쉬운 자리다. 화면 없이 입력·출력만으로 확인된다.                                                                                                                                                                                                                                                                                                                                                                                                                                                       | 페이지 계산이 틀려서 마지막 페이지 상품에 접근할 수 없다                                                                                                                                                  |
| 4   | 목록 로딩 → 성공                                                                                                 | 통합 (RTL + jsdom, MSW)                       | 상태 전이가 화면으로 나타나야 하므로 렌더링이 필요하다. MSW 성공 응답을 지연하고, 응답 전에는 성공 상품이 없으며 응답 후 상품이 노출되는지를 본다. 현재 스켈레톤은 `aria-hidden`이라 스켈레톤 개수·클래스 같은 구현 세부사항은 단언하지 않는다. 최초 진입에 다른 조건의 캐시가 남아 있어도 그 목록을 그리지 않는다는 규칙은 `ProductListResults.test.tsx`가 덮으므로 여기서 겹쳐 보지 않는다.                                                                                                                                                                                                                                                   | 성공 응답이 왔는데도 상품이 끝까지 나타나지 않아 응답을 화면으로 옮기는 경로가 끊긴다                                                                                                                     |
| 5   | 목록 빈 결과 (① 결과 0건 ② 페이지 오버플로우)                                                                    | 통합 (RTL + jsdom, MSW)                       | 4번과 같은 컴포넌트의 다른 분기라 같은 계층에 둔다. 빈 결과가 코드상 두 갈래(`totalCount === 0` / `totalCount > 0`)이고 화면이 다르므로 두 케이스를 모두 본다. ②는 URL을 직접 고쳐야 재현되어 개발 중에 드러나지 않는다. MSW 핸들러가 빈 `products`와 서로 다른 `totalCount`를 돌려주도록 덮어쓴다.                                                                                                                                                                                                                                                                                                                                             | ① 결과가 0건인데 안내 문구가 안 나온다. ② 마지막 페이지를 넘어선 URL로 들어왔을 때 페이지네이션이 사라져서, 화면 안에서 앞 페이지로 돌아갈 방법이 없다                                                    |
| 6   | 목록 에러 (`ApiError` 경로 — ① 최초 실패 ② 갱신 실패)                                                            | 통합 (RTL + jsdom, MSW)                       | 4·5번과 같은 컴포넌트의 `isError` 분기다. MSW가 500을 돌려주면 컴포넌트 안에서 끝나므로 jsdom으로 충분하다. 범위를 `ApiError`로 한정한 이유는 목록의 로딩·빈 결과와 나란히 놓인 항목이라 "목록 자리에서 처리되는 에러"로 읽었기 때문이다. 계약 밖 예외(→ 루트 `error.tsx`) 경로는 3장으로 뺀다. `shouldThrowProductListError`의 분류 규칙 자체는 `queries.test.ts`가 이미 덮고 있고, 여기서는 분류 결과가 화면에 어떻게 나타나는지를 본다. 에러 화면은 코드상 두 갈래다. ① 표시할 데이터가 없는 최초 실패는 목록 자리를 실패 안내로 바꾸고, ② 직전 목록이 남아 있는 갱신 실패는 그 목록을 그대로 두고 흐름 밖 알림만 띄운다. 두 갈래 모두 본다. | ① 통신 오류가 났는데 사용자에게 아무 안내가 없거나, 안내는 뜨지만 재시도할 방법이 없다. ② 조건 변경이 실패했는데 화면에는 이전 조건의 결과가 아무 표시 없이 남아, 사용자가 그것을 새 조건의 결과로 읽는다 |
| 7   | 에러에서 재시도로 복구 (6번의 두 갈래 각각)                                                                      | 통합 (RTL + jsdom, MSW)                       | 6번이 에러 화면이 뜨는지를 본다면 여기는 거기서 빠져나올 수 있는지를 본다. `refetch`가 끊겨 있으면 6번은 초록불이어도 사용자는 갇힌다. 클릭과 재요청뿐이라 jsdom으로 충분하다. MSW 핸들러가 첫 두 응답은 실패, 세 번째 요청은 성공으로 응답하게 한다. 재시도가 한 번 더 실패해도 에러 안내가 유지되는지까지 같은 테스트에서 본다. 갱신 실패 쪽도 같은 구조로 본다 — 재시도가 성공하면 알림이 사라지고 목록이 직전 조건에서 새 조건으로 실제로 갈아끼워지는지까지 단언한다. 목록 노출뿐 아니라 에러 안내가 사라지는 것까지 단언한다 — 에러 상태를 지우지 않고 목록만 덧붙이는 구현도 가능하기 때문이다.                                          | 재시도 버튼을 눌러도 목록이 돌아오지 않아 사용자가 에러 화면에 갇힌다. 또는 목록은 돌아왔는데 에러 안내가 남아 실패한 것처럼 보인다. 갱신 실패에서는 재시도가 성공해도 화면이 직전 조건의 목록에 머무른다 |
| 8   | 카테고리 변경 → 목록 변경                                                                                        | 통합 (RTL + jsdom, MSW, `NuqsTestingAdapter`) | 조작에 따라 목록이 갈리는지만 보므로 렌더링이 필요하고 jsdom으로 충분하다. 주소창 반영과 히스토리는 11·13·14번(E2E)이 맡아 중복을 피한다. `useProductFilters`가 필터 변경 시 `page: 1`을 함께 넣으므로, 3페이지에서 카테고리를 바꿨을 때 페이지네이션이 1을 가리키는지도 같이 단언한다. 요청 파라미터를 들여다보는 대신 화면에 보이는 페이지 번호로 확인한다.                                                                                                                                                                                                                                                                                   | 카테고리를 바꿨는데 목록이 그대로거나, 이전 페이지 번호가 남아 결과가 없는 페이지를 보게 된다                                                                                                             |
| 9   | 정렬 변경 → 순서 변경                                                                                            | 통합 (RTL + jsdom, MSW, `NuqsTestingAdapter`) | 8번과 같은 구조다. 정렬은 서버가 수행하므로 이 테스트가 보는 것은 "정렬이 올바른가"가 아니라 "선택한 정렬로 요청이 나가고 돌아온 순서대로 화면에 그려지는가"다. MSW 핸들러가 정렬별로 다른 순서를 돌려주게 해서 구분한다. 8번과 마찬가지로 페이지네이션이 1로 돌아가는지 본다.                                                                                                                                                                                                                                                                                                                                                                  | 정렬을 바꿨는데 화면 순서가 그대로거나, 이전 페이지 번호가 남아 있다                                                                                                                                      |
| 10  | 페이지 이동 → 목록 변경                                                                                          | 통합 (RTL + jsdom, MSW, `NuqsTestingAdapter`) | 8·9번과 같은 계층이지만 규칙이 반대다. 페이지 이동은 `page`를 1로 되돌리면 안 된다. 필터는 유지한 채 페이지만 바뀌는지를 본다. 페이지만 옮겼는데 선택해둔 카테고리·정렬이 풀리면 안 된다.                                                                                                                                                                                                                                                                                                                                                                                                                                                       | 페이지를 옮겼는데 같은 목록이 계속 보이거나, 페이지를 옮기면서 선택해둔 필터가 풀린다                                                                                                                     |
| 11  | 조작이 URL에 반영 · URL로 재진입                                                                                 | E2E (Playwright)                              | 주소창과 실제 진입이 대상이라 jsdom에는 없는 것들이다. 중심 단언은 URL 문자열이 아니라 **새 브라우저 컨텍스트로 그 주소에 진입했을 때 같은 화면이 나오는가**다. 컨텍스트가 비어 있으면 상태가 URL 말고 다른 곳(스토리지 등)에 있을 수 없으므로, 형식에 묶이지 않고 "URL이 상태를 담는가"를 확인할 수 있다. 여기에 더해 **기본값 생략은 단언한다** — 필터를 바꿀 때 `page`가 URL에서 사라지는지를 본다. 파라미터 순서는 단언하지 않는다. 처음에는 기본값 생략도 단언하지 않기로 했다가 구현 단계에서 뒤집었고, 경위는 「판단 1」에 있다.                                                                                                         | 필터를 걸고 링크를 공유했는데, 받은 사람이 열면 필터가 적용되지 않은 화면이 나온다                                                                                                                        |
| 12  | 담기 → 헤더 개수 · 다시 누르면 빠짐                                                                              | 통합 (RTL + jsdom)                            | 담기·빼기라는 행위가 store를 거쳐 화면에 나타나는지를 본다. 1번이 store에 담긴 값 자체를 봤다면 여기는 그 값이 화면에 반영되는 경로다. 버튼과 헤더가 서로 다른 컴포넌트라 둘을 함께 렌더해 store로 이어지는지 확인한다. 화면에 드러나는 면이 두 곳이므로(헤더 숫자, 버튼의 `aria-pressed`) 둘 다 단언한다. 네트워크가 없는 클라이언트 상태라 MSW는 필요 없다. store가 모듈 전역이고 `persist`를 쓰므로 테스트마다 초기화한다.                                                                                                                                                                                                                   | 담기를 눌렀는데 헤더 개수가 그대로거나, 다시 눌러도 빠지지 않는다. 또는 헤더와 버튼 표시가 서로 어긋난다                                                                                                  |
| 13  | 뒤로·앞으로 가기로 필터 복원                                                                                     | E2E (Playwright) + 통합 (RTL, 가짜 타이머)    | 한 항목을 두 계층으로 나눈 유일한 자리다. 근거는 「판단 2」에 있다. 실제 브라우저의 History API와 Next 라우터가 대상이다. 확정된 검색 조건에서 `goBack()`·`goForward()`를 실행한 뒤 URL, 입력값, 목록이 함께 복원되는지 조건 기반으로 확인한다. 예약된 디바운스 작업의 취소는 실제 시간을 기다리지 않도록 RTL과 Vitest 가짜 타이머로 분리한다. 이 RTL 테스트도 다른 통합 테스트와 같이 `NuqsTestingAdapter`를 쓴다. 처음에는 `nuqs` 모듈을 직접 모킹했다가 되돌렸고, 경위는 「모킹 경계」에 적었다.                                                                                                                                             | 뒤로·앞으로 이동했을 때 URL만 바뀌거나 입력값·목록이 이전 필터와 일치하지 않는다                                                                                                                          |
| 14  | 새로고침해도 필터 상태가 유지                                                                                    | E2E (Playwright, 11번 시나리오에 이어서)      | 11번과 상당 부분 겹친다. 둘 다 "조작 결과가 주소창에 실제로 반영됐는가"를 묻고, 11번이 빈 컨텍스트로 진입해 통과한다면 스토리지가 남아 있는 새로고침은 더 느슨한 조건이다. 그럼에도 유지한 이유는 두 가지다. ① 겹침을 이유로 뺄 만큼의 비용이 없다 — 별도 spec으로 브라우저를 새로 띄우는 게 아니라 11번 시나리오 끝에 `page.reload()`와 단언 한 줄을 붙인다. ② 경로가 완전히 같지도 않다. 11번은 클라이언트 상태가 없는 상태에서 진입하고, 14번은 이미 조작을 마친 상태에서 새로고침한다.                                                                                                                                                      | 필터를 걸어둔 채 새로고침하면 조건이 풀려 처음 화면으로 돌아간다                                                                                                                                          |
| 15  | 목록 진입 → 담기 → 헤더 확인 (+ 새로고침 후 유지)                                                                | E2E (Playwright)                              | 12번과 대상이 겹쳐 보이지만 보는 것이 다르다. 12번은 Header와 버튼을 **테스트가 손으로 붙여** store 연결을 확인하는 반면, 실제 페이지가 그렇게 조립돼 있는지는 아무도 보지 않는다. `'use client'` 경계, 레이아웃의 Header 배치, 상품 카드의 버튼 부착이 전부 12번 밖이다. 15번은 부품이 아니라 배선을 본다. 이미 브라우저를 띄운 김에 새로고침 한 줄을 덧붙여 `persist` 복원까지 덮는다(범위 확장 — 아래 「과제 목록에서 넓힌 것」 참고).                                                                                                                                                                                                       | 각 부분은 동작하는데 실제 페이지에서는 이어지지 않는다 — 담기를 눌러도 헤더가 반응하지 않거나, 담은 내용이 새로고침으로 사라진다                                                                          |

"빨간불이 되면 알게 되는 것"에 "코드가 잘 돌아간다", "컴포넌트가 렌더된다" 같은 답이 나오면 그 항목은 다시 본다.

### 기존 테스트와의 관계

기존 테스트를 모두 유지한 채 같은 시나리오를 새로 추가하지 않는다. 브라우저가 필요 없는 화면 동작은 RTL로 옮기고, 실제 브라우저 경계만 Playwright에 남긴다.

한 대상은 아래 다섯 줄 중 한 곳에만 들어간다.

| 상태                       | 대상                                                                                                                                                                              |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 그대로 유지                | 1번 collection store 단위 테스트, `queries.test.ts` 단위 테스트, `ProductListResults.test.tsx`(조회 상태별 분기)                                                                  |
| 검증 대상 유지, 파일 개편  | `api.test.ts` — [0단계](../week-08/step0-status.md)에서 `fetch` stub 3곳을 MSW 핸들러로 교체하고 `@vitest-environment jsdom` docblock을 붙인다. 무엇을 검증하는지는 바뀌지 않는다 |
| RTL로 이동 (기존 E2E 제거) | 빈 결과와 페이지 오버플로우(5번), 오류와 재시도(6·7번), 카테고리·정렬·페이지 변경이 목록에 반영되는 부분(8~10번), 담기 버튼과 Header 연결(12번)                                   |
| E2E에 남김 (정리만)        | URL 재진입(11번), 뒤로·앞으로 복원(13번), 새로고침(14번), 목록 진입→담기→헤더 배선(15번). 접근 가능한 locator와 단언만 정리하고 브라우저 경계 밖은 걷어낸다                       |
| 신규                       | 3번 `getTotalPages` 단위 테스트, 4~10·12번 RTL 통합 테스트, 13번 디바운스 취소 RTL 테스트                                                                                         |

겹치는 세 자리는 이렇게 가른다.

- 기존 E2E "검색·카테고리·정렬 변경은 URL과 목록을 갱신하고 page를 1로 되돌린다"는 URL 반영만 남기고(11번), 목록이 갈리는지와 페이지 번호가 1로 돌아가는지는 RTL(8·9번)로 옮긴다.
- 기존 E2E "마지막 페이지를 초과하면…"과 "검색 결과가 0건이면 페이지네이션을 표시하지 않는다"는 5번이 RTL에서 두 갈래를 모두 덮으므로 제거한다.
- 기존 E2E "디바운스 대기 중 페이지를 떠나면 검색어 변경을 취소한다"는 제거한다. 판단 2에서 취소를 RTL로 분리해놓고 E2E에도 남겨둔 자리였다. 자세한 경위는 판단 2에 적었다.
- `ProductListResults.test.tsx`는 조회 상태(최초 진입·캐시 잔존·최초 실패·갱신 실패)별로 무엇을 그리는지를 컴포넌트 단위로 본다. 4번과 6번은 같은 화면을 다루지만 `ProductListContent`부터 렌더해 MSW 응답이 화면까지 이어지는 경로를 본다. 상태별 분기 자체는 앞쪽에 맡기고 뒤쪽에서 다시 단언하지 않는다.

### 표를 다 채운 뒤 정한 것

아래는 방법론이 정해지면서 드러난, 구현 단계에서 결정할 사항이다.

**3번 — `totalPages` 계산을 어떻게 부를 것인가** (결정됨)

현재 이 계산은 `src/shared/lib/usePagination.ts` 안에 한 줄로 들어 있다.

```ts
const totalPages = Math.max(1, Math.ceil(totalCount / pageSize))
```

`getTotalPages(totalCount, pageSize)` 순수 함수로 분리하고 `usePagination`은 그 결과를 사용한다. 계산은 React와 무관해 `renderHook`과 jsdom을 세우지 않는 node 단위 테스트가 가장 싸다.

테스트만 통과시키기 위한 seam이 아니다. 페이지 수 계산과 React 상태 연결은 서로 다른 책임이고, 테스트 설계를 계기로 훅 안에 섞여 있던 순수 계산이 드러난 것으로 본다. 공개 동작은 바꾸지 않는다.

**4번 — 로딩 상태를 어떻게 관측할 것인가** (결정됨)

`isPending` 분기가 그리는 스켈레톤에는 로딩임을 알리는 표식이 없다(`aria-hidden`). 테스트가 "아직 로딩 중"을 식별할 방법이 없어 스켈레톤 개수 같은 구현 세부사항에 단언을 묶게 된다.

이번 단계에서는 `aria-busy`를 추가하지 않는다. 대신 MSW 성공 응답에 지연을 주고 응답 전후의 전이를 본다. 이 테스트는 데이터가 화면에 연결되는 실패를 잡지만 스켈레톤 자체가 사라지는 회귀는 잡지 않는다. 접근 가능한 로딩 안내는 별도 접근성 개선으로 다룬다.

**5번 — 페이지 오버플로우를 보정할 것인가** (결정됨)

`?page=99`처럼 마지막 페이지를 넘어선 URL로 들어왔을 때 현재 동작은 "URL을 그대로 두고 빈 화면 + 페이지네이션"이다. 표를 채우다가 "마지막 페이지로 자동 보정해야 하는 것 아닌가"라는 의문이 나왔다.

이번 과제에서는 현재 동작을 검증한다. 자동 클램프는 `totalCount` 응답 이후 URL을 `replace`하고 목록을 다시 요청해야 하는 새 제품 동작이라 테스트 계획에 섞지 않는다. 이전 버튼만으로 돌아가는 비용이 크다는 한계는 남으므로 후속 UX 개선 후보로 기록한다.

### 과제 목록에서 넓힌 것

과제가 준 15개 항목 중 하나에 대상을 덧붙였다. 무엇을 왜 덧붙였는지 적는다.

**15번에 새로고침을 덧붙였다.**

|           | 내용                                                                                                                                                                                                                                                      |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 원래 대상 | 목록 진입 → 담기 → 헤더 확인                                                                                                                                                                                                                              |
| 덧붙인 것 | 새로고침 후에도 헤더 개수가 유지되는가                                                                                                                                                                                                                    |
| 이유      | 장바구니·위시리스트는 `persist`로 `localStorage`에 저장되고 `create-collection-store.ts`에 `version`·`migrate`·`merge`까지 들어 있는데, 이 복원 경로를 보는 테스트가 하나도 없다. 14번의 새로고침은 필터(URL)를 보는 것이라 zustand store를 지나지 않는다 |
| 비용      | 거의 없다. 이미 열려 있는 페이지에서 새로고침 한 줄이라 브라우저를 새로 띄우지 않는다                                                                                                                                                                     |

항목을 **대체**한 것이 아니라 뒤에 **덧붙인** 것이다. 원래 대상인 "목록 진입 → 담기 → 헤더 확인"은 그대로 검증한다. 14번에서는 대상 자체를 필터에서 장바구니로 바꾸려다 접었는데, 그건 덧붙이는 게 아니라 다른 항목을 만드는 일이었다.

14번에도 새로고침이 있지만 보는 것이 다르다. 14번은 URL에 담긴 필터를, 15번은 `localStorage`에 담긴 장바구니를 본다. 필터를 새로고침해도 zustand store는 지나가지 않으므로 겹치지 않는다.

구현에 없어서 넘어가는 항목은 없다. 15개 항목에 해당하는 기능이 모두 구현되어 있다.

## 2. 애매했던 판단

표를 채우면서 어느 쪽이든 될 것 같았던 항목 중 두 개를 고른다. 왜 그쪽으로 정했는지, 다른 쪽을 골랐다면 무엇이 달라졌을지 쓴다.

### 판단 1 — 11번, URL 자체를 단언할 것인가

**처음 정한 것**: 단언하지 않는다. 새 브라우저 컨텍스트로 그 주소에 진입했을 때 같은 화면이 나오는지만 본다.

**왜**: 재진입이 빈 컨텍스트에서 성공하면 상태가 URL 말고 다른 곳에 있을 수 없다. 그래서 URL 문자열을 직접 보지 않아도 "URL이 화면 상태를 담는다"는 약속은 확인된다.

단언하지 않기로 한 것 중에 성격이 다른 두 가지가 있었다.

| 대상                                        | 성격                                         |
| ------------------------------------------- | -------------------------------------------- |
| 파라미터 순서                               | 명백한 구현 세부사항. 바뀌어도 버그가 아니다 |
| 기본값 생략 (`?sort=latest`를 URL에서 지움) | 의도적으로 내린 결정이긴 하다                |

두 번째가 애매했다. `clearOnDefault`를 요청과 URL에서 다르게 쓴 건 판단이 들어간 부분이고, 깨져도 아무 테스트가 안 잡는다.

**구현 단계에서 뒤집은 것**: 기본값 생략 중 `page`만 단언하기로 했다.

표를 채울 때는 기본값 생략을 "주소창을 깔끔하게 두려는 내부 규칙"으로 묶었는데, `page`는 그 묶음에 들어가지 않았다. 필터를 바꿀 때 `page`가 URL에 남으면 공유한 링크를 받은 사람이 결과가 없는 3페이지를 보게 된다. 화면이 정상이고 링크도 그대로 동작한다는 조건이 `page`에서는 성립하지 않는다. `sort`·`category`의 기본값 생략은 여전히 단언하지 않는다.

그래서 E2E는 필터·정렬·검색어를 바꾼 뒤 `page`가 URL에서 사라지는지를 단언한다. 화면 쪽의 같은 규칙(페이지 번호가 1로 돌아가는지)은 8·9번 RTL이 본다. 둘은 같은 동작의 다른 면이다 — RTL은 사용자가 보는 페이지 번호를, E2E는 공유되는 주소를 본다.

**파라미터 집합을 단언한 곳이 한 군데 있다**: "공백과 URL 예약 문자가 포함된 검색어" 테스트가 URL의 키 목록이 `['q']`인지 본다. 이건 순서 규칙을 고정하려는 게 아니라 `&?%#` 같은 입력이 인코딩되지 않고 새 파라미터로 쪼개지지 않는지를 보는 단언이다. 목적이 다르므로 위 규칙의 예외가 아니라 다른 항목으로 읽는다.

**다른 쪽을 골랐다면**: `sort`·`category`까지 URL 문자열을 전부 단언했다면 기본값 생략 규칙 전체가 회귀할 때 잡혔을 것이다. 대신 파라미터를 하나 추가할 때마다 버그가 없는데도 빨간불이 뜬다. 테스트가 리팩터링을 막는 쪽으로 기운다.

### 판단 2 — 13번, 디바운스 경합까지 E2E로 볼 것인가

**정한 것**: 실제 뒤로·앞으로 이동과 확정된 필터 복원은 E2E로 보고, 예약된 디바운스 작업의 취소는 RTL과 Vitest 가짜 타이머로 분리한다.

**왜**: `useProductFilters`의 이 effect가 그 경합만을 위해 존재한다.

```ts
// 뒤로·앞으로 이동처럼 URL에서 q가 바뀌면 이전 입력의 대기 작업을 취소한다.
useEffect(() => {
  cancelQueryUpdate()
}, [cancelQueryUpdate, q])
```

빼도 화면은 대부분 멀쩡하고, 300ms 안에 뒤로가기를 눌러야만 드러난다. 수동으로는 재현이 어렵고 코드 리뷰에서도 "이 effect 왜 있지?"로 지워지기 쉽다. 테스트가 아니면 지킬 방법이 없는 종류다.

**분리한 이유**: History API와 Next 라우터를 거치는 복원은 실제 브라우저가 필요하다. 반면 `cancelQueryUpdate`가 300ms 예약 작업을 취소하는지는 실제 시간을 기다리지 않고 가짜 타이머로 결정적으로 검증할 수 있다. 둘을 E2E 하나에 묶으면 `waitForTimeout`이 필요해지거나 실행 속도에 따라 흔들릴 수 있다.

E2E는 `goBack()`·`goForward()` 뒤 URL, 입력값, 목록의 복원을 조건 기반으로 기다린다. RTL에서는 디바운스 실행을 예약하고 외부 쿼리 상태를 바꾼 뒤 가짜 시간을 진행해, 이전 검색어가 다시 반영되지 않는지를 본다.

**다른 쪽을 골랐다면**: 경합까지 E2E로 묶으면 실제 브라우저 조립 상태를 한 번에 볼 수 있다. 대신 실시간 300ms 경계에 기대므로 느리고 flaky해질 가능성이 커진다. 기본 복원만 E2E로 보고 취소 테스트를 생략하면 저 effect가 삭제되는 회귀를 잡지 못한다.

**남겨뒀던 E2E 한 건은 결국 제거했다**: 위 원칙을 정해놓고도 5주차부터 있던 `debounce 대기 중 페이지를 떠나면 검색어 변경을 취소한다`는 E2E에 그대로 뒀다. 이 테스트가 CI의 WebKit에서 실패하면서 세 가지를 확인했다.

1. `page.clock.install()`은 가짜 타이머를 깔 뿐 시간은 계속 흐른다. 멈추는 건 `pauseAt()`이다. 즉 이 테스트는 시계를 통제한 적이 없고, 클릭 내비게이션이 300ms를 넘기면 디바운스가 먼저 발화해 이동을 덮어썼다. 판단 2가 우려한 "실시간 300ms 경계에 기대는 flaky"가 그대로 일어난 것이다. 6주차와 7주차 기록에 간헐 실패로 남아 있던 것도 같은 원인이다.
2. `pauseAt()`으로 실제로 멈추면 통과하고 실행 시간도 1.6분에서 8.9초로 줄었다. 하지만 `goto` 직후에 멈추면 하이드레이션이 타이머를 쓰지 못해 입력창조차 찾지 못한다. 화면이 상호작용 가능해진 뒤에 멈춰야 한다.
3. 고쳐놓고 보니 이 테스트는 의도한 것을 검증하지 못했다. `useDebouncedCallback`의 언마운트 정리를 통째로 지우고 프로덕션 빌드로 다시 돌려도 통과한다. 페이지를 떠나면 `nuqs` 쪽이 이미 URL 갱신을 막고 있어, 우리 정리 코드가 없어도 결과가 같기 때문이다.

flaky를 고치는 것보다 먼저 물었어야 할 것은 "이게 빨간불이 되면 무엇을 알게 되는가"였다. 답이 "nuqs가 언마운트 후 URL을 안 바꾼다"라면 우리 코드의 회귀를 지키는 테스트가 아니다. 취소 로직의 회귀는 판단 2대로 RTL 쪽 `useProductFilters.test.tsx`가 맡는다.

## 3. 이 목록 밖은 어떻게 할지

위 15개 외에도 테스트할 만한 것이 남아 있다. 변경 빈도와 실패 비용을 근거로 각각 하나씩 고른다.

### 다음에는 하면 좋겠다

**대상 — 계약 밖 예외가 루트 `error.tsx`로 넘어가는 경로**

`throwOnError: shouldThrowProductListError`는 에러를 둘로 나눈다. `ApiError`는 목록 자리에서 재시도로 복구하고(6·7번), 응답 파싱 실패 같은 계약 밖 예외는 페이지째 루트 `error.tsx`로 보낸다. 뒤쪽은 이번 목록에서 뺐다.

| 항목      | 판단                                                                             |
| --------- | -------------------------------------------------------------------------------- |
| 변경 빈도 | 낮다. 에러 분류 규칙과 `error.tsx`는 자주 손대지 않는다                          |
| 실패 비용 | 높다. 여기가 뚫리면 예외가 아무 화면 없이 삼켜지거나 흰 화면이 된다              |
| 비용      | `error.tsx`는 App Router 라우팅 파일이라 jsdom에 없다. 검증하려면 E2E가 필요하다 |

낮은 빈도 × 높은 비용이라 "지금 당장"은 아니지만 버리기도 아깝다. 분류 규칙 자체(`shouldThrowProductListError`)는 이미 단위 테스트가 덮고 있어서, 남은 건 "그 분류대로 화면이 갈라지는가" 한 겹이다. E2E를 한 개 더 감당할 수 있게 되면 그때 추가한다.

### 앞으로도 안 하겠다

**대상 — 스켈레톤이 실제 콘텐츠와 시각적으로 일치하는가 (layout shift)**

`ProductGridSkeleton`은 실제 카드와 같은 그리드·같은 높이를 흉내 내서 로딩이 끝날 때 화면이 밀리지 않게 하는 것이 목적이다. 그 목적이 지켜지는지는 테스트하지 않는다.

| 항목      | 판단                                                                                         |
| --------- | -------------------------------------------------------------------------------------------- |
| 변경 빈도 | 높다. 카드 마크업이나 간격이 바뀔 때마다 스켈레톤도 따라 바뀐다                              |
| 실패 비용 | 낮다. 어긋나도 로딩 직후 한 번 밀려 보일 뿐 기능은 정상이고 데이터도 잃지 않는다             |
| 비용      | 높다. jsdom에는 레이아웃 계산이 없어 높이를 잴 수 없고, 실제로 보려면 픽셀 스냅샷이 필요하다 |

높은 빈도 × 낮은 비용이라 「다음에는 하면 좋겠다」의 `error.tsx`(낮은 빈도 × 높은 비용)와 정확히 반대쪽에 있다. 자주 바뀌는데 깨져도 손해가 작은 것을 테스트로 고정하면, 테스트가 잡아주는 것보다 막는 것이 많아진다.

여기에 더해 이 대상은 테스트가 볼 수 있는 표면 자체가 없다.

```tsx
<div className={gridStyles.grid} aria-hidden="true">
```

스켈레톤은 장식용 placeholder라 스크린리더에서 숨겼다. role도 name도 없으니 접근 가능한 쿼리로는 잡히지 않고, 남는 것은 클래스명이나 `div` 개수 같은 구현 세부사항뿐이다. 4번에서는 스켈레톤 자체를 찾지 않고 지연된 응답 전후 상품의 부재와 노출만 본다. 로딩 중 화면이 실제와 얼마나 닮았는가는 그 밖이다.

대신 지키는 방법은 테스트가 아니라 규칙으로 둔다. `CLAUDE.md`가 스켈레톤 수정 시 이미지 비율·텍스트 높이·간격을 실제 콘텐츠와 맞추고 layout shift를 눈으로 확인하도록 요구한다. 사람이 보면 바로 드러나고 자동화했을 때만 비싸지는 종류다. 시각 회귀 스냅샷을 도입한다면 그때 다시 보되, 이 항목 하나를 위해 들일 도구는 아니다.

## 3단계 예고 — 무엇을 망가뜨릴지

3단계는 구현을 일부러 한 곳 망가뜨려서 2단계 테스트가 그걸 잡는지 확인한다. 계층마다 하나씩 필요하므로 후보를 미리 적어둔다. 쉬운 자리를 피하려고, 지워도 화면이 대체로 멀쩡해 보이는 곳으로 잡았다. 실제 실험은 3단계에서 하고 결과에 따라 대상이 바뀔 수 있다.

| 계층 | 후보                                                                     | 왜 눈에 안 띄는가                                                                                                            |
| ---- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| 단위 | `getTotalPages`의 `Math.max(1, ...)`를 벗겨 `Math.ceil`만 남긴다         | `totalCount`가 0일 때만 0페이지가 된다. 상품이 있는 평소 화면에서는 드러나지 않는다                                          |
| 통합 | `useProductFilters`가 필터 변경 시 함께 넣는 `page: 1`을 지운다          | 카테고리를 바꾸면 목록은 실제로 바뀌므로 절반은 통과한다. 3페이지에서 바꿨을 때만 빈 결과가 된다                             |
| E2E  | `create-collection-store`의 `partialize`가 `{ ids: [] }`를 저장하게 한다 | 12번은 store를 직접 붙여 렌더하므로 초록불이다. 클릭 직후 화면도 정상이고, 새로고침으로 복원이 끊기는 것만 15번에서 드러난다 |

E2E 후보는 12번(RTL)이 못 잡고 15번만 잡는 자리라, 두 계층을 나눠둔 것이 값을 하는지도 함께 확인된다.

세 후보 모두 바꾸지 않고 그대로 실험했고 전부 잡혔다. 각 파일의 나머지 테스트는 통과하고 경계 하나만 빨개졌다. 같은 `partialize` 변형을 둔 채 12번(RTL)을 돌리면 3개 전부 통과하므로, 12번과 15번을 나눠둔 판단이 값을 한다는 것도 확인됐다. 실험 기록은 [`step3-result.md`](../week-08/step3-result.md)에 있다.

- 네트워크는 MSW가 자른다. `fetch`·`axios`를 직접 바꿔치기하지 않는다.
- 공개 동작은 테스트를 통과시키기 위해 바꾸지 않는다. 다만 3번처럼 독립된 순수 계산 책임이 드러난 경우에는 동작을 유지한 채 분리할 수 있다.

통합 테스트의 핸들러와 단언 경계는 다음과 같다.

| 대상     | MSW 응답 규칙                                                     | 화면에서 확인할 결과                                                     |
| -------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 4번      | 성공 응답만 해당 테스트에서 지연                                  | 응답 전 상품 부재 → 응답 후 상품 노출                                    |
| 5번      | `products: []`를 반환하고 `totalCount`를 0 또는 양수로 구분       | 빈 결과 문구, 오버플로우일 때 페이지네이션 노출                          |

### 13번 RTL도 어댑터로 — 예외를 없앤 이유

처음에는 `useProductFilters.test.tsx` 한 곳만 `NuqsTestingAdapter` 대신 `vi.mock('nuqs')`로 `useQueryStates`를 바꿨다. 훅의 `setParams` 호출을 직접 보는 편이 쉬웠고, 어댑터로 "취소되었음"을 관찰하려면 가짜 타이머와 어댑터 내부 갱신을 함께 다뤄야 한다고 판단했다.

값이 비쌌다. nuqs의 시그니처가 바뀌면 이 테스트는 초록불인 채로 실제 코드와 어긋나고, 그 회귀는 실제 어댑터를 쓰는 8·9·10번에서만 드러난다. 리뷰에서 이 트레이드오프를 다시 지적받아 어댑터로 같은 것을 볼 수 있는지 실제로 돌려봤고, **둘 다 가능했다.** 예외를 없애고 "네트워크는 MSW가 자르고 그 밖은 실제 구현을 쓴다"를 모든 테스트가 지키게 했다.

바뀐 단언은 훅의 호출이 아니라 URL이다.

- 300ms 반영: `?page=3`에서 시작해 `onUrlUpdate`의 `queryString`이 `?q=셔츠` 하나인지 본다. `page`는 기본값 1로 돌아가 URL에서 사라지므로, "필터 바꾸면 1페이지로"가 사용자에게 보이는 형태로 확인된다.
- 취소: 같은 `renderHook` 안에서 `useQueryStates(productListParsers)`의 setter로 URL의 `q`를 먼저 바꾼 뒤 디바운스를 발화시킨다. 대기 중이던 입력이 URL을 덮지 않는지 본다.

옮기면서 알게 된 것도 있다. nuqs는 URL 갱신을 자체 큐에 모았다가 흘려보내므로, 가짜 타이머로 디바운스만 넘기면 `onUrlUpdate`가 오지 않는다. 디바운스를 동기로 넘긴 뒤 큐가 비워질 시간을 따로 줘야 한다. `setParams()`가 돌려주는 promise를 가짜 타이머 아래서 `await` 하면 멈추므로 흘려보낸다. 어댑터의 `searchParams` prop을 rerender로 바꾸는 방식은 초기값 스냅샷이라 훅에 반영되지 않는다.

두 테스트가 실제로 회귀를 잡는지는 `useProductFilters`의 취소 `useEffect`를 지우고 확인했다. 지우면 빨간불이 된다.

8~10번은 호출 순서에 따라 응답하지 않는다. 잘못된 쿼리로 요청해도 순서만 맞아 통과하는 일을 막기 위해 MSW가 실제 URL의 요청 조건을 읽고, **`app/api/products/route.ts`가 400을 주는 조건은 핸들러도 400을 준다**(지원하지 않는 `sort`·`category`, 양의 정수가 아닌 `page`, `pageSize > 24`). 정렬값이 없으면 서버와 마찬가지로 정렬하지 않는다. 테스트는 `fetch` 호출 자체를 spy하지 않고 사용자가 보는 결과를 단언한다. 7번만 동일 조건의 재시도 흐름이므로 요청 횟수를 사용한다.

핸들러가 서버보다 관대하면 잘못된 쿼리를 보내기 시작하는 회귀에 실제 앱은 에러 화면이고 테스트는 초록불이 된다. "조건을 읽는다"까지만 정하면 이 상태도 규칙을 만족하므로, 응답 코드까지 판정 조건으로 적는다.

_**직접 정한 것.** 15개 항목의 방법론과 이유, 빨간불 칸, 애매했던 판단 두 개, 「다음에는 하면 좋겠다」, 그리고 **각 테스트가 무엇을 단언할지와 모킹 경계**. 구현 중 문서와 코드가 어긋났을 때 어느 쪽에 맞출지도 작성자가 정했다._
