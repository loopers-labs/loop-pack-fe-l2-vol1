측정일: 2026-09-11 KST. 대상 PR #198의 head `66b3e83a4da91ed01a5f69078b18e2b966dc792e`.

## 결론 — 병합 전 핵심·배포 전 전체 정책 유지

**main 대상·non-draft·런타임 변경 PR은 핵심 E2E, Production 배포 전에는 전체 E2E를 실행하는 기존 정책을 유지한다.** 같은 코드의 로컬 비교에서 전체 실행의 추가 시간은 약 11.77초였고, 기존 CI 성공 실행의 중앙값 차이는 약 11초였다. 이 측정은 현재 16개 테스트의 비용이며, 테스트가 늘어난 뒤의 실행 시간이나 장기 flaky 비용을 보여주지는 않는다.

병합 차단 범위는 핵심 흐름으로 두고, 전체 검증은 배포 자격으로 유지한다는 작성자 판단이다. 전체 테스트 증가에 따른 PR 반복 실행 비용과 비핵심 flaky의 병합 차단 범위를 고려하되, 비핵심 회귀의 main 유입에 따른 수정·원복·배포 재검증 비용은 수용한다. 표본에서 flaky는 관찰되지 않았으므로 현재 flaky 회피 이득을 실증했다고 주장하지 않는다. 비핵심 회귀로 배포 지연이 반복되거나 기능의 실패 영향이 커지면 해당 흐름의 핵심 편입을 재검토한다. workflow·required는 변경하지 않았다.

## 2. 기존 GitHub CI의 시간과 flaky

fork `heeji289/loop-pack-fe-l2-vol1`의 최신 Quality 50개 run을 조회했다. 생성 시각 범위는 UTC 2026-09-10 05:35:48~17:27:09, 각 run의 **최신 attempt만** 포함한다. 모든 과거 실행의 전수조사나 동일 SHA A/B가 아니며, 취소 run에서 이미 완료된 E2E도 실행 표본에 포함한다.

| 범위 | 실제 E2E 실행 | 성공 step 중앙값 | 성공 step 범위 | 보고된 flaky |
| --- | ---: | ---: | ---: | ---: |
| 핵심 | 23회, 모두 성공 | 10초 | 8–12초 | 0 |
| 전체 | 19회: 성공 18·의도적 실패 1 | 21초 | 19–23초 | 0 |
| E2E 생략 | 8회 | — | — | 미실행 |

시간은 Actions jobs API의 초 단위 step 시작/종료 시각이다. flaky는 job 성공 여부로 추측하지 않고 **42회 모두의 E2E summary**에서 확인했다. 핵심 69회 테스트 실행, 전체 304회 테스트 실행(303 passed·1 failed), skipped 0이다. 여러 커밋·서버 부하·변경 범위가 섞여 있으므로 21−10=11초는 관찰상 차이이지 통제된 CI 인과 추정은 아니다.

유일한 실패는 [Dialog 오류 주입 run](https://github.com/heeji289/loop-pack-fe-l2-vol1/actions/runs/34441821105)의 동일 테스트가 retry #1·#2까지 계속 실패한 경우다. 자연 발생 flaky로 집계하지 않는다. 예산/env·배포 CLI 실패 등 다른 job 실패도 E2E flaky로 집계하지 않았다.

대표 정상 전체 실행: [현재 PR head의 main run](https://github.com/heeji289/loop-pack-fe-l2-vol1/actions/runs/34507836049), 전체 E2E step 22초·16 passed·flaky 0. 대표 핵심 실행: [PR run](https://github.com/heeji289/loop-pack-fe-l2-vol1/actions/runs/34507839978), 핵심 step 11초·3 passed·flaky 0.

표본 내 flaky 0은 향후 확률 0이 아니다. 반복 실행은 독립 표본도 아니므로 실패율 신뢰구간이나 미래 비용을 산출하지 않았다. retries=2 때문에 한 번 실패 후 회복하면 flaky로 표시되지만, 재시도 두 번 모두 실패하는 거짓 빨간불의 미래 빈도는 알 수 없다.

## 3. 병렬 checks를 고려한 PR 대기 시간

성공한 PR run 중 핵심 E2E를 실행한 22개를 대상으로 checks와 build-e2e의 실제 종료 시각을 대조했다. checks가 build-e2e보다 늦게 끝난 시간은 중앙값 0초, 범위 −47~23초다. 음수는 build-e2e가 이미 더 늦게 끝났다는 뜻이다.

전체 E2E로 바꾸어 build-e2e가 **11초 증가한다고 가정**하고, 나머지 시간·job 시작 시차를 고정했다.

`증가량 = max(checks 종료, build-e2e 종료 + 11초) − max(checks 종료, build-e2e 종료)`

- 추정 증가량: 중앙값 **10.5초**, 범위 **0~11초**.
- 22개 중 완전히 병렬 여유에 숨는 경우는 2개였다.
- 이것은 **기존 시각에 대한 가정 계산**이다. 실제 정책 변경 후 CI 실측이 아니다. runner 준비 변동, 리포트 크기 증가, guard 스케줄링 변화는 반영하지 않았다.
- 러너 점유 시간과 작성자의 대기 시간은 다르다. 병렬 여유로 대기가 줄어도 전체 E2E의 실행 비용은 발생한다.

## 5. 변경 비용과 남는 판단

| 축 | 현 정책 유지 | main 대상 준비 완료 런타임 PR에서 전체 E2E |
| --- | --- | --- |
| 실행 시간 | 핵심으로 회당 약 11초 적게 실행하는 관찰 | 회당 약 11~12초 추가, PR 대기는 대체로 그대로 증가할 가능성 |
| 병합 차단 범위 | 핵심 3개만 E2E 병합 차단 | 전체 16개로 확대. 영향 없는 비핵심의 거짓 빨간불도 병합을 막을 수 있음 |
| flaky 근거 | 표본 내 0. 비핵심 flaky 회피 이득은 아직 미관측 | 표본 내 0. 향후 거짓 빨간불 위험은 남음 |
| main 복구 부담 | 비핵심 실패는 원인 확인·수정/원복 후 배포 재검증 | 기존 비핵심 E2E가 잡는 실패를 병합 전에 발견 |
| 도입 비용 | 없음 | scope·guard 보완, 스펙/RFC 갱신, 실패 차단→원복 통과·문서 생략·ready 전환 실증 |

전체 E2E를 병합 게이트로 바꾸면 비핵심 flaky 대응도 정해야 한다. CI 재시도 후 회복은 현재대로 flaky를 기록하고, 재시도를 소진하면 일단 병합을 막는다. 반복되는 flaky는 trace로 원인을 고친다. 비핵심 테스트의 임시 격리를 허용한다면 담당자·기간·남는 검증 범위·복구 조건을 명시해야 하며, 현재 full 실행 검사에서 skip을 거부하므로 테스트에 skip만 붙여 우회할 수 없다. 이는 이번 측정으로 자동 확정할 정책이 아니다.

측정으로 확인한 사실은 **현재 규모에서 core 유지의 시간 이득은 약 11초이며, 비핵심 flaky 회피 이득은 아직 입증되지 않았다**는 것이다. 두 정책의 장기 기대비용은 이 자료만으로 비교할 수 없다. 실행 시점은 기존 정책을 유지하며, 전체 E2E가 검출하는 비핵심 회귀는 배포 전에 차단한다. 모든 버그의 부재나 모든 회귀의 main 유입 방지를 보장하지 않는다.
