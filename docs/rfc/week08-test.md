# 8주차 — 3단계 실험 선정 고민 기록

> - 이 문서는 AI 보조로 작성했다.
> - 3단계(자가 검증)에서 **무엇을 망가뜨릴지 어떻게 선정할지**, 그리고 **살아남은 테스트를 어떻게 판단할지**에 대한 고민을 AI와의 대화로 정리한 기록이다.
> - 실제 실험 결과 표는 3단계 수행 시 이 문서의 형식에 맞춰 채운다.

## 1. 무엇을 망가뜨릴지 선정하는 기준

### 1.1 원칙 3가지

**원칙 1 — 1단계 표에서 거꾸로 고르기 (제일 중요)**

1단계 표의 "빨간불이 되면 알게 되는 것" 칸은 **테스트가 지키겠다고 약속한 것**이다. 그 약속을 이루는 **구현 코드 한 줄**을 찾아 그것을 깨는 것이 실험이다.
예: 약속이 "빈 결과일 때 빈화면이 뜬다"였다면 → 빈 결과 분기가 있는 코드를 고른다.

**원칙 2 — "행복 경로" 말고 경계·분기를 고르기**

| 바꾸는 방식       | 예시                                            |
| ----------------- | ----------------------------------------------- |
| 경계 부호 바꾸기  | `length > 0` → `length >= 0`                    |
| 조건 뒤집기       | `if (존재하면 제거)` → 무조건 추가              |
| 분기 삭제/연결    | 에러 분기를 성공 분기로 연결                    |
| 호출 한 줄 지우기 | `setFilters({ q, page: 1 })`에서 `page: 1` 제거 |

**원칙 3 — 한 곳만, 한 줄만 바꾸기**

두 군데를 바꾸면 어떤 테스트가 어떤 변경을 잡았는지 알 수 없다.

### 1.2 이 레포 기준 구체적 후보

**단위 후보**

- `src/shared/lib/validateStoredItems.ts:14` — `value.id.length > 0`을 `>= 0`으로. 빈 문자열 id가 새어 들어가는 경계라 과제가 원하는 "눈에 안 띄는 곳"이다.
- `src/features/add-to-cart/model/store.ts:33-35` — toggle의 exists 분기를 뒤집어서 **같은 상품이 계속 추가**되게 만들기.

**통합 후보**

- `ProductList`의 빈 결과/에러 분기 — 빈 결과일 때 빈화면 조건을 성공 렌더와 바꾸기.
- `src/features/product-filters/model/useProductListFilters.ts:50` — `setSort`에서 `page: 1` 제거. 이 변경은 `e2e/navigation.spec.ts:34`가 노리는 것이어서 **통합 테스트는 못 잡고 E2E만 잡을 수도** 있다. 어느 쪽이 잡는지 보는 것 자체가 실험이다.

**E2E 후보**

- `src/widgets/header/Header.tsx`의 개수 표시 — `items.length`를 `0` 고정으로. `e2e/cart-wishlist.spec.ts`가 잡아야 한다.
- `useProductListFilters.ts:45`의 `history: 'push'` 옵션 제거 — 뒤로/앞으로 복원 테스트가 잡는지 확인.
- `add-to-cart/model/store.ts:48`의 `partialize`에서 `items`를 빼기 — "새로고침해도 유지"를 노리는 변경이다.

### 1.3 주의할 함정 — 테스트가 구현의 상수를 import하는 경우

테스트가 구현의 **상수를 직접 import**하면, 그 상수를 바꿔도 테스트가 같이 바뀌어서 **영원히 못 잡는다**.
예: 통합 테스트가 `PAGE_SIZE`를 소스에서 import해 쓰고 있어서, `PAGE_SIZE` 자체를 바꾸는 실험은 "살아남음"이 거의 확정된다. 왜 못 잡았는지 설명할 좋은 사례가 되지만, 의도한 실험인지는 스스로 판단해야 한다.

### 1.4 실행 팁

- E2E는 느리니까 **무엇을 바꿀지 미리 정해두고 한 번만** 돌린다.
- 되돌리기는 `git restore <파일>`로 한다. 실험 전에 `git status`로 깨끗한 상태인지 확인한다.
- 다 잡혔다면 성공이 아니라 "쉬운 곳만 골랐다"는 신호다. 경계 쪽(`>= 0`)으로 다시 도전한다.

## 2. 살아남은 테스트는 나쁜 테스트인가

**"살아남었다 = 나쁜 테스트"가 아니라, 왜 살아남았는지에 따라 판단이 갈린다.** 4가지 경우로 나눈다.

### 경우 1 — 그 경계가 "지키겠다고 약속한 동작"인데 못 잡았다 → 이때만 나쁜 테스트

테스트의 가치는 모든 코드 변경을 잡는 것이 아니라, **자신이 지키기로 한 약속(공개 동작)이 깨졌을 때만 실패하는 것**이다.

예: `value.id.length > 0`을 `>= 0`으로 바꾸면 `{ id: '' }` 같은 빈 문자열 id가 새어 들어간다. 테스트가 `id: ''` 케이스를 아예 안 넣고 `id: 'ok'`만 확인했다면 → 약속한 검증에 구멍이 있는 것이므로 테스트를 고친다:

```ts
// 경계 케이스를 명시적으로 추가
expect(isStoredItem({ id: '' })).toBe(false);
```

### 경우 2 — 의미가 바뀌지 않는 변경이라면 → 원래 못 잡는 게 정상

`length > 0`을 `length >= 1`로 바꾸면 실제 동작은 하나도 안 바뀐다. 이런 건 누가 뭘 해도 못 잡는 **동등 변형**이다. 테스트의 결함이 아니다. (Advanced의 Stryker에서 "죽일 수 없는 변형"이라고 부르는 것이 이것이다.)

### 경우 3 — 구현 세부사항이라면 → 못 잡는 게 오히려 올바른 것

내부적으로 `>`를 쓰든 `>=`를 쓰든 사용자에게 보이는 결과가 같다면 약속 밖의 영역이다. 굳이 잡게 만들면 구현에 과하게 붙은 깨지기 쉬운 테스트가 된다 — 리팩토링만 해도 실패하는 테스트는 점점 무시당한다.

### 경우 4 — 다른 테스트가 잡는 경우 → 전체 묶음으로 판단

한 테스트가 못 잡아도 다른 테스트(예: E2E)가 잡는다면 묶음 전체로는 지키고 있는 것이다. 다만 "이 동작은 이 레이어가 지킨다"라는 설계 의도가 있었다면 그 위치를 다시 생각해 본다.

### 판단하는 순서

살아남았을 때 이렇게 자문한다:

1. **이 변경이 사용자에게 보이는 동작을 바꾸나?** → 아니오면 경우 2/3이니 기록하고 넘어간다.
2. **바꾼다면, 그 동작을 지키겠다고 1단계에서 약속했나?** → 했다면 경우 1이니 테스트에 경계 케이스를 추가한다.
3. 고친 뒤 **같은 실험을 다시 돌려서 이번엔 잡히는지 확인**한다.

### 판단 기준을 두 질문으로 풀어보기

"살아남음 = 나쁜 테스트가 아니라, 그 변경이 (1) 사용자에게 보이는 동작을 바꾸는지, (2) 1단계에서 약속한 검증인지로 판단한다"는 문장은 **두 개의 질문을 순서대로 던지는 절차**다:

- **질문 1 — 이 변경이 사용자에게 보이는 동작을 바꿨나?** 망가뜨린 변경이 실제 동작에 영향을 주지 않았다면 잡을 게 없으므로 못 잡은 게 당연하다. 예: `length > 0` → `length >= 1`은 완전히 같은 뜻이라 동작이 하나도 안 바뀐다.
- **질문 2 — 바꿨다면, 그 동작을 지키겠다고 약속했나?** 동작이 바뀌었더라도 1단계 문서에 그 동작을 검증하겠다고 적지 않았다면 그 테스트의 담당 밖이다.

|                          | 질문 2: 약속했나? | 결론                                                      |
| ------------------------ | ----------------- | --------------------------------------------------------- |
| **질문 1: 동작 안 바뀜** | 상관없음          | 살아남음 = 정상. 기록만 하고 넘어감                       |
| **질문 1: 동작 바뀜**    | 아니오            | 살아남음 = 그 테스트의 담당 밖. 다른 테스트가 잡는지 확인 |
| **질문 1: 동작 바뀜**    | 예                | **이때만 살아남음 = 테스트 결함.** 경계 케이스 추가       |

비유하자면 테스트는 **담당 구역(1단계에서 정한 약속)이 있는 경비원**이다. 담당 구역 밖에서 사건이 났는데 모른 척했다고 나쁜 경비원이 아니고, 담당 구역 **안에서** 사건이 났는데 눈치채지 못했다면 그때가 문제 있는 경비원이다.

살아남음은 테스트의 사형선고가 아니라, **테스트가 무엇을 지키고 무엇을 안 지키기로 했는지 보여주는 정보**다. 그래서 과제가 "살아남은 변경을 숨기지 마세요. 그게 가장 값어치 있는 기록"이라고 하는 것이다.

## 3. 실제 고민 사례 — `validateStoredItems.ts` 경계 실험

### 3.1 실험 설계

`src/shared/lib/validateStoredItems.ts:14`의 경계를 바꾼다.

```ts
// 원래 코드
export const isStoredItem = (value: unknown): value is StoredItem =>
  isRecord(value) && typeof value.id === 'string' && value.id.length > 0;

// 실험: > 를 >= 로
... value.id.length >= 0;
```

### 3.2 결과와 첫 번째 반응

- **결과: 살아남음** — 테스트가 통과했다.
- 첫 번째 반응: "id의 길이가 0인 경우가 앱에 없을 것 같은데, 이런 건 못 잡아도 상관없는 것 아닌가?"

### 3.3 "없을 것 같다"가 성립하지 않는 이유 — 입력이 어디서 오는지 보기

이 함수만은 "없을 것 같다"가 성립하지 않는다. `isStoredItem`이 검증하는 데이터는 zustand persist가 **localStorage에서 읽어온 값**이기 때문이다. 그런데 localStorage는:

- 사용자가 DevTools → Application 탭에서 **언제든 직접 수정할 수 있는** 영역이다.
- 옛날 버전 스키마의 흔적이 남아있을 수도 있다.

실제로 함수 자체의 주석이 그렇게 쓰여 있다:

> persist로 불러온 값은 사용자 브라우저에서 **변조됐거나, 옛날 스키마**로 남아있을 수 있다 (`validateStoredItems.ts:1`)

즉 `{ id: '' }`는 **앱의 정상 흐름에서는 안 나오지만, 이 함수는 애초에 정상 흐름이 아닌 입력을 걸러내려고 존재하는 함수**다. "정상적으로 담은 상품은 id가 있으니까 괜찮다"고 하면 이 검증 함수 전체가 필요 없어지는 논리가 된다.

**교훈: "없을 것 같다"는 입력이 어디서 오는지 확인하고 판단해야 한다. localStorage는 내 저장소가 아니라 사용자의 저장소라서, 이 함수의 세계에서 빈 id는 실재하는 입력이다.**

### 3.4 빈도 × 비용으로 평가하기

발생 확률만 보면 거의 안 일어난다. 하지만 검증 코드는 원래 **"낮은 확률 × 나쁜 결과"**를 막으라고 있는 것이다.

|                     | 비용                                               |
| ------------------- | -------------------------------------------------- |
| 빈 id가 통과했을 때 | 고스트 항목이 장바구니에 남아 헤더 개수가 이상해짐 |
| 경계 케이스 추가    | 테스트 **한 줄**                                   |

```ts
expect(isStoredItem({ id: '' })).toBe(false);
```

한 줄짜리 보험이다. 판단: **추가한다.**

### 3.5 원래 코드가 이미 잘 작동하는데, 굳이 경계값을 수정하는 의미가 있는가

실험 중 든 의문: "`isStoredItem`은 원래 `value.id.length > 0`을 검증해서 `id.length`가 0인 경우를 런타임에 이미 걸러준다. 그렇다면 굳이 `>= 0`으로 망가뜨리는 실험에 의미가 있나?"

**핵심: 이 실험은 코드를 고치려는 게 아니라 테스트를 검사하는 것이다.** `>= 0`은 코드를 좋게 만들려는 변경이 아니라 "미래의 누군가(또는 미래의 나)가 리팩토링하다가 실수로 이렇게 바꾸면?"을 시뮬레이션하는 **가짜 버그**다. 그래서 실험이 끝나면 반드시 원래대로 되돌린다.

안전망은 두 겹이고, 각각 지키는 대상과 작동 시점이 다르다:

| 안전망                        | 무엇으로부터 무엇을 지키나                   | 언제 작동하나                         |
| ----------------------------- | -------------------------------------------- | ------------------------------------- |
| `isStoredItem` 코드 (`> 0`)   | 나쁜 localStorage 데이터로부터 **앱**을 지킴 | 사용자가 사이트를 쓰는 **런타임**     |
| `validateStoredItems.test.ts` | 코드가 나빠지는 것으로부터 **코드**를 지킴   | `pnpm test`를 돌리는 **개발/CI 시점** |

첫 번째 안전망은 지금 잘 작동한다. 3단계 실험이 묻는 건 **"첫 번째 안전망에 구멍이 생기면(누가 `>=`로 실수하면), 두 번째 안전망(테스트)이 그걸 알아채나?"**다.

리스크 시나리오 — 몇 개월 뒤 누군가 이 함수를 리팩토링하다가 `>`를 `>=`로 오타냈다고 하자:

- **보강 전 (실험에서 살아남은 상태):** 테스트에 `id: ''` 케이스가 없으니 `pnpm check`는 여전히 초록불 → 버그가 그대로 merge → 운영에서 고스트 장바구니 항목 발생
- **보강 후:** `expect(isStoredItem({ id: '' })).toBe(false)`가 있으니 CI에서 즉시 빨간불 → 실수한 사람이 바로 고침

비유하자면 이미 잘 작동하는 화재 경보기의 **테스트 버튼을 눌러보는 것**과 같다. 버튼을 누르는 건 불이 나길 원해서가 아니라 "진짜 불이 났을 때 이 경보기가 울릴 거야?"를 확인하는 절차다.

### 3.6 실험 기록 (3단계 형식)

| #      | 망가뜨린 곳                 | 어떻게 바꿨나                  | 결과                                                                       | 실패한 테스트 |
| ------ | --------------------------- | ------------------------------ | -------------------------------------------------------------------------- | ------------- |
| 단위-1 | `validateStoredItems.ts:14` | `value.id.length > 0` → `>= 0` | 살아남음 → 보강 후 잡힘 (보강 전: `validateStoredItems.test.ts` 전체 통과) |

**왜 못 잡았는지:** 테스트가 `id: ''`(빈 문자열) 경계 케이스를 포함하지 않았다. 정상 케이스와 배열이 아닌 입력만 검증하고 있었다.

**대응:** `expect(isStoredItem({ id: '' })).toBe(false)` 추가 후 같은 실험을 다시 돌려 잡히는 것을 확인했다. (3단계 수행 시 실제로 확인하고 결과를 갱신한다.)

**교훈:**

- 살아남음 = 나쁜 테스트가 아니라, 그 변경이 (1) 사용자에게 보이는 동작을 실제로 바꾸는지, (2) 1단계에서 약속한 검증인지로 판단한다. 사용자에게 보이는 동작을 바꾸지 않는다면 변경의 의미가 없고, 바꾼다면 설계가 잘못된 것이다.
- "발생 안 할 것 같다"는 판단은 **입력 출처**를 먼저 확인해야 한다. localStorage/URL/외부 API처럼 신뢰할 수 없는 입력을 다루는 검증 코드라면, 가상의 케이스도 실재하는 입력으로 취급한다.
- 이 사례는 Advanced의 "살아남은 변형 중 의미 있는 것을 골라 테스트를 보강"하는 절차의 손으로 하는 버전이기도 하다.

## 4. 두 번째 고민 사례 — `add-to-cart` toggle 분기 뒤집기

### 4.1 실험 설계

`src/features/add-to-cart/model/store.ts:32-35`의 toggle 삼항 연산자에서 **두 분기를 뒤집는다**:

```ts
// 원래 코드
items: exists
  ? state.items.filter((existing) => existing.id !== item.id) // 있으면 제거
  : [...state.items, item],                                    // 없으면 추가

// 실험: 분기 뒤집기
items: exists
  ? [...state.items, item]                                     // 있으면 또 추가 (중복)
  : state.items.filter((existing) => existing.id !== item.id)  // 없으면 제거 (아무 일 없음)
```

이 변경이 만드는 실제 동작:

- 이미 담긴 상품을 다시 누르면 → 빠지는 대신 **계속 추가**된다 (중복 발생)
- 새 상품을 담으면 → 추가가 안 된다 (없는 id를 filter하니 배열이 그대로)

### 4.2 단위 테스트에서 잡혔는데, 통합·E2E도 돌려보는 이유

단위 실패를 확인한 뒤 든 의문: "이미 단위에서 잡았는데 왜 나머지 층도 돌리나?" 이유는 세 가지다.

**이유 1 — "어떤 층이 잡았는지" 자체가 실험 결과다.** 3단계 기록표의 "실패한 테스트" 칸은 전체 실패 목록을 적는 것이다. toggle은 단위(항목 1), 통합(항목 12 — 담기→헤더·다시 누르면 빠짐), E2E(항목 15 — 진입→담기→헤더) 세 층이 같은 코드를 바라본다. 어느 층이 빨간불을 켰는지 알아야 이 변경에 대한 안전망이 어디까지 뻗어 있는지 알 수 있다.

**이유 2 — 1단계에서 설계한 "층 분리"가 실제로 작동하는지 검증한다.** test-plan은 "12는 통합, 15는 E2E로 층을 갈라 역할 분담"이라고 설계했다. 그 설계가 진짜인지 확인하려면 통합 12번과 E2E 15번이 **실패해야** 정상이다. 만약 단위만 잡고 통합·E2E가 통과한다면 그 테스트들이 toggle 동작을 실제로 검증하지 않고 있다는 뜻이다 — 살아남음 발견이고, 그것도 값진 기록이다.

**이유 3 — "가장 싼 층에서 잡혔다"는 것도 정보다.** 이 변경이 단위(가장 빠르고 쌈)에서 잡혔다면 "이 동작은 아래층에서 지킨다"는 설계가 잘 맞아떨어진 것이다. 반대로 단위가 못 잡고 E2E(가장 느림)에서만 잡혔다면 피드백이 느려진다는 신호라서 검증 위치를 다시 생각해야 한다.

비유하자면 화재 경보기를 거실에만 달았는데 주방에서 불이 났다면, 거실 경보기가 울린 것과 별개로 **주방 경보기도 울리는지** 확인해야 내 설계(층 분리)가 제대로 됐는지 알 수 있다. 정리하면: 단위 실패는 "버그를 잡았다"는 확인이고, 통합·E2E 실행은 **"내가 설계한 안전망 전체가 설계대로 작동하는지"**를 확인하는 절차다.

### 4.4 관찰 — 계층마다 실패 메시지의 성격이 다르다

같은 결함(toggle 분기 뒤집힘)인데 층마다 보여주는 증거가 달랐다:

| 층   | 실패 메시지                                                                                | 증거의 성격                                      |
| ---- | ------------------------------------------------------------------------------------------ | ------------------------------------------------ |
| 단위 | `expected [] to deeply equal [ { id: 'p1' } ]`                                             | store 상태를 직접 봄. 원인 유추가 가장 빠르다    |
| 통합 | `Unable to find an element with the text: 장바구니 1` + DOM 덤프(헤더에 "장바구니 0" 표시) | 사용자가 보는 화면 기준. 맥락(DOM)이 함께 나온다 |
| E2E  | `Expected: "장바구니 1", Received: "장바구니 0"` (5초 조건 기반 대기 후)                   | 실제 브라우저에서의 최종 사용자 가시 상태        |

세 층 모두 메시지만 보고 "toggle의 추가 분기가 깨졌다"고 원인을 유추할 수 있었다.

**교훈:**

- 1단계에서 설계한 층 분리(1=단위, 12=통합, 15=E2E)가 실제로 그대로 작동했다. 세 층이 같은 결함을 각자의 시선(상태 / 화면 / 브라우저)에서 잡았다.
- 이 변경은 **단위(가장 싼 층)에서 잡혔으므로** "toggle 동작은 아래층에서 지킨다"는 설계 의도와 일치한다. 통합·E2E의 실패는 같은 결함의 중복이 아니라, 각 층이 자기 담당(wiring, 전체 여정)을 검증하고 있다는 확인이다.
- 단위만 돌리고 끝냈다면 "12·15가 이 결함을 잡는지"는 영영 모르고 지나갔을 것이다. 살아남음이 없었더라도 **전 층 확인이 층 분리 설계의 검증**이라는 것을 배웠다.
- 실험 후 `git restore src/features/add-to-cart/model/store.ts`로 원복했는지 확인한다. (망가뜨린 코드가 커밋에 남으면 안 된다.)
