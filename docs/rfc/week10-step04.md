# 4단계 — AI 코드리뷰 활용

리뷰 기준을 이 프로젝트의 규칙으로 명문화하고, AI 리뷰의 유효 지적과 오탐을 가려 프롬프트를 고친 기록이다.

| 항목        | 내용                                                              |
| ----------- | ----------------------------------------------------------------- |
| 도구        | Codex CLI 0.153.4, 로컬 `codex exec --sandbox read-only`          |
| 비용        | 기존 구독으로 로컬 실행. 별도 API 결제 없음                       |
| 리뷰 기준   | `docs/ai-review-prompt.md`                                        |
| 리뷰 대상   | 10주차 작업 diff `faa07cb0..ab7e8f76` — 10개 파일, 996줄          |
| 게이트 배치 | **advisory** — CI에 붙이지 않음                                   |
| 실행 횟수   | 6회 — 프롬프트 v1–v4 각 1회, v4 재현성 확인 2회. 회당 23–26k 토큰 |

## 1. 리뷰 기준을 어디서 가져왔나

일반론이 아니라 10주간 이 저장소에서 실제로 합의한 것만 넣었다.

| 출처                             | 프롬프트에 넣은 규칙                                       |
| -------------------------------- | ---------------------------------------------------------- |
| 1주차 `eslint.config.mjs`        | `no-console`은 error, `warn`만 허용                        |
| 1주차 제1원칙                    | 판단이 들어간 곳에 근거 주석                               |
| 2~3주차 CLAUDE.md 컴포넌트 규칙  | View는 그리기만, 한 가지 책임, 파생값은 변수로             |
| 4주차 CLAUDE.md 네이밍           | 의도 없는 이름 금지, props boolean 접두사                  |
| 5주차 상태 분류 기준             | URL 상태, 서버 응답을 전역 스토어에 복사 금지              |
| 6주차 `eslint-plugin-boundaries` | FSD 레이어 방향, 역할 없는 배럴 금지                       |
| 7주차 측정 규칙                  | 전송량·타이밍 주장에는 측정 근거                           |
| 9~10주차 사람 리뷰 피드백        | 추적되는 RFC에서 gitignore 경로를 언급하지 않기            |
| 10주차 3단계 판단                | CI에 실제 비밀값 금지, required 배치는 네 가지 축으로 판단 |

## 2. 잘 잡아낸 리뷰

### 스킵 정책에 정책 범위 밖 경로가 남아 있었다

프롬프트 v1~v4 **네 번 모두** 같은 지적이 나왔다.

```
### 커밋되는 RFC가 추적되지 않는 로컬 문서 경로를 언급함
- 파일: docs/rfc/week10-step02.md
- 위반한 규칙: 커밋되는 docs/rfc/** 문서에서 gitignore 대상 경로를 언급하지 않는다.
- 근거: 스킵 대상 목록에 그 경로가 들어 있다.
```

**확인한 사실**

| 확인                | 결과                                                                |
| ------------------- | ------------------------------------------------------------------- |
| `.gitignore`        | 해당 디렉터리를 추적하지 않는다                                     |
| `e2e.yml`의 판정    | PR 변경 목록에 나타날 수 없는 경로라 스킵 분기가 실행될 일이 없었다 |
| 실제 판정 변화      | 제거 전후로 판정 결과가 달라진 사례는 확인되지 않았다               |
| 추적되는 RFC의 언급 | `week10-step02.md`가 그 경로를 그대로 적어 두었다                   |

**판정** — 정책 범위에 포함되지 않는 경로가 스킵 목록에 남아 있어 설정이 불필요하게 넓어져 있었다. 현재 일반 PR에서 즉시 검증 누락을 일으킨 사례는 확인되지 않았지만, 경계가 불명확하므로 제거 대상으로 판단했다.

**조치** — `.github/workflows/e2e.yml`의 스킵 목록과 `docs/rfc/week10-step02.md`의 정책 설명에서 함께 제거했다. 2단계 기록과 충돌하지 않도록 step02에는 「수정 기록 (4단계)」 인용문을 남겨 초기 설계와 제거 사유를 같이 볼 수 있게 했다.

이 지적이 5단계 승격 대상이다. 사람 리뷰에서도 반복해서 나왔고, 참/거짓을 결정적으로 가를 수 있다.

## 3. 헛소리한 리뷰

### `no-console` 위반 (프롬프트 v1)

```
### CI 스크립트에서 console.log 사용
- 파일: .github/workflows/e2e.yml:43, 67, 110-111
- 위반한 규칙: no-console은 error다. console.warn만 허용.
```

규칙 이름·줄 번호·인용이 전부 맞아서 그럴듯하다. **적용 범위가 틀렸다.**

| 반증                                                                                  |
| ------------------------------------------------------------------------------------- |
| `pnpm lint` = `eslint --config eslint.config.mjs` — YAML은 검사 대상이 아니다         |
| lint-staged도 `*.{js,jsx,ts,tsx}`에만 건다                                            |
| 규칙 주석이 목적을 적어 뒀다: "프로덕션 번들에 디버깅 로그가 실리는 것을 막기 위해"   |
| workflow 인라인 스크립트의 출력은 번들에 실리지 않는다. 그 출력 자체가 Actions 로그다 |

같은 규칙이 `scripts/measure-transfer.mjs`에는 실제로 적용된다 — `.mjs`라 lint 대상이고, 3단계에서 `no-console` 오류가 나서 `process.stdout.write`로 바꿨다. **같은 규칙이 한쪽에는 적용되고 한쪽에는 적용되지 않는다는 점을 프롬프트가 알려주지 않아서 생긴 오탐이다.**

### timeout 근거 없음 (프롬프트 v1)

```
### CI timeout의 시간 주장에 측정 근거가 없음
- 파일: .github/workflows/quality.yml:15
- 근거: "관측된 실행보다 충분히 긴 상한"이라고 했지만 근거가 diff에 없다.
```

이 지적은 **"근거가 없다"가 아니라 "리뷰 대상 diff에서 근거를 찾지 못했다"로 써야 맞다.** 실제 실행 시간 자료가 존재했기 때문이다.

| run                                                                                      | quality job 소요 |
| ---------------------------------------------------------------------------------------- | ---------------- |
| [34512231899](https://github.com/kate-son/loop-pack-fe-l2-vol1/actions/runs/34512231899) | 72초             |
| [34512237149](https://github.com/kate-son/loop-pack-fe-l2-vol1/actions/runs/34512237149) | 64초             |
| [34512240338](https://github.com/kate-son/loop-pack-fe-l2-vol1/actions/runs/34512240338) | 73초             |

10분 상한은 관측값의 8배 이상이다. 1단계 측정 기록도 `week10-ci.md`에 있다. diff만 보고 판단하는 리뷰어에게 "diff 밖에 근거가 있을 수 있다"를 알려주지 않은 것이 원인이다.

## 4. 프롬프트 개선

오탐이 줄면 다음 층의 과도한 규칙이 드러나는 식으로 네 번 고쳤다.

| 버전 | 추가한 제한                                                      | 앞 버전의 오탐  | 새로 드러난 문제                                       |
| ---- | ---------------------------------------------------------------- | --------------- | ------------------------------------------------------ |
| v1   | 기준 명문화만                                                    | —               | `no-console` 범위 오적용, 근거 부재 단정               |
| v2   | 규칙별 **적용 범위** 명시 + "diff에 근거 없음 ≠ 근거 없음"       | 두 건 모두 해소 | 합의된 적 없는 지역 변수 네이밍 지적 2건               |
| v3   | 네이밍 규칙을 컴포넌트 props로 한정 + 목록에 없는 규칙 생성 금지 | 해소            | required 배치를 일반론("비싸다·비결정적이다")으로 반박 |
| v4   | required 판단을 이 프로젝트의 결정과 네 가지 축으로 명시         | 해소            | 없음                                                   |

핵심 문장 세 개다.

```
적용 범위: `pnpm lint`가 도는 파일 = *.ts, *.tsx, *.js, *.jsx, *.mjs.
적용 대상 아님: workflow YAML 안의 인라인 스크립트. lint를 타지 않고, 출력 자체가 Actions 로그다.

diff에 근거가 없는 것과 근거가 없는 것은 다르다. 주장의 근거가 diff 밖(문서·설정·기존 코드)에
있을 수 있는 경우는 위반으로 단정하지 말고 `확인 필요`로 분류하고, 어디를 봐야 하는지 지목한다.

명시된 팀 컨벤션이나 실제 오류와 연결되지 않는 단순 네이밍 선호는 지적하지 않는다.
```

**교환 관계** — 적용 범위를 명시하니 오탐은 줄었지만, 규칙을 넓게 남겨 둔 자리에서 가치가 낮은 스타일 지적이 늘었다. 규칙마다 범위를 적는 비용을 치러야 신호가 남는다.

v4 최종 출력은 유효 지적 1건(위 2절)과, 3단계 문서가 이미 「남은 것」으로 적어 둔 required 영구 배치 미완 1건이었다. 후자는 새 정보가 아니라 문서에 이미 있는 내용을 다시 짚은 것이다.

## 5. advisory로 두는 근거, CI에 붙이지 않는 근거

required 여부는 3단계에서 쓴 네 축으로 판단한다.

| 축          | AI 리뷰                                                           |
| ----------- | ----------------------------------------------------------------- |
| 실패 영향   | 지적을 놓쳐도 `quality`·`e2e-required`가 코드 결함을 따로 막는다  |
| 검증 신뢰도 | 오탐이 실제로 3건 나왔고, 결과가 기준 문구에 민감하다 (아래)      |
| 실행 비용   | 회당 23~26k 토큰. 모든 PR 자동 실행이면 비용·소음이 빠르게 커진다 |
| 대체 검증   | 반복 지적은 5단계에서 결정적 룰로 내린다. 그쪽이 required가 된다  |

### 재현성은 재 봤다

같은 diff에 v4 프롬프트를 그대로 3회 돌렸다.

| 회차 | 지적                                                |
| ---- | --------------------------------------------------- |
| 1    | RFC의 gitignore 경로 언급 / required 영구 배치 미완 |
| 2    | 같음                                                |
| 3    | 같음                                                |

**표현만 다르고 지적 집합은 같았다.** 이 표본에서 실행 간 흔들림은 관찰되지 않았다. 다만 3회는 판단 근거로 삼기에 적은 표본이고, 리뷰 대상 diff도 하나뿐이다. **이 결과는 v4에만 해당한다.** v1~v3에서는 반복 실행을 하지 않았고, 프롬프트를 바꿀 때마다 지적 집합이 통째로 달라진 것은 위 4절 표에 있다.

### 그럼에도 required로 두지 않는 이유

흔들림이 아니라 **기준 문구에 대한 민감도**가 문제다.

| 근거                                                                                                                          |
| ----------------------------------------------------------------------------------------------------------------------------- |
| 프롬프트 한 줄을 바꿀 때마다 지적 집합이 통째로 바뀌었다 (4절 표). required로 두면 기준 문서를 고치는 순간 통과·실패가 바뀐다 |
| 오탐 3건이 모두 "그럴듯하게 틀린" 형태였다. 규칙명·줄번호·인용이 맞아서, 사람이 코드를 열어 반증해야 가려졌다                 |
| 반증에 쓴 근거(lint 대상 범위, 규칙의 목적 주석, 실행 시간 자료)가 전부 diff 밖에 있었다. 리뷰어가 볼 수 없는 자리다          |

`quality`의 검증은 같은 입력에 같은 결과를 낸다. 이 리뷰는 기준 문서를 어떻게 쓰느냐에 결과가 달라진다. 두 성질이 달라서 같은 자리에 두지 않는다.

CI에 붙이지 않는 이유는 두 가지다. 첫째, 붙이면 트리거·동시성·토큰 한도를 같이 설계해야 하는데 이번 주 범위를 넘는다. 둘째, advisory 결과를 Actions 화면에 올려도 사람이 읽고 판단하는 절차는 그대로라, 로컬 실행 대비 얻는 것이 적다. 나중에 붙인다면 모든 PR 자동이 아니라 label이나 코멘트로 사람이 명시적으로 부를 때만 돌린다.

## 6. 책임 구분

| 무엇                                           | 누가 판정           | 이번 주 위치              |
| ---------------------------------------------- | ------------------- | ------------------------- |
| 타입·lint·테스트·빌드·번들 예산·환경 변수 형식 | 기계 (결정적)       | `quality` — required      |
| 사용자 흐름 회귀                               | 기계 (결정적)       | `e2e-required` — required |
| 추적 문서의 gitignore 경로 참조                | 기계로 내릴 수 있음 | **5단계 승격 대상**       |
| 컨벤션·설계 냄새·적용 범위 판단                | AI (비결정적)       | advisory, 로컬 실행       |
| 무엇을 required로 둘지, 예산을 얼마로 할지     | 사람                | 3단계 문서                |

AI 리뷰의 오탐 3건은 모두 **"규칙을 아느냐"가 아니라 "규칙이 어디에 적용되느냐"** 에서 났다. 적용 범위 판단은 맥락이 필요해 AI·사람에 남고, 범위가 파일 경로로 딱 떨어지는 것만 기계로 내려간다. 5단계 대상을 그 기준으로 골랐다.
