## 1. 프로젝트 요약

Next.js 16 App Router 위의 커머스 데모다. 상품 목록(카테고리·정렬·페이지·검색을 URL 로), 위시리스트·장바구니(게스트 상태), 로그인·보호 경로·세션 만료, 주문서·주문 내역, 계측 이벤트까지 있다. 백엔드는 같은 앱의 Route Handler 가 흉내내는 mock 이고, 10주 동안 매주 하나의 관점(컴포넌트 → 상태 → 프레임워크 → 구조 → 성능 → 테스트 → E2E → CI)으로 같은 앱을 다시 만졌다.

- 배포: Production `https://loop-pack-fe-l2-vol1-durumis-projects-5329bd23.vercel.app`, Preview `https://loop-pack-fe-l2-vol1-d1xhgizzl-durumis-projects-5329bd23.vercel.app`
- 검증: vitest 190개(node·jsdom 분리), Playwright 12개, CI warm 63초

## 3. 주요 기술 결정 3개와 근거

**결정 1 — 세션은 서버 상태다(9주차).** 5주차 zustand 패턴을 쓰지 않고 TanStack Query 에 `initialData`(서버가 쿠키를 읽어 넘긴 값) + `staleTime: 0` 으로 두었다. 근거: 보호 데이터 요청이 없는 마이페이지에서도 탭 복귀 시 만료를 알아야 했고, 만료 판정은 "이 탭이 로그인 상태라고 믿던 중이었나" 라는 캐시 상태로만 가를 수 있었다(`/api/auth/me` 는 미로그인과 만료를 같은 401 로 준다). 대가로 루트 layout 이 동적 렌더가 되어 정적이던 데모 3개가 함께 동적이 됐고, 이후 `(commerce)` 라우트 그룹으로 좁혀 되돌렸다(`f0b2ab53`).

**결정 2 — E2E 는 2개 플로우만(9주차).** 시드 로그 22,427 이벤트·8,000 세션에서 봇 486세션·중복 77줄을 걷어낸 7,514 세션 기준으로 경로 빈도를 재고, 60.5% 의 목록 조작은 8주차 통합 테스트(nuqs 어댑터 + MSW)가 지키므로 붙이지 않았다. 8.6% 의 인증은 jsdom 이 못 보는 것(proxy 리다이렉트, httpOnly 쿠키, 초기 HTML, 라우터 캐시)이 핵심이라 붙였고, 실제로 통합 145개가 초록인 채로 E2E 만 잡은 버그 2개(보호 링크 prefetch 가 307 을 캐시, 주문 성공 시 콜백 유실)와 8워커에서만 드러난 경합 1개를 얻었다.

**결정 3 — build 와 E2E 를 한 job 에(10주차).** 교과서는 build artifact 를 e2e job 으로 넘기라고 하지만, 측정하니 job 하나의 setup 이 12~~23초고 e2e 자체가 16초였다. artifact 로 나누면 setup 을 한 번 더 내고 업/다운로드까지 더해 오히려 느리다. 대신 Playwright 브라우저 캐시(24~~39초 → 3~8초)와 lint·typecheck·unit 병렬화로 warm 104 → 63초를 얻었다(`week10-ci.md` 1.3). 같은 측정에서 pnpm store 캐시는 복원 10초 > 다운로드 5초로 이득이 없다는 것도 드러났다 — 걸었다고 빨라지는 게 아니라 재야 안다.

## 4. 테스트와 품질 게이트

- **8주차**: 15개 검증 항목을 단위 3 / 통합 9 / E2E 3 으로 배치하고 그 이유를 항목마다 적었다. node·jsdom 프로젝트 분리로 환경 시간 15.43s → 5.34s. MSW 는 기본 성공 경로 + 테스트 안 `server.use`, `onUnhandledRequest: "error"`. Stryker 로 스위트를 감사해 56개 변이 중 55 사멸(98.21%), 픽스처의 `price = 번호×1000`·`createdAt = 30−번호` 역상관 때문에 latest 와 price-asc 가 같은 순서라는 함정도 그때 잡았다.
- **9주차**: storageState 경계(로그인 검증 테스트는 빈 상태로, 나머지는 워커당 1회 실제 로그인), 워커별 계정 `looper{N}`, 시간 대기 0, `getByTestId` 0. `retries: 0`, `reuseExistingServer: false`.
- **10주차**: 게이트를 CI 에 고정 — required 는 `lint`·`typecheck`·`unit`·`build`(validate-env + 예산 + 조건부 E2E). 게이트 자체도 자가 검증했다: 예산 초과 PR(#7)과 env 오류 PR(#8)이 빨간불로 막히고 되돌리면 초록, 문서 PR(#5)에서 E2E 가 skip 되어도 머지 가능. 그리고 게이트의 **오탐**도 겪었다 — Vercel 플랫폼 변수가 "비밀 복사" 로 잡혀 배포가 두 번 막혔고 규칙을 소유한 비밀값으로 좁혔다(`week10-ci.md` 3.6). 8주차의 "내 테스트가 진짜 뭘 잡는지 확인하라" 가 게이트에도 그대로 적용됐다.

## 7. AI 활용 회고 — 무엇을 AI 에, 무엇을 기계에 맡겼나

10주를 관통한 결론은 1주차의 문장 그대로다: **설명할 수 없는 코드는 커밋하지 않는다.** AI 는 그 문장을 지키는 데 두 방향으로 쓰였다.

**AI 가 잘한 것 — 초안과 패턴 발견.** 워크플로 YAML, validate-env·size-limit 스크립트, ESLint selector, 테스트 골격은 AI 초안으로 시작했다. 리뷰어로서는 사람 리뷰 7건이 놓친 위반(`e2e/fixtures/auth.ts` 의 구현 상수 import)과 파이프라인 결함 3건(dependabot 이 composite action 을 안 훑음, 스크립트가 lint 밖, summary 의 입력 가드)을 찾았다. 특히 "반복 패턴" 절을 요구하자 5단계의 승격 후보가 저절로 나왔다.

**AI 가 틀린 것 — 그럴듯한 외부 사실과 규칙의 전제.** 문서를 기억으로 인용해 필요한 권한을 빼라고 했고(빼면 필터가 403), 이유가 RFC 에 있는 변경을 "설명 없음" 으로 올렸다. 8주차 실험을 짤 때 픽스처의 역상관을 모르고 latest↔price-asc 를 제안했던 것과 같은 종류다 — 데이터·문서를 열지 않고 말한다. 프롬프트 v2 의 자가 점검 3개("전제가 성립하나 / 원문을 열었나 / 규칙을 넓혔나")는 그 실패에서 나왔다.

**기계로 내린 것.** 참/거짓이 정적으로 갈리는 규칙은 사람도 AI 도 보지 않게 했다: 레이어 방향(6주차), `any`·hooks(1주차), mock 경계·E2E import(10주차), env 형태, 번들 예산. 승격의 진짜 가치는 룰 하나가 아니라 **리뷰 질문 하나를 지우는 것** 이다 — `_data` 경계가 lint 가 된 뒤 "이 import 괜찮은가" 는 아무도 묻지 않는다.

**사람에 남긴 것.** 무엇을 required 로 둘지, 예산을 몇 % 로 할지, 어떤 지적을 승격할지, `useEffect` 가 동기화인지 구독인지, `as` 의 사유가 타당한지. 그리고 AI 가 짚은 병목·만든 룰·낸 지적을 로그와 실험으로 확인하는 일. 이번 주 5단계의 "기계 / AI / 사람" 표(`week10-ci.md` 5.3)는 1주차 책임 모델 표를 이 프로젝트의 실제 사례로 다시 쓴 것이고, 10주 전체의 결론도 같다 — **AI 를 잘 쓴다는 것은 AI 의 출력을 믿는 것이 아니라, AI 가 찾은 반복을 결정적 하네스로 굳혀 AI 와 사람이 볼 것을 줄이는 것이다.**

## 8. 다시 만든다면

- **mock 백엔드의 공개 표면을 처음부터 정한다.** 6주차에 "api 는 FSD 를 import 하지 않는다" 만 정하고 반대 방향(앱이 api 내부를 import)을 비워 둔 것이 10주차의 7건이 됐다. 계약 파일 하나(`_contract.ts`)가 아니라 공개 모듈 목록을 lint 로 못박았어야 했다.
- **`process.env` 는 첫날 한 곳으로.** 5곳에 흩어진 읽기와 각자의 기본값이 10주차에야 `resolveAppOrigin` 으로 모였다. 검증 스크립트가 보는 목록과 코드가 읽는 목록이 처음부터 같았다면 3단계 게이트는 훨씬 작았다.
- **서버 컴포넌트가 자기 API 를 HTTP 로 다시 부르지 않게.** `APP_ORIGIN` 이 배포 사고의 진입점이 된 이유다. 응답 빌더 직접 호출(8주차 패턴)을 전 경로로 확장하면 origin 문제의 절반이 사라진다.
- **측정을 먼저.** 7주차(LCP)와 10주차(CI) 모두 "재고 나서 하나만 고치기" 가 통했고, 재지 않았다면 artifact 분리·pnpm 캐시처럼 교과서적이지만 여기서는 효과 없는 일에 시간을 썼을 것이다.
- **E2E 픽스처는 테스트가 소유한다.** 계정·비밀번호·URL 파라미터 이름을 앱에서 import 하지 않는다는 원칙을 첫 E2E 파일에서부터 lint 로 강제한다.
