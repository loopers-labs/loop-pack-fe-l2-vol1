# 10주 기술 회고

## 1. 프로젝트 요약

이 프로젝트는 Next.js 16 App Router와 React 19로 만든 커머스 애플리케이션입니다. 10주차에는 새
기능을 추가하기보다, 어떤 변경이 어떤 검증을 통과해야 배포까지 갈 수 있는지를 스스로 설명할 수
있게 만드는 데 집중했습니다. CI 실행 조건, 예산 게이트, AI 리뷰 기준을 정리한 것도 그 연장선입니다.

## 2. 10주 동안의 구조 변화

| 주차    | 변화                                                                 |
| ------- | -------------------------------------------------------------------- |
| 2~3주차 | 컴포넌트와 훅의 책임 분리                                            |
| 6주차   | FSD 레이어·슬라이스와 Public API 경계 정리                           |
| 8주차   | 단위·통합 테스트와 브라우저 경계 구분                                |
| 9주차   | 인증·라우팅·브라우저 흐름을 Playwright E2E로 남김                    |
| 10주차  | 위 경계들이 실제로 지켜지는지 CI 실행 조건·결정적 소비처 검사로 확인 |

돌아보면 10주차는 앞서 나눠온 경계들을 말로만 두지 않고, 실제로 지키고 있는지 기계가 확인하게
만드는 단계였습니다.

## 3. 주요 기술 결정 3개와 근거

### 조건부 E2E 경로 분류와 미분류 fallback

처음에는 변경 경로를 path filter로만 나누면 E2E 비용을 쉽게 줄일 수 있을 거라 생각했습니다. 그런데
막상 해보니 route가 추가될 때마다 분류 목록과 예외 처리를 계속 갱신해야 했고, 무엇보다 미분류
경로가 검증에서 통째로 빠질 위험이 있었습니다. 그래서 명확히 스킵해도 되는 문서·스타일 변경만
제외하고, 나머지 미분류 변경은 전체 E2E로 승격하는 쪽으로 방향을 바꿨습니다. 실제 scope 결과는
[PR #12](https://github.com/im-wen3y/loop-pack-fe-l2-vol1/pull/12)의 전체 실행과
[PR #13](https://github.com/im-wen3y/loop-pack-fe-l2-vol1/pull/13)의 문서-only 스킵에서
확인했습니다.

### 환경 변수 차단 게이트와 번들 advisory

두 게이트는 성격이 달라서 배치도 다르게 했습니다. 환경 변수 오류는 잘못된 API 주소나 secret
노출처럼 배포 전에 반드시 막아야 하는 설정 사고라 required 경로에서 실패하게 만들었습니다. 반면
번들 예산은 7주차 측정값 `273.74 kB`에 5% 여유폭을 더한 `287.4 kB`를 기준으로 삼았지만, 초과해도
되돌리기 쉬운 성능 저하라고 판단해 advisory로 남기고 초과량만 PR 코멘트에 드러냈습니다. 실제로
환경 변수 오류는 [PR #20](https://github.com/im-wen3y/loop-pack-fe-l2-vol1/pull/20)에서 Quality
failure로 확인했고, 번들 초과는
[PR #21](https://github.com/im-wen3y/loop-pack-fe-l2-vol1/pull/21)에서 경고·리포트로 확인했습니다.

### hydration 가드는 방어부터 두르지 않고, 재현해보고 뺐다 (5주차)

장바구니·위시리스트를 새로고침해도 유지되게 Zustand `persist`를 붙이면서, 서버는 0을 그리고
클라이언트는 복원값을 그려 hydration이 어긋날 거라 지레짐작하고 `useStoreHydrated` 가드부터
만들었습니다. 그런데 데모 페이지를 만들어 담기 → 새로고침을 직접 재현해보니, 훅으로 읽는 값
(`useCartStore((s) => s.ids.length)`)은 불일치가 나지 않았고 `getState()`로 직접 읽을 때만
`Hydration failed` 에러가 났습니다. zustand 훅이 `useSyncExternalStore`의 `getServerSnapshot`을
초기 상태로 고정해 돌려주기 때문이었고, Header·버튼은 전부 훅으로 읽고 있어 가드 없이도 이미
안전했습니다. 그래서 먼저 만들어뒀던 가드를 지웠습니다. 재현 절차와 스크린샷은
[`docs/week-05/hydration-test.md`](../week-05/hydration-test.md)와
[`docs/week-05/decisions.md`](../week-05/decisions.md)의 "10. persist + hydration 가드는 정말
필요했나"에 남겼습니다.

## 4. 테스트와 품질 게이트

Quality는 test·lint·typecheck·build를 모든 PR에서 실행합니다. E2E는 변경 범위에 따라 필요한
스펙을 실행하고, 감지 실패나 미분류 경로는 전체 실행으로 fallback합니다. 최종
[PR #12](https://github.com/im-wen3y/loop-pack-fe-l2-vol1/pull/12)에서는 Detect E2E scope,
Chromium, WebKit, Quality와 Vercel 검사가 모두 통과했습니다.

로컬 `pnpm verify`는 테스트 29개 파일·164개 테스트, lint, typecheck를 통과했습니다. Public API
검사는 `pnpm lint` 안에서 실행되며, `pnpm check:public-api`로 단독 재현할 수 있습니다.

## 5. 성능 개선 결과 (7주차 측정값)

Before 측정에서 E2E의 가장 긴 구간은 `Run E2E tests`였고 중앙값은 약 57초였습니다. 브라우저 설치는
약 46~~52초였으며, pnpm 캐시 hit·miss에 따른 install 차이는 약 2초 대 6~~7초였습니다. 이 값을 보고
설치 캐시를 더 복잡하게 만드는 대신, 브라우저별 job을 독립 실행하고 필요한 경로만 E2E에 태우는 조건
설계 쪽에 시간을 쓰기로 했습니다. 측정의 상세 raw 값·범위·한계는
[`week10-ci.md`](./week10-ci.md#before)에 있습니다.

번들 예산의 임계값도 새로 잰 숫자가 아니라 7주차 측정값을 그대로 재사용했습니다. 7주차에 잰 홈 JS
실제 전송 크기 `273.74 kB`에 여유폭 5%를 더해 `287.4 kB`를 임계값으로 잡았고, 지금 값이 그 임계값을
넘으면 경고로 표시되게 했습니다. 이 임계값을 required가 아니라 advisory로 둔 판단과 실제 초과
확인 로그는 3절 「환경 변수 차단 게이트와 번들 advisory」에 정리했습니다.

## 6. CI/CD와 AI 협업

Quality와 E2E workflow에는 최소 권한과 action SHA 고정을 적용했고, PR 코멘트가 필요한 Quality
job에만 `pull-requests: write`를 부여했습니다. AI는 workflow·스크립트 골격과 PR 지적 후보를
제시했지만, required 배치·예산·E2E 조건·승격 룰은 로그와 실제 diff를 직접 대조해가며 제가
결정했습니다.

[PR #12](https://github.com/im-wen3y/loop-pack-fe-l2-vol1/pull/12) AI 리뷰에서는 P2 네 건과
P4 한 건을 실제 라인 코멘트로 전달했습니다. `APP_ORIGIN` 검증 지적은 맞는 말이라 채택해 수정했고,
pagination 의견은 그 자체로는 유효하지만 이번 범위에서는 P4로 기각했습니다. 코드 사실과 규칙에
반하는 실제 오탐은 확인하지 못했으므로, 오탐을 억지로 만들어 기록하지는 않았습니다.

## 7. AI 활용 회고 — 무엇을 AI에, 무엇을 기계에 맡겼나

이번 주에 정리하면서 잡은 경계는 이렇습니다. test·lint·typecheck·build·환경 변수 형식·Public API
소비처처럼 참과 거짓을 기계적으로 가를 수 있는 부분은 기계에 맡기고, 설계 냄새나 실행 조건의
적절성, 예산 우선순위처럼 맥락 판단이 필요한 부분은 AI와 제가 나눠 맡되 AI 제안은 실제
diff·로그·실험으로 확인한 뒤에만 받아들였습니다. 이번 주 Public API 소비처 검사가 그 사례입니다.
반복되던 지적을 기계 게이트로 내렸지만, 어떤 심볼을 공개할지는 여전히 제가 결정하도록 경계를
남겼습니다.

10주 전체를 놓고 보면 이 경계는 이번 주에 갑자기 생긴 게 아니라 계속 좁혀온 결과입니다. 초반에는
컴포넌트 분리나 상태 관리처럼 사람이 눈으로 매번 판단하던 것들을, 6주차 FSD 경계와 8·9주차 테스트
경계를 거치며 점점 더 많이 결정적 규칙으로 내렸습니다. 10주차의 결론은 그 흐름의 마지막 단계로,
"판단은 사람이, 반복 검증은 기계가" 나누는 기준을 CI 게이트 하나하나에 실제로 새겨 넣은 것입니다.

## 8. 다시 만든다면

다시 한다면 이렇게 하고 싶습니다. path filter의 분류 목록과 미분류 fallback을 처음부터 같이
설계해서, 나중에 예외를 하나씩 덧붙이는 일을 줄이겠습니다. 캐시도 설정부터 추가하지 않고
hit·miss 시간을 먼저 재본 뒤, 병목이 실제로 확인될 때만 키나 job 구조를 바꾸겠습니다. AI 리뷰는
초기 프롬프트에 파일·라인 근거와 추측 금지 조건을 처음부터 못박아두고, 오탐이 실제로 나온 경우에만
전후 프롬프트를 비교해보겠습니다.

## 제출 질문

### 1. E2E를 모든 PR에 required로 걸면 어떤 문제가 생길까?

E2E 테스트가 불필요한 문서-only PR에서도 실행되면 실행 시간과 CI 비용이 늘어나 업무 병목이 생길 수
있습니다. 또한 E2E를 required로 두면서 조건부로 실행하면, 스킵된 PR의 check가 영구 대기 상태가 될
수 있습니다. 그래서 저비용 검증은 모든 PR에서 실행하고, E2E는 관련 경로에서만 실행하되 스킵 시에도
성공으로 정리되는 guard 구조가 필요합니다.

### 2. Lighthouse 점수 하락은 항상 merge blocker여야 할까?

Lighthouse 점수가 하락했다고 해서 항상 merge blocker로 둘 필요는 없다고 생각합니다. 크래시나 핵심
사용자 흐름 중단처럼 즉시 동작을 깨뜨린 문제가 아니라면, 측정 변동성과 영향 범위를 확인한 뒤 PR
머지 후 후속 개선으로 다룰 수 있습니다. 다만 반복적인 하락이나 사전에 정한 임계값을 크게 넘은
경우에는 별도 판단을 통해 차단할 수 있습니다.

### 3. Preview 환경이 production API를 바라보면 무슨 일이 생길까?

Production API와 운영 DB에는 실제 운영 데이터와 깨끗한 상태가 유지되어야 합니다. Preview가
Production API를 바라보면 Preview에서 수행한 로그인·주문·테스트 요청이 운영 DB에 기록될 수 있어
데이터 오염과 사용자 영향으로 이어집니다. 따라서 Preview에서는 배포별 URL이나 별도 테스트 환경을
사용하고, `APP_ORIGIN`이 다른 환경을 가리키지 않는지 build 전에 검증해야 합니다.

### 4. AI가 만든 workflow를 그대로 머지하면 어떤 리스크가 있을까?

AI가 만든 workflow는 조건문 오류로 필요한 검증을 스킵하거나, 실패 상황을 통과시키고, 권한 또는
secret 키를 과도하게 노출할 수 있습니다. 따라서 조건문이 정상 동작하는지 실패 상황을 만들어 확인하고,
실제 PR에서도 실행해 봐야 합니다. 또한 workflow 권한이 최소인지와 secret 값이 로그·step 환경 변수에
노출되지 않는지를 반드시 확인해야 합니다.
