## 1. 프로젝트 요약

감성 인테리어 큐레이션 커머스. Next.js(App Router) + React 19 + TypeScript, 서버 상태는 TanStack Query, URL 상태는 nuqs, 클라이언트 상태는 Zustand, 검증은 Zod로 다룬다. 1~3주차는 React+Vite 위에서 판별·분리 연습을 했고, 4주차부터 이 스택으로 본체를 만들었다. Production은 https://loop-pack-fe-l2-vol1.vercel.app 이고, main push는 전체 E2E가 성공한 SHA만 배포된다.

10주의 주제를 한 문장으로 줄이면 이렇다: **판단 기준을 세우고(1주차), 코드에 적용하고(2~7주차), 테스트로 고정하고(8~9주차), CI에 새겼다(10주차).** 각 주의 산출물이 다음 주의 근거가 되도록 쌓았다 — 1주차 리뷰 데이터가 ESLint 하네스와 AI 리뷰 기준이 되고, 7주차 측정값이 10주차 예산 임계값이 되고, 9주차 E2E 범위 판단이 10주차 조건부 실행이 됐다.

## 2. 10주 동안의 구조 변화

### 2~3주차 — "어디서 잘라야 하는가"의 기준 세우기

- 2주차([#32](https://github.com/loopers-labs/loop-pack-fe-l2-vol1/pull/32))는 동작은 하지만 상태·분기의 자리가 정리되지 않은 체크아웃 화면에서 bad smell을 판별하는 과제였다. 상태 배치가 매번 개별 판단이 되지 않도록 공유 상태의 기준을 한 문장으로 정의했다: **"결제하기를 눌렀을 때 서버로 보내는 값만 페이지가 공유한다."** 배송지·쿠폰·적립금·결제수단은 공유하고, `isTermsOpen`이나 입력 중인 `couponCode`는 각 컴포넌트 안으로 내렸다. `finalPrice`는 state를 지우고 파생 계산으로 바꿨다.
- 3주차([#55](https://github.com/loopers-labs/loop-pack-fe-l2-vol1/pull/55))에서 단일 컴포넌트 `ProductListPage`를 Components/Hooks/Services 레이어로 분리했다. 분리의 실익은 구조 미학이 아니라 **"단일 출처가 어디인가"를 강제로 묻게 된 것**이었다 — URL로 진입해도 필터가 반영되지 않던 버그의 원인이 "원본이 URL이 아니라 React state였다"로 드러났고, 이때 서버 상태는 TanStack Query, URL 상태는 nuqs로 원본별 도구를 정했다.

### 6주차 — 기준을 폴더와 하네스로 옮기기

전환 전 구조의 문제는 삭제 시나리오로 구체적으로 드러났다: 위시리스트를 지우려면 `features/wishlist` 폴더 밖에서 `shared/store.ts`(도메인과 무관해야 할 폴더에 있던 조합 코드)와 찜 버튼을 직접 import하던 `ProductCard`까지 함께 고쳐야 했고, 카드는 홈 두 섹션과 목록이 같이 쓰는 컴포넌트라 수정 영향이 세 화면으로 번졌다. "기능을 지울 때 함께 지울 코드를 폴더 이름으로 답할 수 있는가"를 성공 기준으로 두고 6주차([#122](https://github.com/loopers-labs/loop-pack-fe-l2-vol1/pull/122), [RFC](week06-fsd.md))에서 FSD로 전환했다. 현재 구조와 결정 근거:

```
app → _pages → features → entities → shared   (단방향 의존)
```

- **widgets 미도입** — 공유 조합이 헤더·카드 둘뿐이라 레이어 하나를 더 얹을 근거가 없었다.
- **`_pages` 명명** — Next Pages Router로 오인되는 것을 막는다.
- **Public API는 barrel(`export *`)이 아니라 index.ts 선별 수출**, shared는 index 없이 파일 직접 import.
- 경계는 문서가 아니라 `eslint-plugin-boundaries`로 강제했다. **직접 규칙을 만드는 것과 비교**했는데, 가능은 하지만 유지보수 관점에서 잘 만들어져 있고 앞으로도 관리될 플러그인을 쓰는 편이 낫다고 판단했다. 한계도 같이 적었다 — FSD를 표준과 다르게 쓰게 되면 직접 구현으로 돌아가야 하고, ESLint는 import 방향만 보므로 구조 관점 리뷰는 architecture-review 스킬이 맡는다. 마이그레이션 중 warn으로 위반을 추적하다 **44건 → 0건**을 확인한 뒤 error로 승격했다. 이후 구조 위반은 리뷰가 아니라 lint가 잡는다.

결과는 같은 삭제 시나리오로 판정했다: 전환 후에는 카드가 행위를 모르므로 조합 지점만 남고 store 편집도 `client-state` 안으로 좁혀져, 위시리스트 삭제 반경이 폴더 2개 + 허브 3파일 + 사용처 3파일 + 테스트 3파일로 닫힌다.

## 3. 주요 기술 결정 3개와 그 근거

### ① 상태는 도구가 아니라 "원본이 어디인가"로 분류한다 (3·5주차)

서버 응답은 TanStack Query(서버가 원본 — Zustand로 복제하면 동기화할 상태가 하나 더 생긴다), 확정된 검색·정렬·페이지는 URL/nuqs(공유·새로고침·앞뒤 이동 복원이 요구사항), 장바구니·위시리스트 ID는 Zustand persist(localStorage가 원본), 입력 중 검색어는 uncontrolled input(미확정 조건이라 URL에 안 올린다). history는 쿠팡·에어비앤비의 동작을 관찰한 뒤 `push`로 하되 마지막 페이지 초과 보정만 `replace`로 했다.

증거: 오류 화면에서 재시도 1번으로 상품 12개 복구·URL과 navigation 횟수 불변, 서버 prefetch 후 브라우저 초기 API 중복 요청 0건([#102](https://github.com/loopers-labs/loop-pack-fe-l2-vol1/pull/102)).

### ② 공통 UI는 라이브러리의 "경계"를 읽고 직접 구현한다 (4주차)

Select의 공개 API는 세 갈래 — 스타일 포함 `<Select />` 컴포넌트, render prop, hook — 를 놓고 골랐다. 컴포넌트 구조로 가면 UI 종류가 늘수록 props와 if 분기가 커지고, render prop은 DOM 구조까지 사용처가 갖게 된다. 상태와 동작 계약만 제공하는 hook(`useSelect`)이 Headless에 맞다고 판단했다. Downshift·Radix 소스에서 배운 것은 API 모양이 아니라 **왜 그 경계를 그었는가**였다: 선택 비교는 참조가 아니라 `itemToKey`(refetch·map 가공 시 selected 풀림 방지), 바깥 닫기는 blur/click이 아니라 `pointerup`, Dialog scroll lock은 document라는 전역 자원의 장부로 보고 모듈 ref-count.

결과는 수치보다 검증 사실로 남았다: 테스트 66개 통과, 그리고 Trigger의 `type="button"` 누락으로 form이 submit되는 버그를 테스트로 재현한 뒤 수정 — 라이브러리들이 왜 그 기본값을 두는지 직접 구현이 같은 함정을 밟으며 확인한 사례다([#77](https://github.com/loopers-labs/loop-pack-fe-l2-vol1/pull/77)).

### ③ 세션은 서버가 검증하고, 첫 HTML부터 로그인 상태를 반영한다 (9주차)

먼저 접근 권한의 원본을 정했다: 서버가 서명을 검증하는 httpOnly 쿠키가 원본이고, Zustand에는 서버가 전달한 초기 사용자와 로그인·로그아웃·만료에 따라 바뀌는 UI 복사본만 둔다. 그다음 문제는 **그 로그인 상태를 첫 화면에 어떻게 담는가**였다. `/api/auth/me`를 React Query로 조회하면 캐시·재검증 기능을 얻지만, 첫 HTML 이후 같은 사용자 정보를 한 번 더 요청하게 된다. 그래서 commerce layout에서 `cookies()`를 읽어 요청별 `SessionProvider`에 `initialUser`를 전달했다 — 재호출 없이 헤더·마이페이지가 첫 HTML부터 로그인 상태를 보여주는 대신, layout이 `cookies()`를 읽는 순간 **커머스 전체가 동적 렌더링되는 비용을 감수**했다.

감수한 범위는 감수로 끝내지 않고 검증했다: 7주차에 분리해 둔 홈 셸과 Hero가 느린 데이터 조회에 다시 묶이지 않는지 production build에서 확인했다. 경계 처리도 같은 원칙이다 — `next` 파라미터는 `toSafeNextPath()`로 open redirect(`//evil.com` 등)를 차단하고, 401은 "로그인 API의 401(폼 내부)"과 "인증 필요 API의 401(세션 만료, `error.tsx` 한 곳)"으로 나눠 처리했다([#185](https://github.com/loopers-labs/loop-pack-fe-l2-vol1/pull/185)).

## 4. 테스트와 품질 게이트 (8~10주차)

### 무엇을 어느 층에서 보는가 (8주차)

커버리지 수치가 아니라 "지키기로 한 동작"을 먼저 정하고 15개 항목을 배치했다: 단위 3(개수 파생·URL→query key·총 페이지 계산), 통합 8(목록 상태·조건 변경·스토어 반영), E2E 4(URL 반영·히스토리·새로고침·진입→담기). 환경은 Vitest `test.projects`로 node/jsdom을 분리해 전체 Duration **4.18s → 2.21s(−47%)**, node로 옮긴 7개 파일 단독은 4.18s → 0.27s(−93%). 분리 기준은 확장자(`.ts`/`.tsx`)로 시작했다가 예외 2종이 생겨 `*.dom.test.*` 명명 기준으로 바꿨다 — 기준이 예외를 만들면 기준을 바꾼다([#167](https://github.com/loopers-labs/loop-pack-fe-l2-vol1/pull/167), [테스트 계획](week08-test-plan.md)).

테스트가 진짜 잡는지는 변이 실험 4건으로 확인했다. 3건은 잡혔고, `confirmedTotalPages` 가드 삭제는 살아남았는데 — **살아남은 변이를 곧 빈틈으로 세지 않고** "지키기로 한 동작인가"를 먼저 물었다. 재현 테스트를 붙여봤지만 캐시 만료 타이밍에 묶여 깨지기 쉬워 제거하고 주석으로 남겼다. 이 과정에서 `keepPreviousData`가 재조회 실패 시 직전 목록을 날리는 실제 버그를 재현·수정했다.

### E2E는 빈도가 아니라 실패 비용으로 고른다 (9주차)

시드 로그 7,514세션(봇 486세션·중복 77건 정제 후)을 분석했지만, 로그는 후보 선정용이고 최종 기준은 **사용 빈도 × 실패 비용 × 브라우저 필요성**이다. 그래서 결정이 빈도 순위와 반대였다: 최다인 목록 조작(60.5%)은 통합+기존 E2E가 이미 커버해서 제외, 인증(8.6%)과 주문 완료(5.6%)는 보호 기능의 관문·거래 경계라서 포함([RFC](week09-e2e-scope.md)).

E2E 고유 가치는 파괴 실험으로 실증했다: 쿠키 `path: "/" → "/api"`로 바꾸면 **통합 389개는 전부 통과하고 E2E만 실패한다** — 통합은 Set-Cookie 문자열만 보고, 브라우저의 Path 해석은 E2E만 본다.

### 게이트로 굳히기 (10주차)

- 테스트 궤적: 66개(4주차) → 158개(6주차) → 205개(8주차) → 389개(9주차) → 490개+E2E 16개(10주차).
- 단언 품질은 ESLint 하네스로 내렸다: `toBeTruthy`/`toBeDefined`/`not.toBeNull` 금지("값·개수·텍스트로 단언합니다"), `no-disabled-tests`·`no-focused-tests`로 침묵 처리 차단.
- required는 `checks`·`guard`(+strict)만. 전체 E2E는 PR required가 아니라 **Production 배포 조건**이고(사후 검출이 아니라 배포 차단), Lighthouse는 변동성, AI 리뷰는 비결정성 때문에 required에서 뺐다(ADR-12).

## 5. 성능 개선 결과 (7주차)

측정 절차를 `measure-protocol.md`에 고정하고(SHA 외 조건 동일, Lighthouse 5회 중앙값), 라운드마다 가장 작은 변경만 반영했다([#146](https://github.com/loopers-labs/loop-pack-fe-l2-vol1/pull/146), [기록](../week-07-performance/)).

| 홈 (Desktop) | Before `4a04dddf` | After `d3c6b8d5` |
| --- | --- | --- |
| LCP | **6.7 s** | **0.8 s** |
| FCP | 0.3 s | 0.3 s |
| CLS | 0.004 | 0.006 |

핵심은 LCP 총합이 아니라 **축 분해**였다: TTFB 40ms / 로드 지연 530ms / 다운로드 6.14s / 렌더 80ms로 쪼개고 긴 두 축에만 개입했다.

- **R1** `cf571ae6` — `next/image`로 Hero 전송 크기 **7,368 KiB → 399.7 KiB(−94.6%)**. 원본 intrinsic은 3840×2160 그대로다 — 이미지를 줄여 수치를 낮춘 게 아니다. AVIF는 20% 더 작지만 인코딩이 50% 느려 WebP q=75 유지.
- **R2** `f787a51a` — Hero를 Suspense 밖 셸로 이동해 로드 지연 520 → 10~30ms. 대신 CLS 0 → 0.008 회귀가 생겼고, **R3** `4070396f`에서 `min-height: 132px` 실측 예약으로 0.006까지 줄인 뒤 잔여분은 감수했다.
- **R5** — 갱신 중 이전 목록 유지(`placeholderData` 확대)로 목록 갱신 중 CLS 0.33이 새로 생겼다. 4가지 시도(제목 고정·key 재생성·빈 자리 확보·스크롤 이동)를 전부 되돌리고, "목록을 비우지 않는다"는 요구를 지키는 쪽으로 감수를 기록했다. 줄인 수치만큼 **안 줄이기로 한 수치와 그 이유**를 남긴 게 이 주의 산출물이다.

R0에서 가설 4개에 반증 조건을 미리 적어두고 After에서 판정했다(2개 적중, 2개 유지). 이 측정값은 10주차 예산 임계값의 근거로 재사용된다(6절).

## 6. CI/CD와 AI 협업 (10주차)

### 측정하고 병목만 줄였다 (1단계)

같은 커밋에서 cold/warm 각 3회 측정([기록](week10-ci.md)):

| wall-clock | Before (run 34329855053) | After (run 34357394959) |
| --- | --- | --- |
| cold 중앙값 | 144초 (128–146) | **94초 (91–110, −35%)** |
| warm 중앙값 | 134초 (132–151) | **71초 (69–83, −47%)** |

병목은 타임스탬프로 지목했다: `pnpm check` 직렬 실행 중 E2E 32~33초 + Playwright 설치 23~32초 = **약 60초, 전체의 43%**. 여기에 맞는 전략 3개만 적용했다 — job 병렬화(checks ∥ build-e2e), E2E webServer의 중복 build 제거(32 → 20~22초), Playwright 브라우저 캐시(설치 27 → 15초; 공식 문서는 비권장이지만 실측 이득으로 유지). node_modules artifact 전송(warm install이 이미 2초), Next build 캐시(build 11초) 등 병목과 무관한 전략은 근거와 함께 안 썼다. After 판정은 "Before/After 구간이 겹치지 않을 때만 개선"으로 측정 전에 고정했다(ADR-4).

캐시는 걸었다고 믿지 않고 깨서 증명했다: lockfile 변조 `7b1c55a5` → run 34363213822에서 pnpm store만 miss(브라우저 캐시는 버전 키라 hit), 원복 `a098c839` → run 34363761765에서 `reused 540, downloaded 0`·install 2초 복귀.

### 검증을 4층으로 나눴다 (2단계)

전체 E2E 16개를 모든 PR에 required로 돌리는 것이 왜 답이 아닌지부터 수치로 확인했다: CI에서 전체 E2E step 중앙값 21초(19–23) vs 핵심 3개 10초(8–12), 같은 코드 로컬 비교로는 11.774초 차이다([비용 기록](week10-e2e-cost.md)). 문서만 고친 PR에서도 이 비용과 flaky 노출면을 지불하게 되고, required로 걸어둔 검증이 조건부로 실행되지 않으면 머지가 영영 막힌다. 그래서 검증을 결정성과 비용 기준으로 4층으로 나눴다:

| 층 | 실행 조건 | 내용 |
| --- | --- | --- |
| ① 모든 PR | 무조건 | lint·type·unit 전체 + **변경 관련 integration**(vitest related, 관련 6초 vs 전체 16초) + build + env + 번들 예산 |
| ② 핵심 E2E | main 대상·non-draft·런타임 변경 PR | `@critical` 3개(로그인 성공/실패·주문) |
| ③ 전체 E2E | main push | 16개 성공 후 **같은 SHA만 Production 게시** |
| ④ 정기 | 주 1회 + 수동 | 전체 E2E + Lighthouse |

스킵 안전 논리: 문서만 바꾼 PR은 런타임을 안 바꾸고, required 충돌은 **guard job이 "의도된 생략"을 성공으로 보고**하는 구조로 막았다. 비핵심 E2E 회귀는 main까지는 들어올 수 있지만 배포 전 전체 E2E가 사용자 노출을 차단한다 — 보장 범위의 한계까지 적었다. 실증은 PR 쌍으로 했다: 코드 PR #4(핵심 E2E 실행)·문서 PR #5(생략·머지 가능), draft↔ready 재판정 #6, 비핵심 실패를 일부러 머지해 배포가 차단되고 기존 Production이 유지되는 것 #9→#10(차단 run 34441821105 → 원복 34442109441, 복구 4분08초). flaky는 CI만 retries 2로 두고 42회 실행에서 flaky 0을 기록했다.

### 임계값은 실측에서 나왔다 (3단계)

번들이 늘어나는 것은 lint·type·테스트 어느 것도 막지 않는다 — 실증 PR #35에서 홈 초기 JS가 231,993B(+60,637B, +35.4%)로 늘어난 상태에서도 lint·typecheck·테스트 490개는 전부 통과했고, 예산 게이트만 빨간불이었다. 이 축을 보는 게이트가 예산이고, 임계값은 감이 아니라 실측에서 정했다.

- **번들 예산(size-limit)**: 홈 155,779B·목록 159,533B·공유 149,479B(3회 측정 범위 0)에 `현재값 + 범위 + 10%` = **171,356 / 175,486 / 164,426B**. 7주차의 7,368KiB→409kB는 이미지 전송량이라 JS 예산 근거로 쓰지 않고, 7주차 SHA `d3c6b8d5`를 재측정해 한 달 증가 속도 +2.5~5.4%를 확인 — 임계값은 서너 달치 여유다. 여유율이 실제로 유효한지는 zod 클라이언트 유입 실측 +72,880B(+46.8%) = 즉시 빨간불로 확인했다.
- **env 게이트**: Zod 규칙 하나를 `next.config.ts` phase(빌드)와 `instrumentation.register()`(서버 시작) 두 시점에서 호출한다. URL 형식 오류, 비밀 값의 `NEXT_PUBLIC_` 변형, 시크릿 누락이면 exit 1. 검사 자체는 0.1초(run 34487715872)라 별도 job이 아니라 build 앞 step으로 뒀다.
- **빨간불 실증**: env 오류 PR #22 — run 34501339378 BLOCKED → 원복 run 34501597916 green. 번들 초과 PR #35 — `57697d5e`에서 `mergeStateStatus=BLOCKED`·코멘트에 초과량 표시 → 원복 `af6d63ad`(159,491B)에서 같은 코멘트가 초록으로 갱신(PR #36에 기록).
- **결과 가시성**: Quality 완료를 `workflow_run`으로 받아 PR 코멘트 1개로 게시한다(`pr-comment.yml`, PR 코드 미실행). 로그를 열지 않아도 무엇이 얼마나 초과했는지 PR 화면에서 보인다.

### AI 리뷰는 advisory, 반복 지적은 룰로 (4~5단계)

- `ai-review.yml`은 Quality 완료 후 `workflow_run`으로 돌고, **advisory**다(비결정적 검증을 required로 두지 않는다는 9주차 논리, ADR-11). 한도: 호출 1회·6,000토큰·3분·입력 1MiB·재실행 1회. PR head는 Git 객체로만 읽고 실행하지 않으며 `pull_request_target`은 쓰지 않는다. 첫 리뷰는 PR #25에서 기준 6개를 읽고 게시하는 것까지 확인했고, 지적을 못 남기던 원인 4가지(그중 "하나가 어긋나면 전체를 버리는" 두 경로)는 PR #26·#33에서 고쳤다.
- 리뷰 기준은 일반론이 아니라 10주간의 규칙이다. 1~9주차 요구사항을 [감사 문서](week10-ai-review-requirements-audit.md)로 전수 대조해 rules 3종(`rendering`·`performance`·`state-data`) 신설·`testing` 보강, 스킬 4종(`state-design-review`·`test-design-review`·`e2e-scope-review`·`workflow-review`) 신설로 내렸다(PR #29·#37).
- **잘 잡은 리뷰 / 헛소리 판별**([기록](week10-ai-review.md)): 같은 기준으로 로컬(Claude Code)과 CI(gpt-5.6-luna) 두 형태에서 쌍을 확보했다. 잘 잡은 쪽 — checkout draft의 **두 출구 비대칭**: 로그아웃은 `clearCheckoutDraft()`로 지우는데 세션 만료는 안 지워서, 같은 탭에서 사용자가 바뀌면 B가 A가 고른 상품·수량을 그대로 확정할 수 있는 경로를 파일·줄 번호와 재현 순서로 짚었다. CI 쪽에서는 4단계에 신설한 `state-data.md` 조항이 `CurrencySelect`의 hydration 불일치 지적을 실제로 만들어냈다. 헛소리 쪽 — 저장소에 없는 CI 명령(`--workers=2`)을 비용 측정 문서에서 옮겨 적어 blocker 등급을 지탱했고, CI 리뷰는 `!cancelled()`의 플랫폼 의미론을 지어냈다가 실제 run 34518767357이 반증했다. 두 오탐의 공통점은 **자료에 없는 사실을 전제로 삼은 것**이다.
- **프롬프트 개선**: 오탐의 원인을 모델의 확신도가 아니라 **근거의 출처**로 진단하고, test-review 스킬에 "지적의 근거는 직접 읽은 파일에서 인용해 확인한 것만 쓴다" 조항을 신설했다(v1/v2는 SHA-256으로 고정). 같은 조건 재실행에서 목표한 오탐은 사라지고 기존 유효 지적 5개는 유지됐다 — 다만 v1의 유효 지적 3건이 누락된 것도 같은 실행의 결과라, 한 번의 비교를 "정확도 향상"으로 일반화하지 않고 "특정 오탐이 조항 추가 후 같은 조건에서 재현되지 않았다"까지만 기록했다.
- **결정적 룰 승격 1건**: 판별 과정에서 확증된 지적(타임존 고정 없는 `toLocaleString` 단언)을 **날짜 로케일 포맷 금지 룰**로 승격했다(`no-restricted-syntax`, `f4d5e02a`). 근거 — 구현과 테스트가 같은 식으로 기대값을 만들면 로컬(KST)과 CI(UTC)가 서로 다른 값을 단언하며 **양쪽 다 통과**한다. 화면이 틀린 시각을 보여줘도 빨간불이 없다. 오탐을 좁히려 금액 표시(`Number.toLocaleString`)는 수신자 검사로 제외하고, 타임존을 고정하는 `shared/format-datetime.ts`만 예외로 뒀다. flat config에서 테스트 블록이 같은 룰을 통째로 덮어 조용히 사라지는 경로에는 회귀 검사(`scripts/eslint-locale-date.test.ts`)를 남겼고, 승격한 검출 범위는 test-review 스킬에서 뺐다("린트가 막으므로 다시 지적하지 않는다") — 같은 검토를 AI가 반복하지 않도록 책임을 실제로 옮겼다.

## 7. AI 활용 회고 — 무엇을 AI에, 무엇을 기계에 맡겼나

10주간 위임 범위는 넓어졌지만 검증 주도권은 넘기지 않았다: 1주차엔 룰을 이해하려고 물었고, 4주차엔 라이브러리 소스 분석과 테스트 구현을 맡겼고, 8주차엔 변이 실행·수집을, 10주차엔 workflow 초안과 실증 실험 실행까지 맡겼다. 대신 매주 같은 것을 지켰다 — **AI 산출물은 읽고 검증한 뒤 채택하고, 판단(범위·임계값·required·수용/반려)은 직접 한다.** 6주차부터는 AI의 구조 지적도 사람 리뷰처럼 수용/반려 근거를 남기는 대상으로 다뤘고, 8주차엔 반대로 AI가 내 테스트의 거짓 양성 3건을 잡아주기도 했다. 10주차엔 헛소리를 찾으려고 리뷰 지적 27건을 코드로 훑다가 오히려 8건을 확증하기도 했다 — 판별은 오탐만 거르는 게 아니라 수용할 것을 확정하는 일이기도 했다.

이 경험이 책임 모델의 결론으로 이어진다. 판별 기준은 **결정적으로 참/거짓을 가를 수 있는가**다:

| 담당 | 맡긴 것 | 근거 |
| --- | --- | --- |
| 기계 (결정적 게이트) | lint·type·테스트 490개, FSD 경계(6주차, 44→0 후 error), 단언 하네스(8주차), env·번들 예산·E2E 게이트, 날짜 로케일 포맷(10주차) | 참/거짓이 갈리고 반복 비용이 0에 수렴 |
| AI (advisory) | PR diff 리뷰(rules·스킬 기준), 초안(YAML·픽스처·테스트·문서), 조사·실험 실행 | 그럴듯하게 틀릴 수 있어 게이트로 안 둠 |
| 사람 (작성자) | 지킬 동작 선정, E2E 범위, 임계값·required, AI 지적 수용/반려, 승격 대상 선택 | 맥락·비용 판단은 결정적으로 판별 불가 |

그리고 이 모델은 정적이 아니다. **AI·사람이 반복 지적하는 것 중 결정적으로 판별 가능한 게 생기면 기계로 내린다** — 6주차 FSD 경계와 8주차 단언 룰이 그렇게 내려갔고, 10주차엔 날짜 로케일 포맷이 같은 절차(반복 지적 → 룰 승격 → 양방향 검증 → AI 검사 범위에서 제거)로 내려갔다. 반대로 **기계에 못 내리는 것도 판별로 확인했다**: 같은 리뷰 스킬이 같은 중복(`productById` Map)을 한 화면에서는 공통화하라고, 다른 화면에서는 하지 말라고 낸 사례처럼, 중복의 공통화 여부나 테스트 이름과 단언의 의미 대조는 사실 다툼이 아니라 판단 다툼이라 AI·사람에 남긴다. "AI를 잘 쓴다"의 내 결론은 AI를 많이 쓰는 게 아니라, **AI가 찾은 반복 패턴을 하네스로 굳혀 AI와 사람이 볼 것을 줄여가는 것**이다.

## 8. 다시 만든다면

**매 주차 배운 것을 그 주에 rule·skill로 승격하고, 결정적/비결정적 게이트를 그때그때 갱신한다.** 10주차에 한 일 — 1~9주차 요구사항 전수 감사, rules 3종·스킬 4종 신설, 날짜 로케일 룰 승격 — 은 전부 소급 작업이었고 비용이 컸다. 그런데 재료는 매주 이미 있었다. 타임존 함정은 test-review의 검토 표에 문장으로 있었는데 린트가 된 건 10주차였고, 승격 후보 풀의 "HTTP 호출 위치 강제"는 3주차(API 분리)·5주차(팩토리)·9주차(401 단일화) 세 번 재등장한 규칙인데 열 주 내내 게이트가 아니었다. 문장과 게이트 사이의 그 시차 동안 같은 검토가 문서 없이 대화로 반복됐다 — 반복 지적을 rule·skill로 옮긴 커밋의 "왜"가 정확히 그 문장이다.

**반복 지적의 감지도 회고가 아니라 그 자리에서 한다.** 리뷰에서 같은 지적이 두 번 나오면 즉시 승격 후보 목록에 올리고, 주차를 닫을 때 후보를 결정적(린트·CI 검사)과 비결정적(rule 문서·스킬)으로 갈라 반영한다. 이 루프를 1주차부터 돌렸다면 10주차 5단계는 새로 만든 절차가 아니라 이미 돌던 루프의 열 번째 반복이었을 것이고, 전수 감사 대신 후보 목록에서 고르기만 하면 됐을 것이다.

**저장하는 상태에는 "소유자"를 처음부터 새긴다.** 5주차 상태 분류의 축은 원본·수명·공유 범위 세 개였고, "사용자가 바뀔 때 남길 값인가"라는 네 번째 질문이 없었다. 그 공백이 10주차 리뷰의 가장 좋은 지적으로 돌아왔다 — checkout draft에 소유자 표시(userId)가 없어 로그아웃은 지우고 세션 만료는 안 지우는 두 출구가 서로 다른 답을 냈고, 같은 탭에서 사용자가 바뀌면 B가 A가 고른 상품·수량을 그대로 확정할 수 있는 경로가 열려 있었다(6절). 다시 만든다면 계정 범위 데이터를 기기 저장소에 둘 때 "사용자 전환 시 지운다/남긴다"를 저장 설계 시점에 같이 결정한다 — 상태 분류 표에 열 하나를 처음부터 추가하는 일이다.
