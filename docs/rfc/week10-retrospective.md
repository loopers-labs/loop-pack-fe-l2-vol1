# 10주 기술 회고

각 절의 주장에는 커밋 SHA, Actions run, 측정값, PR 링크를 붙였다. 실행하지 않은 것은 실행하지 않았다고 적었다.

---

## 1. 프로젝트 요약

Next.js 16 · React 19 · TypeScript로 만든 커머스 화면(홈, 상품 목록, 장바구니·위시리스트, 주문, 인증)이다. 10주 동안 화면 기능보다 **무엇을 어떤 근거로 통과시킬지**를 정하는 데 시간을 더 썼다.

10주차에 바뀐 것은 검증의 위치다. 사람이 매번 눈으로 보던 것 중 결정적으로 판별할 수 있는 항목을 CI로 내렸고, 판별 기준이 맥락에 걸리는 항목은 AI·사람 리뷰에 남겼다. 검증을 어디까지 끝낼지는 **컷**으로 나눴다.

| 컷   | 정의                                      | 이번 주 상태                       |
| ---- | ----------------------------------------- | ---------------------------------- |
| CI   | 코드만 있으면 재현되는 결함               | 검증 구축 완료                     |
| CD   | 배포된 실행 환경이 있어야 재현되는 결함   | **배포 환경이 없어 확인하지 못함** |
| LIVE | 실제 사용자 트래픽이 있어야 드러나는 결함 | 수집 경로가 없어 판정하지 않음     |

컷과 required는 다른 축이다. 컷은 "어디서 확인이 끝나는가", required는 "실패하면 무엇을 멈추는가"를 정한다. 둘을 섞지 않으려고 표를 나눠 적었다(4절).

## 3. 주요 기술 결정과 근거

### 결정 1 — 병목을 로그로 지목한 뒤 그것만 제거했다

`quality` job은 E2E를 실행하지 않는데도 Chromium을 설치하고 있었다. 먼저 재고 없이 Before를 6회 측정해 가장 긴 단계를 특정했다.

| 구분        | raw              | 중앙값 | 범위 |
| ----------- | ---------------- | -----: | ---: |
| Before cold | 91초, 85초, 94초 |   91초 |  9초 |
| Before warm | 81초, 88초, 90초 |   88초 |  9초 |

모든 표본에서 가장 긴 단계는 24~30초의 Chromium 설치였다. 설치 step만 제거하고 검증 순서·범위는 그대로 뒀다(`76f332c9`).

| 구분       | raw              | 중앙값 | 범위 |
| ---------- | ---------------- | -----: | ---: |
| After cold | 62초, 64초, 71초 |   64초 |  9초 |
| After warm | 68초, 56초, 60초 |   60초 | 12초 |

cold 중앙값 91→64초, warm 중앙값 88→60초다. 두 변화량(27·28초)이 각 조건의 범위(9·12초)보다 크고, 제거한 단계가 차지하던 24~30초와 크기가 가깝다. 그래서 이 변화를 해당 단계 제거와 연결해 설명할 수 있다.

**하지 않은 것** — job 분리는 후보에서 뺐다. 이 병목과 직접 연결되지 않고, 나누면 러너 총 사용 시간이 늘어난다. 캐시 효과도 단정하지 않았다. install은 warm에서 1~2초, cold에서 6초였지만 job 전체 중앙값 차이는 3초로 범위보다 작았다.

근거: `docs/rfc/week10-ci.md`, [Before run 34497848152](https://github.com/kate-son/loop-pack-fe-l2-vol1/actions/runs/34497848152) / [After run 34501622108](https://github.com/kate-son/loop-pack-fe-l2-vol1/actions/runs/34501622108)

#### 측정과 분리해 둔 것 — 동시 실행 정책

> 병목 측정 이후 중복 실행을 줄이기 위한 workflow 운영 정책을 추가했다. 단일 실행 시간 개선으로 해석하지 않았으며, 기존 Before/After 수치에는 반영하지 않았다.

키에 ref가 없으면 PR 실행이 `main` push 실행을 취소할 수 있고, 취소를 무조건 켜면 `main` push 실행이 뒤 실행에 끊긴다. 그래서 두 조건을 함께 걸었다.

> `quality.yml`의 `concurrency`는 `github.ref`를 그룹 키에 포함하고, `pull_request` 이벤트에서만 `cancel-in-progress`를 활성화한다. 따라서 설정 구조상 PR 실행끼리만 취소되고 `main` push 실행은 취소 대상에서 제외된다. 다만 `main` push 동시 실행 실험은 수행하지 않았다.

정적 검토로 확인한 것과 실행으로 확인한 것을 나눠 적는다.

| 확인 항목                              | 확인 방식  | 결과                                                                                                                                                                                                                                                                           |
| -------------------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 그룹 키에 `github.ref` 포함            | 정적 검토  | `.github/workflows/quality.yml:16`                                                                                                                                                                                                                                             |
| 취소가 `pull_request`에서만 활성화     | 정적 검토  | `.github/workflows/quality.yml:17` — `push` 이벤트에서는 식이 `false`로 평가된다                                                                                                                                                                                               |
| YAML 문법                              | 정적 검토  | prettier 파싱 통과                                                                                                                                                                                                                                                             |
| 같은 PR 연속 push에서 이전 실행만 취소 | **실행**   | [34519325667](https://github.com/kate-son/loop-pack-fe-l2-vol1/actions/runs/34519325667) `cancelled` → [34519371648](https://github.com/kate-son/loop-pack-fe-l2-vol1/actions/runs/34519371648) `success` ([PR #15](https://github.com/kate-son/loop-pack-fe-l2-vol1/pull/15)) |
| `main` push 동시 실행                  | **미수행** | `main`에 push하지 않아 재현 범위 밖이다                                                                                                                                                                                                                                        |

마지막 줄이 이 항목의 한계다. `main` 쪽은 설정 구조로만 판단했고 실행으로 보여 주지는 못했다.

### 결정 2 — E2E는 조건부로 실행하되 required 자리는 guard job에 뒀다

E2E는 느리고 변동이 있어 모든 PR에서 돌릴 이유가 약하다. 그렇다고 job 자체를 required로 지정하면, 스킵된 회차에서 결과가 보고되지 않아 머지가 영영 막힌다.

그래서 실행 여부를 판정하는 `changes`, 실제 실행하는 `e2e`, **항상 결과를 보고하는** `e2e-required` 세 job으로 나눴다. guard는 두 조합만 통과시킨다.

| `changes` 판정 | `e2e` 결과 | `e2e-required` |
| -------------- | ---------- | -------------- |
| `false`        | `skipped`  | 성공           |
| `true`         | `success`  | 성공           |
| 그 외 전부     | —          | 실패           |

판정 출력이 비었거나 예상 밖인 경우, `changes` job 자체가 실패한 경우도 실패로 처리한다. 스킵을 통과로 오해하지 않기 위해서다. 경로 필터는 **생략해도 되는 문서 경로만** 나열해, 분류하지 않은 경로가 생기면 실행 쪽으로 기울게 했다.

근거: `docs/rfc/week10-step02.md`, `.github/workflows/e2e.yml`

### 결정 3 — 반복된 리뷰 지적 하나를 스크립트로 내렸다

10주차 AI 리뷰 프롬프트 v1~v4 네 번 모두, 그리고 그 전 사람 리뷰에서 되풀이해서, 추적되는 RFC가 무시된 로컬 문서 디렉터리를 가리킨다는 지적이 나왔다. 파일 경로와 링크 문법만 보면 참/거짓이 갈리므로 `scripts/validate-rfc-links.mjs`로 내렸다.

판정 기준을 **문자열 등장**이 아니라 **문서 경로로 해석되는 참조**로 좁힌 것이 이 결정의 핵심이다. 문자열을 막으면 규칙을 설명하는 문서가 자기 규칙에 걸린다. 코드로 표시된 문자열은 링크로 렌더링되지 않아 따라갈 수 있는 참조가 만들어지지 않으므로 통과시킨다.

근거: `docs/rfc/week10-step05.md`, [위반 run 34515725879](https://github.com/kate-son/loop-pack-fe-l2-vol1/actions/runs/34515725879) / [복귀 run 34515873701](https://github.com/kate-son/loop-pack-fe-l2-vol1/actions/runs/34515873701)

## 4. 테스트와 품질 게이트

### 실행 조건과 required 실제 상태

| 검증                            | 컷             | 실행 조건          | required 실제 상태                |
| ------------------------------- | -------------- | ------------------ | --------------------------------- |
| lint / typecheck / unit / build | CI             | 모든 PR            | 현재 미설정                       |
| E2E                             | CI             | 관련 변경 PR       | guard 구조 검증 완료, 현재 미설정 |
| 번들 예산 · 환경 변수 형식      | CI             | 모든 PR            | 구현 결과에 따라 후보             |
| RFC 링크 검사                   | CI             | 모든 PR            | `quality` 안에 포함, 현재 미설정  |
| 배포 값 · URL smoke             | CD             | 배포 후            | 배포 환경 없음                    |
| Web Vitals                      | LIVE           | 실사용 데이터 수집 | 미측정                            |
| AI 리뷰                         | 컷 밖 advisory | 수동 실행          | required 아님                     |

**현재 `main`과 `feat/week-10`에는 branch protection이 없고, 따라서 영구 required check도 없다.** 위 표의 "후보"는 required로 지정하려고 정해 둔 대상이라는 뜻이지 지금 걸려 있다는 뜻이 아니다.

### required 동작은 임시 보호 브랜치에서 확인했다

`main`에 영향을 주지 않기 위해 임시 브랜치 `experiment/week10-protected-base`에만 `quality`·`e2e-required`를 required로 지정하고 세 경로를 확인한 뒤, 설정과 브랜치를 지웠다.

| 경로               | PR                                                              | `e2e`     | `e2e-required` | mergeStateStatus |
| ------------------ | --------------------------------------------------------------- | --------- | -------------- | ---------------- |
| 앱 파일 변경       | [#11](https://github.com/kate-son/loop-pack-fe-l2-vol1/pull/11) | success   | success        | **CLEAN**        |
| 문서만 변경        | [#12](https://github.com/kate-son/loop-pack-fe-l2-vol1/pull/12) | `skipped` | success        | **CLEAN**        |
| E2E 단언 고의 실패 | [#13](https://github.com/kate-son/loop-pack-fe-l2-vol1/pull/13) | failure   | **failure**    | **BLOCKED**      |

세 PR은 base와 보호 설정이 같고 `quality`도 모두 성공했으며 리뷰 요구를 걸지 않았다. 그래서 #13만 막힌 것을 `e2e-required` 실패로 볼 수 있다.

### 게이트가 실제로 빨간불을 켜는지

| 게이트        | 위반을 만든 방법                 | 결과                                                                                                                                                                                                  |
| ------------- | -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 번들 예산     | `/products`에 무거운 import 주입 | [실패](https://github.com/kate-son/loop-pack-fe-l2-vol1/actions/runs/34511183387) — `Bundle budget`만 실패, [복귀 후 통과](https://github.com/kate-son/loop-pack-fe-l2-vol1/actions/runs/34511448577) |
| E2E guard     | 단언을 깨뜨림                    | 실패 → 머지 차단 (위 #13)                                                                                                                                                                             |
| RFC 링크 검사 | 위반 링크가 든 문서 추가         | 실패 → 제거 후 통과 (3절)                                                                                                                                                                             |

임계값을 낮춰 통과시키는 방식은 쓰지 않았다. 그러면 "번들이 커져서 막혔다"가 아니라 "예산 설정만 바뀌었다"가 된다.

### workflow 보안

| 항목                  | 적용                                                                            |
| --------------------- | ------------------------------------------------------------------------------- |
| 최소 권한             | 두 workflow 모두 기본 `contents: read`. `changes` job에만 `pull-requests: read` |
| third-party action 핀 | `pnpm/action-setup`을 커밋 SHA로 핀. `actions/*`도 SHA + 버전 주석              |
| `pull_request_target` | 쓰지 않음                                                                       |
| 자격 증명             | `persist-credentials: false`                                                    |
| CI의 비밀값           | 실제 값을 넣지 않고 로그에 남아도 되는 검증용 값만 주입                         |

| `/`         | 219,033 | 3,213 | **222,246** | 0        |
| `/products` | 228,480 | 3,213 | **231,693** | 0        |

byte 단위까지 세 번 모두 같았다. 예산은 최대 진입점 231,693 B + 10% → 249KB로 정했다. **10%는 측정 변동폭이 아니라 정책값이다.** 반복 범위가 0이라 흔들림 대비 여유는 필요 없고, 의존성 패치 같은 작은 증가를 매번 막지 않으려고 둔 폭이다.

### 10주차에 다시 잰 값 — CI 시간

3절 결정 1의 Before/After 표가 그대로 이 절의 결과다. cold 91→64초, warm 88→60초.

## 6. CI/CD와 AI 협업

### 항목별 컷 분류

주차 단위가 아니라 **항목 단위**로 나눠야 한다. 같은 주차 안에서도 코드만으로 끝나는 것과 배포 환경이 있어야 하는 것이 섞여 있기 때문이다.

| 항목                              | 컷          | 이번 주 상태                     |
| --------------------------------- | ----------- | -------------------------------- |
| 4주차 production build 확인       | CI          | `quality`의 `Build`로 매 PR 확인 |
| 4주차 Preview URL 동작            | CD          | 확인하지 못함                    |
| 5주차 상태·URL 동기화 코드 규칙   | CI          | 단위·통합 테스트로 확인          |
| 6주차 FSD 경계                    | CI          | `lint`로 확인                    |
| 9주차 로컬 production build E2E   | CI          | `e2e` job으로 확인               |
| 9주차 배포 환경의 쿠키·환경 변수  | CD 후보     | 확인하지 못함                    |
| 환경 변수 형식·접두사 오용        | CI          | `validate:env --context=ci`      |
| 환경 변수 실제 주입·fallback 여부 | CD          | 스크립트만 준비, 실행하지 못함   |
| Lighthouse 실험실 측정            | 게이트 아님 | 참고용                           |
| 실사용 Web Vitals                 | LIVE        | 수집 경로 없음                   |

> 배포 환경이 준비되지 않아 Preview·Production URL에서의 환경 변수 주입, 쿠키, 배포 후 smoke test는 확인하지 못했다. 로컬 production build에서 재현 가능한 항목은 CI 컷으로 검증했고, 실제 배포 환경이 필요한 항목은 CD 검증 계획으로 남겼다. Lighthouse 실험실 측정은 배포 게이트로 사용하지 않았으며, 실제 사용자 데이터가 없어 LIVE 컷 판정은 수행하지 않았다.

### 환경 변수 검증을 두 컷으로 나눈 이유

`src/app/api/_data/auth.ts:16`과 `src/shared/api/response.ts:23`에 fallback이 있어, 값을 주지 않아도 빌드와 실행이 통과한다. 그 상태로 배포되면 기본 시크릿으로 돌지만 코드 검증으로는 드러나지 않는다.

| 컷  | 무엇을 보나                                       | 상태          |
| --- | ------------------------------------------------- | ------------- |
| CI  | URL 형식, 시크릿 존재, `NEXT_PUBLIC_` 접두사 오용 | 매 PR 실행    |
| CD  | 값이 실제로 주입됐는지, fallback으로 도는지       | 실행하지 못함 |

CI에서 값의 진짜 여부를 묻지 않는 이유는 CI에 실제 비밀값이 없기 때문이다. 로그에 남아도 되는 검증용 값을 넣고, 진짜 값 확인은 CD로 미뤘다.

### AI 리뷰를 advisory로 둔 이유

재현성 확인은 **v4 프롬프트에 한정해** 했다. 같은 diff에 v4를 그대로 3회 돌렸을 때 지적 집합이 같았고, 표현만 달랐다. 그래서 실행 간 흔들림을 advisory 근거로 삼지 않았다. 다만 이 결과가 v1~v3에도 해당한다고 볼 수는 없다 — **프롬프트를 바꿀 때마다 지적 집합은 통째로 달라졌다**(7절 표). 대신 두 가지가 걸린다.

1. **기준 문구에 결과가 민감하다.** 프롬프트 한 줄을 바꿀 때마다 지적 집합이 통째로 바뀌었다(7절 표). required로 두면 기준 문서를 고치는 순간 통과·실패가 바뀐다.
2. **오탐 반증에 쓴 근거가 전부 diff 밖에 있었다.** lint 대상 범위, 규칙의 목적 주석, 실행 시간 자료 — 리뷰어가 볼 수 없는 자리다.

CI에도 붙이지 않았다. 붙이면 트리거·동시성·토큰 한도를 함께 설계해야 하는데 이번 주 범위를 넘고, advisory 결과를 Actions 화면에 올려도 사람이 읽고 판단하는 절차는 그대로라 로컬 실행 대비 얻는 것이 적다.

## 7. AI 활용 회고 — 무엇을 AI에, 무엇을 기계에 맡겼나

### 유효 지적과 오탐

Codex CLI를 로컬에서 6회 실행했다(프롬프트 v1~v4 각 1회, v4 재현성 확인 2회). 대상은 10주차 작업 diff `faa07cb0..ab7e8f76`(996줄).

**유효 지적** — 스킵 정책에 정책 범위 밖 경로가 남아 있었다. 네 버전 모두에서 나왔다. 다만 그 경로는 무시 대상이라 일반 PR의 변경 목록에 나타나지 않으므로, 즉시 검증 누락을 일으킨 사례는 확인되지 않았다. 경계가 불명확해 제거 대상으로 판단했고 workflow와 문서에서 함께 지웠다.

**오탐 3건** — 셋 다 "규칙을 아느냐"가 아니라 **"규칙이 어디에 적용되느냐"** 에서 났다.

| 오탐                                 | 왜 틀렸나                                                                   |
| ------------------------------------ | --------------------------------------------------------------------------- |
| workflow YAML의 `console.log`가 위반 | lint 대상은 `*.{ts,tsx,js,jsx,mjs}`뿐이고, 규칙 목적은 프로덕션 번들 보호다 |
| timeout 근거가 없다                  | 실측 64·72·73초가 존재했다. "diff에서 근거를 찾지 못함"이 정확한 표현이다   |
| E2E를 required에서 빼라              | 프롬프트가 required 판단을 일반론으로 적어 둔 탓이다                        |

### 프롬프트 개선

오탐을 줄이면 다음 층의 과도한 규칙이 드러나는 식으로 네 번 고쳤다.

| 버전 | 추가한 제한                                                | 새로 드러난 문제                 |
| ---- | ---------------------------------------------------------- | -------------------------------- |
| v1   | 기준 명문화만                                              | 적용 범위 오적용, 근거 부재 단정 |
| v2   | 규칙별 적용 범위 + "diff에 근거 없음 ≠ 근거 없음"          | 합의된 적 없는 네이밍 지적       |
| v3   | 네이밍을 컴포넌트 props로 한정, 목록에 없는 규칙 생성 금지 | required 배치를 일반론으로 반박  |
| v4   | required 판단을 이 프로젝트의 결정으로 명시                | 없음                             |

적용 범위를 적으면 오탐은 줄지만, 넓게 남겨 둔 자리에서 가치가 낮은 지적이 늘었다. 규칙마다 범위를 적는 비용을 치러야 신호가 남는다.

### 10주 전체에 대한 결론

**1주차에 "설명할 수 없는 코드는 커밋하지 않는다"를 기준으로 세웠다. 10주 동안 그 기준을 지키는 방법이 세 번 바뀌었다.**

처음에는 사람이 매번 확인했다. 6주차에 FSD 경계를 `eslint-plugin-boundaries`로 내리면서, 문서에 적힌 규칙 중 참/거짓이 결정적으로 갈리는 것은 기계가 판정하게 됐다. 10주차 5단계에서 같은 일을 문서 규칙 하나에 다시 했다.

경계는 **적용 범위가 파일 경로와 문법으로 정해지는가**에 있다. 이번에 승격한 항목은 검사 대상이 경로 패턴으로 정해지고 판정이 링크 문법으로 끝나서, 사람이 매번 볼 이유가 없어졌다. 반대로 오탐 3건은 모두 규칙의 적용 범위를 묻는 것이었고, 그 답은 규칙의 목적과 저장소의 사정을 함께 봐야 나온다.

| 무엇                                           | 누가 판정        | 위치                |
| ---------------------------------------------- | ---------------- | ------------------- |
| 타입·lint·테스트·빌드·번들 예산·환경 변수 형식 | 기계 (결정적)    | `quality`           |
| 추적 문서의 무시된 경로 참조                   | 기계 (이번 승격) | `quality`           |
| 사용자 흐름 회귀                               | 기계 (결정적)    | `e2e-required`      |
| 규칙의 적용 범위, 설계 냄새                    | AI (비결정적)    | advisory, 로컬 실행 |
| 예산 값, required 배치, 승격 여부              | 사람             | 3·5단계 문서        |

기계가 늘어난다고 사람이 볼 것이 줄어드는 것은 아니다. 사람이 볼 것이 맥락 판단으로 좁혀진다.

### 배포 환경을 먼저 확보한다

이번 주의 가장 큰 공백이다. 배포 URL이 하나라도 있었으면 CD 컷 항목을 실제로 확인할 수 있었다. 순서를 바꿔 배포를 먼저 붙이고 검증을 설계했을 것이다. 확인할 것은 이미 정해져 있다.

### 측정 프로토콜을 처음부터 고정한다

7주차 초반에 도구와 환경이 라운드마다 달라서 값끼리 직접 비교할 수 없게 됐다. 도구·프로필·URL·throttling·포트를 첫 측정 전에 정하고, 정하기 전의 값은 비교 대상으로 쓰지 않는 편이 낫다. 10주차 CI 측정에서는 이 경험을 반영해 cold/warm을 로그로 분류하고 확인되지 않은 실행은 표본에서 뺐다.

### 캐시를 측정 변수로 다룬다

Before/After를 잴 때 캐시 상태를 통제하지 않으면 시간 차이의 원인을 지목할 수 없다. 이번에는 캐시를 지우고 로그로 복원 여부를 확인한 뒤 cold/warm을 나눴고, lockfile을 임시로 바꿔 키 불일치까지 재현했다([실험 run 34504209852](https://github.com/kate-son/loop-pack-fe-l2-vol1/actions/runs/34504209852)). 다만 job 전체 시간의 중앙값 차이가 범위보다 작아 캐시 효과 자체는 단정하지 못했다. 표본을 더 늘렸어야 했다.

### required 설정을 마지막이 아니라 중간에 둔다

게이트를 다 만든 뒤에 required를 붙이려니, 문서마다 "지정하면 막지만 지금은 지정 안 됨"을 반복해 적게 됐다. 임시 보호 브랜치로 동작을 확인하는 방식은 `main`을 건드리지 않아 좋았지만, 확인한 설정을 어디에 영구 배치할지는 처음에 정해 뒀어야 한다.

## 함께 생각해 볼 질문

### 1. E2E를 모든 PR에 required로 걸면 어떤 문제가 생길까?

PR을 올릴 때마다 E2E가 돌면 실행 비용이 계속 늘어난다. 그리고 테스트가 빨간불이 되면 머지가 막히므로 개발 진행에 부담이 된다. 그래서 모든 PR에 거는 대신, 사용자 플로우를 기준으로 E2E 하나를 골라 그 영향도만 보거나, 중요한 로직이 있는 디렉터리가 바뀐 경우에만 실행되도록 CI를 설정하는 편이 낫다고 본다.

### 2. Lighthouse 점수 하락은 항상 merge blocker여야 할까?

운영에 배포되기 전 환경에서 재는 Lighthouse 값은 의미가 크지 않다고 본다. 개발 환경은 운영 환경보다 인프라가 약하게 구성될 수 있어서, 그 값으로 판단하면 오히려 잘못된 결론이 나올 수 있다. 그래서 Lighthouse는 CI·CD 영역과 떼어 놓고 LIVE 영역에서 재는 편이 맞다고 본다.

### 3. Preview 환경이 production API를 바라보면 무슨 일이 생길까?

Preview는 아직 운영에 배포되기 전 환경이다. 이 환경이 production API를 바라보면 운영 쪽에 테스트 데이터가 쌓이고, 데이터로 재는 모든 지표가 오염된다. 이걸 되돌리는 비용도 만만치 않다 — 연관된 릴레이션 테이블을 하나씩 파악해야 한다. 잘못 테스트하면 운영 서버에서 앱 푸시나 문자 발송까지 나갈 수 있으므로, 실제 production 환경이 아니면 production API를 호출해서는 안 된다.

### 4. AI가 만든 workflow를 그대로 머지하면 어떤 리스크가 있을까?

검증을 거치지 않았기 때문에, 초안에 섞인 오류가 드러나지 않은 채 production까지 올라간다고 봐야 한다. 그렇게 올라간 뒤 문제가 생기면 복구 비용이 크다. 그러므로 사람이 결과물을 직접 판단한 뒤에 머지해야 한다.
