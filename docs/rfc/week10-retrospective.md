# 10주 기술 회고

## 1. 프로젝트 요약

1~3주차는 Vite + React 였다. 1주차는 AI 에이전트에게 CLAUDE.md 및 rules를 이용해 지침 주입과 ESLint + Prettier를 이용한 기계적 하네스를, 2주차에 `market/CheckoutPage` 결제 화면의 비대한 컴포넌트를 쪼갰고, 3주차에 `productList/ProductListPage` 상품 목록 화면을 레이어로 갈랐다. 4주차에선 Vite 에서 Next 16 으로 스택을 갈아탔다.

**그 전환 이후 1~3주차에 만진 파일은 하나도 남지 않았다.** 지금 저장소는 Next.js 16 App Router 커머스로, 상품 목록과 필터, 장바구니와 위시리스트, 로그인과 주문을 가지고 있다.

## 2. 10주 동안의 구조 변화 (2~3·6주차 구조 결정)

### 2~3주차: 컴포넌트를 쪼갤 기준이 없었다

시작할 때 내가 컴포넌트를 보며 쓰던 기준은 몇 개 안 됐다. props 가 다섯 개를 넘는지, 파일이 긴지, 계산으로 될 걸 state 로 들고 있는지 정도였다. 2주차에 11개 전략을 하나씩 체크해보면서 조금씩 기준이 잡혀나가기 시작했다. 같은 "props 가 많다"도 인자를 묶을 문제인지 slot 으로 선택할지 갈렸다.

이때 배운 게 하나 더 있다. **고치는 것만큼 안 고치기로 정하는 것도 근거가 필요했다.** `OrderLineRow` 를 더 쪼갤지, 결제 버튼 금액에 `Price` 컴포넌트를 쓸지는 성급한 추상화로 보고 보류했는데, 이 보류도 왜 지금은 아닌지 설명할 수 있어야 했다.

3주차에는 내 코드 리뷰가 놓친 구멍이 발제에서 드러났다. `page=99` 처럼 `totalPages` 보다 큰 값이 들어오면 없는 페이지로 갔고, URL 동기화를 전부 `replaceState` 로 통일해서 뒤로가기가 안 됐다. 둘 다 "URL 동기화"를 한 덩어리로 보고 똑같이 처리한 탓이었다. 필터 변경과 페이지 이동은 되짚을 수 있어야 하는지가 다르다.

### 6주차: FSD 로 옮기며 경계 기준을 다시 배웠다

폴더를 옮기는 일 자체보다 **무엇을 한 슬라이스로 볼 것인가**가 어려웠다. 카테고리 셀렉트와 정렬 셀렉트를 나눌 때 나는 "엄밀히 따지면 다른 기능"을 근거로 댔는데, 리뷰에서 그건 분류의 논거라 반증이 어렵다는 지적을 받았다.

경계의 진짜 기준은 **서로 다른 이유로 바뀌는가**였다. `sort-select` 가 바뀔 때 `_pages/products` 를 안 건드릴 수 있는지로 검증할 수 있는 논거를 댔어야 했다. 이건 FSD 만의 얘기가 아니라 2주차에 이미 나왔던 응집도 기준인데, 그때 배운 걸 6주차에 못 끌어왔다.

응집은 삭제 시나리오로 쟀다. 위시리스트를 통째로 지우면 `entities/wishlist` 와 `features/toggle-wishlist` 두 폴더를 지우면 되고, 결합된 소비처 네 곳이 전부 public API 로만 import 돼 있어 그 경로만 grep 하면 잡혔다. 흩어져서 grep 없이 못 찾으면 응집 실패라는 기준이 명확했다.

그리고 마이그레이션을 8단계로 쪼갠 게 나중에 값을 했다. RFC 원안은 목록 조회 조건 로직을 `_pages/products` 에 두려 했는데, 3단계에서 상품 queryOptions 를 `entities/product` 로 내리고 나니 entity 가 상위 레이어를 import 하게 됐다. 이 충돌은 계획을 세울 때가 아니라 **3단계를 실제로 지나고 나서** 보였다. 한 번에 다 옮겼으면 여러 충돌이 뒤엉킨 채로 마주쳤을 것이다.

## 3. 주요 기술 결정과 근거

### 상태를 나누기 전에 원본이 어디인지 먼저 물었다 (5주차)

5주차 질문은 "어떤 상태 라이브러리를 쓸까"가 아니었다. **"이 상태의 원본은 어디에 있나"** 였다.

화면에 필요한 상태를 `상태 · 소유자 · 수명 · 공유 범위 · 선택 이유` 로 먼저 표에 적고 나서 도구를 골랐다. 질문을 이렇게 바꾸니 서버 원본을 Zustand 에 복사하거나 URL 이 원본이어야 할 조건을 컴포넌트 state 에 가두는 선택이 애초에 후보에서 빠졌다.

- 서버가 원본인 목록은 TanStack Query. `queryOptions` 팩토리로 key·queryFn·캐시 정책을 한곳에 묶어 클라이언트 `useQuery` 와 서버 `prefetchQuery` 가 같은 정의를 썼다
- 공유·새로고침·앞뒤 이동으로 복원돼야 하는 조건(`q`·`category`·`sort`·`page`)은 원본이 URL 이라 nuqs
- 서버 원본이 없는 익명 장바구니는 클라이언트가 원본이라 Zustand 에 id `Set` 만 저장하고, 헤더 개수는 저장하지 않고 `.size` 로 파생

**도구는 원본을 정한 뒤에 따라왔다.** 10주차에 AI 리뷰 기준을 짜면서 이 규칙이 어느 문서에도 문장으로 없다는 걸 알았다. 지키고는 있었는데 적혀 있지 않았다.

### 성능은 고칠 때마다 대가가 붙었다 (7주차)

hero 이미지 하나가 LCP 의 93%, 7,904ms 를 먹고 있었다. `next/image` 로 7.5MB 를 130kB 로 줄였다.

그런데 **공짜로 좋아지는 변경은 거의 없었다.** hero 전송을 줄이는 대가로 document 가 0.8KB 늘고 render delay 가 13ms 붙었다.

동적 metadata 가 같은 `page=1` 을 한 번 더 부르는 문제도 그랬다. 줄일 방안을 둘 검토했고 둘 다 안 썼다.

- **Data Cache 를 붙인다.** 서버 호출 하나는 줄지만 신선도 지연과 캐시 누수를 담보로 잡는다
- **metadata 의 동적 생성을 없앤다.** 중복 호출이 근본적으로 사라지는 대신 og:image 를 통째로 포기해야 한다

둘 다 얻는 것보다 내주는 게 크다고 판단했다.

가장 예상 못 한 건 동적 metadata 였다. title·og 를 데이터로 채우겠다는 결정 하나가 metadata 를 느리게 만들고, 느린 metadata 는 스트리밍을 부르고, 스트리밍은 렌더 패스를 쪼개서 같은 `page=1` 을 한 번 더 부르고, 태그가 붙는 위치와 첫 바이트 타이밍이 User Agent 에 따라 갈렸다. **기능 하나 붙인 줄 알았는데 서버 호출 수와 크롤러 응답 시점까지 같이 움직였다.**

## 4. 테스트와 품질 게이트

### 8주차: 무엇을 지킬지 먼저 적고 그것만 테스트했다

과제가 준 전제가 이거였다. 프론트엔드는 지켜야 할 스펙이 어디에도 적혀 있지 않으니, 무엇을 어떻게 검증할지 먼저 정하고 그것만 테스트로 쓰라는 것이었다.

해보니 부수 효과가 있었다. **AI 에게 만들어 달라고 하기 전에 스스로 한 번 생각하게 된다.** 바로 시켰으면 그럴듯한 테스트가 나왔을 텐데, 그게 무엇을 지키는 테스트인지는 내가 설명하지 못했을 것이다.

뮤테이션 테스트로 일부러 망가뜨려 검증했더니, 살아남은 변형이 **코드가 죽었다는 신호일 수도 테스트가 비었다는 신호일 수도** 있다는 걸 알게 됐다. 점수 100%를 목적으로 삼으면 오히려 구현 세부 테스트를 쓰게 된다.

그래서 Stryker 를 상시로 쓰지 않기로 했다. 16초짜리가 대상이 늘면 금방 몇 분대가 되고, 검출 8건 중 안 고친 것도 있어서 어디까지 허용할지 기준이 애매했다. 그때 이렇게 적었다.

> 만약 붙인다면 CI 에서 자동 실행해 PR 코멘트로 띄우되 머지는 막지 않는 참고용 리포트로 두는 정도가 맞겠다 싶었다.

### 9주차: E2E 가 흔들리지 않게 만든 것들

발제를 통해 Playwright 에 `storageState` 라는 게 있다는 걸 알았다. 로그인 한 번 해서 그 결과를 파일로 저장해두고 다음부터 그 파일을 물고 시작하는 기능이다. 반복되는 로그인이 통째로 사라지니 바로 써보려고 했다.

그런데 저장한 파일을 **실행 간에도 재사용**하려니 걸리는 게 있었다. 세션 TTL 이 1시간이다. 그 시간이 지난 파일을 물고 시작하면 만료된 쿠키로 authed 스펙이 돈다. **코드는 한 줄도 안 바꿨는데 어제는 초록이고 오늘은 빨강이 되는 것이다.**

그래서 기능은 쓰되 재사용 범위를 좁혔다. `storageState` 자체는 그대로 두고 **실행 때마다 새로 로그인해서 파일을 다시 만든다.** 워커당 한 번이면 되는 건 fixture 를 워커 스코프로 둬서 이미 보장되니, 아끼려던 것의 대부분은 그대로 남는다. 실행 간 재사용 하나만 내주고 신선도를 샀다.

### 아직 고치지 못한 9주차 리뷰를 통해 알게 된 결함

**하나. E2E 가 확인한다고 적어둔 것에 단언이 없었다.** RFC 에 쿠키 속성과 초기 HTML 과 만료 안내를 E2E 가 본다고 적었는데 셋 다 단언이 없다. 초기 HTML 은 더 나쁘다. 테스트가 보는 이메일이 서버가 심는 값이 아니라 클라이언트가 `/me` 응답을 기다려 받는 값이라, 초기 HTML 을 확인하는 테스트가 아니었다. 인증 검증 셋을 한 테스트에 묶은 걸 두고 "묶었다"고 설명했는데 실상은 **"빠졌다"** 에 가까웠다.


**둘. 계측은 들어갔는데 테스트가 하나도 지켜주지 않았다.** 이벤트 이름을 바꿔도 지워도 `identify` 와 `reset` 을 지워도 vitest가 통과한다. 로거 테스트가 테스트 안에서 만든 문자열을 되받는 구조라 실제 호출부를 한 번도 import 하지 않는다. RFC 의 이벤트 매핑 표가 유일한 계약인데 **문서라서 실행이 안 되고, 이미 코드와 어긋나 있었다.** 

**셋. 퍼널 정의가 앱의 현재 구현에 기대고 있었다.** 로그인이 담기 뒤에 온다는 순서를 퍼널에 넣었는데, 그건 데이터의 성질이 아니라 이 앱이 담기 시점에만 로그인을 요구하도록 만들어졌기 때문에 나온 결과다. 진입점을 하나만 추가해도 퍼널을 통째로 다시 짜야 한다. 당장 할 일은 집계를 다시 도는 게 아니라 **"이 퍼널은 담기 시점 로그인 강제를 전제한다"를 한 줄 적어두는 것**이었다. 그 한 줄이 있어야 나중에 진입점이 늘었을 때 퍼널부터 의심하게 된다.

#### 공통적인 문제점

**문서에 적은 것이 실행되지 않으면 계약이 아니다.** E2E 가 본다고 적었지만 단언이 없었고, 이벤트 매핑 표는 코드와 갈라져 있었고, 퍼널의 전제는 적히지도 않았다. 셋 다 "문서에는 있는데 아무것도 그걸 강제하지 않는" 상태였다.

### 10주차: 검증을 기계에 새기기

이번 주에 머지를 막는 검사를 셋 더했다. 번들 예산, 환경 변수, pnpm 버전 단일 출처다. 그런데 만들면서 오래 붙잡고 있던 건 무엇을 더 막을지가 아니라 **이걸 required 로 걸어도 되는가** 였다.

기준은 8주차에서 가져왔다. 그때 뮤테이션 점수를 게이트로 안 건 이유가 "통과시키려고 구현 세부 테스트를 쓰게 된다"였는데, 뒤집어 보면 **같은 코드에 같은 답이 안 나오는 검사는 게이트가 못 된다**는 얘기였다. 번들 예산이 이 기준을 통과할지 확신이 없어서 같은 커밋을 세 번 빌드해봤다. 271,424 바이트가 세 번 다 똑같이 나왔다. 변동이 0이라 초과가 뜨면 그건 코드가 늘어난 것이지 측정이 흔들린 게 아니다. 그제야 required 로 걸었다.

AI 컨벤션 리뷰 하나만 required 에서 뺐다. 같은 diff 에 다시 돌려도 지적이 달라지니 같은 기준에 걸린다.

## 5. 성능 개선 결과 (7주차 측정값)

### 고치기 전에 측정 조건을 고정했다

LCP 가 8.5초였고, 과제의 7.5MB 짜리 hero 이미지가 원인이었다. 우선은 모바일 프리셋, CPU 4배 감속, Fast 4G, 5회 측정에 raw 와 중앙값·최소·최대까지 하여 기준을 미리 정했다.

**조건이 하나라도 달라지면 숫자가 바뀐 이유가 내 변경 때문인지 조건 때문인지 가릴 수 없다.** 그러면 개선했다고 말할 근거가 없어진다. 이는 10주차도 마찬가지였다.

### 고친 것과 그 대가

`next/image` 로 hero 를 7.5MB 에서 130kB 로 줄였다. 이미지 전송이 7,904ms 에서 270ms 가 됐다. 대신 document 가 0.8KB 늘고 render delay 가 13ms 붙었다. preload `<link>` 와 `srcset` 이 초기 HTML 에 들어가서다. 7.7초를 벌면서 그만큼 내주는 거라 유지했다.

INP 는 selector 한 줄이었다. 카드마다 `wishlistIds` 배열 전체를 구독해서 찜 하나 누를 때 카드 24개가 전부 리렌더됐다. 자기 id 의 boolean 만 구독하게 바꾸니 processing duration 이 96ms 에서 12ms 가 됐다.

### 적용했다고 적용된 게 아니었다

After 를 다시 재는데 Lighthouse 가 LCP 이미지에 `fetchpriority="high"` 가 없다고 했다. `next/image` 의 `priority` 를 분명 줬는데도. Next 16 부터 `priority` 가 deprecated 되면서 하는 일이 쪼개졌고, `fetchpriority` 는 더 이상 안 붙는다. 나눠서 명시하니 LCP 가 1.0초에서 0.8초로 한 번 더 내려갔다.

### 그런데 JS 는 한 번도 안 쟀다

측정 할 때는 각각 다른 도구를 사용했다. LCP 는 Lighthouse 와 Performance 패널, 전송 크기는 Network waterfall, INP 는 Interactions track 과 React Profiler, 서버 호출 수는 Route Handler 로그, 크롤러 지연은 `curl -w` 였다.

그러고도 document 와 이미지만 봤다. 그게 이 주차의 진짜 구멍인데 3주 뒤에야 알았다. 그 얘기는 8절에 적었다.

## 6. CI/CD 와 AI 협업

### AI 리뷰는 기준을 저장소 안에 두고 경로로 참조했다

리뷰 기준을 `.claude/skills/convention-review/SKILL.md` 에 두고, 워크플로는 `/convention-review` 로 부르기만 한다. 규칙 본문은 복사하지 않고 `CLAUDE.md` 와 `.claude/rules/` 를 경로로 참조하게 했다. 242줄을 프롬프트에 복사해 두면 규칙 문서를 고쳐도 프롬프트가 옛 기준을 계속 말한다.

설계의 핵심은 **근거 규칙 인용 강제**였다. 지적마다 문서의 실제 문장을 인용하게 하면, 규칙에 없는 지적이 그 자리에서 드러난다. 인용할 문장을 못 찾는 지적은 근거가 없다는 뜻이다.

첫 실행 결과는 5건이었다([run 34420348395](https://github.com/read0more/loop-pack-fe-l2-vol1/actions/runs/34420348395)). 4건은 사실 확인까지 마쳤고 1건은 애매하다고 판단한 부분이었다.

### 애매하다고 판단한 부분

AI 는 `getBaseUrl.ts` 에서 지운 주석이 "왜"를 설명하던 문장이라고 지적했다.

```diff
- // env 없이도 바로 과제 확인 가능하게 로컬 기본값을 둔다.
  export const SITE_URL = process.env.APP_ORIGIN ?? "http://localhost:3000";
```

주석은 "로컬 기본값을 둔다"고 말하는데 코드가 `?? "http://localhost:3000"` 이라고 이미 그대로 말한다. 잃은 정보가 없다고 판단했다.

굳이 따지자면 과제 확인 가능하게 부분인데 이 부분도 필요 없다고 생각했다.

> 기준: 주석을 지웠을 때 잃는 정보가 있으면 남기고, 코드만 봐도 아는 내용이면 지운다.

프롬프트를 두 군데 고쳤다. 주석 삭제를 지적하려면 그 정보가 코드에 없음을 먼저 보이게 했고, 인용한 규칙에 판정 기준이 딸려 있으면 대입 결과를 판정에 적게 했다.

### CI 를 붙이며 뒤집은 판단

처음엔 "결제 때문에 CI 에 안 붙인다"고 정했는데 사실이 아니었다. `claude setup-token` 으로 구독 토큰을 만들 수 있어서 종량제 결제가 붙지 않는다는 걸 알았기 때문에 판단을 뒤집었다.

## 7. AI 활용 회고 — 무엇을 AI에, 무엇을 기계에 맡겼나

| | 맡긴 것 | 왜 |
| --- | --- | --- |
| 🤖 기계 | lint·type·test·build, 번들 예산, 환경 변수, pnpm 버전 단일 출처 | 판정에 코드의 의미가 필요 없다 |
| 🤝 AI | 컨벤션 위반 중 읽어야 보이는 것. advisory, 라벨로 부를 때만 | 규칙을 코드에 대입하려면 의미를 읽어야 한다 |
| 🔍 사람 | 기준과 임계값을 정하는 일 | 도구는 재기만 한다. 무엇을 기준으로 삼을지는 안 정해준다 |

### 기계에 맡긴 예 — pnpm 버전 단일 출처

`packageManager` 가 이미 단일 출처인데 워크플로가 같은 값을 세 job 에 다시 적고 있었다. `version:` 문자열이 있느냐 없느냐로 끝나는 판정이라 사람이 직접 볼 이유가 없다.

### AI 에 남긴 예 — `find*` 이름과 반환값 불일치

`findMissingKeys` 가 키가 아니라 실패 메시지 배열을 돌려준다는 지적이다. 발제의 

> "설계 냄새"처럼 맥락 판단이 필요한 건 AI·사람에 남는 게 맞아요

이 부분에 해당 하는 부분이라고 판단했기 때문에 AI에 맡겼다.

### 사람이 정한 예 — 번들 예산을 시간으로 세운 것

처음 AI가 잡은 안은 "현재 값 271kB 에 여유 20kB 를 더해 285kB" 였다. 단순히 용량으로 기준을 잡기 보다에는 이유가 약하다고 생각했다.

그래서 질문을 바꿨다. "몇 바이트까지 봐줄까"가 아니라 **"느린 회선에서 몇 초 안에는 떠야 하나"** 로 생각하여 Slow 4G 에서 1.5초로 가정했다.

처음엔 1.25초로 잡으려 했다. 그런데 현재 값이 이미 1.36초라 그 예산은 세우는 순간 실패한다. 게이트를 세우자마자 못 지키는 기준은 기준이 아니라서 조금 더 여유를 주어 1.5초로 했다. 남는 여유가 28.1kB 인데, 이건 "20kB 짜리 의존성 하나는 통과하고 둘은 막힌다"로 읽힌다.

300kB 는 그 1.5초를 바이트로 환산한 값일 뿐이다. 환산에 쓴 회선은 Lighthouse·DevTools 의 Slow 4G 프리셋 1.6 Mbps 인데, **실제 사용자 회선을 잰 게 아니라 가정한 값이다.** 그래서 예산도 전송 시간도 전부 이 가정 위의 산술이고 RTT·핸드셰이크·파싱·실행이 빠져 있다. 실제 체감은 이보다 길다. CI 리포트에도 이 사실을 그대로 적어두었다.

## 8. 다시 만든다면

### 안 잰 항목이 있는지 먼저 확인한다

7주차에 이미지 전송은 쟀는데 JS 전송은 한 번도 안 쟀다. 그래서 이미지를 130kB 로 줄이는 동안 JS 가 이미 더 오래 걸리고 있다는 걸 몰랐다. 

다음엔 손대기 전에 같이 느려질 수 있는 항목을 재볼 것 같다. 최적화하려는 게 아니라 기준선만 남기는 거라 비용이 크지 않다.

### 지키고 있는 규칙을 문장으로 적어둔다

10주차에 AI 리뷰 기준을 짜면서 "10주간 합의한 규칙" 중 셋이 어느 문서에도 없다는 걸 알았다. URL 상태 동기화, custom hook 분리 기준, 서버 응답을 로컬 상태에 복사하지 않기다.

6주차에 받은 피드백과 같은 결이라 생각한다. **규칙의 예외는 규칙 본문에 적어야 한다.** 계약 테스트가 위젯 내부를 직접 import 하는 예외를 `steiger.config.ts` 주석에만 적어둬서, 문서만 읽는 사람은 그걸 위반으로 읽게 됐다.

### 대안을 고르기 전에 명세부터 정확히 읽는다

5주차에 홈 데이터를 Server Component 에서 직접 fetch 하도록 짰다. 인터랙션이 없는 화면이니 클라이언트 구독을 걷어내는 게 낫겠다고 봤다. 그런데 그 주차 필수 요구사항이 "홈·목록 **각각** queryOptions 팩토리를 만들어 재사용"이었고, 나는 그러면서 홈 팩토리를 아예 지워버렸다.

대안 자체는 나쁘지 않았는데 **증명해야 할 것을 증명하지 못한 결과물**이 됐다. 실무였어도 같다. 명세를 잘못 읽고 결과물이 명세와 달라지면 그 어긋남 자체가 문제다. 더 나은 방법이 보이면 혼자 바꾸는 게 아니라 먼저 공유하고 합의하는 순서였어야 했다.
