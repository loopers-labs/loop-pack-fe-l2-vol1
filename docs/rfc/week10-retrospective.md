# 10주 기술 회고

## 1. 프로젝트 요약

Next.js(App Router) 기반 커머스 앱. 10주간 인증, 상품 목록/필터, 장바구니, 주문서, 이벤트 계측, 성능 최적화, 테스트, CI를 순서대로 쌓았다. 기술 스택은 `CLAUDE.md`에 고정: TypeScript, TanStack Query, nuqs, Zustand, Vitest, Playwright, pnpm.

## 2. 10주 동안의 구조 변화

- **2~3주차**: 컴포넌트를 "역할이 두 개 이상이면 분리한다" 기준으로 책임 분리 시작 — early return, 단일 책임, 커스텀 훅 분리가 이때부터 컨벤션(`CLAUDE.md`)으로 굳었다.
- **6주차(FSD 마이그레이션, `docs/rfc/week06-fsd.md`)**: 폴더 구조를 `app > _pages > widgets > features > entities > shared`로 재편. 핵심은 "변경 반경을 예측 가능하게 만드는 것" — 삭제 시나리오 자가 검증(위시리스트 제거, 신상품 뱃지 추가, 장바구니 서버 전환)으로 실제로 폴더 단위로 영향 범위가 끝나는지 확인했다. `eslint-plugin-boundaries`로 레이어 역방향 import를 lint error로 강제했고, 이 설정이 10주차까지 그대로 이어져 5단계 룰 승격의 기반이 됐다.

## 3. 주요 기술 결정 2~3개와 근거

1. **상태 3분할** (`docs/decisions/week-05.md`): 서버 데이터는 TanStack Query, URL에 반영돼야 하는 값은 nuqs, 그 외 클라이언트 전역 상태만 Zustand. 계산 가능한 값은 `useState`에 안 담고 `const`로 파생시킨다는 원칙을 이때 세웠고, 이후 모든 주차의 코드 리뷰 기준이 됐다.
2. **9주차 E2E 범위 설계** (`docs/rfc/week09-e2e-scope.md`): 로그(빈도·실패비용)를 근거로, 빈도는 낮아도 실패 비용이 큰 인증 플로우는 넣고, 빈도가 높아도 실패 이벤트 자체가 로그에 안 남는(서버 요청 없는 로컬 상태 변경) 장바구니 담기는 뺐다. "자주 쓰이는 것"과 "실패하면 크게 아픈 것"은 다른 축이라는 게 이번 학기 전체를 관통하는 판단 기준이 됐다(10주차 2단계 조건부 실행 설계에도 그대로 재사용).
3. **10주차 CI 빌드 중복 제거** (`docs/rfc/week10-ci.md` A~E절): `next build`가 CI 1회 실행당 2번(quality check 안, E2E webServer 안) 돌고 있던 걸 측정으로 찾아내 하나로 줄였다. cold/warm 3+3회 Before/After로 E2E step이 25s→15s대로 줄어든 걸 확인 — "느낌"이 아니라 숫자로 병목을 지목하고 검증한 사례.

## 4. 테스트와 품질 게이트 (8·9·10주차)

- 8주차(`docs/rfc/week08-test-plan.md`)에서 단위/통합/E2E 분류 기준을 세우고, mutation 방식 자가 검증("실패 메시지로 원인을 짐작할 수 있었나")으로 테스트가 진짜 뭘 잡는지 확인했다.
- 9주차에서 인증·E2E 범위를 위 기준으로 좁혔고, 5단계 자가 검증 중 계획에 없던 실제 버그(Next.js 클라이언트 라우터 캐시 문제)를 E2E가 잡아낸 사례가 나왔다.
- 10주차에서 이 모든 검증을 CI 게이트로 승격: lint/typecheck/test/build는 항상, E2E는 조건부(2단계), 번들 예산·env 검증은 build 게이트(3단계), 반복 지적(이유 없는 eslint-disable)은 결정적 룰(5단계)로.

## 5. 성능 개선 결과 (7주차 측정값)

Hero 이미지가 LCP를 지배하는 병목이었다(`docs/decisions/week-07.md`). Lighthouse 시뮬레이션 기준 LCP 6813ms(중앙값) → `next/image` 적용(WebP 자동 변환, 7.5MB→400KB) 후 772~815ms로 **약 88% 개선**, 측정 범위가 전혀 겹치지 않을 정도로 명확한 변화였다. 이 측정값은 10주차 3단계 Lighthouse 임계값 근거로 재사용할 수 있는 자산이 됐다(이번 주엔 Lighthouse CI는 선택 항목이라 실제 게이트로는 안 걸었지만, 번들 예산은 오늘 직접 잰 값 251.9KB+20%로 300KB를 설정 — 7주차엔 이미지가 병목이라 JS 번들 수치를 안 남겼던 공백을 이번 주에 메웠다).

## 6. CI/CD와 AI 협업 (10주차)

1단계 CI 측정·최적화, 2단계 조건부 실행, 3단계 예산 게이트, 4단계 AI 리뷰, 5단계 룰 승격까지 전부 이번 주에 새로 만들었다(`docs/rfc/week10-ci.md`). 특히 2·4단계에서 **AI가 만든(또는 공식 문서대로 따라 만든) workflow가 처음부터 제대로 작동한 적이 없었다** — `dorny/paths-filter`가 PR 전체 diff를 보는 문제(2번 실패 후 수정), `claude-code-action`이 OIDC 권한 누락 → GitHub App 미설치 → Bash 비활성화 → max-turns 부족(2회) 순으로 총 6번 실패했다. 마지막엔 근본 원인(액션에 리뷰 범위를 좁히는 공식 옵션이 없음)을 못 찾은 채 CI 연동을 중단하고 로컬 리뷰로 전환했다.

## 7. AI 활용 회고 — 무엇을 AI에, 무엇을 기계에 맡겼나

- **기계(결정적 게이트)로 내린 것**: lint/typecheck/test/build, 번들 예산, env 검증, FSD 레이어 경계, 이유 없는 eslint-disable — 전부 참/거짓을 확실히 가를 수 있는 것들이다.
- **AI(비결정, advisory)로 남긴 것**: PR diff 코드 리뷰. required로 걸지 않은 이유는 이번 주에 직접 겪었다 — 같은 workflow도 실행마다 걸리는 시간이 달랐고(14턴/7분 vs max-turns 초과로 실패), "왜 안 되는지"조차 한 번에 특정하기 어려웠다. 비결정적인 걸 required 게이트로 걸면 안 된다는 과제의 원칙을 몸으로 확인한 셈이다.
- **사람(나)에게 남은 것**: 무엇을 required로 할지, 임계값을 얼마로 할지, 비싼 검증을 언제 돌릴지, AI 리뷰를 어디까지 밀어붙이고 언제 포기할지(4단계에서 6번 실패 후 로컬로 전환한 것 자체가 이 판단이다) — 이건 끝까지 AI가 대신 못 했다.

이게 10주 전체의 결론과 이어진다: 1주차의 "AI가 그럴듯하게 틀린 코드를 낸다"는 원칙이, 10주차엔 "AI가 그럴듯하게 틀린 workflow도 낸다"로 확장됐다. 공식 문서를 그대로 따라도 실제로 돌려보기 전까진 못 믿는다는 게 10주 동안 변하지 않은 교훈이었다.

## 8. 다시 만든다면

- FSD 마이그레이션(6주차)과 CI 설계(10주차)를 더 일찍 병행했으면, `eslint-plugin-boundaries`처럼 반복되는 리뷰 지적을 기계로 내리는 작업을 매주 조금씩 쌓을 수 있었을 것 — 10주차에 한 번에 몰아서 하지 않아도 됐을 것 같다.
- CI에 AI 리뷰를 붙일 때, `claude-code-action`을 실제로 몇 번 돌려보기 전에 로컬에서 최소 재현(`prompt`만 바꿔가며 소규모 diff로 먼저 검증)했다면 6번 실패 사이클을 줄일 수 있었을 것.
- 주차별 브랜치가 이어지는 구조(PR base가 항상 뒤처짐) 자체가 2·4단계에서 반복적으로 문제의 원인이 됐다 — 매주 PR을 머지해서 base를 최신으로 유지했다면 애초에 안 겪었을 문제들이다.
