# 10주 기술 회고

기능 목록이 아니라 기술 결정과 그 근거를 적는다. 수치·커밋·run은 각 주차 RFC·README·[10주차 CI 문서](week10-ci.md)에 있는 것만 인용한다.

## 1. 프로젝트 요약

Next.js 16(App Router) 위의 커머스 앱이다. 홈·상품 목록·장바구니·주문서·주문 내역·로그인이 있고, 백엔드는 Route Handler로 만든 mock이다. 서버 데이터는 TanStack Query, 검색·필터·정렬·페이지는 nuqs(URL), 익명 장바구니·위시리스트는 Zustand(persist), 인증은 서명 쿠키와 `proxy`다. 구조는 FSD(`app → _pages → widgets → features → entities → shared`)이고 의존 방향은 `eslint-plugin-boundaries`가 강제한다. 검증은 유닛·통합 283개(vitest, MSW), E2E 29개(Playwright, production build 위), CI는 GitHub Actions 하나에 quality·changes·e2e 세 job이다.

## 2. 10주 동안의 구조 변화

- **2~3주차 — 한 파일에서 층으로.** 500줄 `ProductListPage`를 Components / Hooks / Services / Utils로 나눴다. 나눈 기준은 "상태가 어디 사는가"였고, 나누지 않은 것도 근거를 남겼다. 파생 값을 상태로 들고 있던 버그(VIP 할인 미반영)가 이때 잡혔다.
- **4주차 — 패턴을 직접 구현.** Select는 headless(`useSelect` + prop-getter), Dialog는 compound + controlled/uncontrolled 이중 API. 이 두 패턴이 뒤의 컨벤션(`onXxxChange` 하나, `data-*`로만 상태 노출)이 됐다.
- **5주차 — 상태를 소유자별로.** 도구를 먼저 고르지 않고 source of truth를 먼저 찾았다. 서버 데이터·URL·익명 상태·입력 초안이 각각 다른 저장소로 갔다.
- **6주차 — FSD와 하네스.** 슬라이스를 재정렬하고 `types/commerce.ts` God-file을 소유자별로 나눴다. 역방향·cross-slice import를 사람 눈이 아니라 `boundaries`로 막았고, 위반 probe로 실제로 잡히는지 확인했다.
- **7~9주차 — 구조는 유지, 경계에서만 손봄.** 성능은 가장 긴 구간(이미지 전송) 하나만, 테스트는 층 배치 기준 세 개로, 인증은 proxy·queryClient 두 지점으로. 구조 재설계 없이 갔다.
- **10주차 — 규칙을 CI로.** 사람이 지키던 규칙(절대경로 import)을 ESLint로, 설정 사고를 env 게이트로, 번들 성장을 예산으로 내렸다. 코드 구조는 바뀌지 않았고 검증 구조가 바뀌었다.

## 3. 주요 기술 결정 세 개와 근거

### 3.1 저장소는 도구가 아니라 "누가 정하느냐"로 고른다 (5주차)

같은 값이라도 정하는 주체가 바뀌면 소유자가 바뀐다는 기준이다. 검색 조건은 사용자가 정하고 새로고침·공유·뒤로가기에서 복원돼야 해서 URL로, 장바구니는 여러 페이지가 함께 쓰는 익명 상태라 Zustand로, 서버 응답은 TanStack Query 캐시에서만 읽고 store엔 id만 둔다. 이 결정의 대가는 6주차 서버 prefetch에서 나왔다. 서버가 `searchParams`를 읽어야 해서 동적 라우트가 됐고, `useSearchParams` Suspense를 걷어냈다. 근거 기록은 [6주차 RFC](week06-fsd.md)에 있다.

### 3.2 첫 로딩 실패만 경계로, 배경 재조회 실패는 목록 유지 (6·7주차)

`throwOnError`를 data 우선으로 뒀다. 5xx라도 화면에 데이터가 있으면 경계로 던지지 않고 인라인 배너로 알린다. 7주차 재측정에서 홈은 `prefetchQuery` + 클라 `useQuery`라 5xx가 기본 3회 재시도 뒤에야 드러나 스켈레톤이 오래 떠 있었다(HAR `/api/home` 3회). HTTP·business 오류는 재시도하지 않고 네트워크만 1회로 바꿔 에러가 즉시 뜨게 했다(재측정 `/api/home` 1회, 응답 0.5s). 이 결정은 8주차 통합 테스트(5xx는 경계, 4xx·network는 인라인)로 고정됐다.

### 3.3 E2E는 빈도가 아니라 실패 비용으로 붙인다 (9주차)

30일 시드 로그(8,000세션)를 집계하면 목록(100%)·담기(17.4%)가 상위이고 인증은 3.7~8.6%다. 그런데도 E2E는 인증에 붙였다. proxy·쿠키·SSR 로그인 상태의 얽힘은 통합 테스트가 못 잡고, 로그인이 막히면 그 뒤 보호 경로가 전부 막힌다. 자가검증에서 proxy `matcher` 파손은 E2E만 잡았다(유닛은 함수만 부르고 "어느 경로에 거나"를 건너뛴다). 반대로 목록·담기는 통합이 이미 덮어 순수 신규 가치가 0이라 붙이지 않았다. 근거는 [9주차 RFC](week09-e2e-scope.md) B·C·D절이다.

## 4. 테스트와 품질 게이트

- **8주차 — 층을 기준으로 나눴다.** 함수 호출만으로 확인되면 단위, 렌더·네트워크가 필요하면 통합, 실제 브라우저 동작이 있어야 하면 E2E. 라이브러리가 책임지는 부분은 다시 확인하지 않았다. `fetch`를 바꿔치기하던 테스트를 MSW로 옮겨 정의 안 된 요청이 바로 실패하게 했고, node·jsdom을 나눠 환경 준비를 약 2.8배 줄였다. Stryker 전수 변형으로 손 실험이 놓친 자리(에러 종류 가드·찜 토글 대상·파서 기본값)를 찾았고 점수 바닥값은 87.83%다.
- **9주차 — 초록 아래를 다시 팠다.** 인증 세 곳을 일부러 부숴 E2E가 잡는지 봤고 셋 다 잡혔다. 그 결론이 "고른 세 건에 한해" 참이었다는 걸 리뷰 뒤 더 넓게 부수며 알았다. 실제 만료 쿠키 통과, 프리페치된 307이 복원을 가로채는 것, `..//` 오픈 리다이렉트, 로그아웃 뒤 사용자 간 캐시 노출 등 12건을 재현(빨강) → 고침(초록) 짝으로 닫았다. 유닛 236 → 263, E2E 25 → 29.
- **10주차 — 게이트를 required로.** fork의 통합 브랜치 `kjeunn`에 `quality`·`e2e`를 required로 걸었다. quality는 env → lint → typecheck → test → dupcheck → build → 번들 예산 순이고, e2e는 런타임에 안 실리는 경로만 바뀐 PR에서 스킵된다. 빨간불 실험 PR 세 개(번들 초과·상대 import·잘못된 env)가 각각 의도한 step에서 멈췄고 revert 뒤 초록으로 돌아왔다. 상세는 [CI 문서 3·5절](week10-ci.md#3-예산-게이트)이다.

## 7. AI 활용 회고 — 무엇을 AI에, 무엇을 기계에 맡겼나

1주차 책임 모델을 이 프로젝트 기준으로 다시 쓰면 이렇다.

| 몫       | 이 프로젝트에서 실제로 맡은 것                                                                                |
| -------- | ------------------------------------------------------------------------------------------------------------- |
| 기계(CI) | import 경로, FSD 의존 방향, deprecated prop, env 값의 형태와 관계, 번들 바이트, 유닛·통합·E2E                 |
| AI 리뷰  | 단일 책임·네이밍·성급한 추상화·상태 소유권 같은 맥락 판단, 그리고 실패 경로에서 게이트가 조용히 통과하는 결함 |
| 사람     | AI 지적의 옥석, required 범위, 예산 폭, 무엇을 룰로 내릴지                                                    |

10주 동안 AI를 쓰면서 반복된 건 두 가지다.

**AI 초안은 초록으로 돈다.** 10주차 워크플로 초안엔 선행 job이 실패하면 E2E가 조용히 스킵되는 조건, 매니페스트 형식이 바뀌면 예산이 항상 통과하는 정규식, summary에만 쓰고 로그엔 원인을 남기지 않는 step이 있었다. 셋 다 CI는 초록이었다. 9주차도 같았다. 초록이었던 코드에서 결함 12건이 나왔다. 초록은 "확인한 것들은 통과했다"이지 "안전하다"가 아니다.

**설정 사고는 형태 검사로 안 잡힌다.** 첫 production 배포에서 대시보드의 실제 도메인을 확인하지 않고 `APP_ORIGIN`을 넣었고, 그 값은 형태는 완벽한 남의 주소였다. `og:url`이 남의 사이트를 가리켰고, 코드상 서버 self-fetch도 그쪽으로 갔다. 규칙 ①·②는 "origin처럼 생겼나, 둘이 같나"만 봤다. "내 것인가"를 보는 ⑥은 사고 뒤에 나왔다. 규칙은 사고 시나리오에서 역산해야 한다는 3단계의 원칙을 사고로 다시 배웠다.

**억제하면 신호도 사라진다.** 4단계에서 컨벤션 규칙 ID와 억제 규칙을 넣은 프롬프트는 노이즈를 15 → 6건으로 줄였지만, 규칙 밖 결함 5건(실패 경로 3·낡은 주석 2)을 아예 내지 않았다. 앵커가 없는 리뷰가 그걸 찾았다. AI 리뷰의 몫을 "맥락 판단"으로만 정의하면 실패 경로 결함이 빠진다는 걸 여기서 배웠고, 프롬프트에 "결함 후보" 섹션을 더했다.

기계로 내린 것과 내리지 못한 것의 경계도 이번 주에 분명해졌다. 절대경로 import는 문자열로 참/거짓이 갈려 내렸다. `data`·`temp` 같은 네이밍은 `id-denylist`로 내리려다 TanStack `{ data }` 18건이 전부 오탐이라 버렸다. 판단이 섞인 규칙은 룰로 만들면 오탐이 나고, 그건 AI·사람에 남는 게 맞다. 그리고 AI가 뽑고 사람이 걸러야 하는 것도 그대로였다. 9주차 생성기의 `test.fixme`를 걷어낸 것, 10주차 리뷰의 "`makeOrder` 미사용" 오판을 Grep으로 뒤집은 것이 그 예다.

## 8. 다시 만든다면

- **env 검증을 값이 생긴 주에 넣는다.** `APP_ORIGIN`은 7주차(`571138ec`)에 생겼고 같은 주 리뷰에서 기본값을 제거했는데, 검증은 10주차에 왔다. 그 사이에 10주차 첫 E2E run 전멸이 있었다. 설정 사고는 값이 생기는 순간 게이트가 있어야 한다.
- **E2E job을 8주차에 CI에 붙인다.** 8주차 문서는 "CI가 Playwright를 각각 실행한다"고 적었지만 워크플로엔 없었고, Chromium만 매 run 설치했다. 문서-워크플로 대조를 그때 했으면 두 주 동안 안 도는 E2E와 낭비되는 설치를 미리 잡았다.
- **번들을 7주차부터 잰다.** 7주차 RFC엔 이미지·document 바이트만 있어 10주차에 옛 SHA를 다시 빌드해 기준값을 만들었다. 측정을 시작한 주에 JS 바이트도 같이 기록했으면 성장 곡선이 실측으로 남았다.
- **사람이 지키는 규칙은 처음부터 도구로.** 절대경로 규칙은 1주차에 있었고 위반은 28건(우리 코드 18건, 스타터 10건) 쌓였다. 규칙을 문서에 적는 순간 ESLint 룰이나 probe가 같이 있어야 했다. 이번 주 룰 승격이 그 정정이다.
- **통합 브랜치 보호를 먼저 건다.** required check가 없으면 빨강은 신호일 뿐 게이트가 아니다. 이번 주에 처음 걸었고, 워크플로가 생긴 5주차부터 통합 브랜치 `kjeunn`에서는 병합 뒤 CI가 한 번도 안 돈 상태였다(push 트리거가 `main`뿐이었다).
- **배포를 일찍 붙인다.** 배포는 마지막 날에 붙였고, 붙이자마자 사고(남의 origin)와 규칙 ⑥이 나왔다. 그 전까지 env 규칙 ④는 설계와 테스트만 있었다. 채점 대상이 아니어도 운영 근거는 배포가 있어야 생기고, 사고도 배포가 있어야 드러난다.
