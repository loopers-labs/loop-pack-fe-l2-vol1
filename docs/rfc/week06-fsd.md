## R: 요구사항

### 보존할 동작

리팩토링은 폴더 이동이지 기능 변경이 아니다. 아래 동작을 사용자 입장에서 정의하고, 파일을 옮기기 전에 실제 화면에서 전부 재현해 확인했다(발견 버그 0건). 옮긴 후에도 이 목록이 그대로 성립해야 한다.

**홈**

- 홈에 들어오면 배너, 카테고리 5종, 인기 상품 6개, 신상품 6개가 보인다.
- 데이터를 불러오는 동안에는 "홈을 불러오는 중입니다…" 안내가 보인다.
- 불러오기에 실패하면 실패 안내와 "다시 시도" 버튼이 보이고, 다시 시도를 누르면 페이지 새로고침 없이 홈이 복구된다.
- 보여줄 상품이 없으면 인기 상품과 신상품 자리에 "표시할 상품이 없습니다."가 보이고, 배너와 카테고리는 그대로 유지된다.

**상품 목록**

- `/products`에 들어오면 상품 목록(총 개수, 페이지 표시)과 검색, 카테고리, 정렬 필터가 보인다.
- 검색어를 제출하거나 카테고리나 정렬을 바꾸면 목록이 그 조건으로 갱신되고, 보던 페이지는 1페이지로 돌아간다. 이미 걸어둔 다른 조건은 유지된다.
- 이전/다음 버튼으로 페이지를 넘길 수 있고, 현재 페이지와 전체 페이지 수("2 / 3")가 보인다.
- 조건에 맞는 상품이 없으면 "총 0개"와 "조건에 맞는 상품이 없습니다."가 보인다.
- 목록을 불러오는 동안에는 로딩 안내가 보이고, 실패하면 실패 안내와 "다시 시도" 버튼이 보인다. 다시 시도를 누르면 보던 조건 그대로, 페이지 새로고침 없이 목록이 복구된다.

**URL과 조건 공유**

- 조건이 걸린 URL을 공유받아 열면 보낸 사람이 보던 것과 같은 필터 값과 같은 목록이 보인다.
- 새로고침해도 보던 조건과 목록이 유지된다.
- 뒤로/앞으로 가기를 누르면 직전에 보던 조건(검색어, 카테고리, 정렬, 페이지)과 목록이 그대로 복원된다.

**장바구니와 위시리스트**

- 상품 카드의 찜/담기 버튼을 누르면 그 자리에서 버튼 상태가 바뀌고, 헤더의 위시리스트, 장바구니 개수가 함께 바뀐다.
- 홈에서 바꾼 찜/담기 상태는 목록의 같은 상품에도 그대로 보이고, 목록에서 바꾼 상태도 홈에 그대로 보인다.
- 페이지를 이동해도 찜/담기 상태와 헤더 개수가 유지되고, 새로고침해도 남아 있다.

**품질 게이트**

- `pnpm check`(테스트 156개, lint, typecheck, build) 통과.

### 이번 주에 하지 않을 것과 그 이유

- **기능 추가나 UI 변경을 하지 않는다.** 이번 작업은 리팩토링이다. 위 "보존할 동작" 목록 밖의 새 동작을 만들지 않고, 진행 중 발견한 기존 버그만 구조 변경과 분리된 커밋으로 수정한다(재현 방법, 원인, 수정 위치, 검증 결과를 기록).
- **mock 백엔드(`src/app/api`)는 FSD 전환 범위에서 제외한다.** Route Handler와 fixture는 프론트엔드가 아니라 백엔드를 흉내 내는 스타터 자산이다. FSD는 프론트 코드의 구조이므로 mock은 지금 위치에 두고, 프론트와 mock의 경계는 아키텍처(A)에서 설명한다.
- **지난 주차 학습 자산은 전환 범위에서 제외한다.** `src/app/demos`(4주차 데모 라우트)와 `src/examples/week-05-layout`(스타터 참고 예제)은 커머스 기능이 아니라 과제 이력이다. `src/shared/ui`의 dialog와 select는 도메인과 무관한 공통 UI로 이미 FSD의 `shared/ui` 세그먼트 위치에 맞아 옮길 필요가 없다.
- **발생할 수 없는 실패의 처리 코드를 만들지 않는다.** 로그인이 없는 서비스라 인증 만료(401)나 권한 없음(403) 같은 실패가 존재하지 않는다. 에러 처리 표에는 "해당 없음, 향후 로그인 도입 시 필요"로 기록하고 억지 구현을 두지 않는다.
- **변경 반경 실험(Advanced B)은 보류한다.** 기본 과제(전환, 에러 경계, 삭제 시나리오)를 완성한 뒤 여유가 있을 때 따로 결정한다.
