# Week9 3단계 - E2E 범위

## A. 이벤트 스키마

2단계에서 정한 이름 규칙과 공통 프로퍼티, 시드 로그와의 매핑.

### 이름 규칙

이벤트 이름은 `fixtures/events-30d.jsonl`를 참고하여 동일하게 지었습니다.

각 이벤트의 객체 = **공통 필드 + `props`(이벤트 고유).**

**공통 필드** (모든 이벤트에 추가됨): `sessionId · ts · name · device · userId`(로그인 시)

| 이벤트 | 발생 시점 | `props` |
|---|---|---|
| `product_list_view` - 목록 진입 | category·sort·page 변경마다 | `{ category, sort, page }` |
| `product_detail_view` - 상세 진입 | **앱에 상세 화면이 없어 미계측(뺌)** | - |
| `cart_add` - 담기 | 토글이 "담김"으로 갈 때만 | `{ productId }` |
| `login_start` - 로그인 시작 | 로그인 제출(`onMutate`) | `{}` |
| `login_success` - 로그인 성공 | 로그인 성공(`onSuccess`) | `{}` |
| `login_fail` - 로그인 실패 | 로그인 실패(`onError`) | `{ reason }` |
| `order_start` - 주문 시작 | 주문 클릭(`onMutate`) | `{ itemCount }` |
| `order_complete` - 주문 완료 | 주문 성공(`onSuccess`) | `{ itemCount }` |

**이벤트 필드 예시(product_list_view)**
```json
{
    "name": "product_list_view",
    "sessionId": "s_ojlg",
    "ts": "2026-08-30T04:42:23.897Z",
    "device": "desktop",
    "props": {
        "category": "all",
        "sort": "latest",
        "page": 1
    }
}
```

### 시드 로그와의 매핑

이벤트 이름과 공통 봉투 필드(`sessionId · ts · name · device · userId`)는 모두 시드(`fixtures/events-30d.jsonl`)와 동일하게 설정하였습니다. `props`는 시드에 맞출 수 있는 필드는 맞추고, 앱 구조상 못 맞추는 필드는 뺐습니다.

| 이벤트 | 시드 `props` | 앱 `props` | 같음/다름 |
|---|---|---|---|
| `product_list_view` | `{ category, sort, page }` | `{ category, sort, page }` | 같음 |
| `product_detail_view` | `{ productId }` | 미계측(상세 화면 없음) | 앱에서 뺌 |
| `cart_add` | `{ productId, quantity }` | `{ productId }` | `quantity` 뺌 |
| `login_start` | `{ from }` | `{ from }` | 필드 일치 |
| `login_success` | `{ from }` | `{ from }` | 필드 일치 |
| `login_fail` | `{ reason }` | `{ reason }` | 같음 |
| `order_start` | `{ productId }` | `{ productIds }` | 단수→복수 |
| `order_complete` | `{ productId, totalPrice }` | `{ productIds }` | 단수→복수, `totalPrice` 뺌 |

**못 맞춘 것과 이유**

- `cart_add`의 `quantity`: 담기가 토글(담김/뺌)이라 수량 개념 자체가 없습니다. 실을 값이 없어 뺐습니다.
- `order_complete`의 `totalPrice`: 주문 API 응답에 가격이 없고(`Order` = `{ id, createdAt, items }`) 카트에 담을 때 상품 id만 담고 있기 때문에 뻈습니다. 카트에 담을 때 가격까지 함께 담는 구조로 바꿀 경우 추가가 가능하지만, 이번 범위에서는 추가로 구현하지 않았습니다.
- `product_detail_view`: 앱에 상세 화면이 없어 이벤트 발생 지점 자체가 없습니다. 필드가 아니라 화면이 없는 경우라, 없는 화면을 만들지 않고 계측에서 뺐습니다. 로그 스키마와 현재 구현이 어긋나는 사례입니다.

## B. 시드 로그 분석

전체 세션 7514. 필터링(봇·오류·중복 제거) 후 세션 기준입니다.

- **경로 묶음 기준**: 이벤트를 기준으로 잡았습니다.
- **비율의 분모**: 진입 이벤트(`product_list_view`)는 앞 단계가 없어 **전체 세션 대비**. 앞 단계가 있는 이벤트는 **직전 단계 통과 세션 대비**(각 행 괄호에 분모 표기). 퍼널 `목록 → 담기 → 로그인 → 주문`은 완전 중첩(매 단계 직전 단계를 100% 포함)이라 이 비율이 유효하다고 판단 했습니다.
- **이탈률 정의**: **"다음 단계로 넘어가지 못한 비율"**(`1 - 다음 단계 도달수 / 이 단계 도달수`). 비율과 같은 단계 전환을 공유해 옆 행으로 검산됩니다. 다음 단계가 없는 리프(`order_complete`·`login_fail`)는 N/A입니다.
- **실패로 센 이벤트**: 완료 이벤트의 **부재**로 판정합니다. `order_start`는 있는데 `order_complete`가 없음 = 주문 실패(142건, 33.9%). `login_start`는 있는데 `login_success`가 없음 = 로그인 최종 실패(58세션, 전부 `login_fail` 동반). `login_fail` 이벤트는 121건이지만 그 중 63건은 재시도로 성공했으므로 최종 실패는 58입니다. 이 신호는 이탈률과 동일합니다. `client_error`는 실패가 아니라 필터링 대상(아래)입니다.

| 경로(이벤트) | 세션 수 | 비율(분모) | 이탈률 | 실패 비용 | E2E 여부(가설) |
| --- | --- | --- | --- | --- | --- |
| `product_list_view` | 7514 | 100% (전체) | 82.6% (→담기 못감) | 목록이 안 뜨면 이후 모든 퍼널 진입 불가 | 안 붙임(빈도 1위지만 8주차 통합·렌더로 검증, E2E 중복) |
| `cart_add` | 1309 | 17.4% (목록 대비) | 50.8% (→로그인 못감) | 담기가 막히면 주문할 항목이 안 담겨 주문 불가. | 안 붙임(8주차 통합으로 검증) |
| `login_start` | 644 | 49.2% (담기 대비) | 9.0% (→성공 못감=로그인 실패율) | 로그인이 막히면 주문불가. 실패=로그인 시작 후 성공 못 한 58세션(=이탈률 9.0%). 이 58개는 모두 `login_fail`로 끝남(시작만 하고 결과 없이 사라진 세션은 0). `login_fail` 이벤트 121건 중 63건은 재시도로 성공 | 붙임(필수): 인증. 막히면 뒤 경로 전부 막힘 |
| `login_success` | 586 | 91.0% (로그인 시도 대비) | 28.5% (→주문 못감) | 위와 동일 | 붙임(필수): 인증 플로우 |
| `order_start` | 419 | 71.5% (로그인 성공 대비) | 33.9% (→완료 못감) | 주문이 막히면 구매 불가 | 붙임(후보. 결제 핵심 경로이기 때문이며 이탈도 크기 때문) |
| `order_complete` | 277 | 66.1% (주문 시도 대비) | -(다음이 없음) | 구매 실패 | 붙임(후보. 위와 같은 이유) |
| `login_fail` | 121 | 18.8% (로그인 시도 대비 실패율) | -(다음이 없음) | 로그인이 막히면 주문불가. | 안 붙임(단순히 로그인 실패 신호이기 때문) |

### 필터링 기준 (봇·오류·중복)

- **A에서 계측하기로 정한 이벤트 외의 이벤트 → 집계 제외**: 집계 대상은 A에서 계측하기로 정한 7개 이벤트뿐입니다. 시드에만 있고 앱은 계측하지 않는 이벤트(`product_detail_view`·`category_filter_change`·`page_change`·`sort_change`·`wishlist_add`·`client_error`)는 집계 전에 제외했습니다.
- **`device: null`을 봇 세션으로 가정하여 제거**: 근거는 null 자체가 아니라 행동입니다. UA 파싱 실패라고 예상됨 + `product_list_view` 단일 이벤트 + 이후 상호작용이 없어서 크롤러라 가정했습니다.
- **같은 `sessionId`에서 `name`·`props`·`ts` 모두 동일한경우 중복 전송으로 판단**: 저 필드들이 모두 같다면 같은 시간에 같은 이벤트가 두 번 찍힌 것이므로, 더블클릭이나 재전송 같은 중복 전송으로 보고 1건만 남깁니다. 반대로 `name`만 같고 `props`가 다른 경우(예: 목록에서 1페이지 → 2페이지로 넘겨 `product_list_view`가 두 번 찍히는 것)는 정상 동작이라 지우지 않습니다.

### 필터링 전후 순위 비교

집계 대상 7개 이벤트를 세션 수로 줄 세운 순위는 필터 전후로 **바뀌지 않습니다.**

- `product_list_view`만 8000 → 7514로 줄지만(봇 486세션 제거) 여전히 압도적 1위입니다.
- 나머지 6개는 숫자·순서 모두 그대로입니다.
- **안 바뀌는 이유**: 봇은 진입 이벤트(원래 1위)만 갉아먹었고, 중복은 양이 미미합니다. 필터가 진입 이벤트와 잡음에만 닿고 퍼널 중간 순위를 못 흔듭니다. 상위 경로 판단이 잡음에 견고하다는 뜻입니다.

## C. 붙일 곳과 안 붙일 곳

### 안 붙인 경로

인증 외의 모든 경로에 붙이지 않았습니다.

- **목록·담기(`product_list_view` · `cart_add`)**: 아래 "빈도 높은데 E2E 안 붙인 경로"에서 설명합니다.
- **로그인(`login_start` · `login_success`)**: 아래 "빈도 낮은데 E2E 붙인 경로"에서 설명합니다.
- **`order_start` / `order_complete` (주문)**: B의 가설(붙임 후보)에서 정한 결정을 다음 이유로 뒤집었습니다. 결제 게이트웨이·결제창이 없어 실패해도 돈이 걸리거나 다른 기능을 막지 않습니다(실패 비용 축이 약함). 주문 로직(카트 → POST `/api/orders` → 카트 비우고 `/orders` 이동)은 상태 변화 → UI 변화라 MSW 통합으로 검증돼 "통합으로 안 되는 이유"가 없습니다. 로그인된 사용자가 `/orders/new`에 도달하는 부분은 인증 E2E가 이미 지납니다.
- **`login_fail`**: 별도 사용자 흐름이 아니라 로그인 실패 신호입니다. 인증 E2E(로그인 실패·세션 만료 경로)에서 자연히 확인됩니다.

### 빈도 높은데 E2E 안 붙인 경로

- 목록(`product_list_view`, 전체 1위)·담기(`cart_add`)·필터/정렬/페이지 변경입니다. 8주차에 이미 통합과 E2E로 덮었습니다. 각 항목의 코드 위치는 아래와 같습니다.
  - 통합 - `src/_pages/products/ui/ProductList.test.tsx`: 로딩 → 성공 `:100`, 빈 결과 `:136`, 에러(5xx 경계/4xx 인라인) `:168`, 재시도 복구 `:200`, 카테고리 변경 → 목록 교체 `:268`, 정렬 변경 → 순서 변경 `:330`, 페이지 이동 → 목록 교체 `:377`
  - 통합 - 담기 → 헤더 배지: `src/__tests__/commerceState.contract.test.tsx:35`
  - E2E - URL 반영·그 URL 재진입 복원: `e2e/urlState.spec.ts:6`(반영), `:18`(재진입 복원)
  - E2E - 뒤로/앞으로 필터 복원: `e2e/history.spec.ts:8`(뒤로), `:24`(앞으로)
  - E2E - 새로고침 필터 유지: `e2e/reload.spec.ts:7`
  - E2E - 목록 진입 → 담기 → 헤더: `e2e/cart.spec.ts:5`

### 빈도 낮은데 E2E 붙인 경로

- **인증 플로우 (필수)**: 과제에서도 명시된 부분으로, 인증이 깨지면 보호 경로(`/orders`·`/orders/new`·`/mypage`)가 전부 막혀 주문·마이페이지를 못 씁니다. 빈도는 낮아도(`login_start` 담기 대비 49.2%, 전체 대비로는 하위) 실패 비용이 최대라 필수입니다. 또한 인증에서 확인할 것(쿠키 `httpOnly`·`SameSite` 해석, proxy 302 리다이렉트 + `redirectUrl` 복원, SSR 초기 HTML에 로그인 상태 반영, 세션 만료 401 안내)은 브라우저에서 테스트 하는게 적합합니다. 
  - 테스트 개수: 쿠키·리다이렉트+복원은 한 번 로그인하는 동안 함께 확인되어 1개로 합치고, 진입 조건이 다른 세션 만료 까지 합해서 총 2개입니다.


### 유지보수 비용 추정

**대상 시나리오**: 미로그인이 `/orders/new` 진입 → proxy 302 `/login?redirectUrl=/orders/new` → 로그인 → `/orders/new` 복원.

**이 흐름이 지나는 화면의 문구·구조가 바뀌면 고칠 곳**

1. `/login`의 입력·버튼 셀렉터 (이메일·비밀번호 입력, 로그인 버튼)
2. `redirectUrl` 파라미터 단언 (`?redirectUrl=/orders/new`) - 복원 파라미터 이름이 바뀌면 고칩니다.
