## A. 이벤트 스키마

> 체크리스트 3-1. 상세 판단 근거는 `docs/rfc/week09-rfc.md`의 "이벤트 이름 규칙 결정 (2-0)", "공통 프로퍼티 결정 (2-0)", "시드 로그 이벤트 매핑 표 (2-3)" 절에 있다.

### A-1. 이벤트 이름 규칙

**`객체_행동` 순서의 snake_case로 통일한다. 이름 하나가 "화면(대상) + 행동"을 정확히 가리켜야 한다.**

- 규칙: snake_case, 앞에 객체 뒤에 행동 (`product_detail_view`, `category_filter_change` 스타일). 행동은 view·change·add·success/fail 등 결과 중심 동사.
- 금지: `button_click`, `page_view` 같은 범용 이름 — 나중에 집계할 수 없다.
- 코드상 위치: 이벤트 이름 문자열은 `src/analytics/events.ts`에만 존재한다 (2-3 래퍼 결정). 이 문서(A절)와 `events.ts`가 스키마 지식의 두 원천이며, 어긋나면 둘 중 하나를 고친다.

현재 계측 중인 이벤트 5종:

| 이벤트              | 발생 시점                                | props       |
| ------------------- | ---------------------------------------- | ----------- |
| `product_list_view` | 상품 목록 진입 (mount 1회)               | —           |
| `cart_add`          | 장바구니 담기 (담기 시점만, 해제 미기록) | `productId` |
| `login_start`       | 로그인 화면 진입 (mount 1회)             | —           |
| `login_success`     | 로그인 성공 직후 (`identify` 연결 다음)  | —           |
| `login_fail`        | 로그인 실패 (catch 분기)                 | `reason`    |

### A-2. 공통 프로퍼티

**모든 `track` 이벤트에 `sessionId`, `ts`, `device`가 자동으로 붙는다. `userId`는 공통 프로퍼티가 아니라 `identify()`/`reset()`으로 관리한다.**

| 프로퍼티    | 생성 방식                                                      | 비고                                                                       |
| ----------- | -------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `sessionId` | `sessionStorage` + `crypto.randomUUID()`                       | 탭 단위 — 새로고침 유지, 탭 종료 시 새 발급. "한 번 방문" 단위의 분모      |
| `ts`        | `new Date().toISOString()`                                     | 이벤트 발생 시점에 평가 (`setCommonProperties`가 함수를 받음)              |
| `device`    | `window.innerWidth` 휴리스틱                                   | `<768` mobile · `<1024` tablet · 나머지 desktop — 시드 로그 값 집합과 일치 |
| (`userId`)  | `identify(user.id)` 로그인 성공 직후 / `reset()` 로그아웃 직후 | 이벤트 행에는 없고 콘솔 로그로만 확인 가능 (consoleProvider 특성)          |

### A-3. 시드 로그 매핑 표

**시드 로그(`fixtures/events-30d.jsonl`)와 내 앱 이벤트의 대응 관계. 3단계 B절 집계의 번역표다.**

## B. 시드 로그 분석

> 체크리스트 3-2. 집계는 스크립트(jq/node)로 수행했다. 원본 22,427 이벤트 / 8,000 세션.

### B-0. 노이즈 걸러내기 기준

1. **봇 세션**: `device`가 `null`인 이벤트를 포함한 세션을 봇으로 판단해 제외한다(486 세션). 근거: 해당 세션은 전부 이벤트가 딱 1건(`product_list_view`)이고, 타임스탬프 밀리초가 전부 `.000`으로 떨어지는 정각 값이라는 일관된 지문을 공유한다 — 크롤러가 목록 페이지만 찍고 나가는 패턴. 단, 정각 타임스탬프(`.000Z`)만으로는 거르지 않는다. 사람 이벤트 27건도 정각이라 오탈(誤刹)이 발생하기 때문.
2. **오류 이벤트**: `client_error`(전부 `IMAGE_LOAD_FAILED`, 103건)는 화면 이동 단계가 아니므로 경로 집계에서 제외한다. 단, 이 이벤트들은 사람 세션의 정상 흐름 한가운데 끼어 있으므로 **세션째 제외하지 않는다**, B-2의 실패 신호로만 참조한다.
3. **중복 전송**: `sessionId`·`ts`·`name`·`props`가 완전히 동일한 줄은 이중 전송으로 보고 1건만 남긴다(77건, 0.3%). `ts`가 다른 같은 이름의 이벤트는 정상 데이터이므로 건드리지 않는다.

### B-1. 거르기 전 / 후 순위 비교 (세션 수 기준)

| 순위 | 거르기 전 (세션 8,000) | 거른 후 (세션 7,514) |
| ---- | ---------------------- | -------------------- |
| 1    | 상품 목록 8,000        | 상품 목록 7,514      |
| 2    | 상품 상세 4,656        | 상품 상세 4,656      |
| 3    | 장바구니 담기 1,309    | 장바구니 담기 1,309  |
| 4    | 로그인 644             | 로그인 644           |
| 5    | 위시리스트 480         | 위시리스트 480       |
| 6    | 주문 419               | 주문 419             |

**전후 비교: 순위는 한 칸도 바뀌지 않았다.** 이유: 봇 486 세션이 전부 1위 경로(상품 목록)의 단일 이벤트였기 때문에, 다른 경로의 세션 수는 1건도 오염되지 않았다. 바뀐 것은 **수치의 신뢰도**다 — 상품 목록 세션 수 8,000 → 7,514(6.1% 과장 제거), 전체 세션 분모 8,000 → 7,514로 모든 경로의 비율이 실제에 가깝게 조정됐다. 즉 이 로그에서 노이즈 제거의 가치는 "순위 뒤집기"가 아니라 **"분모 정화"**였다.

### B-2. 경로별 표 (거른 후 기준)

**경로 단위**: 이벤트별이 아니라 **화면 묶음**으로 정했다 — 같은 화면 안의 인터랙션(`category_filter_change`·`sort_change`·`page_change`)은 목록이라는 한 단계의 내부 행동이므로 `상품 목록`에 합친다. 퍼널 분석의 단위는 화면이기 때문.
**비율 분모**: 노이즈 제외 후 전체 세션 7,514.
**이탈률 정의**: "그 경로의 이벤트가 세션의 마지막 경로 이벤트였던 비율"을 택했다. "다음 단계로 못 넘어간 비율" 정의는 경로 간 선후 관계가 반드시 일렬이 아닌(위시리스트는 목록↔상세 어디서든) 이 데이터에서는 계산이 어긋나기 쉽기 때문.

| 경로          | 세션 수 | 비율 (분모 7,514)       | 이탈률 | 실패 비용                                                                                            | E2E 여부(가설)                                           |
| ------------- | ------- | ----------------------- | ------ | ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 상품 목록     | 7,514   | 100% (모든 세션의 입구) | 38.0%  | 실패 이벤트 정의 없음(진입 화면). 막히면 모든 후속 경로 진입 불가                                    | **안 붙임** — 8주차 E2E·통합 테스트가 이미 URL 상태 검증 |
| 상품 상세     | 4,656   | 62.0%                   | 64.5%  | `client_error`(IMAGE_LOAD_FAILED)가 유일한 실패 신호. 막히면 담기·주문 유입 감소                     | **붙일 수 없음** — 내 앱에 화면이 없음 (A-3 매핑)        |
| 장바구니 담기 | 1,309   | 17.4%                   | 50.8%  | 실패 이벤트 정의 없음(클라이언트 토글). 막히면 전환 퍼널 단절                                        | **안 붙임** — 8주차 `cart-wishlist.spec.ts`가 이미 검증  |
| 로그인        | 644     | 8.6%                    | 34.9%  | `login_fail` 121건 — 시작한 세션의 9%가 실패 경험(성공률 91%). 막히면 주문·마이페이지·복원 전부 불가 | **붙임 (필수)** — C절                                    |
| 위시리스트    | 480     | 6.4%                    | 71.9%  | 실패 이벤트 정의 없음. 부가 기능이라 주문 직접 단절 아님                                             | **붙일 수 없음** — 화면 없음(버튼만 존재), 미계측        |
| 주문          | 419     | 5.6%                    | 100%   | 시작 419 중 완료 277 — **34%(142 세션)가 시작만 하고 중단**. 매출 직결                               | **붙일 수 없음** — 주문 생성 플로우가 앱에 없음          |

부수 발견: 주문 경로의 이탈률 100%는 "주문을 시작한 세션은 이후 다른 화면으로 가지 않는다"는 뜻으로, 생성된 시드 데이터의 특성(주문 = 세션의 마지막 행동)이다. 진짜 이탈 지표는 시작 대비 완료의 34% 갭이다.

## C. 붙일 곳과 안 붙일 곳

> 체크리스트 3-3. 4단계에서 구현할 E2E의 최종 범위다.

### C-1. 결론 — 신규 E2E는 인증 3갈래만

**인증 플로우는 빈도와 무관하게 필수로 붙인다.**

1. **로그인이 막히면 그 뒤가 전부 막힌다.** 주문(5.6%), 마이페이지, 보호 경로 복원 — 인증은 이 모든 경로의 관문이다. 빈도 8.6%는 "로그인할 일이 적다"가 아니라 "한 번 막히면 피해가 전파된다"와 같은 이야기다.
2. **이번 주에 새로 생긴 행위다.** 8주차 테스트는 인증이 없던 시절의 것이다. 인증 가드·복원·만료 처리(1단계)를 검증하는 테스트는 어디에도 존재하지 않는다 — 로그 빈도와 무관하게 **커버리지 공백**이다.

**빈도 낮은데(8.6%) 붙인 이유 — "로그만 보고 정하면 안 되는 이유":** 로그는 "무엇이 자주 일어나는가"만 말한다. "무엇이 망가졌을 때 치명적인가"는 말하지 않는다. 빈도 기준만 따르면 인증은 4위라 탈락하지만, 실패 비용 열을 보면 전파 범위가 가장 넓다. 빈도와 실패 비용을 함께 보는 것이 이 표의 요점이다.

### C-2. 인증 외 추가 후보 — 0개

고르지 않았고, 그 이유가 근거다:

- **상품 목록(빈도 1위, 100%)**: ⚠️ 규칙 적용 — 8주차 `navigation.spec.ts`(E2E)가 URL 상태·필터 복원·새로고침 계약을, 통합 테스트가 필터 로직을 이미 검증한다. 여기에 또 E2E를 붙이는 것은 중복 투자다.
- **장바구니 담기(3위, 17.4%)**: 8주차 `cart-wishlist.spec.ts`(E2E)가 담기·토글·persist 복원을 이미 검증한다. 같은 이유로 제외.
- **상품 상세·주문·위시리스트**: 화면(플로우)이 없어 E2E를 붙일 수 없다. 화면을 새로 만들지 않는다 — 로그 스키마가 구현보다 오래 살아있는 실무적 어긋남이며, A-3 매핑 표에 근거가 있다.

### C-3. 빈도 높은데 E2E를 안 붙인 경로

| 경로      | 빈도       | 안 붙인 이유                                                                         |
| --------- | ---------- | ------------------------------------------------------------------------------------ |
| 상품 목록 | 100% (1위) | 8주차 E2E(`navigation.spec.ts`) + 통합 테스트로 충분. 신규 E2E는 0의 가치를 추가한다 |
| 상품 상세 | 62% (2위)  | 화면이 없다. "로그에 있으니 테스트해야지"는 불가능하며, 만들 필요도 없다             |

### C-4. 유지보수 비용 추정 — "만료 후 재로그인 복원" 시나리오

`expired` 시나리오로 만료 재현 → 보호 API 401 → 전역 처리기가 `/login?expired=1&redirectTo=...` 이동 → 재로그인 → 원래 경로 복원.

이 시나리오가 깨질 때 테스트 코드에서 고쳐야 할 곳:

1. 만료 안내 문구("세션이 만료되었어요. 다시 로그인해 주세요.") 변경 → `toContainText` 단언 1곳
2. 로그인 폼의 레이블("이메일"/"비밀번호") 변경 → `getByLabel` 2곳
3. 로그인 버튼 이름("로그인") 변경 → 1곳
4. 복원 파라미터명(`redirectTo`)·만료 플래그(`expired`) 변경 → URL 단언 2곳

**총 6곳 내외.** 셀렉터를 역할·이름 기반(`getByRole`/`getByLabel`)으로 쓰고, 고정 문자열은 문구 단언에만 썼으므로 CSS·구조 변경에는 깨지지 않는다. 다만 **문구·파라미터명은 계약이라 의도적 변경이 잦지 않다** — 오히려 깨진다면 우연이 아니라 계약 위반이라는 신호다.

### C-5. 최종 E2E 시나리오 목록 (4단계 구현 범위)

1. 미로그인 → 보호 경로(`/orders`) 진입 → 로그인 → **원래 경로 복원** (storageState 미사용)
2. 세션 만료: `expired` 시나리오 재현 → 만료 안내 → 재로그인 유도
3. 잘못된 자격 증명: `invalid` 시나리오 → 에러 메시지 표시

**총 3개 (인증 포함, 3개 이하 ✅)**

## D. 실험 기록 — E2E가 무엇을 잡는지 (5단계)

> 체크리스트 5-0 ~ 5-3. 실험 하나 = 망가뜨리기 → E2E 실행 → 기록 → 원복. 구현은 한 번에 변수 하나만 변경했고, middleware·클라이언트 코드가 빌드에 번들링되므로 **매 실험마다 재빌드 후** 실행했다.

### D-2. 해석 (5-2)

**살아남은 변경(실험 4)과 못 잡은 이유.** 테스트 ①의 주석은 "서버 판독 로그인 상태(초기 HTML) 확인"이라 쓰고 있었지만, 실제 단언은 `로그아웃 버튼 visible` 하나 — hydration이 끝난 뒤의 화면만 봤다. 초기 HTML에서 로그인 상태가 빠져도 클라이언트 `me` 조회가 화면을 채워주므로 눈으로 보는 최종 결과는 같았다. 즉 **주석이 주장하는 계약과 단언이 어긋나 있었다.** 수정: `page.request.get('/orders')`(JS 미실행)로 서버가 그린 순수 HTML을 검사하는 단언을 추가했다. 이 검증은 jsdom 통합 테스트가 원리적으로 못 하는 것(SSR 자체가 없음)으로, **E2E가 존재하는 이유를 실증한 사례**다.

**통합 테스트로 충분한 실험이 있었나.** 실험 2·3의 로직(리다이렉트 대상 계산, SessionExpiredError 분기)은 jsdom 통합 테스트로도 잡을 수 있다. 반면 실험 1(미들웨어 리다이렉트)과 실험 4(SSR 초기 HTML)는 통합 테스트가 원리적으로 커버할 수 없는 영역이다. → **E2E-only 항목 2개 확인 (5-3 완료조건 충족)** — 인증 E2E가 "복원·만료·진입 차단"을 테스트하는 것은 중복이 아니라 커버리지 공백의 제거였다.

**실험 흔적 정리.** `git diff` 확인 — 구현 코드에는 변경이 남지 않았다(실험 4 원복 완료). 남은 diff는 실험 4를 잡기 위해 강화한 테스트 단언 1건뿐이며, 이것은 5-2의 결과물로 의도적으로 커밋한다.
