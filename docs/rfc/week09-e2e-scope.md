# 9주차 인증 범위와 E2E 검증 정책

## 1단계 인증 정책

### 보호 경로

보호 경로는 주문서(`/order`)와 주문 내역(`/orders`)으로 정했다. 두 화면은 주문 생성과 주문 조회처럼 사용자 세션이 필요한 기능을 다룬다.

장바구니(`/cart`)와 위시리스트(`/wishlist`)는 보호하지 않는다. 두 화면은 브라우저에 저장된 로컬 사용자 상태를 확인하는 public-ish 화면으로 보고, 실제 주문을 시작하는 시점부터 인증을 요구한다.

현재 구현하지 않은 마이페이지는 보호 경로 판단 대상에서 제외했다. 이후 마이페이지가 추가되면 계정 정보 화면이므로 보호 경로에 포함한다.

### 복원 경로

미로그인 사용자가 보호 경로에 접근하면 `/login`으로 보낸다. 원래 가려던 경로는 `redirectTo` query string에 담는다.

예를 들어 `/orders?page=1`에 접근하면 `/login?redirectTo=%2Forders%3Fpage%3D1`로 이동한다. 로그인에 성공하면 `redirectTo` 값을 읽어 원래 경로로 돌아간다.

`redirectTo`는 내부 경로만 허용한다. 외부 URL이나 프로토콜이 들어오면 기본값인 `/`로 정규화해, 로그인 후 외부 주소로 튕겨 나가는 일을 막는다.

### proxy 역할

`proxy.ts`는 보호 경로 진입 전 세션 쿠키가 있는지만 확인한다. 여기서 세션 서명까지 검증하지 않는다.

proxy는 Edge 런타임에서 실행된다. 세션 서명 검증에 쓰는 `readSessionToken`은 `node:crypto`에 의존하므로 proxy에서 직접 가져오지 않는다.

실제 세션 신뢰 판단은 Node 런타임에서 한다.

- `(commerce-auth)/layout.tsx`: 보호 route group 진입 시 `readSessionToken`으로 사용자 정보를 복원하고 Header 초기 HTML에 반영한다.
- `/api/auth/me`, `/api/orders`: API 요청마다 `readSessionToken`으로 세션을 다시 검증한다.

이 구조에서는 위조되거나 만료된 쿠키가 proxy를 통과할 수 있다. 대신 보호 layout과 API에서 다시 검증하므로 인증 신뢰 판단은 proxy에 두지 않는다.

## 서버 세션과 초기 HTML

`/order`, `/orders`는 `(commerce-auth)` route group으로 분리했다. 이 layout에서만 쿠키를 읽고 세션 query cache를 hydrate한다.

이렇게 하면 JavaScript가 실행되기 전에도 Header에 로그인 사용자의 이름이 들어간 HTML을 내려보낼 수 있다. 실제로 JavaScript를 끈 E2E에서 `/order`, `/orders`에 진입했을 때 `루퍼1님`이 보이는지 확인한다.

공통 `(commerce)` layout에서는 쿠키를 읽지 않는다. 모든 commerce 페이지를 동적으로 만들면 7주차에서 잡아둔 정적 렌더링 범위를 다시 깨뜨릴 수 있기 때문이다. 그래서 세션 초기 HTML이 반드시 필요한 `/order`, `/orders`만 동적 경계로 올렸다.

## 세션 상태 관리

세션은 요청마다 달라지는 서버 상태다. 그래서 장바구니나 위시리스트처럼 Zustand에 저장하지 않고, React Query의 server state로 관리한다.

반대로 장바구니와 위시리스트는 현재 계정 서버 상태가 아니라 브라우저에 남는 로컬 사용자 상태다. 이 둘은 Zustand persist로 유지한다.

## 401 처리 기준

`/api/auth/me`는 로그인하지 않은 상태와 세션 만료를 같은 401로 돌려준다. 그래서 모든 401을 세션 만료로 보지 않는다.

401 해석 기준은 요청의 목적에 둔다.

- `/api/auth/me` 401: Header의 선택적 세션 확인 실패로 보고 `{ user: null }`로 처리한다.
- 보호 기능 API 401: 보호 화면에 들어온 뒤 발생한 인증 실패이므로 세션 만료 또는 유효하지 않은 세션으로 본다.

보호 기능 API의 401은 `parseApiError`에서 `AuthRequiredError`로 변환한다. 화면마다 401 분기를 직접 만들지 않고, `(commerce-auth)` route group의 `AuthRequiredModalBoundary`에서 한 번만 처리한다.

세션이 만료되면 현재 화면은 유지하고 모달로 다음 행동을 알려준다. 모달의 로그인하기 링크는 현재 경로를 `redirectTo`에 담아 로그인 후 원래 경로로 돌아올 수 있게 한다.

## 로그아웃 정책

로그아웃에 성공하면 세션 query cache를 `{ user: null }`로 갱신해 Header의 로그인 상태를 바로 바꾼다.

장바구니와 위시리스트는 로그아웃해도 지우지 않는다. 현재 구현에서 두 상태는 계정에 묶인 서버 데이터가 아니라 브라우저에 저장되는 로컬 상태다. 비로그인 사용자도 상품을 담거나 찜할 수 있으므로, 로그아웃이 로컬 장바구니와 위시리스트를 삭제하는 것은 더 큰 데이터 손실로 판단했다.

나중에 장바구니나 위시리스트가 서버 계정 데이터로 바뀌면 이 정책도 바뀐다. 그때는 로그아웃 시 React Query cache와 계정 기반 store를 함께 정리해야 한다.

## 2단계 이벤트 스키마

### 이벤트 이름 규칙

이벤트 이름은 시드 로그(`fixtures/events-30d.jsonl`)와 맞춰 `snake_case`를 사용한다. 이미 시드 로그에 있는 이벤트는 이름을 새로 만들지 않고 그대로 쓴다.

이름은 나중에 집계할 행동 단위로 정한다. 모든 클릭을 `button_click`으로 묶지 않고, 상품 목록 진입, 장바구니 담기, 로그인 성공, 주문 완료처럼 분석할 수 있는 단위로 나눈다.

### 공통 프로퍼티

모든 이벤트에는 `setCommonProperties()`로 공통 값을 붙인다.

| property    | 설명                               |
| ----------- | ---------------------------------- |
| `sessionId` | 브라우저 기준 익명 세션 식별자     |
| `device`    | `mobile`, `tablet`, `desktop`      |
| `path`      | 이벤트가 발생한 현재 경로          |
| `ts`        | 이벤트 발생 시각의 ISO 8601 문자열 |

`userId`는 공통 프로퍼티에 넣지 않는다. 로그인 성공 시 `identify(user.id)`로 사용자 식별을 시작하고, 로그아웃 성공 시 `reset()`으로 식별 상태를 끊는다.

### 시드 로그 매핑

시드 로그와 이름이 같은 이벤트는 그대로 사용한다. 현재 앱에 없는 상품 상세 화면만 제외한다.

| 요구사항        | 시드 로그 이름           | 우리 앱 계측 여부 | 이벤트 props                                     |
| --------------- | ------------------------ | ----------------- | ------------------------------------------------ |
| 목록 진입       | `product_list_view`      | 계측              | `q`, `category`, `sort`, `page`                  |
| 상세 진입       | `product_detail_view`    | 제외              | 상품 상세 페이지가 없음                          |
| 담기            | `cart_add`               | 계측              | `productId`, `quantity`                          |
| 주문하기 클릭   | `checkout_click`         | 계측              | `items`, `itemCount`, `totalQuantity`            |
| 위시리스트 추가 | `wishlist_add`           | 계측              | `productId`                                      |
| 카테고리 변경   | `category_filter_change` | 계측              | `category`                                       |
| 정렬 변경       | `sort_change`            | 계측              | `sort`                                           |
| 페이지 변경     | `page_change`            | 계측              | `page`                                           |
| 로그인 시작     | `login_start`            | 계측              | `redirectTo`                                     |
| 로그인 성공     | `login_success`          | 계측              | `redirectTo`                                     |
| 로그인 실패     | `login_fail`             | 계측              | `reason`                                         |
| 주문 시작       | `order_start`            | 계측              | `items`, `itemCount`, `totalQuantity`            |
| 주문 완료       | `order_complete`         | 계측              | `orderId`, `items`, `itemCount`, `totalQuantity` |

`checkout_click`은 시드 로그에는 없지만 현재 앱에서 추가로 남기는 이벤트다. 장바구니를 public-ish 화면으로 유지했기 때문에, 비로그인 사용자가 주문 의도를 보인 시점을 보기 위해 장바구니의 주문하기 클릭을 별도 이벤트로 둔다.

시드 로그의 주문 이벤트는 단일 상품 주문 기준이라 `productId`를 사용한다. 현재 앱은 여러 상품을 선택해 주문할 수 있으므로 `items: [{ productId, quantity }]` 형태로 상품과 수량을 함께 남긴다. `itemCount`와 `totalQuantity`는 주문 규모를 빠르게 집계하기 위한 요약값이다.

주문 이벤트에는 금액을 넣지 않는다. 현재 주문 API 응답에는 금액이 없고, 클라이언트에서 상품 가격을 다시 계산해 넣으면 계측 설계가 주문 금액 계산 책임까지 갖게 된다. 이번 단계에서는 주문 흐름과 수량을 세는 데 필요한 값만 남긴다.

### 계측 호출 위치

계측 코드는 화면 로직에 직접 흩뿌리지 않는다. `src/analytics/commerceEvents.ts`에 이벤트별 얇은 함수를 두고, 화면에서는 그 함수를 호출한다.

`commerceEvents.ts`는 이벤트 이름과 payload 계약만 안다. `_pages`, `entities`, store, query를 import하지 않는다. 필요한 값은 호출하는 쪽에서 계산해 넘긴다.

컴포넌트는 `track()`을 직접 호출하지 않고 `trackCartAdd`, `trackLoginSuccess`처럼 의도가 드러나는 함수를 호출한다. 이벤트 이름 문자열과 payload 구조를 한 파일에 모아, 화면 로직이 분석 스키마 변경에 직접 흔들리지 않게 한다.

| 이벤트                   | 호출 위치                        |
| ------------------------ | -------------------------------- |
| `product_list_view`      | 상품 목록 client 진입 effect     |
| `category_filter_change` | 카테고리 변경 handler            |
| `sort_change`            | 정렬 변경 handler                |
| `page_change`            | 페이지 변경 handler              |
| `cart_add`               | 상품 카드 담기 action 직후       |
| `checkout_click`         | 장바구니 주문하기 클릭           |
| `wishlist_add`           | 상품 카드 위시리스트 action 직후 |
| `login_start`            | 로그인 페이지 진입 effect        |
| `login_success`          | 로그인 mutation 성공             |
| `login_fail`             | 로그인 mutation 실패             |
| `order_start`            | 주문서 페이지 진입 effect        |
| `order_complete`         | 주문 생성 mutation 성공          |

### 초기화와 식별

`initAnalytics()`는 앱 최상단 client provider에서 한 번 호출한다. 이 위치에서 초기화하면 페이지 진입 직후 발생하는 이벤트도 queue에 쌓였다가 provider 초기화 뒤 순서대로 전송된다.

`setCommonProperties()`도 같은 provider에서 설정한다. `sessionId`, `device`, `path`, `ts`는 이벤트 발생 시점마다 평가한다.

로그인 성공 시점에는 `identify(user.id)`를 호출한다. 로그아웃 성공 시점에는 `reset()`을 호출한다. 이렇게 해야 로그인 전 익명 행동과 로그인 후 사용자 행동을 연결하고, 로그아웃 뒤 다음 행동이 이전 사용자에게 붙지 않는다.

### 예상 이벤트 순서

로그인부터 주문까지 한 번 통과하면 이벤트는 다음 순서로 남는다.

1. `/login` 진입: `login_start`
2. 로그인 성공: `identify(user.id)` → `login_success`
3. 상품 목록 진입: `product_list_view`
4. 상품 담기: `cart_add`
5. 장바구니 주문하기 클릭: `checkout_click`
6. 주문서 진입: `order_start`
7. 주문 완료: `order_complete`
8. 로그아웃 성공: `reset()`

## 3단계 E2E 범위 설계

### B. 시드 로그 분석

#### 분석 기준

시드 로그는 이벤트 수가 아니라 세션 수로 분석한다. 같은 사용자가 한 화면에서 조작을 여러 번 반복하면 이벤트 수가 부풀 수 있고, 그러면 실제 사용자 경로의 우선순위가 왜곡될 수 있기 때문이다.

경로는 이벤트 하나하나가 아니라 사용자가 지나가는 화면과 행동 단위로 묶는다. E2E는 개별 이벤트 전송 여부보다 실제 사용자 흐름이 깨지지 않는지를 보는 테스트에 가깝다.

| 경로      | 포함 이벤트                                                                                        | 기준                                         |
| --------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 상품 탐색 | `product_list_view`, `category_filter_change`, `sort_change`, `page_change`, `product_detail_view` | 상품 목록에 진입하고 상품을 찾는 흐름        |
| 담기      | `cart_add`, `wishlist_add`                                                                         | 상품을 구매 후보나 관심 목록에 저장하는 흐름 |
| 인증      | `login_start`, `login_success`, `login_fail`                                                       | 로그인 시도와 결과                           |
| 주문      | `order_start`, `order_complete`                                                                    | 주문서 진입부터 주문 완료까지의 흐름         |

`product_detail_view`는 시드 로그에는 있지만 현재 앱에는 상품 상세 화면이 없다. 로그 분석에서는 상품 탐색 흐름에 포함하고, E2E 구현 후보에서는 제외한다.

`checkout_click`은 현재 앱에서 추가한 이벤트지만 시드 로그에는 없다. 따라서 이번 시드 로그 기반 우선순위 산정에는 반영하지 않는다. 이후 실제 앱 로그가 쌓이면 장바구니에서 주문서로 넘어가려는 의도를 보는 이벤트로 사용한다.

#### 비율 기준

비율은 노이즈를 제거한 뒤의 전체 세션 수를 분모로 계산한다.

```txt
비율 = 해당 경로에 속한 이벤트가 하나라도 있었던 고유 세션 수 / 노이즈 제거 후 전체 세션 수
```

예를 들어 `담기` 경로는 `cart_add`, `wishlist_add` 중 하나라도 발생한 세션을 센다. 같은 세션에서 `cart_add`가 여러 번 발생해도 세션 수는 1개로 계산한다.

#### 이탈률 기준

이탈률은 "해당 경로에 도달했지만 다음 핵심 단계로 넘어가지 못한 세션 비율"로 계산한다.

| 경로      | 이탈로 보는 기준                                                                       |
| --------- | -------------------------------------------------------------------------------------- |
| 상품 탐색 | 상품 탐색 이벤트는 있었지만 `cart_add`, `wishlist_add`, `order_start`가 모두 없는 경우 |
| 담기      | `cart_add` 또는 `wishlist_add`는 있었지만 `order_start`가 없는 경우                    |
| 인증      | `login_start`는 있었지만 `login_success`가 없는 경우                                   |
| 주문      | `order_start`는 있었지만 `order_complete`가 없는 경우                                  |

"그 이벤트가 세션의 마지막이었는가"보다 실제 다음 전환 단계로 넘어갔는지를 보는 쪽이 E2E 후보 선정에 더 직접적이라고 봤다.

#### 실패 비용 기준

실패 비용은 해당 경로가 깨졌을 때 사용자가 잃는 핵심 행동으로 판단한다.

| 경로      | 실패 비용                                                    |
| --------- | ------------------------------------------------------------ |
| 상품 탐색 | 상품을 찾지 못해 이후 담기와 주문 흐름으로 진입하지 못한다.  |
| 담기      | 구매 후보를 저장하지 못해 주문 전환 가능성이 낮아진다.       |
| 인증      | 보호 경로에 접근하지 못하고 주문서, 주문 내역 흐름이 막힌다. |
| 주문      | 구매 완료가 막히며 매출 전환이 직접 실패한다.                |

#### 노이즈 제거 기준

시드 로그에는 봇 세션, 오류 이벤트, 중복 전송이 섞여 있다고 가정한다. 이번 분석에서는 아래 기준으로 노이즈를 제거한다.

- `client_error` 이벤트는 정상 경로 분석에서 제외한다.
- 같은 세션에서 같은 이벤트 이름과 같은 props가 5초 안에 반복되면 중복 전송으로 보고 하나만 남긴다.
- 한 세션에서 100개 이상의 이벤트가 발생하면 봇 후보로 보고 제외한다.
- `device`가 `null`인 이벤트는 경로 분석에는 포함하되, device별 분석에는 사용하지 않는다.

봇 후보 기준은 100개 이상으로 둔다. 정상 사용자도 필터와 페이지 이동을 여러 번 반복할 수 있으므로, 기준을 너무 낮게 잡으면 탐색을 많이 한 사용자를 봇으로 오해할 수 있다.

#### 필터 전후 비교 기준

필터 전과 후의 경로 순위를 모두 기록한다. 순위가 바뀌면 어떤 노이즈가 영향을 줬는지 적고, 바뀌지 않으면 주요 경로가 노이즈 제거 후에도 유지된 것으로 해석한다.

#### 집계 결과

시드 로그는 총 22,427개 이벤트와 8,000개 세션으로 구성되어 있었다. `client_error`는 103건, 같은 세션에서 같은 이벤트 이름과 props가 5초 안에 반복된 중복 전송은 77건이었다. 세션당 이벤트 수는 최대 11개였기 때문에, 100개 이상 이벤트를 남긴 봇 후보 세션은 없었다.

노이즈를 제거한 뒤에도 전체 세션 수는 8,000개로 유지됐다. 따라서 아래 비율의 분모는 노이즈 제거 후 전체 세션 8,000개다.

| 경로      | 세션 수 | 비율   | 이탈률 | 실패 비용                                                    | E2E 여부(가설)                                  |
| --------- | ------- | ------ | ------ | ------------------------------------------------------------ | ----------------------------------------------- |
| 상품 탐색 | 8,000   | 100.0% | 79.3%  | 상품을 찾지 못해 이후 담기와 주문 흐름으로 진입하지 못한다.  | 보류. 빈도는 높지만 8주차 통합 테스트가 많다.   |
| 담기      | 1,654   | 20.7%  | 74.7%  | 구매 후보를 저장하지 못해 주문 전환 가능성이 낮아진다.       | 보류. store와 Header 반영은 통합 테스트가 맞다. |
| 인증      | 644     | 8.1%   | 9.0%   | 보호 경로에 접근하지 못하고 주문서, 주문 내역 흐름이 막힌다. | 포함. 빈도보다 실패 비용이 크다.                |
| 주문      | 419     | 5.2%   | 33.9%  | 구매 완료가 막히며 매출 전환이 직접 실패한다.                | 포함 후보. 전환의 마지막 단계라 비용이 크다.    |

상품 탐색은 모든 세션이 지나간 경로였다. 이탈률도 높게 나왔지만, 여기서의 이탈은 단순히 상품을 보고 나간 세션까지 포함한다. 상품 목록 자체는 8주차에서 통합 테스트와 일부 E2E로 이미 다뤘기 때문에, 빈도만 보고 E2E를 더 늘리지는 않는다.

담기는 1,654개 세션에서 발생했다. 다만 현재 로그에는 장바구니 페이지 진입 이벤트가 없어서, 담기 이후 실제 장바구니를 봤는지까지는 알 수 없다. 그래서 이번 분석에서는 구매 후보를 저장한 뒤 주문서까지 넘어가지 못한 비율만 이탈률로 본다.

인증은 644개 세션으로 빈도는 낮지만, 실패하면 주문서와 주문 내역 접근이 함께 막힌다. 로그에서도 `login_fail`이 121개 세션에서 나타났다. 인증은 과제 필수 시나리오이기도 하므로 E2E에 포함한다.

주문은 419개 세션에서 시작됐고, 그중 142개 세션은 `order_complete`까지 도달하지 못했다. 비율은 낮지만 구매 완료와 직접 연결되므로 인증 외 E2E 후보로 둔다.

#### 필터 전후 비교

필터 전 경로 순위는 상품 탐색, 담기, 인증, 주문 순서였다. 노이즈 제거 후에도 순위는 바뀌지 않았다.

`client_error`는 정상 경로 이벤트가 아니어서 경로 포함 여부에 영향을 주지 않았고, 5초 이내 중복 전송도 같은 세션 안의 반복 이벤트라 세션 수 기준 순위를 바꾸지 않았다. 봇 후보 세션도 없었기 때문에 주요 경로의 우선순위는 필터 전후 모두 유지됐다.

### C. 붙일 곳과 안 붙일 곳

E2E는 인증 플로우와 주문 플로우에 붙인다. 상품 탐색과 담기는 빈도가 높지만 이미 통합 테스트로 더 빠르고 좁게 확인할 수 있으므로 E2E를 늘리지 않는다.

#### E2E를 붙일 시나리오

| 시나리오    | 근거                                                                                                                             | 4단계에서 만들 테스트                                                                                        |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 인증 플로우 | 세션 비율은 8.1%로 높지 않지만, 실패하면 주문서와 주문 내역 접근이 함께 막힌다. 과제 필수 시나리오이기도 하다.                   | 미로그인 보호 경로 진입 → 로그인 → 원래 경로 복원, 잘못된 자격 증명, `expired` 시나리오 세션 만료 안내       |
| 주문 플로우 | 세션 비율은 5.2%지만 구매 완료와 직접 연결된다. `order_start` 이후 `order_complete`로 가지 못한 세션도 33.9%라 실패 비용이 크다. | 로그인된 사용자가 상품 목록에서 상품 담기 → 장바구니에서 주문하기 → 주문서 진입 → 주문 완료 → 주문 내역 확인 |

인증 플로우는 빈도만 보면 상위 경로가 아니지만 E2E에 포함한다. 로그인과 세션 복원이 깨지면 주문서, 주문 내역처럼 보호 경로 전체가 막힌다. 이 흐름은 `proxy.ts`, 쿠키, 로그인 API, `redirectTo` 정규화, production 서버 라우팅이 함께 맞아야 하므로 통합 테스트만으로 충분하지 않다.

주문 플로우는 인증 외에 선택한 E2E 경로다. 상품 목록에서 구매할 상품을 담고, 장바구니에서 주문 의도를 보인 뒤 실제 주문서에 들어가고, 주문 완료 후 주문 내역에서 결과를 확인하는 과정은 구매 전환의 마지막 단계다. store, 인증 쿠키, 주문 API, 라우팅이 모두 연결되므로 사용자 관점의 E2E로 한 번 확인한다.

#### E2E를 붙이지 않을 시나리오

| 시나리오             | 제외 이유                                                                                                                                                           | 대체 검증                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 상품 탐색            | 세션 비율은 100.0%지만, 필터·정렬·페이지 변경은 URL query와 React Query 요청 조건이 맞는지가 핵심이다. 이 계약은 8주차 통합 테스트에서 더 빠르고 세밀하게 확인한다. | 상품 목록 통합 테스트, query 정규화 단위 테스트                                       |
| 담기                 | 20.7% 세션에서 발생하지만, 핵심은 Zustand store 변경과 Header 개수 반영이다. 브라우저/서버 경계보다 클라이언트 상태 연결이 중요하다.                                | 장바구니·위시리스트 통합 테스트, store 단위 테스트                                    |

| 장바구니 페이지 진입 | 시드 로그에 `cart_view`가 없어 장바구니 페이지 자체의 진입률과 이탈률을 계산할 수 없다.                                                                             | `checkout_click`은 이후 실제 앱 로그가 쌓이면 장바구니 → 주문서 전환 분석에 사용한다. |

#### 유지보수 비용 추정

유지보수 비용은 인증 플로우 중 "미로그인 보호 경로 진입 → 로그인 → 원래 경로 복원" 시나리오로 추정한다.

이 테스트가 확인할 사용자 관찰 결과는 `/order` 접근 시 `/login?redirectTo=%2Forder`로 이동하는지, 로그인 성공 후 다시 `/order`로 돌아오는지, 주문서 제목이 보이는지다. 로그인 폼의 label이 바뀌면 이메일과 비밀번호 입력 selector 2곳을 고쳐야 하고, 로그인 버튼 문구가 바뀌면 버튼 selector 1곳을 고쳐야 한다. 보호 경로 복원 파라미터 이름을 바꾸면 URL 단언 1곳도 함께 바뀐다.

현재 예상 수정 지점은 3~4곳이다. 대신 이 테스트는 proxy 보호 조건, `redirectTo` 정규화, 로그인 성공 후 라우팅을 한 번에 확인하므로 그 비용을 감수할 가치가 있다.

## 검증 방식

보호 경로 동작은 production build 위에서 확인한다. 빌드가 통과하는 것과 `pnpm start`로 띄운 앱의 proxy, cookie, redirect 동작이 맞는 것은 다른 문제이기 때문이다.

현재 E2E는 Playwright `webServer`가 `pnpm start`로 앱을 띄운 상태에서 실행한다.

- 미로그인으로 `/order`, `/orders`에 들어가면 `/login?redirectTo=...`로 이동한다.
- 로그인 후 원래 보호 경로로 돌아온다.
- JavaScript를 꺼도 보호 route group의 Header 초기 HTML에 사용자 이름이 보인다.
- `expired` 시나리오에서 현재 화면을 유지하고 세션 만료 모달을 보여준다.

정적 렌더링 범위는 `pnpm build`의 route 목록으로 확인한다. `/order`, `/orders`는 세션을 읽기 때문에 dynamic이고, `/cart`, `/wishlist`는 공통 commerce layout에서 쿠키를 읽지 않으므로 static 범위를 유지한다.

## 4단계 E2E 구현 결과

4단계에서는 3단계에서 정한 대로 인증 플로우와 주문 플로우만 E2E로 구현했다.

- 인증 플로우: `e2e/auth.spec.ts`
- 주문 플로우: `e2e/checkout.spec.ts`
- 로그인 상태 재사용: `e2e/auth.setup.ts`에서 `e2e/.auth/user-0.json`부터 `user-7.json`까지 생성

세션 만료 경계는 `expired` 시나리오 쿠키로 재현했다. 유효한 세션 쿠키가 있어도 `/api/orders`가 401을 응답하게 만들고, 보호 화면에서 세션 만료 모달이 열리는지 확인한다.

로그인 자체를 검증하는 테스트에서는 `storageState`를 쓰지 않는다. 로그인 폼 입력과 인증 실패를 직접 확인해야 하기 때문이다. 반대로 주문 플로우는 `storageState`를 사용해 이미 로그인한 상태에서 시작한다. 매번 로그인 폼을 채우면 주문 흐름이 아니라 로그인 흐름에 테스트가 흔들릴 수 있다.

E2E selector는 `getByTestId` 없이 role, name, label, visible text로 작성했다. 단언 대상도 사용자가 인식할 수 있는 이름으로 찾을 수 있는 요소로 제한했다.

주문 플로우는 상품 목록에서 상품을 담는 단계부터 시작한다. 이후 Header의 장바구니 링크, 장바구니 선택 상태, 주문서 진입, 주문 완료, 주문 내역 확인까지 실제 사용자 경로를 따라간다.

### 병렬 실행과 반복 실행

E2E는 production build 후 `pnpm start`로 띄운 앱을 대상으로 실행한다. 병렬 실행에서 섞일 수 있는 값은 아래처럼 나눴다.

| 구분               | 워커별 분리 방식                                                                       |
| ------------------ | -------------------------------------------------------------------------------------- |
| 계정               | `looper1@loopers.dev`부터 `looper8@loopers.dev`까지 8개 계정을 사용한다.               |
| 스토리지           | `e2e/.auth/user-0.json`부터 `user-7.json`까지 `storageState` 8개를 미리 만든다.        |
| 주문 데이터        | 주문 데이터는 계정별 서버 상태이므로, 워커별 계정을 나눠 주문 내역이 섞이지 않게 한다. |
| 장바구니 로컬 상태 | 장바구니는 브라우저 context별 `localStorage`에 저장되어 테스트 사이에 공유되지 않는다. |

주문 E2E는 `parallelIndex`와 `repeatEachIndex`를 기준으로 사용할 `storageState`를 고른다.

최종 확인할 명령은 아래와 같다.

```bash
pnpm build
pnpm test:e2e:prebuilt --project=chromium --workers=1
pnpm test:e2e:prebuilt --project=chromium --workers=4
pnpm test:e2e:prebuilt e2e/checkout.spec.ts --project=chromium --repeat-each=3
```

### trace 확인 기록

checkout E2E에서 주문 내역 수량 단언을 일부러 틀리게 바꿔 trace를 열어봤다. 원래 기대값은 `${selectedProductId} 1개`지만, 실험에서는 `${selectedProductId} 999개`를 기대하도록 바꿨다.

trace에서는 상품 목록에서 담기, 장바구니 이동, 주문서 진입, 주문 완료, 주문 내역 이동까지 모두 정상적으로 진행된 것을 확인했다. 실패는 마지막 주문 내역 article에서 발생했다. 실제 텍스트는 `p26 1개`였지만, 테스트가 `p26 999개`를 기다리고 있었다. 이 trace로 사용자 흐름이 어디까지 성공했고, 어떤 단언에서 멈췄는지 확인할 수 있었다.
