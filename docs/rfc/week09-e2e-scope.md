# Week 09 E2E 범위 부록 RFC

## 문서 역할

이 문서는 [Week 09 구현 RFC](./week09-implementation.md)의 E2E 부록이다.
이벤트 스키마, 시드 로그 분석, E2E 포함·제외 결정과 실행 증거의 단일 기준으로
사용한다.

| 항목               | 값               |
| ------------------ | ---------------- |
| 상태               | 검증 완료        |
| 현재 범위          | A~E 전체 완료    |
| E2E 구현 가능 여부 | 구현·재검증 완료 |
| 사용자 범위 확인   | 완료             |

## 운영 규칙

- A~C절을 사용자와 확정하기 전 E2E 코드를 작성하지 않는다.
- 이벤트 수가 아닌 고유 세션을 기준으로 집계한다.
- 인증은 필수이며, 인증 외 E2E는 최대 2개다.
- 포함 시나리오의 단언과 최종 범위는 사용자가 직접 결정한다.
- RFC에 없는 E2E 시나리오는 구현하지 않는다.
- D·E절에는 긴 원문 대신 명령, 결과, artifact 위치와 관찰을 기록한다.

## A. 이벤트 스키마

상태: **결정**

### 이름 규칙

이벤트 이름은 시드 로그와 동일한 snake_case를 사용해 매핑 표가 필요 없게 한다.

| 항목                 | 결정                      | 근거                     |
| -------------------- | ------------------------- | ------------------------ |
| 이벤트 이름 형식     | 시드 로그와 동일 이름     | Stage 3 매핑 비용 최소화 |
| 공통 프로퍼티        | `sessionId`·`ts`·`device` | 시드 공통 필드와 일치    |
| 사용자 identity 표현 | `identify(user.id)`       | 이벤트마다 복사하지 않음 |
| 발생 시각 표현       | 발생 시점 ISO 8601 UTC    | track 시점 평가          |

### 공통 프로퍼티

| 프로퍼티    | 타입                               | 생성 시점                           | 개인정보 여부 |
| ----------- | ---------------------------------- | ----------------------------------- | ------------- |
| `sessionId` | `s_<uuid>` 문자열                  | 탭 단위 sessionStorage, 메모리 폴백 | 아니요        |
| `ts`        | ISO 8601 UTC 문자열                | 이벤트 발생 시점                    | 아니요        |
| `device`    | `mobile`·`tablet`·`desktop`·`null` | 발생 시점 width 기준                | 아니요        |

### 이벤트 목록

과제 필수 지점을 기준으로 하되, 현재 앱에 없는 화면은 제외 사실과 이유를 남긴다.

| 이벤트              | 발생 조건                                                      | 프로퍼티                             | 구현 여부 |
| ------------------- | -------------------------------------------------------------- | ------------------------------------ | --------- |
| `product_list_view` | 목록 조회 조건 확정마다 1회 (진입·필터·정렬·페이지, 중복 없음) | `category`, `sort`, `page`           | 구현 완료 |
| `cart_add`          | 장바구니에 없던 상품이 담길 때만                               | `productId`                          | 구현 완료 |
| `login_start`       | 로그인 화면 표시 시 1회                                        | `from`                               | 구현 완료 |
| `login_success`     | 로그인 200 후 `identify()` 다음                                | `from`                               | 구현 완료 |
| `login_fail`        | 로그인 제출 실패마다 1회                                       | `reason`                             | 구현 완료 |
| `order_start`       | 주문서에서 주문 가능 장바구니 준비 시 1회 (빈 장바구니 없음)   | `itemCount`, `productIds`            | 구현 완료 |
| `order_complete`    | 주문 201 후 장바구니 정리 전 1회                               | `orderId`, `itemCount`, `productIds` | 구현 완료 |

제외: `product_detail_view`(상세 화면 없음), `category_filter_change`·`sort_change`·`page_change`
(`product_list_view` 재발생으로 대체), `wishlist_add`(과제 필수 지점 아님),
`client_error`(이번 주 범위 밖).

관측된 실제 순서: `product_list_view` → `cart_add` → `login_start` →
`login_fail` → `login_success` → `order_start` → `order_complete`.

### 시드 로그 매핑

이름은 시드와 동일하므로 이벤트 이름 매핑은 필요 없다. 형식 차이만 기록한다.

| 현재 값               | 시드 값       | 정규화 규칙                                   |
| --------------------- | ------------- | --------------------------------------------- |
| `sessionId` 전체 UUID | `s_0a3f` 형태 | `s_` 접두 일치, 분석은 정확 값 단위 세션 집계 |

### A절 완료 조건

- 이름 규칙과 공통 프로퍼티가 확정됐다.
- 필수 행동별 발생 조건과 필드가 결정됐다.
- 시드 로그와 이름 또는 구조가 다르면 매핑이 존재한다.
- 로그인부터 주문까지 이벤트 순서를 예측할 수 있다.

## B. 시드 로그 분석

상태: **분석 완료**

### 분석 입력

- 파일: `fixtures/events-30d.jsonl` — 22,427행, 8,000세션, 2026-07-22 ~ 2026-08-20
- 필드 설명: `docs/fixtures/events.md`
- 집계 단위: 고유 `sessionId`
- 파싱 실패: 0행

### 정제 기준

| 대상        | 판정 기준                                                                                                                                                                         | 처리                                           | 근거                                                                                                         |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 봇 후보     | 세션의 모든 이벤트가 `device: null`이고, `ts` 밀리초가 `.000`이며, 01시 UTC에만 발생하고, `product_list_view` 한 건만 남기며 props가 `{category:all, sort:latest, page:1}`로 동일 | 세션 제외 (486세션)                            | 다섯 신호가 같은 486세션에 동시 충족. 사람 이벤트에서 `.000`은 27/21,941, 전환은 0건                         |
| 중복 이벤트 | `sessionId`·`ts`·`name`·`props`가 완전히 같은 행                                                                                                                                  | 첫 건만 유지 (77행 제거)                       | 재전송. 목록·페이지·필터·정렬에서만 발생하고 사용자 행동은 한 번                                             |
| 오류 이벤트 | `client_error`                                                                                                                                                                    | 순위 집계에서 제외하고 실패 비용 판단에만 사용 | 사용자 행동이 아니라 결과. 코드가 `IMAGE_LOAD_FAILED` 하나뿐                                                 |
| 잘못된 필드 | 이벤트별 `props` 키 조합 이탈, 선후 관계 위반                                                                                                                                     | 해당 없음                                      | 키 조합은 이벤트마다 1종. `order_start` 없는 `order_complete`와 `product_list_view` 없는 `cart_add` 모두 0건 |

정제 결과는 22,427행 → 21,864행, 8,000세션 → 7,514세션이다.

### 지표 정의

| 지표      | 정의                                              | 분모                     |
| --------- | ------------------------------------------------- | ------------------------ |
| 세션 수   | 해당 이벤트가 1회 이상 발생한 고유 `sessionId` 수 | 없음. 절대값             |
| 비율      | 세션 수 ÷ 정제 후 전체 세션                       | 7,514                    |
| 이탈률    | 1 − (다음 단계 세션 ÷ 시작 단계 세션)             | 각 행에 시작 단계를 명시 |
| 실패 비용 | 실패했을 때 사용자가 잃는 것과 회복 가능성        | 해당 없음                |

빈도 순위와 비용 순위가 어긋난다. 1·2위인 목록과 상세는 실패해도 사용자가 즉시 회복하지만, 10위인 주문은 세션의 5.6%에서만 발생하면서 3분의 1이 완료 없이 끝난다. 로그인은 `login_start` 644건이 모두 담기 이후에 발생하고 `from`이 전부 `cart`여서, 보호 경로 진입의 유일한 관문이다.

### B절 완료 조건

- 정제 기준이 재현 가능하게 설명돼 있다.
- 필터 전후 순위와 변화 이유가 기록돼 있다.
- 모든 비율의 분모가 명시돼 있다.
- 이벤트 수가 아닌 세션 수를 기준으로 순위를 냈다.

## C. E2E 포함·제외 결정

상태: **결정**

### 필수 인증 시나리오

인증은 빈도가 낮더라도 뒤따르는 보호 기능 전체를 막을 수 있어 필수로 포함한다.
과제의 개수 기준에서는 아래 세 갈래를 **인증 플로우 한 시나리오**로 묶는다.

| 시나리오                            | 포함 이유 | 사용자 단언                                                                                                                                  | 상태 |
| ----------------------------------- | --------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| 보호 경로 → 로그인 → 원래 경로 복원 | 필수      | 미로그인으로 `/checkout` 요청 시 `/login?next=%2Fcheckout`으로 이동하고, 로그인 성공 후 `/checkout`이 복원되며, 담기 항목이 그대로 남아 있다 | 결정 |
| 세션 만료                           | 필수      | 만료된 세션으로 보호 경로 요청 시 로그인으로 이동하고 `login_start`의 `from`이 `expired`이며, 재로그인 후 원래 경로가 복원된다               | 결정 |
| 잘못된 자격 증명                    | 필수      | 폼에 머무르고 오류 메시지가 보이며, `login_fail`만 남고 `login_success`와 세션 쿠키가 생기지 않는다                                          | 결정 |

### 추가 후보

인증 외 추가 E2E는 0~2개만 선택한다. 아래 2개를 포함하고 나머지는 제외한다.

| 후보 경로                                              | 로그 근거                                                                                          | 기존 테스트 경계                                                                                                                      | 실패 비용                                              | 결정     |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ | -------- |
| 구매 완료 (인증 재사용 → 담기 → 주문 완료)             | `order_start` 419세션 중 33.9%가 완료 없이 종료. 인증 플로우는 필수 시나리오 3개가 별도로 검증한다 | `CheckoutView.dom.test.tsx`는 라우터를 mock하고 API를 msw로 대체한다. 실제 Route Handler·세션 쿠키·주문 내역 재조회는 미검증          | 가장 높음. 결제 직전 이탈에는 회복 경로가 없다         | **포함** |
| 장바구니 지속성 (인증 재사용 → 담기 → 새로고침·주문서) | `cart_add` 1,309세션 중 68.0%가 주문서에 도달하지 못한다                                           | 통합 테스트는 jsdom localStorage를 쓰고 전체 페이지 이동이 없다. `persist`가 `skipHydration`이라 하이드레이션 경계가 통합 범위 밖이다 | 높음. 장바구니가 비면 사용자가 담기부터 다시 해야 한다 | **포함** |
| 주문 실패 처리                                         | `order_start` 대비 완료 이탈 33.9%의 반대편                                                        | `CheckoutView.dom.test.tsx`의 `does not emit order_complete when the order fails`가 이미 단언한다                                     | 중간                                                   | 제외     |
| 필터·정렬·페이지                                       | 4,544세션 60.5%                                                                                    | `ProductListInteractions.dom.test.tsx`가 URL 상태를 검증한다                                                                          | 낮음. URL 재입력으로 회복                              | 제외     |

두 추가 시나리오는 worker별 로그인 결과를 `storageState`로 재사용해 인증 플로우와
중복되는 비용을 줄인다. 구매 완료는 서버 경계(Route Handler·쿠키·주문 내역)를,
장바구니 지속성은 브라우저 저장소 경계(전체 페이지 이동 뒤의 하이드레이션)를
검증한다.

### 포함 시나리오 단언

| 시나리오        | 단언                                                                                                                                                         |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 구매 완료       | 인증 상태에서 담기 후 `/checkout`에서 주문하면 `/orders`로 이동하고, 생성된 주문이 목록에 보이며, 장바구니가 비워지고 새로고침 후에도 비워진 상태가 유지된다 |
| 장바구니 지속성 | 인증 상태에서 담기 후 전체 새로고침과 보호 경로 이동을 거쳐도 담긴 항목이 그대로 남고, 같은 상품을 다시 담아도 수량이 중복되지 않는다                        |

## D. E2E 실행 증거

상태: **검증 완료**

### storageState와 worker 격리

| 항목                | 결정                                                                                                                                          | 검증 결과                                                          |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 계정 분리           | `parallelIndex`로 `looper1`~`looper8` 중 하나를 배정한다                                                                                      | worker마다 다른 계정으로 storageState를 만들고 주문 데이터를 분리  |
| storageState 재사용 | worker fixture가 UI 로그인 1회의 쿠키를 메모리 storageState로 보관한다                                                                        | 구매 완료·장바구니 지속성은 worker 안에서 같은 인증 상태를 재사용  |
| 로그인 테스트 상태  | 인증 자체를 단언하는 세 시나리오는 기본 `test`의 빈 컨텍스트를 사용한다                                                                       | 익명·만료·잘못된 자격 증명 흐름이 저장된 인증 상태에 가려지지 않음 |
| scenario 쿠키 격리  | 쓰지 않는다. `scenario=expired` 쿠키는 재로그인 후에도 만료 판정을 유지해 복원 단언을 막는다. 대신 서명이 유효하고 `exp`만 지난 토큰을 넣는다 | 만료 → 재로그인 → `/checkout` 복원이 통과                          |

`workerIndex`가 아니라 `parallelIndex`를 쓰는 이유가 있다. `workerIndex`는 worker가
재시작될 때마다 증가해 `--workers=4 --repeat-each=3`에서 8을 넘었고, 계정 부족으로
실패했다. `parallelIndex`는 0 이상 `workers` 미만을 유지하며 동시 실행 worker끼리
겹치지 않는다.

## E. E2E 자가 검증

상태: **검증 완료**

테스트 코드는 변경하지 않고 제품 코드 한 곳만 바꾼다. 각 실험이 끝날 때마다
제품 코드를 원복하고 diff를 확인한다.

| #   | 망가뜨린 곳                 | 단일 변경                               | 통합 테스트         | E2E                     | 실패 메시지                                                                     | 원복 |
| --- | --------------------------- | --------------------------------------- | ------------------- | ----------------------- | ------------------------------------------------------------------------------- | ---- |
| 1   | `src/app/login/page.tsx`    | `LoginView`의 `nextPath`를 `/`로 고정   | 47 passed, 생존     | 보호 경로 복원 1 failed | `/checkout`을 기다렸지만 `/`로 이동해 배선 오류를 바로 확인                     | 완료 |
| 2   | `src/app/checkout/page.tsx` | 만료 redirect에서 `reason=expired` 제거 | 17 passed, 생존     | 세션 만료 1 failed      | 기대 URL에는 `reason=expired`가 있으나 실제 URL에는 없어 원인을 바로 확인       | 완료 |
| 3   | `src/proxy.ts`              | 세션 쿠키 통과 조건 반전                | 2 failed / 8 passed | 보호 경로 복원 1 failed | 익명 요청은 200, 로그인 뒤에는 `/login` redirect loop가 발생해 조건 반전을 확인 | 완료 |

1·2번은 컴포넌트와 순수 정책 테스트가 모두 통과했지만 production 라우트 배선을
지나는 E2E가 실패했다. 따라서 통합 테스트만으로 잡을 수 없는 항목을 두 개 확인했다.
3번은 proxy 단위 테스트가 더 빠르게 원인을 짚었고 E2E도 redirect loop로 사용자
영향을 잡았다. 인증 플로우의 세 갈래는 시스템 배선 경계를, 추가 E2E 2개는
storageState로 인증을 재사용한 뒤 주문·저장소 경계를 맡기는 현재 구성을 유지한다.

### E절 완료 조건

- 실험이 세 가지 이상이다.
- 통합 테스트로 잡지 못하고 E2E만 잡은 항목이 최소 하나다.
- 살아남은 변경이 있다면 원인과 대응을 기록했다.
- 테스트 코드는 실험 중 바꾸지 않았다.
- 제품 코드와 작업트리에 실험 변경이 남아 있지 않다.
