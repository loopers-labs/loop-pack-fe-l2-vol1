# Week 09 E2E 범위 결정

## A. 이벤트 스키마

### 이름 규칙

이벤트 이름은 `<대상>_<행동>` 형태의 snake_case를 쓴다. 화면은 `track()`을 직접 호출하지 않고 `src/analytics/events.ts`의 타입이 붙은 함수만 호출한다. 문자열 오타가 새 이벤트 이름으로 수집되는 일을 막고, 이름과 프로퍼티 변경 지점을 한 파일로 모으기 위해서다.

계측 이벤트는 다음과 같다.

| 이벤트 | 발생 시점 | 프로퍼티 |
| --- | --- | --- |
| `product_list_view` | 목록 화면 최초 진입 | `category`, `sort`, `page` |
| `category_filter_change` | 카테고리 변경 | `category` |
| `sort_change` | 정렬 변경 | `sort` |
| `page_change` | 페이지 변경 | `page` |
| `cart_add` | 장바구니에 추가 | `productId`, `quantity: 1` |
| `wishlist_add` | 위시리스트에 추가 | `productId` |
| `login_start` | 로그인 폼 진입 | `from` |
| `login_success` | 로그인 성공 | `from` |
| `login_fail` | 로그인 실패 | `reason` |
| `order_start` | 주문서 진입 | `productIds`, `itemCount` |
| `order_complete` | 주문 생성 성공 | `orderId`, `itemCount` |

모든 이벤트에는 `setCommonProperties()`를 통해 다음 값을 발생 시점에 붙인다.

| 공통 프로퍼티 | 결정 |
| --- | --- |
| `sessionId` | 탭 단위 `sessionStorage` UUID. 저장소 접근이 막히면 `unavailable` |
| `ts` | 이벤트 발생 시점의 ISO 8601 문자열 |
| `device` | 시드 스키마에 맞춘 `mobile`·`tablet`·`desktop`·`null` |
| `userId` | 로그인 상태에서만 포함 |

`AnalyticsBoundary`는 storefront layout에서 로거를 초기화한다. 서버가 내려준 사용자 변화에 맞춰 `identify()`와 `reset()`을 한 곳에서 호출한다. 초기화 전 이벤트는 스타터 로거의 큐에 쌓이므로 목록 진입 이벤트가 유실되지 않는다.

로그인 성공 시에는 API 응답의 `user.id`를 먼저 `identify()`한 다음 `login_success`를 보낸다. layout 갱신을 기다리면 성공 이벤트만 익명으로 남아 시드 로그의 사용자 퍼널과 이어지지 않기 때문이다. 이후 `AnalyticsBoundary`의 식별은 새로고침과 직접 진입 세션을 복원한다.

`src/analytics`는 현재 FSD 레이어 밖의 횡단 관심사다. 그래서 entities의 담기·찜 버튼도 이벤트 카탈로그를 직접 참조하며, 현재 아키텍처 검사기는 이 방향을 검증하지 못한다. 화면에서 원시 `track()`을 금지하고 타입 wrapper만 허용하는 규칙으로 통제한다. 호출 지점이 더 늘면 analytics를 shared 계층의 명시적 public API로 편입한다.

### 시드 로그 매핑

| 시드 이벤트 | 현재 앱 | 차이 또는 제외 이유 |
| --- | --- | --- |
| `product_list_view` | 동일 | 없음 |
| `product_detail_view` | 미계측 | 상세 화면이 없음 |
| `category_filter_change` | 동일 | 없음 |
| `sort_change` | 동일 | 없음 |
| `page_change` | 동일 | 없음 |
| `cart_add` | 동일 | 현재 장바구니는 수량을 고르지 않으므로 `quantity: 1` 고정 |
| `wishlist_add` | 동일 | 해제 이벤트는 시드 스키마에 없어 보내지 않음 |

## B. 시드 로그 분석

분석은 `pnpm analytics:funnel -- --all --compare`로 재현한다. 비율의 분모는 노이즈 제거 후 남은 전체 세션 7,514개다. 경로는 이벤트 단위로 두었고, 이탈률은 **해당 이벤트가 그 세션의 마지막 이벤트였던 비율**을 사용했다. 퍼널의 단계 간 이탈은 별도로 직전 단계 도달 세션을 분모로 계산했다.

### 노이즈 기준

1. 같은 `sessionId`·이름·시각·props가 모두 같은 줄 77개를 중복 전송으로 제거했다.
2. device가 없고, 목록 진입 한 번만 있으며, 시각이 정각 밀리초(`.000Z`)인 세션 486개를 봇 후보로 제거했다. 로그에 봇 표식이 없으므로 이는 세 가지 비브라우저 징후가 동시에 있는 경우로 좁힌 추정이다.
3. `client_error` 103줄은 사용자 경로가 아니라 실패 관측 이벤트이므로 경로 순위에서 제거했다. 실패 비용을 판단할 때는 별도로 참고한다.

실패 이벤트로는 `login_fail`과 `client_error`를 정했다. `login_fail`은 121세션으로 로그인 시작 644세션의 18.8%이며, 자격 증명 오류·서버 오류·네트워크 실패를 포함한다. `client_error`는 원본 8,000세션 중 103세션(1.3%)에서 발생했다. 전자는 인증 퍼널의 실패율에 포함하고, 후자는 특정 사용자 경로가 아니므로 경로 순위에서는 제외하되 전역 장애 신호로 본다.

| 경로 | 세션 수 | 전체 세션 비율 | 마지막 이벤트 비율 | 실패 비용 | E2E 가설 |
| --- | ---: | ---: | ---: | --- | --- |
| 목록 진입 | 7,514 | 100.0% | 15.2% | 상품 탐색 시작 불가 | 제외 |
| 상품 상세 진입 | 4,656 | 62.0% | 64.5% | 상세 확인·담기 불가. 현재 화면 없음 | 제외 |
| 카테고리 변경 | 3,056 | 40.7% | 25.7% | 탐색 효율 저하 | 제외 |
| 페이지 변경 | 1,756 | 23.4% | 37.8% | 뒤쪽 상품 접근 불가 | 제외 |
| 장바구니 추가 | 1,309 | 17.4% | 50.8% | 주문 시작 불가 | 제외 |
| 정렬 변경 | 943 | 12.5% | 28.2% | 탐색 효율 저하 | 제외 |
| 로그인 시작 | 644 | 8.6% | 0.0% | 인증 기능 전체 차단 | 포함 |
| 로그인 성공 | 586 | 7.8% | 28.5% | 주문과 보호 기능 전체 차단 | 포함 |
| 위시리스트 추가 | 480 | 6.4% | 71.9% | 관심 상품 보관 불가 | 제외 |
| 주문 시작 | 419 | 5.6% | 33.9% | 구매 불가 | 포함 |
| 주문 완료 | 277 | 3.7% | 100.0% | 거래 결과를 만들지 못함 | 포함 |
| 로그인 실패 | 121 | 1.6% | 47.9% | 로그인 시작 세션의 18.8%; 복구 안내가 없으면 이탈 | 인증에 포함 |

퍼널 기준 이탈률은 상세→담기 71.9%, 담기→로그인 성공 55.2%, 로그인 성공→주문 시작 28.5%, 주문 시작→완료 33.9%다.

### 필터 전후 비교

필터 전에는 8,000세션·22,427이벤트, 필터 후에는 7,514세션·21,761이벤트다. 이벤트 순위는 바뀌지 않았다. 제거한 봇 후보가 모두 목록 진입 한 번인 세션이라 목록 진입의 마지막 이벤트 비율은 20.4%에서 15.2%로 5.2%p 낮아졌다. 다만 1위와 2위 사이의 격차가 3,000세션 이상이어서 순서를 뒤집지는 못했다. 중복은 동일 행동을 복제했으므로 세션 기준 순위에 영향을 주지 않았고, `client_error`도 상위 사용자 행동보다 규모가 작았다. 순위가 같아도 노이즈 제거가 이탈률 해석은 바꾼다.

## C. 붙일 곳과 붙이지 않을 곳

### 최종 E2E 범위

사용자 흐름은 두 개만 선택한다.

1. **인증 흐름(필수)**
   - 미로그인 `/orders/new` 진입 → 로그인 → 원래 경로 복원
   - 잘못된 자격 증명 → 인라인 오류, 이동 없음
   - 조회 세션 만료 → `reason=expired` 로그인 안내
   - 빈도는 로그인 성공 기준 7.8%로 낮지만, 실패하면 주문과 모든 보호 경로가 함께 막힌다. 쿠키, Proxy redirect, 서버 초기 HTML은 jsdom으로 재현할 수 없다.
2. **주문 완료**
   - 로그인 상태 재사용 → 상품 담기 → 주문서 → 주문 번호 표시
   - 완료 세션은 3.7%지만 거래 결과가 걸려 실패 비용이 가장 높다. 페이지를 건너 쿠키와 장바구니 상태를 연결하고 실제 주문 API까지 통과하는 과정은 브라우저에서 확인한다.

### 빈도가 높지만 E2E를 붙이지 않는 경로

- 목록 진입·카테고리·정렬·페이지 변경은 기존 `ProductListView` 통합 테스트가 MSW 응답, URL 반영, 로딩·오류 복구를 검증한다. 실제 브라우저가 있어야만 성립하는 단언이 없어 10~30초짜리 E2E로 중복하지 않는다.
- 장바구니 토글은 Zustand 규칙 단위 테스트와 ProductList 화면 통합 테스트로 상태·배지를 확인할 수 있다. 주문 E2E의 준비 동작으로 한 번 지나가지만 별도 E2E 시나리오로 세지 않는다.
- 상품 상세는 로그 2위지만 현재 코드에 화면이 없어 대상에서 제외한다.

### 낮은 빈도지만 인증을 붙이는 이유

로그인은 성공 기준 7.8%지만 주문·주문 내역으로 들어가는 관문이다. 빈도만 보면 목록보다 뒤지만 실패 반경이 훨씬 넓다. 특히 `HttpOnly` 쿠키 발급, Proxy의 307, `next` 복원, 서버가 그린 초기 HTML은 통합 테스트가 같은 보증을 제공하지 못한다.

### 유지보수 비용 추정

“미로그인 주문서 → 로그인 → 복원” 테스트는 로그인 폼의 이메일·비밀번호·버튼 3개와 목적지의 `주문서` heading, URL 두 지점을 관찰한다. 역할과 label을 사용하므로 DOM 구조 변경에는 영향이 없지만 사용자 문구가 바뀌면 최대 4개 locator를 수정한다. 로그인 동작은 한 helper에 모아 다른 E2E가 폼 구조를 반복해서 알지 않게 한다.

### 의도적으로 포기한 검증

- 로그인 500의 fallback 문구와 재시도 없음은 아직 통합 테스트로 고정하지 않았다.
- `scenario=expired` 쿠키는 테스트가 제거하기 전까지 계속 401을 강제하므로, 만료 안내 테스트에서는 재로그인 복원까지 단언하지 않는다.
- 만료 재로그인은 성공 이벤트 직후 문서를 이동한다. 현재 console provider는 동기라 기록되지만, 비동기 분석 SDK를 붙이면 전송 완료 전에 문서를 떠날 수 있다. 실제 provider 도입 시 `sendBeacon` 또는 SDK의 flush 계약이 필요하다.
- `product_list_view`는 컴포넌트 마운트당 한 번이다. 한 세션에서 목록을 떠났다가 돌아오면 다시 발생하므로, 시드 로그처럼 사실상 세션당 한 번인 정의와 이벤트 수는 달라질 수 있다. 본 분석은 세션 기준 중복 제거로 영향을 받지 않는다.
- 상품명·금액은 주문 API 계약에 없어 주문 내역에서 ID·수량만 확인한다.
- 시각적 회귀와 브라우저별 실행은 Basic 범위에서 제외한다.

## AI 사용

계측 wrapper, 집계 스크립트, 테스트 fixture와 반복 코드는 AI가 작성했다. 이벤트 스키마, 노이즈 기준, E2E 선택·제외와 단언은 이 RFC의 근거를 기준으로 검토했다. 자동 생성된 단언이 실제 구현 변이 5건을 모두 실패시키는지 확인했다.
