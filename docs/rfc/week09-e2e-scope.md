# 9주차 E2E 범위 결정 RFC

## 상태와 목적

- 상태: 제안
- 분석 대상: `fixtures/events-30d.jsonl`
- 구현 기준: 이 문서를 E2E 코드보다 먼저 커밋한다.

E2E는 브라우저, 서버 렌더링, 프록시, httpOnly 세션 쿠키, 클라이언트 상태와 API가 실제로 이어지는 경계에만 사용한다. 빈도만으로 테스트를 늘리지 않고, 실패 비용과 기존 테스트의 중복 여부를 함께 판단한다.

## A. 이벤트 스키마

### 이름 규칙과 계측 경계

이벤트 이름은 시드 로그와 같은 `snake_case`를 사용한다. 화면은 raw `track()`을 직접 호출하지 않고 `src/analytics/events.ts`의 타입 함수만 호출한다. `src/analytics`는 feature, page, widget을 import하지 않는다.

| 이벤트 | 발생 시점 | 이벤트 프로퍼티 |
| --- | --- | --- |
| `product_list_view` | 현재 URL 조건의 상품 목록 진입이 성공 또는 최종 오류 상태로 확정됐을 때 | `category`, `sort`, `page` |
| `cart_add` | 장바구니에 없던 상품을 담은 직후 | `productId`, `quantity: 1` |
| `login_start` | 로그인 화면에 진입했을 때 | `from` |
| `login_success` | 로그인 API 성공 응답 후 | `from` |
| `login_fail` | 로그인 API 실패 후 | `reason`, `status` |
| `order_start` | 유효한 장바구니의 주문 요청을 보내기 직전 | `productIds`, `itemCount` |
| `order_complete` | 주문 API 성공 응답 후 | `orderId`, `productIds`, `itemCount` |

같은 목록 URL 조건의 rerender, Strict Mode effect 재실행, background refetch와 오류 화면 재시도는 `product_list_view`를 중복 전송하지 않는다. category, sort, page 또는 검색 조건이 바뀌면 새 목록 진입으로 본다.

`login_start`와 `login_success`의 `from`은 한 번의 로그인 화면 진입 동안 동일한 값으로 유지한다.

- `/checkout` 계열: `cart`
- `/orders` 계열: `orders`
- 그 외 또는 안전하지 않은 외부 경로: `direct`

`login_fail.reason`은 서버 원문이나 개인정보를 포함하지 않는다.

- 400: `INVALID_REQUEST`
- 401: `INVALID_CREDENTIALS`
- 500 이상: `SERVER_ERROR`
- 그 밖의 오류: `UNKNOWN`

### 공통 프로퍼티와 사용자 연결

모든 track 이벤트에는 `setCommonProperties()`로 다음 값을 붙인다.

| 프로퍼티 | 생성 규칙 |
| --- | --- |
| `sessionId` | 탭의 `sessionStorage`에 생성·유지하는 비식별 UUID. 브라우저 저장소나 Web Crypto가 없어도 페이지 수명 동안 안정적인 안전한 대체 ID 사용 |
| `ts` | 이벤트 발생 시점의 ISO 8601 UTC 문자열 |
| `device` | viewport 폭 `<768`: `mobile`, `<1024`: `tablet`, 나머지 `desktop`; viewport가 없으면 `null` |

로그인 성공 이벤트 후 `identify(userId)`를 호출하고, 로그아웃 API 성공 후 `reset()`을 호출한다. 자격 증명, 이메일, 서버 오류 원문과 세션 쿠키는 이벤트에 넣지 않는다.

앱 루트 `Providers`의 `AnalyticsInitializer`가 provider와 공통 프로퍼티를 설정하고 `initAnalytics()`를 호출한다. 타입 이벤트 경계도 같은 설정을 멱등하게 보장하므로 초기화 effect보다 먼저 발생한 이벤트도 공통 프로퍼티와 전송 순서를 유지한다.

### 시드 로그 매핑과 제외

이벤트 이름은 시드와 동일하지만 일부 프로퍼티와 발생 의미는 현재 앱의 계약에 맞게 다음처럼 매핑한다.

| 시드 로그 | 현재 앱 | 이유 |
| --- | --- | --- |
| top-level `userId` | `login_success` 후 `identify(userId)` | 사용자 ID를 모든 이벤트 프로퍼티에 복제하지 않고 provider의 사용자 연결 기능을 사용함 |
| `product_list_view`: 목록 화면 진입 | 목록 조건의 성공 또는 최종 오류 확정, 검색 조건 변경도 새 진입 | 중복 rerender와 refetch는 제외하면서 사용자가 실제로 마주한 조건을 기록함. 검색어 `q`는 현재 이벤트 프로퍼티에는 포함하지 않음 |
| `login_fail.reason` | `login_fail.reason`, `status` | 현재 앱은 정규화한 실패 분류와 함께 HTTP status를 남기며 서버 오류 원문은 수집하지 않음 |
| `cart_add.quantity: 1 또는 2` | `cart_add.quantity: 1` | 현재 앱에는 상품별 수량 조절 기능이 없고 장바구니는 상품 ID 포함 여부만 저장함 |
| `order_start`: 주문서 진입 | `order_start`: 주문 API 요청 직전 | 현재 앱에서는 실제 네트워크 주문과 일대일 대응하도록 더 늦은 시점에 기록함. 두 로그의 시작점이 달라 조건부 미완료율을 직접 비교하지 않음 |
| `order_start.productId` | `order_start.productIds`, `itemCount` | 현재 장바구니는 여러 상품을 한 주문으로 전송함 |
| `order_complete.productId` | `order_complete.productIds`, `itemCount` | 완료 이벤트도 실제 제출 스냅샷 전체를 나타냄 |
| `order_complete.totalPrice` | 미수집 | 주문 API 응답에 금액이 없어 임의 계산하지 않음 |

`product_detail_view`는 현재 상품 상세 화면이 없어 계측하지 않는다. `category_filter_change`, `sort_change`, `page_change`, `wishlist_add`, `client_error`는 이번 최소 계측 범위에서 제외했다. 필터·정렬·페이지 변경은 목록 진입 조건의 변화로 `product_list_view`에 반영하며, 선택 이벤트를 별도로 만들지 않는다.

## B. 시드 로그 분석

### 정제 기준

원본은 22,427개 이벤트와 8,000개 세션이다.

1. `sessionId + ts + name + props`가 모두 같은 이벤트만 정확한 중복으로 보고 한 건만 남긴다.
2. `client_error`는 정상 행동 경로 순위와 종단 지표에서는 제외하지만 실패 비용 분석에는 유지한다.
3. 명시적인 봇 필드는 없으므로 단일 속성이나 단순 이벤트 수만으로 제외하지 않는다. 다만 아래 다섯 조건을 모두 만족하는 데이터셋 특이 반복 군집은 **자동화 의심 군집**으로 분류한다. 이는 봇이라는 ground truth가 아니라 정제 가설이다.
   - `device === null`
   - 세션 이벤트가 정확히 한 개
   - 이벤트가 기본 조건의 `product_list_view(category=all, sort=latest, page=1)`
   - 타임스탬프의 밀리초가 항상 `.000Z`
   - 30일 동안 매일 UTC 01:00~01:14에만 집중
4. 같은 세션의 반복 행동은 경로 세션 수를 늘리지 않는다.

정확한 중복 77건을 먼저 제거해 22,350건이 남았다. 이어서 위 조건을 동시에 만족하는 486개 단일 이벤트 세션을 자동화 의심 군집으로 제외했다. 최종 분석 모집단은 21,864개 이벤트와 7,514세션이다. 일부 조건만 맞는 세션은 제외하지 않았다.

### 경로 묶음

E2E 후보와 같은 사용자 목적 단위로 묶고, 이벤트별 수치는 별도 표로 공개한다.

### 비율과 이탈 정의

- 기본 비율의 분모는 중복과 자동화 의심 군집을 제거한 7,514세션이다.
- 경로 세션 수는 해당 목적 경로의 이벤트를 한 번 이상 가진 고유 세션 수다.
- 종단 이탈률은 해당 경로 진입 세션 중 `client_error`를 제외한 마지막 정상 이벤트가 그 경로였던 세션의 비율이다. 이후 정상 행동이 관측되지 않았다는 뜻이며 오류의 인과관계를 뜻하지 않는다.
- 인증과 주문은 시작 이후 성공 이벤트가 같은 세션에 있는지를 별도 조건부 전환율로 계산한다. 이 지표의 분모는 전체 세션이 아니라 해당 시작 이벤트 세션이다.

### 인증·주문 전환과 실패 비용

실패 신호는 다음처럼 정의한다. `login_fail`은 로그인 **시도 단위** 실패 신호다. 한 세션이 실패 후 재시도해 성공할 수 있으므로 인증 경로의 세션 단위 실패는 `login_start` 이후 `login_success`가 끝까지 없는 경우로 계산한다. 시드에는 주문 실패 이벤트가 따로 없으므로 주문 경로의 세션 단위 실패는 `order_start` 이후 `order_complete`가 없는 경우로 계산한다. `client_error`는 별도의 클라이언트 오류 신호로만 사용하고 인증·주문 실패의 원인으로 합치지 않는다.

| 퍼널 | 시작 세션 | 시작 후 성공 세션 | 조건부 전환율 | 미완료 세션 | 조건부 미완료율 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `login_start → login_success` | 644 | 586 | 91.0% | 58 | 9.0% |
| `order_start → order_complete` | 419 | 277 | 66.1% | 142 | 33.9% |

이미지 오류와 인증·주문 미완료의 인과관계는 이 로그만으로 단정하지 않는다.

실패 비용은 빈도와 별도로 다음 기준으로 평가한다.

- 현재 앱에 실행 가능한 화면과 흐름이 있는가
- 실패하면 뒤의 기능도 함께 막히는가
- 브라우저·쿠키·리다이렉트·서버 렌더링을 함께 검증해야 하는가
- 기존 통합 테스트나 E2E가 같은 위험을 이미 충분히 검증하는가

분석 단계의 E2E 가설은 다음과 같다. 이는 C절의 기존 테스트 감사와 합쳐 최종 판단한다.

| --- | --- | --- |
| 상품 탐색 | 상품 발견 접점과 후속 구매 진입 기회를 잃음 | 브라우저 URL·history 경계 가치가 있으나 기존 E2E와 중복 여부 확인 |
| 상품 상세 | 상품 판단 단계가 막힘 | 현재 앱에 화면이 없으므로 제외 예상 |
| 장바구니 | 주문 후보를 만들 수 없어 구매가 막힘 | 단독보다 주문 완료 흐름에 포함 예상 |
| 인증 | 주문서·주문 내역 등 모든 보호 경로가 막힘 | 프록시·쿠키·서버 렌더링 경계 때문에 필수 |

## C. 붙일 곳과 붙이지 않을 곳

### 최종 선택

인증을 필수 경로 하나로 세고, 인증 외에는 두 경로만 선택한다. 인증의 세 갈래는 4단계에서 별도 테스트로 구현하지만 범위 결정에서는 하나의 인증 경로다.

| 경로 | 세션 수 | 비율 | 핵심 관측 | 실패 비용 | E2E 결정 |
| --- | ---: | ---: | --- | --- | --- |
| 인증 | 644 | 8.6% | 시작 후 미완료 58세션, 9.0% | 실패하면 주문서와 주문 내역 등 모든 보호 경로가 막힘. 프록시 리다이렉트, httpOnly 쿠키, 서버 렌더링과 클라이언트 만료 처리를 한 흐름으로 확인해야 함 | 필수 신규 E2E |
| 주문 완료 | 419 | 5.6% | 시작 후 미완료 142세션, 33.9% | 실제 구매 전환이 막힘. 장바구니 상태, 인증 세션, 주문 쓰기 API, `/orders` 읽기를 한 브라우저 흐름으로 확인해야 함 | 신규 E2E |
| 상품 탐색 URL 복원 | 7,514 | 100.0% | 가장 높은 빈도, 종단 이탈 38.0% | 상품 발견 접점과 URL·history·reload 경계를 잃음 | 기존 8주차 E2E 5개 재사용, 중복 신규 테스트 없음 |

### 인증을 낮은 빈도에도 붙이는 이유

인증은 상품 탐색이나 장바구니보다 세션 빈도가 낮지만, 실패 영향이 한 화면에 머물지 않는다. 미로그인 사용자의 보호 경로 진입, 로그인 응답의 httpOnly 쿠키 저장, 원래 내부 경로 복원, 서버가 읽은 세션이 반영된 보호 화면, 만료된 세션의 중앙 401 처리는 통합 테스트만으로 실제 배포 경계를 한 번에 증명할 수 없다. 로그 빈도보다 경로의 관문 역할과 실제 브라우저 연결 검증 가치가 크므로 필수로 둔다.

### 주문 완료를 붙이는 이유

주문은 빈도는 5.6%지만 시작 세션의 33.9%에서 완료가 관측되지 않았다. 시드의 시작점은 주문서 진입이므로 현재 앱의 요청 직전 계측과 수치를 직접 비교하지 않는다. 로그만으로 미완료 원인을 단정하지 않지만 구매 실패 비용은 직접적이다. 기존 통합 테스트는 장바구니, 주문 버튼, API와 주문 목록을 각각 강하게 검증하지만, 실제 httpOnly 세션을 가진 브라우저가 메모리 장바구니를 주문서로 넘기고 주문을 생성한 뒤 사용자별 주문 목록을 읽는 전체 경계는 아직 없다.

### 높은 빈도인데 새 E2E를 붙이지 않는 경로

- 상품 탐색은 정제 후 7,514세션으로 가장 높지만 8주차 `e2e/week08-product-list.spec.ts`가 URL 재진입, history 뒤로·앞으로, reload, 잘못된 페이지 보정과 장바구니 헤더 왕복을 production build에서 이미 검증한다. 같은 단언을 Week 9 파일에 복제하지 않고 기존 테스트를 선택 범위에 포함해 재사용한다.
- 장바구니는 1,309세션으로 세 번째지만 담기·빼기·헤더 개수는 기존 E2E와 통합 테스트가 검증한다. 주문서로 이어지는 경계는 선택한 주문 완료 시나리오가 포함하므로 독립 E2E를 만들지 않는다.
- 찜은 480세션으로 선택한 주문 419세션보다 많이 관측됐지만 독립 E2E를 붙이지 않는다. 현재 전용 찜 화면이나 다음 단계가 없고, 버튼 상태·헤더 개수·로그아웃 정리는 빠른 store 및 통합 테스트가 모두 검증한다. 빈도가 더 높아도 브라우저 고유 경계와 실패 비용이 작은 사례다.

### 4단계에 들어갈 정확한 시나리오

다음 외에는 Week 9 E2E를 추가하지 않는다.

1. 미로그인으로 query가 있는 `/checkout` 진입 → 로그인 → 외부 주소가 아닌 원래 전체 내부 경로 복원
2. 워커별 저장 로그인 상태와 `scenario=expired` 쿠키로 `/orders` 진입 → `GET /api/orders` 401 → 중앙 만료 처리 → `/login?reason=expired&returnTo=%2Forders`와 만료 안내 확인
3. 저장 상태 없이 잘못된 자격 증명 제출 → 오류 안내, 로그인 화면 유지, 보호 경로 미진입
4. 워커별 `storageState`로 로그인된 사용자 → 상품 담기 → 주문서 → 주문 생성 응답의 새 `order.id` 캡처 → `/orders`에서 바로 그 ID의 주문 확인
5. 기존 `e2e/week08-product-list.spec.ts`의 상품 탐색 5개를 변경 없이 함께 실행

인증 자체를 증명하는 1번과 3번은 `storageState`를 사용하지 않는다. 2번과 4번은 한 번 생성한 워커별 `storageState`를 재사용한다. 주문 데이터를 쓰는 테스트는 워커마다 다른 계정을 사용하고, 저장 파일도 `parallelIndex` 기준으로 분리한다. 모든 대기는 URL, 응답, 역할·이름 기반의 가시 상태로 하고 시간 기반 sleep을 사용하지 않는다.

### 유지보수 비용 추정

대표로 “미로그인 `/checkout` → 로그인 → 원래 경로 복원” 시나리오를 추정한다.

| 변경 종류 | 예상 수정 지점 |
| --- | ---: |
| 로그인 폼의 접근 가능한 필드·버튼 이름 변경 | 공통 로그인 조작 함수 3개 locator |
| 로그인 페이지 제목 변경 | 도착 상태 assertion 1개 |

locator를 역할과 이름 기반 helper로 모으면 동일한 폼을 쓰는 세 테스트에서 각각 고치지 않고 공통 1~3곳을 수정한다. 반대로 접근 가능한 필드·버튼 이름과 복귀 URL 계약을 동시에 바꾸면 표에 적은 약 5개 지점을 수정할 것으로 예상한다. DOM 계층이나 CSS class에는 의존하지 않는다.

## D. E2E 구현과 실행 증거

### 계정과 저장 상태 경계

인증 setup은 로그인 API를 직접 호출하지 않고 `/login` 화면에서 이메일과 비밀번호를 입력하고 `로그인` 버튼을 누른 뒤, `로그아웃` 버튼이 보이는 상태를 저장한다. setup 테스트 네 개는 실행 worker 수와 무관하게 명시적인 계정 인덱스 0~3을 사용해 `test-results/.auth/worker-0.json`부터 `worker-3.json`까지 만든다. 이 경로는 기존 `/test-results` 규칙으로 Git에서 제외된다.

실제 인증 테스트의 `workerAccount`와 `authenticatedPage`는 모두 같은 `testInfo.parallelIndex`를 사용한다. 인증 context는 해당 인덱스의 `storageState`만 읽고 테스트가 끝나면 닫힌다. 미로그인 복원과 잘못된 자격 증명 테스트는 기본 `page`를 사용해 저장 상태를 읽지 않으며, 만료와 주문 테스트만 `authenticatedPage`를 사용한다. 주문 쓰기는 worker별 계정으로 격리하고, 이전 실행의 주문이 남아 있어도 이번 `POST /api/orders` 응답에서 받은 정확한 `order.id`를 주문 목록에서 확인한다.

locator는 접근 가능한 label, role과 name을 사용한다. URL, HTTP method·status가 맞는 응답, 가시 요소를 대기 조건으로 사용했으며 `waitForTimeout`이나 시간 기반 sleep은 사용하지 않았다.

### 안정성 행렬

2026-09-04에 production server를 사용하는 `playwright.week09.config.ts` 전체 선택 범위를 아래 순서로 실행했다. 실행은 겹치지 않게 하나씩 완료한 뒤 다음 명령을 시작했다.

| 실행 조건 | 결과 | Playwright 보고 시간 |
| --- | ---: | ---: |
| `--workers=1` | 16/16 통과 | 27.3초 |
| `--workers=4` | 16/16 통과 | 12.6초 |
| `--workers=4 --repeat-each=3` | 40/40 통과 | 28.6초 |

반복 실행이 48개가 아니라 40개인 이유는 dependency인 인증 setup 4개는 한 번만 실행되고, 나머지 12개가 세 번씩 실행되기 때문이다. 세 실행 모두 retry 없이 통과했다.

### 실제 실패 trace 확인

잘못된 비밀번호 시나리오의 가시 오류 assertion을 실제 문구 `이메일 또는 비밀번호를 확인해주세요.`에서 `의도적으로 틀린 오류 메시지`로 잠시 바꾸고, 해당 테스트를 workers 1과 `--trace=on`으로 실행했다. 인증 setup 4개는 통과했고 대상 테스트는 의도한 `toBeVisible` 5초 timeout으로 실패했다. 생성된 `trace.zip`은 196,465 bytes였으며 `playwright show-trace`로 열어 trace viewer가 제공되는 것을 확인했다.

실패 시점의 URL은 `/login?returnTo=%2Forders`였고, 화면에는 입력한 계정과 `wrong-password`, 실제 alert `이메일 또는 비밀번호를 확인해주세요.`가 남아 있었다. 따라서 앱은 로그인 `POST`의 401 처리와 오류 렌더링까지 완료했으며, 이 의도적 테스트 실패는 실제 alert와 불일치하는 locator에서 발생했다. assertion을 즉시 원래 문구로 되돌린 뒤 같은 focused 실행에서 setup 4개와 대상 테스트 1개가 모두 통과했다(5/5, 9.5초). 첫 trace 명령은 직전 production server가 3109 포트를 잠시 점유해 테스트 본문 전에 종료됐으며, listener가 사라진 뒤 동일 명령을 다시 실행해 위 trace를 수집했다.

### 변이 실험

선택한 E2E가 의도한 배포 경계의 회귀를 실제로 검출하는지 확인하려고 production 코드 한 줄씩만 임시로 바꿨다. 실험 중 테스트 코드는 바꾸지 않았으며, 각 RED를 관찰한 직후 production 코드를 원복했다.

| # | 망가뜨린 곳 | 어떻게 바꿨나 | 결과 | 실패한 테스트 | 실패 메시지로 원인을 알 수 있었나 |
| ---: | --- | --- | --- | --- | --- |
| 1 | 로그인 응답의 세션 쿠키 `Path` | `path: '/'`를 `path: '/api/auth'`로 축소 | 잡힘 | setup 4개가 `auth.setup.ts:16`에서 실패했고, `--no-deps` 미로그인 복원은 `auth.spec.ts:50`에서 실패 | 부분 가능. 로그인 뒤 `주문서` heading이 없다는 단절 지점은 알 수 있지만, 메시지만으로 잘못된 `Path` 값까지 특정할 수는 없어 cookie 저장 상태를 함께 확인해야 했다. |
| 2 | `/checkout` 미로그인 redirect | 원래 `returnTo` 대신 `/`를 인코딩 | 잡힘 | `auth.spec.ts:40`의 `toHaveURL` | 가능. 기대 URL은 `http://localhost:3109/login?returnTo=%2Fcheckout%3Fcoupon%3Dwelcome`, 실제 URL은 `http://localhost:3109/login?returnTo=%2F`로 표시돼 query 포함 복원 경로가 사라진 것을 바로 구분했다. |
| 3 | 보호 API의 중앙 만료 처리 조건 | HTTP `401` 비교를 `403`으로 변경 | 잡힘 | `auth.spec.ts:73`의 `toHaveURL` | 가능. 기대 URL은 만료 안내 로그인 경로였고 실제 URL은 `http://localhost:3109/orders`여서 401 뒤 중앙 탐색이 실행되지 않은 것을 구분했다. |
| 4 | 로그인 응답의 세션 쿠키 `Domain` | `domain: 'example.com'` 한 줄 추가 | 빠른 테스트에서는 살아남음, E2E에서 잡힘 | 빠른 route 테스트 11/11 통과. setup 4개와 `--no-deps` 미로그인 복원의 `auth.spec.ts:50` 실패 | 부분 가능. 로그인 뒤 서버 인증 화면이 없다는 것은 알 수 있지만, heading timeout만으로 Domain 부적합까지 특정할 수는 없다. 브라우저 cookie 적용 상태와 응답 옵션을 함께 봐야 했다. |
| 보조 | 상품 목록 URL history | `push`를 `replace`로 변경 | 잡힘 | `week08-product-list.spec.ts:43` | 가능. 뒤로가기 후 `fashion`이 아니라 `카테고리` combobox 자체가 없어, 상품 목록 history entry가 사라졌음을 확인했다. 인증 변이 3개 계산에는 포함하지 않았다. |

첫 두 변이를 모두 원복한 뒤 두 production 파일의 diff가 0임을 확인하고 원본 production build와 인증 focused 실행을 다시 수행했다. build는 성공했고 setup 4개와 인증 테스트 3개가 7/7로 통과했다(11.2초). 세 번째 변이도 즉시 `401`로 원복해 대상 production 파일의 diff가 0임을 확인했다. 원본 production build 성공 후 setup 4개와 만료 테스트가 5/5로 통과했다(9.2초). 따라서 최종 production 코드에는 세 인증 변이가 모두 남아 있지 않다.

`Domain` 변이도 관찰 직후 한 줄을 제거하고 해당 옵션이 남아 있지 않음을 확인했다. 원본 production build와 관련 빠른 route 테스트 11/11이 다시 통과했고(652ms), 정식 dependency를 포함한 미로그인 복원 focused 실행도 setup 4개와 대상 1개가 모두 통과했다(5/5, 9.3초). 앞의 `path`, `returnTo`, 중앙 401 조건 변경 세 개가 인증 구현 변이 최소 3개를 충족한다. 추가 `Domain` 변경은 현재 빠른 테스트가 해당 속성을 단언하지 않아 살아남았지만 실제 브라우저 적용 단계에서 E2E가 실패한 항목이다. Domain 설정값 자체는 빠른 테스트로도 추가 검증할 수 있으며, 여기서 확인한 E2E의 가치는 브라우저의 쿠키 저장·전송과 보호 화면의 서버 렌더링이 실제로 연결되는지 검증한 데 있다.

상품 목록 URL 상태의 history 방식을 `push`에서 `replace`로 바꾸는 보조 변이도 별도로 수행했다. production build는 성공했지만 기존 8주차 뒤로·앞으로 테스트가 `week08-product-list.spec.ts:43`에서 실패했다. `fashion` 값을 기대했으나 `page.goBack()` 뒤 `카테고리` combobox 자체를 5초 동안 찾지 못했다. 변이를 즉시 원복하고 대상 production 파일의 diff가 0임을 확인했으며, 원본 build 후 같은 테스트가 1/1로 통과했다(테스트 970ms, 전체 3.5초). 이 보조 변이는 기존 상품 탐색 E2E 재사용의 가치를 확인한 것이며, 과제가 요구한 인증 구현 변이 3개에는 포함하지 않는다.

### 초기 HTML과 쿠키 경계 확인

portable Node 22의 `fetch`로 production 로그인 요청과 세션 쿠키를 사용한 홈 document 요청을 차례로 보냈다. 응답은 `loginStatus=200`, `homeStatus=200`이었고, 31,529자인 raw response HTML에서 `루퍼1`과 `로그아웃`은 각각 확인됐으며 현재 markup의 비로그인 action 표식인 `>로그인<`은 발견되지 않았다. 브라우저 JavaScript가 실행된 뒤의 DOM이 아니라 서버가 반환한 HTML 원문을 검사한 결과이므로, 서버 응답 원문에 인증 사용자용 표식이 포함됨을 직접 확인했다.

`HttpOnly`와 `SameSite` 같은 세션 쿠키 속성 자체는 route test가 `Set-Cookie` 계약으로 검사한다. E2E는 UI 로그인 응답 뒤 실제 브라우저에 형성된 세션이 보호 요청에 적용되고, `Path`에 따른 전송 결과가 서버 렌더링까지 이어지는지를 검사한다. 두 레벨의 보증 범위를 구분하며 E2E가 모든 쿠키 속성을 직접 단언한다고 주장하지 않는다.

### AI 사용 범위

요구사항 정리, 구현 후보 도출, 반복적인 테스트·fixture 작성과 정상·적대적 리뷰에 AI를 사용했다. 최종 E2E 범위와 각 테스트가 지킬 단언, 로그를 근거로 한 포함·제외 결정, 실제 검증 결과의 채택은 사용자가 검토하고 승인해 확정했다.

## 결정 요약

- 세션 빈도는 E2E 필요조건이 아니다.
- 인증은 낮은 빈도지만 관문 역할과 브라우저 고유 경계 때문에 필수다.
- 주문 완료는 구매 실패 비용과 분리된 경계의 연결 가치 때문에 추가한다.
- 상품 탐색은 가장 높지만 기존 8주차 E2E를 재사용하고 중복 테스트를 만들지 않는다.
- 장바구니와 찜은 빠른 통합 테스트를 유지하고 독립 E2E를 추가하지 않는다.
- 4단계는 이 문서에 적힌 범위를 늘리지 않는다.
