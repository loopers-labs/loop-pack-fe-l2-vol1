# 9주차 E2E 범위 설계

## A. 이벤트 스키마

### A-1. 계측 대상

| 이벤트                   | 언제                              |
| ------------------------ | --------------------------------- |
| `product_list_view`      | 상품 목록 화면에 처음 들어왔을 때 |
| `category_filter_change` | 카테고리를 바꿨을 때              |
| `sort_change`            | 정렬을 바꿨을 때                  |
| `page_change`            | 페이지를 옮겼을 때                |
| `cart_add`               | 상품을 장바구니에 담았을 때       |
| `wishlist_add`           | 상품을 찜했을 때                  |
| `login_start`            | 로그인 화면에 들어왔을 때         |
| `login_success`          | 로그인에 성공했을 때              |
| `login_fail`             | 로그인에 실패했을 때              |
| `order_start`            | 주문서 화면에 들어왔을 때         |
| `order_complete`         | 주문이 접수되었을 때              |

제외 대상

| 시드 로그 이벤트      | 현재 서비스                                                           | 판단 |
| --------------------- | --------------------------------------------------------------------- | ---- |
| `product_detail_view` | 상품 상세 화면 없음. 목록에서 바로 담음                               | 제외 |
| `client_error`        | 시드의 `IMAGE_LOAD_FAILED`에 대응하는 오류 처리 계약이 현재 앱에 없음 | 제외 |

**제외 기준**

시드 이벤트와 같은 의미로 대응할 수 있는 화면이나 처리 계약이 현재 서비스에 없는 이벤트는 제외한다. 없는 화면이나 없는 오류 처리를 계측을 위해 새로 만들지 않는다.

### A-2. 이벤트 이름

시드 로그의 이름을 그대로 쓰기로 결정

기존 로그와 같은 행동을 같은 이름으로 집계할 수 있도록 시드 로그의 이벤트 이름을 그대로 사용한다. 시드에 없는 새 이벤트를 만들지 않으므로 별도의 이름 규칙은 정의하지 않는다.

로그를 열어보는 시점은 대개 이슈가 생겼을 때다. 이름이 다르면 변환표를 옆에 두고 대조하며 읽어야 해서, 원인을 좁혀야 하는 상황에 확인 단계가 하나 더 붙는다.

이름 문자열은 `src/analytics/events.ts` 한 곳에 상수로 둔다.

### A-3. 공통 프로퍼티

`setCommonProperties()`를 사용한다.

| 이름        | 값                                | 만드는 방법                                                     |
| ----------- | --------------------------------- | --------------------------------------------------------------- |
| `sessionId` | `s_` + 임의 문자열                | 탭을 열 때 발급해 `sessionStorage`에 둔다. 탭을 닫으면 사라진다 |
| `ts`        | ISO 8601 문자열                   | `track()`이 불린 시각                                           |
| `device`    | `mobile` · `tablet` · `desktop`   | 화면 폭으로 가른다                                              |
| `userId`    | 그 시점에 인증돼 있던 사용자의 id | 로그인한 동안에만 붙는다. 로그인 전에는 키 자체가 없다          |

**세션은 탭 단위**

이번 과제에서 분석하는 것은 한 탭에서 로그인부터 주문까지 이어지는 흐름이다. 그래서 탭이 유지되는 동안 같은 `sessionId`를 쓰고, 탭이 닫히면 끝나는 단위로 정의했다.

무활동 30분 기준도 검토했으나, 마지막 활동 시각을 계속 갱신하고 만료를 판정하는 로직이 따라붙어 이번 분석 범위에는 넣지 않았다.

**`userId`는 로거가 자동으로 붙여주지 않는다**

로거의 `identify()`는 프로바이더에 사용자를 알리기만 하고, 그 뒤의 `track()`에 `userId`를 넣지는 않는다. 시드 로그는 `login_success` 이후 이벤트에 `userId`를 담고 있어, 같은 자리에 같은 값을 남기려면 공통 프로퍼티가 그 값을 함께 내보내야 한다.

| 무엇               | 하는 일                                                                                                  |
| ------------------ | -------------------------------------------------------------------------------------------------------- |
| 공통 프로퍼티 평가 | 이벤트가 발생하는 시점에 세션 상태를 읽어, 로그인한 사용자가 있으면 `userId`를 붙인다                    |
| 이벤트 직전 동기화 | 같은 세션 상태를 읽어 프로바이더가 아는 사용자와 비교하고, 달라졌을 때만 `identify()`·`reset()`을 부른다 |

**`userId`가 붙는 범위**

`userId`는 "그 이벤트가 일어난 시점에 인증돼 있던 사용자"를 뜻한다. 이벤트마다 예외를 두지 않는다.

| 상황                                             | `userId` |
| ------------------------------------------------ | -------- |
| 로그인하지 않은 상태의 모든 이벤트               | 없음     |
| 로그인 성공 이후의 모든 이벤트                   | 붙는다   |
| 로그인하지 않은 상태의 `login_fail`              | 없음     |
| 로그인한 사용자가 재로그인에 실패한 `login_fail` | 붙는다   |
| 로그아웃·만료 이후의 모든 이벤트                 | 없음     |

마지막 두 줄이 갈리는 지점이다. 서비스 정책상 로그인한 사용자도 로그인 화면에 직접 들어올 수 있어서, 그 상태에서 다른 계정으로 로그인하다 실패하면 기존 사용자가 붙는다. `userId`를 실패한 자격 증명의 주인으로 읽으면 어긋나 보이지만, 이 값은 그런 뜻이 아니다. 이벤트 하나에만 예외를 두면 로그를 읽을 때마다 "이 이벤트는 예외였나"를 확인해야 한다.

**시드 로그와 같은 것은 필드의 의미다**

시드 JSONL은 `sessionId`·`ts`·`userId`·`device`를 `name`·`props`와 나란히 최상위에 둔다. 스타터 로거는 공통 프로퍼티와 이벤트별 프로퍼티를 `properties` 하나로 합쳐 프로바이더에 넘긴다. 이 문서에서 "시드 로그와 같다"고 할 때 가리키는 것은 값의 의미와 이름이지 중첩 구조가 아니다.

**`device` 경계**

| 화면 폭               | 값        |
| --------------------- | --------- |
| 720px 미만            | `mobile`  |
| 720px 이상 960px 미만 | `tablet`  |
| 960px 이상            | `desktop` |

userAgent로 기기를 판별하면 문자열 규칙을 직접 관리해야 하고 새 기기가 나올 때마다 규칙이 늘어난다.

그래서 실제 기기 종류가 아니라 계측 시점의 viewport 너비를 기준으로 구분했다. 경계값 720px·960px은 `layout.css`에서 그리드 열 수가 바뀌는 지점과 같다. 창을 줄인 데스크톱은 `mobile`로 잡히는데, 이 값으로는 기기를 특정할 수 없다.

### A-4. 이벤트별 프로퍼티

| 이벤트                   | props                                  |
| ------------------------ | -------------------------------------- |
| `product_list_view`      | `category` · `sort` · `page`           |
| `category_filter_change` | `category`                             |
| `sort_change`            | `sort`                                 |
| `page_change`            | `page`                                 |
| `cart_add`               | `productId` · `quantity`               |
| `wishlist_add`           | `productId`                            |
| `login_start`            | `from` — 로그인 후 돌아갈 경로         |
| `login_success`          | `from` — 로그인 후 돌아갈 경로         |
| `login_fail`             | `reason` — 실패의 종류 (네 값)         |
| `order_start`            | `productIds` · `itemCount`             |
| `order_complete`         | `orderId` · `productIds` · `itemCount` |

**`from`에 넣는 값**

| 진입 경로                 | `from`                           |
| ------------------------- | -------------------------------- |
| 보호 경로에서 되돌려짐    | 검증을 마친 `next`의 경로와 쿼리 |
| 로그인 화면에 직접 진입   | `/`                              |
| `next`가 검증을 통과 못함 | `/`                              |

복원 경로에 쓰는 것과 같은 검증을 거친 값이다. 외부 주소나 로그인 경로가 들어오면 홈으로 떨어지므로 로그에도 홈으로 남는다.

**가격은 남기지 않는다**

주문 API에서 가격 입력을 받았을 경우, 주문 시점의 가격을 로그에 남기는 것이 맞다고 판단되었다. 담았을 때의 가격과 실제로 주문하려는 시점의 가격이 어드민에서의 상품 가격 변경으로 상이할 수 있기 때문이다.

하지만, 현재 이 프로젝트에서 주문 API는 가격 입력을 받지도, 검증하지도 않는다.

이를 기록으로 남기게 되면 오히려 서비스 동작이 달라지므로 계측하지 않기로 했다.

담기와 찜에 `price`를 더하는 방안도 검토했다. 버튼 호출부가 값을 이미 갖고 있어 구현 부담은 작다. 다만 시드 스키마에 없는 프로퍼티를 늘리는 쪽이고, 담은 가격이 남아도 주문 확정 금액이 없어 매출과 이을 수 없다. 가격을 쓰는 분석 질문이 정해지면 그때 더한다.

### A-5. 시드 로그와의 차이

이름은 같으나 값의 모양이 다른 곳이다.

| 이벤트                           | 시드 로그                     | 기록할 값                  | 이유                                                                                                                                                                        |
| -------------------------------- | ----------------------------- | -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cart_add`                       | `quantity` 1·2                | 항상 `1`                   | 담기에 수량 개념이 없다. 같은 상품을 여러 번 담아도 1개다                                                                                                                   |
| `order_start` · `order_complete` | `productId` 하나              | `productIds` · `itemCount` | 장바구니 전체를 한 번에 주문한다. 주문 한 건을 한 줄로 남겨야 "몇 건이 주문됐나"를 그대로 셀 수 있다                                                                        |
| `order_complete`                 | `totalPrice`                  | **없음** (대신 `orderId`)  | 주문 API가 금액을 받지도 검증하지도 응답하지도 않아 확정 금액이라 부를 값이 없다                                                                                            |
| `login_start` · `login_success`  | `from: cart`                  | `from`에 경로와 쿼리       | 시드는 진입 지점을 이름으로 남겼다. 현재 앱은 `next`로 돌아갈 경로를 이미 들고 있어 그 값을 그대로 쓴다                                                                     |
| `login_fail`                     | `reason: INVALID_CREDENTIALS` | 아래 네 값                 | 화면 문구는 사유를 나누지 않는다(가입된 이메일이 드러난다). 로그까지 하나로 묶으면 서버 장애로 실패한 것과 비밀번호를 틀린 것을 나중에 나눌 수 없어, 로그에는 종류를 남긴다 |

**`login_fail`의 `reason`**

| 값                    | 언제                                                                 |
| --------------------- | -------------------------------------------------------------------- |
| `INVALID_CREDENTIALS` | 서버가 401로 답했다 — 자격 증명이 맞지 않는다                        |
| `SERVER_ERROR`        | 서버가 그 밖의 상태 코드로 실패를 답했다                             |
| `NETWORK_ERROR`       | 요청을 보내지 못해 응답 자체가 없다                                  |
| `UNKNOWN_ERROR`       | 응답은 받았으나 다룰 수 없었다 — 본문 파싱 실패나 예상하지 못한 오류 |

마지막 두 값을 나눈 이유는 응답을 받았는지 여부가 다르기 때문이다. 본문을 읽지 못한 경우까지 `NETWORK_ERROR`로 적으면 "응답을 받지 못한 경우"라는 정의가 무너지고, 로그를 보고 네트워크 장애를 찾게 된다.

### A-6. 화면 진입의 발생 단위

> 해당 경로에 들어와 화면이 처음 표시될 때 한 번 기록한다. 같은 화면에서 조건만 바뀌면 다시 기록하지 않고 조건 변경 이벤트로 기록한다.

| 상황                        | `product_list_view`                       |
| --------------------------- | ----------------------------------------- |
| 목록에 처음 들어옴          | 보낸다                                    |
| 카테고리·정렬·페이지를 바꿈 | 보내지 않는다 — 조건 변경 이벤트로 남는다 |
| 검색어를 바꿈               | 보내지 않는다 — 아무 이벤트도 남지 않는다 |
| 새로고침                    | 보낸다 (새 진입으로 본다)                 |
| 뒤로 가기로 목록에 돌아옴   | 보낸다                                    |
| 다른 화면 갔다가 다시 옴    | 보낸다                                    |
| React 재렌더링              | 보내지 않는다                             |
| 개발 환경의 중복 실행       | 보내지 않는다                             |

시드 로그를 이 기준으로 읽었다. `product_list_view`의 `category`·`sort`·`page`가 전부 기본값 한 종류뿐이고, 조건이 바뀐 경우는 `category_filter_change`·`sort_change`·`page_change`로만 남아 있다.

검색어 변경은 시드 스키마에 대응하는 이벤트가 없어 계측하지 않는다. 검색 결과가 바뀌어도 `product_list_view`를 다시 기록하지 않으므로, 검색만 한 세션에는 목록 진입 한 줄만 남는다.

`login_start`·`order_start`도 같은 규칙을 따른다.

### A-7. 호출 순서

**초기화**

```
sessionId 준비 → provider 등록 → 공통 프로퍼티 설정 → initAnalytics
```

첫 화면 이벤트보다 먼저 끝나야 한다. `track()`은 불린 시점의 공통 프로퍼티를 이벤트에 합쳐 큐에 넣기 때문에, 초기화가 늦으면 그 이벤트는 `sessionId` 없이 남고 나중에 되살릴 수 없다.

화면 진입 이벤트는 화면 컴포넌트의 effect에서 나가고, React는 자식의 effect를 부모보다 먼저 실행한다. 그래서 공통 부모 컴포넌트 안에 두면 어느 자리든 늦다. 렌더 중에 실행하는 방법도 있으나, 버려지는 렌더에서도 모듈 상태가 바뀌어 되돌릴 수 없다. 모듈이 로드될 때 한 번 실행해 첫 렌더보다 앞세운다.

**로그인 성공**

```
세션 상태 갱신 → login_success → 원래 경로로 이동
```

`identify()`를 따로 부르지 않는다. 이벤트를 보내는 자리가 세션 상태를 읽어 프로바이더와 맞추므로, `login_success`가 프로바이더에 닿기 전에 사용자가 먼저 전달된다. 순서에서 중요한 것은 세션 상태를 먼저 채우는 것뿐이다 — 뒤로 미루면 `userId`도 `identify()`도 함께 빠진다. 자세한 것은 A-3에 있다.

**로그인 실패**

```
login_fail
```

로그인하지 않은 상태에서 실패했다면 세션이 만들어지지 않아 `userId`가 붙지 않는다. 이미 로그인한 사용자가 재로그인에 실패한 경우는 그 사용자가 붙는다 — 범위는 A-3에 있다. `reason`은 실패의 종류를 따라간다.

**로그아웃**

```
로그아웃 응답 확인 → 세션 상태 비우기 → 프로바이더 동기화 → 홈으로 이동
```

로그아웃은 시드 로그에 없는 이벤트라 계측하지 않는다. 이후 이벤트에서 `userId`를 떼는 것은 세션 상태를 비우는 쪽이다. 뒤따르는 이벤트가 없으면 동기화도 일어나지 않아 프로바이더가 이전 사용자를 붙들고 있게 되므로, 여기서는 한 번 직접 맞춘다.

서버가 실패로 답하면 어느 쪽도 하지 않는다 — 세션은 서버에 남았는데 로그에서만 사용자가 사라지면 두 기록이 어긋난다.

세션 만료는 로그아웃 버튼을 거치지 않지만, 만료를 처리하는 자리에서 세션 상태가 비워지고 그다음 이벤트가 프로바이더까지 맞춘다.

**남겨 두는 것 — 동기화 실패의 재시도**

스타터 로거는 프로바이더가 던진 예외를 자기 안에서 잡고 넘어간다. 그래서 `identify()`나 `reset()`이 실패해도 부른 쪽은 알 수 없고, 다음 이벤트에서는 이미 알린 사용자로 보여 다시 시도하지 않는다. 실제 분석 SDK가 일시적으로 실패하면 그 뒤로 사용자 연결이 계속 빠질 수 있다.

이번 과제에서 붙이는 프로바이더는 콘솔 하나뿐이라 여기까지는 다루지 않는다. 다만 알린 사용자를 기록하는 시점은 호출 뒤로 두어, 로거가 실패를 알리도록 바뀌면 그때 재시도가 성립하게 했다. 프로바이더가 여럿일 때 어느 쪽이 실패했는지 가리려면 알린 사용자를 프로바이더별로 나눠 들고 있어야 하는데, 그것도 지금 범위 밖이다.

### A-8. 계측 코드의 위치

이벤트 종류별로 호출 지점을 정한다. 화면 컴포넌트가 로거를 직접 알지 않게 한다.

| 이벤트 종류                                                     | 호출 지점                      |
| --------------------------------------------------------------- | ------------------------------ |
| 화면 진입 — `product_list_view` · `login_start` · `order_start` | 화면 진입 전용 훅              |
| 사용자 행동 — `cart_add` · `wishlist_add` · 조건 변경 3개       | 상태 변경이 확정되는 지점      |
| 요청 결과 — `login_success` · `login_fail` · `order_complete`   | mutation의 성공·실패 처리 지점 |

이벤트 이름과 프로퍼티 조립은 `src/analytics` 안에 둔다. 이 분리는 약속이 아니라 규칙으로 둔다 — `src/analytics`를 boundaries의 별도 요소로 등록해, 화면 계층이 계측을 참조하는 방향만 열고 반대 방향을 막았다.

| 방향                                         | 허용 여부                                                               |
| -------------------------------------------- | ----------------------------------------------------------------------- |
| `app` · `widgets` · `features` → `analytics` | 허용 — 화면이 계측을 부르는 방향                                        |
| `analytics` → `shared`                       | 허용                                                                    |
| `analytics` → `entities`                     | 타입 전용만 허용 — 이벤트 프로퍼티가 도메인 용어를 그대로 쓰기 위해서다 |
| `analytics` → `app` · `widgets` · `features` | 금지 — 계측이 화면 로직을 끌고 들어오는 방향                            |
| `entities` · `shared` → `analytics`          | 금지                                                                    |

세 방향에 위반을 주입해 실제로 걸리는 것을 확인했다.

세션을 어디서 읽는지는 계측이 알지 않는다. 그 연결은 앱 계층의 `src/app/analyticsBootstrap.ts`가 맡는다.

`order_start`는 저장된 장바구니가 되살아난 뒤에 기록한다. 담은 목록은 `sessionStorage`에 있어 hydration 이후에 복원되는데, 마운트하자마자 기록하면 새로고침한 주문서가 빈 목록으로 남는다. 복원을 렌더 단계로 당기면 서버 HTML과 첫 렌더가 어긋나므로, 복원 시점은 그대로 두고 이 이벤트가 스토어의 복원 완료 신호를 기다린다.

`cart_add`는 버튼을 누른 시점이 아니라 **담기지 않은 상태에서 담긴 상태로 바뀐 때** 기록한다. `wishlist_add`도 동일하다.

조건 변경 3개는 **URL이 갱신된 뒤에** 기록한다. 갱신 전에 기록하면 갱신되지 않은 시도까지 남긴다. 그리고 같은 값을 다시 고른 경우는 바뀐 것이 없어 기록하지 않는다.

### B-2. 정제 기준

세 가지를 각각 다르게 다룬다. 같은 방식으로 지우면 남는 데이터의 의미가 달라진다.

| 처리 대상   | 기준                                                            | 처리 방법                           | 영향    |
| ----------- | --------------------------------------------------------------- | ----------------------------------- | ------- |
| 자동화 의심 | `device` 누락 **+** 이벤트 1개 **+** `product_list_view`만      | 세션 전체를 모집단에서 제외         | 486세션 |
| 중복 전송   | 같은 세션·같은 이름·같은 props가 2초 이내 재발생 (담기·찜 제외) | 첫 번째만 남김 (세션은 유지)        | 77건    |
| 오류 이벤트 | `client_error`                                                  | 제거하지 않음. 경로 순위에서만 제외 | 103세션 |

**자동화 의심 세션**

> `device`가 없고, 이벤트가 `product_list_view` 하나뿐인 486세션을 자동화 의심 세션으로 분류해 경로 분석에서 제외한다. 실제 사용자의 즉시 이탈일 가능성도 있으므로, 정제 전후 결과를 함께 비교한다.

**왜 이 조합을 의심하는가**

- `device`가 없다
- 이벤트가 `product_list_view` 하나뿐이다
- 30일 내내 UTC 01시에만 시작한다
- 타임스탬프의 밀리초가 486건 모두 `.000`이다
- 조회 조건이 `category=all·sort=latest·page=1` 한 종류다

조건 하나만으로는 근거가 되지 않는다. `device` 누락만 보면 계측이 빠진 것일 수 있고, 이벤트가 하나뿐인 것만 보면 목록만 보고 바로 나간 사람일 수 있다. 즉시 이탈한 사용자도 목록 이벤트 하나만 남긴다.

`device`가 왜 비었는지는 시드로 알 수 없다. 현재 앱은 화면 폭으로 그 값을 정하지만(A-3), 시드를 만든 환경이 같은 방식이었는지 확인할 방법이 없다. 그래서 `device` 누락을 "화면을 그리지 않았다"는 증거로 쓰지 않고, 위 다섯 신호가 겹친다는 사실만 근거로 삼는다.

| 관찰      | 자동화 의심 486세션                       | 나머지             |
| --------- | ----------------------------------------- | ------------------ |
| 시작 시각 | 30일 내내 UTC 01시에만                    | 24개 시간대에 분포 |
| 밀리초    | 486건 전부 `.000`                         | 21,941건 중 27건   |
| 조회 조건 | 1종류 (`category=all·sort=latest·page=1`) | —                  |

**중복 전송**

같은 `sessionId`에서 같은 이벤트 이름이 같은 props로 2초 안에 다시 나오면 **첫 번째만 남기고 나머지를 뺀다.** 세션은 그대로 두고 그 이벤트만 뺀다.

판정 기준은 A절의 발생 단위 계약에서 온다. 현재 앱은 화면 진입을 처음 한 번만, 조건 변경을 값이 실제로 바뀔 때만 기록한다(A-6·A-8). 시드에서 같은 이름과 같은 props가 연달아 나온 것은 그 계약대로라면 한 번으로 남았을 사건이다.

2초는 직접 고른 값이다. 실제로 걸린 77건은 전부 1초 미만 간격이라 1초로 잡아도 결과가 같지만, 값을 고른 것은 사실이므로 기준으로 밝혀 둔다.

**`cart_add`·`wishlist_add`에는 이 규칙을 적용하지 않는다.** 담기와 찜은 뺐다가 다시 담는 조작이 2초 안에 실제로 일어날 수 있다. 같은 값이 다시 나온 것이 계측 중복인지 사용자의 조작인지 로그로는 가릴 수 없어, 지우지 않는 쪽을 택한다.

**오류 이벤트**

`client_error`는 세 가지로 나눠 다룬다.

| 어디에서              | 어떻게                                            |
| --------------------- | ------------------------------------------------- |
| 정상 경로 순위        | 제외한다 — 사용자가 지나는 경로가 아니다          |
| 오류 경험률           | 포함한다 — 실패 비용을 계산할 근거다              |
| 오류가 난 세션의 행동 | 그대로 둔다 — 목록 진입·담기·주문을 지우지 않는다 |

세 번째가 판단이 필요한 부분이다. 시드의 `client_error` 103건은 **전부 `IMAGE_LOAD_FAILED`** 하나뿐이다. 이미지가 뜨지 않아도 목록을 보고 상품을 담고 주문하는 일은 그대로 이어지므로, 사용자 흐름에서 치명적인 오류로 보기 어렵다. 오류가 하나 섞였다고 그 세션의 나머지 행동까지 노이즈로 버리면, 실제로 일어난 담기와 주문이 집계에서 사라진다.

|               | 오류를 겪은 세션 (103) | 전체 (7,514) |
| ------------- | ---------------------: | -----------: |
| 담기까지 감   |                  29.1% |        17.4% |
| 주문서까지 감 |                   8.7% |         5.6% |
| 주문을 마침   |                   8.7% |         3.7% |

오류를 겪은 세션이 더 깊이 진행한 이유는 로그로 알 수 없다. 오래 머물수록 이미지를 더 많이 불러 오류를 만날 확률이 높아진 것일 수도 있지만, 확인되지 않은 가능성 중 하나다. 확인되는 것은 **이 오류가 뒤따르는 행동을 끊지 않았다**는 사실까지다.

한 세션에서 `client_error`가 있다고 통째로 버리면 실패 비용을 계산할 근거도 함께 사라진다.

### B-3. 정제 전후 규모

```
세션    8,000 → 7,514
이벤트  22,427 → 21,864
```

### B-4. 정제 전후 경로 순위 (세션 기준)

이벤트 수가 아니라 세션 수로 센다. 이벤트 수로 세면 한 사람이 여러 번 한 행동이 부풀려진다.

**분모**

B-4의 경로 비율과 B-6의 비율 열은 **정제 후 7,514세션**을 분모로 쓴다. 전체 8,000세션에서 자동화 의심 486세션을 뺀 값이다.

이탈률과 실패율은 분모가 다르다 — 그 경로의 **시작 세션**을 쓴다. 전체로 나누면 로그인처럼 소수만 지나는 경로의 이탈과 실패가 실제보다 작아 보인다.

분모에서 빼는 것과 세는 대상에서 빼는 것을 나눈다.

| 처리 대상   | 분모(7,514)에서 | 순위표의 행에서 | 이유                                                              |
| ----------- | --------------- | --------------- | ----------------------------------------------------------------- |
| 자동화 의심 | 뺀다 (486세션)  | 뺀다            | 사람의 접속으로 보기 어려워 사용자 경로의 모집단이 아니다         |
| 오류 이벤트 | 빼지 않는다     | 뺀다            | 정상 경로는 아니지만 그 세션의 담기·주문은 실제로 일어난 행동이다 |
| 중복 전송   | 빼지 않는다     | 빼지 않는다     | 세션은 그대로 두고 이벤트만 지우므로 세션 수가 바뀌지 않는다      |

`client_error`를 겪은 103세션은 분모 안에 그대로 있다. 순위표에 행이 없는 것은 사용자가 지나는 경로가 아니어서이지 모집단에서 빠져서가 아니다(B-2).

중복 전송은 세션이 아니라 이벤트를 지우는 처리라 세션 기준 순위에는 영향이 없다. 그중 `cart_add`·`wishlist_add`는 중복 판정 자체를 적용하지 않아 지운 이벤트도 없다 — 뺐다가 다시 담는 조작이 2초 안에 실제로 일어날 수 있어서다(B-2).

**이 분모를 쓰는 근거가 아래 표다.** 486세션을 뺐을 때 순위가 흔들렸다면 어느 분모를 쓰느냐가 결론을 바꾼다는 뜻이라 두 값을 나란히 들고 가야 한다. 순위가 그대로이므로 이후로는 정제 후 하나만 쓴다.

- **자동화 의심 486세션**은 전부 `product_list_view` 하나만 갖고 있다. 다른 경로의 세션 수에는 애초에 들어 있지 않아서, 빼면 1위의 세션 수와 공통 분모만 줄어든다. 2위 이하가 같은 방향으로 함께 올라가므로 상대 순서가 유지된다

### B-5. 경로의 시작·완료 기준

**경로를 묶은 기준**

경로는 사용자 플로우 문서(`week09-user-flow.md`)에 그려 둔 사용자의 흐름대로 묶었다. 이벤트 이름 하나를 경로로 두면 담기와 주문 완료가 서로 무관한 행동처럼 보이는데, 실제로는 한 사람이 이어서 하는 일이고 E2E도 그 이어짐에 붙는다. 표의 한 행이 곧 E2E 하나의 후보가 되도록 단위를 맞췄다.

조건 변경 셋(`category_filter_change`·`sort_change`·`page_change`)은 "상품 탐색" 하나로 묶었다. 셋 다 목록에서 원하는 상품을 찾는 같은 행동이라 흐름에서 구분되지 않는다. 개별 값은 B-4에 이벤트 이름 단위로 남아 있다.

**시작과 완료**

경로마다 어디서 시작하고 무엇을 지나야 끝난 것으로 볼지 먼저 정한다.

| 경로           | 시작 기준           | 완료 기준        |
| -------------- | ------------------- | ---------------- |
| 상품 담기      | `product_list_view` | `cart_add`       |
| 로그인 진입    | `cart_add`          | `login_start`    |
| 로그인 회복    | `login_fail`        | `login_success`  |
| 인증 후 복원   | `login_start`       | `order_start`    |
| 주문 완료      | `order_start`       | `order_complete` |
| 전체 구매      | `cart_add`          | `order_complete` |
| 세션 만료 회복 | 시드 이벤트 없음    | 시드 이벤트 없음 |

두 경로는 끝 두 개만으로 흐름이 성립하지 않아 중간 단계도 요구한다.

| 경로         | 지나야 하는 순서                                                                |
| ------------ | ------------------------------------------------------------------------------- |
| 인증 후 복원 | `login_start` → `login_success` → `order_start`                                 |
| 전체 구매    | `cart_add` → `login_start` → `login_success` → `order_start` → `order_complete` |

명시하지 않으면 우연히 끝 두 개만 가진 세션도 완료로 잡힌다. 이 시드에서는 중간 단계를 요구해도 세션 수가 같았다 — 끝 두 개만 가진 세션이 없었다는 뜻이다.

**로그로 흐름을 세는 방법**

- 같은 세션 안에서 **완료 이벤트가 시작 이벤트보다 뒤에** 나와야 완료로 본다. 같은 세션에 둘 다 있기만 하면 되는 것으로 두면, 주문을 마치고 다시 담은 세션도 완료로 잡힌다
- 한 세션에서 같은 경로가 여러 번 나타나도 **한 번으로** 센다. 경로를 지난 사람이 몇 명인지가 알고 싶은 값이고, 몇 번 지났는지는 아니다
- 실패한 뒤 성공한 세션은 **완료로 본다.** 한 번의 실패가 그 흐름의 끝은 아니기 때문이다. 로그인은 비밀번호를 틀렸다가 고쳐서 다시 시도할 수 있고, 사용자가 하려던 일(주문)은 그 뒤에 그대로 이어진다. 실패했다는 이유로 미완료로 세면 "결국 해냈는가"를 볼 수 없다.
- 세션 만료 회복 경로는 만료를 알리는 이벤트가 시드에 없어 시작도 완료도 정의할 수 없다. 로그로 세지 못한다는 것이지 E2E 대상에서 빠진다는 뜻은 아니다.

**이탈률로 고른 정의**

이탈률은 **"다음 단계로 넘어가지 못한 비율"**을 쓴다. 시작 기준에 도달한 세션 중 같은 세션에서 완료 기준을 채우지 못한 비율이다.

비교 대상인 다른 정의는 아래 표의 **종료율**이다. 경로의 **시작 이벤트가 그 세션의 마지막 이벤트였던 비율**로 계산했다. 고른 근거를 보이려고 둔 값이라 B-6의 필수 표에는 넣지 않았다.

| 경로         | 종료율 | 이탈률 | 두 값의 차이에 해당하는 세션이 시작 뒤에 한 것 (행동별 중복 집계) |
| ------------ | -----: | -----: | ----------------------------------------------------------------- |
| 상품 담기    |  15.2% |  82.6% | 상세 보기 3,347 · 카테고리 변경 2,506 · 페이지 이동 1,450         |
| 전체 구매    |  50.8% |  78.8% | 로그인 시작 367 · 로그인 성공 309 · 주문서 진입 142               |
| 인증 후 복원 |   0.0% |  34.9% | 로그인 성공 167 · 로그인 실패 80                                  |
| 로그인 진입  |  50.8% |  50.8% | 없음                                                              |
| 로그인 회복  |  47.9% |  47.9% | 없음                                                              |
| 주문 완료    |  33.9% |  33.9% | 없음                                                              |

**두 값이 갈리는 경로**는 다음 단계로 가지 않았어도 무언가를 더 했다. 상품 담기의 차이 5,061세션은 담지는 않았지만 상세를 보거나 조건을 바꿨다 — 이탈이라기보다 탐색 중으로 보았다. 종료율로 보면 15.2%만 이탈로 잡혀, 목록을 둘러보다 결국 담지 않은 사람이 통계에서 사라진다. 그래서 이탈률 쪽을 쓴다.

담기 자체가 실패했을 가능성은 이 값에 들어 있지 않다. 담기는 서버 요청이 없는 클라이언트 상태 변경이라(`useToggleCart`) 실패할 API가 없고, 로그에 남을 실패 이벤트도 없다.

**두 값이 같은 경로**는 다음 단계로 못 간 세션이 그 자리에서 전부 끝났다는 뜻이다. 담기를 하고 로그인으로 가지 않은 665세션, 주문서까지 갔다가 사지 않은 142세션에는 그 뒤의 이벤트가 남아 있지 않다.

**인증 후 복원의 종료율 0.0%**는 복원을 못 했다는 뜻이 아니라, 로그인 화면에 들어가 아무것도 하지 않고 떠난 세션이 없다는 뜻이다. 들어간 644세션은 전부 성공(586)이나 실패(121)를 남겼다. 복원하지 못한 것은 미진행 쪽 225세션이고, 그중 167은 로그인에 성공하고도 주문서로 돌아오지 않았다.

시드에는 `login_start` 이후 성공이나 실패 없이 끝난 세션이 없다. 실제 데이터에서도 같은 분포가 나타나는지는 따로 확인해야 한다. 현재 앱은 `login_start`를 화면 진입 시점에 기록하므로, 입력하지 않고 떠난 세션이 생길 수 있다.

### B-6. 경로 분석

정제 후 7,514세션 기준이다. 세션 수는 완료 기준까지 지난 세션이고, 비율의 분모는 7,514다.

이탈률은 **시작과 완료를 연결한 복합 경로에만** 계산한다. 이벤트 하나로 정의한 경로는 완료 기준이 따로 없어 적용하지 않았고 표에 `—`로 둔다.

상품 탐색은 이벤트 셋을 묶은 경로인데도 `—`다. 조건을 바꾼 뒤 무엇을 했어야 "탐색을 마친 것"인지 정할 근거가 로그에 없기 때문이다. 지금 세는 것은 조건 변경이 일어났다는 사실까지이고, 원하는 상품을 찾았는지는 측정하지 못한다.

**무엇을 실패로 셌는가**

로그에 실패로 남은 이벤트만 센다. 두 종류뿐이다.

| 실패 신호      | 규모    | 무엇인가                                         |
| -------------- | ------- | ------------------------------------------------ |
| `login_fail`   | 121세션 | 로그인 시도가 거부됐다                           |
| `client_error` | 103세션 | 전부 `IMAGE_LOAD_FAILED` — 상품 이미지가 안 떴다 |

`order_start` 뒤에 `order_complete`가 없는 것은 **이탈이지 실패가 아니다.** 막혀서 못 산 것인지 그만둔 것인지 로그가 가리지 않는다. `order_fail`이 없어 주문 자체의 실패율은 산출할 수 없다.

실패 비용 열의 비율은 **그 경로의 시작 세션**을 분모로 한다.

실패 신호는 **그 경로의 구간 안에서 발생한 것만** 붙인다. 같은 세션에 있었다는 이유로 붙이면 상관을 인과처럼 쓰게 된다.

| 로그인 진입 (`cart_add` → `login_start`)     | 없음 — `login_fail`은 로그인 화면에 들어간 **뒤**에 발생한다       |

| 세션 만료 회복      | 만료 감지 → 안내 → 재로그인 → 원래 화면 | 만료 전용 이벤트 없음                                    | 산출 불가 | 산출 불가 | 산출 불가 | 만료 전용 실패 신호 없음. 만료 복구가 깨지면 주문과 주문 내역이 모두 막힌다                                                                                                                                                               | **O** — 빈도는 계산할 수 없지만 만료 안내와 재로그인 후 경로 복원이 1단계 완료 조건에 있다. 정상 흐름과 조건이 달라 별도로 만든다                                                                                            |
| 로그아웃            | 로그아웃 → 상태 정리 → 홈 이동          | 로그아웃 이벤트 없음                                     | 산출 불가 | 산출 불가 | 산출 불가 | 실패 신호 없음. 정리가 안 되면 다음 사람에게 이전 목록이 보인다                                                                                                                                                                           | **X** — `useLogoutMutation.test.tsx`가 성공·실패 양쪽에서 세션 캐시·장바구니·찜 정리와 홈 이동을 이미 검사한다. 브라우저를 지나야 확인될 부분이 없다                                                                         |
| 주문 내역 확인      | 주문 완료·헤더 → 주문 내역 확인         | 진입 이벤트 없음                                         | 산출 불가 | 산출 불가 | 산출 불가 | 실패 신호 없음. 주문 결과를 확인할 방법이 없어진다                                                                                                                                                                                        | **X** — 주문 목록 표시와 최신순 정렬은 MSW로 확인할 수 있다. 정렬 계약은 `order.test.ts`가 덮고, 화면 렌더도 브라우저를 지나야 할 부분이 없어 통합 테스트가 맡는다                                                           |

**포함**은 전체 구매 E2E 안에서 확인되므로 따로 만들지 않는다는 뜻이다. O/X 둘로만 나누면 E2E로 아예 안 보는 것과 뭉개진다.

## C. 붙일 곳과 안 붙일 곳

B-6의 가설을 확정하고, 겹치는 경로를 합쳐 실제로 만들 것을 정한다.

### C-1. 인증 플로우

인증 플로우는 과제의 필수 범위이므로 다음 세 갈래를 E2E로 만든다.

| 시나리오                 | 확인할 내용                                                                                             |
| ------------------------ | ------------------------------------------------------------------------------------------------------- |
| 미로그인 보호 경로 복원  | 미로그인으로 주문서에 진입하면 로그인 화면으로 이동하고, 로그인 후 원래 주문서로 돌아온다               |
| 잘못된 자격 증명 후 회복 | 잘못된 비밀번호로 로그인하면 실패 안내가 나타나고, 입력을 고쳐 다시 로그인할 수 있다                    |
| 세션 만료 후 회복        | 세션이 만료된 상태에서 보호 기능을 사용하면 만료 안내가 나타나고, 다시 로그인한 후 원래 경로로 돌아온다 |

첫 번째 시나리오는 주문서로 돌아온 뒤 주문 완료까지 이어서 확인한다. B절에서 전체 구매 경로를 E2E 후보로 선택했기 때문이다. 별도의 주문 완료 E2E를 추가하지 않고 필수 인증 시나리오에 연결한다.

따라서 실제 E2E는 세 개다. 인증 외에 선택한 전체 구매 경로를 첫 번째 인증 시나리오에 합쳤으므로 테스트 개수는 늘어나지 않는다.

### C-2. 인증 외에 고른 경로 — 전체 구매

인증 외에는 전체 구매 경로 하나를 골랐다. 정제 후 전체 7,514세션 중 277세션이 주문을 완료해 비율은 3.7%다.

빈도는 높지 않지만, 담은 상품이 로그인 과정에서 유지되고 주문서와 주문 완료까지 이어지는지를 확인할 필요가 있다. 중간 단계가 끊기면 사용자가 상품을 다시 담거나 주문을 처음부터 진행해야 한다.

이 경로는 C-1의 미로그인 보호 경로 복원 시나리오와 앞부분이 같다. 따라서 별도 E2E를 추가하지 않고, 로그인 후 주문서로 돌아온 다음 주문 완료까지 진행하도록 합친다.

인증 외의 다른 경로는 새로 선택하지 않는다. 상품 목록·탐색·담기·찜은 기존 통합 테스트와 8주차 E2E에서 이미 확인하고 있어 같은 목적의 E2E를 추가하지 않는다.

### C-3. 빈도가 높은데 붙이지 않은 경로

**상품 목록 진입(100.0%)과 상품 탐색(60.5%)**이다. 정제 후 각각 1위와 3위지만 9주차 E2E를 새로 추가하지 않는다.

조회 결과와 화면 상태는 기존 통합 테스트에서 확인한다.

- `ProductView.test.tsx`는 최초 조회·빈 결과·오류·재시도와 조건 변경 후 표시를 확인한다.
- `useProductListParams.test.tsx`는 URL 조건의 파싱과 query key 계약을 확인한다.

브라우저 동작이 필요한 로딩 화면 전환, URL 반영, 뒤로·앞으로 이동, 새로고침 후 조건 복원은 기존 8주차 E2E가 확인한다. 따라서 빈도는 높지만 현재 테스트에서 비어 있는 경로가 아니며, 같은 목적의 9주차 E2E를 추가하지 않는다.

기존 8주차 E2E는 그대로 유지한다. 기존 테스트의 삭제나 통합 테스트로의 이관은 9주차 신규 E2E 범위를 정하는 이번 작업에 포함하지 않는다.

### C-4. 빈도가 낮은데 붙이는 경로

**로그인 회복(0.8%)과 세션 만료 회복(산출 불가)**이다. 빈도로 줄을 세우면 마지막과 순위 밖이다.

로그인 회복은 63세션에서 확인됐다. 전체 대비 비율은 낮지만, 잘못된 자격 증명 이후 다시 로그인할 수 없으면 보호 경로와 주문으로 돌아갈 수 없다. 또한 잘못된 자격 증명은 4단계 인증 E2E의 필수 분기다.

세션 만료 회복은 시드에 만료 전용 이벤트가 없어 세션 수와 비율을 산출할 수 없다. 그러나 1단계 완료 조건에 만료 안내와 재로그인 후 원래 경로 복원이 포함돼 있고, 이 흐름이 깨지면 주문서와 주문 내역을 계속 이용할 수 없다.

### C-5. 유지보수 비용 추정 — 전체 구매

전체 구매는 상품 목록부터 주문 내역까지 네 화면을 지난다. 선택한 세 시나리오 중 화면과 상태 변화가 가장 많아 유지보수 비용을 살펴볼 대상으로 골랐다.

| 화면          | 확인할 대상                       | 변경 시 예상 수정 지점 |
| ------------- | --------------------------------- | ---------------------: |
| `/products`   | 담기 버튼과 장바구니 반영         |                  1~2곳 |
| `/login`      | 입력 필드, 로그인 버튼, 복원 경로 |                  2~3곳 |
| `/orders/new` | 주문 상품과 주문 버튼             |                  1~2곳 |
| `/orders`     | 방금 생성한 주문의 표시           |                    1곳 |

접근 가능한 이름과 URL을 기준으로 작성하면 문구·라벨·화면 구조·`next` 파라미터가 바뀔 때 약 5~8곳을 수정할 것으로 예상한다. 실제 개수는 4단계에서 셀렉터와 단언을 확정한 뒤 달라질 수 있다.

이 시나리오는 여러 화면을 연결하므로 한 화면의 구조가 바뀌어도 영향을 받을 수 있다. 대신 담기, 로그인, 경로 복원, 주문 완료를 각각 별도 E2E로 만들 때 생기는 로그인과 주문서 진입의 반복을 줄일 수 있다. 이 범위를 감수하고 전체 연결을 하나의 시나리오로 확인한다.

셀렉터는 기존 8주차 E2E와 같이 접근 가능한 이름을 우선 사용한다. `data-testid`로 문구 변경을 피하기보다 사용자가 인식하고 조작하는 요소를 기준으로 확인한다.

## D. 4단계 E2E 구현 기록

### D-1. 로그인 상태와 병렬 실행 격리

세션 만료 테스트만 워커별 `storageState`를 사용한다. 이 테스트는 만료 직전의 로그인 상태가 전제이므로 `looper5`부터 `looper8`까지 워커별 계정을 배정하고, 상태 파일도 프로젝트 이름과 워커 번호로 나눴다.

미로그인 보호 경로 복원과 잘못된 자격 증명 테스트는 로그인 자체가 검증 대상이다. 사전 인증 상태를 사용하면 보호 경로의 리다이렉트와 로그인 폼을 건너뛰므로 `storageState`를 사용하지 않는다. 이 두 테스트에는 `looper1`부터 `looper4`까지 워커별 계정을 배정했다.

브라우저 컨텍스트가 쿠키와 `sessionStorage`를 테스트별로 나누고, 워커별 계정이 주문 데이터를 나눈다. 상태 파일까지 워커별로 나눠 병렬 실행 중 같은 파일을 덮어쓰지 않게 했다.

| 실행 조건                              | 결과      |
| -------------------------------------- | --------- |
| 전체 E2E `--workers=4`                 | 11개 통과 |
| 전체 E2E `--workers=1`                 | 11개 통과 |
| 인증 E2E `--workers=4 --repeat-each=3` | 9개 통과  |

### D-2. trace 확인 기록

로그인 회복 테스트의 기대 URL을 `/orders/new`에서 `/orders/trace-check`로 바꾸고 `--trace=on`으로 실행해 의도적으로 실패시켰다. trace에서 로그인과 실제 `/orders/new` 이동은 완료됐고, 잘못된 `/orders/trace-check`를 기다리는 URL 단언에서 시간 초과된 것을 확인했다.

확인 후 기대 URL을 `/orders/new`로 되돌렸고, 같은 테스트를 다시 실행해 통과하는 것을 확인했다.

## E. 5단계 E2E 자가 검증

테스트 코드는 바꾸지 않고 인증 구현을 한 곳씩 바꿨다. 각 실험은 결과를 확인한 직후 원복한 다음 다음 실험으로 넘어갔다.

### E-1. 실험 결과

| #   | 망가뜨린 곳                                       | 어떻게 바꿨나                                            | 결과 | 실패한 테스트                                    | 실패 메시지로 원인을 알 수 있었나                                                                                                |
| --- | ------------------------------------------------- | -------------------------------------------------------- | ---- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `src/app/api/auth/login/route.ts`                 | 세션 쿠키에 현재 호스트와 다른 `Domain=example.com` 추가 | 잡힘 | 미로그인 → 로그인 → 원래 주문서 복원 → 주문 완료 | 알 수 있었다. 기대한 `/orders/new` 대신 `/login?next=%2Forders%2Fnew`에 남아 쿠키가 보호 경로에 전달되지 않았음을 좁힐 수 있었다 |
| 2   | `src/features/auth-login/api/useLoginMutation.ts` | 로그인 성공 후 `redirectPath` 대신 `/`로 이동            | 잡힘 | 미로그인 → 로그인 → 원래 주문서 복원 → 주문 완료 | 알 수 있었다. 복원 단계에서 기대 URL은 `/orders/new`, 실제 URL은 `/`로 표시됐다                                                  |
| 3   | `src/app/_lib/requireSession.ts`                  | 만료 상태여도 로그인 경로에 `expired` 플래그를 싣지 않음 | 잡힘 | 세션 만료 → 안내 → 재로그인 → 원래 경로 복원     | 알 수 있었다. 실제 URL에 `next`는 남았지만 `expired=1`이 없었고, 만료 안내를 확인하는 단계에서 실패했다                          |

### E-2. 통합 테스트와 E2E의 경계 재검토

실험 1을 주입한 상태에서 로그인 API 테스트 11개는 모두 통과했다. 이 테스트는 `Set-Cookie` 문자열의 필수 속성을 확인하지만, 브라우저가 현재 호스트와 맞지 않는 쿠키를 거부하고 다음 보호 경로 요청에 보내지 않는 동작은 재현하지 않는다. 브라우저의 쿠키 수락과 전달을 연결해서 확인해야 하므로 이 실험은 E2E만 잡을 수 있었던 항목이다.

실험 2를 주입한 상태에서도 로그인 mutation 테스트 4개는 통과했다. 현재 테스트는 로그인 실패 사유 계측을 확인하고, 성공 뒤 실제 화면 이동은 다루지 않는다. 로그인 성공과 원래 경로 복원이 연결되는지는 E2E에 남긴다.

실험 3을 주입한 상태에서도 현재 경로와 전역 401 처리 테스트 20개는 통과했다. 이 테스트들은 경로 조립과 클라이언트 요청의 401 처리를 각각 확인하지만, 서버의 만료 판정이 로그인 화면 안내까지 이어지는지는 확인하지 않는다. 세션 만료 회복도 E2E에 남긴다.

관련 하위 테스트로 함께 잡힌 실험은 없었으므로 E2E 시나리오를 통합 테스트로 내리지 않았다.

### E-3. 실험 뒤

세 실험은 모두 E2E에서 실패했고 살아남은 변경은 없었다. 실패 단계와 기대값·실제값으로 원인을 좁힐 수 있어 테스트를 보강하지 않았다.

실험용 변경을 모두 원복한 뒤 전체 E2E를 `--workers=4`로 실행해 11개가 통과하는 것을 확인했다. 인증 구현과 E2E 테스트 코드에는 실험용 변경이 남아 있지 않다.
