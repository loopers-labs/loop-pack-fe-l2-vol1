# 9주차 이벤트 계측 및 E2E 범위

**상태:** 3단계 범위 확정

이 RFC는 이벤트 스키마와 30일 시드 로그를 근거로 4단계에서 구현할 E2E 범위를 정한다. 인증의 세 분기, 주문 제출 후 주문 내역 반영, 비회원 장바구니의 로그인 병합을 선택한다. 상품 탐색과 무한 목록은 신규 E2E에서 제외한다.

| 구분 | 결정 |
| --- | --- |
| 필수 E2E | 인증: 보호 경로 복원, 만료 세션, 잘못된 자격 증명 |
| 인증 외 E2E | 주문 제출 → 주문 내역 반영, 비회원 장바구니 → 로그인 병합 |
| 신규 E2E 제외 | 상품 탐색, 무한 목록, 필터·정렬, 위시리스트 |
| 기존 회귀 E2E | URL 직접 진입·새로고침 복원 1개, 방문 기록 복원 1개 |
| 예상 구성 | 상품 회귀 2개 + 인증 3개 + 장바구니 병합 1개 + 주문 1개 = 7개 |

## A. 이벤트 스키마

이벤트 이름은 시드 로그와 같은 `snake_case`를 사용하고 `<대상>_<행동 또는 결과>` 순서로 쓴다. 화면 노출은 `view`, 흐름 진입은 `start`, 성공과 실패는 `success`·`fail`, 최종 완료는 `complete`로 구분한다.

| 이름 | 발생 시점 | 프로퍼티 |
| --- | --- | --- |
| `product_list_view` | 상품 목록에 처음 진입했을 때 | `category: string`, `sort: string`, `page: number`(1부터 시작) |
| `product_detail_view` | 상세 상품 조회 후 화면에 진입했을 때 | `productId: string` |
| `cart_add` | 장바구니 수량을 늘린 직후 | `productId: string`, `quantity: number` |
| `login_start` | 로그인 화면에 처음 진입했을 때 | `from: "cart" \| "orders" \| "direct"` |
| `login_success` | 로그인 성공 후 복원 경로로 이동하기 전 | `from: "cart" \| "orders" \| "direct"` |
| `login_fail` | 로그인 실패 후 같은 폼에서 다시 행동해야 할 때 | `from`, `reason` |
| `order_start` | 상품 조회가 끝나 주문 가능한 주문서가 됐을 때 | `productIds: string[]`, `itemCount: number`, `totalPrice: number`(원) |
| `order_complete` | 주문 API 성공 후 장바구니를 비우기 전 | `orderId: string`, `productIds: string[]`, `itemCount: number`, `totalPrice: number`(원) |

`login_fail.reason`은 401을 `INVALID_CREDENTIALS`, 400을 `INVALID_REQUEST`, 500 이상을 `SERVER_ERROR`, 그 밖의 실패를 `UNKNOWN_ERROR`로 기록한다. `from`은 로그인 목적지가 아니라 실제 이전 화면이다. `/cart`의 주문 링크는 `cart`, 주문 화면과 세션 만료는 `orders`, 직접 진입과 일반 로그인은 `direct`로 기록한다. 허용되지 않은 값은 `direct`로 바꾼다.

모든 이벤트에는 다음 공통 프로퍼티를 붙인다.

| 프로퍼티 | 값 |
| --- | --- |
| `sessionId` | 탭의 `sessionStorage`에 저장한 `s_<uuid>` |
| `ts` | 이벤트 발생 시점의 ISO 8601 UTC 문자열 |
| `device` | 뷰포트 폭에 따른 `mobile`(<768), `tablet`(<1024), `desktop` |
| `userId` | 로그인 이후 이벤트에만 포함하는 사용자 ID |

앱과 시드 로그의 이벤트 이름은 같다. 상품 목록·상세·담기 프로퍼티도 같다. 로그인은 시드의 `from: cart`에 `orders`와 `direct`를 추가한다. 주문은 여러 상품을 지원하기 위해 시드의 `productId`를 `productIds`로 확장하고 `itemCount`, `totalPrice`, `orderId`를 추가한다.

화면은 오타와 프로퍼티 누락을 컴파일 시점에 잡을 수 있도록 문자열 기반 `track()` 대신 `src/analytics/events.ts`의 타입 있는 함수만 호출한다. `AnalyticsInitializer`가 페이지 진입 effect보다 먼저 실행되는 루트 Provider에서 공통 프로퍼티를 등록하고 `initAnalytics()`를 호출한다. 초기화 전 이벤트는 로거 큐가 순서를 보존한다. 로그인 성공 시 이동 전에 `identify()`를 호출하고, 새 문서에서는 서버가 복원한 사용자 ID를 다시 식별한다. 로그아웃 성공 후에는 `reset()`을 호출한다.

장바구니에서 로그인해 주문을 완료하면 다음 순서가 남는다.

1. `login_start { from: "cart" }`
2. `identify(<userId>)`
3. `login_success { from: "cart" }`
4. 전체 문서 이동 후 `identify(<userId>)`
5. `order_start { productIds, itemCount, totalPrice }`
6. `order_complete { orderId, productIds, itemCount, totalPrice }`

## B. 시드 로그 분석

분석은 다음 명령으로 재현한다.

```bash
pnpm analyze:week09
```

2026-07-22부터 2026-08-20까지의 원본은 22,427이벤트·8,000세션이다. 다음 기준으로 정제한 결과는 21,864이벤트·7,514세션이다.

- 자동 트래픽 후보: 이벤트가 하나뿐이고 `product_list_view`, `category=all`, `sort=latest`, `page=1`, `device=null`, 밀리초 `.000`, UTC 01시 조건을 모두 만족한 486세션
- 완전 중복: `sessionId`, `ts`, `name`, `props`, `userId`, `device`가 모두 같은 이벤트의 두 번째 행부터 제거한 77건

집계 단위는 고유 `sessionId`다. 경로는 화면과 사용자의 핵심 행동 단위로 묶고 필터·정렬·페이지 이동 같은 보조 행동은 제외했다. 비율의 분모는 정제한 전체 7,514세션이다. 이탈률은 현재 단계에 도달한 세션 중 같은 세션의 이후 시점에 다음 핵심 단계가 없는 비율이다.

| 경로 | 세션 | 비율 | 다음 단계 전환율 | 이탈률 | 실패 비용 | E2E 가설 |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| 상품 목록 | 7,514 | 100.00% | 61.96% | 38.04% | 탐색 시작 차단 | 제외 |
| 상품 상세 | 4,656 | 61.96% | 28.11% | 71.89% | 장바구니 진입 차단 | 제외 |
| 장바구니 담기 | 1,309 | 17.42% | 49.20% | 50.80% | 주문할 상품 유실 | 병합 후보 |
| 로그인 시작 | 644 | 8.57% | 90.99% | 9.01% | 모든 회원 흐름 차단 | 필수 |
| 로그인 성공 | 586 | 7.80% | 71.50% | 28.50% | 원래 흐름 복귀 실패 | 인증에 포함 |
| 주문 시작 | 419 | 5.58% | 66.11% | 33.89% | 구매 완료 차단 | 주문 후보 |
| 주문 완료 | 277 | 3.69% | 해당 없음 | 해당 없음 | 구매 결과 신뢰 훼손 | 주문에 포함 |

필터링 전후의 세션 도달 순위는 바뀌지 않았다. 자동 트래픽 후보가 목록 진입에만 섞였고, 중복 전송은 이미 해당 행동에 도달한 세션 안에서 발생했기 때문이다. 다만 자동 트래픽 후보를 남기면 상세 이하 모든 비율의 분모가 커져 실제 사용자 후보의 도달률을 낮춘다.

로그인 시작 644세션 중 121세션(18.79%)에서 자격 증명 실패가 발생했다. 이 중 63세션은 같은 세션에서 로그인에 성공했고 58세션은 성공하지 못했다. `client_error` 103세션은 이미지 로드 실패만 기록하므로 상품·주문 API 실패 근거로 사용하지 않는다. 주문 시작 419세션 중 142세션(33.89%)에는 완료 이벤트가 없지만, 실패 이벤트가 없어 사용자 중단·API 실패·계측 누락을 구분할 수 없다. 주문 미완료율을 시스템 결함률로 해석하지 않는다.

## C. 최종 E2E 범위

E2E는 이벤트 빈도뿐 아니라 실패 비용, 실제 브라우저 경계, 더 낮은 테스트의 대체 가능성을 함께 평가한다.

| 대상 | 선택 근거 | 더 낮은 테스트의 책임 |
| --- | --- | --- |
| 인증 | 빈도는 8.57%지만 인증이 막히면 모든 회원 흐름이 차단된다. 보호 경로 복원, 만료 세션, 잘못된 자격 증명은 `proxy.ts`·쿠키·서버 렌더링·로그인 API·페이지 이동이 함께 작동해야 한다. | 안전한 `returnTo`는 단위 테스트, 응답 계약과 오류 UI는 Route Handler·통합 테스트 |
| 주문 제출 → 주문 내역 반영 | 주문 완료는 277세션(3.69%)으로 낮지만 구매 결과와 직접 연결된다. 실제 로그인 쿠키와 회원 장바구니를 가진 사용자가 주문을 제출한 뒤 `/orders`에서 해당 상품을 포함한 새 주문을 확인한다. | 합계·수량 계산은 단위 테스트, 요청 본문·장바구니 초기화·`router.replace()` 호출·400·500 오류 UI는 통합 테스트 |
| 비회원 장바구니 → 로그인 병합 | 장바구니 담기는 1,309세션(17.42%)이다. 로그인 전후 세션 쿠키, 사용자별 `localStorage`, 서버 UI가 함께 바뀌며 병합 실패 후 자동 복구 경로가 없다. 로그인 뒤 주문서에 같은 상품과 수량이 남는지만 확인한다. | 수량 합산은 단위 테스트, 사용자별 저장·복원·`guest` 정리·`storage` 이벤트는 통합 테스트 |

상품 목록과 상세는 각각 100%, 61.96%로 빈도가 높지만 신규 E2E에서 제외한다. 요청 조건, 잘못된 파라미터 정리, 로딩, 오류, 재시도, 렌더링은 MSW 통합 테스트가 더 빠르게 실패 원인을 알려준다. 필터·정렬과 무한 목록도 통합 테스트가 담당한다. 실제 뷰포트에서 자동 로딩이 실패해도 접근 가능한 `더 보기` 버튼으로 탐색할 수 있다.

기존 상품 E2E에서는 실제 브라우저 경계인 두 시나리오만 유지한다. 하나는 필터·정렬 URL로 직접 진입하거나 새로고침했을 때 같은 조건과 목록을 복원하는 테스트다. 다른 하나는 뒤로가기·앞으로가기에서 URL과 목록을 함께 복원하는 테스트다. 필터·장바구니·위시리스트를 한꺼번에 새로고침하는 테스트는 제거한다. 장바구니와 위시리스트 저장·복원은 단위·통합 테스트가 담당한다.

인증 E2E는 다음 세 분기를 독립 테스트로 둔다.

- 비로그인 보호 경로 → 로그인 → 안전한 원래 경로 복원
- 만료된 세션 → 로그인 이동
- 잘못된 자격 증명 → 오류 노출 후 로그인 화면 유지

주문 E2E는 워커별 로그인 계정의 `storageState`와 상품 1개가 든 회원 장바구니 fixture를 준비한다. 사용자가 주문 버튼을 누른 뒤 `/orders`로 이동하고, 해당 상품과 수량이 포함된 새 주문이 표시되는지 확인한다. 같은 상품을 두 번 담기, 새로고침 후 수량 복원, 결제 금액 계산, 장바구니 비움은 이 테스트에서 다시 검증하지 않는다.

장바구니 병합 E2E는 비회원 장바구니에 상품 1개를 준비하고 다음 흐름만 검증한다.

- 비회원 장바구니 → 주문하기 → 로그인 → `/orders/new`에서 같은 상품과 수량 확인

다중 탭 동기화와 로그아웃 후 빈 `guest` 장바구니는 핵심 E2E에서 제외한다. `CartStoreProvider` 통합 테스트에서 owner 전환, `guest` 정리, `storage` 이벤트를 각각 검증한다. 실제 다중 탭 동기화가 제품의 명시적 인수 조건이 되면 병합·로그아웃과 섞지 않고 독립 회귀 E2E로 추가한다.

### 유지보수 비용

주문 시나리오는 `e2e/order.spec.ts` 한 파일에 둔다. 역할과 접근 가능한 이름, `/orders` URL, 새 주문 카드를 계약으로 사용한다. 접근 가능한 이름이 바뀌면 주문 제출 버튼과 주문 내역 제목 등 로케이터 최대 2곳을 수정한다. URL이나 주문 카드 구조가 바뀌면 URL 단언과 주문 결과 단언을 각각 1곳 수정한다. 스타일 클래스와 DOM 깊이는 단언하지 않는다.

### 4단계 완료 조건

- 인증 테스트와 장바구니 병합 테스트는 로그인 UI를 직접 통과한다.
- 주문 테스트는 `parallelIndex`로 분리한 워커별 계정과 `storageState`를 재사용한다.
- 상품 회귀 E2E는 URL 직접 진입·새로고침과 방문 기록 복원 두 브라우저 경계만 검증한다.
- 각 테스트는 다른 테스트가 만든 쿠키, 저장소, 주문 결과에 의존하지 않는다.
- 프로덕션 빌드에서 역할과 접근 가능한 이름으로 요소를 찾고 고정 시간 대기를 사용하지 않는다.
- `--workers=1`과 `--workers=4`의 결과가 같고, 전체 E2E를 3회 연속 실행해도 결과가 같다.
- 일부러 실패시킨 단언의 트레이스를 직접 열어 브라우저 이동·네트워크·DOM 상태에서 원인을 찾을 수 있는지 확인한다.
