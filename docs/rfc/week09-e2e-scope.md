# 9주차 — 계측 스키마와 E2E 범위

> 이 문서가 정하는 것: **어떤 이벤트를 어떤 모양으로 남기는가(A)**, **그 로그가 무엇을 말하는가(B)**,
> **그래서 비싼 테스트를 어디에 쓰는가(C)**.
> 4단계에서 만들 E2E 는 여기 C절 표에 있는 것뿐이다. 표에 없으면 만들지 않는다.

---

## A. 이벤트 스키마

### A-1. 공통 프로퍼티

모든 이벤트에 붙는다. `setCommonProperties()` 에 함수를 넘겨 **이벤트 발생 시점에** 평가한다.

| 키          | 값                              | 어떻게 만드는가                                           |
| ----------- | ------------------------------- | --------------------------------------------------------- |
| `sessionId` | UUID                            | `sessionStorage` 에 담는다. **탭 하나가 세션 하나**다     |
| `device`    | `mobile` / `tablet` / `desktop` | 화면 폭. 768 미만 mobile, 1024 미만 tablet, 그 외 desktop |
| `ts`        | ISO 8601                        | 발생 시점의 `new Date().toISOString()`                    |
| `userId`    | string                          | **로그인한 뒤에만 붙는다.** 로그아웃하면 사라진다         |

**세션 정의**: 탭 하나가 세션 하나다. `sessionStorage` 는 탭을 닫으면 사라지고 새 탭으로 복사되지 않아,
"한 번의 방문"이라는 정의가 저장소 동작으로 그대로 지켜진다. 유휴 시간을 재는 로직도, 그 로직을 검증할
테스트도 필요 없다. 대신 **한 사람이 탭을 두 개 열면 세션도 둘**이 된다.

**`device` 를 User-Agent 로 판정하지 않은 이유**: 파싱 규칙을 직접 유지해야 하고, 개발자 도구의 기기
에뮬레이션에서 실제와 다른 값이 찍혀 계측 확인이 어려워진다. 폭 기준은 "지금 어떤 레이아웃을 보고
있는가"를 그대로 말한다.

**`userId` 가 props 가 아니라 공통 프로퍼티인 이유**: 시드 로그는 `userId` 를 이벤트의 top-level 필드로
두고 `login_success` · `order_start` · `order_complete` 에만 싣는다. `docs/fixtures/events.md` 도
_"로그인한 뒤의 이벤트에만 있습니다"_ 라고 적었다. 우리 `logger.track()` 은 이름과 프로퍼티만 받으므로
top-level 필드를 만들 수 없어, 공통 프로퍼티에 조건부로 얹어 **같은 성질**(로그인 전엔 키 자체가 없음)을 냈다.

### A-2. 이벤트 12종

이름은 시드 로그의 것을 그대로 쓴다. 이름 규칙은 `{대상}_{행위}` 이며 시드 로그가 이미 그 규칙이다.

| 이벤트                   | 발생 시점        | props                              |
| ------------------------ | ---------------- | ---------------------------------- |
| `product_list_view`      | 목록 화면 진입   | `category` `sort` `page`           |
| `category_filter_change` | 카테고리 변경    | `category`                         |
| `sort_change`            | 정렬 변경        | `sort`                             |
| `page_change`            | 페이지 이동      | `page`                             |
| `product_detail_view`    | 상세 화면 진입   | `productId`                        |
| `cart_add`               | 장바구니 담기    | `productId` `quantity`             |
| `wishlist_add`           | 위시리스트 추가  | `productId`                        |
| `login_start`            | 로그인 화면 진입 | `from`                             |
| `login_success`          | 로그인 성공      | `from`                             |
| `login_fail`             | 로그인 실패      | `reason`                           |
| `order_start`            | 주문서 진입      | `productIds` `itemCount`           |
| `order_complete`         | 주문 완료        | `orderId` `productIds` `itemCount` |

**발화 규칙 두 가지**

- **진입 이벤트는 화면당 1회**다. 조건을 바꿔도 다시 발화하지 않는다 — 조건 변경은
  `category_filter_change` · `sort_change` · `page_change` 가 따로 맡는다. 조건마다 발화시키면
  B절에서 "목록을 본 세션"이 조작 횟수만큼 부풀어 순위가 틀어진다.
- **행위 이벤트는 성공한 시점에만** 발화한다. 담기에서 **빼기는 세지 않고**(시드 로그에 `cart_remove` 가
  없어 대응할 이름이 없다), 주문이 실패하면 `order_complete` 가 없다.

### A-3. 시드 로그와의 매핑

이름은 12종 모두 같다. **props 가 네 곳에서 다르다.**

| 이벤트                           | 시드 로그                       | 우리                                       | 왜 다른가                                                                                                                                                                                                                   |
| -------------------------------- | ------------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cart_add`                       | `productId`, `quantity`         | `quantity` 가 항상 1                       | 장바구니가 상품 집합만 저장하고 수량 조절 UI 가 없다                                                                                                                                                                        |
| `login_start` · `login_success`  | `from: "cart"`                  | `from`: order / orders / mypage / direct   | proxy 가 붙인 `returnTo` 의 첫 구간을 옮겼다. 보호 목록에 없는 값은 `direct` 로 접는다 — 임의 경로를 그대로 실으면 값의 가짓수가 열려 집계할 수 없다                                                                        |
| `login_fail`                     | `reason: "INVALID_CREDENTIALS"` | 401 이면 같은 코드, 그 외 `REQUEST_FAILED` | 서버가 코드가 아니라 사람이 읽는 문구를 준다. 자격 증명 오류와 서버 장애는 대응이 달라 한 값으로 뭉치지 않았다                                                                                                              |
| `order_start` · `order_complete` | `productId` 단수, `totalPrice`  | `productIds` 배열, `itemCount`, `orderId`  | **도메인 모델이 다르다.** 시드 로그는 상세에서 상품 하나를 바로 주문하고, 우리는 장바구니를 일괄 주문한다. `totalPrice` 는 장바구니가 가격을 갖고 있지 않아 싣지 않았다 — 넣으려면 주문서에 상품 가격 조회가 하나 더 붙는다 |
| top-level `userId`               | 이벤트 필드                     | 공통 프로퍼티                              | A-1 참고                                                                                                                                                                                                                    |

### A-4. 붙이지 않은 것

| 로그에 있으나 안 붙임 | 사유                                                                                                                                                                                                                           |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `client_error`        | 화면 진입도 도메인 행위도 아닌 **오류 신호**다. 이걸 계측하면 B절의 노이즈 커트라인과 얽혀 "우리가 만든 오류 이벤트를 우리가 노이즈로 거른다"가 된다. 시드 로그의 103건은 전부 `IMAGE_LOAD_FAILED` 로, 진행을 막지 않는 종류다 |
| 검색어 변경           | 시드 로그에 대응하는 이름이 없다. `product_list_view` 의 props 에도 `q` 가 없어, 새 이름을 만들면 시드 로그와 대조할 수 없는 줄이 생긴다                                                                                       |

### A-5. 로그인부터 주문까지 남는 순서

한 사람이 목록에서 시작해 주문까지 갔을 때:

```
product_list_view    { category: 'all', sort: 'latest', page: 1 }
product_detail_view  { productId: 'p1' }
cart_add             { productId: 'p1', quantity: 1 }
login_start          { from: 'order' }                        ← /order 진입이 proxy 에 막혀 여기로 옴
login_success        { from: 'order' }                        ← 이후 userId 가 붙기 시작
order_start          { productIds: ['p1'], itemCount: 1 }
order_complete       { orderId: 'o1', productIds: ['p1'], itemCount: 1 }
```

주문서로 가는 길은 **헤더의 장바구니 개수** 하나다. 주문서가 곧 담긴 목록을 보여주는 화면이라 별도의
장바구니 화면을 두지 않았고, 그래서 위 흐름은 주소를 직접 치지 않아도 클릭만으로 재현된다.

**미로그인으로 `/order` 에 들어가도 `order_start` 는 남지 않는다.** proxy 가 요청 경계에서 가로채
로그인으로 보내므로 주문서 화면 자체가 렌더되지 않고, 계측이 붙은 훅도 돌지 않는다. 그래서 이 흐름에서
`login_start` 의 `from` 이 `order` 인 것이 "주문하러 왔다가 튕겼다"를 말해주는 유일한 흔적이다.

이 배치에는 대가가 있다 — `/order` 가 보호 경로라 **담아둔 것을 보기만 하려 해도 로그인해야 한다.**
담기 자체는 비로그인에서도 되지만 확인은 안 되는 셈이다. 튕겨도 `returnTo` 로 돌아오므로 담은 것이
사라지지는 않는다.

시드 로그의 `order_start`(419세션)와 우리 것을 나란히 놓을 때 이 차이를 알고 있어야 한다. 시드 로그는
로그인 여부와 무관하게 주문서 진입을 세지만, 우리 것은 **로그인한 사람만** 센다.

## B. 시드 로그 분석

원본: `fixtures/events-30d.jsonl`, **8,000세션 / 22,427이벤트**.

### B-1. 무엇을 걸렀는가

로그에 "이건 봇이다" 하는 표시가 없으므로 기준을 직접 정했다.

| 단계        | 기준                                                              | 제거량         |
| ----------- | ----------------------------------------------------------------- | -------------- |
| 중복 전송   | `sessionId` + `name` + `ts` 가 완전히 같은 줄                     | **77 이벤트**  |
| 봇 세션     | `device` 가 `null` 이면서 `product_list_view` **단 1건**뿐인 세션 | **486 세션**   |
| 오류 이벤트 | `client_error`                                                    | **103 이벤트** |

**봇 기준을 이렇게 잡은 근거**: `device` 가 `null` 인 이벤트는 로그 전체에서 486건이고, 그 486건이
**각각 다른 세션의 유일한 이벤트**다. 즉 "기기를 알 수 없는 채로 목록만 한 번 긁고 사라진" 패턴이 정확히
486세션이다. 세션 길이로는 가를 수 없었다 — 최대 길이가 11이고 p99 가 8이라 비정상적으로 긴 세션이 없다.

**남은 것: 7,514세션 / 21,761이벤트.** 이하 모든 비율의 분모는 이 7,514다.

**거르지 않기로 한 것 하나.** `docs/fixtures/events.md` 가 경고한 네 가지는 봇 트래픽, 중복 전송,
오류 이벤트, 그리고 **"이 코드베이스에 없는 화면의 이벤트"** 다. 앞의 셋은 위 표에서 걸렀다.
하지만 `없는 화면의 이벤트` 항목은 거르지 않기로 결정했다.

8주차 시점의 화면은 홈과 목록뿐이었으므로 `product_detail_view`(4,656) · `login_start`(644) ·
`login_success`(586) · `login_fail`(121) · `order_start`(419) · `order_complete`(277) 이 전부 여기
해당했다. 로그 22,427건 중 **6,703건**, 세션 기준으로는 퍼널의 2단계부터 6단계 전부다.

**이것을 제외하면 B절이 목록 하나짜리 표가 된다.** 퍼널이 1단계에서 끝나고, 전단계 대비 전환율을
계산할 구간이 사라지며, C절의 선정 규칙("기존 검증 자산이 없는 구간 × 실패 비용")을 적용할 대상 자체가
없어진다. 로그가 이상해서가 아니라 **구현이 로그를 따라가지 못한 것**이므로, 거르는 대신 화면을 만들었다
— `/products/[id]` · `/order` · `/orders` · `/mypage` 넷이다.

그 결과 **13종 전부가 대응하는 화면·행위를 갖는다.** 값도 대조했다 — `category` 는 `all` 과
`casual·digital·fashion·goods·home` 으로 코드베이스의 `CategoryId` 5종 + 필터의 `all` 과 일치하고,
`productId` 는 `p1`~`p30` 30개로 `commerce.ts` 와 일치한다. 로그에만 있고 코드에 없는 값은 없다.

### B-2. 필터 전후 순위 — 바뀌지 않았다

세션 기준(같은 세션에서 여러 번 일어난 행위를 1로 센다).

| #   | 이벤트                   | 전 (분모 8,000) | 후 (분모 7,514) |
| --- | ------------------------ | --------------- | --------------- |
| 1   | `product_list_view`      | 8,000 · 100.0%  | 7,514 · 100.0%  |
| 2   | `product_detail_view`    | 4,656 · 58.2%   | 4,656 · 62.0%   |
| 3   | `category_filter_change` | 3,056 · 38.2%   | 3,056 · 40.7%   |
| 4   | `page_change`            | 1,756 · 21.9%   | 1,756 · 23.4%   |
| 5   | `cart_add`               | 1,309 · 16.4%   | 1,309 · 17.4%   |
| 6   | `sort_change`            | 943 · 11.8%     | 943 · 12.5%     |
| 7   | `login_start`            | 644 · 8.1%      | 644 · 8.6%      |
| 8   | `login_success`          | 586 · 7.3%      | 586 · 7.8%      |
| 9   | `wishlist_add`           | 480 · 6.0%      | 480 · 6.4%      |
| 10  | `order_start`            | 419 · 5.2%      | 419 · 5.6%      |
| 11  | `order_complete`         | 277 · 3.5%      | 277 · 3.7%      |
| 12  | `login_fail`             | 121 · 1.5%      | 121 · 1.6%      |

**12개 전부 순위가 같다.** 안 바뀐 이유가 데이터에 그대로 있다 — 걸러낸 봇 486세션이 `product_list_view`
**하나만** 쐈고 그건 이미 1위였다. 나머지 11개 순위에는 봇 세션이 애초에 등장하지 않는다. 중복 77건과
`client_error` 103건도 특정 이벤트에 몰려 있지 않아 순위를 흔들 만한 양이 아니다.

**바뀐 것은 순위가 아니라 분모다.** 모든 비율이 일률적으로 올라갔다(예: 상세 58.2% → 62.0%). 필터가
쓸모없었다는 뜻이 아니라, **"몇 등인가"에는 영향이 없고 "몇 퍼센트인가"에는 있다**는 뜻이다. C절에서
순위로 고르는 판단에는 필터가 결론을 바꾸지 않았고, 퍼널 수치를 인용할 때는 필터 후 값을 써야 한다.

### B-3. 경로별 표

**경로를 화면 단위로 묶었다.** 묶은 기준: **그 화면의 이벤트가 하나라도 있으면 그 화면을 지난 것으로 본다.**
이벤트 단위로 12행을 만들면 `sort_change` 같은 조작 이벤트의 "다음 단계"가 정의되지 않아 이탈률 칸이 빈다.

**이탈률 정의**: **다음 단계 미진입률**. 그 화면을 지난 세션 중 다음 화면에 도달하지 못한 비율이다.
"그 이벤트가 세션의 마지막이었던 비율"은 쓰지 않았다 — 마지막 이벤트가 무엇이든 사용자가 다음 화면으로
못 갔다는 사실이 우리가 알고 싶은 것이기 때문이다.

**실패로 센 것**: `login_fail` 과 **주문 시작 후 미완료**. 앞은 앱이 명시적으로 남기는 유일한 실패
신호이고, 뒤는 실패 이벤트가 아니라 이탈이지만 돈에 가장 가까운 지점이라 실패 비용으로 읽었다.
`client_error` 는 세지 않았다 — 103건 전부 `IMAGE_LOAD_FAILED` 라 진행을 막지 않고, B-1 에서
노이즈로 걸러낸 것을 다시 비용으로 쓰면 기준이 섞인다.

| 경로       | 세션 수 | 비율 (분모 7,514) | 이탈률    | 실패 비용                                                                                                                          | E2E 여부 (가설) |
| ---------- | ------- | ----------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------- | --------------- |
| **목록**   | 7,514   | 100.0%            | 38.0%     | 막히면 서비스 자체가 없다. 다만 8주차에 이미 E2E 2개가 덮고 있다                                                                   | 아니오          |
| **상세**   | 4,656   | 62.0%             | **86.2%** | 막히면 담기·주문이 전부 막힌다. 이탈률이 가장 크지만 그건 원래 구매로 이어지는 비율이 낮은 것이지 고장이 아니다                    | 아니오          |
| **로그인** | 644     | 8.6%              | 34.9%     | **막히면 주문(5.6%)과 마이페이지가 통째로 막힌다.** 로그인 시도 644건 중 **18.8%가 실패를 겪고 9.0%(58건)는 끝내 성공하지 못한다** | **예**          |
| **주문**   | 419     | 5.6%              | —         | **주문 시작 후 33.9%(142건)가 완료하지 못한다.** 돈이 움직이는 유일한 경로                                                         | **예**          |

### B-4. 6단계 퍼널

전체 대비와 전단계 대비를 함께 적는다. 전체 대비만 보면 뒤로 갈수록 다 작아 보여 어느 구간이 문제인지 알 수 없다.

| 단계                  | 세션  | 전체 대비 | 전단계 대비 | 다음 단계 미진입률 |
| --------------------- | ----- | --------- | ----------- | ------------------ |
| `product_list_view`   | 7,514 | 100.0%    | —           | 38.0%              |
| `product_detail_view` | 4,656 | 62.0%     | 62.0%       | 71.9%              |
| `cart_add`            | 1,309 | 17.4%     | **28.1%**   | 50.8%              |
| `login_start`         | 644   | 8.6%      | **49.2%**   | 34.9%              |
| `order_start`         | 419   | 5.6%      | 65.1%       | 33.9%              |
| `order_complete`      | 277   | 3.7%      | 66.1%       | —                  |

4단계를 `login_success` 가 아니라 `login_start` 로 잡았다. 로그인을 **시도한** 사람이 주문으로 갔는지가
알고 싶은 것이고, 성공 여부는 그 안의 실패율(18.8%)로 따로 본다.

> **각주 — 건너뛴 세션 0건.** 앞 단계 없이 뒤 단계에만 나타난 세션은 **0건**이다. 6단계를 순서대로
> 지나지 않은 세션이 없으므로 전단계 대비 비율을 그대로 읽어도 된다. 이 확인 없이 전단계 대비를 쓰면
> 건너뛴 세션이 분자에 섞여 100%가 넘는 칸이 나올 수 있다.

## C. 붙일 곳과 안 붙일 곳

**선정 규칙: "전환율 손실이 큰 구간"이 아니라 "기존 검증 자산이 없는 구간 × 실패 비용"으로 고른다.**

B 절의 손실 구간을 그대로 E2E 로 옮기지 않는 이유가 둘이다.

첫째, **이미 덮여 있는 것을 또 사게 된다.** 손실이 가장 큰 구간은 상세→담기(전단계 대비 28.1%)인데,
그 구간은 8주차 E2E 가 이미 지난다. 빈도나 손실만 보고 고르면 같은 것을 두 번 산다.

둘째, **로그는 실패 비용을 말하지 않는다.** 빈도는 "몇 명이 지났는가"이지 "막히면 무엇이 무너지는가"가
아니다. 로그인은 세션의 8.6%만 지나지만 막히면 주문도 마이페이지도 전부 막힌다. 담기가 막히면
담기만 막힌다.

그래서 각 경로를 두 축으로 본다 — **기존 자산(8주차 E2E·통합 테스트)이 그 구간을 실제로 지나는가**,
그리고 **막혔을 때 잃는 것이 무엇인가.** 앞이 "아니오"이고 뒤가 클수록 붙인다.
C-2 와 C-3 은 이 규칙을 각각 반대 방향으로 적용한 결과다 — 빈도가 높아도 앞이 "예"라 뺐고(C-2),
빈도가 낮아도 뒤가 커서 붙였다(C-3).

### C-1. 붙일 곳

**인증 (필수) — 5갈래**

| #   | 시나리오                                                           | 통합 테스트가 볼 수 없는 것                                                                                                                                      |
| --- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 미로그인 → 보호 경로 → 로그인 → **원래 경로 복원**                 | proxy 가 심고 → URL 을 타고 → `page.tsx` 가 읽어 넘기는 **4단 릴레이**. 통합은 `returnTo` 를 prop 으로 손수 꽂아 시작하므로 앞 구간이 이어져 있는지 말할 수 없다 |
| 2   | 세션 만료(`expired` 노브) → 로그인 화면의 만료 안내                | `window.location.href` 로 일어나는 **전체 페이지 이동**. jsdom 은 따라가지 않아 화면이 만들어지지 않는다                                                         |
| 3   | 잘못된 자격 증명(`invalid` 노브) → 실패 문구, URL 은 `/login` 유지 | "머무른다"를 URL 로 확인하는 것. jsdom 에서 라우터는 아무 일도 안 하는 스텁이라 이동해도 컴포넌트가 남아 있다                                                    |
| 4   | `returnTo=//evil.com` 으로 로그인 → **origin 을 벗어나지 않음**    | 통합은 "코드가 계산한 목적지"까지만 본다. **브라우저가 우리 origin 에 남아 있는지**는 실제 이동이 있어야 알 수 있다                                              |
| 5   | 로그인·로그아웃 후 **헤더가 실제로 바뀜**                          | `router.refresh()` → 서버 재렌더 → 새 `isLoggedIn` prop → DOM 의 사슬. jsdom 에는 서버가 없어 첫 칸에서 멈춘다                                                   |

**인증 외 — 1갈래**

| #   | 시나리오                                                    | 고른 이유                                                                                                                                                                                                                                                       |
| --- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 6   | `/products/p1` 직접 진입 → 담기 → 주문 → **주문 완료 표시** | **돈이 움직이는 유일한 경로**다. 주문 시작 후 33.9%가 완료하지 못하는데, 그중 얼마가 마음이 바뀐 것이고 얼마가 고장인지 로그로는 가를 수 없다. 그리고 이 경로만 `POST /api/orders` 로 서버 상태를 바꾼다 — 다른 어떤 경로도 되돌릴 수 없는 결과를 만들지 않는다 |

### C-2. 빈도가 높은데 E2E 를 안 붙인 경로 — 담기

`cart_add` 는 세션의 **17.4%** 가 지나 상위 5위이고, 목록(100%)·상세(62.0%)는 그보다 높다.
그런데도 안 붙였다.

**8주차가 이미 덮고 있기 때문이다.**

- `e2e/cart-flow.spec.ts` — 목록 진입 → 담기 → 헤더 개수, 그리고 **새로고침 후에도 유지**.
  `persist` 의 localStorage 왕복과 Next hydration 을 한 번에 지나는 유일한 테스트다.
- `e2e/product-list-history.spec.ts` — 공유 링크 · 뒤로/앞으로 · 새로고침.
- 통합 `ProductListPage.dom.test.tsx` · `Header.dom.test.tsx` — 조건 변경에 목록이 반응하는지,
  담기가 헤더 개수로 이어지는지.

빈도 1위라는 이유로 목록·담기에 다시 붙이면 **같은 것을 두 번 사는 것**이다.

**다만 상세 화면은 다르다.** `/products/[id]` 는 9주차에 새로 만든 화면이고, 8주차 E2E 두 개는
상세 경로를 **한 번도 지나지 않는다**(`e2e/*.spec.ts` 에 `/products/` 진입이 0건). 그래서 상세의
담기·찜은 8주차 자산이 덮지 못한다 — 그 구간은 C-1 의 6번(주문 흐름)이 `/products/p1` 직접 진입으로
지나면서 함께 덮는다. 상세를 위한 별도 갈래를 만들지 않은 이유가 이것이다.

### C-3. 빈도가 낮은데 E2E 를 붙인 경로 — 인증

로그인은 세션의 **8.6%** 만 지나고 12개 이벤트 중 7위다. 순위만 보면 담기(17.4%)·페이지 이동(23.4%)보다
아래다. 그런데도 5갈래를 붙였다.

**로그만 보고 정하면 안 되는 이유가 여기 있다.**

- **빈도는 실패의 파급을 말하지 않는다.** 로그인이 막히면 `order_start`(5.6%)와 `order_complete`(3.7%),
  그리고 마이페이지가 **전부** 막힌다. 담기가 막히면 담기만 막힌다.
- **로그에는 실패한 사람이 안 남는다.** 로그인이 완전히 고장 나면 `login_start` 만 남고 `login_success`
  도 `login_fail` 도 안 남는다. 다음 달 로그에서 그 경로의 빈도는 오히려 **낮아 보인다.**
- **로그에 아예 없는 것이 있다.** `//evil.com` 같은 오픈 리다이렉트 시도는 정상 사용자 로그에 나타나지
  않는다. 빈도가 0인 경로인데 뚫리면 로그인 직후 신뢰가 가장 높은 시점에 외부 사이트로 나간다.
  **빈도가 아니라 실패 비용으로 고른 것**이다.
- **로그 스키마에 없는 화면이 있다.** 시드 로그 13종에 마이페이지·주문내역 진입 이벤트가 없다.
  헤더의 로그인 상태(5번)는 로그로는 근거를 만들 수 없고, "모든 화면에 걸친 전역 UI"라는 성질로 골랐다.

### C-4. 유지보수 비용 추정 — 1번(복원) 시나리오

이 시나리오 하나가 만지는 것:

| 무엇이 바뀌면                       | 고칠 곳                                                                |
| ----------------------------------- | ---------------------------------------------------------------------- |
| 로그인 폼의 라벨(이메일 / 비밀번호) | 셀렉터 2곳                                                             |
| 로그인 버튼 문구                    | 셀렉터 1곳                                                             |
| `returnTo` 파라미터 이름            | `shared/config/routes.ts` 1곳 (spec 이 상수를 import 하면 spec 은 0곳) |
| 보호 경로 목록                      | `PROTECTED_ROUTES` 1곳 + spec 의 진입 경로 1곳                         |
| 헤더의 장바구니 문구                | spec 의 진입 클릭 1곳 — 이 시나리오는 헤더에서 주문서로 들어간다       |
| 주문 내역 화면의 제목               | 도착 확인 단언 1곳                                                     |

**화면 문구가 바뀌면 5곳**이다. `getByRole` + 이름 기반 셀렉터를 쓰므로 DOM 구조가 바뀌어도 안 깨지지만,
**사용자에게 보이는 문구가 바뀌면 그만큼 깨진다.** 이건 비용이자 의도된 신호다 — 로그인 폼의 라벨이
바뀌면 그걸 읽는 스크린리더 사용자에게도 바뀐 것이므로, 조용히 지나가면 안 된다.

한 갈래당 유지비가 이 정도라, 인증 5갈래는 **문구 변경 한 번에 최대 20여 곳**이 될 수 있다. 그래서 인증
외에는 1개만 골랐다.

### C-5. 알려진 한계

- **SSR 단계에서는 미로그인과 만료를 구분할 수 없다.** 서버 레이아웃은 세션 쿠키의 **존재 여부**만 보고
  서명을 검증하지 않으므로, 만료된 세션도 초기 HTML 에는 로그인 상태로 그려진다. 실제 만료는 클라이언트가
  `/api/auth/me` 에서 401 을 받은 뒤에야 드러난다. 2번 시나리오가 보는 것은 "만료가 감지된 뒤"이지
  "만료된 채 첫 화면이 그려지는 순간"이 아니다.
- **이벤트 발화를 지키는 자동 검증이 없다.** 계측 이벤트의 이름과 props 는 자주 바뀌는 분석 정책이고,
  `shared/lib/analytics/events.ts` 가 이미 그 단일 정의여서 테스트가 props 를 다시 적으면 두 벌이 된다.
  E2E 로도 올리지 않기로 했으므로 **계측이 끊겨도 아무도 알려주지 않는다.** 5단계 뮤테이션에서 계측 훅
  호출을 지웠을 때 살아남는 것으로 이 공백이 기록될 것이다.
- **`totalPrice` 를 남기지 않아 객단가를 집계할 수 없다.** 장바구니가 가격을 갖고 있지 않아 뺐다.
  시드 로그와 같은 기준으로 매출 지표를 비교하려면 주문서에 상품 가격 조회를 붙여야 한다.
- **탭을 두 개 열면 세션이 둘로 세진다.** B절의 모든 세션 기준 수치가 그만큼 부풀어 있을 수 있다.
