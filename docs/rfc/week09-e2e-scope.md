# RFC: Week 09 — E2E 범위: 인증과 비싼 테스트를 어디에 붙일 것인가

브랜치 `feat/week-09` · 상태: 1·2단계 구현 완료, 3단계 설계 · 작성 2026-09-04

**이 문서의 구성** — A절은 2단계에서 정한 이벤트 스키마, B절은 시드 로그 분석, C절은 그 근거로 정한 E2E 범위다. 이 문서는 E2E 코드보다 먼저 커밋한다(과제 규칙). 4단계(구현)는 C절의 표만 만들고, 5단계(자가 검증) 기록은 부록으로 뒤에 붙인다.

E2E 한 번은 production build 위에서 mock API 500ms 고정 지연을 실제로 기다린다. 통합 테스트가 수백 ms 에 끝나는 일을 E2E 는 수십 초에 하므로, **로그가 말하는 곳과 로그가 말하지 못하는 곳을 갈라 붙일 자리를 정한다.**

**빨리 훑을 때** — 노이즈 기준 §B.1, 필터 전후 표 §B.2, 붙일 곳·안 붙일 곳 §C.1~C.3, 유지보수 비용 §C.4.

## A. 이벤트 스키마

### A.1 이름 규칙과 경계

- **이름은 시드 로그 스키마를 그대로 쓴다.** `snake_case`, `<대상>_<행위>`. 계측 스키마는 팀이 합의하는 것이라 이미 있는 이름에 맞추는 것이 목적이다. 새 이름을 만들지 않았다.
- **이름과 프로퍼티 타입은 `src/shared/analytics/events.ts` 한 곳에 있다.** 화면 코드는 `trackEvent(name, props)` 만 부르고, 이름·프로퍼티가 스키마에 없으면 타입 에러다. `button_click` 같은 이름이 들어올 자리가 없다.
- **컴포넌트는 스타터 로거(`src/analytics/*`)를 직접 부르지 않는다.** `shared/analytics` 한 겹만 부른다. eslint 하네스에 `@/analytics/*` 를 shared 밖에서 금지하는 규칙을 추가했다(`eslint.config.mjs`). 한 겹을 둔 이유는 두 가지다 — (1) 스키마 강제, (2) 나중에 실제 도구(GA4·Amplitude)를 붙일 때 `setupAnalytics()` 의 provider 목록만 바꾸면 된다.
- 스타터 로거는 손대지 않았다(`git diff 39707de6 -- src/analytics` 빈 diff).

### A.2 공통 프로퍼티 (`setCommonProperties`)

| 키          | 값                                                      | 근거                                                                          |

### A.4 identify · reset · initAnalytics 의 자리

- **`identify()`·`reset()` 은 세션 상태 전이가 유일한 출처다.** `entities/session/model/use-session.ts` 의 effect 가 `user.id` 가 바뀔 때 `identifyUser` / `resetUser` 를 부른다. 로그인 폼·로그아웃 버튼·만료 처리가 각자 부르지 않는다. 같은 값이면 무시하므로(`identifyUser` 는 현재 id 와 같으면 no-op) `useSession` 이 여러 곳에 마운트돼도 한 번만 나간다. 예외 하나 — `login_success` 이벤트에 `userId` 를 싣기 위해 `use-login.ts` 가 `identifyUser` 를 먼저 부른다. effect 는 그 뒤에 같은 id 를 보고 무시한다.
- **`initAnalytics()` 는 루트 `Providers` 안의 `<AnalyticsInit/>` effect 에서 부른다.** 이 위치를 택한 이유는 모든 라우트가 지나는 유일한 클라이언트 경계라는 것 하나다. 첫 화면의 진입 이벤트(`product_list_view` 등)가 이 effect 보다 먼저 `track()` 되어도(형제·자식 effect 순서에 따라 그럴 수 있다) 두 가지가 지켜진다 — (1) 로거 큐가 초기화 전 이벤트를 담아 두고 초기화 직후 순서대로 내보내므로 **손실이 없다**, (2) 공통 프로퍼티(`setCommonProperties`)와 프로바이더 등록은 `trackEvent` 가 첫 호출 때 동기로 보장하므로 **첫 이벤트에도 `sessionId·device·ts` 가 붙는다**. 즉 `<AnalyticsInit/>` 의 트리 안 위치는 결과에 영향을 주지 않는다(검토에서 "자식 effect 가 먼저라서 된다" 는 초안의 근거가 틀렸음을 확인하고, 순서에 의존하지 않도록 고쳤다).
- 진입 이벤트는 `useTrackOnMount` 가 마운트당 한 번만 보낸다. dev StrictMode 의 effect 재실행, `enabled` 의 재진입에도 1회다 — 시드 로그에서 노이즈로 걸러낸 "완전 동일 줄"(§B.1)을 우리 계측이 스스로 만들지 않기 위해서다.

### A.5 로그인부터 주문까지 예측되는 순서

문서만 읽고 예측할 수 있어야 한다(완료조건). 익명으로 `/products` 진입 → 담기 → 헤더 장바구니 → 로그인 → 주문서 → 주문하기:

```
product_list_view {category, sort, page, hasQuery}            (userId 없음)
cart_add          {productId, quantity:1}                     (userId 없음)
login_start       {from:"cart"}                               (userId 없음)
identify u7
login_success     {from:"cart"}                               userId:"u7"
order_start       {productIds:[…], itemCount}                 userId:"u7"
order_complete    {orderId, productIds, itemCount, totalPrice} userId:"u7"
```

로그아웃하면 `reset` 이 한 번 나가고 이후 이벤트에 `userId` 가 빠진다. 로그인 상태로 새 탭을 열면 서버가 준 초기 세션으로 `identify` 가 먼저 나간다. 익명으로 처음 들어온 탭에서는 `reset` 이 나가지 않는다(이미 익명이면 no-op). 2단계 런타임 검증(production build, 2026-09-04)에서 관측한 순서가 위와 정확히 같았다.

### B.2 경로 표 — 세션 기준

**묶은 기준** — 이벤트 하나가 화면 하나인 것은 그대로, 목록 화면 안의 조작 세 개(카테고리·정렬·페이지)는 "목록 조작" 으로 묶었다. 같은 화면에 머무는 행동이고 8주차에 한 묶음으로 검증했기 때문이다.

**분모** — 비율은 **필터 후 사람 세션 7,514** 대비다. 필터 전 표의 분모는 8,000.

**이탈률 정의** — "그 경로를 지난 세션 중 **다음 단계 이벤트가 없는** 비율"(퍼널). 다음 단계: 목록·목록 조작→상세, 상세→담기 또는 찜, 담기→로그인 시작 또는 주문서, 로그인 시작→로그인 성공, 로그인 성공→주문서, 주문서→주문 완료. "세션의 마지막 이벤트였던 비율" 은 다른 값이 나온다(예: 로그인 시작 0% vs 9%) — 로그인 시작 뒤엔 성공/실패가 반드시 따라와서 마지막일 수 없기 때문에, 퍼널 정의를 쓴다.

**실패 비용** — 실패로 센 이벤트: `client_error`(상세), `login_fail`(로그인). 비율과 함께 "이 화면이 막히면 뒤따라 막히는 것" 을 쓴다.

### B.3 필터 전후 비교

| 경로       | 세션(전 → 후) | 순위(전 → 후) | 이탈률(전 → 후) |
| ---------- | ------------- | ------------- | --------------- |
| 목록 진입  | 8,000 → 7,514 | 1 → 1         | 41.8% → 38.0%   |
| 나머지 9개 | 변화 없음     | 변화 없음     | 변화 없음       |

**순위는 하나도 바뀌지 않았다.** 이유는 봇이 목록 진입 하나만 남기고 떠났기 때문이다 — 486 세션이 모두 1위 경로에만 더해졌고 1위는 이미 압도적(2위의 1.6배)이었다. 중복 77줄은 세션 기준 집계에서는 애초에 세지지 않는다(같은 세션이 같은 경로를 두 번 지나도 1세션). **바뀐 것은 이탈률이다** — 목록 진입 이탈률이 3.8%p 부풀려져 있었다. 봇을 안 걸렀다면 "목록에서 상세로 못 넘어가는 사람이 42%" 라고 읽었을 것이다. 순위가 안 바뀐 것도 결과다: 이 로그에서 노이즈는 순위가 아니라 **비율을 왜곡** 한다.

## C. 붙일 곳과 안 붙일 곳

E2E 시나리오는 **인증 + 최대 2개** 다. B 표를 놓고 고른 결과는 **인증 + 주문 완료 플로우, 총 2개** 다. 시나리오 선택은 AI 가 아니라 작성자가 했다 — AI 는 B 표의 집계와 후보의 장단점을 정리했고, 어느 것을 붙일지는 표를 보고 직접 정했다(하나도 안 붙이는 선택지와 로그아웃 정리를 셋째 시나리오로 두는 선택지를 놓고 비교했다).

### C.1 붙이는 곳

**① 인증 플로우 — 필수, 빈도는 낮은데 붙인다.** 로그인 시작은 사람 세션의 8.6% 에서만 일어난다. 빈도만 보면 10개 중 5위다. 그런데 로그인 관문 뒤에 주문·마이페이지가 전부 서 있고, 로그인이 막히면 그 뒤의 세션 7.8% 가 통째로 0 이 된다. 로그만 보고 정할 수 없는 이유가 하나 더 있다 — **인증의 핵심 동작은 브라우저와 서버의 경계에 산다.** proxy 리다이렉트(요청이 페이지에 닿기 전), httpOnly 쿠키(JS 가 못 본다), 서버 렌더된 초기 HTML 의 로그인 상태, 로그인 후 `router.refresh` 와 라우터 캐시 — jsdom 은 이 중 어느 것도 재현하지 못한다. 1단계 런타임 검증에서 **통합 테스트 145개가 전부 초록인데 브라우저에서만 재현되는 결함 2개**(로그인 후 주문서 복귀 실패 — prefetch 캐시, 주문 후 이동 유실 — 언마운트 타이밍)가 나왔다. 그 두 개가 이 시나리오의 존재 이유다.

세 갈래(과제 요구):

| 갈래                                     | 재현                                                             | 단언                                                                                                            |
| ---------------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 보호 경로 진입 → 로그인 → 원래 경로 복원 | 미로그인으로 `/orders` 진입                                      | URL `/login?next=%2Forders` → 폼 로그인 → URL `/orders`, 헤더 `루퍼N님`                                         |
| 세션 만료 경계                           | `storageState` 로그인 + `scenario=expired` 쿠키로 `/mypage` 진입 | URL `/login?next=%2Fmypage&reason=expired`, alert `세션이 만료되었어요`, 헤더에 `로그인` 링크(죽은 쿠키 정리됨) |
| 잘못된 자격 증명                         | 틀린 비밀번호                                                    | alert `이메일 또는 비밀번호를 확인해주세요.`, URL 은 `/login` 유지                                              |

덧붙이는 경계 두 개(같은 파일, 개수를 늘리는 게 아니라 세 갈래의 경계): 복원 경로가 외부 주소(`next=https://evil.com`)면 `/` 로 떨어진다 · JavaScript 를 끈 컨텍스트(`javaScriptEnabled: false`)로 `/mypage` 를 열어도 헤더에 인사말·로그아웃이 보이고 로그인 링크가 없다(초기 HTML 의 로그인 상태). 익명 컨텍스트에는 로그인 링크가 있어야 한다 — 헤더가 서버에서 아예 렌더되지 않아도 앞 단언이 통과하는 일을 막는 양성 단언이다.

**② 주문 완료 플로우 — 로그 근거로 고른 하나.** 담기 → 헤더 장바구니 → (로그인 상태) 주문서에 상품·금액 → 주문하기 → 주문 내역에 새 주문 1건 추가. 세션 비율 3.7% 로 낮지만 유일한 매출 경로고, 8주차에 검증된 적이 없으며(화면이 이번 주에 생겼다), 통합 테스트가 못 보는 것이 둘 있다 — (a) 주문 저장소가 Route Handler 프로세스 메모리에 있어 **저장 → 재조회 왕복은 실제 서버에서만** 성립하고, (b) 주문 성공 후 `router.push("/orders")` 가 장바구니 비움과 경쟁하는 타이밍은 1단계에서 실제로 유실됐던 결함이다. 상대 개수로 단언한다(실행 누적 대비 +1건).

### C.2 안 붙이는 곳

- **목록 조작(2·3위, 60.5%) — 빈도는 높은데 E2E 를 안 붙인다.** 이 경로가 지키려는 사실은 "조작 ↔ 요청 파라미터 ↔ 목록 교체" 의 계약이고, 8주차 통합 8~11 이 `NuqsTestingAdapter` + MSW 로 정확히 그것을 지킨다. 브라우저만 가진 사실(히스토리·reload)은 이미 E2E 13·14 가 지난다. 여기 E2E 를 더 붙이면 같은 사실을 100배 비싸게 두 번 지키는 것이다. "빈도 1위니까 E2E" 는 8주차에 이미 무엇으로 검증했는지 확인하면 답이 나온다.
- **상세 진입(2위, 62%)** — 화면이 없다. 로그 스키마가 구현보다 앞서 있는 경우로, 없는 화면을 만들지 않는다. 계측(A.3)에서도 뺐다.
- **목록 진입 → 담기 스모크** — 8주차 E2E 15 가 찜 버튼으로 동형 경로를 지난다. 담기는 ②의 첫 단계로 한 번 지나가면 충분하다.
- **위시리스트** — E2E 15 그대로.

### C.3 4단계에 들어갈 테스트 (이 문서만 읽고 예측 가능해야 한다)

| 파일                         | storageState | 테스트                                                                                                                                       |
| ---------------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `e2e/auth.spec.ts`           | **안 씀**    | 복원(+외부 주소 차단), 자격 증명 실패, 초기 HTML 로그인 상태                                                                                 |
| `e2e/session-expiry.spec.ts` | 씀           | `scenario=expired` → 만료 안내 · 죽은 쿠키 정리                                                                                              |

### C.4 유지보수 비용 추정 — 인증 시나리오

문구·구조가 바뀌면 몇 군데를 고치나:

| 변경                                             | 고칠 곳                                                                                                                                        | 개수      |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| 폼 라벨(`이메일`·`비밀번호`)·버튼(`로그인`) 문구 | Page Object `e2e/pages/login-page.ts` 의 로케이터                                                                                              | 1파일 3줄 |
| 만료·실패 안내 문구                              | 단언 2곳(만료 1, 실패 1) — 문구를 상수로 두면 1곳                                                                                              | 2 → 1     |

셀렉터를 역할·이름으로 두고 문구·URL 상수를 공유하면 **가장 흔한 변경(문구)은 1파일**, 구조 변경은 4곳에서 멈춘다. 이 추정을 넘어가면 시나리오를 줄이거나 통합으로 내리는 신호로 본다.

### A.1 살아남은 것에 대한 대응

- **5번은 동치 뮤턴트** 라 테스트로 잡을 수 없고 잡을 필요도 없다. 대신 코드 주석이 잘못된 인과("순서가 지킨다")를 말하고 있어 고쳤다.
- **5′ 은 통합 테스트의 공백** 이었다. 버튼 컴포넌트만 렌더하는 테스트는 "주문 성공 → 장바구니 비움 → 주문서가 빈 상태 분기로 바뀜 → 버튼 언마운트" 를 재현하지 못한다. `src/_pages/checkout/ui/checkout-page.dom.test.tsx` 를 추가했다 — 주문서 전체를 렌더하고 주문 뒤 빈 화면으로 바뀐 다음에도 `router.push("/orders")` 가 호출됐는지 본다. 5′ 뮤턴트를 다시 넣고 돌려 실패하는 것을 확인했다.
- **통합으로도 잡히게 된 5′ 을 두고 주문 플로우 E2E 를 남길 이유가 있나** — 있다. 이 시나리오가 지키는 사실 중 "주문 저장 → 주문 내역 재조회에서 +1" 은 Route Handler 프로세스 메모리의 주문 저장소를 실제로 거쳐야 하고, MSW 는 그 왕복을 흉내낼 뿐이다(핸들러가 `{orders: []}` 를 돌려주도록 우리가 정한다). 이동 유실은 통합으로 내렸고, E2E 에는 서버 왕복과 로그아웃 뒤 재잠금이 남는다.
- 3·6번처럼 **통합·단위가 함께 잡는 항목** 은 E2E 의 존재 이유가 아니다. 그 둘은 인증 시나리오의 경계 케이스로 같은 파일에 얹혀 있어 추가 비용이 수 초라 남겼다. 인증 E2E 가 이 둘만 잡는 시나리오였다면 지웠을 것이다.

| 스토리지      | `test-results/.auth/worker-{parallelIndex}.json`, 실행마다 새로 로그인                                | 파일을 갈라야 storageState 가 섞이지 않는다. TTL 1시간이라 디스크 재사용은 하지 않는다                            |
| 데이터        | 주문 개수는 "내 계정 +1" 상대 단언                                                                    | 서버 프로세스가 실행 사이에 살아 있으면 주문이 누적된다                                                           |
| 장바구니·위시 | 갈 필요 없음                                                                                          | persist 가 없어 storageState 에 실리지 않는다 — 모든 테스트가 0 에서 시작한다                                     |

세션은 무상태 HMAC 이라 만료 테스트의 "죽은 쿠키 정리(logout)" 와 주문 플로우의 로그아웃은 **그 컨텍스트의 쿠키만** 지운다. 워커 저장 파일과 다른 테스트의 토큰은 그대로다.

### B.2 결정론 (2026-09-04, production build)

| 명령                         | 결과                         | 시간     |
| ---------------------------- | ---------------------------- | -------- |
| `--workers=4` × 3회 연속     | 12 passed × 3                | 7.8~7.9s |
| `--workers=1`                | 12 passed                    | 18.3s    |
| `--workers=8` × 15회         | 12 passed × 14, **1회 실패** | 7.2~8.8s |
| (경합 수정 후) `--workers=4` | 12 passed                    | 8.0s     |

통과 집합은 워커 수와 무관하게 같은 12개다. **8워커 15회 중 1회 실패는 테스트가 아니라 앱의 경합이었다** — 로그인 화면이 마운트되면서 미인증 세션 재확인(`GET /api/auth/me`, 500ms 지연)이 나가고, 그 401 이 도착하기 전에 로그인이 성공해 세션 캐시가 채워지면 `SessionBoundary` 가 뒤늦은 401 을 "로그인 상태였는데 401 = 만료" 로 읽어 `/login?reason=expired` 로 되돌렸다. 워커 8개가 단일 `next start` 를 두드릴 때 `me` 응답이 밀려 창이 넓어졌다. 수정: 로그인 성공 시 진행 중인 세션 쿼리를 `cancelQueries` 로 취소하고(`use-login.ts`), `getSession` 이 `AbortSignal` 을 받아 요청 자체를 중단한다. 같은 순서를 jsdom 에서 재현하는 회귀 테스트를 `login-form.dom.test.tsx` 에 두었다. 통합 테스트 전부가 초록인 상태에서 병렬 E2E 만이 드러낸 결함이라, C.1 의 "인증은 로그만 보고 정할 수 없다" 는 근거가 하나 더 늘었다.

### B.3 trace 를 직접 읽은 기록

1. `e2e/auth.spec.ts` 의 자격 증명 실패 테스트에서 기대 문구를 `"비밀번호가 틀렸습니다."` 로 고의로 틀리게 바꿨다.
2. `pnpm exec playwright test e2e/auth.spec.ts --trace=on --workers=1` → 1 failed, `test-results/auth-자격-증명이-틀리면-…-chromium/trace.zip` 생성.
3. `pnpm exec playwright show-trace <그 경로>` 로 연다. 액션 6개 중 `expect.toHaveText` 하나만 빨갛다 — `newPage`·`goto /login`·`fill`×2·`click` 은 전부 44ms 이내에 끝났고, 네트워크 탭에 `POST /api/auth/login → 401` 이 t+150ms 에 시작해 t+655ms 에 끝나 있다. 실패한 단언은 5,010ms 를 기다리며 9번 폴링했는데 매번 alert 요소 `이메일 또는 비밀번호를 확인해주세요.` 를 찾았다.
4. **읽은 것** — "느려서 못 기다린" 것이 아니다. 단언이 시작될 때 서버 응답과 alert 렌더는 이미 끝나 있었고, 셀렉터도 맞았으며, 기대 문자열만 틀렸다. 앱을 고칠 일이 아니라 기대값을 고칠 일이라는 판단이 trace 한 장에서 나온다. 단언을 원래대로 되돌렸다.

### B.4 8주차 환경에서 바꾼 것

- `reuseExistingServer: !CI` → `false`. 로컬에 `next dev` 가 3000 에 떠 있으면 dev 빌드 위에서 조용히 돌 수 있었다. 이제 항상 production 서버를 Playwright 가 직접 띄우고, 포트가 점유돼 있으면 재사용 대신 실패한다.
- `workers: isCI ? 2 : 4`, `retries: 0`, `trace: "retain-on-failure"`, `fullyParallel: true` 추가. 재시도를 0 으로 둔 것은 B.2 의 경합처럼 **간헐 실패를 재시도로 덮지 않기 위해서** 다.
