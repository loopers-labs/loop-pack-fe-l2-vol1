# 9주차 E2E 범위 설계

> [과제 문서](../assignments/week-09.md) 3단계에 대한 답이다. 이 문서는 E2E 코드보다 먼저 커밋한다.
>
> 2단계에서 정한 이벤트 스키마(§A), 시드 로그를 집계해 낸 상위 경로와 노이즈 기준(§B), 그 근거로 정한 붙일 곳과 안 붙일 곳(§C)이 있다. **이 문서만 읽어도 판단과 근거가 닫히도록 필요한 내용은 본문에 옮겼고, 아래 링크는 참고용이다.**
>
> 참고 — [1단계 설계 판단 기록](../week-09/decisions.md) · [2단계 이벤트 계측 범위](../week-09/event-instrumentation-scope.md) · [화면별 role·이름과 URL 계약](../week-09/test-cases.md)

## 요약

- **E2E 3개를 만든다** — ① 인증 플로우 ② 담기 → 장바구니 이동 → 담은 상품 확인 ③ 주문 → 주문내역 확인. ([§C](#e2e로-만들-시나리오))
- **목록·필터·정렬·페이지는 안 붙인다** — §B 1·2·3·5위로 빈도는 높지만, 8주차 통합 테스트가 이미 덮고 있고 실제 브라우저 경계가 추가되지 않는다. ([§C](#빈도가-높은데-안-붙인-경로))
- **집계는 세션 기준.** 노이즈 세 기준(봇 · 중복 전송 · 오류 이벤트)으로 8,000 → 7,514세션. **거르기 전후 순위는 바뀌지 않았고**, 세션 기준을 고른 것이 그 이유다. ([§B](#거르기-전후-순위))
- **로그 순위만으로 정하지 않았다** — 시드 2위 `product_detail_view`는 이 앱에 화면이 없어 빠지고([§C](#계측했지만-대상에서-빠지는-경로)), 빈도가 낮은 인증·주문 완료는 실패 비용 때문에 넣었다([§C](#빈도가-낮은데-붙인-경로)).
- **유지보수 비용** — 2번 시나리오 기준, 문구 변경 2군데 · 상품명 변경 3군데 · 구조 변경 최대 3군데. 가장 넓게 퍼진 것은 문구가 아니라 상품명이다. ([§C](#유지보수-비용-추정))

### 테스트 계층을 고르는 순서

1. 컴포넌트를 렌더링하지 않고 값이나 상태만 확인해도 되는가? → **단위 테스트**
2. 렌더링된 요소와 상호작용하면 충분한가? → **통합 테스트**
3. 실제 브라우저의 탐색·렌더링·API가 있어야 재현되는가? → **E2E 후보**

### E2E 후보의 우선순위를 고르는 기준

E2E 후보가 여러 개라면 다음 질문으로 우선순위를 정한다.

1. 실패하면 사용자가 핵심 목표를 완료하지 못하는가?
2. 실패가 주문·결제 기회 손실이나 추가 비용으로 이어지는가?

## A. 이벤트 스키마

2단계에서 정한 내용이다. 판단 과정과 대안 검토는 [이벤트 계측 범위 문서](../week-09/event-instrumentation-scope.md)에 있고, 여기에는 3단계 집계에 필요한 결과만 옮긴다.

### 이름 규칙

이벤트 이름은 `오브젝트_행동(동사)` 순서의 소문자 스네이크 케이스로 쓴다.

- 오브젝트를 먼저, 사용자의 행동을 동사로 뒤에 쓴다 — `wishlist_add`, `order_complete`
- 행동을 시작했는지 완료했는지 구분되도록 시점을 드러내는 동사를 쓴다 — `view` · `start` · `add` · `remove` · `success` · `fail` · `complete`
- 구현 요소가 아니라 분석하려는 행동을 이름으로 삼는다 — `button_click`이 아니라 `order_start`
- **같은 의미의 행동에 화면이나 버튼 위치에 따라 다른 이름을 만들지 않는다.** 위치 차이는 프로퍼티로 구분한다

목록 조회 성공과 사용자의 조건 변경은 서로 다른 사건으로 구분한다. `product_list_view`는 결과가 실제 표시된 시점이고, `category_filter_change`·`sort_change`·`page_change`는 사용자가 화면에서 조건을 직접 조작한 시점이다. 이렇게 나눠 앞·뒤 이동이나 URL 복원을 구매 의도로 세지 않는다.

### 공통 프로퍼티

`setCommonProperties()`로 등록하고 이벤트 발생 시점에 평가한다. 개별 `track()` 호출에는 이벤트별 프로퍼티만 넘긴다.

| 프로퍼티    | 값                            | 언제 평가되나    | 넣은 이유                                              |
| ----------- | ----------------------------- | ---------------- | ------------------------------------------------------ |
| `sessionId` | `sessionStorage`의 탭 단위 값 | 이벤트 발생 시점 | 세션 기준 집계의 단위. 탭 세션 내내 같은 값을 유지한다 |
| `device`    | `desktop` 고정                | 이벤트 발생 시점 | PC 전용 과제라 viewport 분류 로직을 두지 않는다        |
| `ts`        | ISO 8601 UTC                  | 이벤트 발생 시점 | 순서와 간격 집계의 기준                                |
| `userId`    | 로그인 시에만                 | 이벤트 발생 시점 | 로그인 전후 행동을 같은 세션 안에서 구분한다           |

`flow_id`는 모든 이벤트에 붙지 않으므로 공통 프로퍼티가 아니라 로그인·주문 퍼널의 이벤트별 프로퍼티로 둔다. 키 이름은 시드 로그의 `sessionId`·`userId`를 그대로 써서 집계 시 이름 매핑을 만들지 않는다.

### 계측 지점과 이벤트

| 조작                             | 이벤트                             | 함께 실리는 값                                                                |
| -------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------- |
| 목록 조회 성공                   | `product_list_view`                | `page` · `category` · `sort`. 같은 조합 재렌더에는 중복 기록하지 않는다       |
| 카테고리 직접 변경               | `category_filter_change`           | 변경한 `category`                                                             |
| 정렬 직접 변경                   | `sort_change`                      | 변경한 `sort`                                                                 |
| 페이지 직접 변경                 | `page_change`                      | 변경한 `page`                                                                 |
| 담기                             | `cart_add`                         | `product_id` · `quantity`                                                     |
| 장바구니 개별 삭제 · 전체 비우기 | `cart_remove`                      | `product_id`. 전체 비우기는 담긴 항목 수만큼 기록                             |
| 찜 켜기 / 끄기                   | `wishlist_add` / `wishlist_remove` | `product_id`. 토글 전 상태로 이벤트를 나눈다                                  |
| 위시리스트 진입                  | `wishlist_view`                    | `entry_point` — `header_wishlist` · `mypage_wishlist` · `direct`              |
| 로그인 화면 표시                 | `login_start`                      | `flow_id` · `entry_point` · `return_path` · (담기·찜에서 왔으면) `product_id` |
| 로그인 성공                      | `identify()` → `login_success`     | 같은 `flow_id`. 이후 모든 이벤트에 `userId`가 붙는다                          |
| 로그인 실패                      | `login_fail`                       | 같은 `flow_id` 유지                                                           |
| 주문 요청 시작                   | `order_start`                      | `flow_id` · `product_ids`                                                     |
| 주문 성공                        | `order_complete`                   | `flow_id` · `order_id` · `product_ids`. 이후 `flow_id` 폐기                   |
| 로그아웃 성공                    | `logout_complete` → `reset()`      | 그 뒤 `flow_id`·`userId` 없음                                                 |

`login_start`의 `entry_point`는 `header_wishlist` · `header_cart` · `header_login` · `product_wishlist` · `product_cart` · `protected_route` 여섯 개로 제한한다. 가드가 만든 로그인 URL에는 `entryPoint`가 없어 `protected_route`로 간주한다. `return_path`는 `toSafeReturnPath()`를 거친 내부 경로만 기록한다.

`flow_id`는 로그인 화면이 뜰 때 만들어져 `sessionStorage`에 남고, 주문 완료 또는 로그아웃에서 지워진다. 담기 → 로그인 → 주문까지 한 번에 통과하면 다섯 이벤트가 같은 값을 단다.

### 시드 로그와의 매핑

| 시드 로그 이름           | 이 앱의 이름             | 관계                      | 비고                                                                   |
| ------------------------ | ------------------------ | ------------------------- | ---------------------------------------------------------------------- |
| `product_list_view`      | `product_list_view`      | 같은 이름, 발생 범위 다름 | 시드는 목록 진입, 앱은 조건 변경을 포함해 조회 결과가 실제 표시된 시점 |
| `category_filter_change` | `category_filter_change` | 동일                      | 사용자가 카테고리를 직접 변경한 시점                                   |
| `sort_change`            | `sort_change`            | 동일                      | 사용자가 정렬 조건을 직접 변경한 시점                                  |
| `page_change`            | `page_change`            | 동일                      | 사용자가 페이지를 직접 변경한 시점                                     |
| `product_detail_view`    | 없음                     | **시드에만 존재**         | 상세 화면과 이동 경로가 없어 계측하지 않는다                           |
| `cart_add`               | `cart_add`               | 동일                      | 그대로 사용                                                            |
| `wishlist_add`           | `wishlist_add`           | 동일                      | 그대로 사용                                                            |
| `login_start`            | `login_start`            | 동일                      | 로그인 화면이 실제 표시된 시점으로 기록                                |
| `login_success`          | `login_success`          | 동일                      | 그대로 사용                                                            |
| `login_fail`             | `login_fail`             | 동일                      | 그대로 사용                                                            |
| `order_start`            | `order_start`            | 같은 이름, 의미 다름      | 시드의 주문서 진입을 이 앱의 주문 요청 시작으로 매핑                   |
| `order_complete`         | `order_complete`         | 동일                      | 주문 API 성공 후 기록                                                  |
| `client_error`           | 없음                     | 시드에만 존재             | 기술 관측 영역으로 보고 2단계 사용자 행동 계측에서 제외                |
| —                        | `cart_remove`            | 앱 확장                   | 담은 뒤 제거한 흐름을 보기 위한 이벤트                                 |
| —                        | `wishlist_view`          | 앱 확장                   | 위시리스트 유입 경로 분석                                              |
| —                        | `wishlist_remove`        | 앱 확장                   | 찜 해제                                                                |
| —                        | `logout_complete`        | 앱 확장                   | 로그아웃 성공                                                          |

시드에만 있는 이벤트 중 `product_detail_view`와 `client_error`는 화면이나 계측 대상 자체가 없어 빠진다. 조건 변경 세 개는 사용자의 직접 조작을 나타내는 이벤트로 앱에서도 같은 이름을 사용한다.

## B. 시드 로그 분석

집계 대상은 `fixtures/events-30d.jsonl`이다. 30일 · **22,427 이벤트 · 8,000 세션**. 필드 설명은 [`docs/fixtures/events.md`](../fixtures/events.md)에 있다.

기준을 먼저 정하고 그다음 집계했다. 기준 없이 스크립트부터 쓰면 코드에 박힌 임계값이 판단이 되어 버린다.

### 집계 기준

- **경로의 단위** — **이 앱의 이벤트 단위.** `product_list_view`와 `category_filter_change`·`sort_change`·`page_change`를 서로 다른 경로로 센다. 직접 조작과 조회 성공 결과를 구분해야 앞·뒤 이동이나 URL 복원을 구매 의도로 세지 않기 때문이다.
- **순위의 기준** — **세션 수.** 이벤트 수로 세면 한 사람이 여러 번 한 행동이 부풀려진다.
- **비율의 분모** — **전체 세션 8,000으로 고정.** 노이즈를 거른 뒤에도 분모를 바꾸지 않아, 거르기 전후 값을 같은 축에서 비교한다.
- **경로별 세션 마지막 비율** — 해당 이벤트를 거친 세션 중 그 이벤트가 마지막이었던 세션의 비율이다. 경로 전체를 같은 축에서 비교하기 위한 참고값이며, 구매 의도를 보인 사용자의 이탈률과는 구분한다.
- **구매 의도 이탈률의 정의** — `category_filter_change`·`sort_change`·`page_change` 중 하나 이상을 직접 조작한 세션을 분모로 삼고, 그중 조건 변경 이후 핵심 구매 행동인 `cart_add`로 넘어가지 않은 세션을 분자로 삼는다. 앞·뒤 이동과 URL 복원은 조건 변경 이벤트가 없으므로 제외한다. 시드 로그는 조건 변경 뒤 `product_list_view`를 다시 기록하지 않아 목록 표시 성공 여부를 확인할 수 없으므로, 조건 변경 자체를 구매 의도의 대리 지표로 사용한다. 조회 실패·지연은 행동 이탈률이 아니라 오류 관측 영역으로 보고 이번 집계에서 다루지 않는다. `wishlist_add`는 결제로 직접 이어지는 핵심 행동이 아니라 관심을 보류한 보조 행동으로 보고 성공 분자에 합치지 않는다.
- **실패로 센 이벤트** — **`login_fail`.** `client_error`는 §A에서 계측 대상에서 제외했고, 시드에서도 100% 상세 화면 직후에만 발생해 이 앱에 대응 경로가 없다.

**변화에 대한 해석**

순위가 안 바뀐 이유는 집계를 **세션 기준**으로 했기 때문이다. 중복 전송은 같은 세션 안에서 같은 이벤트를 두 번 세는 것이라 "그 세션이 그 경로를 지났는가"에는 영향이 없고, `client_error`는 다른 경로와 섞이지 않은 독립 행이다. 이벤트 수 기준으로 셌다면 중복 77건이 목록 계열에만 얹혀 있어 순위가 움직였을 것이다. 세션 기준을 고른 것이 노이즈에 대한 방어로도 작동한 셈이다.

목록 한 행이 움직인 것은 봇으로 거른 486세션이 전부 `product_list_view` 하나짜리 세션이라, 세션 수와 "마지막이었던 횟수"가 함께 줄었기 때문이다. 나머지 경로는 세션 수·비율·이탈률이 모두 그대로다.

| `order_start`       | 419     | 5.2%      | 71.5%     |
| `order_complete`    | 277     | 3.5%      | 66.1%     |

**실패(`login_fail`)의 규모**

  └ 끝내 성공하지 못한 세션 58 = login_start의 9.0%

2번은 8주차 계획의 15번을 현재 UI 계약에 맞게 갱신한 시나리오다. ProductCard의 담기 버튼은 더 이상 toggle하지 않고 추가만 담당하며, 제거는 장바구니 화면에서만 한다. 담기 성공의 우선 결과는 헤더 개수 변경이 아니라 **장바구니 화면에 해당 상품이 나타나는 것**으로 정했다. 따라서 팝업의 `장바구니 이동`을 눌러 실제 화면을 이동한 뒤 상품이 보이는 데까지를 이 시나리오의 범위로 두고, 헤더 장바구니 개수는 단언하지 않는다.

1번 인증 시나리오 안에서 `login_start`는 세 갈래의 로그인 화면 진입, `login_success`는 정상 자격 증명 제출과 원래 보호 경로 복원, `login_fail`은 잘못된 자격 증명 오류와 재시도를 담당한다. 세 이벤트를 각각 별도 E2E로 만들지 않고 하나의 인증 흐름 안에서 브라우저 경계를 나눠 검증한다.

### 빈도가 낮은데 붙인 경로

<!-- 인증과 주문 완료가 여기 해당한다. "로그만 보고 정하면 안 되는 이유"가 이 절의 내용이다. -->

인증은 보호된 화면과 사용자별 상태를 여는 전제이므로 로그 빈도만으로 제외하지 않는다. 인증이 실패하면
보호 경로에 접근할 수 없고 주문 흐름도 시작할 수 없다. 또한 미로그인 사용자의 보호 경로 진입,
세션 만료, 잘못된 자격 증명은 실제 리다이렉트·쿠키·401 응답 경계를 통과해야 하므로 낮은 빈도라도
브라우저에서 확인할 가치가 있다.

주문 완료도 빈도만으로 제외하지 않는다. 결제 성공 뒤 주문내역에 주문이 노출되지 않으면 고객은
구매 증거를 확인할 수 없고, 결제 취소·중복 문의 등 큰 CS 비용으로 이어질 수 있다. 따라서
`order_start`부터 주문 성공 후 주문내역에 나타나는 흐름을 별도 E2E 시나리오로 포함한다.
카카오톡·문자·이메일 같은 외부 알림 발송은 이 앱의 브라우저 경계와 외부 Provider를 함께 검증해야
하므로 이번 시나리오 범위에서 제외하고, 주문내역 노출을 구매 완료 확인의 종료 지점으로 삼는다.

### 계측했지만 대상에서 빠지는 경로

시드 로그에는 있는데 이 앱에는 대응 화면이 없어 자연히 빠지는 경로다. 없는 화면을 만들지 않고 빠지는 이유만 남긴다.

| 경로                  | 시드 로그에서의 크기                    | 왜 §B 표에 없나                                                                                                                                     |
| --------------------- | --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `product_detail_view` | 4,656세션 (전체의 58.2%, 시드 기준 2위) | 상품 상세 화면과 목록에서 상세로 가는 경로가 없다. 계측 대상에서도 제외했다(§A). **경로의 단위를 이 앱의 이벤트로 정했으므로 순위에 올리지 않는다** |
| `client_error`        | 103세션 (1.3%)                          | 시드에서 100% 상세 직후에 발생한다. 상세가 없어 이 앱에는 대응 경로가 없고, 오류 이벤트로 걸러 §B에서 제외했다                                      |

두 경로는 규모가 작아서 빠진 게 아니다. 상세는 시드 로그에서 두 번째로 큰 경로인데도 **이 앱에서 재현할 수 없어서** 빠진다. 로그 순위만 보고 E2E 대상을 정하면 안 되는 이유가 여기서 한 번 드러난다.

세 가지가 이 결정에 딸려 온다.

- **시드 로그에서 `cart_add`는 100% 상세 화면을 거친 뒤 발생한다**(1,309세션 전원). 이 앱은 목록 카드에서 바로 담을 수 있어 단계가 하나 적다. 따라서 §B의 목록 → 담기 전이 17.4%는 **시드 로그가 관측한 값이지 이 앱에서 기대할 값이 아니다.** 아래 판단에서 이 숫자를 근거로 쓸 때 그 차이를 함께 적는다.
- 시드의 담기 이탈률 50.8%도 같은 이유로 이 앱의 값이 아니다. 상세라는 중간 단계에서 이미 걸러진 사람들의 값이다.
- `client_error`를 노이즈로 거르자 그 세션들의 마지막 이벤트가 `product_detail_view`로 바뀌었다(68세션). §B 표에서 상세를 빼면서 이 변화도 표에 나타나지 않지만, **오류를 거르면 그 오류가 가리고 있던 이탈이 드러난다**는 관찰은 남겨 둔다.

이 시나리오가 화면에 거는 약속은 [화면별 케이스 문서의 「E2E가 쓸 접근 가능한 이름」](../week-09/test-cases.md#e2e가-쓸-접근-가능한-이름)에 있다. 담기 버튼은 `aria-label`을 달고 있어 화면 글자(`담기`)와 접근 가능한 이름(`{상품명} 장바구니`)이 다르다. 로케이터가 잡는 것은 뒤쪽이라, 문구가 아니라 상품명이 바뀔 때 깨진다.

| 바뀌는 것                                                                                   | 고쳐야 하는 곳                                                                                                                                      | 몇 군데                                            |
| ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 문구가 바뀐다 — 확인 창 안내 문구나 확인 버튼 라벨을 다듬는 경우                            | 확인 창 제목 `장바구니 페이지로 이동하겠습니까?`, 확인 버튼 `장바구니 이동`                                                                         | 2군데. 문구 하나가 바뀌면 그중 1군데               |
| 상품 데이터가 바뀐다 — 시드 상품명이 바뀌거나 카드 표기 형식이 바뀌는 경우                  | 목록에서 카드 찾기, 담기 버튼의 접근 가능한 이름 `{상품명} 장바구니`, 장바구니에서 담긴 상품 확인                                                   | 3군데. 전부 같은 상품명에 묶여 있다                |

**추정 결과와 그에 대한 판단:** 자주 오는 변경은 싸고, 비싼 변경은 자주 오지 않는다. 문구가 바뀌면 고칠 곳은 문자열 하나다. 구조가 바뀌면 세 단계가 통째로 날아가지만 그건 사용자 흐름 자체가 바뀐 경우라, 테스트가 깨져서 알려주는 쪽이 맞다. 그래서 이 시나리오는 유지할 만하다고 봤다. 실제로 가장 넓게 퍼진 것은 문구가 아니라 상품명이다. 세 자리가 같은 값에 묶여 있어 시드 상품 하나만 바뀌어도 함께 깨진다. 이건 테스트가 쓰는 상품을 픽스처 상수로 두고 세 자리가 그 값을 참조하게 하면 한 곳으로 줄어드므로, 4단계에서 그 방향을 검토한다.

## 4단계 경계 — 격리와 `storageState`

<!--
4단계에서 정할 것이지만, 여기서 미리 적어 두면 시나리오를 고를 때 비용이 보인다.
  - `storageState`를 쓰는 테스트와 안 쓰는 테스트의 경계 (로그인 자체를 검증하는 테스트는 안 쓴다)
  - 병렬 실행에서 계정·데이터·스토리지 중 무엇을 워커별로 가를지 (계정이 8개인 이유)
-->

3단계 커밋 시점에는 경계만 적어 둔 절이다. 4단계에 들어가기 전 저장소 코드를 다시 읽고 확정했고, 그 과정에서 드러난 제약(만료 재현 · `sessionStorage`)을 함께 적었다.

### `storageState`를 쓰는 테스트와 안 쓰는 테스트

`storageState`는 로그인된 쿠키와 스토리지를 파일로 저장해 두고 테스트 시작 시 주입한다. 매번 로그인 화면을 거치지 않아 빠르지만, **로그인 자체를 검증하는 테스트에는 쓰지 않는다.** 검증 대상을 건너뛰고 시작하는 셈이라 로그인이 깨져도 통과하기 때문이다.

| 시나리오                | `storageState` | 필요한 사전 상태                                              | 이유                                                                                     |
| ----------------------- | -------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 1. 인증 플로우          | 쓰지 않는다    | 미로그인. 만료 갈래만 유효 세션 + `scenario=expired` 쿠키     | 로그인 화면 진입·성공·실패가 검증 대상이다. 주입해 버리면 검증할 것이 남지 않는다        |
| 2. 담기 → 장바구니 이동 | 쓴다           | 로그인 · 장바구니 비어 있음                                   | 미로그인에서 [담기]는 로그인 화면으로 보낸다(OWN-04). 로그인은 여기서 검증 대상이 아니다 |
| 3. 주문 → 주문내역      | 쓴다           | 로그인 · 장바구니는 비어 있고 상품 1건은 테스트 안에서 담는다 | 주문 API·라우팅·주문내역 반영이 검증 대상이다. 로그인만 건너뛰면 충분하다                |

**만료는 "만료된 쿠키"로 재현하지 않는다.** `proxy.ts` 가드는 세션 쿠키의 존재만 보고 서명·만료 검증을 API에 남겨 두었으므로(1단계 6번), 만료된 값을 손으로 만들 자리가 애초에 없다. 유효한 세션 쿠키에 `scenario=expired` 쿠키를 더해 API 쪽만 401을 내게 만든다.

그런데 그것만으로는 아무 일도 일어나지 않는다. `getSession()`은 401을 던지지 않고 `null`로 돌려주므로(미로그인 방문자에게 만료 화면이 뜨는 것을 막으려는 선택) 전역 만료 핸들러를 지나가지 않는다. 만료 리다이렉트를 실제로 일으키는 것은 **401에 `ApiError`를 던지는 쿼리**뿐이고, 지금 그런 화면은 주문 내역 하나다. 그래서 만료 갈래는 `/orders`에서만 재현할 수 있다.

`storageState`는 쿠키와 `localStorage`만 싣고 `sessionStorage`는 싣지 않는다. `flow_id`와 `sessionId`가 `sessionStorage`에 있으므로(`analytics/browser-context.ts`), 로그인을 건너뛴 시나리오 2·3의 주문 이벤트에는 `flow_id`가 실리지 않는다. 계측 연속성을 볼 수 있는 자리는 로그인 화면을 실제로 거치는 시나리오 1뿐이다.

### 병렬 실행에서 무엇을 워커별로 가를까

계정 · 서버 데이터 · 브라우저 스토리지 셋 중 **계정을 가른다.** 브라우저 스토리지는 Playwright가 테스트마다 새 컨텍스트를 주므로 이미 격리돼 있고, 서버 데이터(장바구니 · 주문)는 소유자별로 보관하기로 정했으므로 계정을 가르면 따라 갈린다. 남는 축이 계정 하나다.

`looper1@loopers.dev` ~ `looper8@loopers.dev` 여덟 계정이 있어 워커 수를 여기에 맞춘다. 워커가 계정을 공유하면 한쪽이 장바구니를 비우는 사이 다른 쪽이 주문해 서로의 상태를 망가뜨린다.

배정은 `parallelIndex`로 한다. worker 스코프 fixture가 그 워커의 첫 테스트에서 한 번 로그인해 `playwright/.auth/worker-{parallelIndex}.json`에 저장하고, 이후 그 워커의 테스트가 재사용한다.

처음에는 `workerIndex`로 짰는데 그게 틀렸다. `workerIndex`는 워커 프로세스가 새로 뜰 때마다 계속 증가하는 값이라 `--workers=4`로 돌려도 8번이 나온다. 0..(워커 수 - 1) 범위를 보장하는 것은 `parallelIndex`이고, 계정을 나누는 축은 "동시에 몇 개가 도는가"이므로 이쪽이 맞다. 실행해 보지 않았으면 못 찾았을 종류의 어긋남이다.

워커 수는 config에서 4로 둔다. 계정이 8개라 상한은 8이고 그것을 넘으면 `accountForSlot`이 명시적으로 던지지만, 8코어 머신에서 워커 8개와 Next 서버가 같이 돌면 서로를 굶겨 로직과 무관한 30초 타임아웃이 난다(같은 코드가 어떤 회차에는 전부 통과했다). 인증 API에 500ms 지연이 걸려 있어 동시 로그인이 특히 비싸다. 상한은 계정이 정하고, 실제 실행 수는 머신이 정한다.

브라우저 프로젝트가 chromium·webkit 둘이라 같은 테스트가 두 번 돌지만, 워커 풀은 프로젝트 공통이고 `workerIndex`는 워커 프로세스마다 고유하다. 두 브라우저가 같은 계정을 동시에 쥐지는 않는다.

### 어디까지 단언할까

시나리오는 §C에서 정했고, 그 안에서 무엇을 단언할지를 여기서 정한다.

| 갈래                 | 단언                                                                                                            | 이 범위인 이유                                                                                                                                      |
| -------------------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1-A 보호 경로 복원   | 리다이렉트된 `/login`의 `returnUrl` → 로그인 후 원래 경로 도달 → 헤더의 계정 메뉴 → **초기 HTML의 로그인 상태** | 가드·복원·세션 반영이 한 흐름에서 닫힌다. 초기 HTML은 JS를 끈 컨텍스트로 따로 보며, 통합 테스트로는 볼 수 없어 5단계 실험 대상이 된다               |
| 1-A 계측             | `login_start`와 `login_success`가 같은 `flow_id`를 단다                                                         | `flow_id`는 `sessionStorage`에 살아 로그인 화면을 실제로 거치는 이 갈래에서만 관측된다. 나머지 계측은 logger 단위·통합 테스트가 덮는다              |
| 1-B 세션 만료        | `/orders` 진입이 `/login?returnUrl=%2Forders`로 이동하고 로그인 폼이 보인다                                     | 1단계에서 "만료 처리는 한 곳"이라고 정한 결정이 실제로 동작하는지가 검증 대상이다                                                                   |
| 1-C 잘못된 자격 증명 | `role="alert"` 문구와 `/login`에 머무는 것 → 이어서 올바른 비밀번호로 재시도해 성공                             | 오류와 재시도를 한 테스트에서 덮는다. 로그인 401이 전역 만료 처리로 새지 않는다는 것도 같이 확인된다                                                |
| 2 담기               | 확인 창 제목 → [장바구니 이동] → `/cart`에 담은 상품이 보인다 → 새로고침 후에도 보인다                          | 헤더 개수는 단언하지 않는다. 새로고침은 8주차 스펙이 보던 것을 옮겨 온 것으로, 저장(localStorage)과 소유자(세션)가 새 문서에서 다시 만나는지를 본다 |
| 3 주문               | `/cart`에서 주문 → `POST /api/orders` 응답의 `order.id`로 주문내역의 `주문번호 {id}`를 확인                     | 주문은 서버 메모리에 계정별로 누적되고 최신이 목록 마지막에 온다. 개수나 순서를 가정하면 3회 연속 실행에서 깨진다                                   |

계측을 시나리오 2·3에서 보지 않는 것은 범위를 줄이려는 선택이 아니라, `storageState`를 쓰는 한 `flow_id`가 존재하지 않기 때문이다. 로그인을 거치게 만들면 볼 수는 있지만 "매 테스트에서 로그인 폼을 다시 채우지 않는다"는 과제 요구와 맞바꾸게 된다.

초기 HTML 단언 하나가 아직 열려 있는 결정을 붙잡고 있다는 점은 적어 둔다. 헤더를 `Suspense`로 감싸면 첫 렌더가 빨라지지만, 경계를 여는 것이 React가 넣는 인라인 스크립트라 **JS를 끈 브라우저에서는 fallback이 그대로 남는다.** 그러면 "JavaScript 실행 전에도 로그인 여부가 보인다"는 1단계 요구가 그 자리에서 깨지고, ①의 마지막 단언이 먼저 실패한다. 통합 테스트는 그 변경에 조용하다 — 서버가 그린 HTML을 보지 않기 때문이다. 성능과 이 요구 중 무엇을 고를지는 아직 정하지 않았고, 지금 붙인 E2E는 요구 쪽에 서 있다. 테스트가 결정을 막는 것이 아니라 값을 청구하는 자리다.

테스트가 쓰는 상품은 `e2e` 아래 상수 한 곳에 두고 세 자리(카드 제목 · 담기 버튼 · 장바구니 행)가 그 값을 참조한다. 「유지보수 비용 추정」에서 남긴 방향을 그대로 적용한 것이다. 8주차 스펙도 같은 상품명을 쓰고 있지만 손대지 않는다 — "8주차 테스트가 그대로 통과하는가"를 확인해야 하는 주에 그 파일을 같이 바꾸면 통과의 의미가 흐려진다.

### 실제로 돌려 보고 확인한 것

경계를 정한 대로 도는지 확인한 기록이다. 프로덕션 빌드 위에서 `CI=1`로 돌렸다 — 그래야 `reuseExistingServer`가 개발 서버를 집어 가지 않는다(5단계 「기준선」에서 한 번 데인 자리다).

| 확인 항목     | 결과                                              | 비고                                                                                                                                      |
| ------------- | ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `--workers=4` | 26 passed / 0 failed (27.5s)                      | chromium 13 · webkit 13. 워커 파일은 `worker-0` ~ `worker-3`                                                                              |
| `--workers=1` | 26 passed / 0 failed (1.4m)                       | 결과는 4와 같고 시간만 3배다. 만들어진 파일이 `worker-0.json` 하나뿐이라 계정 배정이 `parallelIndex`를 따른다는 것이 파일 이름으로 보인다 |
| 3회 반복      | 26 / 26 / 26 passed, 0 failed (26.7s·27.4s·29.4s) | 실패도 flaky도 없다. 주문이 계정별로 계속 쌓이는데 회차 간 결과가 같은 것은 개수와 순서를 단언하지 않기 때문이다                          |
| trace 확인    | 실패한 단계와 대기 대상이 목록에서 바로 갈렸다    | 아래                                                                                                                                      |

`--workers=1`이 같은 결과를 낸다는 것은 통과가 병렬 타이밍에 기대고 있지 않다는 뜻이다. 반대로 4에서만 깨졌다면 계정 격리를 의심할 자리였다.

### trace를 열어 본 기록

인증 복원 테스트의 계정 메뉴 단언을 없는 이름으로 바꿔 일부러 실패시키고 `--trace=on`으로 돌린 뒤 `npx playwright show-trace`로 열었다.

- 액션 목록에서 `Navigate to "/orders"` → `Fill` → `Click` → `Wait for navigation`(1.1s)까지 통과하고, **`Expect "toBeVisible"`가 10.0s를 다 쓰고 끝났다.** 어느 단계에서 멈췄는지가 시간만 봐도 갈린다.
- 대기 대상은 그 줄에 `getByRole('button', { name: '없는 계정 메뉴' })`로 그대로 적혀 있고, 하단 Log 탭에도 `waiting for ...` 한 줄이 남는다.
- 그 단계의 스냅샷에는 `/orders`가 정상으로 렌더돼 있고 **헤더에 계정 메뉴가 보인다.** 로그인과 경로 복원은 다 됐고 locator만 어긋났다는 것이 화면 하나로 닫힌다.
- Network 탭에는 `/orders` 307 → `/login?returnUrl=%2Forders`, `GET /api/auth/me` 401(아직 미로그인), `POST /api/auth/login` 200이 순서대로 남아 있다. 앱이 아니라 단언이 문제라는 근거가 여기서 한 번 더 나온다.

5단계 1번 실험에서 "타임아웃 4개는 로그를 봐야 알 수 있었다"고 적은 것이 정확히 이 작업이다. `trace: 'retain-on-failure'`로 둔 값이 여기서 회수된다.

확인 뒤 단언은 바로 되돌렸고 `git diff`로 남은 변경이 없는 것을 확인했다.

### `playwright/.auth`는 만들어 주지 않아도 된다

`playwright/.auth`는 gitignore 대상이라 클린 checkout에는 없다. fixture에서 `mkdir(..., { recursive: true })`를 먼저 부르도록 넣었다가 뺐다 — `context.storageState({ path })`가 상위 디렉터리를 알아서 만든다. 디렉터리를 통째로 지우고 돌려 확인했고, 없는 상태에서 그대로 통과했다. 위의 workers 4·1 실행과 3회 반복도 전부 `.auth`를 지운 상태에서 시작했다.

## 5단계 실험 — E2E가 무엇을 잡았나

E2E는 비싸니 값을 하는지 확인한다. 인증 구현을 **한 실험에 한 곳씩** 바꾸고 전체 E2E를 돌렸다. 테스트 코드는 건드리지 않았고, 실험이 끝날 때마다 `git checkout`으로 되돌려 작업 트리가 깨끗한 것을 확인했다.

### 기준선

프로덕션 빌드 위에서 **26 passed / 0 failed**, `pnpm verify`는 147 passed다. 실험마다 여기서 무엇이 늘었는지를 본다.

기준선을 다시 잡은 이유가 있다. `playwright.config.ts`의 `reuseExistingServer`가 로컬에서 `true`라, 포트 3000에 개발 서버가 떠 있으면 Playwright가 **프로덕션 빌드 대신 그것을 재사용한다.** 4단계 실행이 그 상태였다. 개발 서버를 내리고 다시 돌려 같은 결과(26 passed)를 확인한 뒤 실험을 시작했다. 가드와 서버 렌더는 dev와 prod가 다르게 도는 영역이라, 이 확인 없이는 아래 표의 값을 믿을 수 없다.

### 실험 기록

| #   | 망가뜨린 곳          | 어떻게 바꿨나                    | 결과            | 실패한 테스트                                | 실패 메시지로 원인을 알 수 있었나                                                                                                                                                              |
| --- | -------------------- | -------------------------------- | --------------- | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `proxy.ts` 가드 조건 | `has(SESSION_COOKIE)`를 `!has`로 | 잡힘 (6 failed) | 인증-복원 · 담기 · 주문 (각 chromium·webkit) | **부분.** 인증은 `Expected "/login" / Received "/orders"`로 즉시 짚였지만, 담기·주문은 `waitForURL('**/cart')` 타임아웃이라 로그의 `navigated to /login?returnUrl=%2Fcart`를 봐야 알 수 있었다 |
| 2   | `proxy.ts` matcher   | `'/orders/:path*'` 한 줄 삭제    | 잡힘 (2 failed) | 인증-복원만                                  | **예.** 같은 `Expected "/login" / Received "/orders"`. 보호돼야 할 경로가 그냥 열렸다는 것이 한 줄로 드러난다                                                                                  |
| 3   | `app/layout.tsx`     | `SessionHydration` 제거          | 잡힘 (2 failed) | 인증-복원의 **마지막 단언만**                | **예.** `getByRole('button', { name: '루퍼N 계정 메뉴' })` not found. 실패한 줄이 JS를 끈 컨텍스트라 초기 HTML 문제라는 것이 위치로 드러난다                                                   |

**세 실험 모두 `pnpm verify`는 147 passed였다.** 단위·통합 테스트는 셋 중 하나도 보지 못했다.

### E2E만 잡을 수 있었던 항목

3번이다. 그것도 E2E 안에서 한 갈래만 잡았다.

JS가 켜진 앞 단계(복원 직후 헤더의 계정 메뉴 확인)는 **통과했다.** 서버가 세션을 넣어주지 않아도 클라이언트 세션 쿼리가 뒤늦게 채우기 때문이다(실패까지 12.5초가 걸린 것도 그 때문이다). 서버가 그린 HTML을 보는 자리는 `javaScriptEnabled: false` 컨텍스트 하나뿐이었고, 그 단언이 없었다면 이 변경은 통째로 살아남았을 것이다.

1·2번도 통합 테스트로는 재현할 수 없다. `proxy.ts`는 요청 경계에서 도는 코드라 jsdom에 그 단계가 없다. 다만 그건 "E2E만 잡는다"이지 "E2E만이 유일한 방법"은 아니다 — 가드의 리다이렉트는 라우트 핸들러 단위 테스트로도 확인할 수 있는 종류다. 3번은 그마저도 어렵다. 서버가 실제로 렌더한 문서를 브라우저가 JS 없이 받아야 관측된다.

### 잡힌 개수가 실험의 값은 아니었다

1번과 2번은 같은 파일의 같은 결정을 건드렸는데 값이 갈렸다.

- **2번**은 단언 하나만 정확히 죽여서 메시지만으로 원인이 닫혔다
- **1번**은 6개를 죽였지만 그중 4개가 타임아웃이라, 무엇이 원인인지 알려면 trace나 로그를 열어야 했다

3단계에서 "②는 단언이 마지막 한 곳에만 걸려 있어 앞 단계를 건드리면 연쇄로 무너진다"고 적어 둔 것이 그대로 나왔다. 앞 단계를 망가뜨리는 실험은 "잡혔다"는 쉽게 얻지만 실패 메시지의 값이 떨어진다.

### 살아남은 변경과, 살아남는 게 맞는 것

살아남은 변경은 없었다. 셋 다 잡혔으므로 테스트를 고칠 일도 없었다.

다만 **세션 만료 갈래는 1·2번에서 통과했고 그게 정상이다.** 만료 시나리오는 유효한 세션 쿠키를 들고 있어 가드가 원래도 통과시키고, `scenario=expired`가 만드는 401 → 전역 만료 처리 경로는 가드와 무관하다. 「4단계 경계」에서 "②는 세션 쿠키가 있어 어차피 통과하므로 그대로 산다"고 예측한 그대로다. 통과한 테스트가 무엇을 보지 않는지까지 미리 적어 두면, 실험 결과를 읽을 때 "왜 이건 안 잡혔지"로 헤매지 않는다.

### 통합 테스트로도 잡히는 실험은 없었다

과제가 "통합 테스트로도 잡히는 실험이 있었다면 그 시나리오를 E2E에 둘 이유가 남아 있는지 다시 판단하라"고 하는데, 이번 세 실험에는 해당하지 않는다. 셋 다 `pnpm verify`를 통과했다. 따라서 §C에서 정한 세 시나리오를 다시 줄일 근거는 나오지 않았다.
