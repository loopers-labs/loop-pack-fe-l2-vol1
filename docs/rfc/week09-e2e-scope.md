# 9주차 E2E 범위 RFC

## A. 이벤트 스키마

### 이름 규칙

시드 로그(`fixtures/events-30d.jsonl`)의 스키마를 따른다.

- `{대상}_{일어난 일}` 형태의 snake_case. 대상은 화면·컨트롤·도메인 객체·플로우 등 그때그때 자연스러운 단위다.
- 이벤트 이름은 집계 단위, 세부 값은 props로 둔다. 카테고리 변경을 `category_living_click`이 아니라 `props.category`로 담는 방식이다. 이름이 너무 크면(`button_click`) 아무것도 셀 수 없고, 너무 잘게 나누면 전체를 세려고 이름을 다 알아야 한다.
- 새 이벤트는 집계할 질문이 생겼을 때만 추가한다.

### 공통 프로퍼티

모든 이벤트에 붙는 값은 이벤트의 내용이 아니라 맥락 — 어떤 이벤트든 잘라 볼 수 있는 집계 축이다.

| 키 | 형식 | 생성 |
| --- | --- | --- |
| `sessionId` | string | 탭 단위. `sessionStorage`의 `analytics_session_id`, 없으면 `crypto.randomUUID()`로 생성. 탭 복제·`window.open`에서는 저장값이 복사되어 세션이 이어질 수 있다 |
| `ts` | ISO 8601 string | 이벤트 발생 시점의 `new Date().toISOString()` |
| `device` | `mobile` \| `tablet` \| `desktop` | viewport 폭 기준: 768px 미만 mobile, 1024px 미만 tablet, 나머지 desktop |

- **이벤트에 `userId`가 없다.** 신원은 `identify()` 채널이 담당하고, 이벤트에 신원을 붙이는 것은 분석 도구(provider)의 일이다. 개발용 `consoleProvider`는 신원을 이벤트에 합치지 않으므로 이번 로그에서는 userId가 보이지 않는다. 시드의 userId는 실제 도구가 붙인 결과물이다.
- `identify`와 `reset`은 `window.__analytics`에 쌓이지 않고 콘솔로만 확인된다.
- **출력 형식**: 로거가 공통 프로퍼티를 이벤트별 props와 병합해 전달하므로, `window.__analytics`에서는 공통값도 `properties` 안에 들어간다. 시드 JSONL의 최상위 필드 구조와 다른 개발용 출력 형식이다.

### 계측 지점과 시드 매핑

| 이벤트 | 발생 시점 | props | 시드 대비 |
| --- | --- | --- | --- |
| `product_list_view` | 목록 화면 진입 | `{ category: CategoryId \| 'all'; sort: ProductSort; page: number }` | 동일 |
| `cart_add` | 장바구니에 상품 추가(해제는 계측 안 함) | `{ productId: string; quantity: number }` | 동일 |
| `login_start` | 로그인 화면 진입 | `{ from: LoginFrom }` | 키 동일 · 값 확장 |
| `login_success` | 로그인 성공 | `{ from: LoginFrom }` | 키 동일 · 값 확장 |
| `login_fail` | 로그인 실패 | `{ reason: LoginFailReason }` | 키 동일 · 값 확장 |
| `order_start` | 주문서 진입 — draft가 처음 준비 완료된 시점에 1회 | `{ productIds: string[] }` | 변경 (다중 상품) |
| `order_complete` | 주문 생성 성공 | `{ orderId: string; productIds: string[]; totalPrice: number }` | 변경 (다중 상품 · orderId 추가) |

**제외** — `product_detail_view`: 이 앱에는 상품 상세 화면이 없다. 없는 화면의 이벤트는 계측하지 않고, 그 경로는 E2E 후보에서도 자연히 빠진다.

**주문 props 변경 사유** — 시드는 단일 상품 주문이라 `productId` 하나로 충분하지만, 이 앱은 여러 상품을 한 주문으로 처리한다. 상품마다 이벤트를 쪼개 보내면 이벤트 수가 주문 수와 어긋나 집계가 부푼다. 시드가 지키는 집계 단위(이벤트 1건 = 그 시점의 주문 전체)를 보존하고 props만 `productIds` 배열로 바꾼다. `orderId`와 `productIds`는 응답의 `order`에서 가져오고(orderId는 완료 이벤트의 중복 구분용), `totalPrice`는 주문 응답에 금액이 없어 제출한 주문서의 계산값을 쓴다. 총수량 분석은 범위에 없어 `quantity` 합계나 `itemCount`는 수집하지 않는다.

**값 확장 사유** — 시드의 `from`은 `cart`만, `reason`은 `INVALID_CREDENTIALS`만 관측된다. 이 앱은 `from`을 `cart | my | orders | direct`(로그인 화면에 들어온 출처), `reason`을 `INVALID_CREDENTIALS | INVALID_REQUEST | SERVER_ERROR | UNKNOWN`(HTTP status 기반 분류)으로 정의한다. 키와 의미는 시드와 같고 값의 범위만 넓어진다.

**생성 규칙** — `from`은 로그인 URL의 `from` 파라미터만 검증해 쓰고, `next`(로그인 뒤 목적지)는 쓰지 않는다. `cart | my | orders` 밖의 값이나 파라미터 없음은 `direct`다. `reason`은 HTTP status로 분류한다: 401은 `INVALID_CREDENTIALS`, 400은 `INVALID_REQUEST`, 500은 `SERVER_ERROR`, 그 밖은 `UNKNOWN`. 메시지 문자열과 사용자 입력값은 수집하지 않는다.

### 대표 시퀀스

문서만 읽고 이벤트 순서를 예측할 수 있어야 한다. 아래가 그 기준이다.

- **해피패스**: `product_list_view` → `cart_add` → (미로그인 주문 진입) → `login_start` → `identify` → `login_success` → `order_start` → `order_complete`
- **로그인 실패 후 재시도**: `login_start` → `login_fail` → `identify` → `login_success`
- **로그인 상태 재방문**: `identify` → `product_list_view` → …

## B. 시드 로그 분석

### 분석 기준

- **경로 단위**: 상품 목록 진입은 `product_list_view`로 본다. 로그인은 `login_start` · `login_success` · `login_fail`, 주문은 `order_start` · `order_complete`를 각각 하나의 목표 경로로 묶었다. `category_filter_change` · `page_change` · `sort_change`는 같은 목록 화면의 탐색 조작이라 하나의 경로로 묶고 세부 빈도만 따로 비교한다. 나머지는 이벤트 하나를 행동 경로 하나로 본다.
- **봇 추정 세션**: `device`가 `null`이라는 이유만으로 제외하지 않았다. `device=null` · 단일 이벤트 세션 · 기본 조건(`category=all`, `sort=latest`, `page=1`)의 `product_list_view` · UTC 01시대 · 밀리초가 `.000Z`인 타임스탬프가 30일 동안 함께 반복된 486세션을, 사람이 반복하기 어려운 일정성과 단조로운 행동 패턴을 근거로 자동화 트래픽으로 추정해 제외했다.
- **중복 전송**: `sessionId` · `ts` · `name` · `props` · `userId` · `device`가 모두 같은 이벤트는 첫 건만 남겼다. 초과분 77건을 제거했으며, 타임스탬프가 다른 반복 행동은 유지했다.
- **오류 이벤트**: `client_error` 103건은 모두 `IMAGE_LOAD_FAILED`였다. 사용자 행동 경로의 세션 수와 순위에서는 제외하되, 상세 경로의 실패율을 계산할 때는 사용했다. 오류가 발생한 세션 자체는 제외하지 않았다.
- **비율**: 봇 추정 세션을 제외한 7,514세션을 분모로 사용한다. 중복과 오류 이벤트는 제거해도 고유 세션 수가 줄지 않는다.
- **이탈률**: 흐름으로 분석한 경로는 해당 경로에 도달한 세션 중 아래 표에 적은 다음 단계에 도달하지 못한 비율이다. 목록 조작은 독립적인 조작 모음이라 다음 단계를 정하지 않았다. 사용자 변심도 포함되므로 기술 실패율과는 구분한다.
- **실패 판단**: `IMAGE_LOAD_FAILED`는 상세 이미지 로딩 실패, `login_fail`은 로그인 시도 실패로 셌다. 주문에는 실패 이벤트가 없어 `order_start` 후 `order_complete`가 없는 세션을 실패 대용 지표로 썼다. 나머지 경로는 로그만으로 실패율을 알 수 없다.

필터 · 정렬 · 페이지 이동 중 하나 이상이 발생한 세션은 4,544개(60.5%)였다. `category_filter_change` 3,056세션, `page_change` 1,756세션, `sort_change` 943세션 순이었다. 각 값은 이벤트 발생 횟수가 아니라 해당 이벤트가 한 번 이상 발생한 고유 세션 수이며, 여러 조작을 한 세션은 항목별 수치에 중복으로 포함된다.

정제 전 순위는 상품 목록(8,000) → 상품 상세(4,656) → 목록 조작(4,544) → 장바구니 담기(1,309) → 로그인(644) → 위시리스트 추가(480) → 주문(419)이었다. 정제 후에는 상품 목록만 7,514세션으로 줄고 순서는 같았다. 봇 추정 세션이 이미 1위인 상품 목록에만 몰려 있었고, 중복 전송은 같은 세션 안에서 발생해 세션 기준 순위에 영향을 주지 않았기 때문이다.

시드 로그에는 `home_view`와 `cart_view`가 없어 홈과 장바구니 화면은 독립 경로로 집계하지 않았다. 대신 상품 목록은 `product_list_view`, 장바구니는 `cart_add` 행동을 기준으로 집계했다.

## C. 붙일 곳과 안 붙일 곳

### 판단 기준

로그는 후보와 우선순위를 찾는 데 쓰고, 최종 범위는 다음 세 가지가 겹치는지로 정한다.

1. **사용 빈도** — 정제한 세션에서 실제로 많이 지나가는가
2. **실패 비용** — 실패하면 구매나 보호 기능이 막히는가
3. **브라우저 필요성** — 통합 테스트로 재현하기 어려운 쿠키 · 서버 리다이렉트 · 페이지 간 상태 연결이 있는가

최종 E2E 시나리오는 경로 기준으로 **인증과 주문 완료 2개**다. 인증 외에는 주문 완료 1개만 고른다. 인증 시나리오는 4단계 요구사항에 따라 세 테스트로 나눈다.

| 결정 | 경로 | B절 근거 | E2E가 필요한 이유 |
| --- | --- | --- | --- |
| 포함 | 인증 | 644세션(8.6%), 로그인 성공 미도달 58세션(9.0%). 실패하면 주문과 보호 경로가 함께 막힌다. | `proxy.ts`의 실제 리다이렉트, 로그인 응답의 세션 쿠키, 로그인 뒤 원래 URL 복원은 브라우저와 서버를 함께 거쳐야 검증할 수 있다. |
| 포함 | 장바구니 담기 → 주문서 → 주문 완료 | 주문서 진입 419세션(5.6%), 완료 미도달 142세션(33.9%). 실패하면 구매가 완료되지 않는다. | 실제 세션 쿠키, 장바구니와 주문 draft, 주문 API, 페이지 이동, 주문 내역 반영이 한 흐름으로 연결되는지는 각 부분을 나눈 통합 테스트만으로 보장되지 않는다. |

### 4단계에서 만들 테스트

인증은 하나의 필수 시나리오이며 아래 세 갈래를 각각 테스트한다. 주문 완료는 인증 외에 선택한 한 시나리오다.

| 경로 | 시나리오 | 핵심 단언 | 로그인 상태 준비 |
| --- | --- | --- | --- |
| 인증 | 미로그인으로 `/orders/new` 진입 → 로그인 → `/orders/new` 복원 | 로그인 URL에 원래 경로가 보존되고, 성공 뒤 그 경로로 돌아온다. 실제 `session` 쿠키의 `httpOnly`와 `SameSite=Lax`도 확인한다. | 사용하지 않음 — 실제 로그인이 검증 대상이다. |
| 인증 | 로그인 상태에서 `expired` 시나리오 → 보호 API 401 → 로그인 화면 | 만료 안내와 다시 로그인할 경로가 보이고 원래 보호 경로가 보존된다. | 워커별 `storageState` 사용 |
| 인증 | `invalid` 시나리오로 로그인 실패 | 오류를 보여주고 로그인 화면에 머물며 `session` 쿠키가 생기지 않는다. | 사용하지 않음 — 실제 로그인 실패가 검증 대상이다. |
| 주문 완료 | 로그인 상태에서 상품 담기 → 장바구니 선택 → 주문서 → 주문하기 → 주문 내역 | 주문 뒤 `/orders`로 이동하고 새 주문의 상품과 주문 번호가 화면에 나타난다. URL 이동이나 토스트만으로 성공을 판단하지 않는다. | 워커별 `storageState` 사용 |

인증 테스트를 세 개로 나누는 이유는 서로 다른 경계를 검증하기 때문이다. 경로 복원은 `proxy.ts`의 서버 리다이렉트와 로그인 성공 뒤 이동을, 세션 만료는 로그인 이후 보호 API에서 발생한 401의 전역 처리를, 잘못된 자격 증명은 로그인 API의 401이 만료 처리로 번지지 않고 폼 안에서 끝나는지를 검증한다. 한 테스트에 합치면 앞 단계 실패 때문에 뒤 경계를 확인하지 못하고 실패 원인도 흐려진다.

`storageState`는 워커별 계정으로 UI 로그인을 한 번 거쳐 만든다. 로그인 성공·실패 자체를 확인하는 두 시나리오에는 재사용하지 않고, 로그인 상태가 전제일 뿐인 만료와 주문 시나리오에만 쓴다. 잘못된 자격 증명의 오류 UI는 통합 테스트에도 있지만, 필수 인증 분기에서는 실제 브라우저에 세션 쿠키가 생기지 않는 것까지 확인한다. 주문 오류 화면과 재시도는 이미 통합 테스트에서 다루므로 주문 E2E는 완료 흐름 한 개만 만든다.

주문 완료 미도달 33.9%에는 사용자 이탈이 섞여 있으므로 기술 실패율로 해석하지 않는다. 이 수치는 실패 비용과 함께 후보의 우선순위를 정하는 데만 쓰고, E2E에서는 실제 구성 요소가 연결된 완료 흐름을 검증한다.

### 붙이지 않는 곳

| 경로 | 결정 근거 |
| --- | --- |
| 목록 조작 → 조건에 맞는 결과 갱신 | 필터 · 페이지 이동 · 정렬을 사용한 세션이 4,544개(60.5%)로 빈도는 높지만 새 E2E를 만들지 않는다. 조건 변경에 따른 요청과 목록 갱신은 `ProductList.conditions.dom.test.ts`가 검증하고, 브라우저에서만 의미 있는 URL · 뒤로가기 · 새로고침은 기존 `e2e/products.spec.ts`가 검증한다. 같은 동작을 다시 E2E로 만들면 중복이다. |
| 상품 목록 → 상품 상세 | 목록 진입은 100%지만 현재 앱에 상세 화면이 없다. 시드 로그에만 있는 화면을 E2E 때문에 추가하지 않는다. 목록 렌더링과 상태 분기는 통합 테스트에 둔다. |
| 장바구니 담기 | 기존 E2E가 담기와 새로고침 뒤 유지를 검증하고, 새 주문 E2E도 이 행동을 지나간다. 독립 시나리오를 더 만들지 않는다. |
| 위시리스트 추가 | 480세션(6.4%)이고 구매 흐름을 막지 않으며 현재 앱에는 시드와 같은 상세 경로도 없다. 이번 범위에서는 제외한다. |

목록 조작은 인증보다 약 7배 많이 사용되지만 통합 테스트와 기존 E2E의 책임이 이미 나뉘어 있다. 반대로 인증은 8.6%로 낮아도 보호 기능의 관문이다. 로그인이 망가지면 이후 주문 이벤트 자체가 남지 않으므로, 관측된 로그인 세션 수만으로는 잃게 될 하위 경로의 비용을 계산할 수 없다. 따라서 빈도만으로 두 경로의 결정을 뒤집지 않는다.

### 유지보수 비용 추정

**미로그인 보호 경로 → 로그인 → 원래 경로 복원** 시나리오를 기준으로 잡는다. 로그인 입력은 역할과 이름 기반 locator를 공통 `submitLoginForm` 함수 한 곳에 둔다.

| 변경 | 예상 수정 지점 |
| --- | ---: |
| 이메일 · 비밀번호 · 로그인 중 문구 하나 변경 | 공통 함수의 해당 locator 1곳 |
| 세 문구 모두 변경 | 공통 함수의 locator 3곳 |
| DOM 구조만 변경하고 역할과 접근 가능한 이름은 유지 | 0곳 |
| 복원 파라미터의 이름이나 형식 변경 | 로그인 URL 단언 1곳 |
| 보호 경로 자체 변경 | 최초 진입 URL과 최종 복원 URL 2곳 |

CSS 구조 셀렉터와 테스트 전용 id는 쓰지 않는다. 같은 로그인 동작을 사용하는 `storageState` 준비 코드도 이 함수를 재사용해 화면 문구를 중복하지 않는다. 구조 변경이 접근성 계약을 보존하면 테스트도 고치지 않는 것을 목표로 한다.
