# 9주차 — E2E 범위 설계 (week09-e2e-scope)

## A. 이벤트 스키마

### 이름 규칙

시드 로그(`fixtures/events-30d.jsonl`)에 이미 정의된 이벤트 이름을 그대로 쓴다. 새 규칙을 만들지 않는다 — 계측 스키마는 혼자 정하는 게 아니라 팀(여기서는 로그를 만든 쪽)이 이미 합의해둔 걸 따르는 것이라고 판단했다.

- 형식: `snake_case`, `{도메인}_{동작}` (예: `product_list_view`, `cart_add`)
- 과제가 요구한 8개 지점 중 실제로 계측한 7개(상세 진입은 우리 앱에 해당 화면이 없어 제외 — 아래 매핑표 참고) 전부 시드 로그의 이름과 동일하다 — 이름 매핑표가 따로 필요 없다.

### 공통 프로퍼티

`setCommonProperties()`(`src/shared/analytics/common-properties.ts`)로 모든 이벤트에 공통으로 붙인다.

| 필드 | 계산 방법 | 비고 |
| --- | --- | --- |
| `sessionId` | 브라우저 탭당 1회 `crypto.randomUUID()`로 생성, `sessionStorage`에 저장 | 로그인 여부와 무관. `entities/session`의 인증 세션과는 다른 개념(둘 다 "세션"이라 이름이 겹치지만 별개) |
| `device` | 화면 너비 기준 `mobile`(≤767px) / `tablet`(≤1023px) / `desktop`(그 이상) | 이벤트 발생 시점마다 재계산 |
| `ts` | `new Date().toISOString()` | 이벤트 발생 시점마다 재계산 |

`userId`는 공통 프로퍼티에 넣지 않았다. `identify(userId)`를 호출해도 지금 등록된 `consoleProvider`는 그 값을 어디 저장해두지 않아서(실제 분석 도구, 예를 들어 GA4·Amplitude는 내부적으로 기억해뒀다가 이후 이벤트에 자동으로 붙여주지만, `consoleProvider.identify()`는 콘솔에 찍기만 함) 자동으로 이후 이벤트에 붙지 않는다. 그래서 로그인 이후 이벤트인 `login_success`·`order_start`·`order_complete`에는 그 시점에 아는 `user.id`를 **이벤트 프로퍼티에 직접 넣었다**.

### `initAnalytics()` 호출 위치

`src/app/providers.tsx`에서 `src/shared/analytics/init-analytics.ts`를 부수효과로 import — 앱이 로드되는 가장 이른 시점에 `registerProviders()` → `setCommonProperties()` → `initAnalytics()` 순으로 실행된다. 초기화가 늦어질수록 그 사이 발생한 `track()` 호출이 큐(최대 100개, 초과분은 오래된 것부터 버려짐)에 쌓이는 시간이 길어지므로, 가능한 한 이르게 실행되도록 했다.

### `identify()` / `reset()` 호출 위치

- `identify(user.id)` — 로그인 mutation 성공 시(`src/features/auth-login/model/useLoginForm.ts`)
- `reset()` — 로그아웃 mutation 성공 시(`src/features/auth-logout/model/useLogout.ts`)

### 계측 코드는 화면이 직접 호출

컴포넌트·훅이 `track()`을 직접 부른다. 별도 래퍼를 두지 않았다 — `src/analytics/logger.ts` 자체 주석("화면 코드는 `track()`만 부른다")이 이미 이 설계를 의도하고 있고, `track()` 자체가 이미 프로바이더(어느 분석 도구로 보낼지)를 가리는 추상화라 한 겹 더 감싸는 건 지금 스코프엔 과했다.

### 계측 지점 매핑표

| 이벤트 | 시드 로그 정의 | 우리 구현 위치 | 일치 여부 / 조정 |
| --- | --- | --- | --- |
| `product_list_view` | 목록 화면 진입 | `ProductListPage` 마운트 시 (`src/_pages/product-list/ui/ProductListPage.tsx`) | 이름·프로퍼티(`category`,`sort`,`page`) 동일. 필터 변경마다는 다시 안 보냄 — 그건 `category_filter_change` 등 별개 이벤트 영역 |
| `product_detail_view` | 상세 화면 진입 | — | **제외.** 상세 페이지(`/products/[id]`) 자체가 코드베이스에 없음 |
| `cart_add` | 장바구니 담기 | `ProductCard` 담기 클릭 (`src/widgets/product-card/index.tsx`) | 이름 동일. `quantity`는 항상 `1` — `cartStore`가 상품 id만 저장하고 수량 개념이 없음 |
| `login_start` | 로그인 화면 진입 | `LoginForm` 마운트 시 (`src/features/auth-login/ui/LoginForm.tsx`) | 이름 동일. `from`은 `redirect` 쿼리 파라미터 값(없으면 `'direct'`) — 어느 보호 경로를 시도하다 왔는지를 나타냄 |
| `login_success` | 로그인 성공 | `useLoginForm` mutation `onSuccess` | 이름 동일. `userId` 직접 첨부(위 "공통 프로퍼티" 참고) |
| `login_fail` | 로그인 실패 | `useLoginForm` mutation `onError` | 이름 동일. `reason`은 API가 실패 사유를 세분화해서 주지 않아 상태 코드 기준으로 분류(`401`→`INVALID_CREDENTIALS`, `400`→`INVALID_REQUEST`, 그 외→`UNKNOWN_ERROR`) — 시드 로그의 `INVALID_CREDENTIALS`와 형식(SCREAMING_SNAKE_CASE)을 맞춤 |
| `order_start` | 주문서 화면 진입 | `CheckoutPage` 마운트 시 (`src/_pages/checkout/ui/CheckoutPage.tsx`) | 이름 동일. `productId`(단수) → **`productIds`(배열)**로 조정 — 우리 주문서는 장바구니 전체(여러 상품)를 한 번에 주문함. `userId` 직접 첨부 |
| `order_complete` | 주문 완료 | `useCheckoutSubmit` mutation `onSuccess` | 이름 동일. `productIds` 배열로 조정(위와 같은 이유). **`totalPrice`는 생략** — 이후 `cartStore`에 상품 상세정보를 저장하도록 개선하면서 화면(주문서)에는 총 주문 금액을 계산해 보여주게 됐지만, 계측 이벤트에까지 넣는 건 과제가 요구한 8개 지점에 포함되지 않는 프로퍼티라 스코프를 늘리지 않기로 함. `userId` 직접 첨부 |

### 예시 흐름 — 로그인부터 주문까지 한 번 통과했을 때

비로그인 상태로 상품 목록에 들어가 담고, 로그인해서 주문서로 이동해 주문을 완료하는 시나리오라면 이 순서로 이벤트가 남는다.

1. `product_list_view` — `/products` 진입 (`category`, `sort`, `page`)
2. `cart_add` — 담기 클릭 (`productId`, `quantity: 1`)
3. `login_start` — `/login` 진입, 보호 경로(`/orders/new`)에서 튕겨온 경우 `from`이 그 경로 (그 외엔 헤더의 "장바구니 N" 클릭 등으로 직접 옴)
4. `login_success` — 로그인 폼 제출 성공 (`from`, `userId`) — 이 직전에 `identify(userId)`가 먼저 불림
5. `order_start` — `/orders/new` 진입 (`productIds`, `userId`)
6. `order_complete` — 주문하기 클릭 성공 (`productIds`, `userId`)

로그인에 실패하면 4번 대신 `login_fail`(`reason`)이 남고, 5·6번으로 이어지지 않는다(로그인 못 했으니 보호 경로에 못 들어감). 로그아웃하면 `reset()`이 불려서 이후 이벤트에는 `identify()`로 붙였던 사용자 정보가 더는 안 남는다.

### 계측하지 않은 것 (시드 로그엔 있지만 이번엔 제외)

`category_filter_change`, `sort_change`, `page_change`, `wishlist_add`, `client_error` — 과제가 요구한 8개 지점(목록 진입·상세 진입·담기·로그인 시작/성공/실패·주문 시작/완료) 밖이라 이번엔 계측하지 않았다.

## B. 시드 로그 분석

`fixtures/events-30d.jsonl`(30일치, 8,000세션, 22,427줄)을 `sessionId` 기준으로 묶어 분석했다. 스크립트는 일회성이라 저장소에 남기지 않았다(`/tmp/log-analysis/*.mjs`).

### 데이터 정제

1. **완전 중복 라인 제거** — 같은 줄이 그대로 반복된 케이스가 있어 `Set`으로 걸러냄
2. **봇 세션 제외** — 다음 조건을 모두 만족하는 세션(486개, 전체의 6.1%): 이벤트가 딱 1개, `device: null`, `product_list_view` 단일 이벤트, 파라미터가 전부 기본값(`category: 'all'`, `sort: 'latest'`, `page: 1`). 실제 사용자라면 화면을 한 번 보고 아무 것도 안 누르고 나갈 순 있어도 `device`가 `null`로 찍힐 이유가 없고(공통 프로퍼티는 화면 너비로 매번 계산되므로), 이런 조합만 유독 세션 수 대비 비중이 높아 크롤러/헬스체크로 판단했다. 검증: 이 486개 세션이 `product_list_view` 외의 다른 이벤트를 하나라도 남긴 적이 없음을 확인했다(0건) — 즉 봇 세션은 다른 흐름과 전혀 안 섞여서, 제외해도 나머지 분석에 부작용이 없다.
   - **이 기준의 한계**: 조건이 꽤 엄격하다 — 이 조건에 안 걸리는 다른 유형의 봇(여러 페이지를 도는 크롤러, `device`가 정상적으로 찍히는 헬스체크 등)은 안 걸러지고 남아있을 수 있다. 즉 486개는 "이 기준으로 잡히는 가장 명백한 봇"일 뿐, 로그에 섞인 봇 세션 전체라고 단정할 수는 없다.

정제 전/후로 6개 경로의 순위 자체는 바뀌지 않았다(아래 표). 봇 세션이 전부 `product_list_view` 한 곳에만 몰려 있어 비율만 살짝 낮추고 순서는 안 흔든 것 — 그래서 이후 분석은 정제된 7,514세션 기준으로만 서술한다.

### 경로별 세션 수 · 이탈률 · 실패 비용

경로는 시드 로그의 이벤트 이름을 화면·행동 단위로 묶었다(괄호 안은 포함 이벤트). **비율의 분모는 정제 후 전체 세션(7,514)** — 각 경로가 앞 단계를 지나온 세션 중 몇 %인지가 아니라, 전체 사용자 중 몇 %가 이 경로를 한 번이라도 거쳤는지를 본다. **이탈률**은 "그 경로의 이벤트가 세션의 마지막 이벤트로 끝난 비율"을 썼다(다음 행동 없이 세션이 끝났다는 뜻 — 반드시 나쁜 신호는 아니다. 주문 완료 후 이탈은 정상 종료다). **실패 비용**은 이 경로에서 "실패"로 볼 이벤트를 직접 정의하고, 그 비율과 함께 "이게 막히면 뒤따라 무엇이 막히는지"를 적었다.

**분모가 칸마다 다르다는 점에 주의**: "비율" 칸은 전체 세션(7,514) 대비지만, "실패 비용" 칸의 %(로그인 9.0%, 주문 33.9%)는 **그 경로에 진입한 세션**(로그인 시작 644개, 주문 시작 419개) 대비다. 전자는 "전체 사용자 중 몇 %가 이 경로를 겪는지", 후자는 "그 경로에 들어간 사람 중 몇 %가 실패하는지"로 질문 자체가 다르기 때문에 분모를 통일하지 않았다.

| 경로 | 세션 수 | 비율 | 이탈률 | 실패 비용 | E2E 여부(가설) |
| --- | --- | --- | --- | --- | --- |
| 상품 목록 탐색(`product_list_view` 외 3종) | 7,514 | 100% | 38.0% | 실패로 볼 이벤트가 로그에 없음(조회는 성공/실패 구분이 없는 이벤트). 대신 모든 경로의 진입점이라, 막히면 이후 전 경로가 통째로 막힘 — 이 로그만으로는 안 잡히는 "구조적 비용" | 아니오 |
| 상품 상세 조회(`product_detail_view`) | 4,656 | 62.0% | 63.0% | 해당 없음 — 우리 앱에 상세 페이지 자체가 없음(A절에서 이미 제외) | 대상 아님(화면 없음) |

| 주문(`order_start`/`order_complete`) | 419 | 5.6% | 100.0% | `order_start`는 있는데 `order_complete`가 없는 세션 — 419세션 중 142개(33.9%). 막히면 매출 직접 손실. 게다가 완료까지 간 세션은 평균 5.09개 경로를 거쳐온 사용자(아래 "경로 중첩" 참고)라 손실의 무게가 큼 | 예 |

부가로 확인한 것들:

- **주문 실패 비용의 정의**: 표의 "주문 경로 이탈률 100%"와 실패 비용의 "33.9%"는 다른 지표다. 이탈률은 "주문 이벤트가 세션의 마지막이었는가"만 보고, 실패 비용은 "시작은 했는데 끝을 못 봤는가"를 본다. 실제로 `order_start`·`order_complete` 순서가 어긋나거나 완료 없이 다른 이벤트로 이어진 세션은 없었다(검증 완료) — 전부 "주문 이벤트가 세션의 마지막"이었다. 즉 이 이탈은 다른 화면으로 넘어가서가 아니라 그 자리에서 앱을 떠나는 형태다.
- **에러 이벤트**: `client_error`가 있는 103세션은 전부 상품 목록·상세 탐색 이벤트도 함께 갖고 있다(103/103) — 로그인·주문 흐름이 아니라 목록/상세를 보던 중 나는 에러로 보인다. 그래서 위 표의 실패 비용 정의에 `client_error`를 넣지 않았다: 로그인·주문 경로와 상관관계가 없어 그 경로들의 "실패"로 보기엔 근거가 약하다.
- **로그 기반 판단의 한계**: 위 표에서 목록 탐색·장바구니 담기·위시리스트를 "실패 이벤트가 없어 안전하다"고 판단했는데, 이건 "실제로 안전해서"가 아니라 "로그가 애초에 그런 실패를 기록하도록 설계되지 않아서"일 수 있다. 예를 들어 담기 버튼이 UI 버그로 아예 안 눌리는 경우는 이벤트 자체가 안 남아 로그로는 절대 못 잡는다. 그래서 이 표의 "실패 비용 없음"은 "위험이 없다"가 아니라 "로그만으로는 위험을 판단할 수 없다"로 읽어야 한다.

| 3개 | 943 | 12.5% |
| 4개 | 267 | 3.6% |
| 5개 | 401 | 5.3% |
| 6개(전부) | 43 | 0.6% |

가장 흔한 건 경로 1개(목록 탐색만 보고 끝)가 아니라 **경로 2개**다(40.0%) — 대개 "목록 탐색 + 담기" 또는 "목록 탐색 + 상세조회" 정도로 한 걸음 더 나간 세션이 가장 많다는 뜻이다. 그런데 **`order_complete`까지 도달한 277세션만 따로 보면 평균 5.09개 경로**를 거쳤다(6개 중 5개꼴) — 전체 분포의 중심(1~2개)과 뚜렷이 차이 난다. 즉 주문까지 가는 사용자는 로그인·장바구니·위시리스트·상세조회를 다 거쳐서 온, 앱을 훨씬 폭넓게 쓴 사용자다. 이는 뒤 C절에서 "주문 흐름이 다른 여러 기능의 연결점"이라는 근거로 쓴다.

## C. 붙일 곳과 안 붙일 곳

### 고른 것: 인증 플로우(필수) + 주문

인증 외에 로그 근거로 하나만 더 고른다(허용 범위 2개 이하 중 1개만 사용). **주문**이다.

- **로그 근거**: B절 표에서 실패 비용이 가장 크다 — `order_start` 대비 `order_complete` 미완료율 33.9%로 로그인(9.0%)보다 훨씬 높고, 막히면 매출이 직접 손실된다. 게다가 완료까지 간 세션은 평균 5.09개(6개 중 5개) 경로를 거쳐온 사용자다 — 이 앱을 가장 폭넓게 쓴, 잃으면 가장 아까운 사용자층이 지나가는 길목이라는 뜻이다.
- **빈도는 낮다(5.6%, 6개 경로 중 꼴찌)**. 그런데도 고르는 이유가 바로 이 문서가 요구하는 "빈도와 무관하게 실패 비용으로 판단"이다 — 로그인과 같은 논리다.
- **왜 하나만 고르는가**: 장바구니 담기(17.4%, 로그인보다도 빈도 높음)도 후보로 볼 수 있었지만 뺐다. 실패로 볼 이벤트 자체가 로그에 없고(담기는 항상 성공 이벤트로만 남음), 이유도 확인했다 — `cartStore.addItem()`은 서버에 요청을 보내지 않고 브라우저 로컬 상태만 바꾸는 동작이라(`src/widgets/product-card/index.tsx`) 401·500 같은 실패가 애초에 날 수 없는 구조다. "로그 근거로 고른다"는 이번 과제의 전제를 통과할 방법이 없어 뺐다. 위시리스트는 실패해도 다른 경로에 영향이 없어 비용이 낮다. 상세 조회는 화면 자체가 없다. 남는 후보가 없어 1개만 고른다.

### 인증 플로우 — 빈도는 낮은데 붙인 경로

로그인은 전체 세션의 8.6%에서만 관측된다 — 6개 경로 중 4위, 위시리스트(6.4%)보다 살짝 위다. 로그만 보면 "자주 안 쓰이는 경로"로 보인다.

그런데도 붙이는 이유는 로그가 못 보여주는 게 있어서다: **로그는 "얼마나 자주 쓰였는가"만 보여주지, "안 되면 무엇이 막히는가"는 안 보여준다.** 로그인 자체는 8.6%만 거치지만, 그 뒤에 있는 주문·(장래의) 마이페이지 전부가 로그인 없이는 진입조차 안 된다 — B절 표의 "막히면 뒤따라 무엇이 막히는지"가 로그인 행에서 유독 넓은 이유다. 빈도가 로그인 자체의 실사용률이 아니라 "그 경로를 거쳐야만 도달하는 다른 경로들의 총합에 대한 병목"이라는 걸 로그만 보고는 알 수 없고, 그래서 로그만 보고 정하면 안 된다는 게 이 항목의 요지다.

### 빈도가 높은데 E2E를 안 붙인 경로: 상품 목록 탐색

빈도 1위(100%)지만 E2E 대상에서 뺀다. 이미 8주차에 이 화면을 통합 테스트로 촘촘히 검증해뒀다 — `ProductListPage.test.tsx`, `ProductListPage.url.test.tsx` 등에서 카테고리·정렬·페이지네이션이 URL에 반영되는지, MSW로 응답을 흉내 낸 상태에서 목록이 정확히 렌더되는지까지 이미 다룬다. 이 화면이 망가지는 원인은 대부분 "컴포넌트가 props/쿼리 상태를 잘못 반영한다"는 프론트엔드 로직 문제이고, 이건 실제 브라우저·네트워크·쿠키까지 띄우는 E2E가 아니어도 jsdom + MSW 조합으로 충분히 잡힌다. E2E로 다시 만들면 같은 것을 더 비싼 값에 두 번 검증하는 셈이라 스코프에서 제외한다.

(과제의 힌트 그대로다 — "빈도 1위니까 E2E"라는 결론이 나오면 8주차에 이미 뭘로 검증했는지 확인하라고 했다.)

### 시나리오별 이유

- **미로그인으로 보호 경로 진입 → 로그인 → 원래 경로 복원**: `proxy.ts`(가드) → 리다이렉트 → 로그인 폼 제출 → 서버가 원래 경로로 돌려보내는 전체 흐름은 여러 레이어(미들웨어, 쿠키, 폼 제출, 리다이렉트)를 실제로 관통해야 검증된다. 단위·통합 테스트로는 `proxy.ts`가 실제 HTTP 리다이렉트를 일으키는지, 그 사슬 끝에서 브라우저 URL이 진짜로 원래 경로가 되는지를 볼 수 없다. **이 테스트에서 로그인 성공 시 발급되는 세션 쿠키의 `httpOnly` 속성도 함께 단언한다** — `HttpOnly`가 실제로 붙는지는 브라우저가 헤더를 해석해야 확인되는 것이라 jsdom(MSW로 `Set-Cookie` 헤더 문자열을 흉내내도 `httpOnly`·`SameSite` 자체를 해석하는 주체가 없음)으로는 검증 불가능하다.
- **세션 만료 경계(`expired` 시나리오)**: 401을 받았을 때 전역 에러 핸들러가 실제로 로그인 화면으로 옮기고, 헤더가 즉시 비로그인 상태로 바뀌는지는 TanStack Query 캐시·라우팅·화면 렌더링이 실시간으로 맞물려야 확인된다. 이 조합 자체가 여러 레이어에 걸쳐 있어 통합 테스트 단위로는 잘라내기 어렵다.
- **잘못된 자격 증명**: 로그인 폼 자체는 단순하지만, 이 시나리오만 `storageState`를 안 쓰는 이유(과제가 요구하는 서술)가 여기 속한다 — 로그인 실패를 검증하는 테스트가 "이미 로그인된 상태"로 시작하면 애초에 무엇을 검증하는지 의미가 없어지기 때문이다.
- **주문**: 장바구니에 담긴 상품으로 주문서에 진입해 제출하기까지 `cartStore`(zustand) → API 제출 → 성공 후 화면 전환이 실제로 맞물리는지가 핵심이다. 이 전체 사슬이 끊어지면 매출이 막힌다는 게 B절 실패 비용의 근거이므로, 이 사슬 자체를 E2E로 관통해서 본다. **범위는 정상 완료 흐름 1개**(담기 → 주문서 진입 → 제출 → 완료 확인)로 좁힌다 — `POST /api/orders`가 400(빈 목록·없는 상품 id·수량 오류)을 돌려주는 실패 케이스는 이번 3단계에 넣지 않는다. `useCheckoutSubmit`에 아직 테스트가 하나도 없어서 "이미 다른 테스트로 커버된다"고 말할 근거는 없고, 단순히 **컴포넌트가 에러 응답을 받아 화면에 반영하는 문제라 통합 테스트(MSW로 400 응답 흉내)로 충분히 재현되는 성격**이라 판단해 E2E 스코프에서 뺐다. 이 통합 테스트 자체는 이번 3단계 산출물이 아니라 별도로 남는 과제다. **이 테스트(storageState로 이미 로그인된 상태로 시작)에서 초기 HTML에 로그인 상태가 반영되는지도 함께 확인한다** — `page.request`로 JS 실행 없이 원시 HTML을 받아 사용자 이름이 이미 박혀 있는지 보는 방식으로, 이것도 jsdom엔 서버 렌더 단계 자체가 없어 검증 불가능한 지점이다.
- **B절 실패 비용의 정의 대비 초기 계획에서 빠졌던 것**: 과제가 "통합 테스트로 못 잡는 것"의 대표 예시로 든 세 가지(미들웨어 리다이렉트, 쿠키 속성, 초기 HTML 로그인 상태) 중 처음엔 미들웨어 리다이렉트만 챙기고 나머지 둘을 구체적인 단언으로 못 옮겼다 — 4단계 구현 중 뒤늦게 발견해 위 두 시나리오에 단언을 추가하는 방식으로 보강했다(새 시나리오 파일을 만들지는 않음 — "3단계에서 정한 것만 만든다"는 범위를 지키기 위해 기존 시나리오 안에 단언만 추가).

### 유지보수 비용 추정 — 미로그인 → 로그인 → 원래 경로 복원

이 시나리오 하나를 골라 화면이 바뀌었을 때 몇 군데를 고치게 되는지 추정한다.

- **로그인 폼 문구·구조가 바뀌면**: 이메일·비밀번호 입력 필드를 역할(`getByRole('textbox', { name: ... })`)로 잡는다면 라벨 문구가 바뀌지 않는 한 셀렉터는 안 깨진다. 라벨 문구 자체가 바뀌면 셀렉터 1곳(그 필드를 찾는 줄)만 고치면 된다.
- **`redirect` 쿼리 파라미터 이름을 바꾸면**: `proxy.ts`, `login/page.tsx`, 그리고 이 테스트가 리다이렉트 URL을 조립·확인하는 부분까지 총 3곳(프로덕션 코드 2곳 + 테스트 1곳)을 고쳐야 한다.
- **보호 경로 목록이 늘면(예: 장바구니도 보호 대상으로 바뀌면)**: 이 테스트 자체는 안 바뀐다 — 어떤 보호 경로로 시도하든 "미로그인 → 로그인 → 복원"이라는 시나리오 구조는 동일해서, 진입 경로 URL 문자열 1곳만 바꾸면 된다.

정리하면 화면 문구 변경엔 강하고(역할 기반 셀렉터), 파라미터 이름처럼 코드-테스트가 같은 계약을 공유하는 부분엔 약하다 — 이건 E2E의 일반적인 특성이라 이 시나리오만의 문제는 아니다.
