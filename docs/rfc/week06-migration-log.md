# 6주차 FSD 전환 작업 로그

[RFC](./week06-fsd.md)가 무엇을 왜 결정했는지를 다룬다면, 이 문서는 **각 단계가 왜 그 순서에
들어왔고 무엇을 대가로 치렀는지**를 다룬다. 커밋 하나가 항목 하나에 대응한다.

## 기록 축

매 단계에서 아래를 판단한다. 해당 없는 축은 비우지 않고 "해당 없음"과 그 이유를 적는다.
빈칸은 검토하지 않은 것과 검토 후 없다고 판단한 것을 구분하지 못한다.

| 축 | 묻는 것 |
| --- | --- |
| 인과 | 왜 이 단계가 지금 들어와야 하는가. 앞 단계의 무엇을 입력으로 쓰는가 |
| 성능 | 런타임, 번들, 빌드 시간에 미치는 영향 |
| 엣지케이스 | 이 변경으로 새로 생기거나 사라지는 경계 조건 |
| 테스트 | 무엇을 회귀로 고정했는가. 고정하지 않았다면 왜인가 |
| 장애 영향도 | 이 코드가 실패할 때 무엇이 함께 죽는가 |
| 인프라 비용 | 빌드, 배포, 의존성, 실행 환경에 드는 추가 비용 |
| 과잉설계 | 지금 근거 없이 미리 만든 것이 있는가 |
| 트레이드오프 | 무엇을 얻고 무엇을 포기했는가 |

## 1. 멘토링 세션 입력을 결정 근거로 배치

**커밋**: `docs: 멘토링 세션 입력을 결정 근거 순위와 함께 배치`

### 인과

Decision 6(실패 경계)이 멘토링 조언을 근거로 쓸 예정이다. 아직 문서에 없는 근거를 인용할 수
없으므로 기록이 먼저다. 기록하는 김에 조언이 **이미 내린 결정 네 개에 어떤 영향을 주는지**도
함께 판정했다. 나중에 판정하면 결론을 맞춰놓고 근거를 고르게 된다.

조언을 사실과 같은 자리에 적지 않은 이유가 있다. 멘토는 우리 코드를 보지 않았다. 우리 코드에서
확인한 사실과 조언이 어긋나면 사실을 따라야 하는데, 같은 목록에 섞어두면 그 구분이 사라진다.
그래서 Decision Priority에 7위로 명시했다. 관례(8위)보다 위, 우리 코드의 사실(1위)보다 아래다.

### 판정 결과

| 결정 | 판정 | 근거 |
| --- | --- | --- |
| Decision 1 (capability 경계) | 유지 | "라이브러리와 충돌하면 내 설계를 의심하라"를 적용해도, 충돌한 쪽은 Zustand 관례이고 우리 경계는 필수 변경 시나리오에서 나왔다 |
| Decision 3 (조합 위치) | 지지받음 | "조합 지점은 widget"이 결론과 같다. 다만 사후 확인이지 근거는 아니다 |
| Decision 4 (조회 계약 소유자) | Revisit 추가 | 홈의 다중 도메인 응답을 entity가 `select`로 나눠 가지는 경쟁안을 비교하지 않았다 |
| Decision 6 (실패 경계) | 입력 확보 | "컴포넌트 단위가 기준", "고객 경험으로 Suspense를 나눈다" |

Decision 3을 "검증됐다"가 아니라 "지지받는다"로 적은 이유는, 조언이 결론과 같다는 사실이
결론을 강화하지 않기 때문이다. 근거는 여전히 spike에서 측정한 20줄짜리 공통 조합 블록이다.

### 성능

해당 없음. 문서만 변경했다.

### 엣지케이스

해당 없음. 실행 경로가 없다.

### 테스트

해당 없음. 문서에 대한 자동 검증 수단이 이 저장소에 없다. 대신 조언과 결정의 연결을 표로
만들어, 나중에 결정을 바꿀 때 어느 조언이 근거였는지 되짚을 수 있게 했다.

### 장애 영향도

해당 없음.

### 인프라 비용

해당 없음.

### 과잉설계 점검

조언 일곱 개 중 이번 전환에서 실제로 쓰는 것은 네 개다. 나머지 셋(도입 시점, 죽은 코드,
`select` 경쟁안)은 결정을 만들지 않고 참조로만 남겼다. 조언이 있다고 해서 그에 맞는 결정을
새로 만들지 않았다.

### 트레이드오프

얻은 것은 Decision 6이 인용할 근거와, 조언과 사실의 우선순위 구분이다.
포기한 것은 문서 분량이다. Preflight가 길어졌고, 조언 중 셋은 이번 전환에서 아무 역할도
하지 않으면서 자리를 차지한다. 그래도 남긴 이유는 Revisit 조건이 되기 때문이다.
