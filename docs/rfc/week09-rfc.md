## 결정 한 줄 요약 — 보호 경로 경계

**`/checkout`(주문서), `/orders`(주문 내역), `/mypage`(마이페이지)는 보호 경로로 가드한다. `/cart`(장바구니), `/wishlist`(위시리스트)는 보호하지 않는다.**

## 판단 기준

경로마다 질문 하나로 필터링했다.

> "로그인하지 않은 사람이 이 화면에 들어오면 무엇이 문제 되는가?"

이때 화면이 의존하는 **데이터가 어디에 사는가**(서버의 개인 데이터 vs 브라우저 로컬 데이터)를 기준으로 판단한다.

- 화면이 **서버의 세션(개인 데이터)을 바로 요구**하는 API를 호출한다 → 보호
- 화면이 **브라우저에만 존재하는 데이터**(localStorage 등)로 동작한다 → 미보호 가능

## 결정 표

| 경로                     | 보호 여부  | 근거                                                                                                                                                                                           |
| ------------------------ | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/checkout` (주문서)     | **포함**   | `POST /api/orders`를 호출하며 미로그인이면 401. "나"라는 주체 없이는 주문이 성립하지 않음                                                                                                      |

| `/mypage` (마이페이지)   | **포함**   | 로그인 상태(이름·계정 정보)를 보여주는 화면. 미로그인 사용자에게 보여줄 내용이 없으므로 접근 시 로그인으로 안내하는 것이 UX상 자연스러움                                                       |

| `/wishlist` (위시리스트) | **미포함** | 장바구니와 동일하게 로컬 데이터로 유지한다. 담기 자체에 로그인을 요구하면 탐색 중 이탈이 늘어나므로, 미로그인 사용자의 담기는 허용하고 주문 시점에 로그인을 요구함                             |

## 복원 경로 파라미터 결정

**파라미터 이름: `redirectTo`. 값 형식: 경로 + 쿼리스트링 통째로, `encodeURIComponent`로 인코딩해서 실는다.**

### 배경

미로그인으로 보호 경로에 들어오면 `proxy.ts`가 `/login`으로 돌려보내는데, 이때 "원래 가려던 곳" 정보를 실어 보내지 않으면 로그인 후 사용자가 목적지를 잃어버린다. 리다이렉트 URL에 원래 경로를 쪽지처럼 붙여서 복원한다:

```
미로그인으로 /orders?page=2 진입
  → proxy.ts가 /login?redirectTo=%2Forders%3Fpage%3D2 로 이동
  → 로그인 성공 후 redirectTo를 읽어 /orders?page=2 로 복원
```

### 왜 이 이름인가

| 후보                    | 참고                                                                    |
| ----------------------- | ----------------------------------------------------------------------- |
| **`redirectTo`** (선택) | 과제 체크리스트 예시와 일치. "어디로 되돌려보낼지"라는 의미가 가장 명확 |
| `next`                  | Vercel·Next.js 생태계에서 흔함                                          |
| `returnTo`              | Auth0 등에서 사용                                                       |
| `callbackUrl`           | NextAuth 기본값                                                         |

이름 자체에는 정답이 없다. 중요한 것은 **이 문서로 하나의 이름을 미리 확정**한 것이다.

### 이름을 미리 확정하는 이유

이 파라미터는 세 곳이 전부 같은 이름을 써야만 동작한다.

1. `proxy.ts` (1-3) — 리다이렉트 시 `?redirectTo=...`를 실어 보냄
2. 로그인 화면 (1-1) — `useSearchParams()`로 `redirectTo`를 읽음
3. 세션 만료 처리 (1-4) — 만료로 로그인을 보낼 때도 같은 이름으로 실어 보냄

이름이 서로 어긋나면(예: 한쪽은 `redirectTo`, 한쪽은 `returnTo`) 에러가 나지 않고 **복원이 조용히 깨진다.** URL 문자열이라 타입 시스템도 테스트도 잡아주지 못하므로, 구현 전에 문서로 박아두는 것이 유일한 안전장치다.

### 값 형식을 "경로 + 쿼리 통째로"로 정한 이유

경로만 넣으면 원래 `/orders?page=2`를 보고 있던 사용자가 복원 후 1페이지로 초기화된다. URL 안에 URL이 들어가는 꼴이라 인코딩(`encodeURIComponent`)이 필요하다.

### 보안 주의 (별도 결정 항목)

`redirectTo` 값은 사용자가 주소창에서 조작할 수 있다(`?redirectTo=https://evil.com`). 검증 없이 믿으면 오픈 리다이렉트 취약점이 된다. 검증 규칙은 아래 "복원 값 검증 방식 결정" 절에서 확정했다.

## 복원 값 검증 방식 결정

**규칙: 디코딩된 `redirectTo` 값이 `/`로 시작하고 `//`로는 시작하지 않을 때만 복원한다. 그 외의 값은 에러를 내지 않고 기본 경로(`/`)로 되돌린다. 검증은 값을 실어 보내는 곳이 아니라 값을 읽어 실제 이동시키는 순간(로그인 성공 핸들러)에서, `shared/lib`의 한 함수로만 수행한다.**

### 배경 — 오픈 리다이렉트

`redirectTo`는 URL 파라미터라 사용자가 자유롭게 조작할 수 있다. 검증 없이 로그인 후 그대로 이동시키면 `?redirectTo=https://evil.com` 같은 값으로 사용자를 외부 피싱 사이트에 보내는 오픈 리다이렉트 취약점이 된다.

### 왜 블랙리스트가 아니라 화이트리스트인가

블랙리스트는 "안전하지 않은 것"을 전부 나열하는 방식이라 하나라도 빠지면 끝난다.

```
❌ 거르는 목록(블랙리스트): https:// ❌ → 근데 http://는? //evil.com은? javascript:는?
```

반면 화이트리스트는 "안전한 것의 조건"을 정의하고 그 외를 전부 거부한다. 보안 검증은 거의 항상 화이트리스트가 정답이므로, 허용 조건을 정하고 그 외에는 전부 거부하는 방식을 택했다.

### `/`로 시작하는지만 보면 되나 — `//evil.com` 함정

`/`로 시작하는지만 검사하면 이 값이 통과한다:

```
/login?redirectTo=//evil.com
```

그런데 `//evil.com`은 스킴이 생략된 **프로토콜 상대 URL**이라, 브라우저는 "지금 페이지와 같은 프로토콜로 evil.com에 가라"로 해석한다. 즉 `https://evil.com`과 똑같이 외부로 나간다. 그래서 허용 조건은 두 개다:

```ts
// 허용: '/'로 시작 && '//'로는 시작하지 않는 값
value.startsWith('/') && !value.startsWith('//');
```

이 두 조건이면 `https://evil.com`, `//evil.com`, `javascript:alert(1)`이 별도의 거부 목록 없이 전부 "조건 불일치"로 함께 걸린다.

### 검증 위치 — 사용하는 곳에서 한다

검증을 "값을 실어 보내는 곳"(`proxy.ts`가 `?redirectTo=`를 붙이는 자리)에만 두면 뚫린다. 공격자는 보호 경로를 거치지 않고 `/login?redirectTo=//evil.com` 링크를 직접 전달할 수 있기 때문이다. 이 요청에는 `proxy.ts`의 리다이렉트 생성 코드가 실행될 기회 자체가 없다.

값이 들어오는 입구는 여러 개다. `proxy.ts`가 만든 URL, 세션 만료 처리(1-4)가 만든 URL, 주소창 직접 입력, 외부로 돌아다니는 조작된 링크. 반면 이 값으로 위험한 일이 일어나는 출구는 하나다 — 로그인 성공 직후 `router.push(값)` 한 줄. 입구는 막을 수 없으므로 **출구에서 한 번만 검증**한다.

- 위치: 로그인 성공 핸들러에서 이동 직전에 호출
- 구현: `src/shared/lib/getSafeRedirectPath.ts` 한 곳 (`getFailureReason.ts`와 같은 순수 함수 + 단위 테스트 패턴)

```ts
// src/shared/lib/getSafeRedirectPath.ts (1-1에서 구현)
export const getSafeRedirectPath = (value: string | null | undefined, fallback = '/'): string => {
  if (!value) return fallback;
  if (!value.startsWith('/') || value.startsWith('//')) return fallback;
  return value;
};
```

### 세부 규칙

- **거부 시 동작**: 조용히 기본 경로(`/`)로 보낸다. 공격 시도든 오타든 사용자에게 에러를 보여줄 상황이 아니다.
- **디코딩된 값에 대해 검사한다**: `useSearchParams()`가 주는 값은 이미 디코딩된 값이라, `%2F%2Fevil.com` 같은 인코딩 우회도 `/`·`//` 검사가 자연히 잡는다. 검증은 항상 디코딩된 최종 값에 한다.

## 쿠키 검증 수위 결정

**결정: `proxy.ts`는 세션 쿠키의 "존재"만 확인한다. 서명과 만료의 실제 검증은 데이터를 내보내는 API가 항상 수행한다.**

### 배경

`proxy.ts`(미들웨어)는 보호 경로로 들어오는 모든 요청에서 쿠키를 보고 통과·리다이렉트를 판단한다. 이때 검증 수위는 두 가지다: (A) 쿠키가 존재하는지만 보거나, (B) 서명·만료까지 검증하거나. 세션 쿠키는 사용자가 개발자 도구에서 위조·추가할 수 있고(예: `session=fake.fake`), 페이로드는 누구나 읽을 수 있지만 서명은 비밀키 없이는 재현할 수 없다.

### 실측 실험 — 같은 요청 4종을 두 버전으로 실행

production build 위에서 `src/proxy.ts`의 두 버전을 갈아끼우며 curl로 측정했다. matcher는 실험을 위해 `/orders` 한 경로로 축소했다.

- **버전 A(존재만 확인)**: 로직 11줄. `if (!session) redirect` — 기존 상수(`auth-cookies.ts`)만 import.
- **버전 B(서명·만료 검증)**: 로직 약 50줄. Edge 런타임이라 `node:crypto`·`Buffer`를 못 써서 Web Crypto(비동기) + `atob` 기반 base64url 디코딩을 새로 구현해야 했다.

| 요청                     | 버전 A: 존재만 확인                 | 버전 B: 서명까지 검증         |
| ------------------------ | ----------------------------------- | ----------------------------- |
| 쿠키 없음                | 307 → `/login?redirectTo=%2Forders` | 307 → 동일                    |
| 가짜 쿠키 (`fake.fake`)  | **200 통과** → 이후 API 401로 잡힘  | **307 → 문 앞에서 즉시 차단** |
| 진짜 쿠키                | 200                                 | 200                           |
| 서명은 정상, 만료된 쿠키 | (200 통과 → API가 잡음)             | **307 → 문 앞에서 즉시 차단** |
| 응답 시간 (curl 실측)    | 2.6~8ms                             | 1.9~6.5ms — 차이 없음         |

### 실험 관찰 3가지

1. **최종 보안 결과는 두 방식이 동일하다.** 데이터는 API(`orders/route.ts`의 `readSessionToken`)가 서명 검증 후에만 내보내므로, 가짜·만료 쿠키 사용자는 어느 쪽이든 데이터를 얻지 못한다. proxy는 보안 경계가 아니라 UX 가드다. 어느 쪽을 고르더라도 각 API의 검증은 유지된다(다층 방어).
2. **B의 이득은 "문 앞 즉시 차단"뿐이다.** 영향받는 사람은 만료·위조 쿠키 사용자뿐(정상 유저 0)이고 빈도는 세션 만료 시 1회, 차이는 수백 ms의 여정. 이 여정은 1-4의 만료 안내 화면으로 UX 설계가 가능하다.
3. **B의 비용은 실측에서 직접 확인했다.** 로직 11줄 → 약 50줄, `Buffer` 부재로 디코딩 수동 구현, 비동기 전염, 그리고 실제 타입 에러(`Uint8Array<ArrayBuffer>` 호환) 1회 수정. 보안 로직이 2벌이 되면 이런 마찰과 불일치 리스크가 따른다.

### 결론 근거

B가 사는 것은 "만료·위조 쿠키 사용자가 수백 ms 빨리 돌려보내지는 것"이고, 잃는 것은 "검증 코드 2벌 유지 + 구현 마찰 + 오탐 시 전 유저 진입 불가 리스크"다. 파는 것보다 잃는 것이 크므로 **존재만 확인**을 택한다. 단, 이 결정의 전제인 "API는 항상 자기 검증을 한다"가 무너지면(쿠키 존재만 믿는 API가 생기면) 이 결정은 재검토 대상이다.

### 실험 흔적 정리

실험용 `src/proxy.ts`는 결과 기록 후 삭제했다. `/login` 페이지가 아직 없어 가드를 남겨두면 사용자가 404로 가기 때문이다. 1-3에서 버전 A 기반으로 matcher(`/checkout`, `/orders`, `/mypage`)를 확장해 재작성한다.

## 세션 만료(401) 처리 위치 결정

**결정: 감지는 `fetcher.ts`, 반응은 `QueryProvider`의 전역 onError 한 곳.** 401 만료 복구 절차를 수행하는 코드는 앱 전체에서 이 한 자리에만 존재한다.

### "만료 처리"의 정의

세션 만료는 서버가 "너는 로그인 상태가 아니다"라고 선언하는 사건이고, 클라이언트는 아직 로그인 상태를 믿고 있다(헤더, 캐시). 이 불일치를 해소하는 절차가 처리다:

1. **알아채기** — 이 401이 만료인지 판별 (auth 엔드포인트의 401 = 로그인 실패는 제외)
2. **정리하기** — React Query 캐시 비우기, 카트·위시리스트 처리(별도 결정 항목)
3. **알려주기** — "세션이 만료됐어요. 다시 로그인해 주세요" (완료조건: 다음 행동을 화면에서 알 수 있어야 함)
4. **다시 들여보내기** — 현재 경로를 `redirectTo`로 `/login` 이동, 재로그인 후 복원

미처리 시: 헤더는 로그인 중인데 API는 실패하는 상태로, 사용자는 다음 행동을 알 수 없다.

### 401은 "요청이 나가는 순간"에만 발견된다

HTTP는 요청-응답 구조라 서버가 먼저 만료를 알려줄 수 없다. 새로고침·경로 이동의 문서 요청은 proxy가 잡지만(쿠키 `maxAge` 경과 시 브라우저가 쿠키 삭제), **쿠키가 살아있는데 서버가 거부하는 경우**(시계 차이, 서버 측 무효화, `expired` 시나리오 노브)는 화면 내 API 요청의 401로만 나타난다. 이른바 게으른 감지(lazy detection)가 표준이며, 선제적 타이머·폴링은 "장시간 폼 작성 중 제출 시 내용 유실" 같은 실제 근거가 생기면 그때 도입한다.

이 특성 때문에 처리기는 **모든 요청 경로를 커버해야 한다**: 조회(query), 제출(mutation), React Query를 거치지 않는 fetch까지. 한 경로라도 빠지면 그 동작에서 만료가 무처리로 끝난다.

### 후보 검토

| 후보                         | 판단      | 이유                                                                                                                              |
| ---------------------------- | --------- | --------------------------------------------------------------------------------------------------------------------------------- |
| API 래퍼에서 즉시 리다이렉트 | 기각      | shared 모듈(운반책)이 내비게이션까지 수행하면 층이 오염된다. MSW로 401 시나리오를 만드는 모든 테스트에서 리다이렉트 난동이 터진다 |
| fetch 인터셉터               | 해당 없음 | 우리 스택에 없는 개념(axios 기능). `apiFetch`가 사실상 그 역할                                                                    |
| React Query 전역 onError     | **채택**  | 한 자리에서 router 사용 가능. fetcher는 순수 유지. query·mutation을 `QueryCache`·`MutationCache`로 모두 커버                      |

### 처리 구조 (구현 시)

```text
[감지 — fetcher.ts, 기존 구현 유지]
  모든 fetch가 지나는 관문. 401은 ApiError(status: 401)로 throw.
  "어디서 터졌는지"를 몰라도 되므로 감지 자체는 공통 관문이 맞다.

[반응 — QueryProvider 전역 onError, 유일한 한 자리]
  error.status === 401 && auth 엔드포인트 아님 →
    queryClient.clear()          (② 정리)
    카트·위시리스트 처리         (별도 결정 항목)
    /login?redirectTo=<현재경로> 이동 + 만료 안내  (③④)

[화면들]
  개별 401 분기 삭제 (OrderList의 alert 분기 포함).
  "한 곳"이 되려면 나머지가 사라져야 한다.
```

### 401의 두 얼굴 구분 규칙

이 401 처리기가 어떤 401을 만료로 볼지의 기준은 아래 "401 두 얼굴 구분 기준 결정" 절에서 확정했다.

## 401 두 얼굴 구분 기준 결정

**결정: 401을 돌려받은 요청이 향한 엔드포인트로 의미를 분류한다.** 응답 본문으로는 구분이 불가능하므로, 요청의 목적지가 유일한 단서다.

| 401 출처                    | 해석                     | 처리 자리                          |
| --------------------------- | ------------------------ | ---------------------------------- |
| `POST /api/auth/login`      | 자격 증명 실패           | 로그인 폼 (에러 메시지 표시)       |
| `GET /api/auth/me`          | 로그인 안 함 (정상 상태) | 헤더 (조용히 로그아웃 UI 렌더)     |
| 보호 API (`/api/orders` 등) | 세션 만료                | 전역 처리기 (정리·안내·리다이렉트) |

### 배경 — 서버가 원인을 뭉개서 준다

`readSessionToken`은 "쿠키 없음 / 서명 불일치 / 만료" 세 이유를 모두 `null`로 뭉개서 돌려주고, me와 orders는 그를 동일한 401 본문(`{ message: '로그인이 필요합니다.' }`)으로 변환한다(스타터 계약이라 변경 불가). 게다가 httpOnly라 클라이언트 JS가 쿠키 존재 여부를 확인할 수도 없다. 그래서 클라이언트가 구분할 수 있는 단서는 **"이 요청이 어디를 향했는가"**뿐이다.

### me의 401을 만료로 취급하면 생기는 재앙 (틀린 규칙 시뮬레이션)

로그인한 적 없는 방문자가 홈을 열면 → 헤더가 me 호출 → 401 → 전역 처리기가 "만료"로 발동 → 홈을 못 보고 로그인 페이지로 강제 이동 + 엉뚱한 "세션 만료" 안내. 연쇄 문제:

1. 이 앱은 회원가입이 없어 **신규 방문자의 탈출구가 사라진다**
2. `/login`에도 헤더가 있으면 me 401 → 리다이렉트 → **무한 루프 위험**
3. "products·홈은 공개", "게스트 카트 허용"이라는 기존 결정들과 **정면충돌**

빈도도 비대칭이다: 미로그인 방문자는 **매 방문**, 만료 회원은 **만료 시 1회**. 틀린 규칙은 가장 자주 터지는 지점을 노리게 된다.

### 감수하는 트레이드오프

me의 401에는 실제로 만료된 회원의 401도 섞여 있다(서버가 구분 불가). 이 규칙은 그 회원이 **me 경로로는 만료 안내를 받지 못함**을 감수한다. 대신 다른 두 관문이 교정한다:

- 쿠키가 자연 삭제(maxAge 경과)된 경우: 새로고침 문서 요청을 **proxy**가 먼저 잡아 `/login?redirectTo`로 보낸다
- 쿠키가 살아있는데 서버가 거부한 경우(시계 차이, `expired` 노브 등): 보호 API 동작 시 **전역 처리기**가 정확한 만료 처리를 수행한다

개선 옵션(서버가 만료 시 다른 본문 반환, localStorage에 로그인 흔적을 둔 클라이언트 휴리스틱)은 실무에서 필요 근거가 생기면 검토할 사항으로 남긴다.

### 만료 재현 방법

`?scenario=expired`(또는 scenario 쿠키) 노브로 재현한다 — "쿠키는 유효한데 API가 401"이라, proxy를 우회하는 만료 경로를 시간 재현 없이 테스트할 수 있다. (4단계 E2E 만료 경계 테스트가 이 경로를 검증한다.)

## 로그아웃·만료 시 클라이언트 상태 정리 방침 결정

**결정: 로그아웃과 세션 만료 모두에서 React Query 캐시는 반드시 비우고, 장바구니·위시리스트(localStorage)는 유지한다. 두 이벤트는 같은 정리 절차(한 곳의 함수)를 공유한다.**

### 정리 대상의 분류

| 대상                          | 소유                | 방침             | 이유                                                                         |
| ----------------------------- | ------------------- | ---------------- | ---------------------------------------------------------------------------- |
| React Query 캐시 (me, orders) | 세션 파생           | **반드시 clear** | 같은 브라우저에서 다른 계정이 로그인하면 개인 데이터가 혼입된다. 선택지 없음 |
| 장바구니·위시리스트           | 기기 (localStorage) | **유지**         | 아래 근거 3가지                                                              |

### 유지의 근거 3가지

1. **일관성**: 게스트 카트(미로그인 담기 허용)의 취지는 "담아두고 나중에 로그인·구매"다. 로그아웃 시 비우면 그 취지와 모순 — 재로그인 시 담아둔 것이 증발해 이탈을 유발한다. (카트를 열어준 이유가 사라진다.)
2. **단순함**: 만료는 사용자 의지가 아닌 강제 로그아웃이다. 만료 때 카트를 비우면 담는 노력이 증발한다. "어떤 형태든 로그아웃 상태면 유지"라는 단일 방침은 로그아웃 버튼과 만료 처리기가 같은 정리 함수를 공유하게 하고, 코드 조건도 설명도 한 줄이 된다.
3. **조건부 결정임을 인정**: 이 판단의 전제는 "각자 개인 기기를 쓰는 쇼핑 서비스"다. 공용 PC(피시방·키오스크)가 주 환경이면 프라이버시 때문에 '지운다'가 정답이 되고, 카트를 서버 계정에 동기화하는 실무 서비스라면 이 질문 자체가 사라진다(로그아웃은 클라이언트 캐시만 지움). **전제가 바뀌면 재검토한다.**

### 구현 위치

정리 함수는 만료 처리기(QueryProvider 전역 onError)와 로그아웃 버튼 핸들러가 공유한다. 카트·위시리스트 유지는 "기본값(no-op)을 쓰겠다 + 근거 문서화"라는 형태라 별도 코드가 필요 없다.

## 세션 상태 소유 구조 검토

**결론: 세션은 5주차 분류상 '서버 상태'지만, 소유 구조를 그대로 가져오면 안 된다. 진실의 원천은 httpOnly 쿠키 + 서버 검증이 유일하게 소유하고, 클라이언트는 조회 캐시(사본)만 가진다.**

5주차 패턴 = 서버 상태(React Query) / URL 상태(nuqs) / 클라이언트 상태(zustand+persist)의 분류. 세션의 특수성: (1) 서버만 진실을 판정하고, (2) 아무도 건드리지 않아도 시간(exp)에 의해 스스로 무효화되며, (3) httpOnly라 클라이언트가 원본을 읽을 수 없다.

| 패턴                           | 적용 검토                       | 결과                                                                                                                                                                                                 |
| ------------------------------ | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| zustand + persist (카트 방식)  | 세션 원본을 localStorage에 저장 | ❌ 기각 — 진실의 원천이 둘 생긴다(localStorage의 믿음 vs 서버 판정). 만료 시 "헤더는 로그인 중, API는 401"인 이중 진실이 된다. 토큰을 localStorage에 두면 XSS 탈취 위험(httpOnly 존재 이유를 무효화) |
| React Query (서버 상태 조회)   | me 조회 캐시                    | ⭕ 채택 + 조건 — (a) 만료 401 시 무효화가 전역 처리기에 필수 (b) 세션은 아무도 안 건드려도 만료되므로 staleTime 함정 주의 (c) 쿠키가 필요한 요청이라 서버 prefetch 불가 → 클라이언트 전용 조회       |
| URL 상태 (nuqs)                | —                               | 해당 없음 (세션을 URL에 두는 것 자체가 보안 사고)                                                                                                                                                    |
| (신규) 서버 컴포넌트 쿠키 읽기 | 초기 HTML에 로그인 상태 반영    | 5주차 체계에 없던 추가 패턴. JS 실행 전 표시 요구(1-2) 때문에 필요                                                                                                                                   |

### 진실의 원천 대비

| 데이터          | 진실의 원천               | 클라이언트의 위치                                                                 |
| --------------- | ------------------------- | --------------------------------------------------------------------------------- |
| 카트·위시리스트 | localStorage (클라이언트) | 원본 소유 — zustand persist가 적합했던 이유                                       |
| 세션            | 쿠키 + 서버 검증          | 원본을 볼 수도 없음 — me 조회로 받은 사본만. 궁금하면 버리고(clear) 다시 물어본다 |

### 초기 HTML 반영 위치와 정적 생성 트레이드오프 (1-2)

쿠키를 읽는 컴포넌트가 있는 경로는 정적 생성(○)이 동적 생성(ƒ)으로 바뀐다. 요청마다 달라지는 세션 값을 정적 HTML에 담을 수는 없기 때문이다. 그래서 읽는 위치를 나눴다:

- **보호 경로(`/orders`)**: 서버 컴포넌트가 `cookies()` + `readSessionToken`으로 세션을 판독해 헤더에 이름을 그린다. ○ → ƒ 전환은 개인 데이터 페이지가 요청마다 사용자별로 렌더되어야 하므로 옳은 변화다. 초기 HTML(JS 실행 전)에 로그인 상태가 있어야 한다는 요구를 충족한다.
- **공개 페이지(홈 `/` ○, `/login` ○)**: 쿠키를 읽지 않고 정적 생성을 유지하고, 헤더의 로그인 상태는 클라이언트 me 조회로 채운다(첫 페인트 후 채워지는 짧은 지연 존재). **7주차 성능 기준(정적 생성·LCP)을 깨지 않기 위한 선택**이다.
- 검증: `pnpm build` Route 목록 — `/` ○, `/login` ○, `/orders` ƒ. curl(= JS 실행 없음)로도 확인: 쿠키 있음 → 초기 HTML에 `루퍼1님`+로그아웃 버튼, 없음 → `로그인` 링크.

공개 페이지의 깜빡임이 문제가 되면(근거 생기면) 그때 공개 페이지도 동적 전환 또는 PPR 도입을 재검토한다.

## 리다이렉트 수행 주체 총정리

리다이렉트는 proxy의 전유물이 아니라, **발견 시점별로 세 주체가 나눠 수행한다.** 같은 규칙(`redirectTo` 파라미터, `getSafeRedirectPath` 검증)을 공유한다.

| 주체                       | 트리거                                        | 예                                                                 |
| -------------------------- | --------------------------------------------- | ------------------------------------------------------------------ |
| `proxy.ts`                 | 미로그인으로 보호 **페이지** 진입 (문서 요청) | 쿠키 삭제 후 `/orders` 새로고침 → `/login?redirectTo=/orders`      |
| QueryProvider 전역 onError | 페이지 사용 중 **보호 API** 401               | 주문 제출 401 → 정리 후 `/login?redirectTo=/checkout`              |
| 로그인 폼 성공 핸들러      | 로그인 성공                                   | `router.push(getSafeRedirectPath(redirectParam))` — 원래 경로 복원 |

proxy의 matcher는 API 경로를 포함하지 않는다 — 존재만 확인하는 proxy가 API에서 할 일이 없고, API는 상태 코드(401)와 JSON으로 답해야지 리다이렉트로 답하면 안 되기 때문이다.

### 로그아웃 후 목적지

**결정: `/`(홈)으로 이동한다.** 근거: 로그아웃 직후 머무를 곳은 개인 데이터가 없는 공개 페이지여야 하는데, 현재 페이지가 보호 경로(`/orders` 등)일 수 있어 유지하면 proxy가 다시 `/login`으로 튕긴다. 로그아웃 = "공간을 나온다"는 의미와도 자연스럽다.

## 이벤트 이름 규칙 결정 (2-0)

**결정: `객체_행동` 순서의 snake_case로 통일한다. 이름 하나가 "화면(대상) + 행동"을 정확히 가리켜야 한다. (예: `product_list_view`, `cart_add`, `login_success`)**

> 체크리스트 2-0 "이벤트 이름 규칙 정하기"에 대응한다.

### 배경 — 이름이 곧 집계 단위

이벤트 이름은 나중에 로그를 집계할 때의 단위다. 그래서 규칙을 정하기 전에 "나중에 이 이름으로 무엇을 셀 것인가"를 먼저 생각해야 한다. `button_click` 하나로 몰아넣으면 "무엇을 클릭했는지"가 이름에서 사라지고, 목록→상세→담기→주문 퍼널의 어느 단계인지 구분할 수 없어 집계 자체가 불가능해진다.

### 규칙

| 규칙                                             | 예                                              |
| ------------------------------------------------ | ----------------------------------------------- |
| snake_case, 앞에 객체 뒤에 행동                  | `product_detail_view`, `category_filter_change` |
| 행동은 view·change·add·success/fail 등 결과 중심 | `login_fail`, `order_complete`                  |
| 한 이름 = 한 화면·한 행위 (범용 이름 금지)       | `button_click`, `page_view` ❌                  |

### 시드 로그와의 관계

시드 로그(`fixtures/events-30d.jsonl`)가 이미 같은 규칙을 따른다. 규칙을 일치시키면 2-3의 "시드 로그 ↔ 내 이름 매핑 표" 비용이 최소화된다. 단, "무조건 일치"는 강제가 아니다 — 로그에는 이 코드베이스에 화면이 없는 이벤트(`wishlist_add` 등)가 있고, 반대로 내 앱에만 있는 이벤트는 시드 로그에 없다. 매핑 표가 존재하는 이유 자체가 양쪽이 완전히 같지 않을 수 있음을 전제하는 것이다.

### 후보 검토

| 후보                            | 판단     | 이유                                                              |
| ------------------------------- | -------- | ----------------------------------------------------------------- |
| `객체_행동` snake_case          | **채택** | 시드 로그와 규칙이 일치해 매핑 비용 최소. 집계 스크립트 친화적    |
| camelCase (`productListView`)   | 기각     | 시드 로그·GA4 이전 세대 관례와 불일치. 매핑 표에서 실수 여지 증가 |
| 범용 이벤트 (`button_click` 등) | 기각     | 행동 대상이 이름에서 사라져 아무것도 셀 수 없음 (본 절 배경 참고) |

## 공통 프로퍼티 결정 (2-0)

**결정: 모든 track 이벤트에 `sessionId`, `ts`, `device`를 공통 부착한다. `userId`는 공통 프로퍼티에서 제외하고, 로그인 성공 시 `identify()` · 로그아웃 시 `reset()`으로 관리한다.**

> 체크리스트 2-0 "공통 프로퍼티 목록 정하기"에 대응한다. 시드 로그의 필드 구조를 기준으로 삼았다.

### 판단 기준

한 필드가 공통 프로퍼티인지의 기준은 **"모든 이벤트에 같은 의미로 붙는가"** 하나다.

- 예 (공통): `sessionId` — 모든 이벤트가 어느 방문에 속했는지
- 아니오 (이벤트별 props): `productId` — 장바구니 담기에만 의미가 있음

### 시드 로그 필드 대응표

| 시드 로그 필드 | 내 처리             | 근거                                                                                                   |
| -------------- | ------------------- | ------------------------------------------------------------------------------------------------------ |
| `sessionId`    | 공통 프로퍼티       | 세션 = "한 번 방문" 단위. 3단계에서 이벤트 수가 아닌 **세션 기준**으로 순위를 매길 때의 분모가 된다    |
| `ts`           | 공통 프로퍼티       | 이벤트 발생 순간의 기록. 세션 내 이벤트 순서 재현에 필수                                               |
| `device`       | 공통 프로퍼티       | 세그먼트 분석용. 시드 로그의 값 집합(mobile/desktop/tablet)과 일치시킴                                 |
| `userId`       | `identify()`로 분리 | logger가 identify를 track과 별도 타입으로 분리한 구조를 따른 것. 로그인 전후 구분이 코드 구조로 명시됨 |
| `name`/`props` | `track()` 인자      | 이벤트별 값이라 공통이 아님                                                                            |

### 구현 결정 상세

- **`sessionId`: `sessionStorage` + `crypto.randomUUID()`.** 탭 단위라 새로고침해도 유지되고 탭을 닫으면 새로 발급된다 — "새 방문 = 새 세션" 정의에 정확히 대응. `localStorage`는 기각: 며칠 뒤 재방문도 같은 세션이 되어 "방문"이라는 개념이 소멸하고, 그러면 세션 기준 집계(3단계)가 불가능해진다.
- **`ts`: 함수 등록으로 발생 시점 평가.** `setCommonProperties`는 값이 아니라 `() => EventProperties` 함수를 받고, `track()`이 불릴 때마다 실행한다(logger.ts). 만약 등록 시점에 객체를 미리 만들어 넣으면 모든 이벤트의 ts가 페이지 로드 시각으로 고정되는 버그가 된다.
- **`device`: `window.innerWidth` 휴리스틱** (<768 mobile, <1024 tablet, 나머지 desktop). 시드 로그 값 집합과 일치시켜 나중에 로그와 대조 가능하게 한다.
- **검증 방법**: `window.__analytics`의 모든 항목에 동일한 `sessionId`가 붙는지, `ts`가 이벤트마다 조금씩 다른지 확인한다 (2-3, 2-4의 콘솔 검증으로 이어짐).

## initAnalytics 호출 위치 결정 (2-1)

**결정: 루트 레이아웃에 심는 클라이언트 전용 컴포넌트(`AnalyticsInit`)의 첫 effect에서 `registerProviders` → `setCommonProperties` → `initAnalytics` 순으로 1회 호출한다.**

> 체크리스트 2-1 "`initAnalytics()`를 부를 위치 정하고 근거 메모"에 대응한다.

### 배경 — 큐 한도와 이벤트 유실

logger는 초기화 전에 도착한 이벤트를 큐에 보관했다가 개점 시 순서대로 보낸다. 큐는 100개 한도이고 넘치면 오래된 것부터 폐기한다(MAX_QUEUE_SIZE, logger.ts). 초기화가 늦을수록 그 사이 도착한 track이 큐에 적립되므로, **"앱이 켜진 뒤 도달 가능한 가장 이른 시점"**에서 초기화하는 것이 유실 위험을 최소화한다.

### 후보 검토

| 후보                                           | 판단     | 이유                                                                                              |
| ---------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------- |
| `layout.tsx`(서버 컴포넌트)에서 직접 호출      | 기각     | 서버에 `window`가 없다. 브라우저 전용 작업의 자리가 아님                                          |
| 각 페이지 컴포넌트마다                         | 기각     | 페이지마다 누락 위험이 있고, 경로마다 초기화 시점이 제각각이라 큐 적립이 커진다                   |
| `'use client'` 파일 모듈 최상단                | 기각     | 서버에서도 모듈 평가가 일어난다(SSR). import 시점의 사이드 이펙트는 실행 환경을 보장할 수 없다    |
| **루트 레이아웃의 클라이언트 컴포넌트 effect** | **채택** | (1) 전 경로를 한 곳에서 커버 (2) 브라우저에서 가장 이른 시점 (3) 기존 `QueryProvider`와 같은 패턴 |

### 호출 순서 규칙

`registerProviders` → `setCommonProperties` → `initAnalytics`의 순서가 절대다. 개점(`initAnalytics`)이 등록보다 먼저 되면 `initialized = true`인 상태로 프로바이더 명단이 비어 있어, 이후 모든 이벤트가 어디에도 전달되지 않고 **에러 없이 조용히 증발**한다.

### 부수 결정

- `useEffect(fn, [])` 빈 의존성 배열 — 첫 렌더 후 정확히 1회.
- React StrictMode의 개발 모드 이중 실행은 `initialized` 플래그의 멱등성(logger.ts)으로 안전하다.
- 검증: `pnpm start` 후 콘솔의 `[analytics]` 로그와 `window.__analytics` 확인 (2-3, 2-4로 이어짐).

### 배치 표

### 제외한 화면 — 근거 기록

| 시드 로그 이벤트                                  | 제외 근거                                                                                                                                                                                                                  |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `product_detail_view` (상세 진입)                 | 상품 상세 화면이 없다. `ProductCard`는 표현(entity)만 하고 상세 경로로의 링크가 없어, 진입 자체가 존재하지 않는다. 화면을 새로 만들지 않는다 (체크리스트 3-2 "로그에는 있는데 내 코드에 화면이 없는 이벤트"의 근거가 된다) |

### 세부 규칙

- **`cart_add`는 "담기" 시점만 기록한다.** `CartButton`은 토글 버튼이라(담기 ⇄ 해제) 해제에도 불리면 시드 로그 스키마에 없는 이벤트가 만들어진다. `isInCart === false`일 때만 track하고, 해제는 스키마 확장 전까지 기록하지 않는다.
- **`login_fail`의 `reason`은 시드 로그와 같은 코드 체계를 쓴다** — `INVALID_CREDENTIALS`(401) / `INVALID_FORMAT`(400) / `UNKNOWN`(그 외). 나중에 시드 로그의 실패 집계와 직접 비교할 수 있게 하기 위함이다 (`getLoginFailReason`, `getLoginErrorMessage`와 같은 순수 함수 패턴).
- **`identify`는 `login_success`보다 먼저 연결한다** — "이 시점부터 이 사용자"라는 의미 순서다. `reset`은 로그아웃 요청 성공 직후에 둬서 로그아웃 이후 행동이 이전 사용자 것으로 기록되지 않게 한다.

## 구현에 미치는 영향

1. **`proxy.ts` 가드 대상**: `/checkout`, `/orders`, `/mypage` 세 경로. 미로그인 진입 시 `/login?redirectTo=<원래 경로>`로 리다이렉트한다. 파라미터 이름은 위 "복원 경로 파라미터 결정" 절 참고. 검증 수위는 "존재만 확인"("쿠키 검증 수위 결정" 절).
2. **화면 신규 생성 필요**: 현재 앱에 `/checkout`, `/orders`, `/mypage` 페이지가 없다. 가드를 검증하려면 최소 하나의 보호 화면이 실제로 존재해야 하므로, `GET /api/orders`로 주문 내역을 보여주는 `/orders` 페이지를 먼저 만든다. (체크리스트 1-0 "보호할 화면이 앱에 없으면 먼저 만들기")
3. **세션 만료(401) 처리**: 감지는 `fetcher.ts`(ApiError throw), 반응은 `QueryProvider`의 전역 onError 한 곳에서 정리·안내·`/login` 이동을 수행한다. `/api/auth/*`의 401(로그인 실패)은 제외하고, 화면별 401 분기는 삭제한다. 근거는 위 "세션 만료(401) 처리 위치 결정" 절 참고.
4. **복원 값 검증**: `redirectTo`는 로그인 성공 핸들러에서 이동 직전 `getSafeRedirectPath()`(`shared/lib` 예정)로 검증한 뒤 이동시킨다. 규칙과 근거는 위 "복원 값 검증 방식 결정" 절 참고.
5. **쿠키 검증 수위**: `proxy.ts`는 존재만 확인하고, 서명·만료 검증은 각 API가 `readSessionToken()`으로 수행한다. 실측 실험 기록은 위 "쿠키 검증 수위 결정" 절 참고.
6. **401 두 얼굴 구분**: 엔드포인트 기준으로 분류한다 — login 401 = 자격 증명 실패(폼이 자체 표시), me 401 = 로그인 안 함(헤더가 조용히 로그아웃 UI), 보호 API 401 = 만료(전역 처리기). 근거는 "401 두 얼굴 구분 기준 결정" 절 참고.
7. **상태 정리 방침**: 로그아웃·만료 모두 React Query 캐시는 clear, 카트·위시리스트는 유지. 정리 함수는 만료 처리기와 로그아웃 버튼이 공유한다. 근거는 "로그아웃·만료 시 클라이언트 상태 정리 방침 결정" 절 참고.
8. **세션 소유 구조**: 세션 원본은 클라이언트 저장소에 두지 않는다. me는 React Query 조회 캐시로, 초기 HTML 표시는 서버 컴포넌트 쿠키 읽기로. 근거는 "세션 상태 소유 구조 검토" 절 참고.
9. **리다이렉트 주체**: 진입 차단은 proxy, 사용 중 만료는 QueryProvider, 복원은 로그인 폼, 로그아웃 이동은 홈(/)으로. 근거는 "리다이렉트 수행 주체 총정리" 절 참고.
10. **이벤트 이름 규칙**: `객체_행동` snake_case로 통일한다. 2-2 계측 배치와 3단계 RFC A절 매핑 표의 기준이 된다. 근거는 "이벤트 이름 규칙 결정" 절 참고.
11. **공통 프로퍼티**: `sessionId`·`ts`·`device`를 `setCommonProperties`로 등록해 전 이벤트에 자동 부착한다. `userId`는 공통 프로퍼티에서 제외하고 로그인 성공 시 `identify()`, 로그아웃 시 `reset()`으로 관리한다. 근거는 "공통 프로퍼티 결정" 절 참고.
12. **initAnalytics 위치**: 루트 레이아웃의 `AnalyticsInit`(클라이언트 컴포넌트) effect에서 등록 → 공통 프로퍼티 등록 → 개점 순으로 1회 호출한다. 근거는 "initAnalytics 호출 위치 결정" 절 참고.
13. **계측 지점 배치**: 목록 진입·장바구니 담기·로그인 3종을 지정 지점에 배치하고, `identify`(로그인 성공 직후)·`reset`(로그아웃)을 연결한다. 상세 진입·주문 시작/완료는 화면 부재로 제외한다. 근거는 "계측 지점 배치와 제외 결정" 절 참고.
