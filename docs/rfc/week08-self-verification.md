# 8주차 3단계: 내 테스트가 진짜 뭘 잡는지

> 구현을 한 곳씩 일부러 망가뜨려, 2단계에서 쓴 테스트가 그걸 잡는지 확인한 기록.
> 과제: `docs/assignments/week-08.md` 3단계 / 구현 계획: `specs/260820-week08-step2-tests.spec.md`

## 무엇을 고를지부터가 실험이었다

2단계를 진행하며 테스트를 쓸 때마다 변이를 돌려 스무 건 넘게 확인했다. 전부 잡혔지만 3단계의 재료로 삼기엔 약하다. **방금 쓴 테스트가 겨눈 자리를 그대로 되돌린 것이라 잡히는 게 당연했다.** 과제도 같은 것을 경고한다.

> 세 실험이 전부 한 번에 잡혔다면, 쉬운 곳만 고른 게 아닌지 다시 보세요.

그래서 기준을 세 가지로 잡고 다시 골랐다.

- **형태를 맞춘다.** 조건을 뒤집거나, 호출을 지우거나, 경계 부호를 바꾼다. 라이브러리를 갈아끼우는 것은 "구현 한 곳"이 아니다.
- **살아남을 자리를 노린다.** 살아남아야 왜 못 잡았는지를 캐고 보강할 수 있다.
- **잡혀도 거기서 끝내지 않는다.** 실패 목록만 보고 원인을 좁힐 수 있는지가 테스트 이름과 단언의 품질이다.

## 실험 기록

| #   | 망가뜨린 곳                                    | 어떻게 바꿨나                          | 결과         | 실패한 테스트                                                        |
| --- | ---------------------------------------------- | -------------------------------------- | ------------ | -------------------------------------------------------------------- |
| 1   | `product-list-params.ts` page 파서 (단위)      | `&& page >= 1` 조건 삭제               | 잡힘         | `page=0` · `page=-1`은 1페이지로 되돌린다 (네 케이스 중 둘)          |
| 2   | `ProductList.tsx` `confirmedTotalPages` (통합) | `isPlaceholderData ? null :` 가드 삭제 | **살아남음** | 없음. vitest 205개와 Playwright 11개가 모두 통과                     |
| 3   | `search-params.ts` `usePageClamp` (E2E)        | `history: 'replace'` → `'push'`        | 잡힘         | 페이지 보정은 히스토리에 남지 않아 뒤로 가면 원래 있던 곳으로 나간다 |
| 4   | `ProductList.tsx` 이전 버튼 (통합)             | 경계 부호 `page <= 1` → `page < 1`     | 잡힘         | 첫 페이지에서는 이전으로 갈 수 없다                                  |

## 실험 1 — 페이지 하한을 지운다 (단위)

```diff
- return Number.isSafeInteger(page) && page >= 1 ? page : null;
+ return Number.isSafeInteger(page) ? page : null;
```

"페이지는 1부터"라는 규칙만 걷어내고 정수 검사는 남겨, 일부만 무너지게 했다.

**잡혔다.** `it.each` 네 케이스 중 둘이 실패했다.

```
FAIL  page=0처럼 1 이상의 정수가 아니면 1페이지로 되돌린다
-   "page": 1,
+   "page": 0,
```

**실패 메시지로 원인을 알 수 있었다.** 값 하나가 아니라 어떤 케이스가 죽고 어떤 케이스가 살았는지가 함께 보였기 때문이다. `1.5`와 `abc`는 여전히 통과했으니 정수 검사는 멀쩡하고 하한만 사라졌다는 데까지 좁혀진다.

이름을 `page=%s`로 케이스마다 찍어둔 덕이다. `'잘못된 page를 거른다'`처럼 한 덩어리였다면 어느 입력이 뚫렸는지 알 수 없었을 것이다.

## 실험 2 — 갱신 중 총 페이지 수 가드를 지운다 (통합, 살아남음)

### 무엇을 바꿨나

```diff
- const confirmedTotalPages = isPlaceholderData ? null : totalPages;
+ const confirmedTotalPages = totalPages;
```

`usePageClamp`는 이 값으로 "지금 페이지가 범위를 벗어났는가"를 판정한다. 가드를 지우면 갱신 중에 **이전 조건의 총 페이지 수로** 판정한다.

### 결과 — 살아남았다

통합만이 아니라 단위와 E2E까지 아무도 잡지 못했다. vitest 205개, Playwright 11개 모두 통과.

### 왜 못 잡았나

**깨지긴 한다.** `?page=3`(전체 3페이지)에서 홈(1페이지)으로 옮기고 5분 넘게 머문 뒤 뒤로 가면, 목록 쿼리의 `gcTime`(기본 5분)이 지나 캐시가 없어진 상태라 홈 목록을 갱신 중 화면으로 쓴다. 그때 `page 3 > totalPages 1`로 판정해 1페이지로 밀어낸다. `page.clock.fastForward`로 재현했다.

**그런데 이건 1단계에서 지키기로 한 동작이 아니다.**

| 항목 8·9·10이 지키기로 한 것                               | 이 가드가 지키는 것              |
| ---------------------------------------------------------- | -------------------------------- |
| 조건을 바꾸면 새 요청이 나가고 화면이 그 응답으로 갈아탄다 | 갱신 중에 보정이 끼어들지 않는다 |

**살아남은 것이 테스트의 빈틈을 뜻하지 않는다.** 지키기로 한 적이 없으니 안 잡히는 게 맞다. 3단계가 물을 것은 "이 코드가 안 잡히나"가 아니라 "지키기로 한 것을 테스트가 지키나"다.

### 대응 — 테스트를 붙여봤지만 남기지 않는다

재현용 Playwright 테스트를 실제로 붙여봤다. `?page=3`에서 홈 카테고리로 이동해 새 목록이 완전히 도착할 때까지 기다린 뒤, 이전 쿼리의 구독이 끊긴 상태에서 `page.clock.fastForward`로 기본 `gcTime` 5분을 넘기고 뒤로 가는 순간의 요청을 지연시켜야 변이가 드러났다. 변이는 잡았지만 테스트의 성패가 사용자 동작보다 캐시 만료 시점, 구독 해제 순서, 응답 지연에 묶였다. 캐시 정책이나 요청 타이밍만 바뀌어도 기능이 정상인데 깨질 테스트라 재현 가능성만 확인하고 제거했다.

- **범위 밖이다.** 1단계에서 지키기로 한 동작이 아니다.
- **깨지기 쉽다.** 카테고리를 바꾼 뒤 새 목록이 도착할 때까지 기다리지 않으면 이전 쿼리가 구독자를 잃지 않아 만료 타이머가 시작되지 않고, 시계를 돌려도 변이가 드러나지 않는다.
- **지키는 값이 작다.** 5분 넘게 머문 뒤 뒤로 갈 때 한 페이지 밀리는 증상이다.

대신 이 줄이 무엇을 막는지를 코드 옆에 적는다. 그게 없으면 다음 사람이 지워도 되는지 판단할 수 없다.

```ts
// 이전 목록을 보여주는 동안에는 현재 조건의 총 페이지 수를 아직 모른다.
// 그 값으로 보정하면 캐시가 만료된 뒤 뒤로 왔을 때 엉뚱한 페이지로 밀어낸다.
const confirmedTotalPages = isPlaceholderData ? null : totalPages;
```

## 실험 3 — 페이지 보정을 히스토리에 남긴다 (E2E)

```diff
  const [{ page }, setConditions] = useQueryStates(conditionParsers, {
-   history: 'replace',
+   history: 'push',
  });
```

보정은 사용자가 이동한 것이 아니므로 기록에 남기지 않는다는 결정이, 코드에는 단어 하나로만 있다. `clampPage` 호출을 통째로 지우면 화면이 "올바른 페이지로 이동 중입니다"에서 멈춰 너무 쉽게 잡히므로, 보정은 정상인데 흔적만 남는 차이를 골랐다.

**잡혔다.** E2E 11개 중 하나가 실패했다.

```
FAIL  페이지 보정은 히스토리에 남지 않아 뒤로 가면 원래 있던 곳으로 나간다
  Expected pattern: /\/products$/
  Received string:  "http://localhost:3000/products?page=3"
  Call log:
    3 × unexpected value "http://localhost:3000/products?page=99"
```

**실패 메시지가 증상을 그대로 보여줬다.** 뒤로 가니 보정 전 주소인 `?page=99`가 나왔고, 거기서 보정이 다시 돌아 `?page=3`으로 튕겼다. 두 주소 사이를 왕복하는 모습이 call log에 찍혀, 보정이 기록에 쌓였다는 것을 바로 짚을 수 있었다.

이 실험은 방법론 배치도 함께 검증한다. 히스토리는 jsdom에서 재현되지 않아 통합으로는 볼 수 없다. 1단계에서 항목 13을 E2E로 내린 판단이 옳았다는 증거다.

## 실험 4 — 이전 버튼의 경계 부호를 바꾼다 (통합)

실험 2가 살아남으면서 통합 쪽에는 "무언가를 잡았다"는 기록이 없어졌다. 통합 테스트가 실제로 지키는 것이 있는지 보이려고 하나를 더 골랐다.

```diff
- disabled={page <= 1 || isUpdating}
+ disabled={page < 1 || isUpdating}
```

1페이지에서 `1 < 1`이 거짓이 되어 `이전` 버튼이 열린다.

**잡혔다.** 하나가 실패했다.

```
FAIL  페이지 이동 > 첫 페이지에서는 이전으로 갈 수 없다
  expect(element).toBeDisabled()
  Received element is not disabled
```

**메시지만으로는 절반만 알 수 있었다.** "잠겨 있어야 할 것이 안 잠겼다"까지만 말하고 왜인지는 말하지 않는다. 원인을 좁혀준 것은 테스트 이름이었다. `'첫 페이지에서는 이전으로 갈 수 없다'`가 조건과 결과를 함께 담고 있어 잠금 조건의 경계를 보러 가면 된다는 게 바로 나온다. `'이전 버튼 동작'` 정도였다면 어디를 열어야 할지 알 수 없었을 것이다.

---

## 정리

- **방법론마다 하나 이상** — 단위 1건, 통합 2건, E2E 1건.
- **살아남은 변경 1건** — 실험 2. 테스트의 빈틈이 아니라 1단계에서 지키기로 하지 않은 코드였다. 대응은 테스트가 아니라 주석 한 줄이다.
- **잡힌 세 건에서 갈린 것은 이름이었다** — 실험 1은 케이스별 이름 덕에, 실험 3은 call log 덕에 메시지만으로 원인이 잡혔다. 실험 4는 메시지가 아니라 이름이 원인을 좁혀줬다. 세 번 모두 "조건과 결과를 이름에 담는다"는 규칙이 실패를 읽는 시간을 줄였다.
- **망가뜨린 코드는 남기지 않았다** — 네 변경을 모두 되돌렸고, 남은 것은 실험 2에서 얻은 주석 한 줄뿐이다. 되돌린 뒤 vitest 205개와 Playwright 11개가 모두 통과한다.
