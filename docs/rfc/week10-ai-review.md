`.github/ai-review-prompt.md`. 일반론을 빼고 **이 저장소가 10주 동안 실제로 합의한 규칙만** 담았고,

지금은 로컬 CLI(Claude Code)로 돌린다. **CI 통합은 하지 않았다** — 뒤의 "어디에 둘 것인가" 참고.

## 잘 잡은 것 — 테스트 전용 코드가 번들 예산 안에 들어와 있다

**지적**: `/gallery`는 시각 회귀 테스트 전용 라우트인데 production 빌드에 정적 라우트로 들어간다.
같은 성격의 `/dialog-demo`, `/select-demo`, `/performance-lab/inp`도 마찬가지다.
그런데 이번 주 3단계에서 건 번들 예산은 `.next/static/chunks`의 **모든** 클라이언트 JS를 센다.
사용자가 쓸 일 없는 코드가 예산 안에 들어가 있다.

**근거(확인)**: 빌드 산출물에서 각 라우트의 표식 문자열로 청크를 찾아 gzip으로 쟀다.

| 라우트 | 청크 | gzip |
| --- | --- | --- |
| `/gallery` | 1개 | 0.7KB |
| `/performance-lab/inp` | 1개 | 6.7KB |
| 합계(식별된 것만) | 2개 | **7.4KB** |

전체 237.5KB 중 7.4KB다. 3%지만 **예산 여유 23.5KB의 3분의 1**이다.
`dialog-demo`·`select-demo`는 표식으로 안 잡혀서 실제 값은 이보다 크다.

**왜 중요한가**: 예산의 정의를 "우리가 브라우저로 내보내는 JS"라고 써 놓고, 정작 그 안에
사용자에게 내보낼 이유가 없는 코드가 있다. 나중에 데모 페이지 하나가 커져서 예산이 터지면
**진짜 회귀가 아닌 것 때문에 빨간불이 난다.** 반대로 데모를 지워서 생긴 여유가 실제 회귀를 가릴 수도 있다.

**제안**: 둘 중 하나다. (1) 데모·갤러리 라우트를 production 빌드에서 빼거나,
(2) 예산 측정에서 그 청크를 제외하고 제외했다는 사실을 리포트에 찍는다.
지금은 (2)가 싸고, 제외 목록이 길어지면 (1)을 본다. **이번 주에는 적용하지 않고 남긴다** —
예산 기준선을 이미 237.5KB로 잡아 두었으므로, 빼면 기준선부터 다시 재야 한다.

## 헛소리 — 경계 위반이라고 두 번 잘못 짚었다

**지적(틀림)**: `src/app/gallery/stories.ts`가 `@/_pages/products/ui/ProductsSkeleton.story`를
import 하는 것을 보고 두 가지를 의심했다.

1. C1 역방향 의존 — "app이 _pages를 import한다"
2. C3 Public API 우회 — "슬라이스 내부 파일(`ui/...`)을 직접 import한다"

**둘 다 틀렸다.**

1. 레이어 순서가 `shared → entities → features → _pages → app`이고 `app`이 최상위다.
   상위가 하위를 쓰는 것은 정방향이다. "app이 page를 가져온다"는 **모양만 보고 방향을 뒤집어 읽었다.**
2. `_pages` 슬라이스에는 `index.ts`가 아예 없다. `find src/_pages -name index.ts` 결과가 0건이고,
   `index.ts`가 있는 건 `entities/*` 다섯 곳뿐이다. 공개 API가 없으니 우회할 대상도 없다.
   기존 `app/(commerce)/products/page.tsx`도 같은 방식으로 `_pages/products/ui/ProductsPage`를 직접 가져온다.

**왜 이런 오탐이 났나**: 규칙 이름만 보고 패턴 매칭했다. C1은 순서표를 다시 읽지 않았고,
C3은 **그 규칙의 전제(index.ts가 있는가)를 확인하지 않은 채** 적용했다.
둘 다 파일 하나만 더 열어 봤으면 안 났을 지적이다.

## 프롬프트를 어떻게 고쳤나

이 오탐 때문에 세 군데를 고쳤다.

| 고친 곳 | 전 | 후 |
| --- | --- | --- |
| 리뷰 방법 | 확신도만 요구 | **규칙을 적용하기 전에 그 규칙의 전제가 성립하는지 코드에서 먼저 확인**하고, 확인 못 했으면 쓰지 말 것 |
| 출력 형식 | `확신도: 확인 \| 추론` | `확인`으로 쓰려면 **무엇을 어떻게 확인했는지 한 줄** 같이 적을 것. 못 적으면 `추론` |
| C1 | 화살표 한 줄 | 최상위·최하위를 명시하고 **허용되는 정방향 예시**(`app → _pages`)를 규칙 안에 박음 |
| C3 | "내부 파일 직접 import 금지" | **"`index.ts`를 둔 슬라이스에 한해"**로 좁히고, 현재 그런 슬라이스가 `entities/*`뿐임을 명시 |

핵심은 "더 엄격하게"가 아니라 **"규칙의 전제를 먼저 확인하라"**다. 오탐 둘 다 규칙 자체는 맞는데
그 규칙이 적용되는 상황인지를 안 본 것이었다.

## 어디에 둘 것인가 — advisory, CI 미통합

AI 리뷰는 비결정적이다. 같은 diff를 두 번 돌리면 다른 것을 짚을 수 있고,
위처럼 **자신 있게 틀린다**. required 게이트로 두면 틀린 지적 하나가 머지를 막는다.

9주차에서 "비싸고 변동성 큰 검증을 어디에 둘지"를 정할 때 쓴 논리가 그대로 적용된다.
결정적으로 판별되는 것만 게이트로 내리고, 비결정적인 것은 참고로 둔다.
그래서 **advisory**로 두고, CI에는 붙이지 않았다. 붙이지 않은 이유는 두 가지다.

- 이 저장소는 1인 포크다. PR마다 자동으로 도는 리뷰는 소음과 비용만 늘고 읽는 사람이 나 하나다.
- 붙인다면 트리거를 `@ai` 코멘트나 label로 제한하고 `max_turns`·`timeout-minutes`·`concurrency`를
  같이 걸어야 한다. 그 안전장치까지가 한 묶음인데, 지금은 그 묶음을 유지할 이유가 약하다.

대신 **반복해서 나오는 지적은 5단계에서 결정적 룰로 내린다.** 그게 AI 리뷰를 줄이는 방법이다.
