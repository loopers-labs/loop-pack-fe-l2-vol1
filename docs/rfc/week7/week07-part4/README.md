## 2부. LCP 구간 비교 — 숫자보다 "무엇이 LCP였나"가 핵심

## LCP element가 바뀌었다

|                      | Before                                                          | After                                  |
| -------------------- | --------------------------------------------------------------- | -------------------------------------- |
| 홈 LCP element       | `h2#week07-hero-title` — **"매일 새롭게 발견하는 취향" 텍스트** | `section.hero > img` — **hero 이미지** |
| 상품목록 LCP element | `h2#week07-hero-title` — **"상품 목록" 텍스트**                 | hero 이미지                            |

**Before에서는 hero가 한 번도 LCP가 되지 못했다.** Lighthouse의 `network-requests`가 그 이유를 보여준다.

|                            | Before 홈                       | Before 상품목록     | After                     |
| -------------------------- | ------------------------------- | ------------------- | ------------------------- |
| hero 요청 완료(`finished`) | **`0`(미완료)**                 | **`false`(미완료)** | ✅ 완료                   |
| 측정 창 안에서 받은 양     | **682,096 bytes (전체의 9.0%)** | 약 7,274KB          | 홈 163.7KB / 목록 132.4KB |
| 전체 파일 크기             | 7,545,239 bytes                 | 7,545,239 bytes     | —                         |

**측정이 끝난 시점의 화면 캡처도 같은 이야기를 한다.** 각 리포트의 `final-screenshot`을 [`./captures/`](./captures/)에 상태별로 남겼는데, 전송량과 화면이 정확히 대응한다.

|                                                       | 측정 창 안에서 받은 양           | 캡처에 찍힌 화면                             |
| ----------------------------------------------------- | -------------------------------- | -------------------------------------------- |
| [Before 홈](captures/before/home/run-1.jpg)           | 682,096 / 7,545,239 B (**9.0%**) | **hero 위쪽 띠만 그려지고 나머지는 빈 배경** |
| [Before 상품목록](captures/before/products/run-1.jpg) | 약 7,274 / 7,545 KB (**96%**)    | 거의 다 그려짐                               |
| [최종 After 홈](captures/final/home/run-1.jpg)        | 167,625 B (완료)                 | hero 전체                                    |

홈과 상품목록이 같은 Before 코드인데 화면이 다른 이유가 여기서 드러난다 — **전송이 어디까지 진행됐느냐의 차이**다. 홈은 9%에서 끊겨 hero가 LCP 후보가 될 수 없었고, 그래서 작은 `h2` 텍스트가 LCP로 잡혔다.

`lcp-breakdown-insight`도 같은 이야기를 한다.

| 구간                       | Before 홈     | After 상품목록 |
| -------------------------- | ------------- | -------------- |
| Time to first byte         | 4ms           | 9ms            |
| Resource load delay        | —             | 581ms          |
| **Resource load duration** | **항목 없음** | 2,422ms        |
| Element render delay       | 3,733ms       | 27ms           |

**Before에는 `Resource load duration` 항목 자체가 없다** — LCP가 이미지가 아니라 텍스트였기 때문에 이미지 로딩 구간이 잡히지 않는다.

### 그래서 상품목록의 "LCP +1,176ms"는 악화가 아니다

Before의 LCP 1,444ms는 **작은 텍스트가 LCP였을 때의 값**이고, After의 2,620ms는 **거대한 hero 이미지가 완전히 로드된 시점**이다. 측정 대상이 다르므로 이 둘을 뺄셈해 "느려졌다"고 말할 수 없다.

같은 페이지에서 **Speed Index가 12,502ms → 2,310ms로 81.5% 줄었다**는 것이 실제 사용자 체감을 보여준다. Speed Index는 화면이 시각적으로 채워지는 과정 전체를 적분한 값이라, 7.5MB 이미지가 progressive JPEG로 12초 넘게 서서히 채워지던 Before의 상태를 정확히 반영한다.

## 5부. FCP가 안 움직여서 추가로 한 것

4부에서 **FCP만 개선되지 않은 채로 남았다**(1,395.1 → 1,387.5ms, −7.6ms). 측정 범위가 1.5–3.0ms인데 −7.6ms면 통계적으로는 유의미하지만 체감상 없는 것과 같다. Part 1–3이 전부 **이미지·리소스 우선순위** 층의 작업이었고 문서가 처음 도착하는 경로는 한 번도 건드리지 않았으니 당연한 결과다. 그래서 FCP만 따로 분해했다.

### 관찰 — FCP는 왕복 2회다

After 홈 run-1의 `network-requests`에서 FCP(1,388ms) 이전에 끝난 요청만 뽑으면 임계 경로가 그대로 드러난다.

| 리소스      | 요청 시작 | 종료      | 전송 크기 | 성격                |
| ----------- | --------- | --------- | --------- | ------------------- |
| 문서 `/`    | 0ms       | **609ms** | 8,880 B   | —                   |
| CSS ×2      | 604ms     | 1,227ms   | 3,747 B   | **render-blocking** |
| (첫 페인트) |           | 1,388ms   |           |                     |

`render-blocking-insight` 감사가 **"Est savings of 650 ms"** 로 같은 진단을 내린다.

### 원인 가설 — 3.7KB CSS가 왜 620ms를 쓰나

| 감사                              | 값          |
| --------------------------------- | ----------- |
| `network-rtt`                     | 0.27ms      |
| `server-response-time`(루트 문서) | 9ms         |
| `network-server-latency`(오리진)  | **573.9ms** |

RTT가 0.27ms인 로컬호스트이고 문서 자체의 서버 응답도 9ms인데, Lantern은 이 오리진의 서버 응답 시간을 **574ms로 추정하고 모든 요청에 동일하게 부과**한다. 552바이트짜리 RSC 요청도 577ms가 걸린다. 즉 `FCP ≈ 574(문서) + 574(CSS) + 240(렌더)`이고, **같은 574ms가 두 번 직렬로 청구**된 구조다.

574ms의 출처를 **이때는 "동시 요청 경합"으로 봤다** — 홈 한 번 로드에 서버로 가는 요청이 41개(이미지 변환 12건, RSC 프리페치 13건)이니 싱글스레드 Node가 밀리는 동안 정적 청크 응답까지 줄을 선다는 것이었다(script 응답 중앙값 729ms). **이 가설은 뒤에서 반증된다.**

### 반증 방법

왕복 횟수와 서버 동시 요청 수를 각각 줄였을 때 FCP가 따라 내려가지 않으면 이 가설이 틀린 것이다.

### 변경 1 — CSS를 문서에 인라인

`next.config.ts`에 `experimental.inlineCss: true`. CSS 총량이 3.7KB뿐이라 인라인해도 문서가 크게 무거워지지 않으면서 왕복 하나가 통째로 사라진다.

|                           | 적용 전               | 적용 후  |
| ------------------------- | --------------------- | -------- |
| `<link rel="stylesheet">` | 2개 (render-blocking) | **0개**  |
| 인라인 `<style>` CSS      | —                     | 7,891 B  |
| 문서 전송 크기(gzip)      | 8,880 B               | 16,092 B |

문서가 7.2KB 늘지만 10,240 Kbps에서 전송 시간으로는 약 5.6ms다. 이 라운드에서 관찰된 절감폭(약 620ms 왕복)은 위에서 짚은 574ms 오리진 추정치 이중 청구의 영향을 크게 받은 값이라, 실제 배포 환경에서 그대로 재현된다고 보기 어렵다 — 이 수치 자체를 인라인의 근거로 삼지 않는다. 대신 **CSS 총량이 3.7KB로 TCP 초기 혼잡 윈도우(약 14KB) 안에 들어가는 크기라, 인라인해도 문서가 그 윈도우를 벗어나지 않는다**는 걸 근거로 인라인을 택했다. 이 근거는 로컬 서버 특성과 무관하게 배포 환경에서도 그대로 성립한다.

### 변경 2 — 카테고리 링크의 viewport 자동 프리페치 해제

홈의 카테고리 `<Link>` 5개가 Next의 viewport 자동 프리페치로 RSC 요청 10건을 쏘고 있었다. 그런데 **같은 목적의 프리페치가 이미 하나 더 있었다** — `HomeView`의 `onMouseEnter`에서 React Query로 상품 목록 데이터를 미리 받고 있었다(Part 1에서 추가). 첫 로드에 10건을 쏘는 쪽은 중복이고, 서버 응답 추정치를 끌어올리는 원인이기도 하다.

다만 `prefetch={false}`는 타입 문서상 **viewport와 hover 프리페치를 둘 다 끈다.** 그대로 끄면 클릭 체감이 나빠질 수 있어서, 기존 hover 핸들러에 `router.prefetch()`를 같이 넣어 **"첫 로드에는 안 쏘고, hover에서 라우트+데이터를 함께 예열"** 로 옮겼다. 프리페치를 없앤 게 아니라 **시점을 옮긴 것**이라는 게 이 선택의 핵심이다.

Header의 `/`·`/products` 링크는 주 내비게이션이라 그대로 뒀다(남은 3건).

|                      | 적용 전    | 적용 후                      |
| -------------------- | ---------- | ---------------------------- |
| 첫 로드 RSC 프리페치 | 13건       | **3건**(Header만)            |
| 첫 로드 총 요청 수   | 41건       | **32건**                     |
| hover 시 발생 요청   | 데이터 1건 | 데이터 1건 + 라우트 프리페치 |

> 검증은 Playwright로 홈을 열어 `_rsc=` 요청을 직접 센 것이다. hover 후 `/api/products?category=digital…`과 `/products?category=digital` 프리페치가 모두 발생하는 것까지 확인했다.

측정 프로토콜은 4부와 동일하다(시크릿 창, DevTools, `--preset=desktop`, 이미지 변환 캐시 예열, 포트 3000 고정). 5회 raw 값은 1부 "최종 After" 표에 있다.

### ❌ 반증된 부분 — 변경 2는 FCP에 기여하지 않았다

"반증 방법"으로 적어둔 것은 **"왕복 횟수와 서버 동시 요청 수를 각각 줄였을 때 FCP가 따라 내려가지 않으면 가설이 틀린 것"**이었다. 결과는 갈렸다.

| 가설                                                | 조치                             | 결과                                                  | 판정        |
| --------------------------------------------------- | -------------------------------- | ----------------------------------------------------- | ----------- |
| 왕복이 2회라서 FCP가 느리다                         | CSS 인라인                       | 왕복 1회 → FCP −608ms                                 | ✅ **지지** |
| 동시 요청 수가 서버 응답 추정치(574ms)를 끌어올린다 | 프리페치 13 → 3건 (총 41 → 32건) | `network-server-latency` **574 → 581ms**, 사실상 불변 | ❌ **반증** |

즉 **FCP 개선은 전부 CSS 인라인에서 나왔다.** 변경 2는 그래도 유지한다 — hover 프리페치와 목적이 겹치는 중복 요청을 없앤 것 자체가 옳고, 회귀도 없기 때문이다. 이 판단은 코드 주석에도 그대로 적어 뒀다.

### 574ms의 실제 출처 — 과제가 심어둔 mock API 지연

가설이 반증된 뒤 오리진의 **관측 TTFB를 URL별로 직접 쟀다.** Lighthouse의 시뮬레이션 값이 아니라 `curl`로 잰 실제 응답 시간이다.

| URL                 | 실제 TTFB   |
| ------------------- | ----------- |
| `/`                 | 2.1ms       |
| `/products`         | 3.5ms       |
| 정적 JS 청크        | 1.0ms       |
| **`/api/home`**     | **502.2ms** |
| **`/api/products`** | **501.4ms** |

출처는 `src/app/api/_data/commerce.ts`의 `waitForMockApi(requestedDelayMs = 500)`다. 두 Route Handler가 모두 이걸 호출한다(`scenario === 'slow'`면 1,500ms). **과제가 "느린 API"를 재현하려고 의도적으로 심어둔 지연**이고, 우리 코드가 만든 병목이 아니다.

**이 500ms 자체는 Part 2에서 이미 짚었다** — 3부 "남은 Lighthouse 항목" 표에서 `Resource load delay`의 원인으로 지목하고 "과제가 준 fixture이므로 없애는 것은 측정 조작에 가깝다"고 적었다. 이번에 새로 안 것은 그 지연이 **거기서 끝나지 않는다**는 점이다. Lighthouse는 오리진 단위로 서버 응답 시간을 추정하므로, `/api/*`의 500ms가 **문서·CSS를 포함한 모든 요청에 뿌려진다.** 그래서 실제로는 2.1ms에 응답하는 8.8KB 문서가 609ms로 계산됐다.

Part 2에서는 이걸 "API 응답을 기다리는 한 페이지의 문제"로 봤는데, 실제로는 **그 페이지의 FCP 계산 전체를 좌우하는 값**이었다.

동시 요청 경합이 아니라는 것도 같은 방법으로 확인했다 — 이미지 변환 8건을 동시에 걸어둔 상태에서 문서 TTFB는 **2.1ms → 5.3ms**로 3ms 남짓 늘었을 뿐이다. 574ms를 만들 수 있는 크기가 아니다.

**정리하면 이렇다.**

|                   | 처음 본 것        | 실제                             |
| ----------------- | ----------------- | -------------------------------- |
| 574ms의 출처      | 동시 요청 경합    | **mock API의 의도적 500ms 지연** |
| 프리페치를 줄이면 | 추정치가 내려간다 | 내려가지 않는다(574 → 581ms)     |
| 실제 서버 응답    | 느리다            | 문서 2.1ms · 정적 자산 1.0ms     |

그래서 **이 FCP 숫자에는 남은 개선 여지가 사실상 없다.** 더 줄이려면 mock API의 지연을 건드려야 하는데, 그건 과제가 재현하려는 조건 자체를 없애는 것이라 하지 않는다. 실제 배포 환경이라면 API 응답 시간이 오리진 추정치를 좌우하므로, **"API를 빠르게 하는 것이 문서와 CSS의 체감 속도까지 끌어올린다"** 는 것이 여기서 얻은 진짜 교훈이다.

### 트레이스 두 건은 로드 비교에 쓰지 않았다

- **홈 트레이스**(Slow 4G, DPR 1): FCP 607ms, LCP 915ms인데 **LCP 요소가 hero가 아니라 `h2` 텍스트(42,307px²)**다. 첫 입력이 36,454ms라 입력이 LCP를 끊은 것도 아니다. 4부에 기록한 `929d03c8` 트레이스는 hero가 918ms에 LCP였는데, Slow 4G에서 167KB가 918ms에 끝날 수 없으므로 **그쪽이 이미지 캐시가 살아 있는 상태**였다고 본다. 두 트레이스는 캐시 조건이 달라 직접 비교하지 않는다.
- **상품목록 트레이스**: `navigationStart`가 **0건** — 로드가 아니라 검색·카테고리 조작을 녹화한 것이다. 로드 비교에는 쓸 수 없고, 대신 아래 CLS 관찰의 근거가 됐다.

### 갱신 실패를 제대로 재현했더니 — 목록은 유지되는데 실패를 9초 뒤에 알렸다

브라우저 쪽 가로채기로는 재현이 안 되므로, **API 라우트에 임시 계측을 넣어 서버에서 실패를 만들었다.** 환경변수로만 켜지게 해서 테스트·빌드에는 영향이 없도록 했다.

```ts
// TEMP-PART4-UPDATE-FAILURE (관찰 후 제거)
if (process.env.TEMP_FAIL_SORT && params.get('sort') === process.env.TEMP_FAIL_SORT) {
  return NextResponse.json({ message: '상품 목록을 불러오지 못했습니다.' }, { status: 500 });
}
```

첫 로드는 성공시키고 정렬만 실패시켜, **"기존 목록이 있는 상태의 갱신 실패"** 를 정확히 만들었다.

- **관찰**: 목록 12개는 그대로 유지되고 pending 오버레이도 519ms에 떴지만, "갱신에 실패했다"는 인라인 에러와 재시도 버튼은 **9,123ms 뒤에야** 나타났다.
- **원인 가설**: `new QueryClient()`에 `retry` 설정이 없어 기본 3회 재시도가 걸리고, 지수 백오프(1s·2s·4s)에 mock API의 500ms가 매 시도마다 더해진다.
- **반증 방법**: 재시도 횟수를 줄였을 때 노출 시점이 그만큼 앞당겨지지 않으면 원인이 아니다.
- **가장 작은 변경**: `productsQueryOptions`의 `retry`를 1회로 묶는다.

관측된 응답 타임라인이 가설과 정확히 맞았다.

|                                    | 수정 전                               | 수정 후             |
| ---------------------------------- | ------------------------------------- | ------------------- |
| `/api/products` 500 응답 시각      | +517 · +2,026 · +4,535 · **+9,043ms** | +514 · **+2,021ms** |
| pending 오버레이 등장              | +519ms                                | +517ms              |
| **인라인 에러 + 재시도 버튼 등장** | **+9,123ms**                          | **+2,038ms**        |
| 기존 목록 유지                     | 12개                                  | 12개                |

**구현은 처음부터 맞았고 노출 시점만 늦었다.** 필터 변경은 사용자가 방금 일으킨 상호작용이고, 이전 목록이 화면에 남아 있으며, 명시적인 "다시 시도" 버튼도 있으므로 자동 백오프를 길게 끌 이유가 없다고 **직접 판단해** `retry`를 1회로 묶었다. 상수에 이름과 근거를 붙였고(`PRODUCT_LIST_RETRY_COUNT`), 테스트는 정확한 값이 아니라 **"상한이 있다"는 성질**을 부등호로 고정했다 — 지켜야 할 것은 1이라는 숫자가 아니라 실패가 빨리 드러난다는 성질이기 때문이다.

임시 계측은 관찰 후 제거했고, **소스와 `.next` 빌드 산출물 양쪽에서 `TEMP_FAIL_SORT`·`TEMP-PART4-UPDATE-FAILURE` 문자열이 0건**임을 확인했다. `git diff`상 `route.ts`는 완전히 원상복구다.

> 이 발견의 경위 자체가 기록할 만하다. 처음에는 "검증 스크립트가 실패를 재현 못 한다"는 **도구 문제로 보였고**, 한 번은 관찰 창이 8초라 "인라인 에러가 아예 안 뜬다"고 **잘못 결론냈다가 정정**했다. 두 번 다 더 오래·더 정확히 재현해서야 실제 문제(9초 지연)에 닿았다.

### 관찰만 남기는 것 — 조작 중 CLS 0.0147

상품목록 조작 트레이스에서 `LayoutShift` 3건이 나왔고 **셋 다 대상이 `NAV.week05-pagination` 하나**다.

| 시각         | score      | `had_recent_input` | 공식 CLS 채점 |
| ------------ | ---------- | ------------------ | ------------- |
| 5,677ms      | 0.0002     | true               | 제외          |
| 7,921ms      | 0.0139     | true               | 제외          |
| **19,383ms** | **0.0147** | **false**          | **채점됨**    |

19,383ms 시프트는 `/api/products?category=goods…` 응답이 19,380ms에 도착한 직후이고, `old_rect [0,0,0,0] → new_rect y=704px`다. **결과 개수가 바뀌면서 목록 높이가 달라져 그 아래 Pagination이 이동한 것**으로 보인다.

- **관찰**: 검색어·카테고리를 바꿔 결과 개수가 달라질 때 Pagination이 이동하고, 그중 입력 제외 창(500ms)을 벗어난 1건이 CLS 0.0147로 채점됐다.
- **원인 가설**: 목록 높이가 결과 개수에 따라 달라지는데 그 아래 Pagination에는 높이 보장이 없다.
- **반증 방법**: 결과 개수가 같은 두 조건끼리 전환했을 때도 시프트가 나오면 원인은 개수가 아니다.
- **가장 작은 변경**: 목록 영역에 최소 높이를 주거나, Pagination을 목록 높이와 무관한 위치에 고정한다.

**이번 Part에서는 관찰만 남기고 고치지 않는다.** Part 2의 "검색 CLS 0건" 결론은 결과 개수가 크게 바뀌지 않는 시나리오에서 얻은 것이라 **틀렸다기보다 범위가 좁았다**. cold load CLS는 최종 After 5회 전부 **0.000**이라 Lighthouse 점수에는 나타나지 않는다.

### 고친 것 — `/products` 초기 HTML의 `h2` id 중복

3단계 증거로 쓰는 "JavaScript 없이 받은 초기 HTML"을 다시 확인하다 발견했다.

|                        | `h2` 개수 | `#week07-hero-title` |
| ---------------------- | --------- | -------------------- |
| JS ON(하이드레이션 후) | 1         | 1                    |
| **JS OFF(초기 HTML)**  | **2**     | **2 ← id 중복**      |
| 홈(JS OFF)             | 1         | 1                    |

- **관찰**: `/products`의 초기 HTML에 같은 `id`를 가진 `h2`가 두 개 실린다. JS를 켜면 하나가 제거돼 1개가 된다.
- **원인 가설**: `loading.tsx`가 기하를 맞추려고 실제 `PageHeading`을 그대로 재사용하는데, 그 컴포넌트가 `id="week07-hero-title"`을 하드코딩하고 있어 Suspense fallback과 본 콘텐츠가 초기 HTML에 함께 실린다. `loading.tsx`가 없는 홈에서는 재현되지 않는 것이 이 가설과 맞는다.
- **반증 방법**: `loading.tsx`에서 `PageHeading`을 빼고도 중복이 남으면 원인은 fallback이 아니다.
- **가장 작은 변경**: `PageHeading`이 제목 id를 prop으로 받게 하고 `loading.tsx`에서만 다른 값을 넘긴다.

체크 항목이 묻는 것(제목·설명·링크·구조가 JS 없이 보이는가)은 원래도 충족했지만, **중복 `id`는 HTML 유효성과 `aria-labelledby` 지시 대상이 모호해지는 문제**다. 원인이 확정됐고 변경이 작아 이번에 고쳤다.

`PageHeading`이 `titleId`를 prop으로 받게 하고(기본값은 기존 id 그대로), `loading.tsx`에서만 `week07-hero-title-loading`을 넘긴다. 공통 컴포넌트가 "한 문서에 둘 이상 실릴 수 있다"는 사정을 스스로 알 필요는 없으므로, 그 사정을 아는 호출부가 id를 정하게 했다.

|                                 | 수정 전                | 수정 후                                           |
| ------------------------------- | ---------------------- | ------------------------------------------------- |
| `/products` 초기 HTML의 `h2` id | `week07-hero-title` ×2 | `week07-hero-title-loading` + `week07-hero-title` |
| 같은 id 중복                    | **2건**                | **0건**                                           |
| `aria-labelledby`               | 둘 다 같은 id를 가리킴 | 각자 자기 제목을 가리킴                           |
| 홈(`loading.tsx` 없음)          | 1건                    | 1건(변화 없음)                                    |
| JS ON 하이드레이션 후           | `h2` 1개               | `h2` 1개(변화 없음)                               |

`PageHeading.test.tsx`에 두 케이스를 넣어 고정했다 — 기본값일 때 id와 `aria-labelledby`가 같은 값을 가리키는 것, 그리고 **한 문서에 둘을 함께 그려도 id가 겹치지 않는 것**(실제 `/products`의 상황을 그대로 재현).

### 이번 측정에서 지킨 것 — 0단계의 반성 반영

체크리스트에 ⚠️로 남겼던 "이미지 변환 캐시 상태 미통제" 문제를 이번에는 통제했다. 측정 전 캐시를 예열해 **5회 전부 hero 전송량이 동일**하게 나왔다(홈 163.7KB, 목록 132.4KB, 범위 0). Before는 raw `<img>`라 변환 캐시가 존재하지 않아 애초에 이 변수가 없다.
