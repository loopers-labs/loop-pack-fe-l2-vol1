# 5단계 — AI 지적을 결정적 룰로 승격

4단계에서 반복해서 나온 지적 하나를 사람·AI 판단에서 떼어내 CI 게이트로 내린 기록이다.

| 항목      | 내용                                                   |
| --------- | ------------------------------------------------------ |
| 승격한 것 | 추적되는 RFC가 무시된 로컬 문서 디렉터리를 참조하는 것 |
| 구현      | `scripts/validate-rfc-links.mjs`                       |
| 실행      | `pnpm validate:docs`                                   |
| 배치      | `quality` job의 step. 새 check 이름을 만들지 않았다    |
| 실행 시간 | CI에서 1초 미만                                        |

---

## 1. 왜 이것을 골랐나

승격 대상은 **반복해서 지적됐고, 참/거짓을 결정적으로 가를 수 있는 것**이어야 한다. 이 항목이 두 조건을 모두 만족한다.

| 조건        | 확인                                                                             |
| ----------- | -------------------------------------------------------------------------------- |
| 반복 지적   | 4단계 AI 리뷰의 프롬프트 v1~v4 네 번 모두 같은 지적이 나왔다                     |
| 반복 지적   | 그 전부터 사람 리뷰에서 같은 항목이 되풀이됐다                                   |
| 결정적 판별 | 파일 경로와 링크 목적지만 보면 되고, 맥락 해석이 필요 없다                       |
| 실패 영향   | 문서를 받은 사람이 링크를 따라가면 존재하지 않는 파일로 이어져 근거를 볼 수 없다 |

4단계에서 나온 다른 지적들은 승격하지 않았다. `no-console`의 적용 범위, timeout 근거의 위치, required 배치 판단은 모두 "어디에 적용되는가"를 사람이 정해야 해서, 파일 경로만으로 참/거짓이 갈리지 않는다.

---

## 2. 무엇을 금지하는지 — 문자열이 아니라 참조

처음에는 금지 경로 **문자열이 나오는 것**을 막으려 했다. 그렇게 두면 규칙 자체를 설명하는 문서가 자기 규칙에 걸린다. 이 문서와 2단계 문서가 그 경로를 언급해야 하기 때문이다.

반대로 코드블록만 예외로 두면, 실제 링크를 백틱으로 감싸 검사를 피할 수 있다는 우려가 생긴다. 다만 백틱으로 감싼 문자열은 링크로 렌더링되지 않으므로, 읽는 사람이 따라갈 수 있는 참조가 만들어지지 않는다.

그래서 판정 기준을 **문서 경로로 해석되는 참조**로 좁혔다.

> 추적되는 `docs/rfc/**/*.md`에서 `docs/` 아래 무시된 로컬 문서 디렉터리를 Markdown·HTML 링크 대상으로 참조하면 CI를 실패시킨다. 코드로 표시된 문자열은 링크가 되지 않으므로 통과시킨다.

이 규칙이 막으려는 것은 경로 이름을 적는 일이 아니라, 받는 사람이 열 수 없는 파일을 문서가 가리키는 일이다.

### 판정 표

| 형태                                                  | 판정 | 이유                             |
| ----------------------------------------------------- | ---- | -------------------------------- |
| Markdown 링크 `[설명](경로)` · 이미지 `![설명](경로)` | 실패 | 렌더링하면 따라갈 수 있는 링크다 |
| Markdown 참조 정의 `[라벨]: 경로`                     | 실패 | 같은 이유                        |
| Markdown 자동 링크 `<경로>`                           | 실패 | 같은 이유                        |
| HTML `href="경로"` · `src="경로"`                     | 실패 | 같은 이유                        |
| 코드가 아닌 본문에 적힌 경로                          | 실패 | 파일 참조로 읽힌다               |
| 코드블록 안의 예시                                    | 통과 | 링크가 되지 않는다               |
| 인라인 코드로 경로를 설명하는 경우                    | 통과 | 같은 이유                        |
| `docs/rfc` 밖 문서 (예: `docs/ai-review-prompt.md`)   | 통과 | 검사 범위 밖                     |
| 추적되지 않는 파일                                    | 통과 | 다른 사람에게 전달되지 않는다    |

이 문서도 규칙을 지킨다. 금지 경로를 실제 링크로 쓰지 않고 설명용 코드로만 표시했다.

## 3. 구현

`scripts/validate-rfc-links.mjs`가 세 단계로 판정한다.

1. `git ls-files`로 추적되는 `docs/rfc` 아래 Markdown 파일 목록을 만든다.
2. 코드블록(` ``` `, `~~~`)과 인라인 코드 구간을 같은 길이의 공백으로 바꾼다. 길이를 맞추는 이유는 오류 메시지의 줄 번호가 원문과 어긋나지 않게 하기 위해서다.
3. 남은 본문에서 링크 목적지 네 종류와 맨 경로를 찾아 금지 접두사와 대조한다.

실패 메시지에 파일명, 줄 번호, 참조 종류, 링크 대상, 고치는 방법을 함께 출력한다. 로그를 열지 않고 요약만 봐도 어디를 고쳐야 하는지 알 수 있게 하기 위해서다.

```
docs/rfc 문서가 무시된 로컬 문서 디렉터리를 참조한다. 2건.

  ✗ docs/rfc/_link-check-fixture.md:5  Markdown 링크  →  (금지 경로)/raw-notes.md
  ✗ docs/rfc/_link-check-fixture.md:5  HTML 링크      →  (금지 경로)/table.html

이 경로는 .gitignore 대상이라 저장소를 받은 사람에게는 존재하지 않는다.
고치는 방법:
  - 참조가 필요 없으면 지운다.
  - 내용이 필요하면 해당 문서로 옮겨 적는다.
  - 규칙을 설명하려고 경로를 적는 경우라면 코드블록이나 인라인 코드로 감싼다.
```

## 4. 자가 검증

### 로컬 — 위반과 정상을 같이 넣었다

임시 문서를 만들어 한 번에 돌렸다. 확인 뒤 모두 지웠다.

| 케이스                                 | 기대 | 결과                               |
| -------------------------------------- | ---- | ---------------------------------- |
| 실제 Markdown 링크                     | 실패 | 실패 — `Markdown 링크`로 분류      |
| 실제 HTML 링크                         | 실패 | 실패 — `HTML 링크`로 분류          |
| 이미지 링크                            | 실패 | 실패                               |
| 참조 정의 `[라벨]: 경로`               | 실패 | 실패 — `Markdown 참조 정의`로 분류 |
| 본문에 적힌 맨 경로                    | 실패 | 실패 — `본문 경로 참조`로 분류     |
| 코드블록·인라인 코드 안의 링크와 설명  | 통과 | 통과                               |
| `docs/rfc` 밖 문서의 실제 링크         | 통과 | 통과                               |
| `docs/rfc` 안이지만 추적되지 않는 파일 | 통과 | 검사 대상에서 빠짐                 |

**정상 케이스가 통과하는 것까지 확인했다.** 위반만 잡히는지 보면 오탐 여부를 알 수 없기 때문이다.

### CI — [PR #14](https://github.com/kate-son/loop-pack-fe-l2-vol1/pull/14)

게이트를 `feat/week-10`에 넣기 전에 실험 브랜치에서 먼저 확인했다.

| 회차 | 커밋       | run                                                                                      | 결과        |
| ---- | ---------- | ---------------------------------------------------------------------------------------- | ----------- |
| 위반 | `541fc16d` | [34515725879](https://github.com/kate-son/loop-pack-fe-l2-vol1/actions/runs/34515725879) | **failure** |
| 복귀 | `cdcf4d73` | [34515873701](https://github.com/kate-son/loop-pack-fe-l2-vol1/actions/runs/34515873701) | **success** |

위반 회차의 step 결과다. 링크 검사가 가장 앞에 있어 뒤 검증은 실행되지 않았다.

```
failure  Validate RFC links
skipped  Validate env (ci)
skipped  Test / Lint / Typecheck / Build
skipped  Bundle budget
```

복귀 회차에서는 일곱 step이 모두 통과했고, 링크 검사 출력은 `RFC 링크 검사: 20개 문서, 위반 없음`이었다. step 소요는 1초 미만이다.

실험 PR은 머지하지 않고 닫았으며 브랜치도 지웠다.

## 5. 배치

`quality` job의 step으로 넣었다. 별도 job으로 빼면 required 후보 이름이 하나 늘어나는데, 이 검사는 실행 조건이 갈리지 않고 `quality`와 같은 조건에서 항상 돌기 때문에 나눌 이유가 없다.

**`quality`를 required로 지정하면 이 검사 실패가 머지를 막는다. 다만 지금 저장소에는 branch protection이 없어서 실제로 막히는 상태는 아니다.** 지정했을 때 머지가 막히는 동작은 3단계에서 임시 보호 브랜치로 확인했고, 영구 배치는 그때 「남은 것」으로 남겨 뒀다.

step 순서는 가장 앞이다. 정적 텍스트 검사라 실행 시간이 1초 미만이고 설치 외에 다른 검증에 기대지 않으므로, 앞에 두면 실패했을 때 나머지 검증 시간을 쓰지 않는다. 다만 링크 검사에서 막히면 코드 결함은 이 회차에서 드러나지 않으므로, 고친 뒤 한 번 더 돌려야 전체 결과를 볼 수 있다.

## 6. 룰이 잡는 것과 못 잡는 것

| 못 잡는 것                                          | 이유                                                      |
| --------------------------------------------------- | --------------------------------------------------------- |
| 코드블록·인라인 코드 안의 문자열                    | 의도한 예외다. 규칙을 문서로 설명하려면 필요하다          |
| `docs/rfc` 밖 문서                                  | 의도한 범위다. 리뷰 기준 파일이 금지 경로를 적어야 한다   |
| 추적되지 않는 파일                                  | 다른 사람에게 전달되지 않아 문제가 생기지 않는다          |
| 다른 무시 대상 경로(`.env*`, `/my-doc`, `.idea` 등) | 지금은 한 접두사만 본다. 필요해지면 목록을 늘리면 된다    |
| 존재하지 않는 파일로의 링크 전반                    | 이 룰의 범위가 아니다. 링크 검사기를 따로 두어야 한다     |
| 링크 목적지를 여러 줄에 걸쳐 쪼갠 경우              | 줄 단위로 보기 때문이다. 실제로 그렇게 쓰면 링크가 깨진다 |

마지막 항목은 우회 경로로 남는다. 다만 그렇게 쓰면 렌더링에서도 링크가 만들어지지 않아, 규칙이 막으려던 결과와 같아진다.

## 7. 무엇이 기계로 내려가고 무엇이 남는가

10주간 사람이 눈으로 막던 것 중에서, 파일 경로와 문법만으로 참/거짓이 갈리는 것은 기계로 내려가고 나머지는 사람과 AI에 남는다. 이번에 승격한 항목은 검사 대상이 경로 패턴으로 정해지고 판정도 링크 문법으로 끝나서, 사람이 매번 확인할 이유가 없어졌다. 반면 4단계에서 오탐으로 판정한 세 건은 모두 "규칙이 어디까지 적용되는가"를 묻는 것이었고, 그 답은 규칙의 목적과 저장소의 사정을 함께 봐야 나온다. 그래서 적용 범위 판단, 설계 냄새, 예산과 required 배치 결정은 AI 리뷰와 사람 리뷰에 남긴다. 기계가 늘어날수록 사람이 볼 것이 줄어드는 것이 아니라, 사람이 볼 것이 맥락 판단으로 좁혀진다.

| 무엇                                           | 누가 판정     | 위치                      |
| ---------------------------------------------- | ------------- | ------------------------- |
| 타입·lint·테스트·빌드·번들 예산·환경 변수 형식 | 기계 (결정적) | `quality`                 |
| **추적 문서의 무시된 경로 참조**               | **기계**      | **`quality` (이번 추가)** |
| 사용자 흐름 회귀                               | 기계 (결정적) | `e2e-required`            |
| 규칙의 적용 범위, 설계 냄새                    | AI (비결정적) | advisory, 로컬 실행       |
| 예산 값, required 배치, 승격 여부              | 사람          | 3·5단계 문서              |

`quality`와 `e2e-required`는 required 대상으로 정한 두 check다. 영구 배치는 아직 하지 않았고, 지정했을 때의 차단 동작만 3단계에서 확인했다.
