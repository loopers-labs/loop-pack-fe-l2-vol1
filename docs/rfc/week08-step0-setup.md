# 8주차 0단계: 테스트 환경과 모킹 정리

과제 문서는 테스트 도구가 설치되지 않았고, DOM이 필요 없는 테스트 파일 5개만 있는 상태를 전제로 합니다. 하지만 이 브랜치에는 앞선 7주 동안 작성한 테스트와 설정이 이미 들어가 있었습니다.

| | 과제의 전제 | 현재 브랜치 |
| --- | --- | --- |
| 테스트 도구 | 모두 설치 필요 | Vitest·RTL·user-event·jest-dom·jsdom·Playwright 설치 완료, MSW만 필요 |
| 기존 테스트 | DOM이 필요 없는 5개 파일 | 19개 파일, 테스트 178개 |

과제가 지목한 5개 중 API 관련 테스트 3개와 성능 테스트 1개는 그대로 남아 있습니다. 여기에 `queries.test.ts`와 `api-client.test.ts`도 DOM이 필요하지 않아, node로 옮길 대상은 모두 7개였습니다.

나머지 하나인 `HeroSection.test.tsx`는 이 브랜치에 없습니다. 7주차(#146)에 Hero 이미지와 오버레이 카드를 홈 셸로 흡수하면서 컴포넌트 경계가 사라졌기 때문입니다. 홈 조회 결과를 쓰지 않는 영역을 첫 청크에 실어 보내려던 변경이었고, 지금은 `HomePage.tsx`가 그 마크업을 직접 그리며 `HeroSection.module.css`만 이름으로 남아 있습니다.

원본이 고정하던 단언과 지금의 위치는 이렇습니다.

| 원본 `HeroSection.test.tsx`의 단언 | 지금 어디에 있나 |
| --- | --- |
| `src="/images/week-07/hero-original.jpg"` · `width="3840"` · `height="2160"` | `HomePage.test.tsx` — 셸·성공·실패 세 상태에서 모두 확인 |
| props로 넣은 `title` · `description`이 마크업에 그대로 나온다 | 대체됨. props 되받기 대신 **서버가 준 배너가 화면에 도달하는지**를 본다 |
| (원본에 없음) 실제 배너 문구 값 | `route.test.ts` — 응답 계약이 지킬 몫이라 보고 `toEqual`로 못 박았습니다 |

이미지 계약은 그대로 이어받았고, 문구 단언은 검증 층을 옮겼습니다. 원본은 `title`에 문자열을 넣고 그 문자열이 마크업에 있는지 보는 구조라 사실상 prop 전달만 확인했는데, 지금은 조회 전/성공/실패 세 경로에서 배너가 어떻게 그려지는지를 봅니다.

`vitest.config.ts`를 확인해보니 `environment: 'jsdom'`이 모든 테스트에 적용되고 있었습니다. DOM이 필요 없는 파일 7개도 jsdom에서 실행되고 있어, node와 jsdom을 나누는 방법을 비교했습니다.

| | docblock (`// @vitest-environment node`) | `test.projects` |
| --- | --- | --- |
| 환경 지정 | 파일마다 직접 표기 | 파일 경로에 따라 자동 분류 |
| setup 분리 | 불가 | 프로젝트별 지정 가능 |

프로젝트마다 환경과 setup을 함께 나눌 수 있는 `test.projects`를 선택했습니다. DOM이 필요한 테스트는 `*.dom.test.*`로 이름 붙여 jsdom에서, 나머지는 node에서 실행합니다.

처음에는 확장자로 갈랐습니다(`.ts`는 node, `.tsx`는 jsdom). 그런데 확장자는 JSX 유무를 뜻하지 DOM 필요 여부를 뜻하지 않아 양쪽으로 어긋났습니다. `localStorage`만 쓰는 스토어 테스트 3개는 JSX가 없는데도 `.tsx`로 바꿔야 했고, JSX를 쓰지만 서버 렌더만 검증하는 `HomePage.test.tsx`는 설정에 파일 이름을 박아 예외로 빼야 했습니다. 환경을 이름에 직접 적으니 두 예외가 모두 사라졌습니다.

## 0-2. 환경 분리 중 발견한 문제

환경을 나누는 과정에서 `HomePage.test.tsx`가 서버 렌더 테스트인데도 브라우저의 재시도 정책을 따르고 있다는 사실을 발견했습니다. jsdom에서는 브라우저로 판정돼 조회 실패 시 1초와 2초의 백오프를 기다렸습니다.

이 테스트를 node 프로젝트로 옮겨 서버 정책인 `retry: 0`을 검증하도록 바꿨습니다. 환경 판정도 `environmentManager.isServer()`로 통일하고, 테스트에서는 `setIsServer`로 서버 여부를 직접 지정합니다.

## 0-3. MSW로 기존 모킹 이관

`tests/msw/`에 공통 픽스처, 핸들러, 서버를 두고 기존의 직접 모킹 4곳을 MSW로 바꿨습니다. 이제 테스트가 만든 에러를 바로 화면에 넘기지 않고, MSW 응답이 `apiClient`와 TanStack Query를 거쳐 화면에 도달합니다.

## 0-4. E2E 실행 위치 결정

E2E를 `pnpm test`에 포함할지, 별도 명령으로 분리해 `pnpm check`에서만 실행할지 고민했습니다.

| | `pnpm test`에 포함 | `pnpm check`에 포함 |
| --- | --- | --- |
| 장점 | 한 명령으로 모든 테스트를 확인 | 작업 중에는 Vitest만 빠르게 반복하고, PR 전에는 전체 검증 |
| 단점 | 매번 프로덕션 빌드와 페이지 로드가 필요 | 작업 중 E2E를 확인하려면 `pnpm test:e2e`를 따로 실행 |

Vitest만 실행하는 `pnpm test`는 약 5초, E2E까지 포함한 전체 검증 명령 `pnpm check`는 약 42초였습니다. `pnpm test`는 코드를 고치는 동안 자주 실행하므로, 여기에 프로덕션 빌드와 E2E를 넣으면 테스트 자체를 덜 돌리게 될 수 있습니다. 그래서 `pnpm test`에는 Vitest만 남기고, E2E는 PR 전과 CI에서 실행하는 `pnpm check`에 넣었습니다.

이 42초 안에는 프로덕션 빌드가 두 번 들어 있습니다. `pnpm check`가 `pnpm build`를 부르고, 이어지는 `pnpm test:e2e`의 `webServer`도 `pnpm build && pnpm start`로 다시 빌드합니다. 빌드 한 번이 약 6초라 중복도 그만큼입니다. `webServer`에서 빌드를 빼면 `pnpm test:e2e`를 단독으로 실행했을 때 프로덕션 빌드 위에서 돈다는 보장이 사라지고, `check`에서 빼면 E2E를 건너뛴 검증이 불가능해집니다. 단독 실행 보장을 택해 중복을 그대로 두었습니다.

프로덕션 빌드 위에서 실행된다는 조건도 지켜야 했습니다. `reuseExistingServer: true`이면 3000번 포트에 떠 있는 서버를 그대로 사용합니다. 실제로 `pnpm dev`가 실행 중일 때 빌드를 건너뛴 채 약 2초 만에 통과했습니다. 개발 서버를 검사하고도 프로덕션 빌드를 검증했다고 오인할 수 있어 `reuseExistingServer: false`로 설정했습니다. 잘못된 서버로 통과하는 것보다 실행에 실패하는 편이 낫다고 판단했습니다.
