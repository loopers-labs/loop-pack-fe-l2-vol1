## 무엇을 골랐나 — FSD 의존 방향

6주차에 정한 레이어 의존 방향이다.

```
shared → entities → features → _pages → app        (상위가 하위를 쓴다)
❌ entities/product/ui → features/add-to-cart       역방향
❌ features/add-to-cart → features/toggle-wishlist  같은 레이어 슬라이스 간
```

이 규칙은 `docs/rfc/week06-fsd.md`에 6주차부터 적혀 있었다. **그런데 문서에만 있었다.**
ESLint에는 import 경계 규칙이 하나도 없었고(`no-restricted-paths`도 `no-restricted-imports`도 없음),
그래서 지키는지는 매번 사람이 눈으로 봐야 했다.

승격 대상으로 고른 이유는 셋이다.

1. **결정적으로 참/거짓을 가릴 수 있다.** import 경로와 파일 위치만 보면 된다. 맥락 판단이 없다.
2. **반복해서 지적되는 종류다.** 6주차 이후 구조를 건드릴 때마다 확인해야 했다.
3. **실제로 새고 있었다.** 아래 참조.

## 승격 전에 이미 새고 있었다

전수 조사(모든 `@/` import를 레이어별로 집계)에서 위반 2건이 나왔다. 둘 다 같은 파일이다.

| 방향 | 파일 | import |
| --- | --- | --- |
| `features → app` 역방향 | `AddToCartButton.dom.test.tsx` | `@/app/SiteHeader` |
| `features → features` 같은 레이어 | 〃 | `@/features/toggle-wishlist/ui/WishButton` |

**10주 동안 사람 리뷰도, 4단계의 AI 리뷰도 이걸 잡지 못했다.** 문서에 있는 규칙은
읽는 사람이 그 순간 기억해야만 작동한다. 이게 "기계에 새긴다"의 이유다.

## 그런데 이 위반은 고치지 않았다 — 룰을 좁혔다

그 파일을 열어 보니 정당한 코드였다. 검증 대상이 **"담기 버튼과 헤더가 같은 스토어를 보는가"**라
헤더(app)와 다른 feature의 버튼을 한 화면에 조합하는 것이 곧 테스트의 내용이다.
페이지가 할 조합을 테스트가 대신 하는 것이고, 이 결합은 **배포되지 않는다.**

과제가 말한 오탐이 정확히 이것이다. 정상 코드를 막으면 룰이 아니라 장애물이다. 그래서 좁혔다.

```js
ignores: ['**/*.test.ts', '**/*.test.tsx'],
```

**한계도 같이 적는다.** 이 제외 때문에 테스트 파일 안의 구조 문제는 룰이 보지 못한다.
런타임 결합이 아니라는 근거로 제외했지만, 테스트가 나쁜 구조를 정상처럼 보이게 만들 여지는 남는다.
그건 사람이 볼 몫으로 남긴다.

## 구현

`eslint.config.mjs`에 `no-restricted-imports`를 레이어별로 스코프해 넣었다.
새 의존성은 넣지 않았다 — `import/no-restricted-paths`를 쓰려면 `eslint-plugin-import`가 필요한데,
경로 패턴만으로 충분해서 코어 룰로 끝냈다.

`fsdBoundary(layer)` 하나가 그 레이어보다 **상위인 레이어 전부**를 금지 패턴으로 만들고,
슬라이스 레이어(`entities`·`features`)면 같은 레이어 자기 자신도 추가한다.
`shared`와 `app`은 슬라이스 구조가 아니라 내부 참조가 정상이므로 같은 레이어 금지에서 뺐다
(예: `shared/test/render.tsx` → `@/shared/api/query-client`는 정상이다).
`app`은 최상위라 역방향이 없어 대상 자체가 아니다.

메시지에는 **무엇이 왜 막혔는지와 근거 문서 경로**를 넣었다. 실패 메시지만 보고 고칠 수 있어야 한다.

## 자가 검증

### 위반을 막는가

레이어별로 임시 파일을 만들어 넣고 `pnpm lint`를 돌렸다. 넷 다 error로 막혔다.

| 만든 위반 | 결과 |
| --- | --- |
| `shared` → `@/entities/cart` | ❌ 차단 — "shared는 상위 레이어(entities)를 알면 안 된다" |
| `entities` → `@/features/add-to-cart/ui/…` | ❌ 차단 — "entities는 상위 레이어(features)를…" |
| `features` → `@/features/toggle-wishlist/ui/…` | ❌ 차단 — "같은 레이어의 다른 슬라이스를 직접 import" |
| `_pages` → `@/app/SiteHeader` | ❌ 차단 — "_pages는 상위 레이어(app)를…" |

### 정상 코드를 통과시키는가

- 승격 직후 `pnpm lint` exit 0. 기존 소스 전체가 그대로 통과한다.
- 정방향 import를 일부러 만들어 봤다: `features` → `@/entities/cart`. **걸리지 않았다.**
- 테스트 파일의 기존 위반 2건도 걸리지 않는다(의도한 제외).

검증이 끝나고 임시 파일은 전부 지웠다. `git status`로 확인했다.

## 무엇을 기계에, 무엇을 사람과 AI에

1주차 책임 모델을 이 저장소 기준으로 다시 쓰면 이렇다.

**기계로 내려간 것**은 참/거짓이 코드에서 결정되는 것들이다. 타입(`tsc`), 린트 규칙,
테스트, 번들 예산(237.5KB/261KB), 환경 변수 형식, 그리고 이번에 내린 FSD 의존 방향이다.
공통점은 **판정에 맥락이 필요 없다**는 것이다. import 경로가 `@/features/`로 시작하는지는
누가 봐도 같은 답이 나온다.

**사람과 AI에 남은 것**은 판정에 맥락이 필요한 것들이다. 예를 들어 위의 테스트 파일이
"정당한 조합인가 구조 누수인가"는 검증 대상이 무엇인지를 알아야 답할 수 있다.
레이어를 하나 더 만들지(6주차 widgets), 예산 여유를 몇 퍼센트로 둘지, E2E를 어디에 둘지,
캐시 저장 28초와 3초 중 무엇을 믿을지 — 전부 근거를 비교해 고르는 일이다.

**그래서 AI 리뷰를 줄이는 방법은 AI를 더 잘 시키는 게 아니라, 반복되는 지적을 기계로 내리는 것이다.**
이번 주에 그걸 한 번 했다. FSD 경계는 이제 리뷰에서 물어볼 필요가 없다.
4단계에서 AI가 경계를 두 번 잘못 짚었던 것도 같이 사라진다 — 이제 정답은 ESLint가 말한다.
