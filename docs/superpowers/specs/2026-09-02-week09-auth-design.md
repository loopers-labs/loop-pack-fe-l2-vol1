# 9주차 인증 흐름 설계

## 1. 목적과 범위

9주차 1단계 요구사항에 맞춰 제공된 인증 API를 로그인 UI, 서버 렌더링 헤더, 보호 경로, 경로 복원, 세션 만료 및 로그아웃 처리에 연결한다.

이 설계의 범위는 인증 단계로 제한한다. 이벤트 이름과 공통 프로퍼티를 정하고 `identify()`·`reset()`을 연결하는 작업은 2단계 이벤트 계측에서 수행한다. 다만 로그인·로그아웃 기능에는 2단계에서 계측을 연결할 수 있는 명확한 성공 지점을 둔다.

### 제공된 서버 API

- `POST /api/auth/login`
- `POST /api/auth/logout`
- `GET /api/auth/me`
- `POST /api/orders`
- `GET /api/orders`

API 계약과 시나리오 노브는 변경하지 않는다.

### 이번 단계에서 만드는 사용자 경로

- `/login`: 로그인 화면
- `/checkout`: 주문서, 필수 보호 경로
- `/orders`: 주문 내역, 필수 보호 경로

장바구니와 위시리스트는 비로그인 사용자도 사용할 수 있게 둔다. 상품을 고른 뒤 주문 단계에서 로그인하도록 하여 로그인 전 구매 준비 상태를 보존한다.

## 2. 설계 원칙

### 서버 세션이 인증의 유일한 기준이다

인증 사용자를 Zustand나 React Context에 별도의 원본 상태로 저장하지 않는다. 서버가 요청의 `session` 쿠키를 검증한 결과만 실제 인증 상태로 취급한다.

클라이언트에서 `user` 값을 임의로 설정해도 보호 경로에 들어갈 수 없어야 한다. 로그인·로그아웃 후에는 페이지 이동 또는 `router.refresh()`로 서버가 쿠키를 다시 읽게 한다.

### 1차 가드와 최종 인증을 분리한다

- `proxy.ts`: 보호 경로 요청에 `session` 쿠키가 존재하는지만 확인한다.
- 서버 인증 함수: 쿠키의 서명, 만료 및 사용자를 최종 검증한다.

`proxy.ts`를 통과했다는 사실은 인증 성공을 뜻하지 않는다. 조작되거나 만료된 쿠키는 보호 페이지의 서버 인증 단계에서 거부한다.

## 3. 구성 요소와 책임

### `proxy.ts`

`/checkout`과 `/orders` 요청을 감시한다.

- 쿠키가 없으면 `/login`으로 리다이렉트한다.
- 원래의 path와 query string을 `returnTo`에 보존한다.
- 쿠키가 있으면 다음 단계로 통과시킨다.
- 쿠키의 서명이나 만료는 검증하지 않는다.

### 서버 세션 코어

세션 타입과 쿠키 검증 코어를 `entities/session`에 둔다. 현재 `src/app/api/_data/auth.ts`에서 세션 생성·검증에 해당하는 부분만 추출하고, 주문 저장 로직은 이동하지 않는다.

API Route와 Server Component가 같은 세션 코어를 사용한다. 검증 로직을 복제하거나 UI 계층에서 `app/api` 내부 파일을 직접 import하지 않는다.

서버 전용 함수 `getCurrentUser()`는 현재 요청의 쿠키를 읽어 다음 중 하나를 반환한다.

- 유효한 세션: 인증 사용자
- 쿠키 없음, 조작, 만료 또는 알 수 없는 사용자: `null`

### 헤더

현재 클라이언트 `Header`의 책임을 분리한다.

```text
Header (Server Component)
├── getCurrentUser() 호출
├── 미로그인: 로그인 링크 렌더링
├── 로그인: 사용자 이름 렌더링
└── HeaderActions (Client Component)
    ├── 장바구니 개수
    ├── 위시리스트 개수
    └── 로그아웃 버튼
```

서버가 생성하는 HTML에 로그인 여부가 포함되어야 한다. 세션 토큰은 클라이언트 props로 전달하지 않고 표시와 동작에 필요한 최소 정보만 전달한다.

쿠키를 읽는 위치 때문에 홈과 상품 페이지의 렌더링 범위가 달라질 수 있다. 구현 후 `pnpm build`와 production 실행에서 기존 7주차 스트리밍 구조가 유지되는지 확인한다. 회귀가 관찰되면 인증 헤더를 작은 서버 렌더링·Suspense 경계로 격리하되 초기 HTML의 로그인 상태 요구는 유지한다.

### 로그인 기능

로그인 폼은 이메일과 비밀번호를 받아 `POST /api/auth/login`을 호출한다.

- 성공: 브라우저가 응답의 httpOnly `session` 쿠키를 저장한 후 안전한 복원 경로로 이동한다.
- 400: 입력 또는 요청 형식 오류를 표시한다.
- 401: 이메일 또는 비밀번호 오류를 표시한다.
- 500: 서버 오류를 표시한다.
- 요청 중: 중복 제출을 막고 진행 상태를 표시한다.

로그인 API가 반환한 사용자를 전역 인증 상태에 저장하지 않는다. 페이지 이동 후 서버가 저장된 쿠키를 다시 검증한다.

### 안전한 복원 경로

`returnTo`를 검증하는 순수 함수 하나를 둔다. path와 query string을 포함한 같은 사이트의 내부 경로만 허용한다.

허용 예:

- `/`
- `/checkout`
- `/orders`
- `/checkout?coupon=welcome`

거부 예:

- `https://evil.example`
- `//evil.example`
- `\evil.example`
- `javascript:...`

거부되거나 파싱할 수 없는 값은 `/`로 대체한다. `proxy.ts`가 만든 값도 로그인 성공 직전에 같은 규칙으로 다시 검증한다.

### 보호 페이지

`/checkout`과 `/orders`의 Server Component는 `getCurrentUser()`로 세션을 최종 검증한다.

- 유효: 페이지 렌더링
- 무효: 현재 내부 경로를 보존해 `/login`으로 리다이렉트

`/checkout`은 현재 장바구니 상품을 주문할 수 있는 최소 화면이다. 기존 장바구니가 상품 ID만 저장하므로 각 항목의 주문 수량은 이번 범위에서 `1`로 전송한다. 수량 변경 기능은 추가하지 않는다.

`/orders`는 `GET /api/orders`로 현재 로그인 사용자의 주문을 표시한다. 사용자 ID를 클라이언트가 전달하지 않고 API가 세션에서 사용자를 결정한다.

## 4. 세션 만료와 오류 처리

일반 `fetchJson()`에서 모든 401을 세션 만료로 처리하지 않는다. 인증이 필요한 API 요청만 사용하는 보호 요청 경계를 둔다.

```text
보호 API 요청
→ 401
→ 현재 내부 경로 보존
→ /login?reason=expired&returnTo=... 이동
→ 세션 만료 안내
```

401의 의미는 다음 기준으로 구분한다.

- 로그인 API의 401: 잘못된 자격 증명
- 최초 `/api/auth/me`의 401: 로그인하지 않음
- 로그인된 흐름에서 보호 API의 401: 세션 만료

서버 페이지가 조작되거나 유효하지 않은 쿠키를 발견했을 때는 원인을 확정할 수 없으므로 세션 만료 문구를 표시하지 않고 일반 로그인으로 보낸다. 과제의 `expired` 시나리오는 보호 API 요청에서 재현한다.

## 5. 로그아웃과 클라이언트 상태

로그아웃 성공 시 다음 순서를 따른다.

1. `POST /api/auth/logout`으로 `session` 쿠키를 제거한다.
2. 위시리스트를 초기화한다.
3. 장바구니는 유지한다.
4. 서버가 새 쿠키 상태로 헤더를 다시 만들도록 갱신한다.

정책의 근거:

- 장바구니는 로그인 전부터 사용자가 만든 구매 준비 상태다. 로그아웃으로 제거하면 사용자의 작업이 유실되므로 유지한다.
- 위시리스트는 계정에 귀속된 개인화 정보로 취급한다. 같은 브라우저를 사용하는 다음 사용자에게 노출하지 않도록 초기화한다.

주문이 성공하면 구매가 끝난 항목이므로 장바구니를 초기화하고 `/orders`로 이동한다. 위시리스트는 주문 성공으로 변경하지 않는다.

## 6. 예상 파일 경계

```text
src/
├── app/
│   ├── login/page.tsx
│   ├── checkout/page.tsx
│   └── orders/page.tsx
├── _pages/
│   ├── login/
│   ├── checkout/
│   └── orders/
├── entities/
│   ├── session/
│   ├── cart/          # clearCart 추가
│   └── wishlist/      # clearWishlist 추가
├── features/
│   ├── auth/
│   └── create-order/
├── shared/api/
│   └── 보호 요청 경계

    └── ui/HeaderActions.tsx

proxy.ts
```

구체적인 파일 수와 이름은 구현 계획에서 기존 public API와 테스트 구조를 대조해 최소화한다. 새 외부 의존성과 tsconfig·Next 설정 변경은 이 설계에 포함하지 않는다.

## 7. 검증 전략

### 단위 테스트

- 안전한 내부 `returnTo` 허용
- 외부·프로토콜 상대·역슬래시 경로 거부
- 세션 코어의 유효·만료·조작 토큰 판정
- 장바구니·위시리스트 초기화 동작

### 통합 테스트

- 로그인 폼의 성공, 400, 401, 500 상태
- 보호 API 401의 중앙 만료 처리
- 로그인 실패 401이 만료로 처리되지 않음
- 주문 요청 데이터와 성공 후 장바구니 초기화
- 로그아웃 후 위시리스트 초기화와 장바구니 유지

### 실제 실행 검증

- production build에서 API Route 네 개가 노출됨
- 미로그인 보호 경로 접근이 500 없이 로그인으로 이동함
- 로그인 후 원래 경로로 복귀함
- 초기 HTML에 로그인 상태가 반영됨
- 외부 복원 경로로 나가지 않음
- 홈과 상품 페이지의 7주차 렌더링·스트리밍 구조가 회귀하지 않음

Playwright E2E의 최종 시나리오와 개수는 3단계 `docs/rfc/week09-e2e-scope.md`에서 로그 근거와 함께 결정한다. 1단계에서는 E2E 범위를 선결하지 않는다.

## 8. 완료 기준

- 로그인·로그아웃 화면과 헤더가 서버 세션 상태를 반영한다.
- `/checkout`과 `/orders`가 보호된다.
- 로그인 후 원래 내부 경로로 돌아오며 외부 주소는 차단된다.
- JavaScript 실행 전의 초기 HTML에 로그인 여부가 나타난다.
- 세션 만료 처리가 보호 요청 경계 한 곳에 모인다.
- 로그아웃 상태 정리 정책이 구현과 문서에서 일치한다.
- production build의 실제 라우트와 보호 경로가 정상 동작한다.
- 기존 7주차 성능 구조와 8주차 테스트가 회귀하지 않는다.
- `pnpm test`와 `pnpm check`가 통과한다.
