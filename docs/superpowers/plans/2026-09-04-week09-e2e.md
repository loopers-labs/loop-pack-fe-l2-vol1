# Week 9 E2E Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 승인된 RFC의 인증 세 갈래와 인증된 주문 완료만 production Playwright E2E로 구현하고, 기존 8주차 상품 탐색 E2E와 함께 병렬·반복 안정성을 증명한다.

**Architecture:** Week 9 전용 Playwright config와 fixture가 production 서버, 역할·이름 locator, 워커별 UI 로그인 `storageState`를 소유한다. 인증 자체를 검증하는 테스트는 비로그인 기본 `page`를 사용하고, 만료·주문 테스트만 `parallelIndex`에 대응하는 저장 상태를 사용하는 `authenticatedPage` fixture를 사용한다.

**Tech Stack:** Next.js 16 production build, Playwright 1.62, TypeScript, existing eight test accounts

**Spec:** `docs/rfc/week09-e2e-scope.md`

## Global Constraints

- 새 의존성을 추가하지 않는다.
- `playwright.week09.config.ts`와 `package.json` script 변경은 환경설정 변경이므로 구현 직전 사용자 승인을 받는다.
- `pnpm.cmd`와 portable Node `D:\Loopers-tools\node-v22.23.2-win-x64`만 사용한다.
- Week 9 신규 범위는 인증 세 갈래와 주문 완료 하나뿐이다. 기존 Week 8 상품 탐색 5개는 복제하지 않고 같은 config에서 재사용한다.
- 인증 자체와 잘못된 자격 증명 테스트는 `storageState`를 사용하지 않는다.
- 만료와 주문만 워커별 UI 로그인으로 만든 `storageState`를 재사용한다.
- locator는 역할과 접근 가능한 이름을 사용하고 `getByTestId`, CSS 구조 selector, 시간 기반 sleep을 사용하지 않는다.
- 테스트는 production build 위에서 실행하고, 주문 쓰기는 `parallelIndex`별 계정으로 격리한다.
- 실패한 실험을 위한 의도적 변경 외에는 `it.skip`, 주석 비활성화, retry로 불안정성을 숨기지 않는다.
- Git add·commit 직전에 정확한 파일과 메시지를 제시하고 사용자 승인을 새로 받는다.

## File Structure

- `playwright.week09.config.ts`: Week 8 재사용 + Week 9 setup/spec, production server, 병렬 실행 설정
- `e2e/week09/accounts.ts`: `parallelIndex`를 기존 8개 계정과 저장 파일 경로로 매핑
- `e2e/week09/auth.setup.ts`: 역할·이름 기반 UI 로그인 후 워커별 storage state 생성
- `e2e/week09/fixtures.ts`: `authenticatedPage`와 현재 워커 계정 fixture
- `e2e/week09/auth.spec.ts`: 복원, 만료, 잘못된 자격 증명 세 갈래
- `e2e/week09/order.spec.ts`: 새 주문 ID까지 확인하는 인증 주문 흐름
- `docs/rfc/week09-e2e-scope.md`: 실제 격리·selector·trace 확인 기록 추가
- `package.json`: `test:e2e`를 Week 9 config로 전환

### Task 2: 인증 필수 세 갈래

**Files:**
- Create: `e2e/week09/auth.spec.ts`
- Modify only if a RED test proves a product defect in existing auth code

**Interfaces:**
- Consumes: default unauthenticated `page`, `authenticatedPage`, `workerAccount`

- [ ] **Step 1: Write the three scenarios**

1. Default page opens `/checkout?coupon=welcome`, asserts `/login?returnTo=...`, performs UI login, then asserts the complete original query and `주문서` heading.
2. `authenticatedPage` adds context cookie `scenario=expired`, opens `/orders`, waits for `GET /api/orders` 401, then asserts `/login?reason=expired&returnTo=%2Forders` and the expiry notice.
3. Default page opens `/login?returnTo=%2Forders`, submits a valid account email with a wrong password (or `scenario=invalid`), asserts the accessible alert and that URL remains under `/login`.

- [ ] **Step 2: Verify RED/GREEN honestly**

Run only `auth.spec.ts` with workers 1. If tests pass against existing behavior, record them as characterization coverage rather than fabricating RED. Any discovered defect requires a failing focused test before production change.

- [ ] **Step 3: Attack boundary cases**

Verify no storage state is loaded in scenarios 1 and 3, no API login shortcut exists, response/URL/visible role waits replace sleep, and expired cookie is scoped only to its context.

- [ ] **Step 4: Review and commit gate**

Run normal and adversarial review. Proposed commit: `test: 인증 경계 E2E 시나리오 추가`.

## Definition of Done

- RFC remains earlier in Git history than every Week 9 E2E code commit.
- Authentication restoration, expiry and invalid credentials run on production build.
- Authenticated order checks the exact newly returned order ID.
- Login validation tests do not use storageState; expiry/order reuse UI-created worker state.
- Workers 1 and 4 and three repeated runs agree.
- No fixed sleep, disabled test, API-forged auth, or unselected scenario exists.
- A deliberately failed trace was opened and the observation is recorded after reverting the failure.
- Existing Week 8 five scenarios, full unit/integration suite and `pnpm check` pass.
