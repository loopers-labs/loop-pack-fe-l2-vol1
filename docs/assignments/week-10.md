# 10주차 — CI 파이프라인과 AI 협업: 검증을 기계에 새겨요

> **Phase**: 엔지니어링 레벨업 (마지막 주)

> 💡 이번 주에는 검증을 많이 추가하지 않아요. 1주차에 세운 1차 하네스(lint·type)를 CI로 끌어올려 **측정하고, 병목만 줄이고, 어떤 검증을 언제 돌릴지 조건을 설계하고, 예산을 정하고, AI를 리뷰에 붙였다가 반복되는 지적을 결정적 룰로 굳히는** 게 목표예요. 마지막 목표는 "CI를 붙였다"가 아니라, **어떤 코드가 어떤 검증을 통과해서 배포되는지 설명할 수 있는 상태**예요.

## 왜 이 과제를 하는가

- **1주차 제1원칙의 마지막 회수** — "설명할 수 없는 코드는 커밋하지 않는다." 10주차에는 이 원칙을 **팀 전체가 지키도록 CI에 새깁니다.** 사람이 매번 눈으로 막던 것을 결정적 게이트로 내리고, 결정적으로 판별할 수 없는 것만 AI와 사람에게 남겨요.
- **1주차 책임 모델을 CI/CD로 재해석**

  | 역할               | 10주차에서 맡는 것                                                      |
  | ------------------ | ----------------------------------------------------------------------- |
  | 🤖 기계(CI 게이트) | lint·type·test·build·번들 예산 — **결정적으로 판별 가능한 것 전부**     |
  | 🤝 AI 리뷰어       | 컨벤션·설계 냄새 — **비결정적이라 참고용**, required 게이트로 두지 않음 |
  | 🔍 사람 리뷰어     | 설계 조언·리스크 식별 (버그 부재 보장은 ✗)                              |
  | 👤 작성자          | 정확성·버그·동작의 1차 책임 전부                                        |

- **AI를 잘 쓴다 = AI를 맹신하는 게 아니라, AI가 찾은 반복 패턴을 결정적 하네스로 굳혀 AI·사람 리뷰의 부담을 줄이는 것.** 이번 주 5단계가 그 결론이에요.

> 💡 **AI 사용 원칙** — 이번 주는 AI를 **적극적으로 활용**하세요. workflow YAML 초안, 스크립트 골격, 룰 작성, PR 셀프리뷰까지 AI가 잘 돕는 영역이에요. 쓰는 도구는 자유예요(Gemini·Claude·Codex·로컬 CLI·구독·무료 챗봇 무엇이든). 다만 **과제가 특정 유료 API 결제를 강제하지는 않아요** — AI를 CI에 통합하는 건 선택이고, 붙이더라도 결제가 강제되지 않는 경로(무료 티어·구독·로컬 실행)로 둘 수 있어요. 그리고 **판단·검증은 직접 하세요**: 무엇을 required로, 예산을 얼마로, 무엇을 룰로 승격할지는 AI에 넘기지 않아요.

## 📝 Implementation Quest

### ⏱️ 1단계 — CI 파이프라인을 측정하고 병목만 줄여요

7주차 성능 최적화와 같은 방식이에요. **빠른 숫자를 만들려고 검증을 지우지 않아요.** 같은 조건에서 실행 시간을 재고, 가장 긴 구간만 줄이고, 캐시가 진짜로 작동하는지 증명해요.

#### 0단계 — Before를 고정해요

먼저 PR에서 lint·typecheck·test·build 중 프로젝트에 있는 검증이 자동으로 도는 workflow를 확인하거나 보강해요.

```yaml
name: CI

on:
  pull_request:
  push:
    branches: [main]

# 워크플로가 GITHUB_TOKEN으로 할 수 있는 일을 최소로 제한해요 (공통 섹션 참고)
permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version-file: .nvmrc
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm check
```

**요구사항**

- lint, typecheck, test, build 중 프로젝트에 있는 검증을 모두 CI에서 실행해요. lockfile은 무시하지 않아요(`--frozen-lockfile`). Node 버전은 `.nvmrc` 기준과 맞춰요. job에는 `timeout-minutes`를 둬요.
- **cold(캐시 없음)와 warm(캐시 있음)을 분리**해 각각 3회 실행하고, 전체 wall-clock의 raw 값·중앙값·범위를 남겨요. 캐시가 없는 첫 실행과 있는 실행은 다른 조건이에요.
- Actions 로그의 step별 소요 시간에서 **가장 긴 구간을 지목**해요. "느낌"이 아니라 타임스탬프로요.

> 💡 Before와 After는 같은 커밋 또는 같은 규모의 변경에서 재요. 러너 종류, Node 버전, 캐시 상태(cold/warm)를 제외한 조건을 같게 두세요. GitHub 러너는 시간대에 따라 흔들리니 3회 이상 재고 범위를 함께 남겨야 해요.

> 🤝 **AI 활용** — workflow YAML 초안이나 병목 분석은 AI에게 맡겨도 좋아요. 단, "가장 긴 구간이 어디냐"는 **로그 타임스탬프로 본인이 확인**하세요. AI가 짚어준 병목을 그대로 믿지 말고 숫자로 검증해요.

#### 1단계 — 병목에 맞는 전략만 골라요

| 전략                       | 언제 효과 있나                                                 |
| -------------------------- | -------------------------------------------------------------- |
| job 병렬화                 | 서로 독립인 검증(lint/type/test)이 한 job에서 직렬로 도는 경우 |
| `concurrency` 그룹         | 같은 PR에 연속 push가 잦아 중복 실행이 쌓이는 경우             |
| setup-node·pnpm store 캐시 | `install`이 매 실행마다 의존성을 새로 받는 경우                |

> 💡 path filter로 "안 돌려도 되는 검증을 아예 안 돌리는" 최적화는 **2단계 조건부 실행 설계**에서 본격적으로 다뤄요. 1단계는 "돌리기로 한 검증을 더 빠르게"에 집중해요.

**요구사항**

- Before에서 지목한 병목에 **맞는 전략만** 골라 적용해요. 7주차처럼, 병목과 무관한 최적화는 넣지 않고 안 넣은 근거를 남겨도 돼요.
- 목표는 **같은 검증을 유지한 채** wall-clock을 유의미하게 줄이는 거예요. test를 빼서 시간을 줄이는 건 개선이 아니에요.

**함정(감점 포인트 = 학습 포인트)**

- `concurrency` 그룹 키에 ref를 넣지 않아 `main` push 배포까지 취소하면 사고예요. `group: ${{ github.workflow }}-${{ github.ref }}` 처럼 브랜치별로 갈라야 해요.
- job을 병렬화했는데 각 job이 `install`을 중복 실행해 캐시 이득을 까먹지 않는지 확인해요.

#### 2단계 — 캐시 hit을 증명해요 (자가 검증)

8주차 "내 테스트가 진짜 뭘 잡는지 확인해요"를 CI 캐시에 적용해요. 캐시를 걸었다고 hit 되는 게 아니에요.

**요구사항**

- warm 실행 로그에서 캐시 복원 메시지(예: `Cache restored from key: ...`)를 확인하고 캡처해요.
- **캐시 키를 일부러 깨서 miss를 재현해요.** lockfile을 바꿔 해시가 달라지면 `Cache not found`가 나오고 install이 다시 도는지 확인해요. hit과 miss의 install 시간 차이를 함께 기록해요.
- 실험이 끝나면 lockfile을 원래대로 되돌려요.

#### 3단계 — 같은 조건에서 After를 재요

**요구사항**

- 0단계와 같은 cold/warm 조건에서 3회씩 다시 재고 raw 값·중앙값·범위를 Before와 비교해요.
- 줄어든 시간이 **측정 흔들림(범위)보다 큰 변화인지**, 그리고 그 변화가 지목한 병목과 연결되는지 설명해요.

**완료조건**

Before/After의 cold·warm raw 값·중앙값·범위, 병목 지목 1문단, 캐시 hit/miss 로그, "왜 이 전략만 골랐나"를 제출물에서 확인할 수 있어야 해요. 검증 항목은 Before와 After가 같아야 해요.

### 🔀 2단계 — 조건부 실행을 설계해요

CI에 검증을 다 넣고 모든 PR에서 전부 돌리는 게 정답은 아니에요(9주차). E2E는 20초씩 걸리고, 문서만 고친 PR에서 전체 테스트를 도는 건 낭비예요. 이번 단계의 핵심은 **어떤 검증을 언제 돌릴지 조건을 설계하고, 스킵이 왜 안전한지 증명**하는 거예요.

#### 검증별 실행 조건 판단 (9주차 회수)

| 검증                         | 성격          | 권장 실행 조건                             |
| ---------------------------- | ------------- | ------------------------------------------ |
| lint / typecheck / unit test | 결정적·저비용 | 모든 PR                                    |
| production build             | 결정적        | 모든 PR (설정·소스 변경 시)                |
| E2E                          | 비쌈·느림     | 관련 경로 변경 PR · label · main merge 전  |
| Lighthouse CI                | 변동성 큼     | 주요 화면 변경 PR 또는 정기(schedule) 실행 |

**설계 수단 (규칙 성격에 맞는 것을 고르세요)**

| 수단                                                   | 언제 쓰나                                            |
| ------------------------------------------------------ | ---------------------------------------------------- |
| workflow `on.push/pull_request.paths`                  | 특정 경로 변경 때만 workflow 자체를 트리거           |
| `dorny/paths-filter` 등 changed-files 필터             | 한 workflow 안에서 job별로 "무엇이 바뀌었나"로 분기  |
| PR label 트리거 (`run-e2e` 등)                         | 사람이 명시적으로 부를 때만 비싼 검증 실행           |
| draft PR skip (`if: !github.event.pull_request.draft`) | 작성 중인 PR에서 비싼 검증을 아끼기                  |
| `merge_group` (merge queue)                            | 개별 PR엔 가볍게, main에 들어가기 직전에만 전체 검증 |

**요구사항**

- **저비용 결정적 검증(lint/type/unit)은 모든 PR에서** 무조건 돌게 둬요. 이건 조건을 붙이지 않아요.
- **E2E(또는 프로젝트에서 가장 비싼 검증) 하나 이상에 실행 조건을 설계**해요. 위 수단 중 프로젝트 상황에 맞는 걸 고르고, **왜 이 조건이고 무엇을 스킵하기로 했는지** 근거를 남겨요.
- 조건부로 스킵하기로 한 검증에 대해, **"이걸 스킵해도 깨진 코드가 main에 못 들어간다"는 안전 논리**를 적어요. 예: E2E를 관련 경로 변경 PR에서만 돌리되, main merge 전 `merge_group`에서 한 번 더 전체를 돌려 최종 방어.

**함정(감점 포인트 = 학습 포인트)**

- path filter가 `**`처럼 너무 넓으면 무의미하고, 너무 좁으면 필요한 검증을 스킵해 깨진 코드가 통과해요. 스킵 범위와 그게 안전한 이유를 반드시 적어요.
- **required status check와 조건부 스킵의 충돌** — 어떤 검증을 branch protection의 required로 걸어두고 그 검증이 조건부로 아예 실행되지 않으면, PR이 "체크 대기"로 영영 못 머지될 수 있어요. required로 둘 검증은 **항상 실행되거나, 스킵 시 성공으로 보고되는** 구조여야 해요(예: skip 시 통과하는 guard job).
- label 트리거는 label을 뗐다 붙일 때의 재실행·권한을 확인해요.

#### 자가 검증

**요구사항**

- **조건에 걸리는 PR과 안 걸리는 PR을 각각 하나씩** 만들어, 비싼 검증이 **돌 때는 돌고 스킵될 때는 스킵되는지** Actions 로그로 보여줘요(문서만 바꾼 PR에서 E2E가 안 도는지 등).
- required로 둔 검증이 조건부 실행과 충돌하지 않는지(머지 가능 상태가 되는지) 확인해요.

> 💡 **flaky 대비** — E2E는 환경 때문에 가끔 흔들려요. Playwright `retries`를 CI에서만 켜거나(`retries: process.env.CI ? 2 : 0`), 반복 실패하는 스펙을 격리(`test.fixme`/`skip`)하고 이슈로 남기는 정책을 정해요. **retry로 실패를 감추는 게 목적이 아니라, 흔들림과 진짜 실패를 구분**하려는 거예요. 어떤 정책을 왜 골랐는지 1~2줄로 남겨요.

> 🤝 **AI 활용** — `dorny/paths-filter` 조건이나 `merge_group` 트리거 문법은 실수하기 쉬워요. AI에게 초안을 받아도 좋지만, **"이 필터가 필요한 검증을 스킵하지 않는가"는 실제 PR 두 개로 본인이 검증**하세요.

**완료조건**

E2E(또는 최고비용 검증)의 실행 조건과 그 근거, 스킵이 안전한 이유, 조건에 걸리는/안 걸리는 PR의 Actions 로그, flaky 정책을 제출물에서 확인할 수 있어야 해요.

---

### 💰 3단계 — 예산 게이트를 걸고 결과를 보이게 해요

CI에 명령을 많이 넣는다고 좋은 파이프라인이 아니에요. 중요한 건 **main에 들어가면 안 되는 실패를 어디서, 어떤 근거로 막을지**, 그리고 **막혔을 때 왜 막혔는지 한눈에 보이는지**예요. 임계값은 **7주차 측정값**에 근거해 정해요.

**요구사항**

- **번들 예산**: `size-limit`(또는 동등 도구)으로 주요 진입점의 번들 예산을 걸어요. 임계값 근거는 **7주차에 잰 실제 전송 크기 + 현재 값의 범위**여야 해요. "적당히 300KB"는 감점이에요. 왜 이 값이고 여유폭을 얼마로 뒀는지 적어요.
- **환경 변수 검증**: 배포 사고는 코드보다 설정에서 자주 나요. 필수 환경 변수를 build 전에 검증하는 결정적 게이트를 추가해요. 누락된 값, 잘못된 URL, 브라우저에 노출되면 안 되는 값에 `NEXT_PUBLIC_`이 붙은 경우는 실패해야 해요.
- **(선택) Lighthouse CI**: assertion을 건다면 임계값 근거도 7주차 LCP·CLS 측정값이어야 해요. 변동성이 크니 모든 PR로 둘지, 주요 화면 PR/정기 실행으로 둘지 판단하고 근거를 남겨요(2단계 조건부 실행과 연결).
- **branch protection**: 어떤 status check를 required로 둘지 정하고, required에서 제외한 검증은 실행 비용·변동성·현재 리스크 기준으로 이유를 적어요.
- **결과 가시성**: 예산·CI 결과가 **PR에서 바로 보여야** 해요. size-limit의 PR 코멘트 액션이나 job summary(`$GITHUB_STEP_SUMMARY`)로 "무엇이 얼마나 초과했나"를 PR 화면에서 확인할 수 있게 하세요. 로그를 열어봐야만 알 수 있으면 실무에서 안 봐요.

#### 빨간불 자가 검증

**요구사항**

- **예산을 일부러 초과하는 PR을 하나 만들어** CI가 빨갛게 뜨는 것까지 제출해요. (큰 라이브러리를 무의미하게 import하거나, 잘못된 환경 변수를 넣는 식으로요.)
- **PR 화면(코멘트/summary)만 보고** 무엇을, 얼마나 초과했는지 알 수 있는지 확인해요(8주차 "실패 메시지로 원인을 짐작할 수 있었나"). 알기 어려우면 리포트 출력을 손봐요.
- 수정 후 다시 초록불이 되는 것까지 확인해요. 실험 PR은 머지하지 말고 근거로만 남겨요.

**완료조건**

임계값과 그 근거(7주차 값 인용), 초과 PR의 빨간불과 **PR에 노출된 실패 리포트** 스크린샷, "이 게이트는 required·저 게이트는 아님"의 판단을 제출물에서 확인할 수 있어야 해요.

### 🤖 4단계 — AI를 코드리뷰에 활용해요

1주차의 핵심은 판별력이었어요. AI가 _그럴듯하게 틀린_ 코드를 쏟아내듯, **AI 리뷰도 그럴듯하게 틀립니다.** 이번 단계의 핵심은 세팅이 아니라 **리뷰 기준(프롬프트) 설계와, AI 리뷰의 옥석을 가리는 판별력**이에요.

**요구사항**

- **본인이 쓰는 AI 도구로 PR diff를 리뷰**해요. 도구는 자유예요 — 로컬 CLI(Claude Code·Codex·Gemini CLI 등), 구독 챗봇, 무료 티어 무엇이든 좋아요. **CI(GitHub Actions)에 붙이는 건 선택**이고, 붙인다면 결제가 강제되지 않는 경로(무료 티어 API·구독·self-hosted)로 두거나 로컬 실행으로 대체해도 돼요.
- **리뷰 기준 = 우리 팀이 10주간 합의한 규칙**을 프롬프트에 명문화해요. 일반론("가독성 좋게")이 아니라 이 프로젝트의 규칙이어야 해요.

  | 출처            | 리뷰 기준 예시                                                 |
  | --------------- | -------------------------------------------------------------- |
  | 1주차 CLAUDE.md | 무의미한 `any`/`as`/`eslint-disable`, 설명 없는 커밋           |
  | 2~3주차         | custom hook 분리 기준, 파생 값을 `useEffect`로 동기화하지 않기 |
  | 5·7주차         | URL 상태 동기화 규칙, 서버 응답을 로컬 상태에 복사하지 않기    |
  | 6주차           | FSD import 경계, slice Public API 우회 금지                    |

- **(선택) CI 통합 시 안전장치** — AI 리뷰를 Actions에 붙였다면 폭주·과금을 막아요.
  - `max_turns`, `timeout_minutes`로 폭주를 막아요.
  - `concurrency`로 같은 PR의 중복 실행을 취소해요.
  - 트리거를 **사람이 명시적으로 부를 때만**(`@ai` 코멘트, label 등)으로 제한할지, 모든 PR 자동으로 둘지 결정하고 근거를 남겨요. 모든 PR 자동은 비용·소음이 빠르게 커져요.

**핵심 판단 (9주차 회수)**

- AI 리뷰는 **비결정적**이라 required 게이트로 두면 위험해요. required로 둘지 advisory(참고)로 둘지 결정하고, "비싸고 변동성 큰 검증을 어디에 둘지" 논리로 근거를 적어요. (기본 권장은 advisory예요.)

**제출물**

- **잘 잡아낸 리뷰 1개** + **헛소리한 리뷰 1개**를 함께 제출해요.
- 헛소리를 줄이려고 **프롬프트를 어떻게 고쳤는지** 적어요(1주차 판별력의 대칭 — AI 리뷰의 오탐도 판별 대상이에요).

**완료조건**

팀 컨벤션이 리뷰 기준으로 명문화되어 있고, 잘 잡은 리뷰와 헛소리를 구분해 프롬프트 개선 근거를 남겼고, (CI에 붙였다면) 안전장치와 게이트 배치 판단이 workflow와 문서에 있어야 해요.

### 🔧 5단계 — AI 지적을 결정적 룰로 승격해요

1주차에서 "머리로 배운 기준을 기계에 새긴다"라고 했어요. 이번엔 **AI(비결정)가 찾은 패턴을 결정적 하네스로 내려서 AI·사람 리뷰 의존을 줄여요.** 이게 AI를 잘 쓴다는 것의 결론이에요.

**요구사항**

- 4단계에서 AI가(또는 10주간 사람 리뷰가) **반복적으로 지적한 것** 중, 결정적으로 판별 가능한 규칙 하나를 골라요. 예: FSD 경계 위반 import, 무의미한 `any`, custom hook에서 URL 파싱 로직 중복, 서버 응답을 Zustand에 복사.
- 그걸 **결정적 게이트로 승격**해요. 아래 중 규칙 성격에 맞는 것 하나면 돼요.

  | 규칙 성격      | 승격 수단                                      |
  | -------------- | ---------------------------------------------- |
  | import 경계    | ESLint `import/no-restricted-paths`            |
  | 특정 안티패턴  | ESLint custom rule 또는 `no-restricted-syntax` |
  | 파일·구조 규칙 | danger.js 또는 CI grep 스크립트                |

- **자가 검증**: 승격한 룰이 위반 코드를 빨간불로 막는지, 정상 코드는 통과시키는지 확인해요(8주차 mutation). 오탐(정상 코드를 막음)이 있으면 룰을 좁혀요.
- **판단 1문단**: 무엇이 AI·사람(맥락 판단)에 남아야 하고, 무엇이 기계(결정)로 내려가야 하는지 적어요. 1주차 책임 모델 표를 이 프로젝트 기준으로 다시 쓰는 셈이에요.

> 💡 모든 AI 지적을 룰로 만들 수 없어요. "설계 냄새"처럼 맥락 판단이 필요한 건 AI·사람에 남는 게 맞아요. 승격 대상은 **결정적으로 참/거짓을 가를 수 있는 것**이에요.

> 🤝 **AI 활용** — ESLint custom rule이나 `no-restricted-syntax` selector, danger.js 스크립트 골격은 AI가 잘 만들어줘요. 대신 **위반/정상 코드로 룰이 진짜 동작하는지는 본인이 자가 검증**하세요. AI가 만든 룰이 오탐을 내는 경우가 흔해요.

**완료조건**

AI(또는 사람)가 반복 지적한 규칙 하나가 결정적 게이트로 내려가 위반을 막고, "무엇을 AI·사람에·무엇을 기계에 두는가"의 판단이 근거와 함께 있어야 해요.

## 💬 함께 생각해 볼 질문 (제출)

아래 질문에 각각 **2~4문장으로 본인의 판단과 근거**를 적어 제출해요. 정답을 맞히는 게 아니라, **왜 그렇게 판단하는지 설명**하는 게 핵심이에요(1주차부터 이어진 "설명할 수 있는가"의 마지막 회수). 이 질문들은 위 단계들과 직접 연결돼요.

1. **E2E를 모든 PR에 required로 걸면 어떤 문제가 생길까?** _(2단계와 연결)_
   - 실행 시간·비용, flaky로 인한 거짓 빨간불, required로 걸었는데 조건부로 실행되지 않아 머지가 막히는 경우까지 생각해봐요. 그래서 E2E는 어디에·언제 두는 게 맞을까?

2. **Lighthouse 점수 하락은 항상 merge blocker여야 할까?** _(3단계와 연결)_
   - 측정 변동성이 큰 지표를 required로 두면 어떤 일이 생길까? "막을 것"과 "참고로만 볼 것"을 어떤 기준으로 가를까?

3. **Preview 환경이 production API를 바라보면 무슨 일이 생길까?** _(3단계 환경 변수 검증과 연결)_
   - 테스트 주문이 실제 데이터에 쌓이거나, 실 결제·실 이메일이 나갈 수 있어요. 환경 변수 검증 게이트가 이런 사고를 어떻게 미리 막을 수 있을까?

4. **AI가 만든 workflow를 그대로 머지하면 어떤 리스크가 있을까?** _(4·5단계 + 공통 보안과 연결)_
   - `permissions` 과다 부여, `pull_request_target` 오용, 캐시 키가 hit 안 되는 구조, 필요한 검증을 스킵하는 path filter… AI 초안을 머지 전에 무엇으로 검증해야 할까?

> 💡 **(심화·선택) rollback은 "이전 버전으로 되돌리기"만으로 끝날까?** DB 마이그레이션, 캐시, 진행 중이던 트랜잭션, feature flag까지 생각하면 되돌리기가 그렇게 단순하지 않아요. 이번 주 산출물(배포 자체는 채점 대상 아님)의 밖이지만, 운영까지 상상해보고 싶으면 함께 답해봐요.

## 🔐 공통 — 워크플로 보안 하드닝

CI는 secrets에 접근하고 코드를 실행해요. 실무에서 CI는 흔한 공격 표면이라, 이번 주 workflow에 아래를 **기본으로** 적용하고 무엇을 왜 했는지 남겨요.

- **최소 권한**: workflow(또는 job)에 `permissions:`를 명시하고 기본을 `contents: read`로 좁혀요. PR에 코멘트를 달아야 하면 그 job에만 `pull-requests: write`를 줘요.
- **third-party action 핀**: 신뢰 못 하는 외부 action은 태그가 아니라 **커밋 SHA로 핀**하는 걸 고려해요(`uses: owner/action@<sha>`). 공식 액션(`actions/*`)은 major 태그도 실무에서 통용돼요 — 어디까지 핀할지 판단하고 근거를 남겨요.
- **`pull_request_target` 주의**: 이 트리거는 fork PR에서도 secrets에 접근 가능해 위험해요. 꼭 필요한 게 아니면 쓰지 말고, 쓴다면 PR 코드를 checkout해 실행하지 않도록 주의해요. (AI 리뷰를 CI에 붙일 때 특히 조심해요.)
- **secrets 노출 금지**: secrets(AI API 키 포함)를 로그로 찍거나 fork PR에서 접근 가능한 자리에 두지 않아요.

## 🤖 AI 활용

- 이번 주는 AI를 **적극 활용**하세요 — workflow YAML 초안, size-limit·validate-env 스크립트, danger.js 골격, ESLint 룰 selector, PR 셀프리뷰, 회고 초안 검토. 도구는 자유예요(Gemini·Claude·Codex·로컬 CLI·구독·무료 챗봇).
- **판단은 직접 해요** — 무엇을 required로 둘지, 예산 임계값을 얼마로 할지, 비싼 검증을 언제 돌릴지, AI 리뷰를 어디에 둘지, 무엇을 결정적 룰로 승격할지. 이 결정을 AI에 넘기면 이번 주에 남는 게 없어요.
- **AI 결과는 본인이 검증해요** — AI가 짚은 병목·만든 룰·리뷰 지적은 로그·자가검증·판별로 확인하고 나서 채택해요. 그게 이번 주 내내 반복되는 원칙이에요.

### CI workflow 리뷰 요청 예시

```text
아래 GitHub Actions workflow를 리뷰해줘.

관점:
1. PR에서 main에 깨진 코드가 들어가는 것을 막기에 충분한가
2. concurrency 그룹이 main 배포까지 취소하지 않는가
3. 캐시 키가 실제로 hit 될 구조인가, path filter가 필요한 검증을 스킵하지 않는가
4. required로 둔 검증이 조건부 실행과 충돌해 PR이 못 머지되지 않는가
5. permissions가 최소 권한인가, secrets가 노출될 자리에 있지 않은가
```

**1단계 / CI 측정·최적화**

- [x] 같은 조건(cold/warm)에서 재고 병목을 로그로 지목해 그것만 줄였는가
- [x] `concurrency` 그룹이 main 배포까지 취소하지 않는가

**2단계 / 조건부 실행**

- [x] 초과 PR이 PR 화면에서 원인까지 보이며 빨간불로 막히는가

**4·5단계 / AI 리뷰와 룰 승격**
