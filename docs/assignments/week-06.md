# 6주차 — 프론트엔드 시스템 설계: FSD로 변경 반경을 설계한다

> 5주차까지 만든 커머스의 동작은 유지하면서, **"이 파일은 어디에 두어야 하는가?"와 "이 변경은 어디까지 퍼지는가?"에 답할 수 있는 구조**로 바꿉니다.

## 왜 이 과제를 하는가

- `components / hooks / services` 분리는 한 파일 안의 관심사를 나누는 데는 유용하지만, 하나의 기능에 속한 코드가 여러 폴더로 흩어집니다.
- FSD의 핵심은 폴더 이름이 아니라 **비즈니스 역할에 따른 응집**, **상위→하위 의존 방향**, **슬라이스의 공개 API**입니다.
- 모든 레이어를 만드는 것이 좋은 설계는 아닙니다. **필요 없는 레이어를 만들지 않는 결정도 설계**입니다.
- 5주차에 정한 서버·URL·클라이언트·로컬 상태의 Source of Truth는 폴더를 옮긴다는 이유로 달라지지 않습니다.

이 과제는 리팩토링입니다. 홈·상품 목록·검색·카테고리·정렬·페이지네이션·장바구니·위시리스트의 **기존 동작을 먼저 보존**해야 합니다.

## 이번 주 과제

| #   | 과제                                                                               | 완료 기준                                                                         |
| --- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 1   | **RADIO + RFC** — 코드 전에 현재 문제와 목표 구조를 설계                           | `docs/rfc/week06-fsd.md` (RFC 문서)파일을 생성하여 fsd 구조로 변경 전 커밋에 포함 |
| 2   | **FSD 전환** — 역할과 의존 방향을 기준으로 점진적 마이그레이션                     | 기존 기능 보존 + 각 파일의 이동 근거 기록                                         |
| 3   | **Public API 결정** — barrel file과 Public API의 차이를 근거로 경계 통제 방식 선택 | 사용/미사용 어느 쪽이든 의도와 근거 기록                                          |
| 4   | **에러 처리 경계 설계** — 복구 가능한 오류와 예상 밖 오류를 분리                   | 에러 처리 표 + 인라인 재시도 + 라우트 에러 경계 검증                              |

| 6   | **PR** — 설계와 결과를 함께 리뷰 요청                                              | Before/After 구조, 검증 결과, AI 사용 부분 표기                                   |

의존 규칙을 도구로 강제하는 **의존성 하네스(A)**, 새 요구사항을 실제로 추가하는 **변경 반경 실험(B)**은 Advanced 선택 과제입니다.

## 0단계 — 동작 기준선부터 고정한다

폴더를 옮기기 전에 아래 동작을 직접 확인하고 RFC에 결과를 남깁니다.

- 홈과 상품 목록의 정상·로딩·에러·빈 상태
- 검색·카테고리·정렬·페이지네이션
- URL 공유·새로고침·뒤로/앞으로 가기
- 홈과 목록에서 장바구니·위시리스트 상태 동기화, 페이지 이동 중 Zustand 상태·헤더 개수 유지
- `pnpm check` 통과

리팩토링 중 발견한 기존 버그를 고쳐도 됩니다. 다만 구조 변경과 기능 변경을 같은 커밋에 섞지 말고, `재현 방법 · 원인 · 수정 위치 · 검증 결과`를 따로 기록합니다.

## 1단계 — RADIO로 RFC를 먼저 작성한다

`docs/rfc/week06-fsd.md`에 아래를 작성합니다. 정답 폴더 트리를 복사하는 문서가 아니라 **내 코드에서 내린 결정**을 설명하는 문서여야 합니다.

- **R — Requirements** — 5주차까지의 기능·비기능 요구사항, 이번에 반드시 보존할 동작, **이번 주에 하지 않을 것과 그 이유**
- **A — Architecture** — 현재 구조에서 실제로 겪는 문제 3개 이상, 현재/목표 폴더 트리, 사용할 레이어만 선택한 근거, 허용/금지 import 예시, 단계별 마이그레이션 계획과 검증 방법
- **D — Data Model** — 아래 상태 분류표를 새 구조에 맞게 갱신
- **I — Interface** — 각 슬라이스가 공개할 값과 숨길 구현 세부, `ProductCard`와 장바구니·위시리스트 행위의 조합 방법, Public API 사용 여부와 방식
- **O — Optimization** — TanStack Query 캐시 정책 유지/변경 근거, 로딩·에러 경계 범위, 이번 주에 하지 않을 최적화와 이유

### D — 상태 분류표 (5주차 표를 새 구조로 갱신)

| 상태                | Source of Truth     | 소유 슬라이스/레이어 | 소비하는 곳        | 이동 후에도 중복 저장하지 않는 방법 |
| ------------------- | ------------------- | -------------------- | ------------------ | ----------------------------------- |
| 상품 조회 결과      | 서버/TanStack Query | 직접 결정            | 홈, 상품 목록      | 직접 작성                           |
| 검색·정렬·페이지    | URL/nuqs            | 직접 결정            | 상품 목록          | 직접 작성                           |
| 장바구니·위시리스트 | Zustand             | 직접 결정            | 헤더, 상품 행위 UI | 직접 작성                           |
| Dialog 열림 여부    | React 로컬 상태     | 직접 결정            | 해당 UI            | 직접 작성                           |

> 폴더를 옮기면서 서버 응답을 Zustand에 복사하거나, URL 상태를 별도 `useState`에 동기화하면 안 됩니다.

### A — 파일 매핑표 (이동하는 파일 + 그 자리에 남기는 파일)

| 현재 위치 | 목표 위치 | 레이어 / 슬라이스 / 세그먼트 | 이동 또는 유지하는 이유 |
| --------- | --------- | ---------------------------- | ----------------------- |
| 직접 작성 | 직접 작성 | 직접 작성                    | 직접 작성               |

### A — 애매한 파일 5개 이상 결정표

분류가 갈리는 파일을 골라 후보를 비교하고 최종 결정과 기준을 남깁니다.

| 대상                                     | 후보 A                   | 후보 B                          | 최종 결정 | 기준                                        |
| ---------------------------------------- | ------------------------ | ------------------------------- | --------- | ------------------------------------------- |
| `ProductCard`                            | `entities/product/ui`    | `widgets/product-card`          | 직접 결정 | 재사용 범위와 포함한 비즈니스 행위          |
| 상품 목록 queryOptions                   | `entities/product/api`   | 상품 목록 페이지의 `api`        | 직접 결정 | 여러 페이지에서 재사용되는가                |
| 장바구니 store                           | `entities/cart/model`    | 장바구니 행위 feature의 `model` | 직접 결정 | 상태가 나타내는 도메인과 행위의 경계        |
| `src/types/commerce.ts`의 `Product` 타입 | `entities/product/model` | `shared/types` 유지             | 직접 결정 | 도메인 타입을 한 창고에 모을 때 생기는 결합 |

`src/types/commerce.ts`처럼 여러 도메인의 타입이 모인 통짜 파일은 그대로 옮기는 것도, 분해하는 것도 결정입니다. 어느 쪽이든 "이 타입의 소유자가 누구인가"에 답하고 근거를 남깁니다.

## 2단계 — FSD로 점진적으로 전환한다

### 의존 방향 규칙

```
_app → _pages → widgets → features → entities → shared
  (상위: 조합과 책임이 큼)                  (하위: 기반과 재사용)
```

- 다른 슬라이스는 **자기보다 아래 레이어만** import한다.
- 같은 레이어의 다른 슬라이스를 직접 import하지 않는다. 같은 슬라이스 안 세그먼트끼리는 협력한다.
- `shared`와 `_app`은 비즈니스 슬라이스로 나누지 않는다. `processes` 레이어는 사용하지 않는다.
- 필요한 레이어·세그먼트만 만든다. 빈 폴더와 미사용 `index.ts`는 만들지 않는다.
- 세그먼트는 목적(`ui / model / api / lib / config`)을 드러낸다. `components / hooks / types / utils`처럼 파일 종류만 반복하지 않는다. `shared/lib`을 이름 없는 유틸 창고로 만들지 않는다.

각 레이어의 판단 기준(어떤 질문을 던지는가)은 강의 자료의 FSD 섹션을 참고합니다.

### Next.js App Router에서의 명명 규칙 (이번 과제 공통)

`src/app`은 **Next.js 라우팅 디렉터리**입니다. FSD App 레이어와 이름은 같아도 역할이 다릅니다.

- `src/app/**`의 `page.tsx`·`layout.tsx`·`loading.tsx`·`error.tsx`는 **얇은 라우팅·조합 진입점**으로 둔다. 필요하면 `_pages` 슬라이스의 페이지 컴포넌트를 가져와 렌더링한다.
- FSD App/Pages 레이어가 필요하면 예약 디렉터리와 구분되도록 `src/_app`·`src/_pages`를 쓴다. **`src/pages`는 만들지 않는다** (Pages Router로 오인됨).
- `src/app/api`의 Route Handler·mock fixture는 전환 범위에서 제외해도 된다. 이동한다면 프론트엔드와 mock 백엔드의 경계를 RFC에 설명한다.

### 의존 방향을 `ProductCard` 조합으로 증명한다

`entities/product`가 `features/add-to-cart`나 `features/toggle-wishlist`를 import하면 하위가 상위를 아는 **역방향 의존**입니다. 상품 표현과 사용자 행위를 함께 보여줘야 한다면 `ProductCard`가 action 영역을 받도록 설계하고 **widget 또는 page에서 조합**합니다. 다른 합성 방법도 되지만 `entities → features` 역방향 import는 허용하지 않습니다.

## 3단계 — Public API를 결정한다

슬라이스 루트의 `index.ts`는 **필수가 아닙니다.** 만들기 전에 둘을 구분합니다.

- **barrel file** — 경로를 줄이려고 내부를 습관적으로 재수출하는 파일. 경계 의도가 없고 `export *`가 쌓이면 이름 충돌·순환 의존·번들 비용만 남는다.
- **Public API** — "외부가 알아도 되는 것은 이것뿐"이라는 **계약**. 같은 `index.ts`라도 무엇을 숨기려고 만들었는지가 다르다.

이 차이를 바탕으로 경계 통제 방식을 직접 결정하고, **어느 쪽이든 그 의도를 RFC에 기록**합니다.

## 4단계 — API 에러와 렌더링 에러의 경계를 설계한다

먼저 아래 표를 자신의 프로젝트 기준으로 작성합니다.

| 실패 유형                     | 처리 위치 | Error Boundary로 전파하는가 | 사용자 UI | 재시도 방법 | 이 경계를 선택한 이유 |
| ----------------------------- | --------- | --------------------------- | --------- | ----------- | --------------------- |
| 상품 목록 조회 실패           | 직접 작성 | 직접 작성                   | 직접 작성 | 직접 작성   | 직접 작성             |
| 잘못된 검색 조건(4xx)         | 직접 작성 | 직접 작성                   | 직접 작성 | 직접 작성   | 직접 작성             |
| 예상하지 못한 렌더링 오류     | 직접 작성 | 직접 작성                   | 직접 작성 | 직접 작성   | 직접 작성             |
| 장바구니 행위의 비즈니스 오류 | 직접 작성 | 직접 작성                   | 직접 작성 | 직접 작성   | 직접 작성             |

현재 구현에서 발생할 수 없는 실패라면 억지 처리 코드를 만들지 말고 `해당 없음 · 향후 어떤 변화가 생기면 필요한가`를 기록합니다.

다음을 구현하고 직접 실패를 재현합니다.

1. 조회 실패는 나머지 화면을 모두 가리지 않는 범위에서 표시하고, 전체 새로고침 없이 재시도할 수 있어야 한다.
2. `throwOnError`로 **경계에 전파할 에러와 인라인으로 처리할 에러의 기준**을 정한다(예: 5xx는 경계로, 4xx·빈 결과는 화면 안에서). 이 기준은 위 표의 `전파하는가` 열과 일치해야 한다.
3. 적절한 route segment에 `error.tsx`를 두고 예상 밖 렌더링 오류의 fallback과 `reset`을 구현한다.
4. API 응답을 공통 에러 타입으로 변환한다면 네트워크·HTTP·비즈니스 오류를 구분하고, `shared`에 특정 화면의 문구·행위를 넣지 않는다.
5. Error Boundary가 이벤트 핸들러·비동기 콜백 오류를 자동으로 잡지 못한다는 점을 설명하고, 그 오류를 어디서 처리할지 기록한다.
6. route `loading.tsx`/Suspense와 Query `isPending`이 각각 어느 로딩 범위를 맡는지 구분한다. 하나만 쓴다면 다른 하나가 불필요한 이유를 기록한다.

검증용 `scenario`는 mock API 전용 제어값입니다. 사용자 URL 상태나 `ProductListQuery`에 포함하지 않습니다. 임시 `throw`로 `error.tsx`를 검증했다면 검증 후 반드시 제거합니다.

## 5단계 — 삭제 시나리오로 자가 검증한다

폴더 이동이 끝나면 코드를 수정하지 않고 아래 사고 실험에 답합니다. 기능별 응집이 실제로 됐는지 확인하는 가장 빠른 리트머스입니다.

- **"위시리스트 기능을 통째로 제거한다면"** — 삭제할 폴더·파일 목록과 삭제 후 수정이 필요한 파일 목록을 적는다. 삭제 대상이 여러 레이어에 흩어져 grep 없이 다 찾을 수 없다면 응집 실패다.
- **"신상품 뱃지를 상품 카드에 추가한다면"** — 터치할 파일 목록을 적는다. 자신 있게 예측할 수 없다면 경계 설계를 다시 본다.

결과를 RFC에 기록합니다. 파편화를 발견했다면 전부 즉시 고치기보다, 이번 주에 고칠 것과 남길 것을 근거와 함께 결정합니다.

## Advanced — 선택

필수가 아닙니다. 기본 과제를 먼저 완성한 뒤 여유가 있으면 선택합니다. 선택 이유·추가한 복잡도·검증 결과를 함께 기록합니다.

### A. 의존성 하네스 — 구조 규칙을 기계에 새긴다

ESLint 규칙·아키텍처 테스트·FSD 정적 분석 도구 중 하나로 최소 두 규칙을 자동 검증합니다.

1. 하위 레이어가 상위 레이어를 import하지 않는다.
2. 같은 레이어의 서로 다른 슬라이스가 직접 import하지 않는다.

### B. 변경 반경 실험 — 작은 요구사항을 실제로 추가한다

5단계 사고 실험을 실제 구현으로 증명합니다. 아래 중 하나를 새 구조 위에 추가합니다.

- 상품 목록의 **검색·카테고리·정렬 조건 전체 초기화**
- 비로그인 **장바구니 전체 비우기** 또는 **위시리스트 전체 비우기**

구현 전에 RFC에 예상을 먼저 씁니다(새 feature 슬라이스가 필요한가 / 수정될 슬라이스·Public API / 예상 import 방향). 구현 후 실제 diff와 비교합니다.

| 관점              | 구현 전 예상 | 실제 결과 | 차이가 난 이유 |
| ----------------- | ------------ | --------- | -------------- |
| 수정한 슬라이스   | 직접 작성    | 직접 작성 | 직접 작성      |
| 변경한 Public API | 직접 작성    | 직접 작성 | 직접 작성      |
| 새로 생긴 의존    | 직접 작성    | 직접 작성 | 직접 작성      |

새 행위는 page 또는 widget에서 조합합니다. feature가 다른 feature를 직접 import하거나 관련 없는 `shared` 파일을 여럿 수정했다면 경계를 다시 검토합니다.

## FSD 이해 확인 질문

아래 질문에 PR 본문 또는 RFC에서 각각 2~4문장으로 답합니다.

1. `ProductCard`가 찜 버튼을 직접 import하면 어떤 의존 규칙을 어기며, 어디에서 조합해야 하는가?
2. 한 페이지에서만 쓰는 검색 로직도 반드시 feature여야 하는가? 내 프로젝트에서는 어떻게 결정했는가?
3. `formatPrice`는 항상 `shared/lib`인가? 통화·회원 등급·상품 정책이 포함되면 결정이 어떻게 달라지는가?
4. 두 feature가 협력해야 할 때 직접 import하지 않고 어떤 상위 레이어에서 조합했는가?
5. 폴더 이동 후에도 TanStack Query 데이터와 Zustand 데이터를 서로 복사하지 않은 이유는 무엇인가?
6. barrel file과 Public API는 무엇이 다른가? 내 프로젝트에서는 어느 쪽을 선택했고 그 의도는 무엇인가?
