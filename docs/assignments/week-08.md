# 8주차 — 프론트엔드 테스트: 무엇을 지킬지 먼저 정해요

> **Phase**: 엔지니어링 레벨업

> 💡 이번 주에는 커버리지 숫자를 올리지 않아요. 프론트엔드는 지켜야 할 스펙이 어디에도 적혀 있지 않으니, 무엇을 어떻게 검증할지 먼저 정하고 그것만 테스트로 고정해요. 그리고 내가 쓴 테스트가 진짜로 무언가를 잡는지 직접 확인해요.

## 제공되는 것과 실행 환경

- `.nvmrc`와 `package.json#packageManager`에 지정된 Node.js·pnpm 환경을 사용해요.
- **테스트 도구는 하나도 설치되어 있지 않아요.** 0단계에서 직접 세웁니다.
- 지금 레포에는 아래 5개 테스트가 있고, 전부 **DOM이 필요 없는 테스트**예요. 이번 주 작업으로 이 5개가 깨지면 안 돼요.

  ```
  src/app/api/home/route.test.ts
  src/app/api/products/route.test.ts
  src/app/api/_data/commerce.test.ts
  src/app/performance-lab/inp/products.test.ts
  src/examples/week-07-performance/HeroSection.test.tsx
  ```

- mock 백엔드는 `/api/home`, `/api/products`이고 `?scenario=empty|error|slow`로 **빈 결과·에러·지연**을 만들 수 있어요. 응답 계약은 5주차 문서와 `src/types/commerce.ts`에 있어요.
- mock API는 **production 실행에서 500ms 고정 지연**이 있어요. E2E는 실제 라우트를 타니 이 지연을 그대로 만나고, 통합 테스트는 MSW 핸들러가 지연을 정해요.
- 검증 명령은 아래와 같아요. `pnpm check`는 테스트·lint·타입체크·빌드를 순서대로 실행해요.

  ```bash
  pnpm test
  pnpm check
  ```

- GitHub Actions는 pull request와 `main` push에서 같은 `pnpm check`를 실행해요. Playwright가 설치되어 있으면 CI가 Chromium을 자동으로 받아옵니다.

## 이번 주 범위

- **환경과 모킹 경계** — DOM이 필요한 테스트와 필요 없는 테스트를 함께 돌리고, 네트워크를 어디서 자를지 정해요.
- **설계** — 주어진 검증 항목을 단위·통합·E2E 중 어디로 다룰지 정하고 근거를 남겨요.
- **구현** — 정한 대로 전부 구현해요.
- **자가 검증** — 구현을 일부러 망가뜨려서, 내 테스트가 그걸 잡는지 확인해요.

## 🤖 AI 활용: 테스트 설계 리뷰

AI에게 **"테스트 짜줘"라고 하지 않아요.** 화면 하나를 주고 사용자 시나리오 후보를 뽑게 하는 건 괜찮지만, 무엇이 공개 동작이고 무엇이 구현 세부사항인지는 **직접 판단해서 1단계 문서에 적어요.**

셋업·픽스처·MSW 핸들러 같은 반복 코드는 AI에게 맡겨도 돼요. 다만 **단언(expect)의 내용과 모킹 경계는 직접 정해요.** 그게 곧 "무엇을 지킬 것인가"라서 넘기면 안 되는 결정이에요.

AI가 만든 테스트를 그대로 받았다면 3단계에서 반드시 검증하세요. 통과하는 테스트를 만드는 건 쉽고, 아무것도 안 잡는 테스트를 만드는 건 더 쉬워요.

## 📝 Implementation Quest

### 🧰 0단계 — 테스트 환경과 모킹 경계를 세워요

**설치**

| 패키지 | 역할 |
| --- | --- |
| `@testing-library/react` | 컴포넌트를 그리고 찾기 |
| `@testing-library/user-event` | 클릭·입력 재현 |
| `@testing-library/jest-dom` | DOM matcher |
| `jsdom` 또는 `happy-dom` | DOM 환경 |
| `msw` | 네트워크 요청 가로채기 |
| `@playwright/test` | E2E |

**요구사항**

- 지금 레포의 테스트 5개는 DOM이 필요 없어서 `node` 환경에서 돌고 있어요. 컴포넌트 테스트는 DOM이 필요하고요. **두 종류가 한 명령으로 함께 통과해야 해요.**
- 이때 **전부 DOM 환경으로 돌리지 않아요.** 그렇게 해도 통과는 하지만, DOM이 필요 없는 테스트까지 매번 브라우저 흉내 환경을 세우게 돼요. 테스트가 늘수록 이 비용이 쌓여요. **필요한 테스트만 DOM 환경에서 돌게** 하고, 고른 방식과 근거를 남겨요.
- 나눈 뒤에 `vitest run`의 출력에서 **환경 셋업에 걸린 시간**을 전부 DOM으로 돌렸을 때와 비교해 기록해요.
- MSW 서버를 켜고 끄는 setup을 만들고, **모킹되지 않은 요청이 조용히 나가지 않게** 막아요.
- **앱 코드의 HTTP 클라이언트를 직접 모킹하지 않아요.** `fetch`나 `axios`를 바꿔치기하는 방식이 남아 있으면 안 돼요. 요청은 실제로 나가고 MSW가 가로채는 구조여야 해요.
- Playwright는 **production build 위에서** 돌게 설정해요.
- E2E를 `pnpm test`에 넣을지 별도 명령으로 둘지 결정하고 근거를 남겨요.

> 💡 상대 경로 요청이 안 잡히면 DOM 환경의 base URL을 확인해 보세요. CSS 파일 import가 테스트에서 어떻게 처리되는지도 한 번 봐두면 2단계에서 안 헤매요.

**완료조건**

`pnpm check` 한 번에 기존 5개와 새 컴포넌트 테스트가 모두 통과하고, 앱 코드의 HTTP 클라이언트를 직접 바꿔치기한 곳이 남아 있지 않아요.

### 🗺️ 1단계 — 어떻게 검증할지 정해요

아래 항목들을 **적절한 테스트 방법론을 골라 검증해주세요.** 그 방법론을 고른 이유도 함께 적어주세요.

`docs/rfc/week08-test-plan.md`에 작성하고, **테스트 코드보다 먼저 커밋**해요.

**1. 검증 방법을 정해요**

| 검증 대상 | 방법론 | 그렇게 정한 이유 | 빨간불이 되면 알게 되는 것 |

세 번째 항목은 **직접 고르세요.** 내 코드에서 부수효과 없는 로직 하나를 골라 대상에 적고, 왜 그걸 골랐는지 이유 칸에 씁니다.

**2. 애매했던 판단을 남겨요**

표를 채우다 보면 **어느 쪽이든 될 것 같은 항목**이 나와요. 그중 두 개를 골라, 왜 그쪽으로 정했는지 문단으로 씁니다. 다른 쪽을 골랐다면 무엇이 달라졌을지도요.

**3. 이 목록 밖은 어떻게 할지 정해요**

위 15개는 이번 주에 전부 해요. 그 밖에도 내 코드에는 테스트할 만한 것들이 남아 있을 거예요. 그중에서

- **다음에는 하면 좋겠다** 싶은 것 하나
- **앞으로도 안 하겠다** 싶은 것 하나

를 골라, 변경 빈도와 실패 비용을 근거로 이유를 적어요. 전부 테스트하겠다는 계획은 계획이 아니에요.

**이번 단계에서는 테스트 코드를 쓰지 않아요. 설계만 하고, 구현은 2단계부터 해요.**

> 💡 "빨간불이 되면 알게 되는 것"에 *"코드가 잘 돌아간다"*, *"컴포넌트가 렌더된다"* 같은 답이 나오면 그 항목은 다시 보세요. 그 테스트는 통과해도 보장하는 게 없어요.

**완료조건**

이 문서만 읽고도 2·3단계에 무엇이 들어갈지 예측할 수 있고, 목록 밖의 영역을 어떻게 할지에 대한 판단이 문서 안에 있어요.

### 🧪 2단계 — 정한 대로 구현해요

1단계 표의 **15개 항목을 전부 구현해요.** 방법론은 1단계에서 정한 대로 갑니다.

**공통**

- 15개 항목 **전부**. 다만 내 구현에 그 기능 자체가 없다면(예: 해당 UI를 만들지 않았다면) 그 사실을 1단계 문서에 적고 넘어가요.
- 각 항목마다 **정상 케이스와 경계 케이스를 함께** 넣어요.
- 테스트 이름은 **조건과 결과가 드러나게** 써요. `works`, `renders`, `should be true`는 쓰지 않아요.
- 파일을 **단독으로 돌리든 순서를 바꿔 돌리든** 같은 결과가 나와야 해요.

**단위로 정한 항목**

- **DOM 없이 통과해야 해요.** 컴포넌트를 렌더해서 통과시켰다면 그건 1단계 배치와 어긋난 거예요.

**통합으로 정한 항목**

- 네트워크는 **MSW로 가로채요.** HTTP 클라이언트를 직접 바꿔치기하지 않아요.
- 기본 핸들러에는 **성공 경로만** 두고, 실패·지연·빈 결과는 **그 테스트 안에서** 덮어써요.
- 요소는 **사용자가 인식하는 방식**으로 찾아요. `getByTestId`를 썼다면 왜 다른 방법으로 안 됐는지 남겨요.
- **모든 검증을 `waitFor`로 감싸지 않아요.** 첫 대기만 비동기로 하고 나머지는 동기로 확인해요.
- 전역 스토어와 `localStorage`가 **다음 테스트로 넘어가지 않게** 해요.

**E2E로 정한 항목**

- **production build 위에서** 돌려요. 개발 서버로만 통과하는 건 인정하지 않아요.
- `sleep`으로 기다리지 않아요. **조건 기반 대기만** 써요.
- 셀렉터는 **역할과 이름 기반**으로 정리해요. `codegen`으로 시작해도 되지만 생성된 셀렉터를 그대로 두지 않아요.

**하지 말 것**

- `it.skip`이나 주석 처리로 비활성화
- `toBeTruthy()`처럼 아무것도 보장하지 않는 단언
- 스냅샷으로 검증 대체
- 통과시키려고 구현의 기능을 지우기

> 💡 에러 테스트가 자꾸 타임아웃 난다면 서버 상태 라이브러리의 **재시도 정책**을 확인해 보세요.

**완료조건**

15개 항목이 전부 구현되고 `pnpm check`가 통과해요. 1단계에서 정한 방법론과 실제 구현이 어긋난 곳이 없어요.

### 🔬 3단계 — 내 테스트가 진짜 뭘 잡는지 확인해요

통과하는 테스트를 만드는 건 쉬워요. 아무것도 안 잡는 테스트를 만드는 건 더 쉽고요.

2단계에서 쓴 테스트가 정말로 무언가를 지키고 있는지, **구현을 일부러 망가뜨려서** 확인해요.

**요구사항**

- **1단계에서 나눈 각 방법론마다 최소 하나씩** 실험해요. 단위·통합·E2E에서 각각 하나 이상이요.
- 실험은 **구현 한 곳만** 바꿔요. 조건을 뒤집거나, 호출을 지우거나, 경계 부호를 바꾸는 식으로요. **테스트 코드는 건드리지 않아요.**
- 실험마다 아래를 기록해요.

  | # | 망가뜨린 곳 | 어떻게 바꿨나 | 결과 | 실패한 테스트 |
  | --- | --- | --- | --- | --- |
  | 직접 작성 | 직접 작성 | 직접 작성 | 잡힘 / 살아남음 | 직접 작성 |

- **잡힌 경우** — 실패 메시지만 보고 원인을 짐작할 수 있었는지 함께 적어요. 못 알아봤다면 테스트 이름이나 단언을 손볼 자리예요.
- **살아남은 경우** — 그 테스트를 고치고, **왜 못 잡았는지** 적어요.
- 실험이 끝나면 구현을 원래대로 되돌려요. 망가뜨린 코드가 커밋에 남으면 안 돼요.

> 💡 세 실험이 전부 한 번에 잡혔다면, 쉬운 곳만 고른 게 아닌지 다시 보세요. 눈에 잘 안 띄는 분기나 경계에서 골라야 이 실험이 의미가 있어요.

> 💡 E2E는 한 번 도는 데 오래 걸려요. 실험 대상을 미리 정해두고 한 번에 확인하세요.

**완료조건**

방법론마다 하나 이상의 실험 기록이 있고, 살아남은 변경이 있었다면 그에 대한 대응까지 적혀 있어요. 그리고 최종 커밋에 망가뜨린 코드가 남아 있지 않아요.

### ⚡ Advanced — 자가 검증을 기계에 맡겨요

Basic을 완료한 뒤 선택해요. 3단계에서 손으로 한 실험을 전수로 돌립니다.

**요구사항**

- `@stryker-mutator/core`와 `@stryker-mutator/vitest-runner`를 설치하고 설정해요.
- **변형 대상 범위를 좁혀요.** 통합 테스트가 걸리는 파일까지 넣으면 끝나지 않아요. 1단계에서 단위로 분류한 로직 위주로 한정하고, 그렇게 정한 근거를 남겨요.
- 살아남은 변형 중 **의미 있는 것 2개 이상**을 골라 테스트를 보강해요.
- **죽일 수 없는 변형**이 있으면 왜 그런지 적어요. 의미가 바뀌지 않는 변형은 원래 못 죽여요.
- 3단계에서 손으로 한 실험과 비교해서, **도구가 추가로 찾아준 것**이 있으면 적어요.
- 전체 실행 시간을 기록하고, **이 도구를 상시로 쓸지 말지** 판단을 남겨요.

> 💡 점수 100%를 목표로 삼지 않아요. 살아남은 변형을 하나하나 보면서 "이건 진짜 문제인가"를 판단하는 게 목적이에요.

> 💡 `Cannot find TestRunner plugin "vitest"`가 나오면 설정에서 플러그인을 명시해야 하는 경우예요. pnpm 환경에서 자동 탐색이 안 될 수 있어요.

**완료조건**

범위를 한정한 근거가 있고, 보강한 테스트 2개 이상과 실행 시간·상시 사용 판단이 기록되어 있어요.

## ✍️ Technical Writing Quest — 무엇을 어떻게 지키기로 했는지 설명해요

제출물에는 테스트 개수나 커버리지 숫자 대신, **어떤 결정을 왜 내렸는지**를 적어요.

환경을 어떻게 분리했고 왜 그 방식을 골랐는지, 모킹 경계를 어디에 뒀는지 씁니다. 앱 코드의 HTTP 클라이언트를 직접 바꿔치기하던 곳이 있었다면 MSW로 옮기는 과정에서 무엇이 달라졌는지도요.

1단계 표에서 애매했던 판단 두 개를 어떻게 정했는지, 다른 쪽을 골랐다면 무엇이 달라졌을지 설명해요. 목록 밖에서 다음에 할 것과 앞으로도 안 할 것을 어떤 근거로 나눴는지도 함께요.

2단계에서 `getByTestId`를 썼다면 왜 다른 방법으로 안 됐는지, 격리는 어떻게 확보했는지 적어요. E2E와 통합의 역할을 어떻게 나눴는지도 설명해요.

3단계 실험은 **살아남은 변경을 숨기지 마세요.** 그게 이번 주에 가장 값어치 있는 기록이에요. 왜 못 잡았고 어떻게 고쳤는지 남기면 됩니다.

AI를 쓴 부분은 어디에 어떻게 썼는지, 그리고 단언과 모킹 경계는 직접 정했는지 밝혀요.

## ✅ Checklist

**0단계 / 환경과 모킹 경계**

- [ ] 기존 테스트 5개가 그대로 통과하는가
- [ ] DOM 테스트와 DOM 없는 테스트가 `pnpm check` 한 번으로 함께 돌아가는가
- [ ] DOM이 필요 없는 테스트가 DOM 환경에서 돌고 있지 않은가
- [ ] 환경 분리 방식을 선택한 근거가 남아 있는가
- [ ] 환경 셋업 시간을 전부 DOM으로 돌렸을 때와 비교해 기록했는가
- [ ] 모킹되지 않은 요청이 조용히 나가지 않게 막았는가
- [ ] 앱 코드의 HTTP 클라이언트를 직접 바꿔치기한 곳이 없는가
- [ ] Playwright가 production build 위에서 돌아가는가
- [ ] E2E를 어느 명령에 넣을지 정하고 근거를 남겼는가

**1단계 / 설계**

- [ ] 15개 항목 전부에 방법론과 이유를 적었는가
- [ ] 세 번째 항목(순수 로직)을 직접 골랐는가
- [ ] "빨간불이 되면 알게 되는 것"이 항목마다 채워져 있는가
- [ ] 애매했던 판단 두 개를 문단으로 설명했는가
- [ ] 목록 밖에서 "다음에 할 것"과 "앞으로도 안 할 것"을 하나씩 골랐는가
- [ ] 이 문서가 테스트 코드보다 먼저 커밋되었는가

**2단계 / 구현**

- [ ] 15개 항목이 전부 구현되었는가 (구현에 없는 기능은 그 사실이 문서에 있는가)
- [ ] 각 항목에 정상 케이스와 경계 케이스가 함께 있는가
- [ ] 테스트 이름만 읽고 무엇이 깨졌는지 알 수 있는가
- [ ] 단위로 정한 항목이 DOM 없이 통과하는가
- [ ] 통합 항목의 네트워크를 MSW로 가로챘는가
- [ ] 기본 핸들러에 성공 경로만 두고 예외는 테스트 안에서 덮었는가
- [ ] `getByTestId`를 썼다면 그 이유가 남아 있는가
- [ ] 모든 검증을 `waitFor`로 감싸지 않았는가
- [ ] 파일을 단독으로 돌려도 통과하는가
- [ ] E2E가 `sleep` 없이 조건 기반 대기만 쓰는가
- [ ] 1단계에서 정한 방법론과 실제 구현이 일치하는가

**3단계 / 자가 검증**
