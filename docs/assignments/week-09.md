# 9주차 — 인증과 E2E: 비싼 테스트를 어디에 붙일지 정해요

> **Phase**: 엔지니어링 레벨업

> 💡 E2E는 비쌉니다. 통합 테스트가 200ms면 E2E는 20초고, UI가 바뀔 때마다 고칠 곳이 생겨요. 그래서 이번 주에는 E2E를 많이 만들지 않아요. **어디에 붙일지 근거를 만들고, 그 근거대로만 만듭니다.**

## 일정과 범위

2주 과제예요. 권장 배분은 앞주에 1~3단계, 뒷주에 4~5단계입니다.

- **인증 구현** — 스타터가 인증 API를 제공해요. 프론트엔드를 만듭니다.
- **이벤트 계측** — 사용자 행동을 기록하고, 그 로그로 E2E 대상을 정할 근거를 만듭니다.
- **E2E 범위 설계** — 붙일 곳과 안 붙일 곳을 정하고 이유를 남깁니다.
- **E2E 구현** — 정한 것만 만듭니다.
- **자가 검증** — 인증 구현을 일부러 망가뜨려서 E2E가 잡는지 확인합니다.

## 제공되는 것

8주차에서 세운 테스트 환경(node · jsdom 분리, MSW 경계, production build 위 Playwright)을 그대로 씁니다. 바꿨다면 이유를 남겨요.

### 인증 API

```
POST   /api/auth/login    { email, password }
       200 { user: { id, name, email } } + Set-Cookie
       401 { message }   자격 증명 불일치
       400 { message }   본문 형식이 잘못됨
POST   /api/auth/logout   204, 본문 없음. 세션 쿠키 제거
GET    /api/auth/me       200 { user } | 401 { message }

POST   /api/orders        { items: [{ productId, quantity }] }
       201 { order: { id, createdAt, items } } | 401
       400 { message }   빈 목록 · 없는 상품 id · 수량이 1 미만이거나 정수가 아님
GET    /api/orders        200 { orders } | 401
```

- 세션은 서명된 httpOnly 쿠키(`session`)예요. 서버에 세션 저장소가 없습니다.
- 응답 타입은 `src/app/api/_data/auth.ts`에 함께 있어요. 본인 구조에 맞는 곳으로 옮겨도 됩니다.
- 인증 API는 **다른 모듈에 의존하지 않아요.** 상품 id는 형식만 확인하고(`p1` ~ `p30`), 주문 응답에 금액은 없어요. 금액을 화면에 보여주려면 본인 상품 데이터로 계산하세요.
- 회원가입은 없어요. 계정 8개가 준비되어 있습니다. `looper1@loopers.dev`부터 `looper8@loopers.dev`까지, 비밀번호는 모두 `looper1234`예요.
- 계정이 8개인 이유는 4단계에서 쓰게 돼요.
- 세션 TTL은 1시간이에요. **만료를 시간으로 재현하지 않습니다.** 아래 시나리오를 쓰세요.

> ⚠️ 스타터 라우트는 `src/app/api/**`로 들어옵니다. **App Router를 레포 루트 `app/`으로 옮긴 사람은 라우트 파일도 같이 옮겨야 해요.** 옮기지 않으면 Next가 그 파일을 무시해서 요청이 404가 나는데, **테스트는 그대로 통과합니다.** 테스트가 라우트 함수를 직접 import하기 때문이에요.
>
> 확인하는 방법은 이렇습니다. `pnpm build` 출력의 Route 목록에 `/api/auth/login`, `/api/auth/logout`, `/api/auth/me`, `/api/orders`가 네 개 다 있는지 보세요. 없으면 파일 위치가 잘못된 거예요.

### 시나리오 노브

| 값 | 적용 대상 | 동작 |
| --- | --- | --- |
| `invalid` | login | 자격 증명이 맞아도 항상 401 |
| `expired` | me · orders | 세션 쿠키가 유효해도 항상 401 |
| `error` | login · me · orders | 500 |
| `slow` | login · me · orders | 1.5초 지연 |

`logout`에는 노브가 적용되지 않아요. 항상 204로 응답하고 쿠키를 지웁니다.

query string(`?scenario=expired`)이 우선이고, 없으면 `scenario` 쿠키를 읽어요. 앱 안에서 호출하는 `/api/auth/me`에는 query를 붙일 수 없으니 쿠키 경로가 필요합니다. E2E에서는 `context.addCookies`로, 통합 테스트에서는 MSW 핸들러로 재현하세요.

### 이벤트 로거

`src/analytics/`에 이벤트를 보내는 코드가 들어 있어요. **이걸 직접 만들지 마세요.** 2단계에서 할 일은 이벤트 스키마 설계입니다.

| 파일 | 역할 |
| --- | --- |
| `provider.ts` | 분석 도구를 감싸는 인터페이스. GA4 · GTM · Amplitude 붙이는 자리를 주석으로 안내해요 |
| `consoleProvider.ts` | 개발 중 확인용. 콘솔에 찍고 `window.__analytics`에도 쌓습니다 |
| `logger.ts` | `track()` · `identify()` · `reset()`. 초기화 전 이벤트를 큐에 담아 두고, 초기화 후 흘려보냅니다 |

`track()`은 초기화 전에 불러도 됩니다. 큐에 담아 두고 초기화 후 순서대로 보내요. 공통 프로퍼티는 `setCommonProperties()`로 넣고, 이벤트 발생 시점에 평가됩니다.

**스타터가 정하지 않는 것** — 이벤트 이름, 프로퍼티, 그리고 `sessionId` · `device` · `ts` 같은 공통 값에 무엇을 넣을지. 이게 2단계에서 직접 설계할 부분입니다.

### 시드 이벤트 로그

`fixtures/events-30d.jsonl` — 30일 분량의 이벤트 로그입니다. 필드 설명은 `docs/fixtures/events.md`에 있어요.

```json
{"sessionId":"s_0a3f","ts":"2026-07-24T11:02:17.481Z","name":"product_list_view",

```

봇 세션과 오류 이벤트, 중복 전송이 섞여 있어요. 그대로 집계하면 순위가 틀어집니다.

## 📝 Implementation Quest

### 🔐 1단계 — 인증을 구현해요

스타터가 API를 제공해요. 프론트엔드를 만듭니다.

**요구사항**

- 로그인 · 로그아웃 화면과 헤더의 로그인 상태 반영
- **`proxy.ts`**로 보호 경로를 가드해요. 미로그인으로 들어오면 로그인으로 보내고, **로그인 후 원래 가려던 경로로 돌려보냅니다.** 복원 경로를 어떤 파라미터로 실어 나를지는 직접 정하고, 그 값으로 **외부 주소로 튕겨나가지 않게** 막아요.
- 구현한 뒤 `pnpm start`로 띄워 보호 경로에 요청을 보내 확인해요. 빌드 통과와 동작은 다릅니다.
- 서버에서 세션을 읽어 **초기 HTML에 로그인 상태를 반영**해요. JavaScript 실행 전에도 로그인 여부가 보여야 합니다. 단 쿠키를 읽는 위치에 따라 정적 생성 범위가 달라지니, 7주차 성능 기준을 다시 깨지 않는지 확인하세요.
- 세션 만료(401)를 처리할 자리를 **한 곳으로 정하고** 근거를 남겨요. 화면마다 따로 처리하면 나중에 어디를 고칠지 알 수 없습니다.
- 로그아웃하면 클라이언트 상태를 정리해요. 장바구니와 위시리스트를 지울지 남길지 정하고 이유를 적습니다.
- 보호 경로가 어디까지인지 정해요. **주문서와 주문 내역은 반드시 포함**하고, 장바구니·위시리스트·마이페이지는 본인 판단입니다. 보호할 화면이 아직 없으면 **만들어야** 검증할 수 있어요.

> 💡 세션 쿠키의 서명까지 검증할지, 존재만 확인하고 실제 검증은 페이지나 API에 맡길지 갈립니다. 어느 쪽이든 이유가 있으면 됩니다.

> 💡 `/api/auth/me`는 **"로그인 안 함"과 "세션 만료"를 같은 401로 돌려줍니다.** 어떤 요청의 401을 만료로 볼지 구분하는 기준을 함께 정하세요.

> 💡 세션은 요청마다 값이 달라지는 서버 상태예요. 5주차부터 써온 클라이언트 상태 패턴을 **그대로 써도 되는지** 먼저 검토하세요.

**완료조건**

미로그인으로 보호 경로에 들어가면 로그인 후 원래 경로로 돌아오고, 세션이 만료되면 다음에 무엇을 해야 할지 화면에서 알 수 있어요. **`pnpm start`로 띄운 상태에서 확인합니다.**

### 📊 2단계 — 이벤트를 계측해요

**요구사항**

이벤트 로거는 `src/analytics/`에 있어요. 그 위에 **무엇을 어디서 보낼지**를 설계합니다.

- 이벤트 이름 규칙과 모든 이벤트에 공통으로 붙일 프로퍼티를 **먼저 정해요.** 3단계 RFC의 A절에 씁니다.
- 공통 프로퍼티는 `setCommonProperties()`로 넣어요. 무엇을 넣을지는 직접 정합니다. 시드 로그를 보면 참고가 될 거예요.
- 목록 진입 · 상세 진입 · 담기 · 로그인 시작 · 로그인 성공 · 로그인 실패 · **주문 시작 · 주문 완료**에 계측을 넣어요. 내 앱에 없는 화면은 빼고, 뺐다는 사실을 적습니다.
- 로그인과 로그아웃 시점에 `identify()` · `reset()`을 부를 자리도 정해요. 1단계에서 만든 인증 흐름과 붙습니다.
- `initAnalytics()`를 어디서 부를지 정해요. 이 위치에 따라 큐에 쌓이는 이벤트가 달라집니다.
- 시드 로그(`fixtures/events-30d.jsonl`)와 **이름이 다르면 매핑 표**를 남겨요. 계측 스키마는 혼자 정하는 게 아니라 팀이 합의하는 것이라, 이미 있는 스키마에 맞춰보는 게 목적입니다.
- 계측 코드가 화면 로직에 섞이지 않게 경계를 둬요 (6주차 FSD 경계 유지). 컴포넌트가 `track()`을 직접 부르는 게 맞는지, 아니면 한 겹 두는 게 맞는지 판단하고 이유를 적습니다.
- 실제 분석 도구는 붙이지 않아도 돼요. `consoleProvider`로 충분합니다.

> 💡 이벤트 이름을 정할 때 "나중에 이걸로 무엇을 집계할 것인가"를 먼저 생각해 보세요. 3단계에서 이 로그로 경로를 세게 됩니다. `button_click` 하나에 모든 클릭을 담으면 그때 아무것도 셀 수 없어요.

**완료조건**

로그인부터 주문까지 한 번 통과했을 때 어떤 이벤트가 어떤 순서로 남는지, 문서만 읽고 예측할 수 있어요.

### 🗺️ 3단계 — E2E 범위를 정해요

`docs/rfc/week09-e2e-scope.md`에 쓰고, **E2E 코드보다 먼저 커밋해요.**

**A. 이벤트 스키마**

2단계에서 정한 이름 규칙과 공통 프로퍼티, 시드 로그와의 매핑.

**B. 시드 로그 분석**

| 경로 | 세션 수 | 비율 | 이탈률 | 실패 비용 | E2E 여부(가설) |
| --- | --- | --- | --- | --- | --- |
| 직접 작성 | 직접 작성 | 직접 작성 | 직접 작성 | 직접 작성 | 직접 작성 |

- **경로**는 사용자가 지나가는 화면이나 행동의 단위예요. 이벤트 이름 하나하나로 잡아도 되고, **화면 단위로 묶어도 됩니다.** 묶었다면 묶은 기준을 적어요.
- 상위 경로를 **세션 기준**으로 순위를 냅니다. 이벤트 수 기준으로 세면 한 사람이 여러 번 한 행동이 부풀려져요.
- **비율**은 분모를 밝히세요. 전체 세션인지, 노이즈를 걸러낸 세션인지, 앞 단계를 지나온 세션인지에 따라 값이 달라집니다.
- **이탈률**은 정의를 골라서 쓰세요. "그 이벤트가 세션의 마지막이었던 비율"과 "다음 단계로 넘어가지 못한 비율"은 다른 값이 나옵니다. 어느 쪽을 썼는지 적어요.
- **실패 비용**은 이 경로가 망가졌을 때 무엇을 못 하게 되는지입니다. 로그에서 실패로 볼 이벤트를 직접 정하고(무엇을 실패로 셌는지 적어요), 그 비율과 함께 이 화면이 막히면 뒤따라 막히는 것을 씁니다.
- 봇 세션과 오류 이벤트, 중복 전송을 **어떤 기준으로 걸렀는지** 적어요. 로그에 "이건 봇이다" 하는 표시는 없습니다.
- 걸러내기 전과 후의 순위를 비교해요. **바뀌지 않았다면 왜 안 바뀌었는지**도 씁니다. 안 바뀌는 것도 결과예요.
- 마지막 칸은 **가설**입니다. 최종 판단은 C절에서 합니다.

**C. 붙일 곳과 안 붙일 곳**

- **인증 플로우는 필수입니다.** 로그인이 막히면 주문도 마이페이지도 못 쓰니까요. 이게 아래 "빈도는 낮은데 붙인 경로"에 해당해요.
- 인증 외에 **2개 이하**를 로그 근거로 직접 고릅니다. 하나도 안 고르는 것도 답이에요. 다만 왜 안 골랐는지 써야 합니다.
- 고른 시나리오마다 왜 이건지 씁니다.
- 빈도가 **높은데 E2E를 안 붙인 경로**를 하나 이상 골라요. 통합 테스트로 충분한 이유를 씁니다.
- 빈도가 **낮은데 E2E를 붙인 경로**로 인증을 씁니다. 로그만 보고 정하면 안 되는 이유를 씁니다.
- **E2E 시나리오 하나를 골라** 유지보수 비용을 추정해요. 그 화면의 문구나 구조가 바뀌면 테스트에서 몇 군데를 고치게 되나요?

> 💡 "빈도 1위니까 E2E" 같은 결론이 나오면 그 경로를 8주차에 이미 무엇으로 검증했는지 확인해 보세요.

> 💡 로그에 있는 이벤트가 내 코드에는 화면으로 없을 수도 있어요. 그러면 그 경로는 E2E 대상에서 자연히 빠집니다. 없는 화면을 만들 필요는 없고, **왜 빠지는지만 근거로 남기면** 됩니다. 실무에서도 로그 스키마와 현재 구현은 자주 어긋나요.

**완료조건**

이 문서만 읽고 4단계에 어떤 테스트가 들어갈지 예측할 수 있고, **만들지 않기로 한 것에 대한 근거**도 문서 안에 있어요.

---

### 🎭 4단계 — E2E를 구현해요

3단계에서 정한 것만 만들어요. 개수를 늘리지 않습니다.

**인증 플로우 (필수)**

아래 세 갈래를 다룹니다. 3단계에서 인증을 필수로 넣었으니 여기가 그 구현이에요.

- 미로그인으로 보호 경로 진입 → 로그인 → **원래 경로 복원**
- 세션 만료 경계 — `expired` 시나리오로 재현
- 잘못된 자격 증명 — `invalid` 시나리오 또는 틀린 비밀번호

**공통**

- `storageState`로 로그인 1회를 재사용해요. 매 테스트에서 로그인 폼을 다시 채우면 안 됩니다.
- **로그인 자체를 검증하는 테스트는 `storageState`를 쓰지 않아요.** 왜 그런지 적습니다.
- 병렬로 돌려도 결과가 같아야 해요. 계정 · 데이터 · 스토리지 중 무엇을 워커별로 갈랐는지 남깁니다. 계정이 8개인 이유가 여기예요.
- 셀렉터는 역할과 이름 기반으로 정리해요. `getByTestId`를 썼으면 왜 다른 방법으로 안 됐는지 남깁니다.
- `sleep`으로 기다리지 않아요. 조건 기반 대기만 씁니다.
- production build 위에서 돌려요.
- **trace를 한 번 직접 열어봐요.** 설정에 `trace` 옵션만 넣어두는 것으로는 실패를 읽을 수 없습니다. 아래 순서로 해보세요.
    1. 통과하는 테스트의 단언 하나를 일부러 틀리게 바꿔 실패시킵니다
    2. `--trace=on`을 붙여 실행하면 `test-results/` 아래에 `trace.zip`이 생깁니다
    3. `pnpm exec playwright show-trace <그 경로>`로 열어, 어느 단계에서 무엇을 기다리다 멈췄는지 봅니다
    4. 단언을 원래대로 되돌리고, 무엇을 봤는지 한두 줄로 남깁니다

> 💡 에러 테스트가 타임아웃 난다면 서버 상태 라이브러리의 재시도 정책을 확인해 보세요.

> 💡 `storageState`와 워커별 계정을 함께 쓰는 자리에서 한 번 막힐 수 있어요. 저장 파일을 워커별로 나누는 방향으로 생각해 보세요.

**완료조건**

`--workers=4`와 `--workers=1`의 결과가 같고, 같은 테스트를 3회 연속 돌려도 결과가 같아요.

### 🔬 5단계 — E2E가 무엇을 잡는지 확인해요

E2E는 비싸니까, 그 값을 하는지 확인해야 해요. 8주차 3단계를 E2E에 적용합니다.

**요구사항**

- **실험 하나마다 인증 구현을 한 곳만** 바꿔요. 가드 조건을 뒤집거나, 복원 경로를 지우거나, 만료 분기를 없애는 식으로요. 여러 곳을 동시에 바꾸면 어느 변경이 잡혔는지 알 수 없습니다. **테스트 코드는 건드리지 않아요.**
- 실험 **3개 이상.** 그중 하나는 **통합 테스트로는 잡을 수 없는 것**을 고르세요. 미들웨어 리다이렉트, 쿠키 속성, 초기 HTML의 로그인 상태 같은 것들이요.
- 실험마다 기록해요.

    | # | 망가뜨린 곳 | 어떻게 바꿨나 | 결과 | 실패한 테스트 | 실패 메시지로 원인을 알 수 있었나 |
    | --- | --- | --- | --- | --- | --- |
    | 직접 작성 | 직접 작성 | 직접 작성 | 잡힘 / 살아남음 | 직접 작성 | 직접 작성 |

- **살아남았으면** 테스트를 고치고, 왜 못 잡았는지 씁니다.
- **통합 테스트로도 잡히는 실험이 있었다면**, 그 시나리오를 E2E에 둘 이유가 남아 있는지 다시 판단해요. 없으면 지우는 것도 답입니다.
- 실험이 끝나면 구현을 되돌려요. 망가뜨린 코드가 커밋에 남으면 안 됩니다.

> 💡 E2E는 한 번 도는 데 오래 걸려요. 실험 대상을 미리 정해두고 한 번에 확인하세요.

**완료조건**

실험 기록이 있고, **E2E만 잡을 수 있었던 항목**이 최소 하나 확인돼요.

### ⚡ Advanced — 하나만 골라요

Basic을 완료한 뒤 선택해요. Basic 평가에 영향을 주지 않습니다.

**A. 시각적 회귀**

Playwright 1.62의 컴포넌트 테스트를 씁니다. **story**는 컴포넌트에 props를 고정한 래퍼(`*.story.tsx`의 named export)이고, **gallery**는 `window.mount()`를 노출해 story를 그려주는 페이지예요. 자세한 건 `playwright.dev/docs/test-components`를 보세요.

- story와 gallery를 만들고 `toHaveScreenshot`으로 기준선을 잡아요.
- 비결정성을 어떻게 없앴는지 남겨요. 폰트 로딩, 애니메이션, 시간, 랜덤, 이미지 지연.
- 무엇을 마스킹했고 왜 그건지 적어요.
- **의도한 변경 1회와 의도하지 않은 변경 1회**를 만들어, 각각 결과가 어떻게 나오는지 기록해요.
- 기준선 파일을 커밋할지 말지 정하고 이유를 남겨요.

**B. 에이전트 생성 검수**

- `npx playwright init-agents`로 planner → generator를 돌려요.
- 생성된 테스트와 본인이 4단계에서 쓴 테스트를 비교해요.
- 생성물에서 **지운 단언과 그 이유**를 남깁니다.
- healer는 쓰지 말고, 쓰지 않은 이유를 적어요.

## ✍️ Technical Writing Quest

숫자 대신 결정을 씁니다.

세션 만료를 어디서 처리하기로 했고 왜 거기인지. 보호 경로의 경계를 어디에 뒀는지. 로그아웃 시 장바구니를 어떻게 했고 그 근거가 무엇인지. 복원 경로로 외부 주소로 나가는 걸 어떻게 막았는지.

시드 로그에서 무엇을 노이즈로 판단했고 기준이 무엇인지. 걸러내기 전후로 순위가 바뀌었다면 무엇이 바뀌었는지. 빈도가 높은데 E2E를 안 붙인 경로와 낮은데 붙인 경로를 각각 어떤 근거로 갈랐는지.

`storageState`를 쓴 테스트와 안 쓴 테스트의 경계는 어디인지. 병렬 실행에서 무엇을 갈라 격리를 확보했는지. `getByTestId`를 썼다면 왜 다른 방법으로 안 됐는지.

5단계에서 살아남은 변경이 있었다면 숨기지 마세요. 왜 못 잡았고 어떻게 고쳤는지가 이번 주에서 가장 값어치 있는 기록이에요.

AI를 쓴 자리를 밝히고, 단언과 E2E 범위는 직접 정했는지 적어요.
