# 5주차 상태 설계

## 상태 분류 기준

TanStack Query — 서버 데이터
nuqs — URL에 있어야 하는 것
Zustand — 여러 페이지가 공유하는 것
React 로컬 state — 한 화면에서만 쓰는 것

| 상태 | 소유자 | 수명 | 공유 범위 | 선택 이유 |
| ---- | ------ | ---- | --------- | --------- |
| 홈 배너, 카테고리, 인기상품, 신상품 | TanStack Query | 홈 페이지 있는 동안 | 홈 페이지 | 서버에서 오는 데이터 |
| 목록 상품 데이터 | TanStack Query | 목록 페이지 있는 동안 | 목록 페이지 | 서버에서 오는 데이터 |
| 검색·카테고리·정렬·페이지 | nuqs | URL에 있는 동안 | URL | 새로고침·공유·뒤로가기 후 복원이 필요해서 |
| 비로그인 장바구니·위시리스트 | Zustand | 앱 켜져 있는 동안 | 앱 전체 | 홈·목록 양쪽에서 읽고 써야 해서 |
| 검색어 입력 중 draft | React 로컬 state | 컴포넌트 수명 | useProductFilters 내부 | debounce 전 임시값. URL에 반영하기 전 draft라서 |

## TanStack Query — 캐시 정책 근거

### staleTime
- `HOME = 300_000` (5분): 배너·카테고리는 변경이 드물어 긴 캐시 수명 적용. `/api/home`이 배너·카테고리·인기상품을 한 덩어리로 반환해 분리 불가. 홈은 구매 확정이 아닌 발견 용도라 재방문 시 최대 5분 오래된 데이터를 허용 가능한 트레이드오프로 판단.
- `PRODUCT_LIST = 60_000` (1분): 검색·필터 조합이 다양하고 상품 데이터는 자주 갱신될 수 있어 짧게 설정

### gcTime
- `HOME = 600_000` (10분): staleTime 5분보다 길게 설정. 홈 → 목록 → 홈 이동 시 10분 내 재방문이면 캐시에서 즉시 보여줌
- `PRODUCT_LIST = 120_000` (2분): 필터 조합이 많아 동일한 조건으로 재방문할 가능성이 낮아 짧게 설정

### placeholderData: keepPreviousData
필터 변경 시 새 데이터가 오기 전 빈 화면이 깜빡이는 현상을 방지하기 위해 적용(C 어드밴스).
트레이드오프: 에러 상태가 즉시 표시되지 않고 재시도 완료 후 나타남. 이전 데이터를 보여주는 것이 빈 화면보다 사용자 경험상 낫다고 판단.

## nuqs — URL 상태 설계 근거

### history: "push"
필터 변경마다 히스토리를 쌓아야 브라우저 뒤로가기로 이전 조건을 복원할 수 있음.
`history: "replace"`로 하면 뒤로가기가 필터 이전 페이지로 바로 이동해 탐색 흐름이 끊김.

### page 범위 초과 처리
URL에 `page=3`을 직접 입력해도 해당 페이지가 실제로 존재하면 유지하고, 존재하지 않으면 데이터 로드 후 자동으로 page 1로 리셋.
리셋은 사용자가 의도한 이동이 아니라 자동 보정이므로 `history: 'replace'`로 처리해 히스토리에 쌓이지 않도록 함.

### debounce (검색어)
검색어 입력 중 매 키 입력마다 API를 호출하면 불필요한 요청이 많아짐.
`searchInput`을 로컬 state로 두고 300ms 후 URL에 반영.
마운트 시 초기값으로 인한 page 리셋을 막기 위해 첫 렌더에서는 실행되지 않도록 `useRef`로 건너뜀.

### searchInput ↔ URL sync (앞/뒤로가기)
브라우저 앞/뒤로가기로 URL이 바뀌면 `filters.q`가 바뀌지만 `searchInput`(로컬 state)은 그대로 남음.
이 상태에서 debounce가 실행되면 `searchInput`의 이전 값이 URL을 덮어써 탐색 복원이 깨짐.

두 가지 ref로 해결:
- `skipNextDebounce`: 뒤로가기로 URL이 바뀌어 `searchInput`을 업데이트할 때, debounce가 곧바로 그 값을 URL에 덮어쓰지 않도록 한 번 건너뜀
- `lastDebounceQ`: debounce가 URL을 바꾸면 URL 변화를 감지하는 `useEffect`도 함께 실행됨. 이때 `searchInput`을 URL 값으로 덮어쓰면 타이핑 중인 글자가 지워짐. `lastDebounceQ`에 "내가 방금 이 값을 URL에 썼다"는 것을 기억해두고, 그 값이 다시 들어올 때는 덮어쓰기를 건너뜀.

## Zustand — store 설계 근거

### store 데이터 형태
`items: string[]` — 상품 id 배열만 저장.
가격·이름 등 상품 상세는 TanStack Query 캐시에 있으므로 중복 저장하지 않음.

### 헤더 개수 파생
`cartCount`, `wishlistCount`를 별도 상태로 두지 않고 `items.length`를 selector로 파생.
계산 가능한 값을 state로 중복 저장하지 않는다는 원칙을 지킴.

### selector 경계
- Header: `(state) => state.items.length` — 개수만 구독. 아이템 목록 변경이 헤더를 불필요하게 리렌더링하지 않음
- ProductCard: `(state) => state.items.includes(product.id)` — 해당 상품 상태만 구독

### Advanced A — persist 설계
- `skipHydration: true`: Next.js SSR 단계에서 서버에 localStorage가 없어 hydration 불일치 발생. 초기 hydration을 건너뛰고 클라이언트 마운트 후 수동으로 `rehydrate()` 호출
- `version + migrate`: 저장 스키마가 바뀌었을 때 구 데이터를 안전하게 복구하는 전략. version 0 또는 배열이 아닌 경우 빈 배열로 초기화

### 로그인·서버 동기화가 생기면
현재 Zustand가 비로그인 익명 위시리스트의 원본을 소유하고 있음.
로그인이 추가되면 서버가 사용자 위시리스트의 원본을 소유하게 됨 → TanStack Query로 관리 전환 필요.
로컬 익명 데이터 처리 방향(서버 병합 / 폐기 / 충돌 정책)을 먼저 정해야 하고, 이 시점에 Zustand의 역할은 "서버 상태의 임시 입력 또는 UI 상태"로 다시 제한됨.

## Advanced B — 서버 프리패치 스킵 근거

세 가지 이유로 의도적으로 스킵했다.

**1. 가격이 변경될 수 있음**
인기상품·신상품에는 가격이 포함되어 있어 프리패치한 순간 이미 stale할 수 있음.
`/api/home`은 배너·카테고리·인기상품·신상품을 한 번에 반환하는 구조라 일부만 프리패치하는 것이 불가능함.
API가 분리된다면 변경이 드문 배너·카테고리는 프리패치 대상으로 고려할 수 있음.

**2. 목록 페이지와 일관성**
목록은 기본 필터 첫 접속만 프리패치 가능하고, 필터 변경 이후는 nuqs가 클라이언트 전용이라 프리패치 불가.
목록의 핵심 기능이 필터링인데 절반만 적용되면 실익이 없음.
홈만 프리패치하면 두 페이지의 데이터 로딩 방식이 불일치해 일관성이 깨짐.

**3. 구조 전환 비용**
B를 적용하려면 `page.tsx`를 서버 컴포넌트로 전환하고, 요청마다 새 QueryClient를 만들고, `HydrationBoundary`로 서버 캐시를 클라이언트에 전달하는 코드가 추가로 필요함.
위 두 이유로 실익이 없다고 판단했기 때문에 이 복잡도를 감수할 근거가 없어 스킵.
