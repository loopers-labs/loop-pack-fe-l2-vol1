# 9주차 1단계 — 인증 설계 근거

## 세션 상태 관리 패턴

세션은 5주차부터 써온 클라이언트 상태(zustand/nuqs) 패턴을 그대로 쓰지 않는다. zustand는 "여러 페이지가 공유하는 클라이언트 소유 상태"에 맞고, nuqs는 "URL에 있어야 하는 상태"에 맞는데, 세션은 **요청마다 서버가 유효성을 새로 판정하는 서버 상태**라 TanStack Query로 관리한다. `entities/session`에 `sessionQueries.me()`(`GET /api/auth/me` 기반 `queryOptions`)를 두고, 기존 `productsQueries` 패턴(쿼리키 네임스페이스 + `queryOptions` 팩토리)을 재사용한다.

**캐시 정책**: `retry: false`를 명시한다. TanStack Query 기본값은 실패 시 3회 재시도인데, 401은 재시도해도 결과가 바뀌지 않는 에러라 기본값을 그대로 두면 로그아웃 판정이 지수 백오프만큼(수 초) 늦어진다. `staleTime`은 세션이 로그인/로그아웃 시점에만 명시적으로 invalidate되므로(아래 401 처리 참고) 넉넉하게 `Infinity`로 두고, 자동 재검증에 의존하지 않는다.

## 헤더 초기 로그인 상태

`CommerceLayout`(`src/app/(commerce)/layout.tsx`)을 async 서버 컴포넌트로 바꿔 `cookies()`로 세션 쿠키를 읽고, `src/app/api/_data/auth.ts`의 `readSessionToken()`을 **직접 함수로 재사용**한다. 서버 컴포넌트는 Node 런타임이라 `node:crypto`를 쓰는 이 함수를 그대로 import할 수 있고, 자기 자신의 `/api/auth/me`를 다시 fetch하는 왕복을 피할 수 있다. 얻은 유저 정보는 `queryClient.setQueryData(sessionQueries.me().queryKey, ...)`로 채워 `HydrationBoundary`를 통해 Header에 전달한다. 이렇게 하면 JS 실행 전에도 초기 HTML에 로그인 상태가 반영된다(깜빡임 없음).

**성능 트레이드오프**: `cookies()` 호출은 그 세그먼트를 동적 렌더링으로 전환시킨다. `CommerceLayout` 하위의 홈·상품 목록 페이지가 정적 생성 대상에서 빠질 수 있어 7주차 INP 기준과 충돌할 가능성이 있다. 이 대가를 감수하고도 `CommerceLayout`에서 읽기로 한 이유는, 초기 HTML에 로그인 상태를 반영하는 게 이번 주 필수 요구사항이라 트레이드오프를 피할 방법이 없기 때문이다. 문제가 확인되면 `Header`를 별도 컴포넌트로 분리해 동적 렌더링 범위를 그 컴포넌트로만 좁힌다.

## `proxy.ts` 보호 경로 가드

Next.js 소스(`PROXY_FILENAME` 상수)로 확인한 결과 `src/app` 구조에서는 `src/proxy.ts`가 올바른 위치다. Edge 런타임에서 실행되므로 `node:crypto`를 쓰는 `auth.ts`는 import할 수 없고, 쿠키 이름만 담긴 `auth-cookies.ts`의 `SESSION_COOKIE`만 사용한다.

검증 수준은 **쿠키 존재 여부만 확인**한다(서명·만료 검증은 하지 않음). 실제 유효성 검증은 각 페이지·API(Node 런타임)가 이미 `readSessionToken()`으로 하고 있으므로, `proxy.ts`는 "쿠키 자체가 없는 명백한 미로그인"만 1차로 걸러내는 가벼운 문지기 역할로 충분하다. Edge용으로 서명 검증 로직을 Web Crypto로 별도 구현하는 대안은 같은 로직이 두 군데(Node/Edge) 존재하게 되는 유지보수 부담이 있어 채택하지 않는다.

리다이렉트 시 원래 경로는 쿼리 파라미터 **`redirect`**로 실어 보낸다(예: `/login?redirect=/orders`). 로그인 성공 후 이 값으로 이동하기 전 다음을 모두 검증해 오픈 리다이렉트를 차단한다:
- `/`로 시작하는가 (상대 경로만 허용)
- `//`나 `://`로 시작하지 않는가 (`//evil.com`, `/\evil.com` 같은 프로토콜 상대 URL 차단 — 브라우저가 이걸 외부 도메인으로 해석하는 경우가 있음)

검증에 실패하면(파라미터가 없거나 위 조건을 안 지키면) 기본값 `/`로 보낸다.

**matcher 범위**: `/orders`, `/orders/:path*`만 넣는다. **`/login` 자체는 절대 matcher에 넣지 않는다** — 넣으면 "미로그인 → `/login`으로 보냄 → `/login`도 보호 경로라 다시 미로그인 판정 → 또 `/login`으로 보냄"의 무한 리다이렉트 루프가 생긴다. 보호 대상을 늘릴 때(장바구니 등)도 이 matcher 배열에 경로만 추가하면 되는 구조로 둔다.

## 세션 만료(401) 처리

refresh 토큰이 없고 세션 TTL은 고정(활동해도 연장 안 됨) — 만료되면 재로그인이 유일한 경로다. 처리 지점은 **TanStack Query의 전역 에러 핸들러 한 곳**으로 통일한다. 구체적으로는 `providers.tsx`에서 `QueryClient`를 만들 때 `queryCache`와 `mutationCache`에 각각 `onError`를 등록한다 — 서버 요청이 `useQuery`(세션 조회, 주문내역 조회)와 `useMutation`(로그인, 주문 제출) 두 갈래로 나뉘어 있어서, 한쪽만 걸면 다른 쪽 401은 못 잡는다. 감지되면 세션 쿼리 캐시를 정리하고 로그인 화면으로 이동시킨다.

**"로그인 안 함"과 "세션 만료"를 구분하는 기준**: `/api/auth/me`는 두 상황 모두 401로 응답해서 API 응답만으로는 구분이 안 된다. **보호 경로(`proxy.ts`를 통과해 들어온 페이지)에서 받은 401은 "만료"로 간주**해 로그아웃+로그인 화면 이동을 태운다. 반대로 비보호 경로(예: 홈에서 헤더 세션 조회)의 401은 애초에 로그인한 적 없는 정상 상태이므로 리다이렉트 없이 조용히 "비로그인" UI만 반영한다. `proxy.ts`가 쿠키 없는 요청은 이미 걸러냈으므로, 그 이후 401은 "있었는데 무효화됨(만료/위조)"으로 해석할 수 있다는 논리다.

**로그인 mutation 자체의 401(자격 증명 틀림)은 이 흐름에서 제외한다.** 로그인 폼은 로그인 시도 자체가 아직 안 된 상태라 "만료"라는 개념이 성립하지 않고, 폼 안에서 바로 에러 메시지를 보여주는 게 맞다. `mutationCache.onError`에서 로그인 mutation은 식별해 전역 리다이렉트 대상에서 제외한다.

**로그인 화면에 만료 이유를 표시한다.** 완료조건("세션이 만료되면 다음에 무엇을 해야 할지 화면에서 알 수 있어요")을 충족하려면 사용자가 로그인 화면에 갑자기 도착했을 때 이유를 알아야 한다. 전역 401 핸들러가 리다이렉트할 때 `redirect` 파라미터 옆에 `reason=expired`를 함께 실어 보내고(`/login?redirect=/orders&reason=expired`), 로그인 화면은 이 값이 있으면 "세션이 만료되었습니다. 다시 로그인해주세요" 메시지를 보여준다. `proxy.ts`가 리다이렉트하는 경우(쿠키 자체가 없어 "미로그인"으로 판정한 경우)는 `reason`을 붙이지 않는다 — 이건 만료가 아니라 애초에 로그인한 적이 없는 정상 상태라 별도 안내가 필요 없다.

## 로그아웃 시 클라이언트 상태 정리

장바구니·위시리스트(`cartStore`, `wishlistStore`)는 **로그아웃해도 유지**한다. 이 앱은 계정별로 장바구니를 저장하는 서버 API가 없다(`/api/cart` 부재 확인) — 즉 장바구니는 "계정 소유"가 아니라 "기기 소유" 데이터라, 세션 삭제(로그아웃)가 이걸 지울 근거가 없다. 로그인 시 서버에서 불러오는 장바구니 목록도 없으므로(스타터 API에 해당 엔드포인트 없음), 로그인·로그아웃과 장바구니 상태는 완전히 독립적으로 취급한다.

**고려했지만 채택 안 한 대안**: 공용 PC(도서관 등)에서 로그아웃 시 다음 사용자에게 이전 사용자의 장바구니가 그대로 보이는 문제가 있을 수 있다. 다만 (1) 이 앱에 공용 PC를 겨냥한 별도 요구사항이 없고, (2) 애초에 장바구니가 계정과 연결된 적이 없어 "누구 것"이라는 개념 자체가 없으므로 로그아웃이 지울 명분이 약하며, (3) 이 문제는 로그아웃이 아니라 브라우저 프로필 분리로 해결하는 게 정상적인 해법이라 판단해 채택하지 않는다.

## `auth.ts`/`auth-cookies.ts` 위치 — 옮기지 않는다

과제 문서는 "응답 타입은 `src/app/api/_data/auth.ts`에 함께 있어요. 본인 구조에 맞는 곳으로 옮겨도 됩니다"라고 안내하지만, **옮기지 않고 그 자리에 그대로 둔다.**

**기준**: "화면(프론트엔드)이 알아야 하는 도메인 지식"과 "서버가 그 데이터를 내부적으로 어떻게 만들어내는지"를 구분한다. 전자만 FSD(`entities` 등)로 옮기고, 후자는 API route 전용 구현으로 남긴다.
- 로그인한 유저가 누구인지, 세션이 유효한지 → 화면 여러 곳(헤더, 보호 페이지)이 참조하는 도메인 지식 → `entities/session`(신규)으로 만든다
- 그 세션 토큰을 서버 내부에서 어떻게 서명·검증하는지(`node:crypto`, HMAC) → 화면은 몰라도 되는 서버 내부 구현 → `_data`에 그대로 둔다

**선례**: 이 기준은 새로 만든 게 아니라 6주차 FSD 마이그레이션(`docs/rfc/week06-fsd.md`)에서 이미 세운 원칙이다. 그때 `src/app/api/_data/commerce.ts`(홈·상품 mock 데이터)를 "API route 범위"로 분류해 `entities/product`로 옮기지 않았고, 이후 "신상품 뱃지 추가" 삭제 시나리오 자가 검증에서 "`entities/product/` 안에서 완결, 다른 슬라이스는 안 건드림"으로 응집도까지 확인했다. `auth.ts`도 같은 논리를 적용하는 것뿐이다 — `commerce.ts`는 그대로 두면서 `auth.ts`만 entities로 옮기면 오히려 일관성이 깨진다.

**기술적 제약도 같은 방향을 가리킨다**: `auth-cookies.ts`는 `src/proxy.ts`(Edge 런타임)에서도 import돼야 하는데, `node:crypto`를 쓰는 `auth.ts`와 이미 파일이 분리되어 있어 이 제약을 만족한 상태다. 옮기면 이 분리를 다시 설계해야 해서 얻는 것 없이 위험만 는다.

## 보호 경로 범위

- **주문서(주문하기), 주문내역 — 필수 보호.** 현재 화면 자체가 없으므로 최소 구현으로 신규 생성한다.
- **장바구니, 위시리스트 — 비보호.** 위 로그아웃 정책과 같은 논리: 기기 소유 데이터라 비로그인 상태에서 봐도 문제 없고, 오히려 로그인을 강제하면 구경만 하려는 사용자를 막게 된다.
- **마이페이지 — 대상에서 제외.** 현재 화면이 없고, 이번 주 필수 요구사항(주문서·주문내역)과 무관해 새로 만들 근거가 약하다.
