## 1단계 — 인증을 구현해요 🔐

### 1-0. 설계 결정 먼저 (결정 사항은 PR 본문용으로 메모)

- [ ] **보호 경로 목록** 정하기: 주문서·주문 내역은 반드시 포함. 장바구니·위시리스트·마이페이지는 본인 판단 + 근거 메모
- [ ] 보호할 화면이 앱에 없으면 **먼저 만들기** (예: `GET /api/orders`로 주문 내역 보여주는 페이지)
- [ ] 복원 경로를 실어 보낼 **파라미터 이름** 정하기 (예: `?redirectTo=...`)
- [ ] 복원 값 검증 방식 정하기: 외부 주소(`https://...`, `//...`)를 거르는 규칙을 어떻게 둘지
- [ ] `proxy.ts`가 쿠키 **서명까지 검증할지, 존재만 볼지** 정하기 + 근거 (둘 다 정답, 이유가 중요)
- [ ] **세션 만료(401) 처리 위치를 한 곳** 정하기: API 래퍼 / fetch 인터셉터 / React Query 전역 onError 등 + 근거
- [ ] `/api/auth/me`의 401이 "로그인 안 함"과 "세션 만료" 두 얼굴임을 처리할 기준 정하기 (어떤 요청의 401을 만료로 볼지)
- [ ] 로그아웃 시 **장바구니·위시리스트를 지울지 남길지** 정하고 이유 메모 (정답 없음, 근거 싸움)
- [ ] 5주차 클라이언트 상태 패턴을 세션에 그대로 써도 되는지 검토 메모 ("세션은 요청마다 달라지는 서버 상태")

### 1-1. 로그인/로그아웃 화면

- [ ] 로그인 페이지 UI 만들기 (이메일·비밀번호 폼, 버튼, 에러 메시지 자리)
- [ ] `POST /api/auth/login` 연동: 성공(200) 시 쿠키 발급 확인
- [ ] 401(자격 증명 불일치)과 400(형식 오류)을 **다른 메시지**로 분기 처리
- [ ] 제출 중 로딩 상태와 중복 제출 방지 처리
- [ ] 로그아웃 버튼 만들고 `POST /api/auth/logout`(204) 호출 → 쿠키 제거 확인
- [ ] 로그아웃 후 리다이렉트 목적지 정하기 (어디로 보낼지 + 이유)

### 1-2. 헤더/초기 HTML에 로그인 상태 반영

- [ ] 서버 컴포넌트에서 세션 쿠키(`session`)를 읽어 헤더 상태를 그린다
- [ ] 개발자 도구 Network에서 **document 응답 HTML** 안에 로그인 UI가 이미 있는지 확인 (JS 실행 전 판정)
- [ ] 새로고침 때 "로그인 버튼 → 깜빡이고 이름" 현상이 없는지 확인
- [ ] 쿠키를 읽으면 해당 경로가 동적 생성으로 바뀔 수 있음 → **7주차 성능 기준을 다시 깨지 않는지** 확인하고 기록

### 1-3. proxy.ts 가드 + 경로 복원

- [ ] `proxy.ts` 생성: 미로그인으로 보호 경로 진입 시 `/login`으로 리다이렉트
- [ ] 리다이렉트 시 원래 경로를 파라미터로 실어 보내기
- [ ] 로그인 성공 후 원래 경로로 복원하는 로직 작성 (파라미터 없으면 기본 페이지)
- [ ] **외부 주소 차단**: `https://evil.com`, `//evil.com` 같은 값을 넣었을 때 안 나가는지 확인
- [ ] 로그인 상태에서 `/login` 접근 시 동작 정하기 (예: 홈으로) + 이유

### 1-4. 만료 처리

- [ ] 정한 "한 곳"(래퍼/인터셉터 등)에 401 감지 → 로그아웃 정리 → 만료 안내와 함께 로그인으로 이동 로직 작성
- [ ] 복원 파라미터가 만료 경로에서도 이어지는지 확인
- [ ] `?scenario=expired` (또는 scenario 쿠키) 붙여서 세션 만료 재현 → 화면이 "다시 로그인하세요" 같은 **다음 행동 안내**를 하는지 확인
- [ ] 만료 안내 화면 문구 작성

### 1-5. 동작 확인 (`pnpm start` 필수)

- [ ] `pnpm start`로 production build를 띄운다 (빌드 통과 ≠ 동작)
- [ ] 미로그인 → 보호 경로 진입 → 로그인 페이지로 이동 확인
- [ ] 로그인 → 원래 가려던 경로로 복원 확인
- [ ] 만료 시나리오 → 안내 화면 확인
- [ ] 틀린 비밀번호 → 에러 메시지 확인
- [ ] 보호 경로에서 500이 아닌지 확인
- [ ] 위 플로우 전체를 다시 한 번 스스로 밟아본다 (완료조건: 이것뿐)

## 2단계 — 이벤트를 계측해요 📊

> `src/analytics/`의 로거(provider.ts / consoleProvider.ts / logger.ts)는 **절대 다시 만들지 않는다.**

### 2-0. 스키마 설계 (먼저!)

- [ ] **이벤트 이름 규칙** 정하기 (예: `product_list_view`처럼 무엇_행위 통일)
      → "나중에 이 이름으로 무엇을 셀 것인가"를 먼저 생각. `button_click` 하나로 몰면 아무것도 못 셈
- [ ] **공통 프로퍼티** 목록 정하기 (sessionId, device, ts 등 — 시드 로그의 필드 참고)
- [ ] RFC A절에 쓸 내용으로 초안 메모 (이름 규칙 + 공통 프로퍼티)

### 2-1. 초기화와 공통 프로퍼티

- [ ] `initAnalytics()`를 부를 위치 정하고 **근거 메모** (호출 위치에 따라 큐에 쌓이는 이벤트가 달라짐)
- [ ] `setCommonProperties()`로 정한 공통 프로퍼티 넣기

### 2-2. 계측 지점 배치

- [ ] 목록 진입에 `track()` 넣기
- [ ] 상세 진입에 `track()` 넣기
- [ ] 장바구니 담기에 `track()` 넣기
- [ ] 로그인 시작 / 성공 / 실패 각각에 `track()` 넣기
- [ ] 주문 시작 / 주문 완료에 `track()` 넣기
- [ ] 내 앱에 없어서 **뺀 화면은 따로 기록**해두기 (RFC에서 왜 빠지는지 씀)
- [ ] 로그인 성공 시점에 `identify("looperN")` 연결
- [ ] 로그아웃 시점에 `reset()` 연결 (1단계의 로그아웃 흐름에 붙임)

### 2-3. 구조와 문서

- [ ] 컴포넌트가 `track()`을 직접 부를지, 한 겹 두를지 **판단하고 이유 메모** (6주차 FSD 경계 유지)
- [ ] 시드 로그 이벤트 이름 ↔ 내 이름 **매핑 표** 작성 (RFC A절)
- [ ] 콘솔(consoleProvider)에서 실제로 찍히는 걸 확인

### 2-4. 완료조건 자가 점검

- [ ] 로그인 → 목록 → 상세 → 담기 → 주문까지 한 번 통과
- [ ] 남은 이벤트 이름과 순서를 목록으로 적고, **문서만 보고 예측한 것과 실제 콘솔이 일치**하는지 대조 (틀리면 문서 수정)

## 3단계 — E2E 범위를 정해요 🗺️ (이번 주의 심장)

> 산출물: `docs/rfc/week09-e2e-scope.md`. **E2E 코드보다 먼저 커밋.**

### 3-0. 파일 준비

- [ ] `docs/rfc/week09-e2e-scope.md` 생성 (A/B/C 절 뼈대 잡기)

### 3-1. A절 — 이벤트 스키마

- [ ] 2단계에서 정한 이름 규칙 정리해서 옮기기
- [ ] 공통 프로퍼티 정리해서 옮기기
- [ ] 시드 로그 매핑 표 옮기기

### 3-2. B절 — 시드 로그 분석

- [ ] 노이즈 걸러내기 **기준 정의**: 봇 세션 / 오류 이벤트 / 중복 전송을 각각 어떻게 식별·제외했는지 문장으로 (로그에 "이건 봇" 표시는 없음)
- [ ] **거르기 전** 순위 집계 (그냥 세면)
- [ ] **거른 후** 순위 집계 (노이즈 기준 적용)
- [ ] 전후 비교: 바뀌었다면 무엇이, **안 바뀌었다면 왜 안 바뀌었는지** 쓰기 (안 바뀌는 것도 결과)
- [ ] 상위 경로를 **세션 기준**으로 순위 매기기 (이벤트 수 기준 금지 — 부풀려짐)
- [ ] 경로 단위 정하기: 이벤트 하나하나 / 화면 단위 묶음 → 묶었다면 묶은 기준 쓰기
- [ ] 표 채우기 — **비율**: 분모 명시 (전체 세션? 노이즈 제외? 앞 단계 통과 세션?)
- [ ] 표 채우기 — **이탈률**: 정의 선택 후 명시 ("세션의 마지막 이벤트였던 비율" vs "다음 단계로 못 넘어간 비율")
- [ ] 표 채우기 — **실패 비용**: 실패로 셀 이벤트 직접 정의 + 비율 + 이 화면이 막히면 뒤따라 막히는 것 쓰기
- [ ] 표 채우기 — **E2E 여부(가설)**: 일단 가설로 적고 최종은 C절에서
- [ ] 로그에는 있는데 내 코드에 화면이 없는 이벤트 → E2E 대상에서 빼고 **왜 빠지는지 근거로 남기기** (화면을 새로 만들 필요는 없음)

### 3-3. C절 — 붙일 곳과 안 붙일 곳

- [ ] **인증 플로우 필수**로 명시 (빈도 낮아도 붙이는 대표 사례 — 로그인이 막히면 전부 막힘)
- [ ] 인증 외 추가 후보 리뷰: **2개 이하**, 로그 근거로 고르기 (0개도 답 — 안 골랐으면 그 이유 쓰기)
- [ ] 고른 시나리오마다 "왜 이건지" 문장 쓰기
- [ ] ⚠️ 후보가 "빈도 1위"라면 → 8주차에 이미 통합 테스트로 검증했는지 확인 (중복 투자 체크)
- [ ] **빈도 높은데 E2E 안 붙인 경로 1개 이상** + 통합 테스트로 충분한 이유
- [ ] **빈도 낮은데 붙인 경로**(= 인증)에 "로그만 보고 정하면 안 되는 이유" 쓰기
- [ ] E2E 시나리오 1개 골라 **유지보수 비용 추정** (문구/구조 바뀔 때 고쳐야 하는 곳 수 세기)
- [ ] 총 E2E 시나리오가 **3개 이하**(인증 포함)인지 확인

### 3-4. 완료조건 & 커밋

- [ ] 자가 점검: 이 문서만 읽고 4단계에 어떤 테스트가 들어갈지 예측 가능한가?
- [ ] 자가 점검: **만들지 않기로 한 것과 근거**가 문서 안에 있는가?
- [ ] ⭐ RFC를 **E2E 코드보다 먼저 커밋** (결정이 근거보다 늦으면 "갖다 붙인 근거"가 됨)

## 4단계 — E2E를 구현해요 🎭

> 3단계 표에 있는 것**만** 만든다. 개수 늘리지 않기.

### 4-0. 환경

- [ ] Playwright가 production build 위에서 도는지 설정 확인 (8주차 환경 유지)
- [ ] `playwright.config`에 trace 옵션 설정 (`on-first-retry` 또는 on)

### 4-1. storageState와 격리 설계

- [ ] 로그인 1회 저장용 setup 만들기 (storageState로 재사용 — 매번 폼 채우기 금지)
- [ ] 저장 파일을 **워커별로 분리**하는 방법 설계 (계정 8개 활용 — 워커×저장파일 1:1)
- [ ] 워커별로 **계정을 갈랐는지** 기록 (계정·데이터·스토리지 중 무엇을 갈랐는지 남김)
- [ ] 로그인 자체를 검증하는 테스트는 storageState를 **안 쓰도록** 프로젝트 구조로 강제하고 **그 이유를 메모**
      → 저장된 상태로 시작하면 로그인 과정을 안 거치므로 테스트 불가

### 4-2. 인증 필수 3갈래 (storageState 금지 구역 아님—주의: 이 테스트들은 각각 성격에 맞게)

- [ ] 테스트 ① 미로그인 → 보호 경로 → 로그인 → **원래 경로 복원** (이 테스트는 storageState 없이)
- [ ] 테스트 ② 세션 만료: `expired` 시나리오로 재현 (`context.addCookies` 또는 query)
- [ ] 테스트 ③ 잘못된 자격 증명: `invalid` 시나리오 또는 틀린 비밀번호 입력
- [ ] 에러 테스트가 타임아웃 나면 서버 상태 라이브러리(Retry 등) 정책 확인 메모

### 4-3. 3단계에서 정한 추가 시나리오

- [ ] C절에서 정한 나머지 시나리오만 구현 (표에 없는 건 만들지 않는다)
- [ ] 셀렉터를 **역할/이름 기반**으로 정리 (`getByRole`)
- [ ] `getByTestId`를 썼다면 **왜 다른 방법이 안 됐는지** 메모
- [ ] `grep -r "waitForTimeout"` — 시간 기반 대기 **0개** 확인, 조건 기반 대기만 사용

### 4-4. trace 학습 (설정만 하고 안 열어보면 미달)

- [ ] 통과하는 테스트의 단언 하나를 **일부러 틀리게** 바꾸기 (테스트 코드만, 구현 X)
- [ ] `--trace=on` 실행 → `test-results/` 아래 `trace.zip` 확인
- [ ] `pnpm exec playwright show-trace <경로>`로 열고 어느 단계에서 무엇을 기다리다 멈췄는지 관찰
- [ ] 단언 원래대로 되돌림 + **무엇을 봤는지 한두 줄 기록**

### 4-5. 완료조건 검증

- [ ] `--workers=4` 실행 결과 == `--workers=1` 실행 결과
- [ ] 같은 테스트 **3회 연속** 실행 결과 동일 확인
- [ ] 한 번이라도 어긋나면 격리(계정/데이터/스토리지) 설계 재점검

## 5단계 — E2E가 무엇을 잡는지 확인해요 🔬

> 인증 **구현**만 망가뜨린다. **테스트 코드는 절대 건드리지 않는다.**

### 5-0. 설계

- [ ] 실험 후보 3개 이상 미리 리스트업 (한 번에 변수 하나!)
- [ ] 그중 **1개는 통합 테스트가 못 잡는 것**으로 고르기: 미들웨어 리다이렉트 / 쿠키 속성 / 초기 HTML의 로그인 상태

### 5-1. 실행 (실험 하나 = 망가뜨리기 → 실행 → 기록 → 복구)

- [ ] 실험 1: 구현 한 곳만 망가뜨리기 (예: 가드 조건 뒤집기) → E2E 실행 → 결과 표 기록 → 되돌리기
- [ ] 실험 2: (예: 복원 경로 지우기) → 실행 → 기록 → 되돌리기
- [ ] 실험 3: (예: 만료 분기 제거 / 초기 HTML 로그인 상태 제거 등 E2E-only 후보) → 실행 → 기록 → 되돌리기
- [ ] 각 실험 표 채우기: # / 망가뜨린 곳 / 어떻게 바꿨나 / 결과(잡힘·살아남음) / 실패한 테스트 / **실패 메시지로 원인 알 수 있었나**

### 5-2. 해석

- [ ] 살아남은 변경 있으면: 테스트를 고치고 **왜 못 잡았는지** 쓰기 (숨기지 말 것 — 가장 값진 기록)
- [ ] 통합 테스트로도 잡히는 실험이 있으면: 그 시나리오를 E2E에 둘 이유 재판단 → 없으면 **지우는 것도 답**
- [ ] `git diff`로 망가뜨린 코드가 하나도 남지 않았는지 확인

### 5-3. 완료조건

- [ ] 실험 기록 표가 있는가
- [ ] **E2E만 잡을 수 있었던 항목이 최소 1개** 확인되는가
