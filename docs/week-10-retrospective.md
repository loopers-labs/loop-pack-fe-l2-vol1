# 글로 적은 규칙은 네 번 실패했다

10주 동안 프론트엔드 과제를 하면서 같은 실수를 네 번 했다. 매번 원인을 알아냈고,
매번 문서에 적었다. 8주차 회고에는 이렇게까지 썼다.

> 이번 주에 배운 것 중 다음 주에도 쓸 것은 이 한 줄이다.

그리고 **다음 주에 또 틀렸다.** 두 번 더.

마지막 주 과제가 「AI가 찾은 반복 패턴을 결정적 하네스로 굳혀라」였다. 그래서 그 한 줄을
ESLint 룰로 내렸다. 룰을 켜자마자 **이미 머지된 내 코드에서 위반 2건**이 나왔다.

네 번 반복했다고 문서에 두 번 써 놓고, 다섯 번째와 여섯 번째가 레포에 살아 있었다.

이 글은 그 얘기다.

---

## 그 한 줄이 무엇이었나

> **단언이 "없음"이나 boolean을 향하면, 실패할 때 대신 무엇이 있었는지 말하지 못한다.**

8주차에 테스트를 짜면서 처음 만났다. 구현을 일부러 망가뜨려 테스트가 잡는지 확인하는
단계였는데(변이 실험), 8개 중 7개는 잡혔다. 문제는 잡힌 방식이었다.

```ts
// 500 에러가 경계로 전파되는지 본다
await screen.findByText("경계가 오류를 받았습니다");
```

이게 실패하면 메시지는 *"그 문구가 없다"* 와 DOM 덤프다. **무엇이 없는지는 말하지만
대신 무엇이 그려졌는지는 덤프를 읽어야 나온다.** 인라인 에러가 새고 있었는지, 아무것도
안 그려졌는지, 화면이 로딩에 멈춰 있었는지 — 메시지가 가르지 않는다.

반대로 잘 읽힌 자리도 있었다. 9주차에 프록시 가드를 망가뜨렸을 때다.

```
Expected  "/login?next=%2Fcheckout%3FproductId%3Dp3%26quantity%3D2"
Received  "/checkout?productId=p3&quantity=2"
```

이 한 쌍이 "가드가 안 돌았다"를 바로 말한다. **값을 값으로 대조했기 때문**이다.

차이는 명확했다. 있는 것을 잡아 값으로 대조하면 통과할 때도 실패할 때도 말을 한다.
없음을 단언하면 통과할 때만 정확하다.

그래서 적었다. 그리고 네 번 틀렸다.

---

## 네 번

### ① 8주차 — 경계 문구를 기다렸다

위에 쓴 그 자리다. 알림 하나를 잡고 **문구로 가르도록** 고쳤다. 인라인 에러와 경계
fallback이 둘 다 `role="alert"`이라 그게 가능했다.

### ② 9주차 — 폴링으로 "안 바뀜"을 보려 했다

세션 만료 상태가 재조회에 지워지지 않는 것을 검증하는 테스트였다.

```ts
queryClient.setQueryData(SESSION_QUERY_KEY, EXPIRED);  // 서버가 심어 준 상태
await queryClient.refetchQueries({ queryKey: SESSION_QUERY_KEY });
expect(await screen.findByText("상태: expired")).toBeInTheDocument();  // ← 초록불
```

**통과했다. 그리고 조회 함수를 `anonymous`를 돌려주도록 망가뜨려도 통과했다.**

`refetchQueries`를 `await`한 직후에는 React가 아직 리렌더하지 않는다. DOM에는 심어 둔
`expired`가 그대로 남아 있고, `findByText`는 그걸 즉시 찾는다.

여기서 원칙이 한 겹 더 드러났다. **"바뀌지 않았다"는 조건 기반 대기로 확인할 수 없다.**
폴링은 *"아직 안 바뀜"* 과 *"바뀌지 않는 게 맞음"* 을 구분하지 못한다.

화면이 아니라 조회 결과를 값으로 대조하도록 고쳤다.

```ts
expect(queryClient.getQueryData<SessionState>(SESSION_QUERY_KEY)).toEqual(EXPIRED);
```

### ③ 9주차 — 메커니즘만 보고 호출부를 빠뜨렸다

세션 만료 처리를 `QueryCache.onError`에만 붙여 놓고, 주석에 *"이 401이 세션 상태를
expired로 바꾼다"* 고 썼다. **거짓이었다.** 변경 요청(mutation)은 `QueryCache`를 타지
않는다. `MutationCache.onError`가 따로 필요했다.

더 나빴던 건 그걸 고치면서 쓴 테스트다. 로컬 컴포넌트에 `mutationKey`를 직접 박아 놓고
단언했더니, 실제 `useLogin`을 망가뜨려도 테스트가 통과했다. **테스트가 메커니즘은 보고
호출부는 안 봤다.**

### ④ 9주차 채점 — 라벨 하나에 두 의미

채점 피드백으로 받은 지적이다.

> E6(초기 HTML 로그인 상태 제거) 테스트에 실패했을 때 메세지만 보고는 "서버 렌더 실패"인지
> "로그인 안 됨"인지 구분을 할 수 없었어요.

헤더가 **세 상태를 두 모양으로** 그리고 있었다.

```
session === undefined      "아직 아무도 판정하지 않았다"  → 로그인 링크
session.status anonymous   "판정했고 미로그인이다"        → 로그인 링크   ← 겹침
session.status authenticated                            → 계정 이름
```

`aria-label="로그인 계정 …"` 하나가 「로그인됨」과 「서버가 그렸음」을 동시에 뜻했다.
라벨을 못 찾았다는 사실만으로는 둘을 가를 수 없다.

표시를 덧붙이지 않고 **겹친 상태를 갈랐다.** `undefined`를 「계정 확인 중」으로.
이건 테스트만의 문제가 아니었다 — 서버 주입이 빠지면 **로그인해 둔 사용자에게 한순간
「로그인」이 보인다.**

## 그런데 여기서 더 큰 게 나왔다

고치고 나서 변이를 다시 돌렸는데, `E6`이 실은 **두 변이**였다.

| | 무엇을 바꿨나 | 기존 테스트 |
| --- | --- | --- |
| **E6a** | 서버가 세션을 심는 줄을 지운다 | **전부 통과** |
| **E6b** | 판정 결과를 `anonymous`로 바꾼다 | 잡힘 |

**E6a는 계정 라벨을 보는 단언으로 아예 안 잡히는 변이였다.** 서버 주입이 없어도
하이드레이션 후 클라이언트 조회가 라벨을 채우기 때문이다.

즉 설계 문서에 「E6 잡힘 3건」으로 적어 둔 것은 E6b 쪽이었고, **그것도 `staleTime` 60초
덕이었다.** 심어 둔 값이 60초간 fresh라 재조회가 안 일어나서 화면이 미로그인으로 남았던
것이다. 단언의 힘이 아니었다.

캐시 옵션이 변이를 잡아 준 것을 테스트의 힘으로 오인하고 있었다.

고친 뒤에는 초기 HTML을 직접 읽고 **네 값 중 하나로 접어 대조**한다.

```ts
// page.goto를 쓰지 않는다 — 하이드레이션이 증거를 덮는다
const response = await page.request.get("/checkout?productId=p3&quantity=2");
expect(serverRenderedSession(await response.text(), account.name)).toBe(SERVER_SESSION.login);
```

이제 두 변이가 같은 단언에 **다른 값**을 돌려준다.

```
E6a → "세션을 판정하지 않았다 — (shop) layout의 주입이 빠졌다"
E6b → "미로그인으로 그렸다 — 쿠키가 없거나 로그인이 안 됐다"
```

## 마지막 주 — 기계에 새겼다

10주차 과제의 결론이 *"AI를 잘 쓴다 = 맹신이 아니라, AI가 찾은 반복 패턴을 결정적
하네스로 굳혀 AI·사람 리뷰의 부담을 줄이는 것"* 이었다.

내 반복 패턴은 위의 넷이다. 그런데 **넷 전부를 룰로 만들 수는 없었다.**

| 항목 | 어디로 | 왜 |
| --- | --- | --- |
| `waitFor` 안의 부정 단언 | **기계** | AST로 판별된다 |
| `toBeTruthy` · `toBeFalsy` | **기계** | 호출 이름 하나다 |
| 신호 하나에 두 의미가 겹쳤나 (④) | **사람** | `aria-label`이 무엇을 뜻하는지는 의미 판단이다 |
| 호출부까지 봤나 (③) | **사람** | 설계 판단이다. 변이 실험이 그 자리를 맡는다 |

결정적으로 참·거짓을 가를 수 있는 것만 내렸다.

```js
{
  selector: 'CallExpression[callee.name="waitFor"] MemberExpression[property.name="not"]',
  message: "waitFor 안에서 부정 단언을 쓰지 않는다. 폴링은 '아직 안 바뀜'과 " +
           "'바뀌지 않는 게 맞음'을 구분하지 못해서, 구현을 망가뜨려도 초록불이 된다. " +
           "사라지는 것은 waitForElementToBeRemoved로, 바뀌지 않는 것은 값을 직접 대조한다.",
}
```

메시지에 **무엇을 대신 쓰라는지** 넣었다. 8주차에 배운 것이 여기도 적용된다 —
빨간불이 원인만 말하고 다음 행동을 말하지 않으면 반쪽이다.

### 켜자마자 2건

```
ProductListPage.filters.dom.test.tsx:177
  await waitFor(() => { expect(renderedNames()).not.toEqual(firstPage); });

ProductListPage.states.dom.test.tsx:245
  await waitFor(() => { expect(screen.queryByRole("alert")).not.toBeInTheDocument(); });
```

오탐이 아니라 진짜 위반이었다. 나는 이 결함을 알고 있었고 문서에 두 번 썼는데도
내 레포에 남아 있었다.

### 고치다가 하나 더

두 번째 자리를 룰 메시지가 말한 대로 `waitForElementToBeRemoved`로 바꿨더니
**도구가 거부했다.**

```
Error: The element(s) given to waitForElementToBeRemoved are already removed.
```

`user.click`을 `await`하는 동안 React가 리렌더하면서 refetch가 시작되고 `isError`가
즉시 꺼진다. **클릭이 끝나기 전에 알림이 언마운트된다.**

즉 옛 단언은 알림이 *"있었다가 없어진"* 것을 한 번도 증명하지 않았다. 그냥 "지금 없다"를
확인하고 통과했다. **재시도 버튼이 아예 안 그려졌어도 초록불이었을 것이다.**

제거를 관찰할 창이 없으므로, 목록이 그려진 **정착된 순간에 개수를 값으로** 센다.

```ts
expect(await screen.findByText(/총 \d+개/)).toBeInTheDocument();
// 폴링이 아니라 단발이고, 실패하면 몇 개가 있었는지 말한다(0을 기대했는데 1)
expect(screen.queryAllByRole("alert")).toHaveLength(0);
```

> 부정 단언 자체가 금지가 아니다. 금지는 **폴링 안의** 부정 단언이다.
> 정착된 순간의 단발 부정은 정확하다 — 룰의 selector를 `waitFor` 안으로 한정한 이유다.

### 승격하지 않은 것

같은 성질의 반복이 하나 더 있었다. **「설계 문서의 표와 실제 코드가 갈린다」는 지적을
세 라운드 연속으로 받았다.** 매번 "다음엔 대조하겠다"로 끝냈고 세 번 다 실패했다.

승격 대상으로 제일 값이 커 보였다. 그런데 룰로 만들면 *"테스트 파일이 바뀐 PR에서
문서가 안 바뀌면 경고"* 가 되고, **문구 수정에도 걸린다.** 오탐이 크다.

포기했다. **결정적으로 못 가르는 것을 억지로 게이트로 내리면, 그때부터 사람들이 게이트를
무시하기 시작한다.** 대신 커밋 관례로 적었다 — 테스트를 더하거나 지우는 커밋에서 표를
같은 커밋에 고친다.

이게 이번 주에 배운 경계다. **모든 반복을 룰로 만들 수는 없고, 만들면 안 되는 것도 있다.**

## 같은 주에 또 밟았다

그리고 이 글의 결론이 무색해지는 일이 같은 주에 났다.

룰을 추가하면서 `eslint.config.mjs`를 고쳤는데, CI에서 `format:check`가 빨간불이 됐다.
로컬에서는 통과했다. 원인이 둘 겹쳤다.

1. `pnpm check`에 `format:check`가 없다 — 로컬 습관으로는 확인되지 않는다.
2. lint-staged 패턴이 `*.{ts,tsx,js,jsx}`라 **`.mjs`를 잡지 않는다** — 커밋 훅도 포맷해 주지 않았다.

**이 함정은 내가 이미 알고 메모에 적어 둔 것이었다.** *"CI는 `format:check`를 돌지만
로컬 `pnpm check`엔 없다 — push 전 `format:check` 필수."*

「글로 적는 것은 실패했다」를 쓴 커밋에서, 글로 적어 둔 걸 또 어겼다.

그래서 이것도 아직 룰이 아니다. `package.json`과 커밋 훅을 고쳐야 하는데 이번 주 범위
밖이라 손대지 않았고, **살아 있는 함정으로 문서에 적어 뒀다.** 다음에 또 밟을 수 있다는
뜻이다.

## 남는 것

10주 동안의 결론은 한 문장이다.

> **같은 지적을 세 번 이상 받았다면, 리뷰가 부족한 게 아니라 하네스가 비어 있다는 뜻이다.**

근거가 두 겹으로 있다.

**글로 적는 것은 실패했다.** 규칙 파일에 *"`waitFor` 콜백엔 assertion 하나만"* 이 적혀
있었고, 회고에 *"다음 주에도 쓸 것은 이 한 줄"* 이라고 썼다. 그런데 세 번 더 틀렸다.

**룰을 켜니 즉시 2건이 나왔다.** 내가 안다고 생각한 것과 내 레포에 있는 것이 달랐다.

그런데 반대편 경계도 같이 배웠다. **오탐이 큰 것을 억지로 내리면 게이트 자체가 무시된다.**
그래서 세 번 반복된 문서 문제는 룰로 만들지 않았다. 결정적으로 판별할 수 있는 것만
기계에 주고, 맥락 판단은 사람과 AI에 남긴다 — 그게 "AI를 잘 쓴다"의 내 결론이다.

마지막으로, 이번 주에 가장 많이 쓴 도구는 ESLint가 아니라 **변이 실험**이었다.
형태로 못 보는 것은 "망가뜨려서 잡히는지"로 본다. 그리고 그게 세 번이나 내 테스트가
아무것도 잡지 못한다는 걸 알려줬다.

**고친 뒤에 다시 망가뜨려 보는 것이 고치는 일의 일부다.**
