## 📚 이번 주 학습

- 학습 주제: 인증 플로우의 경계(proxy · 서버 렌더 · 클라이언트 401)를 어디에 두는가, 로그로 E2E 범위를 정하는 법, storageState 와 워커 격리, trace 읽기, 뮤테이션으로 테스트 가치 검증
- 배운 것 / 새로 적용한 것: 아래 결정 목록

### 1단계 — 인증 결정

- **세션 만료(401)는 `features/auth/ui/session-boundary.tsx` 한 곳에서 처리한다.** 루트 layout 에 한 번 마운트되어 QueryCache·MutationCache 를 구독하고, 401 이 오면 "이 탭이 로그인 상태라고 믿던 중이었나"(세션 캐시에 user 가 있나)로 만료를 판정한다. `/api/auth/me` 가 미로그인과 만료를 같은 401 로 주기 때문에, 요청의 출처가 아니라 **클라이언트가 알던 상태**로 구분한다. 세션 캐시가 비어 있을 때의 401(로그인 폼 자격 증명 실패, 익명 세션 재확인)은 각 화면의 에러다. 만료로 판정하면 죽은 쿠키를 서버에서 지우고(logout 은 노브 영향 없이 204) 캐시를 비운 뒤 `/login?next=<지금 경로>&reason=expired` 로 보낸다. 화면마다 따로 처리하지 않으니 고칠 곳이 하나다.
- **보호 경로 경계: `/checkout`(주문서) · `/orders`(주문 내역) · `/mypage`.** 장바구니·위시리스트는 페이지를 만들지 않고 헤더 개수 + 카드 토글로만 존재하는 **게스트 상태**라 보호하지 않는다(로그인 없이 담을 수 있어야 담기→로그인→주문 퍼널이 성립한다). 장바구니 내용을 보는 유일한 화면이 주문서라 열람은 로그인 뒤지만, 상태 자체는 계정에 묶이지 않는다.
- **가드는 두 겹.** `src/proxy.ts` 는 세션 쿠키의 **존재만** 확인한다 — 서명 검증은 비밀키가 필요하고 어차피 서버 페이지(`requireServerSession`)와 API 가 다시 검증하므로, proxy 는 "로그인한 적 없는 요청"만 걸러 `next` 를 실어 보낸다. 쿠키가 있는데 검증에 실패(만료·위조)하면 서버 페이지가 `reason=expired` 를 붙인다.
- **복원 경로는 `next` 파라미터.** `sanitizeReturnTo` 가 `/` 로 시작하지 않거나 `//`·`/\` 로 시작하거나 공백·제어 문자를 포함하거나 `/login`·`/api` 로 가는 값을 전부 `/` 로 떨어뜨린다. proxy·로그인 페이지·로그인 폼이 같은 함수를 쓴다. 단위 테스트 15개 + E2E 1개.
- **로그아웃 시 장바구니·위시리스트는 유지한다.** 계정에 묶인 서버 상태(세션·주문 쿼리)만 비운다. persist 가 없어 새로고침에 사라지는 것도 8주차부터 지켜온 스펙이라, 로그아웃이 "이 기기에서 내 흔적 지우기"가 아니라 "계정 연결 끊기"다. 로그아웃과 만료가 같은 `clearClientSession` 을 쓴다.
- **초기 HTML 에 로그인 상태:** 루트 layout 이 `cookies()` 로 세션을 읽어 헤더에 넘긴다. 대가로 **모든 라우트가 동적 렌더**가 됐다. 7주차에 측정한 `/`·`/products` 는 이미 동적이었고 정적이던 것은 데모 3개(`/dialog`·`/select`·`/performance-lab/inp`)뿐이라 받아들였다(`pnpm build` Route 표에서 ○ 0개 확인).
- **세션은 서버 상태 → TanStack Query.** 5주차 zustand 패턴을 그대로 쓰지 않았다. 서버 초기값을 `initialData` 로 받고 `staleTime: 0` 으로 마운트·탭 복귀 시 재확인한다 — 보호 데이터 요청이 없는 마이페이지에서도 만료를 알 수 있다.
- 브라우저에서만 드러난 결함 2개(런타임 검증에서 발견, 통합 145개는 초록이었다): 미로그인 상태의 헤더 `/checkout` 링크 prefetch 가 proxy 의 307 을 라우터 캐시에 남겨 로그인 후 복원이 그 캐시를 재생한 것(`prefetch={false}` + `router.refresh()`), 주문 성공 시 장바구니 비움이 주문서를 빈 화면으로 바꿔 버튼이 언마운트되며 호출 단위 콜백의 이동이 유실된 것(뮤테이션 레벨 콜백으로).

### 2단계 — 계측

RFC A절. 이름은 시드 스키마 그대로, 스키마는 `src/shared/analytics/events.ts` 한 곳, 컴포넌트는 `trackEvent` 만 부르고 스타터 로거 직접 import 는 린트로 금지. 상세 화면이 없어 `product_detail_view` 는 계측하지 않았다. `identify`/`reset` 은 세션 상태 전이가 유일한 출처(`useSession` effect). `initAnalytics` 는 루트 Providers 의 `<AnalyticsInit/>` — 트리 위치에 결과가 의존하지 않도록 공통 프로퍼티 등록을 첫 `trackEvent` 에서 동기로 보장한다(검토에서 초안 근거가 틀린 것을 잡아 고쳤다). 로그인→주문 이벤트 순서는 RFC A.5 예측과 production 관측이 일치했다.

### 3단계 — 시드 로그

RFC B절. 노이즈: 완전 동일 줄 77개(간격 0초 재전송), `device: null` 세션 486개(전부 단일 `product_list_view`, 매일 01:00~~01:20Z), `client_error` 103건은 경로가 아니라 실패 신호. 필터 전후 **순위는 전부 그대로**였다 — 봇이 1위 경로에만 붙었기 때문이고, 바뀐 것은 목록 진입 이탈률(41.8% → 38.0%)이다. 빈도 높은데 안 붙인 경로: 목록 조작(60.5%, 8주차 통합 8~~11·E2E 13·14 가 지킴). 낮은데 붙인 경로: 인증(8.6%) — 뒤의 7.8% 세션이 전부 이 관문에 선다, 그리고 핵심 동작이 jsdom 밖(proxy·httpOnly 쿠키·초기 HTML·라우터 캐시)에 산다.

### 4단계 — E2E

RFC C.3 표대로 3파일. **storageState 경계:** 로그인 자체를 검증하는 `auth.spec.ts` 는 `{cookies:[], origins:[]}` 로 시작(검증 대상을 픽스처가 대신하면 지키는 게 없다); 만료·주문은 워커당 1회 **실제 로그인 폼**으로 만든 storageState 를 쓴다. **격리:** 계정 `looper{parallelIndex+1}` · 저장 파일 `test-results/.auth/worker-N.json` · 주문은 상대 개수(+1). `getByTestId` 는 쓰지 않았다(전부 role·label·text, 헤더는 `navigation "주요 메뉴"` 로 스코프). 시간 대기 없음. 결과: `--workers=4` 3회 = `--workers=1` = 12 passed. **trace:** RFC 부록 B.3 — 단언 하나를 고의로 틀려 `--trace=on` 으로 열고 "느려서가 아니라 기대값이 틀렸다"를 읽었다. **8워커 15회 중 1회 실패**가 앱의 경합(로그인 성공 직전에 시작된 미인증 `me` 재확인의 늦은 401)을 드러내 `cancelQueries` + `AbortSignal` 로 고쳤고 회귀 테스트를 뒀다(부록 B.2). 8주차 설정 변경: `reuseExistingServer: false`(dev 서버 위에서 조용히 돌지 않게), `workers: CI 2 / 로컬 4`, `retries: 0`.

### 5단계 — 실험

RFC 부록 A. 6개(+5′). **E2E 만 잡은 것:** 서버 컴포넌트의 `next` 읽기 제거, layout 의 서버 세션 미전달(초기 HTML). **살아남은 것:** 5번(뮤테이션 콜백 안 순서 바꾸기)은 동치 뮤턴트 — 대신 잘못된 인과를 말하던 주석을 고쳤다. 5′(실제 있었던 결함 형태)은 E2E 만 잡았고 통합의 공백이라 `checkout-page.dom.test.tsx` 를 추가해 통합에서도 잡게 했다. 그래도 주문 E2E 는 남긴다 — 서버 저장→재조회 왕복은 MSW 가 흉내낼 뿐이다.

### Advanced B — 에이전트 생성 검수

RFC 부록 C. `init-agents --loop=claude` 로 planner → generator 를 돌렸다(이 세션엔 MCP 도구가 없어 정의 파일의 프롬프트를 범용 에이전트에 주고 브라우저 조작만 스크립트로 대체 — 기록에 명시). planner 14 시나리오, generator 8 테스트(`e2e-generated/`, 게이트 밖). **지운 단언:** 픽스처 이름·가격 리터럴(`WOOD GLOVES`, `52,000원`), `context.cookies()` 의 `session` 부재(구현 세부), `toHaveURL` 뒤의 `page.url()` 재확인과 `/login` 에서 `주문 내역` heading hidden(동어반복), 절대 URL → 상대 경로. 지운 뒤 8개 재통과. **healer 미사용:** 이번 주 빨간불은 전부 앱이 틀린 것이었고 healer 는 테스트를 현재 동작에 맞춰 초록으로 덮는 도구라, 5단계의 "잡힘" 과 양립하지 않는다. 생성물의 강점은 탐색·초안·셀렉터 스코프 수법(`region {exact:true}`), 약점은 범위 확장·픽스처 단언·공유 구조(storageState·POM·격리) 부재였다.

## 🤔 고민한 점 / 막혔던 부분

- `/api/auth/me` 401 을 `getSession` 에서 null 로 접었다가, 검토에서 "세션 쿼리가 먼저 401 을 받으면 뒤의 주문 401 이 만료로 안 잡힌다"는 지적을 받고 한 채널(에러)로 되돌렸다. "한 곳에서 처리"는 처리 코드가 한 곳인 것만으로는 부족하고 **신호가 한 채널로 들어와야** 성립했다.
- 5번 실험이 살아남은 것을 "테스트 공백"으로 볼지 "동치 뮤턴트"로 볼지. 뮤테이션 레벨 콜백은 언마운트와 무관하게 실행되므로 관찰 가능한 차이가 없다 → 동치. 대신 진짜 결함 형태(5′)를 다시 넣어 테스트 공백을 찾았다.

## 🙋 피드백 받고 싶은 부분

- 만료 판정 기준을 "요청의 출처"가 아니라 "클라이언트가 알던 상태"로 둔 것이 맞는지.
- 루트 layout 에서 `cookies()` 를 읽어 전 라우트를 동적으로 만든 선택. 대안(헤더만 클라이언트 fetch, 또는 라우트 그룹으로 layout 분리)보다 나은지.

## 🤖 AI 활용

Claude Code 로 구현·검증을 진행했다. 단계마다 요구사항 검토 에이전트와 런타임 검증 에이전트를 병렬로 돌려 지적을 반영했다. **E2E 범위(인증 외 어디에 붙일지)는 시드 로그 집계 표와 후보 3개를 놓고 내가 직접 선택했고**(주문 완료 플로우 1개), 단언 대상은 RFC C.1 표에 먼저 적고 그대로 구현했다. 계측 코드·MSW 픽스처·Page Object·집계 스크립트 같은 반복 코드는 AI 가 작성했다.
