# 8주차 테스트를 만들며 확인한 것

이번 과제에서는 테스트 개수를 늘리는 것보다 **지켜야 할 동작을 먼저 정하고, 테스트가 실제 문제를 잡는지 확인하는 것**에 집중했습니다.

먼저 15개 동작을 어떤 테스트로 확인할지 정했습니다. 테스트를 구현하면서 실제로 드러난 문제를 고쳤고, 마지막에는 구현을 일부러 망가뜨려 테스트가 실패하는지도 확인했습니다.

처음 세운 계획과 각 테스트를 선택한 이유는 [8주차 테스트 계획](../rfc/week08-test-plan.md)에 남겼습니다. 이 문서에는 계획을 실행하면서 확인한 결과를 정리했습니다.

## 이번 과제에서 확인한 결과

| 테스트하면서 확인한 문제 | 바꾼 내용 | 다시 확인한 결과 |
| --- | --- | --- |
| 기본 목록을 뜻하는 두 조건이 서로 다른 query key를 만든다는 걸 알았습니다. | 생략한 카테고리를 `all`로 바꿨습니다. | 두 조건이 같은 query key를 만들었습니다. |
| 상품 검색·카테고리·정렬을 이름으로 구분할 수 없었습니다. | 각 입력에 용도를 알려주는 이름을 붙였습니다. | 사용자가 인식하는 이름으로 요소를 찾을 수 있었습니다. |
| 화면 없는 테스트도 DOM과 MSW 설정을 불러오고 있었습니다. | 공통 설정을 없애고 필요한 테스트에서만 설정을 불러왔습니다. | 화면 없는 테스트는 별도 준비 없이 `node`에서 실행됐습니다. |
| Dialog 테스트 이름과 실제 확인 내용이 달랐습니다. | 이름에 적힌 `className` 전달 여부를 직접 확인했습니다. | 기존 테스트만으로는 `className` 전달 여부를 알 수 없어서 단언을 보강했습니다. |
| 이전 목록 유지 동작에 자동 테스트가 없었습니다. | 실패 후 목록 유지와 재시도 흐름을 통합 테스트로 남겼습니다. | 이미 고친 동작이 다시 깨지는지 확인할 수 있었습니다. |
| 로딩 화면을 지워도 기존 테스트가 통과했습니다. | 로딩 안내가 나타났다가 사라지는지 확인했습니다. | 로딩 안내를 지우자 해당 테스트가 실패했습니다. |

기존 테스트와 새 테스트는 `pnpm check` 한 번으로 함께 실행했습니다. 화면이 필요 없는 테스트는 `node`, 화면이 필요한 테스트는 jsdom에서 실행했습니다. 페이지 이동과 새로고침은 production build를 실행한 실제 브라우저에서 확인했습니다.

## 테스트하면서 발견한 문제

### 같은 목록에 서로 다른 query key가 만들어졌습니다

상품 목록 조건에서 `category`를 생략한 경우와 `category: 'all'`을 직접 넣은 경우는 같은 목록을 뜻합니다. 하지만 처음 테스트를 실행했을 때 두 조건이 서로 다른 query key를 만들었습니다.

이 상태에서는 같은 기본 목록이 React Query 캐시에 두 번 저장될 수 있습니다. `PRODUCT_LIST_DEFAULTS.category`를 `'all'`로 정하고, query key를 만들 때 생략한 값을 기본값으로 바꿨습니다.

이제 다음 두 조건이 같은 query key를 만드는지 확인합니다.

```ts
productListQueryOptions({})
productListQueryOptions({ category: 'all' })
```

### 입력 요소를 이름으로 찾을 수 없었습니다

통합 테스트에서는 사용자가 화면에서 인식하는 역할과 이름으로 요소를 찾으려고 했습니다. 하지만 상품 검색, 카테고리, 정렬 입력에는 용도를 알려주는 이름이 없어서 서로 구분하기 어려웠습니다.

각 입력에 다음 이름을 추가했습니다.

- 상품 검색
- 카테고리
- 정렬

새로 작성한 상품 목록 통합 테스트에서는 `getByTestId` 대신 이 이름으로 요소를 찾았습니다. 테스트를 작성하면서 화면 읽기 도구도 입력의 용도를 알 수 있도록 함께 고쳤습니다.

### Dialog 테스트가 이름에 적힌 동작을 확인하지 않았습니다

기존 Dialog 테스트 이름에는 `custom className`을 전달한다고 적혀 있었습니다. 하지만 실제로는 Dialog가 열리고 Overlay를 누르면 닫히는지만 확인했습니다. 기존 단언만으로는 Dialog가 `className`을 전달하는지 알 수 없었습니다.

테스트 이름과 실제 확인 내용을 맞추기 위해 다음 내용을 추가했습니다.

- Dialog 내용에 표시용 `custom-content` 클래스가 전달되는지 확인했습니다.
- Overlay에 표시용 `custom-overlay` 클래스가 전달되는지 확인했습니다.
- Overlay를 누르면 Dialog가 닫히는지도 계속 확인했습니다.

Select 테스트도 내부에서만 쓰는 `data-disabled` 대신 사용자가 실제로 영향을 받는 `role="option"`과 `aria-disabled`를 확인하도록 바꿨습니다.

### 기존 목록 유지 동작에 자동 테스트가 없었습니다

새 목록을 불러오다 실패했을 때 이전 목록을 유지하는 코드는 8주차 과제를 시작하기 전에 이미 구현돼 있었습니다. 이번 주에 새로 고친 기능은 아닙니다.

하지만 해당 동작을 자동으로 확인하는 테스트가 없었습니다. 목록 유지 코드가 사라져도 기존 테스트에서는 알 수 없었습니다. 이번 주에는 카테고리 변경 요청을 실패시켜 기존 상품과 실패 안내가 함께 남는지 확인하는 통합 테스트를 추가했습니다.

통합 테스트에서는 다음 흐름을 확인했습니다.

1. 기존 상품 목록을 보여줍니다.
2. 카테고리를 바꾼 뒤 요청을 실패시킵니다.
3. 실패 안내와 기존 상품이 함께 남는지 확인합니다.
4. 다시 시도에 성공하면 새 카테고리 상품으로 바뀌는지 확인합니다.

처음 계획에서는 이 경우를 다음에 추가할 대상으로 뒀습니다. 구현 상태를 다시 확인한 뒤, 이미 고친 중요한 동작에 테스트가 없다는 점을 발견해 이번 범위에 포함했습니다.

## 테스트를 세 가지로 나눈 기준

테스트할 동작에 따라 다음 세 가지 방법을 사용했습니다.

| 테스트 종류 | 이 방법을 쓴 경우 | 확인한 내용 |
| --- | --- | --- |
| 단위 테스트 | 화면 없이 계산만 확인할 경우 | 장바구니와 위시리스트 개수, query key, 상품 검색·정렬·페이지 계산 |
| 통합 테스트 | 화면 조작과 API 응답을 함께 확인할 경우 | 로딩·빈 결과·에러·재시도, 필터·정렬·페이지 이동, 위시리스트와 헤더 개수 |
| E2E 테스트 | URL·방문 기록·새로고침처럼 실제 브라우저 동작을 확인할 경우 | URL 재진입, 뒤로가기·앞으로가기, 새로고침, 상품 담기와 헤더 개수 |

## 헷갈렸던 선택

### 필터 변경은 통합 테스트로 확인했습니다

카테고리·정렬·페이지 변경은 통합 테스트로 확인했습니다. 선택값, API 요청, 화면에 나타난 상품을 한 번에 확인할 수 있기 때문입니다.

모든 경우를 E2E 테스트로 작성하면 실제 서버의 지연을 매번 기다려야 하고, 실패했을 때 원인을 찾기도 어려워집니다. 실제 URL에 조건이 남는지, 뒤로가기와 새로고침으로 복원되는지만 E2E 테스트에 맡겼습니다.

### 위시리스트와 헤더는 통합 테스트로 확인했습니다

상품 목록의 찜 버튼과 헤더의 위시리스트 개수가 같은 Zustand 상태를 사용하는지 통합 테스트로 확인했습니다. 전체 페이지를 실행하는 E2E 테스트로도 확인할 수 있지만, 장바구니 E2E와 확인 범위가 겹쳐 추가하지 않았습니다.

## 테스트 환경을 나눈 이유

### 화면이 필요한 테스트만 jsdom에서 실행했습니다

같은 테스트 파일 8개를 두 환경에서 한 번씩 실행해 다음 결과를 확인했습니다.

| 비교한 내용 | 모두 jsdom에서 실행 | 필요한 테스트만 jsdom에서 실행 |
| --- | --- | --- |
| 실행 환경 | 8개 파일 모두 jsdom | 화면 없는 테스트는 `node`, Select와 Dialog는 jsdom |
| Vitest `environment` 시간의 합 | 40.71초 | 6.94초 |

한 번씩 실행한 값이라 정확한 성능 비교는 아니지만, 화면이 필요 없는 테스트까지 jsdom을 준비하는 비용이 크다는 점을 알 수 있었습니다.

환경을 나눈 뒤에도 공통 `setupFiles`가 모든 테스트에서 실행되는 문제가 남아 있었습니다. 화면 없는 테스트도 Testing Library의 DOM 정리 코드를 불러오고 MSW 서버를 시작했습니다. 환경 이름만 `node`로 바꿔서는 준비 코드까지 나뉘지 않았습니다.

공통 설정을 없애고 필요한 테스트에서만 설정 파일을 직접 불러오도록 바꿨습니다.

- 기본 테스트 환경은 `node`로 설정했습니다.
- Select, Dialog, 상품 목록 통합 테스트만 jsdom에서 실행했습니다.
- DOM matcher와 Testing Library의 정리는 jsdom 테스트에서만 준비했습니다.
- MSW 서버는 상품 목록 통합 테스트에서만 시작했습니다.

### 요청 코드는 실제로 실행하고 응답만 준비했습니다

통합 테스트에서는 앱의 `fetch`나 상품 API 함수를 가짜 함수로 바꾸지 않았습니다. 화면에서 상품 목록을 요청하는 실제 코드를 그대로 실행했습니다. 서버로 나가는 요청만 MSW가 받아서 테스트에 필요한 응답을 돌려줬습니다.

- 공통 MSW 응답에는 성공 결과만 뒀습니다.
- 빈 결과, 에러, 느린 응답은 해당 테스트 안에서만 설정했습니다.
- 준비하지 않은 요청이 발생하면 테스트를 바로 실패시켰습니다.
- 테스트가 끝나면 바꾼 응답을 초기화했습니다.

각 통합 테스트는 새로운 QueryClient를 사용했습니다. 장바구니와 위시리스트도 테스트 시작 전에 빈 상태로 되돌렸습니다. 한 테스트에서 만든 상태가 다음 테스트에 남지 않게 하기 위해서입니다.

### E2E는 production build에서 실행했습니다

E2E 테스트는 개발 서버가 아니라 `next build` 결과를 `next start`로 실행해서 확인했습니다. 실제 API route의 지연도 그대로 거쳤습니다.

E2E는 실행 시간이 길어서 Vitest와 명령을 나눴습니다.

- `pnpm test`: Vitest를 실행합니다.
- `pnpm test:e2e`: Playwright를 실행합니다.
- `pnpm check`: 테스트, lint, 타입 검사, production build, E2E를 차례로 실행합니다.

## 구현을 일부러 망가뜨려 확인한 결과

통과하는 테스트가 실제 문제도 잡는지 확인하기 위해 테스트 코드는 그대로 두고 구현 한 곳만 바꿨습니다. 실험이 끝난 뒤에는 구현을 원래대로 되돌렸습니다.

| 테스트 종류 | 일부러 바꾼 내용 | 처음 실행한 결과 | 결과에서 알게 된 점 |
| --- | --- | --- | --- |
| 단위 테스트 | 페이지 시작 위치 계산에서 `page - 1`을 제거했습니다. | 관련 단위 테스트 1개 실패 | `페이지 크기에 따라 겹치지 않는 상품 묶음을 반환한다`가 실패했고, 잘못된 상품 묶음을 보여줘서 계산 문제라는 걸 알 수 있었습니다. |
| 통합 테스트 | 카테고리를 바꿀 때 `page: 1`로 되돌리는 코드를 제거했습니다. | 관련 통합 테스트 1개 실패 | `2페이지에서 카테고리를 바꾸면 1페이지 응답 상품을 보여준다`가 실패해서 페이지 초기화 문제라는 걸 알 수 있었습니다. |
| E2E 테스트 | URL 기록 방식을 `push`에서 `replace`로 바꿨습니다. | 관련 E2E 테스트 1개 실패 | `뒤로가기와 앞으로가기로 이전 카테고리와 상품 목록을 복원한다`가 실패했고, 이전 필터를 복원하지 못한 화면을 확인했습니다. |
| 통합 테스트 추가 실험 | 로딩 스켈레톤 내용을 모두 지웠습니다. | 기존 통합 테스트 9개 모두 통과 | 기존 테스트가 로딩 화면을 확인하지 않는다는 걸 알았습니다. |

로딩 내용을 처음 지웠을 때는 통합 테스트 9개가 모두 통과했습니다. 이 결과를 보고 기존 테스트가 로딩 화면 자체를 확인하지 않는다는 걸 알았고, 로딩 안내가 나타났다가 사라지는지 확인하도록 보강했습니다. 같은 로딩 안내를 다시 지웠을 때는 해당 테스트 1개가 실패하고 나머지 8개는 통과했습니다.

로딩 테스트를 보강하기 전후에 확인한 내용은 다음과 같습니다.

| 비교한 내용 | 보강 전 | 보강 후 |
| --- | --- | --- |
| 로딩 중 확인한 동작 | 카테고리 선택창이 아직 없는지만 확인했습니다. | `role="status"`의 로딩 안내가 나타나는지 확인했습니다. |
| 응답 후 확인한 동작 | 상품과 전체 개수가 나타나는지 확인했습니다. | 상품과 전체 개수가 나타나고 로딩 안내가 사라지는지 확인했습니다. |
| 로딩 내용을 지운 결과 | 통합 테스트 9개가 모두 통과했습니다. | 해당 테스트 1개가 실패하고 나머지 8개는 통과했습니다. |
| 실패 메시지 | 실패가 없어서 문제를 알 수 없었습니다. | `role="status"`를 찾을 수 없다고 알려줘서 사라진 동작을 바로 찾을 수 있었습니다. |

처음 세 실험은 테스트가 실패해서 망가진 동작을 찾을 수 있었습니다. 로딩 실험도 보강한 뒤에는 같은 문제를 실패로 알려줬습니다. 실험이 끝난 뒤에는 일부러 바꾼 코드를 모두 원래대로 되돌렸습니다.

## 추가하지 않은 테스트

빈 장바구니와 빈 위시리스트의 개수가 0인지 확인하는 단위 테스트도 검토했습니다. 하지만 각 테스트의 `beforeEach`가 직접 빈 상태를 만든 뒤 0인지 확인하면 실제 초기값이 잘못돼도 테스트가 통과할 수 있습니다. 테스트 설정을 다시 확인하는 테스트가 되므로 추가하지 않았습니다.

초기 개수 0은 이미 사용자 화면에서 확인하고 있습니다.

- 위시리스트 통합 테스트는 처음에 헤더가 `위시리스트 0`을 보여주는지 확인합니다.
- 장바구니 E2E 테스트는 상품을 담기 전에 헤더가 `장바구니 0`을 보여주는지 확인합니다.
- 단위 테스트는 같은 상품을 여러 번 담거나 다시 찜했을 때 개수가 어떻게 바뀌는지 확인합니다.

Tailwind 디자인 값, HTML 구조, 화면 전체 스냅샷은 테스트하지 않았습니다. 기능이 그대로여도 디자인이나 마크업을 바꾸면 테스트가 실패하기 때문입니다. Dialog의 `className` 전달처럼 공용 컴포넌트가 약속한 동작은 디자인과 관계없는 표시용 클래스 이름으로 확인했습니다.

## 다음에 확인할 테스트

상품 검색 입력부터 URL과 목록까지 이어지는 흐름은 아직 확인하지 않았습니다. API의 검색 계산은 단위 테스트가 확인하지만, 사용자가 검색창에 입력했을 때 다음 동작이 이어지는지는 현재 테스트가 보호하지 못합니다.

1. 검색어를 입력한 뒤 300ms가 지나면 URL에 검색어가 반영됩니다.
2. 다른 페이지에서 검색하면 1페이지로 돌아갑니다.
3. 검색 조건을 포함한 요청을 보냅니다.
4. 검색 결과가 화면에 나타납니다.

이 흐름을 바꾸는 `setSearch` 호출을 지워도 현재 테스트가 통과할 가능성이 높습니다. 아직 구현을 실제로 바꿔 확인한 것은 아니므로 발견한 문제로 기록하지 않고 다음 테스트 후보로 남겼습니다. 검색 테스트를 추가할 때는 앞뒤 공백만 다른 검색어가 같은 목록을 뜻하는지도 함께 판단할 예정입니다.

## 최종 실행 결과

2026년 8월 21일에 과제에서 지정한 Node.js `24.17.0`, pnpm `10.15.1` 환경에서 일부러 바꾼 구현을 모두 되돌린 뒤 `pnpm check`를 실행했습니다.

새로 추가한 단위 테스트 4개 파일과 상품 목록 통합 테스트 파일은 각각 따로 실행해도 통과했습니다. 테스트 순서를 seed `82026`으로 섞었을 때도 13개 파일의 107개 테스트가 모두 통과했습니다.

| 확인한 항목 | 결과 |
| --- | --- |
| Vitest | 13개 파일, 107개 테스트 통과 |
| ESLint | 오류 0개, 기존 경고 1개 |
| TypeScript | 타입 오류 없음 |
