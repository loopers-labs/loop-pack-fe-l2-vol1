# 단언을 스무 개 쓰고 세 개를 잡았다

E2E 테스트를 붙일 자리를 30일치 사용자 로그로 정했다. 그리고 붙인 뒤에 구현을 일부러
망가뜨려서, 그 테스트가 실제로 무엇을 잡는지 셌다.

결과가 예상과 두 번 갈렸다. 한 번은 도구가 만든 테스트에서, 한 번은 내가 쓴 테스트에서.

## 빈도 1위에 E2E를 붙이지 않았다

로그는 22,427개 이벤트, 8,000개 세션, 30일분이었다. 세션 기준으로 순위를 냈다.

| 경로 | 세션 비율 |
| --- | ---: |
| 목록 진입 | 100.0% |
| 상세 진입 | 62.0% |
| 카테고리 변경 | 40.7% |
| 담기 | 17.4% |
| **로그인 시작** | **8.6%** |
| **주문 완료** | **3.7%** |

붙인 것은 아래 두 개다. 1위와 2위는 붙이지 않았다.

**1위 목록 진입(100%)** — 세션 전부가 지나가는 입구다. 그런데 이미 통합 테스트 아홉
항목이 이 화면을 덮고 있었다. 로딩·빈 결과·4xx·5xx·재시도·필터·정렬·페이지·URL 반영.
여기에 E2E를 더 붙이면 같은 것을 두 배 비싸게 다시 보는 것이다.

**2위 상세 진입(62%)** — 그 화면이 내 코드에 없다. 로그 스키마가 구현보다 먼저
정의됐거나, 정의된 뒤 구현이 사라진 경우다. 실무에서 흔하다. 없는 화면을 만들어
E2E를 붙이는 건 순서가 거꾸로다.

그래서 **8.6%인 인증**과 **3.7%인 주문 완료**를 골랐다. 로그만 보면 둘 다 안 붙일
자리다. 로그는 "몇 명이 지나갔나"를 말하고, **실패 비용은 말하지 않는다.** 인증이
막히면 그 8.6%가 못 들어오는 게 아니라 주문과 주문 내역이 같이 막힌다.

상한이 세 개였는데 두 개만 썼다. 세 번째 후보는 담기(17.4%)였고, 이미 통합과 E2E
양쪽에서 보고 있었고 서버에 저장되지도 않아 깨져도 잃는 게 브라우저 안뿐이었다.
**개수를 채우려고 붙이면 그 순간 근거가 근거가 아니게 된다.**

## 노이즈를 걸렀는데 순위가 안 바뀌었다

로그에는 봇과 중복 전송이 섞여 있었고 "이건 봇이다"라는 표시는 없었다.

기준을 두 개 세웠다. 하나는 `device`가 비어 있는 세션. 이 값은 브라우저의
`innerWidth`로 채우니까 브라우저가 아니면 못 채운다. 486개였고, **전부 이벤트가
정확히 하나**였으며 그 하나가 목록 진입이었다. 사람은 평균 2.8개를 남긴다.

또 하나는 세션 안의 모든 이벤트 간격이 1초 미만인 세션. 전체 간격의 1퍼센타일이
2.18초, 중앙값이 21.8초였다. 사람이 화면을 읽는 시간이 그 아래로 내려가지 않는다.
9개였다.

495개를 걸러내고 다시 셌다. **12개 경로의 순위가 하나도 바뀌지 않았다.**

허탈했는데, 왜 안 바뀌었는지를 보니 그게 결과였다. 제외한 세션이 전부 **목록 진입만
가진 얕은 세션**이라 1위의 분자와 분모에서 같이 빠지고, 나머지 11개 경로의 분자에는
애초에 없었다. 그래서 비율은 전부 조금씩 올라가지만 서로의 상대 위치는 그대로다.

**노이즈가 얕은 세션에 몰려 있으면 세션 기준 순위는 노이즈에 둔감하다.** 만약 봇이
퍼널 깊숙이 들어가는 모양이었다면(주문까지 흉내 내는 식으로) 순위가 흔들렸을 것이고,
그때는 거르는 기준 자체가 결론을 좌우한다.

거른 일이 헛수고는 아니었다. 순위는 그대로지만 **분모가 6.2% 달라진다.** 위에서
"인증이 8.6%"라고 쓴 숫자가 거르기 전 기준으로는 8.1%다.

중복 전송은 다르게 다뤘다. 완전히 같은 줄이 77개 있었는데 그중 68개는 **정상 흐름에
한 줄 낀 것**이라 세션째 버리면 멀쩡한 데이터를 잃는다. 그런데 집계가 세션 기준이라
같은 이름이 두 번 있어도 1로 센다. **중복은 순위에 영향을 주지 않았다.** 이벤트 수로
셌다면 여기서 걸러야 했다.

## 망가뜨려 보니 넷은 E2E만 잡았다

구현을 한 곳씩 망가뜨리고 테스트가 잡는지 봤다. 테스트 코드는 건드리지 않았다.
같은 변이를 **E2E와 통합·단위 양쪽에** 돌린 게 이번에 새로 한 것이다.

| 망가뜨린 곳 | E2E | 통합·단위 |
| --- | --- | --- |
| 가드 조건 뒤집기 | **잡힘 4건** | 살아남음 |
| 복원 경로 제거 | **잡힘 1건** | 살아남음 |
| 오픈 리다이렉트 방어 제거 | 살아남음 | **잡힘 3건** |
| 만료 분기 제거 | **잡힘 1건** | 살아남음 |
| 쿠키 `httpOnly` 끄기 | 살아남음 | **잡힘 1건** |
| 초기 HTML 로그인 상태 제거 | **잡힘 3건** | 살아남음 |

깔끔하게 갈렸다. E2E만 잡은 넷은 전부 **브라우저·서버·프록시가 함께 도는 자리**였다.
프록시가 만드는 리다이렉트, 쿠키를 들고 서버를 다시 때려야 나오는 전이, 서버가 그린
HTML. 테스트 환경에 이 셋이 없다.

이게 "빈도 8.6%인 경로에 비싼 테스트를 붙였다"는 결정을 사후에 확인해 줬다. 붙인
이유가 "여기가 유일하게 싼 테스트로 볼 수 없는 자리"였고, 실험 여섯 중 넷이 그
자리에서 나왔다.

### 살아남은 둘은 고치지 않았다 — 하나만 고쳤다

오픈 리다이렉트 방어를 지웠는데 E2E가 못 잡았다. 내 E2E는 절대 URL(`https://evil…`)
하나만 지나가는데, 지운 방어는 `//evil…` 쪽이었다.

**E2E에 케이스를 더하지 않았다.** 단위 테스트가 같은 변이를 세 건으로 잡고 있었다.
문자열 하나 넣고 결과를 보는 순수 함수라 단위가 더 정확하고 사실상 무료다. E2E로
옮기면 같은 것을 확인하려고 브라우저를 세 번 더 띄운다. **더 싼 레벨이 이미 정확히
잡는 것을 비싼 레벨로 올리지 않았다.**

쿠키 `httpOnly`는 달랐다. 라우트 테스트가 잡고 있었는데, 그게 보는 것은 **서버가
무엇을 보냈나**까지였다. 서버가 헤더를 제대로 보내도 클라이언트 코드가 쿠키를 다시
쓰면 노출된다. **브라우저가 그것을 지키는지는 아무도 안 봤다.** 두 줄을 더했다.

```ts
const readable = await page.evaluate(() => document.cookie);
expect(readable).not.toContain("session=");
```

## 도구가 만든 테스트는 단언이 더 많고 덜 잡았다

Playwright의 테스트 생성 에이전트를 돌려봤다. 브라우저로 화면을 탐색해 계획을 만들고,
계획을 한 단계씩 실제로 실행하면서 테스트를 뽑는다.

생성물은 그대로 통과했다. 셀렉터가 전부 역할과 이름 기반이었고 `getByTestId`가 없었다.
이건 정말 잘한 부분이다.

같은 변이를 양쪽에 돌렸다.

| 변이 | 생성물 (단언 **20개**) | 내 것 (단언 **17개**) |
| --- | --- | --- |
| 가드 뒤집기 | 잡힘 1건 | **잡힘 2건** |
| 복원 경로 제거 | 잡힘 1건 | 잡힘 1건 |
| `httpOnly` 끄기 | **살아남음** | **잡힘 1건** |
| 초기 HTML 상태 제거 | 잡힘 1건 | **잡힘 3건** |

**단언이 세 개 더 많은데 잡는 것은 더 적다.**

생성물에서 11개를 지웠다. 문서 제목 2개, 헤더의 장바구니 개수 2개, 화면에 적어둔
테스트 계정 안내 문구 3개, 브랜드명 1개, 상품명 1개, 금액 1개, 그리고 "로그인 링크가
없다"는 없음 단언 1개.

**지운 11개 중 아무것도 변이를 잡지 않았다.** 네 변이를 잡은 것은 생성물에서도
주소를 대조하는 단언 하나였다.

지운 이유는 대체로 같다. 제목·브랜드·상품명·금액은 **다른 것의 계약**이다. 픽스처가
바뀌거나 제목 템플릿을 손대면 인증 테스트가 깨진다. 계정 안내 문구는 목 서버 때문에
화면에 적어둔 임시 블록이라, 단언하면 임시 블록이 계약이 된다.

수량만 남겼다. `?quantity=2`가 화면까지 도달했다는 뜻이고, 상품명은 서버가 id로 찾은
결과라 URL 조건과 무관하다.

**도구가 잘한 것은 셀렉터고, 못한 것은 무엇을 지킬지 정하는 일이었다.** 스냅샷에
보이는 것과 계약인 것을 도구는 구분하지 않는다. 화면에 있는 걸 전부 적으면 통과는
한다. 그런데 그건 "지금 화면이 이렇다"는 기록이지 "이건 지켜야 한다"는 선언이 아니다.

같은 도구 세트에 실패한 테스트를 고쳐주는 healer가 있는데 쓰지 않았다. **healer는
테스트를 통과하게 고치는 도구다.** 지금 하고 있는 건 일부러 구현을 망가뜨려 테스트를
빨간불로 만드는 일이고, 거기에 healer를 붙이면 테스트를 고쳐 통과시켜 실험의 결론을
뒤집는다. healer가 값을 하는 자리는 앱이 정상인데 셀렉터가 낡은 경우다.

## 초록불 아래 세 개가 더 있었다

여기까지 하고 다른 모델로 인증 코드를 다시 훑게 했다. **세 개가 나왔다.** 게이트도
통과했고 E2E 열세 개도 통과한 상태였다.

### 브라우저가 개행을 지운다

복원 경로를 검증하는 함수를 이렇게 썼다. `/`로 시작하고 두 번째 글자가 `/`도 `\`도
아니면 통과.

```
//evil.example      → 막힌다
/%0a/evil.example   → 통과했다
```

디코딩하면 `/\n/evil.example`이 된다. `/`로 시작하고 두 번째 글자가 `\n`이니 검사를
지나간다. 그런데 **브라우저 URL 파서는 탭·개행·캐리지리턴을 제거한 뒤 해석한다.**
제거하면 `//evil.example`이 되고, 브라우저는 `https://evil.example/`로 나간다.

순서가 틀렸다. 브라우저와 같은 순서로 고쳤다 — 제어문자를 먼저 제거하고, 그 값을
검사하고, **검사한 값을 돌려준다.** 원본을 돌려주면 검사한 것과 이동하는 것이 달라져
방어가 무의미해진다.

### 시나리오 노브가 실제 만료와 다른 코드를 탄다

이게 가장 값 있는 발견이었다.

세션 TTL이 한 시간인데 테스트에서 한 시간을 기다릴 수 없으니, 목 서버가 `expired`
시나리오를 제공한다. 그 노브를 걸면 API가 유효한 세션에도 401을 준다. 내 E2E는 그걸
써서 "세션이 만료되었습니다"가 뜨는 것을 확인했고 통과했다.

그런데 **실제로 TTL이 지난 쿠키로 들어오면 그 문구가 뜨지 않았다.**

노브는 **서명이 유효한 쿠키를 그대로 두고** API만 401로 만든다. 그래서 서버는 여전히
"로그인됨"을 초기 HTML에 담고, 만료 판정이 클라이언트 쪽 전이에서 일어난다.
반면 실제 만료 쿠키는 서버 검증에서도 떨어진다. 그러면 서버가 "로그인 안 함"을
담고, 이후 401이 와도 **직전 상태가 로그인됨이 아니어서 전이가 성립하지 않는다.**

로그인했다가 만료된 사람이 "로그인한 적 없는 사람"으로 취급됐다. 요구사항이
"세션이 만료되면 다음에 무엇을 해야 할지 화면에서 알 수 있어야 한다"였는데, 실제
만료에서는 못 지키고 있었다.

기준을 이렇게 바꿨다. **쿠키를 들고 왔는데 서버가 인정하지 않으면 만료다.** 쿠키를
들고 온 것 자체가 "이 브라우저는 로그인했다고 믿는다"는 뜻이고, 서버가 그걸 거절했다면
그게 만료다.

E2E를 하나 더했다. 발급 시각을 두 시간 전으로 준 토큰을 쿠키에 넣는다. 시간은 흘리지
않는다. 고치기 전으로 되돌리는 변이를 돌리니 E2E가 잡고 통합은 살아남는다.

### 워커가 아홉 개면 계정이 겹친다

병렬 실행에서 테스트를 격리해야 했다. 서버의 주문 저장소가 프로세스 메모리에 있는
맵 하나라, 두 워커가 같은 계정으로 주문하면 서로의 주문이 상대 목록에 보인다.
그래서 워커 슬롯 번호로 계정을 갈랐다. 계정은 여덟 개.

`accounts[index % 8]`로 순환시켰는데, 슬롯이 아홉 개면 0번과 8번이 **같은 계정을
쓰면서 통과한다.** 실패가 아니라 잘못된 초록불이다.

순환을 없애고 던지게 했다. 다만 **이 방어는 스위트가 확인하지 않는다.** 워커를 네 개로
고정해 두었으니 겹칠 일이 없고, 순환으로 되돌려도 아무 테스트도 안 잡는다. 구성에
의존하는 방어라는 사실을 그대로 문서에 적었다.

## 고치고 나니 판정하는 자리가 셋이었다

만료를 고치려고 코드를 열었더니, 세션 상태를 정하는 곳이 셋이었다.

| 자리 | 무엇을 보고 정했나 |
| --- | --- |
| 서버 레이아웃 | 쿠키는 있는데 검증에 실패했다 |
| 세션 조회 | `/api/auth/me`가 401을 줬다 → **무조건 로그아웃 상태** |
| 전역 에러 처리 | 보호된 자원이 401을 줬다 → 직전이 로그인이면 만료 |

셋이 각자 판단하니 서로를 덮었다. 서버가 "만료"를 심어도 60초 뒤 조회가 다시
물어보고 401을 받아 "로그아웃"으로 접었다. **사용자가 보던 "세션이 만료되었습니다"가
소리 없이 "로그인하세요"로 바뀐다.**

규칙을 한 함수로 옮겼다.

```
서버가 인정했다                          → 로그인됨
거절했는데, 이 브라우저가 로그인했다고 믿는다  → 만료
거절했고, 믿을 근거도 없다                 → 로그아웃
```

"믿는다"의 **근거가 둘이라 진입점만 둘**이다. 서버는 httpOnly 쿠키를 직접 볼 수 있고,
클라이언트는 못 보니 직전 상태를 본다. 규칙은 하나다.

그리고 만료를 **그리는** 자리도 하나뿐이 아니었다. 주문 내역만 만료를 그렸고,
주문서는 세션을 아예 안 봐서 만료된 사용자가 정상 주문서를 보고 **주문하기를 누른
뒤에야** 알았다. "만료 처리를 한 곳으로"라는 결정을 판정에만 적용하고 표시에는
적용하지 않았던 것이다. 보호 화면이 지나는 문을 하나 두었다.

## 고치면서 쓴 테스트가 아무것도 잡지 않았다

그 수정을 고정하려고 이렇게 썼다.

```ts
await queryClient.refetchQueries({ queryKey: SESSION_QUERY_KEY });
expect(await screen.findByText("상태: expired")).toBeInTheDocument();
```

**통과했다. 그리고 아무것도 잡지 않았다.**

`await` 직후에는 React가 아직 리렌더하지 않아서 DOM에 심어 둔 "expired"가 그대로
남아 있다. `findByText`가 그걸 즉시 찾는다. 조회가 "로그아웃"을 돌려주도록
망가뜨려도 초록불이었다.

**"바뀌지 않았다"는 조건 기반 대기로 확인할 수 없다.** 폴링은 "아직 안 바뀜"과
"바뀌지 않는 게 맞음"을 구분하지 못한다. 화면 대신 조회 결과를 값으로 대조하니
그제야 잡혔다.

## 다시 봤더니 내 주석이 거짓말이었다

여기서 끝난 줄 알았는데 한 번 더 훑었다. 주문서에 이렇게 적어 뒀었다.

> 이 401이 세션 상태를 만료로 바꾸면 다음 렌더에서 문이 받는다

**성립하지 않았다.** 전역 에러 처리를 조회 캐시에만 붙였는데 그건 조회만 받는다.
주문 전송은 변경(mutation)이라 다른 캐시로 간다. 그래서 만료된 사용자가 주문서에서
401을 받아도 세션은 "로그인됨"으로 남고, 문도 열려 있었다.

```
expected 'authenticated' to be 'expired'
```

코드가 틀린 게 아니라 **내가 코드에 대해 믿고 있던 것**이 틀렸다. 주석은 검증되지
않는다.

변경 캐시에도 붙였다. 기본값을 **"401이면 세션이 거절됐다"**로 뒀다 — 보호된 자원에
쓰기를 시도했는데 401이면 세션 문제로 보는 게 맞고, 새 변경이 생겨도 기본이 안전한
쪽이다. 예외는 로그인 실패뿐이다. 그건 "자격 증명이 틀렸다"이지 "만료됐다"가 아니고,
로그인한 사람이 비밀번호를 틀리게 다시 입력하는 경로가 실제로 있다.

같이 나온 것 하나 더. 로그아웃하면 상태가 "로그아웃"이 되는데 문은 "만료"만 막고
있었다. 라우터 이동은 비동기라 **이동이 끝날 때까지 방금 로그아웃한 사람이 자기
주문 내역을 계속 본다.** 통과 조건을 하나로 바꿨다 — 로그인된 상태가 아니면 전부
막는다. 상태를 모르는 경우도. **모른다는 것은 있다가 아니다.**

## 그리고 또 메커니즘만 봤다

변경 캐시를 붙이고 테스트를 썼다. 변이를 돌리니 **두 개가 살아남았다.**

테스트가 자체 컴포넌트에 키를 직접 박아 넣어서, **메커니즘은 검증하고 호출부는
검증하지 않았다.** 실제 로그인 훅이 그 키를 빠뜨려도 초록불이었다.

실제 경로로 다시 썼다. 로그인 폼을 렌더해 401을 받히고 세션이 그대로인지 보고,
문을 상태별로 렌더해 내용이 그려지는지 본다. 그러자 네 변이가 다 잡혔다.

| 변이 | 결과 |
| --- | --- |
| 변경 캐시를 안 붙인다 | 잡힘 |
| 로그인이 세션 판정에서 안 빠진다 | 잡힘 |
| 문이 만료만 막는다 | 잡힘 |
| 만료가 아닌데 만료라고 한다 | 잡힘 |

## 남는 것

이번 주에 같은 실수를 **세 번** 했다. 전부 "없음"이나 "변하지 않음"을 향한 단언이었다.

- 예전 주차에서 `has("page")`가 `false`인지 확인한 것 — 실패해도 무엇이 남았는지 말하지 않았다
- 1.5초 동안 화면이 유지되는지 확인한 것 — 그건 지금도 실제로 1초를 기다린다
- 재조회 뒤에도 만료로 남는지 화면으로 확인한 것 — 리렌더 전이라 옛 값을 봤다

셋 다 "무언가가 일어나지 않았다"를 확인하려 했고, 폴링은 그걸 확인할 수 없다.
폴링이 아는 것은 "지금은 아직"뿐이다.

그리고 더 크게 남은 것. **망가뜨려 보는 실험은 내가 의심한 자리만 본다.** 여섯 개를
고른 것도 나였고, 그 목록에 없는 것은 실험을 아무리 돌려도 나오지 않는다.

교차 검증을 두 번 받았다. 첫 번째는 구현의 결함을 잡았고, 두 번째는 **그 수정에 대해
내가 쓴 주석이 거짓말**이라는 것을 잡았다. 두 번 다, 고치면서 쓴 테스트가 처음엔
아무것도 잡지 못했다.

그래서 이번 주 결론은 이렇다.

초록불의 의미는 "안전하다"가 아니라 **"내가 확인한 것들은 통과했다"**이다.
그 목록을 누가 만들었는지가 남는 질문이고, 목록을 만든 사람이 값을 세는 사람과
같으면 거기에도 사각이 생긴다.

**고친 뒤에 다시 망가뜨려 보는 것이 고치는 일의 일부다.** 두 번 배웠다.
