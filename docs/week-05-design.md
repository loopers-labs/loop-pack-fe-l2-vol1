# 5주차 설계 근거 — 상태의 자리

> 도구를 먼저 고르지 않고 "이 상태의 원본(Source of Truth)이 어디인가"를 먼저 정했다.

## 0단계. 상태 소유권 표

| 상태 | 소유자 | 수명 | 공유 범위 | 선택 이유 |
|---|---|---|---|---|

## 책임을 나눈 기준

- **서버(TanStack Query)**: "서버에 물어봐서 받아오는" 값. 홈·목록. 응답을 Zustand로 복사하지 않는다.
- **URL(nuqs)**: 링크로 공유하거나 새로고침·앞뒤 이동으로 복원돼야 하는 조회 조건. 검색·카테고리·정렬·페이지.
- **전역 클라이언트(Zustand)**: 서버·URL 어디에도 없지만 여러 화면이 함께 보는 비로그인 담기 상태.
- **로컬(useState)**: 한 컴포넌트 수명 안에서만 쓰는 초안·일시 UI.

## staleTime / gcTime 정책

`staleTime`은 "언제 다시 물어볼지", `gcTime`은 "안 쓰는 응답을 언제 버릴지"를 정한다. 둘은 다른 질문이라 따로 정했다.

| 쿼리 | query key | 캐시 entry 수 | staleTime | gcTime |
|---|---|---|---|---|
| 홈 | `["home"]` — 상수 | **항상 1개** | 5분 | **10분 (명시)** |
| 목록 | `["products", {q, category, sort, page}]` | **조건 조합마다 1개, 상한 없음** | 1분 | **기본 5분 (의도적으로 명시하지 않음)** |

- 전역 기본값은 `staleTime 60초`, `retry 1`(mock 500ms 지연 위 과한 재시도 방지).

### 홈에 gcTime 10분을 명시한 이유

카탈로그성 데이터라 자주 바뀌지 않고, key가 상수여서 **아무리 오래 보관해도 entry는 1개**다. 보관 비용에 상한이 있으니 길게 잡아 재방문 시 재요청을 없애는 쪽이 이득이다.

### 목록에 기본 gcTime(5분)을 그대로 둔 이유

같은 판단을 목록에 적용할 수 없다. key에 조건 전체가 들어가므로 **entry 수에 상한이 없다** — 카테고리 6 × 정렬 4 = 24 조합에 페이지가 곱해지고, `q`는 자유 문자열이라 검색을 반복하는 만큼 계속 늘어난다. 홈처럼 길게 잡으면 한 세션의 탐색이 길어질수록 안 쓰는 조합이 계속 쌓인다.

그래서 **사용자 재방문 동선이 실제로 덮이는 만큼만** 보관하는 쪽을 택했다.

- **동선 안쪽 (1분 이내)**: 카테고리·정렬을 바꿔 보다가 되돌아오는 흐름. staleTime 안이라 재요청도 없이 즉시 표시된다 — 검증 #8에서 `pending`이 아예 나타나지 않는 것으로 확인했다.
- **동선 바깥쪽 (1~5분)**: stale이지만 캐시는 남아 있어 이전 결과를 즉시 보여주고 배경에서 갱신한다. 상품을 눌러보고 돌아오는 정도의 왕복이 여기 들어간다. *(Query의 문서화된 동작이며, 이번 수동 검증에서 직접 재현하지는 않았다.)*
- **5분 넘게 안 돌아온 조합**: 사용자가 사실상 떠난 조건이다. 되돌아오더라도 `pending` 512ms(검증 #2)를 한 번 감는 편이, 안 쓸 조합을 메모리에 계속 들고 있는 것보다 낫다.

**정리 시점**: `gcTime`은 마지막 관찰자가 사라져 **비활성이 된 뒤부터** 세는 시간이다. 화면에 붙어 있는 동안에는 제거되지 않는다. 즉 조건을 바꿔 떠난 뒤 5분이 지난 entry가 정리 대상이고, 지금 보고 있는 조건은 영향을 받지 않는다.

**5분이라는 값 자체**는 라이브러리 기본값이며, 별도 근거로 고른 숫자가 아니라 "홈보다 짧아야 한다"는 방향에 기본값이 이미 부합해서 그대로 둔 것이다. 조합 수나 응답 크기가 커지면 명시적으로 더 줄여야 할 값이다.

> 확인: 이 프로젝트의 `@tanstack/query-core@5.101.2`에서 `gcTime` 미지정 시 기본값은
> `newGcTime ?? (isServer ? Infinity : 5 * 60 * 1000)` — **브라우저 5분**이다.
> (Node에서 그냥 재면 `Infinity`가 나오는데, 그건 SSR 경로다.)

## store 데이터 형태와 selector 경계

- 형태: `cart` / `wishlist`를 각각 `Record<id, true>`로 둔다. 상품 상세(가격·이름)는 서버 소유라 복사하지 않고 **id만** 담는다.
- selector: 헤더는 `count`(파생)만, 상품 버튼은 `해당 id 포함 여부 + toggle action`만 구독한다. 다른 상품이 담겨도 무관한 카드는 리렌더되지 않는다.
- 개수는 `Object.keys(...).length`로 파생 — 별도 필드로 저장하지 않는다.

## 전역으로 올리지 않은 상태와 이유

- **검색어 초안**: 제출 전에는 SearchForm 로컬. 확정(제출) 시점에만 URL로 승격.
- **로딩·에러**: Query `status`가 이미 소유. 별도 상태로 만들지 않는다.
- **헤더 개수**: 담긴 id에서 계산되는 파생값.

## 로그인·서버 동기화가 생기면

위시리스트의 원본은 서버(계정)로 옮겨간다. 그때 로컬 익명 상태는 (1) 로그인 시 계정 데이터와 병합할지 / 버릴지, (2) 충돌 처리 규칙을 정한 뒤, Zustand의 역할을 "서버 상태로 보내기 전 임시 입력" 또는 순수 UI 상태로 다시 좁혀야 한다.

## 검증 (수동)

실행 환경: `next dev` (Next 16.2.10 · Turbopack) · Node 24.17.0 · 2026-07-29. mock API는 응답에 500ms 지연이 있다.

상태 4종은 URL만으로 재현된다 — `pending`은 캐시 없는 필터 변경, `error`는 `page=0`(nuqs `parseAsInteger`가 clamp하지 않아 API로 그대로 전달되어 400), `empty`는 결과 없는 검색어.

| # | 시작 조건 | 행동 | 기대값 | 실제 결과 | 판정 |
|---|---|---|---|---|---|

| 2 | `/products`(총 30개 표시), `digital` 캐시 없음 | 카테고리 → 디지털 | 로딩 문구 후 데이터 | `상품을 불러오는 중입니다…` **512ms** 노출 → 총 6개 (mock 500ms 지연과 일치) | ✅ |

**#6 메모**: URL 복원 자체는 동작한다(조건 3개가 그대로 복원됨). 다만 이전 판 문서가 복원 예시로 쓰던 URL이 하필 범위 밖 페이지라 화면은 빈 결과였다. 복원을 보이려면 `page=1`(#5)이 맞는 예시다. 범위 밖 `page`를 어떻게 다룰지(clamp / 마지막 페이지로 보정 / 그대로 빈 결과)는 이번 과제 범위에서 정하지 않았다.

**#7 메모**: 기대했던 `page=1`이 아니라 파라미터 제거로 나타난다. nuqs가 기본값과 같은 값을 URL에서 지우기 때문이며(`parseAsInteger.withDefault(1)`), 실효 페이지는 1이라 동작은 의도대로다. 리셋을 URL 문자열로 확인할 때 헷갈릴 수 있어 적어 둔다.

## AI 협업 표기

- **직접 결정(설계 판단, 근거는 위 표·정책)**: 각 상태를 어느 자리에 둘지, staleTime/gcTime 값, store 데이터 형태(`Record<id,true>`)와 selector 경계, 검색 초안을 로컬로 둔 결정. 목록 gcTime을 명시하지 않고 기본값을 채택한 결정도 여기 포함된다.
- **AI가 작성 후 직접 검토(기계적)**: provider 배선, `fetchJson` 헬퍼·에러 가드, nuqs parser 배선, Zustand 보일러플레이트, 컴포넌트 골격, CSS(5주차 예시 이식).
- **AI가 실행·기록(측정)**: 위 「검증 (수동)」 표 10건의 실제 결과, `pending` 노출 시간(512ms), query-core의 기본 gcTime 확인. 코드는 바꾸지 않고 실행 결과만 옮겼다. 5주차 피드백의 두 지적(목록 gcTime 근거 누락, 상태별 실제 결과 누락)에 대한 보완이다.
