## 1. 먼저 알아야 하는 용어 사전

원문에 나오는 용어를 미리 정리해 둡니다. 본문에서 처음 나올 때마다 다시 설명하지 않으니, 모르는 단어가 나오면 여기로 돌아오세요.

### 테스트 관련

| 용어                          | 뜻                                                                                                                                                                                |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **통합 테스트**               | 여러 부품(컴포넌트 + 함수 + 가짜 서버)을 붙여놓고 "붙여도 잘 도는지" 확인하는 테스트. 빠릅니다(약 200ms).                                                                         |
| **E2E 테스트 (End-to-End)**   | 실제 브라우저를 띄우고 사람처럼 클릭하고 입력하는 테스트. 가장 현실과 비슷하지만 느리고(수십 초), UI가 바뀌면 고칠 곳도 생깁니다. "비싸다"는 건 시간과 유지보수 둘 다를 말합니다. |
| **Playwright**                | 브라우저를 자동으로 조작하게 해주는 도구. E2E 테스트를 만들 때 씁니다.                                                                                                            |
| **MSW (Mock Service Worker)** | 진짜 서버 대신 가짜 응답을 주는 도구. 통합 테스트에서 네트워크를 가로채서 씁니다.                                                                                                 |
| **production build**          | 실제로 사용자에게 배포할 형태로 코드를 번역·압축해 둔 것. 개발 모드와 동작이 달라서 E2E는 이 위에서 돌립니다.                                                                     |
| **스냅샷 테스트**             | 화면이나 결과물을 통째로 찍어두고, 다음에 같은지 비교만 하는 테스트. "달라졌다"는 알려주지만 "왜, 뭘 잘못됐는지"는 안 알려줍니다.                                                 |
| **변이 확인(자가 검증)**      | 일부러 코드를 망가뜨려서 테스트가 실패하는지 보는 것. 테스트가 진짜 버그를 잡는지 증명하는 방법입니다.                                                                            |

### 인증 관련

| 용어                            | 뜻                                                                                                                                                                               |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **인증 (Authentication)**       | "너가 누구인지" 확인하는 절차. 로그인이 여기 속합니다.                                                                                                                           |
| **세션 (Session)**              | 로그인 상태를 유지하는 장치. "이 브라우저는 looper1으로 로그인되어 있다"는 서버와의 약속입니다.                                                                                  |
| **쿠키 (Cookie)**               | 브라우저에 저장되는 작은 데이터 조각. 요청할 때마다 자동으로 서버에 함께 전송됩니다. 세션 정보가 이 안에 담깁니다.                                                               |
| **httpOnly 쿠키**               | JavaScript가 못 읽게 서버가 잠궈놓은 쿠키. 해커가 스크립트로 훔쳐가지 못하게 하는 안전장치입니다.                                                                                |
| **서명된 쿠키**                 | 서버가 "내가 만든 거 맞다"는 도장을 찍어둔 쿠키. 위조를 막습니다.                                                                                                                |
| **보호 경로 (Protected Route)** | 로그인한 사람만 들어갈 수 있는 페이지. 예: 주문 내역.                                                                                                                            |
| **리다이렉트 (Redirect)**       | 자동으로 다른 페이지로 보내버리는 것.                                                                                                                                            |
| **401 / 400 / 500**             | 서버가 알려주는 상태 코드. 401은 "로그인 안 됨/자격 증명 틀림", 400은 "보낸 형식이 잘못됨", 500은 "서버 내부 오류".                                                              |
| **401의 두 얼굴**               | 이 스타터에서 401은 "로그인을 안 한 경우"와 "로그인했는데 세션이 만료된 경우" 둘 다를 가리킵니다. 둘을 어떻게 구분할지가 과제의 고민거리 중 하나입니다.                          |
| **proxy.ts (미들웨어)**         | 페이지에 도착하기 전에 요청을 가로채는 "문지기" 파일. 로그인 안 한 사람을 로그인 페이지로 돌려보내는 역할을 합니다.                                                              |
| **초기 HTML**                   | JavaScript가 실행되기 전에 서버가 처음 보내주는 화면 구조. 여기에 로그인 상태가 박혀 있어야 깜빡임 없이 보입니다.                                                                |
| **정적 생성**                   | 미리 만들어 둔 HTML을 그대로 주는 방식. 빠르지만 "지금 이 사용자"에 맞춘 내용을 넣기 어렵습니다. 쿠키를 읽으면 요청마다 다시 만들어야 해서 7주차 성능 기준과 충돌할 수 있습니다. |

### 계측(분석) 관련

| 용어                       | 뜻                                                                                                        |
| -------------------------- | --------------------------------------------------------------------------------------------------------- |
| **계측 (Instrumentation)** | 사용자가 무엇을 했는지 기록으로 남기는 일. "상품 목록을 봤다", "구매 버튼을 눌렀다" 같은 기록을 쌓습니다. |
| **이벤트**                 | 계측의 한 줄 한 줄. "누가(with sessionId) 언제(ts) 무엇을(name) 했는지"가 담깁니다.                       |
| **이벤트 스키마**          | 이벤트 이름과 담기로 한 값들의 규칙. "이름은 이렇게 짓고, 모든 이벤트에 이 값은 꼭 넣는다"는 약속입니다.  |
| **공통 프로퍼티**          | 모든 이벤트에 반복해서 붙이는 정보. 예: 기기 종류, 세션 ID.                                               |
| **세션(분석 용어)**        | 사용자가 사이트에 들어와서 나갈 때까지의 방문 한 번. 인증의 세션과 이름만 같고 다른 개념입니다.           |
| **노이즈**                 | 데이터를 지저분하게 만드는 불필요한 기록. 봇(자동 프로그램) 활동, 오류, 중복 전송 등.                     |
| **이탈률**                 | 그 단계에서 사용자가 떠나버린 비율. "떠났다"를 어떻게 정의하느냐에 따라 값이 달라집니다.                  |
| **GA4 · GTM · Amplitude**  | 실제 회사에서 쓰는 분석 도구들. 이번 과제에서는 붙이지 않고 콘솔에 찍히는 것으로 충분합니다.              |

### E2E 구현 관련

| 용어                         | 뜻                                                                                                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **storageState**             | Playwright 기능. 로그인 상태(쿠키 등)를 파일로 저장해두고 다른 테스트에서 재사용하게 해줍니다. 매번 로그인 폼을 채우지 않아도 됩니다.                                                |
| **워커 (worker)**            | 테스트를 동시에 나눠서 돌리는 일꾼 프로세스. `--workers=4`면 4개가 동시에 돕니다.                                                                                                    |
| **병렬 실행**                | 테스트 여러 개를 동시에 돌리는 것. 각 테스트가 서로의 데이터를 건드리면 결과가 뒤죽박죽이 됩니다.                                                                                    |
| **격리**                     | 테스트끼리 서로 영향을 주지 않게 분리하는 것. 계정을 나눠주는 것이 한 방법입니다.                                                                                                    |
| **셀렉터**                   | 테스트가 화면의 어떤 요소를 찾을지 지정하는 방법.                                                                                                                                    |
| **역할/이름 기반 셀렉터**    | "로그인 버튼(역할=버튼, 이름=로그인)"처럼 사용자가 보는 것 기준으로 찾는 방법. 마크업 구조가 바뀌어도 잘 안 깨집니다. `getByTestId`는 개발자가 임의로 붙인 꼬리표로 찾는 방법입니다. |
| **시간 기반 대기 (`sleep`)** | "3초 기다려"라고 정해진 시간만큼 멍하게 기다리는 것. 느리고, 컴퓨터 사양에 따라 실패하기도 해서 금지입니다.                                                                          |
| **조건 기반 대기**           | "이 문구가 보일 때까지 기다려"처럼 조건이 만족될 때까지 기다리는 것. 빠르고 안정적입니다.                                                                                            |
| **trace**                    | Playwright가 실패 순간을 녹화해둔 파일. 어떤 단계에서 무엇을 기다리다 멈췄는지 되감아 볼 수 있습니다.                                                                                |

## 2. 이번 주 전체 흐름 — 왜 이 순서일까

```
1단계 인증 구현 → 2단계 계측 → 3단계 범위 설계(문서) → 4단계 E2E 구현 → 5단계 자가 검증
```

순서에 이유가 있습니다.

- **인증을 먼저 만드는 이유**: E2E의 필수 대상이 인증이어서입니다. 재료가 있어야 테스트를 만들 수 있습니다.
- **계측이 E2E보다 먼저 오는 이유**: "어디에 E2E를 붙일지"를 로그 데이터로 정하려면, 로그가 무엇인지 알아야 하기 때문입니다. 시드 로그를 분석하려면 스키마(규칙)를 이해해야 합니다.
- **설계 문서가 코드보다 먼저 커밋되는 이유**: "근거 없이 만들었다"가 되지 않게 하려는 것입니다. 실무에서도 비용이 큰 작업은 문서로 합의를 먼저 만듭니다.
- **자가 검증이 마지막인 이유**: 다 만들고 나서야 "이 테스트가 진짜 버그를 잡나?"를 증명할 수 있기 때문입니다.

### 출제 의도 (주간 전체)

이번 주의 진짜 목표는 "테스트를 많이 만드는 것"이 아닙니다. **비용이 드는 일에 리소스를 어디에 쓸지, 근거를 가지고 결정하고 그 결정을 남과 소통할 수 있는 형태(문서)로 남기는 훈련**입니다. 이건 시니어 엔지니어의 핵심 역량이고, 코드보다 판단을 평가하는 주간입니다.

## 3. 스타터가 주는 것들 — 무엇이고 왜 주는가

### 인증 API (이미 만들어져 있음)

백엔드가 미리 만들어져 있다는 뜻입니다. 여러분은 프론트엔드(화면과 데이터 흐름)만 만듭니다.

- `POST /api/auth/login` — 로그인 요청. 성공하면 200과 함께 쿠키를 주고, 비밀번호가 틀리면 401, 보낸 형식이 이상하면 400.
- `POST /api/auth/logout` — 로그아웃. 204는 "성공했는데 줄 내용이 없다"는 뜻.
- `GET /api/auth/me` — "지금 로그인한 나는 누구?"를 묻는 요청.
- `POST /api/orders`, `GET /api/orders` — 주문 생성/조회. 로그인 필요.

**출제 의도**: 인증의 원리(쿠키 발급, 검증, 만료)는 서버 코드를 직접 안 만들어도, 프론트엔드에서 다뤄야 할 일이 매우 많습니다. API가 주어져 있으니 프론트엔드 관점의 인증 설계(어디서 만료를 처리할지, 무엇을 보호할지)에 집중하게 하려는 의도입니다.

**주의 — 라우트 파일 위치**: `app/` 폴더를 루트로 옮긴 사람은 API 라우트 파일도 같이 옮겨야 합니다. 안 옮기면 요청이 404(없는 주소)가 나는데 테스트는 통과합니다. 테스트가 라우트 함수를 직접 import(가져다 쓰기)하기 때문에 파일 위치가 틀려도 테스트 눈에는 안 보이기 때문입니다. `pnpm build` 출력에 API 4개가 있는지 눈으로 확인하세요.

### 시나리오 노브 — 실패 상황을 만들어주는 스위치

`?scenario=expired`처럼 요청에 붙이면 서버가 일부러 실패하게 해주는 장치입니다. "세션 만료" 같은 상황은 기다려서 재현하면 1시간이 걸리니까, 스위치로 즉시 재현하게 해둔 것입니다.

**출제 의도**: 실무에서 실패 상황을 테스트하려면 이렇게 "실패를 강제하는 장치"가 필요하다는 걸 알려주기 위해서입니다.

### 이벤트 로거 (이미 만들어져 있음)

`src/analytics/`에 `track()`, `identify()`, `reset()` 같은 함수가 준비되어 있습니다. **다시 만들지 마세요.** 여러분이 할 일은 "무엇을 어떤 이름으로 보낼지" 설계하는 것입니다.

- `track()` — "~했다"고 기록 보내기. 초기화 전에 불러도 큐(줄 세우기)에 담겨서 나중에 순서대로 나갑니다.
- `identify()` — "지금부터 이 사용자는 looper1이야"라고 분석 도구에 알려주기.
- `reset()` — 로그아웃 때 사용자 연결 끊기.

### 시드 이벤트 로그

`fixtures/events-30d.jsonl`에 30일치 가짜 사용자 로그가 들어 있습니다. 봇 활동, 오류, 중복도 섞여 있어서 그냥 세면 순위가 틀어집니다.

**출제 의도**: "로그 분석 = 노이즈 걸러내기 + 정의 정하기"라는 실무 경험을 시뮬레이션하기 위해서입니다.

## 4. 각 단계 쉽게 이해하기

### 🔐 1단계 — 인증을 구현해요

**하는 일**:

1. 로그인/로그아웃 화면 만들기
2. 로그인 안 한 사람이 보호 경로에 들어오면 로그인 페이지로 보내고, 로그인하면 **원래 가려던 페이지로 돌려보내기** (이게 없으면 사용자는 로그인 후 처음 페이지로 던져져서 짜증납니다)
3. 돌려보낼 주소에 악의적인 외부 주소를 심어오면 못 보내게 막기 (보안)
4. 서버에서 세션을 읽어 초기 HTML에 로그인 상태 반영하기
5. 세션 만료(401) 처리 위치를 **한 곳만** 정하기
6. 로그아웃 때 장바구니/위시리스트를 지울지 말지 정하기

**왜 / 출제 의도**:

- **"위치를 한 곳으로 정하기"**: 만료 처리를 화면마다 각자 하면 나중에 어디를 고쳐야 할지 아무도 모릅니다. "관심사를 한곳에 모으는" 설계 감각을 기르게 하려는 것입니다.
- **"지울지 말지 정하고 이유 적기"**: 정답이 없는 문제입니다. (예: 장바구니는 로그인과 무관하게 유지하는 게 UX에 좋을 수도, 다른 사람이 이어 쓰는 걸 막으려면 지워야 할 수도.) **정답이 없는 문제를 근거와 함께 결정하는 연습**이 이 과제 전체를 관통하는 훈련입니다.
- **"세션은 서버 상태"라는 힌트**: 5주차의 클라이언트 상태 관리 패턴을 그대로 쓰면 안 될 수 있습니다. 세션은 서버가 진실의 원천이라 요청마다 달라질 수 있기 때문입니다. "상태의 주인이 누구냐"를 생각하게 하는 의도입니다.
- **"`pnpm start`로 확인"**: 빌드가 통과하는 것과 실제로 동작하는 건 다릅니다. 직접 실행해서 확인하는 습관을 기르게 하려는 것입니다.

**완료조건 쉽게 보기**: 로그인 안 하고 들어가면 로그인으로 갔다가 돌아오고, 세션이 죽으면 화면이 "다시 로그인하세요" 같은 안내를 해주면 됩니다.

---

### 📊 2단계 — 이벤트를 계측해요

**하는 일**:

1. 이벤트 이름 규칙 정하기 (예: `product_list_view`처럼 "무엇_행위"로 통일할지)
2. 모든 이벤트에 공통으로 붙일 값 정하기 (기기, 세션 ID 등)
3. 정해진 지점(목록 진입, 상세 진입, 담기, 로그인 시작/성공/실패, 주문 시작/완료)에 `track()` 넣기
4. 로그인/로그아웃 시점에 `identify()`/`reset()` 연결
5. 시드 로그와 이름이 다르면 매핑 표 만들기

**왜 / 출제 의도**:

- **"이름을 어떻게 짓느냐가 3단계를 결정"**: `button_click` 하나에 모든 클릭을 담으면 나중에 아무것도 셀 수 없습니다. **이름 = 나중에 셀 수 있는 단위**라는 걸 깨닫게 하려는 것입니다.
- **"매핑 표"**: 실무에서는 이미 회사가 쓰던 스키마가 있고, 새 코드를 그에 맞춥니다. 혼자 마음대로 정하는 게 아니라 합의에 맞추는 경험을 주려는 의도입니다.
- **"계측이 화면 로직에 섞이지 않게"**: 6주차 FSD(화면-로직 분리 구조) 원칙의 연장입니다. 나중에 분석 도구를 바꿀 때 한 곳만 고치게 하려는 설계입니다.
- **"어떤 이벤트가 남는지 문서만 보고 예측"**: 스키마 문서가 실제와 어긋나면 쓸모가 없습니다. 문서와 실제를 일치시키는 감각을 기르게 하려는 완료조건입니다.

### 🗺️ 3단계 — E2E 범위를 정해요 (이번 주의 심장)

**하는 일**: `docs/rfc/week09-e2e-scope.md` 문서를 쓰고, E2E 코드보다 **먼저 커밋**합니다.

RFC는 "제안서" 정도로 이해하면 됩니다. "이렇게 하겠다, 왜냐하면 이 근거 때문이다"를 남기는 문서입니다.

**B절 표의 각 칸이 무엇인지**:

- **경로**: 사용자가 지나가는 동선. "목록 → 상세 → 장바구니"처럼 묶어도 됩니다.
- **세션 수**: 그 동선을 지나간 방문 횟수. 이벤트 개수로 세면 한 명이 열 번 누른 게 열 명처럼 보입니다. 그래서 **세션 기준**으로 셉니다.
- **비율**: 분모를 명시해야 합니다. "전체의 30%"인지 "노이즈 제거 후의 30%"인지에 따라 의미가 완전히 달라집니다.
- **이탈률**: "그 자리가 방문의 마지막이었던 비율"과 "다음 단계로 못 넘어간 비율"은 다른 숫자가 나옵니다. 어느 정의를 썼는지 밝히면 됩니다.
- **실패 비용**: 여기가 망가지면 무엇을 못 하게 되는지. 매출과 직결되는 경로일수록 큽니다.
- **E2E 여부(가설)**: 아직 최종 결정이 아니라 가설입니다. C절에서 확정합니다.

**C절의 결정 규칙**:

- **인증은 필수**: 로그인이 죽으면 모든 게 죽습니다. "빈도는 낮지만 붙이는 경로"의 대표 사례입니다.
- **인증 외 2개 이하 추가 가능, 0개도 가능**: 다만 이유를 써야 합니다.
- **"빈도 높은데 안 붙인 경로"를 하나 이상**: 통합 테스트로 충분한 이유를 씁니다. 이게 "비싼 도구를 아끼는" 연습입니다.

**왜 / 출제 의도**:

- **"빈도 1위니까 E2E"는 함정**: 그 경로를 8주차에 이미 통합 테스트로 검증했을 수 있습니다. 비싼 도구는 **중복 투자가 아닌, 싼 도구가 못 잡는 것**에 쓰는 겁니다. "빈도 = E2E 우선순위"라는 직관을 깨뜨리는 게 이 단계의 숨은 목표입니다.
- **"노이즈를 어떻게 걸렀나"가 핵심**: 로그에 "나 봇이요"라고 적혀있진 않습니다. 스스로 기준을 만들어야 하고, 그 기준을 남이 이해할 수 있게 써야 합니다. **정의를 내리는 능력**을 보는 겁니다.
- **"유지보수 비용 추정"**: 문구 하나 바꿨을 때 테스트 몇 군데를 고치게 되는지 세보면, E2E가 왜 비싼지 몸으로 느껴집니다. 비용 감각을 기르게 하려는 의도입니다.
- **"문서가 코드보다 먼저 커밋"**: 결정이 근거보다 나중이면 "결정 갖다 붙인 근거"가 됩니다. 순서가 곧 신뢰입니다.

**완료조건 쉽게 보기**: 이 문서만 읽고 4단계에 뭐가 들어갈지 알 수 있고, **만들지 않기로 한 것의 이유**도 문서에 있으면 됩니다. "안 하기로 한 결정"을 문서화하는 게 이번 주의 백미입니다.

### 🎭 4단계 — E2E를 구현해요

**하는 일**: 3단계에서 정한 것만 만듭니다. 인증 필수 세 갈래(경로 복원 / 세션 만료 / 틀린 비밀번호) + 정한 것들.

**핵심 규칙들**:

- **`storageState`로 로그인 1회 재사용**: 매 테스트마다 로그인 폼을 채우면 시간이 폭발합니다. 로그인 상태를 파일로 저장해서 재사용합니다.
- **단, 로그인 자체를 검증하는 테스트는 storageState 금지**: 저장된 상태로 시작하면 로그인 과정을 아예 안 거치니, 로그인을 테스트할 수 없기 때문입니다.
- **워커별로 계정 나누기**: 계정이 8개인 이유가 이것입니다. 4명의 워커가 각자 다른 계정을 쓰면 서로의 세션을 덮어쓰지 않습니다.
- **역할/이름 기반 셀렉터**: "버튼, 이름은 로그인"처럼 사용자가 보는 기준으로 찾으면 마크업을 바꿔도 안 깨집니다.
- **`sleep` 금지, 조건 기반 대기만**: 정해진 시간 기다리기는 느리고 불안정합니다. "무엇이 보일 때까지" 기다려야 합니다.
- **trace 직접 열어보기**: 설정만 해두면 실패를 읽는 법을 못 배웁니다. 일부러 실패시키고 trace를 열어보는 4단계 절차를 직접 따라해 보세요. 실패 읽기 실력이 늘어는 지점입니다.

**왜 / 출제 의도**:

- **`--workers=4`와 `--workers=1` 결과가 같아야 한다**: "내 컴퓨터에서는 되는데"는 테스트가 아닙니다. 동시에 돌려도 결과가 같으려면 격리 설계가 바람직하다는 것입니다. E2E가 늘 "불안하다"는 평판은 대부분 격리 실패에서 옵니다.
- **production build 위에서**: 개발 모드와 배포 모드는 다른 코드 경로를 탈 때가 있습니다. 사용자가 겪는 환경에서 검증해야 의미가 있습니다.

**완료조건 쉽게 보기**: 동시에 돌려도, 3번 연속 돌려도 결과가 같으면 됩니다.

### 🔬 5단계 — E2E가 무엇을 잡는지 확인해요

**하는 일**: 인증 구현을 일부러 망가뜨려서(한 곳만! 테스트 코드는 건드리지 말고!) E2E가 실패하는지 확인합니다. 실험 3개 이상, 그중 하나는 통합 테스트가 못 잡는 것(미들웨어 리다이렉트, 쿠키 속성, 초기 HTML의 로그인 상태 등)으로 고릅니다.

**왜 / 출제 의도**:

- **"한 곳만 바꾸는 이유"**: 여러 곳을 동시에 망가뜨리면 어떤 변경을 어떤 테스트가 잡았는지 알 수 없습니다. 실험은 한 번에 변수 하나가 기본입니다.
- **"살아남은 변경이 제일 값진 기록"**: 테스트가 못 잡은 건 부끄러운 게 아니라 정보입니다. 왜 못 잡았는지 알면 테스트가 지켜주는 경계선을 정확히 알게 됩니다.
- **"통합 테스트로도 잡히면?"**: E2E에 둘 이유가 없을 수 있습니다. 비싼 자리를 회수하는 것도 설계입니다.
- **"망가뜨린 코드는 되돌리기"**: 실험용 찌꺼기가 커밋에 남으면 진짜 버그처럼 보입니다.

**완료조건 쉽게 보기**: 실험 기록 표가 있고, "E2E만 잡을 수 있었던 것"이 최소 하나 있으면 됩니다.

### ⚡ Advanced (선택, 하나만)

**A. 시각적 회귀**: 스크린샷을 기준으로 삼아 화면 변화를 잡는 기법. 폰트 로딩, 애니메이션 같은 "매번 조금씩 달라지는 것(비결정성)"을 어떻게 고정할지가 관건입니다.

**B. 에이전트 생성 검수**: AI가 만든 테스트를 내 테스트와 비교하고, 지울 단언을 고르는 연습. healer(실패한 테스트를 자동으로 "고쳐주는" 기능)는 쓰지 않는 이유를 적습니다 — 실패를 감추는 방향으로 동작할 수 있어서입니다.

| ------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| 근거 없이 E2E 개수 늘리기                  | 3단계 표에 없는 시나리오는 "왜 만들었는지"를 대답 못 합니다. 비용만 늘어납니다.                      |
| `waitForTimeout` (시간 기반 대기)          | 컴퓨터가 느리면 실패하고, 빠르면 시간 낭비입니다. 조건 기반 대기로 바꿔야 합니다.                    |

| 스냅샷으로 기능 검증 대체                  | "달라졌다"만 알려주고 "뭘 잘못됐는지"는 알려주지 않습니다. 기능 검증은 단언(assert)으로 해야 합니다. |
| `it.skip` / 주석 처리                      | 꺼버린 테스트는 없는 테스트입니다. 실패를 숨기는 행위입니다.                                         |
| 통과시키려고 가드/복원 로직 지우기         | 테스트를 통과시키기 위해 기능을 없애는 건 본말전도입니다.                                            |

## 6. Technical Writing Quest — 왜 글을 쓰나

이번 주는 코드보다 **결정과 근거**가 주된 산출물입니다. "세션 만료를 어디서 처리했고 왜", "빈도 높은데 안 붙인 경로는 왜" 같은 내용을 PR 본문에 쓰는 이유는:

1. **남을 설득하기 위해** — 실무에서 "이렇게 했습니다"만으론 리뷰가 안 통과합니다. 근거가 있어야 토론이 됩니다.
2. **미래의 나를 위해** — 3개월 후의 나는 왜 그렇게 정했는지 기억하지 못합니다.
3. **AI와 나의 경계를 밝히기 위해** — 단언과 E2E 범위는 AI에게 넘기면 이 과제의 핵심(판단력 훈련)이 사라집니다. 반복 코드는 AI에게 맡기고, 결정은 직접 한 걸 명시하세요.

## 8. 마무리 — 이번 주에서 가져가야 할 것

1. E2E는 비싸다. 그래서 **근거(로그)로 어디에 붙일지 정하고, 정한 것만 만든다.**
2. 인증은 서버 상태다. 만료 처리 위치, 상태 정리 방침처럼 **정답이 없는 결정을 근거와 함께 내린다.**
3. 데이터는 더럽다. **노이즈 기준, 분모, 이탈 정의를 직접 정하고 밝힌다.**
4. 테스트는 만드는 것으로 끝이 아니다. **망가뜨려서 잡히는지 확인해야 가치가 증명된다.**
5. 결정은 문서로 남긴다. **안 하기로 한 것의 이유까지.**
