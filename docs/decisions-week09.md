# 9주차 판단 근거

1·2단계 범위입니다. 3단계 이후는 진행하면서 덧붙입니다.

이번 주 작업의 상위 틀은 **Ontology → Gate → Contract → Harness** 네 층입니다.

- **Ontology** — `SessionStatus`(`authenticated` / `anonymous` / `expired`), 이벤트 이름과 프로퍼티
- **Gate** — `src/proxy.ts`(쿠키 존재), `src/app/_lib/requireSession.ts`(서명·만료)
- **Contract** — `ApiError`가 상태 코드를 잃지 않게 한 것, `meta.authRequired` 표시, A절의 이벤트 계약
- **Harness** — E2E. 3~5단계에서 다룹니다

---

## 1단계 — 인증 구현

### 보호 경로의 경계를 주문서·주문 내역으로 정한 기준

**결정**: `/orders/new`(주문서)와 `/orders`(주문 내역) 두 개만 가드합니다.

담기는 구매 의사 표시 **전** 단계입니다. 여기에 인증을 요구하면 아직 살지 정하지 않은 사람을 로그인 화면으로 밀어내 이탈만 만듭니다. 결제 책임이 실제로 시작되는 지점은 주문서이므로 그 앞에 경계를 둡니다.

장바구니·위시리스트는 비로그인 상태로 열어 둡니다. 두 값은 서버도 URL도 원본을 갖지 않는 클라이언트 전용 상태라(5주차 기준) 인증과 수명이 다릅니다.

부수 효과로 8주차 E2E("비로그인 상태로 담기 → Header 카운트 확인")가 그대로 통과합니다. 다만 이건 결정의 **근거가 아니라 회귀 검증 결과**입니다. 기존 테스트를 지키려고 정책을 정한 것이 아니라, 정책이 기존 정책과 어긋나지 않았음을 확인한 것입니다.

### 복원 경로를 next에 싣고 검증하는 규칙

**파라미터**: `next`. 값은 pathname + search까지만 담고 origin은 넣지 않습니다. origin을 함께 실으면 그 값이 외부 주소로 바뀌었는지 로그인 화면이 다시 검사해야 합니다.

**검증**(`src/shared/lib/safeRedirectPath.ts`)은 세 조건을 모두 통과해야 합니다.

1. `/`로 시작한다 — `https://evil.com` 같은 절대 URL을 막습니다.
2. `//` 또는 `/\`로 시작하지 않는다 — `//evil.com`은 protocol-relative URL이라 앞의 `/` 하나만 보고 통과시키면 브라우저가 외부 절대 주소로 해석합니다. 브라우저는 URL 해석 시 `\`를 `/`처럼 다루므로 `/\evil.com`도 같은 결과가 됩니다.
3. `/login`으로 시작하지 않는다 — 로그인 후 다시 로그인 화면으로 가면 루프가 됩니다. `/loginable` 같은 다른 경로는 통과시킵니다.

앞쪽 공백·제어문자는 검사 전에 떼어냅니다. 브라우저가 URL을 해석하기 전에 같은 문자를 떼어내므로, `\n//evil.com`이 검사만 우회하고 실제로는 외부로 나가는 상황을 막기 위해서입니다.

하나라도 어기면 홈으로 떨어뜨립니다. **값을 고쳐서 살려내지 않습니다** — 조작된 값을 보정하면 무엇을 막았는지 아무 데도 남지 않습니다.

**복원 규칙을 한 곳에 모은 이유**: 로그인 경로 생성은 proxy(Edge)·보호 페이지(서버)·전역 401 처리기(클라이언트) 세 곳에서 일어납니다. 나뉘어 있으면 파라미터 이름이나 검증 여부가 한쪽에서만 바뀌어도 알아채기 어려워서 `buildLoginPath()` 하나로 모았습니다.

실제로 이 통일이 없던 동안 **쿠키 유무에 따라 복원 규칙이 달라지는 문제**가 있었습니다. proxy를 지나는 미로그인 요청은 `pathname + search`를 보존했지만, 쿠키는 있으나 서버 검증에 실패한 경로에서는 각 페이지가 고정 경로만 넘겨 `?from=cart` 같은 조건이 사라졌습니다. `src/app/_lib/currentPath.ts`의 `toCurrentPath()`로 페이지가 실제 경로를 복원해 넘기도록 고쳤습니다.

```
쿠키 없음(proxy)   next=%2Forders%2Fnew%3Ffrom%3Dcart%26step%3D2
위조 쿠키(서버)     next=%2Forders%2Fnew%3Ffrom%3Dcart%26step%3D2
만료 시나리오       next=%2Forders%3Ftab%3Drecent
```

### proxy와 서버가 인증을 두 겹으로 나눠 보는 이유

**proxy는 세션 쿠키의 존재만 확인하고, 서명과 만료는 서버 컴포넌트가 검증합니다.**

두 겹을 쌓아 안전하게 만들려는 것이 아니라, **각 겹이 볼 수 있는 것이 다르기 때문**입니다. `src/proxy.ts`는 Edge 런타임에서 돌고 서명 검증에 필요한 `readSessionToken()`은 `node:crypto`를 씁니다. 한 파일로 합치면 `next build`는 경고만 내고 통과한 뒤 실제 요청에서 500이 납니다 — 빌드로 잡히지 않는 실패입니다.

그래서 proxy는 "쿠키조차 없는 요청"을 걸러내는 빠른 게이트이고, 위조되거나 만료된 쿠키는 통과시킵니다. 그다음 `requireSession()`이 세션을 해석하면서 다시 걸러 로그인으로 되돌립니다.

이 설계의 관측 가능한 결과로, **위조 쿠키를 들고 보호 경로에 접근하면 500이 아니라 로그인 화면으로 되돌아갑니다.** 확인해 보면 주문서 본문은 렌더되지 않고 응답에 `login?next=%2Forders%2Fnew&expired=1`이 실려 있습니다.

한 가지 유의점 — Next 16은 스트리밍 중 `redirect()`를 만나면 HTTP 3xx 대신 RSC 스트림으로 내보내므로 **문서 응답 상태가 200**입니다. 상태 코드만 보고 판단할 수 없고 응답 본문을 봐야 합니다. 실제 이동 여부는 브라우저가 있어야 확인되는 항목이라 3단계에서 E2E 후보로 다룹니다.

### 세션 만료 처리 — 401의 의미·범위·위치·안내

만료 처리는 네 단계가 이어진 하나의 결정입니다. 판정 기준만 정하고 처리 위치를 따로 정하면 둘의 연결이 끊깁니다.

**① 401의 의미를 가르는 기준**

`/api/auth/me`는 "로그인 안 함"과 "세션 만료"를 **같은 401**로 돌려줍니다. 응답만으로는 갈리지 않으므로 **요청에 세션 쿠키가 실려 있었는지**로 가릅니다.

| 쿠키 | 응답 | 판정                                    |
| ---- | ---- | --------------------------------------- |
| 없음 | 401  | 로그인한 적 없음(`anonymous`)           |
| 있음 | 401  | 그 세션이 더는 유효하지 않음(`expired`) |

서버는 `resolveSessionStatus()`로 바로 가릅니다. 클라이언트는 httpOnly 쿠키를 읽을 수 없으므로 **직전 캐시 값**으로 대신합니다 — 로그인 상태였는데 401이 왔다면 만료, 처음부터 `null`이었다면 미로그인입니다.

**② 만료로 볼 요청의 범위**

모든 401을 만료로 다루면 안 됩니다. `/api/auth/login`의 401은 **자격 증명 불일치**이지 만료가 아닙니다. 비밀번호를 틀렸을 뿐인데 "세션이 만료되었습니다"가 뜨면 사용자는 무엇을 고쳐야 할지 알 수 없습니다.

그래서 인증이 필요한 요청에만 `meta.authRequired`를 붙이고, 전역 처리기는 그 표시가 있는 요청의 401만 만료로 다룹니다. 조회(`ordersQueryOptions`)와 변경(`useCreateOrderMutation`)이 같은 기준을 씁니다. 표시가 없으면 공개 조회가 다른 사유로 401을 받았을 때도 로그인 화면으로 보내게 됩니다.

세션 조회 자체는 401을 에러로 던지지 않고 `null`로 돌려줍니다. `/api/auth/me`의 401은 "조회 실패"가 아니라 "로그인하지 않은 상태"라는 정상 응답이고, 에러로 두면 화면마다 에러 UI가 뜹니다.

**③ 처리 위치는 한 곳**

`src/app/providers.tsx`의 QueryClient 전역 핸들러입니다. 화면마다 401을 다루면 나중에 어디를 고쳐야 할지 알 수 없어집니다. 모든 클라이언트 조회가 `apiResponseResult()`를 지나므로 캐시 단위 `onError` 두 개(QueryCache·MutationCache)로 전부 받을 수 있습니다.

이를 위해 `apiResponseResult()`가 던지는 값을 바꿨습니다. 기존에는 `message`만 담은 `Error`를 던져 호출부에서 401을 다른 실패와 구분할 방법이 없었습니다. `ApiError`가 상태 코드를 함께 담되 `Error`를 상속하므로 `error.message`만 읽던 기존 화면(`ErrorRetry` 등)은 그대로 동작합니다.

**④ 화면 안내**

만료면 `/login?next=현재경로&expired=1`로 보내고 "세션이 만료되었습니다. 다시 로그인해 주세요."를 띄웁니다. 미로그인이면 안내 없이 로그인 폼만 보여줍니다.

만료 여부는 파라미터의 **존재**가 아니라 **값**으로 판정합니다. 존재만 보면 `?expired=0`처럼 사람이 주소를 고쳐 넣은 값에도 안내가 뜹니다. 보안 경계는 아니지만 사실과 다른 안내가 남습니다. `EXPIRED_FLAG`와 `isExpiredFlag()`를 생성 측(`buildLoginPath()`)과 같은 모듈에 둬서 두 쪽이 같은 계약을 씁니다.

### 5주차 클라이언트 상태 패턴을 세션에 그대로 써도 되는지

결론부터 적으면 쓰지 않았습니다. 다만 "서버 상태니까 TanStack Query"라는 분류만으로 넘기지 않고, 5주차 패턴을 세션에 실제로 대입해 어디가 어긋나는지 확인했습니다.

**5주차 패턴이 무엇이었나**

위시리스트·장바구니는 `zustand` + `persist`로 짰습니다. `createJSONStorage`로 sessionStorage에 저장하고, `skipHydration: true`로 둔 뒤 `providers.tsx`의 `useEffect`에서 rehydrate하고, `version`·`migrate`로 저장 형식을 진화시키고, `onRehydrateStorage`에서 손상된 값을 만나면 초기화합니다. 이 조합의 목적은 하나입니다 — **값을 브라우저에 남겨 두었다가 되살리는 것.**

**세션에 그대로 대입하면**

| 5주차 장치                              | 세션에 적용하면                                                                                                                                                                                                                                                                                                                                                                          |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `persist` (저장)                        | **해롭습니다.** 세션의 판정 근거는 httpOnly 쿠키의 서명과 만료이고 그 판정은 서버가 합니다. 클라이언트에 복제본을 저장하면 쿠키가 만료된 뒤에도 저장소에는 "로그인됨"이 남습니다. 저장소는 사용자가 편집할 수 있어서, 화면은 로그인으로 보이는데 API는 401을 돌려주는 상태를 만들 수 있습니다. 실제 권한은 서버가 쥐고 있으니 권한 구멍은 아니지만, **화면이 사실과 다른 상태**가 됩니다 |
| `skipHydration` + `useEffect` rehydrate | **요구사항과 부딪힙니다.** 장바구니는 초기 HTML에 0으로 그려졌다가 rehydrate 후 채워져도 됩니다. 세션에는 "자바스크립트 실행 전에도 로그인 상태가 보여야 한다"는 요구가 있어서, hydration 이후에 값이 도착하는 구조로는 지킬 수 없습니다. 같은 장치가 한쪽에서는 허용되고 다른 쪽에서는 요구 위반이 됩니다                                                                               |
| `version` · `migrate`                   | 쓸 자리가 없습니다. 저장 형식을 진화시킬 이유가 없고, 세션은 매 요청 서버가 새로 정합니다                                                                                                                                                                                                                                                                                                |
| `onRehydrateStorage` 복구               | 마찬가지입니다. 값이 손상되면 되살릴 게 아니라 서버에 다시 물으면 됩니다                                                                                                                                                                                                                                                                                                                 |
| selector 경계                           | **이건 그대로 유효합니다.** Header가 필요한 최소 슬라이스만 구독한다는 원칙은 저장소 종류와 무관합니다                                                                                                                                                                                                                                                                                   |

핵심은 만료입니다. zustand에는 "이 값이 낡았다"는 개념이 없어서, 만료를 알게 되는 경로(보호 경로 요청의 401)에서 스토어를 직접 세팅해 줘야 합니다. 그러면 서버 응답을 상태 저장소에 손으로 동기화하는 코드가 생기고, 서버가 준 값과 저장된 값이라는 **출처가 둘**이 됩니다. 두 값이 어긋나는 시점이 정확히 만료 시점입니다.

**반대 방향도 확인했습니다** — 그러면 장바구니·위시리스트를 react-query로 옮기면 어떤가. 옮길 수 없습니다. 스타터에 장바구니·위시리스트 서버 저장소가 없어서 조회할 대상이 없습니다. 두 패턴이 공존하는 것이 맞고, 가르는 기준은 5주차와 같습니다 — **원본이 어디에 있는가.**

**그래서 채택한 구조**

세션은 `SESSION_QUERY_KEY`에 담긴 react-query 캐시에만 둡니다. zustand는 장바구니·위시리스트만 계속 맡습니다.

- **초기값** — 세션이 필요한 페이지가 서버에서 읽어 `setQueryData`로 심고 `HydrationBoundary`로 내려보냅니다. 그래서 초기 HTML에 로그인 여부가 이미 그려진 채로 도착하고, 클라이언트가 같은 값을 이어받습니다. 저장이 아니라 **전달**이라 위의 `persist` 문제가 생기지 않습니다.
- **재조회 억제** — `staleTime`을 세션 수명(`SESSION_TTL_SECONDS`)으로 잡았습니다. 그대로 두면 마운트 직후 background refetch가 나가는데, `/api/auth/me`에는 500ms 지연이 걸려 있어 홈 cold load의 waterfall에 지연 요청이 하나 더 얹힙니다.
- **만료 감지** — `staleTime`이 만료를 처리하는 것이 아닙니다. 만료는 시간이 아니라 **보호 경로 요청의 401**로 알게 되고, 그때 전역 처리기가 세션을 `null`로 바꾸고 로그인으로 보냅니다.

실측으로 확인했습니다 — `/`와 `/products` cold load 요청 목록에 `/api/auth/me`가 없습니다.

### 로그아웃 시 클라이언트 상태를 비우기로 한 근거

**결정**: 장바구니와 위시리스트를 모두 비웁니다.

둘 다 sessionStorage에 담기므로 탭을 닫으면 사라집니다. 그런데 **로그아웃은 탭을 닫는 행동이 아닙니다.** 정리하지 않으면 같은 탭을 이어 쓰는 다음 사람에게 이전 사용자가 담은 목록이 그대로 보입니다.

**대가**: 잠깐 로그아웃했다 돌아온 사용자도 목록을 잃습니다. 두 값을 세션과 무관한 브라우저 로컬 상태로 볼 수도 있지만, 노출 쪽을 더 무겁게 봤습니다.

**merge를 검토했다가 접은 이유**

정리와 짝을 이루는 질문이 있습니다 — 비로그인 상태에서 담은 것을 로그인 시 기존 데이터에 합쳐야 하지 않나. 규칙까지 정해 봤습니다. 위시리스트는 집합이라 겹치면 그대로 두고 없던 것만 추가, 장바구니는 수량이 있으니 겹치면 `+1`.

접은 이유는 **합칠 상대가 없어서**입니다. 스타터 API는 `home`·`products`·`auth`·`orders` 넷뿐이고 장바구니·위시리스트 서버 저장소가 없습니다. 두 값은 sessionStorage에만 있고 사용자별로 나뉘지도 않습니다. 지금 merge를 넣으면 서버에서 온 데이터가 아니라 같은 브라우저의 저장소 두 칸을 합치는 것이 되어, 규칙은 있는데 그 규칙이 지키는 대상이 없습니다.

수량 개념도 없습니다. `productIds: Set<string>`이라 "담겼다/아니다"만 있어서 `+1`을 하려면 자료구조와 persist migrate, 주문서의 수량 조절 UI가 함께 따라옵니다. 서버 저장소가 없는 상태에서 그 비용을 치를 이유가 없다고 봤습니다.

merge 규칙 자체는 5주차에 이미 적어 뒀습니다(`docs/decisions-week05.md`의 「로그인·서버 동기화가 생기면 위시리스트 소유권이 어떻게 달라지는지」). 서버 저장소가 생기는 시점에 그 문서의 규칙을 그대로 꺼내 쓰면 됩니다. **이번 주에는 정리만 하고 merge는 넣지 않습니다.**

이 정리 코드는 5단계에서 지워보는 실험 대상이 됩니다.

### Header를 루트 layout으로 옮기지 않은 이유

이 항목은 **처음에 결정으로 적었다가 측정으로 뒤집힌 것**이라 그 과정을 남깁니다.

초기 HTML에 로그인 상태를 반영하려면 서버가 세션을 읽어야 하고, Header를 루트 `layout.tsx`로 올려 거기서 `cookies()`를 부르면 한 곳에서 끝납니다. 처음에는 "홈은 이미 `force-dynamic`이고 `/products`는 `searchParams`로 이미 동적이니 새로 깨질 정적 범위가 없다"고 적었습니다.

**틀렸습니다.** 확인 범위가 두 라우트뿐이었고, 변경 전 빌드 출력을 보니 정적 라우트가 셋 있었습니다.

```
변경 전 정적: /_not-found  /examples  /performance-lab/inp
```

루트 layout에서 `cookies()`를 부르면 이 셋이 전부 요청 시 렌더링으로 바뀝니다. 인증 구현이 편하다는 것 말고 그 손실을 정당화할 근거가 없었습니다.

**채택한 구조**: Header는 지금 자리에 두고, **세션이 필요한 페이지만** `readServerSession()`을 부릅니다. `/examples`와 `/performance-lab/inp`는 Header를 쓰지 않으므로 세션을 읽을 이유가 없고, 그래서 정적으로 남습니다.

```
변경 후 정적: /_not-found  /examples  /performance-lab/inp   (유지)
신규 동적:   /login  /orders  /orders/new                    (신규라 회귀 아님)
```

부수 효과로 7주차 결정도 그대로 보존됩니다. Header가 `<main className="week05-page">` 안에 남으므로 `.week05-page`가 주는 폭·중앙정렬을 유지하고, `.week05-page a:focus-visible` 같은 하위 선택자로 걸린 포커스 스타일도 잃지 않습니다. `products/loading.tsx`의 fallback 기하도 그대로입니다.

대가는 세션 주입 코드가 페이지마다 반복된다는 것입니다. 라우트 그룹 layout에서 읽는 방법도 있었지만 그 경우에도 Header가 `<main>` 밖으로 나가는 문제는 남아서 택하지 않았습니다.

### fallback Header가 로그인 상태를 단정하지 않게 한 이유

위 구조에는 처음에 빠진 곳이 있었습니다. `src/app/products/loading.tsx`는 라우트 fallback이라 page의 `HydrationBoundary` **밖**에 있고, 그래서 세션을 물려받지 못했습니다.

fallback과 본 콘텐츠는 같은 초기 HTML에 함께 실립니다. 그 결과 로그인한 사용자에게도 **먼저 그려지는 Header가 로그인 링크를 보여주는** 상태가 됐습니다. 자바스크립트가 교체하기 전까지는 사실과 다른 화면입니다. "초기 HTML에 로그인 상태를 반영한다"를 확인할 때 content Header만 보고 fallback Header를 보지 않은 누락입니다.

두 겹으로 고쳤습니다.

**① Header가 세션 값의 세 상태를 구분합니다.**

| 값          | 뜻                | 렌더                        |
| ----------- | ----------------- | --------------------------- |
| `undefined` | 아직 모른다       | 아무것도 그리지 않는다      |
| `null`      | 로그인하지 않았다 | 로그인 링크                 |
| `AuthUser`  | 로그인했다        | 주문 내역 · 이름 · 로그아웃 |

기존에는 `user ? A : B`로 `undefined`와 `null`을 한데 묶어 "모름"을 "미로그인"으로 단정했습니다. 모를 때는 어느 쪽도 그리지 않는 편이 낫습니다 — 틀린 상태를 보여주는 것보다 비어 있는 편이 사실에 가깝습니다.

**② fallback이 직접 세션을 읽습니다.**

`loading.tsx`가 `readServerSession()`을 부르고 자체 `HydrationBoundary`로 세션을 심습니다. `cookies()`는 I/O가 없어 shell 지연이 사실상 없고, 이 라우트는 이미 요청 시 렌더링이라 렌더링 범위도 달라지지 않습니다. Header를 `loading.tsx`에서 제거하지 않았으므로 7주차의 "로딩 중 Header 선표시" 결정도 유지됩니다.

확인 결과 로그인 상태에서 응답에 담긴 두 Header가 **문자열까지 동일**합니다.

### 보호 경로 링크의 프리페치를 끈 기준

App Router의 `<Link>`는 뷰포트에 들어오면 그 경로의 RSC 페이로드를 자동으로 미리 받습니다(`?_rsc=` 요청). 7주차 Part 4에서 카테고리 링크의 자동 프리페치를 hover 시점으로 옮겨 첫 로드 요청을 41건에서 32건으로 줄인 결정이 있습니다. Header에 링크가 늘면서 그 라인이 흔들렸습니다.

| 링크                                           | 판단               |
| ---------------------------------------------- | ------------------ |
| `/orders/new`(장바구니) · `/orders`(주문 내역) | `prefetch={false}` |
| `/login`(로그인)                               | 프리페치 유지      |

**보호 경로를 끈 이유**: 장바구니 링크는 로그인 여부와 무관하게 항상 헤더에 있습니다. 미로그인 상태에서 프리페치하면 proxy가 307로 로그인 경로를 돌려줄 뿐이라 화면에 쓰이지 않습니다. 클릭한 뒤에 로그인 화면으로 보내는 것으로 충분합니다.

**`/login`을 둔 이유**: 성격이 다릅니다. 미로그인 사용자가 실제로 도착하는 목적지라 예열이 헛되지 않습니다.

대가는 `prefetch={false}`가 hover 프리페치까지 끈다는 점입니다(7주차 Part 4에서 실측으로 확인된 성질). 세 경로 모두 클릭 빈도가 낮아 감수할 만하다고 봤습니다.

실측 결과입니다.

| 상태   | 페이지      | 총 요청 | `_rsc` 프리페치 |
| ------ | ----------- | ------- | --------------- |
| 익명   | `/`         | 35      | 5               |
| 익명   | `/products` | 34      | 5               |
| 로그인 | `/`         | 33      | 3               |
| 로그인 | `/products` | 32      | 3               |

`/orders`·`/orders/new`는 두 상태 모두에서 사라졌고, 로그인 상태 홈은 33건으로 7주차 기준선과 같습니다. 익명만 `/login?_rsc=` 2건(약 2.6KB)이 얹혀 있습니다.

### FSD·Edge 경계를 기계로 강제한 방법과 그 한계

**FSD 레이어 경계.** 인증 계약이 스타터의 `src/app/api/_data/`에 있었는데 이건 `boundaries/elements` 기준으로 `app` 레이어입니다. 정책상 `entities`는 `shared`만, `features`는 `shared`·`entities`만 참조할 수 있어 화면 쪽이 응답 계약을 알 방법이 없었습니다. 소유권을 레이어에 맞춰 나눴습니다.

| 무엇             | 어디로                                                                       | 이유                                                                         |
| ---------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 쿠키 이름·TTL    | `src/shared/config/session.ts`                                               | proxy·app 양쪽이 쓰는 상수. 의존이 없어 어느 레이어에서든 아래로 참조 가능   |
| 응답 타입        | `src/entities/session/model/session.ts`, `src/entities/order/model/order.ts` | 타입 전용. 라우트(app)가 entities를 참조하는 방향은 허용됨                   |
| 서명·검증·저장소 | `src/app/api/_data/auth.ts`에 잔류                                           | `node:crypto`와 프로세스 메모리. 하위 레이어로 내리면 클라이언트 번들로 샌다 |

같은 이유로 `readServerSession()`은 `src/app/_lib/`에 뒀습니다. `cookies()`와 `readSessionToken()`이 둘 다 서버 전용이라 entities에 두면 레이어 위반이면서 동시에 `node:crypto`가 하위로 새는 경로가 생깁니다.

**Edge 런타임 경계.** 처음에는 `boundaries/elements`에 proxy를 등록해 막으려 했는데 동작하지 않았습니다. element 패턴은 폴더만 매칭해서 루트 파일인 `src/proxy.ts`가 어떤 element에도 분류되지 않고, 그러면 `boundaries/dependencies`가 이 파일을 아예 검사하지 않습니다. 위반을 일부러 주입해 확인했습니다 — 에러가 나오지 않았습니다.

파일 범위 `no-restricted-imports`로 바꿔 `src/proxy.ts`가 `@/shared/*` 밖과 `node:*`를 참조하면 error가 나게 했습니다. 다시 위반을 주입해 error가 나오는 것과 원복 시 통과하는 것을 확인했습니다.

**한계**: eslint는 직접 import만 봅니다. `@/shared/*` 안의 모듈이 나중에 Node 전용 모듈을 끌어오면 이 규칙은 잡지 못합니다. 그래서 `pnpm start`로 띄워 보호 경로에 요청을 보내 500이 아닌지 확인하는 것이 최종 검증입니다.

**테스트 환경 경계.** `test/msw/setup.ts`가 `onUnhandledRequest: 'error'`라, Header가 세션을 조회하게 되는 순간 Header를 렌더하는 dom 테스트가 전부 unhandled request로 실패합니다. `test/msw/handlers.ts`에 `/api/auth/me` 기본 핸들러(401 미로그인)를 추가해 기존 테스트가 미로그인 상태로 그대로 통과하게 했습니다.

### 판단을 테스트로 고정한 것

문서에 적은 규칙 중 말로만 남으면 다음 사람이 바꿔도 알 수 없는 것들을 테스트로 옮겼습니다. 1단계에서 테스트는 156개에서 181개로 늘었고, 늘어난 25개가 전부 여기에 해당합니다.

| 무엇                   | 어디                       | 고정한 규칙                                                                                 |
| ---------------------- | -------------------------- | ------------------------------------------------------------------------------------------- |
| 복원 경로 검증         | `safeRedirectPath.test.ts` | 절대 URL·protocol-relative·앞쪽 공백 우회·로그인 루프를 각각 막는지                         |
| 만료 표시 계약         | 〃                         | `buildLoginPath()`가 만든 경로를 `isExpiredFlag()`가 그대로 읽는지. 한쪽만 바뀌면 깨짐      |
| 현재 경로 복원         | `currentPath.test.ts`      | 배열 값 유지·빈 값 처리·인코딩, 그리고 만들어낸 경로가 `safeRedirectPath` 검증을 통과하는지 |
| 401을 만료로 다룰 범위 | `providers.test.ts`        | 인증 필요 조회·변경만 로그인으로 보내고, 공개 조회와 로그인 요청은 보내지 않는지            |

401 정책은 `createQueryClient()` 안에 있어서 테스트를 위해 이 함수만 `export` 했습니다. `MainProvider` 전체를 렌더링하지 않고 실제 QueryClient와 캐시 오류 처리기를 그대로 돌리므로, 검증 범위가 정책에만 머뭅니다.

**테스트가 무엇을 잡는지 확인했습니다.** 규칙을 한 번에 한 곳씩 망가뜨려 보고 실패가 나오는지 봤습니다. 테스트 코드는 건드리지 않았습니다.

| 망가뜨린 곳                      | 결과                                                                 |
| -------------------------------- | -------------------------------------------------------------------- |
| 조회 쪽 `authRequired` 검사 제거 | 잡힘 — "공개 조회의 401이면 이동하지 않는다" 외 1건 실패             |
| 변경 쪽 `authRequired` 검사 제거 | 잡힘 — "로그인 요청의 401이면 이동하지 않는다" 실패                  |
| `hadSession` 판정을 항상 참으로  | 잡힘 — "직전에 로그인 상태가 아니었으면 만료로 표시하지 않는다" 실패 |
| proxy에서 `@/app/*` import       | 잡힘 — lint error                                                    |

셋 다 실패 메시지만 읽고 어느 규칙이 깨졌는지 알 수 있었고, 실험 후 전부 되돌렸습니다. 5단계에서 쓸 방식을 작은 규모로 미리 돌려본 셈입니다.

### 서버 세션 읽기를 요청당 한 번으로 묶은 이유

`/products` 요청 하나에서 `loading.tsx`와 `page.tsx`가 각각 `readServerSession()`을 부릅니다. `cookies()`는 Next가 요청 단위로 메모이즈하지만 `readSessionToken()`의 서명 계산은 부를 때마다 다시 돕니다.

같은 요청 안에서는 같은 쿠키를 보므로 결과도 같습니다. React `cache()`로 감싸 한 번만 계산하게 했습니다 — `getQueryClient`가 이미 쓰는 방식입니다.

묶은 뒤에도 두 Header가 모두 로그인 상태를 그리는지 확인했습니다. `cache()`가 두 번째 호출을 건너뛰면서 fallback이 세션을 못 받는 일은 생기지 않습니다.

**측정 중 발생한 오류 하나**: LCP element 비교를 처음 돌렸을 때 After 서버를 띄우는 셸의 cwd가 Before worktree에 남아 있어 **After도 Before 빌드를 잰** 결과가 나왔습니다. 다시 측정해 위 값을 얻었습니다. Lighthouse 측정은 스크립트 내부에서 디렉터리를 옮기므로 영향이 없었고, After에서만 `/login?_rsc=`가 잡힌 것으로 교차 확인됩니다.

**이번 측정의 범위**

목표는 하나였습니다 — **1단계 변경이 7주차에 확보한 기준을 깼는가.** 성능을 개선하려는 라운드가 아니라 회귀 확인이므로, 같은 조건에서 Before/After를 나란히 재는 것으로 답이 나옵니다.

그래서 아래는 범위 밖입니다. 못 한 것이 아니라 이 측정이 답하려던 질문이 아닙니다.

- **filmstrip 표시 순서** — 타이밍이 걸린 스크린샷은 측정 프로토콜상 사용자가 DevTools Performance 패널에서 직접 녹화합니다.
- **Fast 4G throttling** — 7주차식 성능 라운드의 조건입니다. 이번은 Before/After가 같은 조건이기만 하면 되므로 Lighthouse desktop preset 기본값을 그대로 썼습니다.
- **로그인 상태 CLS** — 회귀 여부는 익명 로드의 Before/After 대조로 판정됩니다.

**구조로 답한 것**

로그인 상태에서 fallback Header와 content Header가 다르면 시프트가 생길 수 있는데, 이건 측정 대신 응답 본문으로 확인했습니다. 두 Header가 **문자열까지 동일**하므로 그 구간에서 시프트가 구조적으로 발생할 수 없습니다.

이 질문에 한해서는 측정이 더 약한 증거입니다. CLS는 뷰포트 안의 `had_recent_input: false` 시프트만 세는 샘플값이라, 전환 창이 짧으면 마크업이 실제로 달랐어도 0이 나올 수 있습니다. 수정 전 상태에서 CLS를 쟀다면 "0이니 문제없다"는 잘못된 결론이 나왔을 가능성이 있습니다 — 그때 헤더는 로그인 링크에서 로그아웃 버튼으로 바뀌고 있었습니다.

**알고 있으나 이번에 다루지 않은 동작**

로그인 상태에서 장바구니·위시리스트 카운트가 rehydrate로 `0 → N`으로 바뀌면 헤더 폭이 변합니다. `skipHydration: true`와 `providers.tsx`의 rehydrate에서 오는 동작으로, 1단계 이전부터 있었고 이번 변경이 만든 것이 아닙니다. 다만 헤더 항목이 늘어난 상태에서 어떻게 전파되는지는 확인하지 않았습니다.

**실제 환경 확인**(`pnpm start`, production build)

| 항목                      | 결과                                                    |
| ------------------------- | ------------------------------------------------------- |
| 미로그인 → 보호 경로      | 307 + `Location: /login?next=%2Forders%2Fnew`           |
| 로그인 후 보호 경로       | `/orders/new` · `/orders` 모두 200                      |
| 초기 HTML 로그인 상태     | JS 없이 `루퍼1님` · 로그아웃 · 주문 내역 노출           |

**남은 항목** — 특정 환경에서 `pnpm test`의 공통 `afterEach`(`vitest.setup.ts`의 `window.localStorage.clear()`)가 실패한다는 보고가 있습니다. Node 24의 실험적 Web Storage가 전역을 가려 `--localstorage-file` 없이 접근하면 던지는 경우로 보이지만, 같은 Node 버전에서 재현되지 않아 원인을 확정하지 못했습니다. dom 테스트 전체가 지나는 공통 경로라 추측으로 `try/catch`를 씌우면 정리가 조용히 건너뛰어져 테스트 간 오염이 생깁니다. 실패 메시지를 확보한 뒤 고칩니다.

## 2단계 — 이벤트 계측

계약은 `docs/rfc/week09-e2e-scope.md` A절에 있습니다. 여기에는 그 계약을 왜 그렇게 정했는지를 남깁니다.

---

### 이벤트 이름을 시드 로그 그대로 쓴 이유

**결정**: `fixtures/events-30d.jsonl`의 이름을 변환 없이 씁니다.

이름을 새로 지으면 기존 로그와 새 로그가 같은 행동을 다른 이름으로 갖게 되어, 두 구간을 잇는 집계마다 변환표가 필요합니다.

로그를 여는 시점은 대개 이슈가 생겼을 때입니다. 그때 변환표를 옆에 두고 대조하며 읽으면, 원인을 좁혀야 하는 상황에 확인 단계가 하나 더 붙습니다.

이름 문자열은 `src/analytics/events.ts` 한 곳에 상수로 둡니다. 화면 코드에 흩어지면 오타가 나도 빌드는 통과하고, 로그가 쌓인 뒤에야 드러납니다.

---

### 계측하지 않는 것을 고른 기준

**기준**: 시드 이벤트와 같은 의미로 대응할 수 있는 화면이나 처리 계약이 현재 서비스에 없으면 제외합니다.

과제 문서가 아니라 시드 로그를 목록의 출처로 삼았습니다. 13종 중 두 개를 뺐습니다.

- `product_detail_view` — 상세 화면이 없습니다. 화면이 없으니 발생 지점도 없습니다.
- `client_error` — 에러가 없어서가 아니라, 무엇을 하나의 오류로 볼지 정하는 계약이 아직 없어서입니다. 목록 이미지 12개는 각각 따로 로드되므로 이미지마다 한 줄을 남길지 화면 단위로 묶을지, 같은 오류의 반복을 어떻게 억제할지, `code`·`path`에 무엇을 넣을지가 먼저 정해져야 합니다. 그 계약 없이 넣으면 로그의 양만 늘어납니다.

없는 것을 "화면이 없다"와 "계약이 없다"로 나눠 판단했습니다. 앞의 것은 만들 대상이 아니고, 뒤의 것은 정하면 넣을 수 있는 대상입니다.

---

### 가격을 로그에 남기지 않은 이유

**결정**: `order_complete`에 `totalPrice`를 넣지 않고 `orderId`를 넣습니다.

주문 API가 금액을 받지도, 검증하지도, 응답하지도 않습니다. 클라이언트가 계산한 값을 넣으면 그 숫자는 서버가 확정한 금액이 아니라 화면이 그때 알고 있던 값입니다. 두 값이 어긋나도 로그만 봐서는 알 수 없습니다.

`orderId`를 남기면 금액이 필요할 때 주문 데이터에서 확정된 값을 가져올 수 있습니다.

---

### `userId`의 출처를 세션 상태로 둔 이유

**결정**: `identify()` 호출을 기억해 두지 않고, 이벤트가 발생하는 시점에 세션 캐시를 읽습니다.

스타터 로거의 `identify()`는 프로바이더에 알리기만 하고 이후 `track()`에 `userId`를 넣지 않습니다. 그래서 공통 프로퍼티가 그 값을 따로 붙여야 합니다.

처음에는 `identifyUser()`가 받은 값을 모듈에 보관하는 방식이었습니다. 로그인 상태는 이 모듈 밖에서 네 갈래로 바뀝니다 — 로그인 성공, 이미 로그인된 채로 새로고침, 세션 만료, 로그아웃. 보관 방식은 이 중 로그인 성공만 지나가므로 나머지에서 값이 어긋납니다. 새로고침은 로그인 함수를 다시 거치지 않아 `userId`가 빠지고, 만료는 로그아웃 버튼을 거치지 않아 이전 값이 남습니다.

발생 시점에 세션 상태를 읽으면 어느 경로로 바뀌든 다음 이벤트에 반영됩니다. 빠뜨릴 경로가 생기지 않는 구조입니다.

프로바이더가 아는 사용자도 같은 상태를 근거로 맞춥니다. 이벤트를 보내기 직전에 비교해 달라졌을 때만 `identify()`·`reset()`을 부릅니다(`src/analytics/currentUser.ts`).

---

### 로그인 상태의 `login_fail`에 `userId`를 붙이기로 한 것

**결정**: `userId`는 "그 이벤트가 일어난 시점에 인증돼 있던 사용자"를 뜻하고, 이벤트마다 예외를 두지 않습니다.

서비스 정책상 로그인한 사용자도 로그인 화면에 직접 들어올 수 있습니다. 그 상태에서 다른 계정으로 로그인하다 실패하면 기존 사용자가 붙습니다.

`userId`를 실패한 자격 증명의 주인으로 읽으면 어긋나 보이지만, 이 값은 그런 뜻이 아닙니다. 이벤트 하나에만 예외를 두면 로그를 읽을 때마다 그 이벤트가 예외였는지 확인해야 합니다.

---

### 로그인 실패 사유를 네 종류로 나눈 이유

**결정**: `INVALID_CREDENTIALS` · `SERVER_ERROR` · `NETWORK_ERROR` · `UNKNOWN_ERROR`.

화면 문구는 사유를 나누지 않습니다 — 나누면 어떤 이메일이 가입돼 있는지가 드러납니다. 그것과 로그를 같은 기준으로 둘 필요는 없습니다. 로그까지 한 종류로 묶으면 서버가 죽어서 실패한 것과 비밀번호를 틀린 것을 나중에 나눌 수 없습니다.

`NETWORK_ERROR`는 `TypeError`인지로 가리지 않습니다. fetch가 실패할 때 던지는 것도 `TypeError`지만, 응답을 받은 뒤 값을 다루다 나는 오류도 `TypeError`일 수 있습니다. `fetch()` 호출만 감싸 "요청을 보내지 못했다"는 사실로 판정합니다. 응답은 받았으나 본문을 읽지 못한 경우는 `UNKNOWN_ERROR`입니다.

---

### 발생 단위를 클릭이 아니라 상태 전이로 잡은 것

같은 버튼이 담기도 하고 빼기도 합니다. 클릭을 세면 뺀 것도 담은 것으로 잡힙니다.

- **담기·찜** — 담기지 않은 상태에서 담긴 상태로 바뀔 때만 남깁니다. 그 판단에 쓰는 값은 화면이 그려질 때의 상태가 아니라 버튼을 누른 시점에 스토어에서 읽은 값입니다. 다시 그려지기 전에 두 번 눌리면 두 값이 어긋납니다.
- **조건 변경** — URL이 갱신된 뒤에 남깁니다. 조건은 URL이 단일 출처이므로, 갱신 전에 남기면 갱신되지 않은 시도까지 기록됩니다. 같은 값을 다시 고른 경우는 바뀐 것이 없어 남기지 않습니다.
- **화면 진입** — 해당 경로에 들어와 처음 표시될 때 한 번입니다. 같은 화면에서 조건만 바뀌면 컴포넌트가 그대로 남아 있어 다시 남기지 않고, 조건 변경 이벤트로 기록됩니다.

---

### `order_start`가 장바구니 복원을 기다리게 한 방법

**결정**: 저장 상태 복원 시점은 그대로 두고, 이 이벤트가 스토어의 복원 완료 신호를 기다립니다.

담은 목록은 `sessionStorage`에 있고 hydration 이후에 복원됩니다. 주문서가 마운트하자마자 기록하면 새로고침한 주문서가 빈 목록으로 남고, 그 로그만 보면 아무것도 담지 않고 주문서에 들어온 것처럼 보입니다.

한 번은 복원을 렌더 단계로 당겨 자식 effect보다 앞세우는 방식으로 고쳤습니다. 그러면 서버 HTML(0개)과 클라이언트 첫 렌더(N개)가 달라져 hydration이 어긋날 수 있고, 이벤트 하나의 시점을 맞추려고 앱 전체의 hydration 경계를 옮기는 셈이 됩니다. 되돌린 뒤 `useCartHydrated()`(`persist.onFinishHydration`)로 이 이벤트만 기다리게 했습니다.

복원 완료 신호를 구독하므로 저장소가 나중에 비동기로 바뀌어도 성립합니다.

---

### 계측 준비를 렌더 밖으로 옮긴 이유

**결정**: `src/app/analyticsBootstrap.ts`가 모듈이 평가될 때 준비를 끝냅니다.

`track()`은 불린 시점의 공통 프로퍼티를 합쳐 큐에 넣습니다. 준비가 늦으면 그 이벤트는 `sessionId` 없이 남고, 나중에 큐를 비워도 빠진 값은 되살아나지 않습니다.

화면 진입 이벤트는 화면 컴포넌트의 effect에서 나가고, React는 자식의 effect를 부모보다 먼저 실행합니다. 그래서 공통 부모의 effect에 두면 어느 자리든 늦습니다.

렌더 중에 실행하는 방법도 써 봤습니다. 그러면 버려지는 렌더에서도 모듈 상태가 바뀌고, 준비 여부를 기억하는 플래그가 폐기된 렌더의 QueryClient를 붙든 채 굳을 수 있습니다. 모듈 평가는 첫 렌더보다 앞서므로 순서를 맞출 필요 자체가 없어집니다.

세션을 어디서 읽는지는 계측이 알지 않습니다. 그 연결은 앱 계층의 부트스트랩이 맡고, 계측은 넘겨받은 함수만 부릅니다.

---

### 브라우저 QueryClient를 하나로 고정한 이유

**결정**: 브라우저에서는 인스턴스 하나를 지연 생성해 재사용합니다(`src/app/queryClient.ts`).

공통 프로퍼티가 이벤트마다 세션 캐시를 읽는데, 그 코드는 React 훅을 쓸 수 없는 자리에 있습니다. 렌더 밖에서 같은 캐시를 읽으려면 인스턴스가 고정돼야 합니다.

401 처리기가 쓰는 이동 방법은 생성 시점에 없으므로 `setLoginRedirect()`로 나중에 주입합니다. 401은 사용자 조작 뒤에만 오므로 주입이 끝난 뒤입니다. 주입 전 기본값은 전체 이동인데, 보호 화면에 머무르는 것보다 낫다고 봤습니다.

서버에서는 요청마다 새로 만듭니다. 요청 사이에 캐시가 섞이면 다른 사용자의 데이터가 보입니다.

---

### 계측 경계를 기계로 강제한 것

**결정**: `src/analytics`를 boundaries의 별도 요소로 등록합니다.

어느 레이어에도 넣지 않으면 boundaries가 이 폴더를 아예 검사하지 않습니다(위반을 주입해 확인). 그러면 "계측이 화면 로직과 분리된다"는 A-8이 개발자 주의에만 기대게 됩니다.

`analytics → entities`는 타입 전용으로만 엽니다. 이벤트 프로퍼티가 도메인 용어(`CategoryId`, `ProductSort`)를 그대로 쓰되, 값까지 열면 계측이 도메인 로직을 끌고 들어옵니다. `entities`·`shared`에서 계측을 참조하는 방향과 `analytics`가 상위 계층을 참조하는 방향은 막았습니다.

세 방향에 위반을 주입해 실제로 걸리는 것을 확인했습니다.

`shared/analytics`로 옮기는 방법도 있었으나, `shared`는 `entities`를 참조할 수 없어 좁혀 둔 이벤트 타입을 문자열로 되돌리거나 같은 뜻의 타입을 다시 정의해야 합니다.

### 남겨 둔 것 — 동기화 실패의 재시도

스타터 로거는 프로바이더가 던진 예외를 자기 안에서 잡고 넘어갑니다. `identify()`가 실패해도 부른 쪽은 알 수 없고, 다음 이벤트에서는 이미 알린 사용자로 보여 다시 시도하지 않습니다. 실제 분석 SDK가 일시적으로 실패하면 그 뒤로 사용자 연결이 계속 빠질 수 있습니다.

이번에 붙이는 프로바이더는 콘솔 하나뿐이라 여기까지는 다루지 않습니다. 다만 알린 사용자를 기록하는 시점을 호출 뒤로 두어, 로거가 실패를 알리도록 바뀌면 그때 재시도가 성립하게 했습니다.

프로바이더가 여럿일 때 어느 쪽이 실패했는지 가리려면 알린 사용자를 프로바이더별로 나눠 들고 있어야 하는데, 그것도 지금 범위 밖입니다.
