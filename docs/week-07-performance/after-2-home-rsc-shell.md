## 검증한 가설

> LCP 4.2초 중 80 %가 Load Delay다. 홈이 100 % client라 이미지 URL이 초기 HTML에
> 없어 발견이 늦다. 셸을 RSC로 올리면 발견 지연이 줄어든다.
> — [after-1-hero-next-image.md](after-1-hero-next-image.md)

## 바꾼 것

홈의 **렌더링 경계**를 데이터 소유권에 맞춰 다시 그었다.

| 영역                       | 이전            | 이후                          |
| -------------------------- | --------------- | ----------------------------- |
| 데이터 소유자              | Client useQuery | **서버 (async RSC)**          |
| 셸 (h1·설명·hero 이미지)   | 데이터 뒤       | **즉시 렌더**                 |
| hero 문구 (배너 title·설명) | 데이터 뒤      | `Suspense` (스켈레톤)         |
| 카테고리·인기·신상품       | 데이터 뒤       | `Suspense` (스켈레톤)         |

왜 async RSC(선택 A)인가 — 홈은 읽기 전용이고 **URL 조건이 없다.** 필터·정렬·페이지가
없어 브라우저가 조건을 바꿔 재조회할 일이 없다. Client Query를 함께 남기면 같은
데이터를 서버와 브라우저가 이중으로 소유하게 되고, refetch 뒤 두 값이 어긋날 수 있다.

`HydrationBoundary`(선택 C)를 쓰지 않은 이유 — 브라우저가 이 데이터를 다시 가져갈
일이 없어 Query Cache를 직렬화해 실어 보낼 이득이 없다. RSC 응답만 커진다.

### 셸이 실제로 먼저 도착하는가

```
curl -s -o /dev/null -w 'start=%{time_starttransfer}s total=%{time_total}s' http://localhost:3000/
run1  start=0.0096s  total=1.5230s
run2  start=0.0073s  total=1.5247s
run3  start=0.0094s  total=1.5306s
```

**첫 바이트 9 ms, 전체 완료 1.52 s.** 셸은 즉시 나가고 느린 1.5초는 뒤따르는

hero 이미지 참조, 스켈레톤이 모두 들어 있다 (Before는 8.5 KB, `h1` 0건).

## 기각한 변경 — `priority`

셸이 이미지 URL을 알게 됐으므로 preload를 검토할 조건이 갖춰졌다. `priority`를
붙이고 같은 조건으로 5회 측정했다. 원본: `evidence/lh-after3-priority/run1~5.json`

| 지표 | RSC 셸 (범위)         | +priority (범위)      | 판정              |
| ---- | --------------------- | --------------------- | ----------------- |
| LCP  | 2,637 ms (2563~2639)  | 2,713 ms (2634~2719)  | **범위가 겹침**   |
| CLS  | 0.010                 | 0.010                 | 불변              |
| FCP  | 905 ms                | 906 ms                | 불변              |

preload 자체는 동작했다. 초기 HTML에 `<link rel="preload" as="image" imageSrcSet=…>`가
들어갔고 `loading="lazy"`가 사라졌다. **구간도 명확히 움직였다.**

| 구간         | RSC 셸  | +priority |
| ------------ | ------- | --------- |
| Load Delay   | 979 ms  | **130 ms** |
| Load Time    | 578 ms  | 902 ms    |
| Render Delay | 558 ms  | 1,147 ms  |

**발견은 849 ms 빨라졌는데 LCP 총량은 줄지 않았다.** 줄어든 Load Delay가 뒤 구간으로
그대로 옮겨갔다. 이미지가 일찍 도착해도 paint가 그만큼 앞당겨지지 않는다는 뜻이고,
지금 LCP의 상한은 이미지가 아니라 **document 스트림이 끝나는 시점(1.53 s)** 쪽에 있다.

→ **기각하고 되돌렸다.** 측정된 이득이 없는데 초기 HTML에 8개 후보의 preload
srcset을 얹는 비용만 남는다. 이 페이지에서 이미지 쪽을 더 손대는 것은 의미가 없다.

> 이 판정은 시뮬레이션 스로틀 기준이다. 구간 이동이 뚜렷했으므로, 실제 사용자
> 네트워크에서 경합이 있을 때도 이득이 없는지는 Field 데이터로만 확정할 수 있다.
> 지금 근거로는 "이 조건에서 이득 없음"까지만 주장한다.

## 회귀 확인

- 시각적 크기·비율·피사체: `.hero`의 `aspect-ratio`와 `object-fit: cover`, 모바일
  `object-position`까지 그대로다. 이미지 품질을 낮춰 수치를 만든 것이 아니다.
- CLS는 오히려 0.016 → 0.010으로 개선됐다 (fallback이 실제 콘텐츠 자리를 예약).
- 에러 경로: 이전에는 `useQuery`의 `throwOnError`가 route error 경계로 보냈고,
  지금은 async RSC가 던진 것을 같은 `app/error.tsx`가 받는다.
- `pnpm check` 통과 (테스트 38개).

## 남은 것

LCP 2.6초의 상한이 document 스트림 완료라면, 다음 지렛대는 이미지가 아니라
**1.5초 API 자체이거나 셸/데이터 경계의 재배치**다. 하지만 과제는 slow 지연을
없애는 것을 금지하며, 셸은 이미 9 ms에 나간다. **1단계에서 할 일은 여기서 끝난다.**
