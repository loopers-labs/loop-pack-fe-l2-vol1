## 관측 1 — 최초 진입 (보여줄 데이터가 없음)

| 시점    | 화면                                       |
| ------- | ------------------------------------------ |
| 171 ms  | `불러오는 중…` **텍스트 한 줄**, 그리드 없음 |
| 2197 ms | 그리드 12장, `총 30개`                     |

요청: `?q=&category=all&sort=latest&page=1&scenario=slow` → 226~1776 ms (1.55초)

**pending UI가 텍스트 한 줄이라 목록의 크기·개수를 전혀 예상할 수 없다.** 1.5초 동안
빈 화면에 가깝고, 그리드가 나타나는 순간 아래 콘텐츠가 밀린다.

## 관측 2 — 필터 변경 (category=all → fashion)

| 시점              | 그리드 | `aria-busy` | 카드 | 총 개수  | 상태 텍스트     |
| ----------------- | ------ | ----------- | ---- | -------- | --------------- |
| 갱신 전           | 있음   | `false`     | 12   | 총 30개  | —               |
| **갱신 요청 직후** | **없음** | —         | **0** | —      | `불러오는 중…`  |
| 갱신 완료 후      | 있음   | `false`     | 6    | 총 6개   | —               |

**기존 목록이 즉시 통째로 사라진다.** 사용자는 1.5초 동안 자기가 보던 목록을 잃는다.

## 관측 3 — 페이지 이동 (page=1 → 2)

| 시점              | 그리드 | `aria-busy` | 카드 | 총 개수 |
| ----------------- | ------ | ----------- | ---- | ------- |
| 이동 전           | 있음   | `false`     | 12   | 총 30개 |
| **이동 요청 직후** | **있음** | **`true`** | **12** | 총 30개 |
| 이동 완료 후      | 있음   | `false`     | 12   | 총 30개 |

**페이지 이동은 이미 목록을 유지하고 갱신 중임을 `aria-busy`로 알린다.**

### 이 비대칭은 버그가 아니라 5주차의 의도된 결정이다

`entities/product/api/queries.ts`의 `placeholderData`가 **필터가 바뀌면
`undefined`를 반환**하도록 되어 있다. 5주차 근거는 "옛 결과가 새 조건의 결과로
오인되지 않게"였다.

7주차 2단계는 정반대를 요구한다 — *"기존 목록이 있을 때 조건을 바꾸면 목록을 즉시
비우지 않고 갱신 중임을 보여줘요."* **두 요구가 정면으로 충돌한다.**

## 관측 4 — 빠른 연속 변경 (300 ms 간격 4회)

`casual → fashion → goods → digital`

| 요청 조건  | 시작    | 종료    | 상태 |
| ---------- | ------- | ------- | ---- |
| `all`      | 251 ms  | 1771 ms | 200  |
| `casual`   | 2222 ms | 3740 ms | 200  |
| `fashion`  | 2594 ms | 4104 ms | 200  |
| `goods`    | 2955 ms | 4473 ms | 200  |
| `digital`  | 3330 ms | 4871 ms | 200  |

- **최대 4개 요청이 동시에 in-flight** (2955~3740 ms 구간)
- **취소된 요청 0건** — `requestfailed`(`net::ERR_ABORTED`) 이벤트 없음
- 정착 후: URL `?category=digital`, 화면 `총 6개` / 6장 → **일치**

### 정합성이 지켜진 이유는 취소 때문이 아니다

`queryKey: ['products', query]`라 조건마다 캐시 항목이 분리되고, 컴포넌트는 **현재
key만 구독**한다. 늦게 끝난 옛 요청의 응답은 자기 캐시 항목에 들어갈 뿐 화면을
덮지 못한다. **정합성은 구조가 보장하고, 취소는 낭비를 줄이는 별개 문제다.**

취소가 0건인 이유는 `queryFn: () => fetchProducts(query)`가 TanStack Query가 주는
`AbortSignal`을 받지도, `fetch`에 넘기지도 않기 때문이다. 이번 관측에서 **버려진
응답 4건**(all·casual·fashion·goods)이 끝까지 전송됐다.

## 관찰 → 가설 → 반증 → 최소 변경

| # | 관찰한 사실                                                     | 원인 가설                                                                 | 반증할 측정                                                                     | 가장 작은 변경                                                              |
| - | --------------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 1 | 최초 진입 1.5초 동안 `불러오는 중…` 텍스트 한 줄만 보인다        | pending UI가 실제 목록의 공간을 예약하지 않아 교체 시 아래가 밀린다        | 실제 그리드와 같은 열·카드 크기의 fallback으로 바꾼 뒤 layout shift가 남는지 확인 | `isPending` 분기를 텍스트 대신 실제 그리드 크기의 스켈레톤으로 교체          |
| 2 | 필터 변경 시 기존 목록이 즉시 사라진다 (페이지 이동은 유지)      | `placeholderData`가 `filterChanged`에서 `undefined`를 반환하기 때문이다    | 해당 분기를 제거하고 필터 변경에서도 목록이 유지되는지 관측 4를 재실행           | `filterChanged` 분기를 없애고 이전 결과임을 `aria-busy`/스타일로 구분        |
| 3 | 빠르게 바꿔도 최종 URL과 화면이 일치한다                         | 취소가 아니라 query key 분리가 정합성을 보장한다                           | key를 조건별로 분리하지 않은 상태에서 같은 시나리오를 돌려 화면이 덮이는지 확인  | **변경하지 않음** — 이미 요구를 만족한다                                    |
| 4 | 취소된 요청 0건, 버려진 응답 4건이 끝까지 전송된다               | `queryFn`이 `AbortSignal`을 `fetch`에 전달하지 않기 때문이다               | signal 배선 후 같은 시나리오에서 `net::ERR_ABORTED`가 관측되는지 확인            | `queryFn: ({ signal }) => fetchProducts(query, signal)`로 배선              |

## 이번 관측이 못 다룬 것

- **성공 + 0건**, **최초 실패**, **갱신 실패** 화면은 아직 관측하지 않았다.
  `scenario`가 요청당 하나뿐이라 `slow`와 `empty`·`error`를 동시에 재현할 수 없다.
  2단계에서 재현 방법을 먼저 정한 뒤 관측한다.
- **CLS 수치**는 이 축에서 재지 않는다. Layout shifts는 Lighthouse/DevTools 축에서 확인한다.
