# 5주차 상태 설계 — 코드보다 소유권을 먼저 정한다

도구를 먼저 고르지 않는다. 각 상태의 원본이 어디에 있고, 언제까지 살아야 하고,
누가 공유하는지를 정하면 도구는 따라온다.

## 사용한 도구와 버전

API가 메이저 버전마다 달라지므로, 이 글의 판단이 어느 버전 기준인지 먼저 밝힌다.

| 도구 | 버전 | 이 글에서 쓴 API |
| --- | --- | --- |
| React | 19.2.4 | - |
| Next.js | 16.2.10 (App Router) | route handler, `error.tsx` 경계 |
| TanStack Query | v5 (5.101) | `queryOptions`, `retry` 함수 형태, `signal` |
| nuqs | v2 (2.9) | `useQueryStates`, `createParser`, `parseAsStringLiteral` |
| Zustand | v5 (5.0) | `create`, selector 구독 |
| TypeScript | 5.9 | `satisfies` |
| Vitest | v4 (4.1) | `vi.fn<T>`, fake timers |

## 상태 소유권 표

| 상태 | 원본(소유자) | 수명 | 공유 범위 | 선택 | 이유 |
| --- | --- | --- | --- | --- | --- |
| 홈 데이터(배너, 카테고리, 인기, 신상품) | 서버 | 캐시 수명(staleTime 60초) | 홈 페이지 | TanStack Query | 서버 원본의 스냅샷이다. 내가 소유한 값이 아니므로 로딩, 에러, 캐시 수명을 쿼리가 함께 관리한다 |
| 상품 목록과 totalCount | 서버 | 캐시 수명(staleTime 30초) | 목록 페이지 | TanStack Query | 검색 조건별로 다른 스냅샷이다. 조건을 query key에 넣어 조건별 캐시로 분리한다 |
| 검색어, 카테고리, 정렬, 페이지 | URL | URL이 살아있는 동안 | 새로고침, 공유, 뒤로가기 | nuqs | 다시 방문하고 공유해야 하는 조건이므로 원본은 URL이다. 컴포넌트 상태에 두면 복원이 불가능하다 |
| 장바구니, 위시리스트에 담긴 상품 ID | 클라이언트(store) | 앱 세션 | 홈, 목록, 헤더 | Zustand | 비로그인 익명 상태라 서버 원본이 없다. 여러 페이지가 공유하므로 컴포넌트보다 위에 둔다 |
| 헤더의 담김, 찜 개수 | 파생 | - | - | selector 파생 | ID 목록의 length로 계산 가능하다. 별도 상태로 저장하면 불일치의 씨앗이 된다 |
| 제출 전 검색어 입력값 | 컴포넌트 | 입력 중에만 | 검색 폼 하나 | React useState | 제출 전에는 나만 아는 임시 값이다. 제출 시점에 URL로 승격한다 |
| 로딩, 에러, 빈 결과 | 파생(쿼리 상태) | - | - | 쿼리 상태 분기 | isPending, isError, 빈 배열 여부에서 파생한다. 저장하는 순간 실제 상태와 어긋날 수 있다 |

## 중복 저장 금지 원칙

- 서버 응답을 Zustand에 복사하지 않는다. store에는 판별에 필요한 상품 ID만 남긴다.
- URL이 원본인 검색 조건을 컴포넌트 상태에 복제하지 않는다. 예외는 제출 전 입력값 하나다.
- 개수, 포함 여부, 화면 분기는 전부 파생값이다. useState로 동기화하지 않고 렌더 중에 계산한다.

## 도구별 책임을 나눈 기준

- TanStack Query: 원본이 서버에 있는 값 전부. 데이터만이 아니라 요청 중, 실패, 오래됨까지 쿼리의 책임이다.
- nuqs: 공유하고 복원해야 하는 값. 새로고침과 뒤로가기에서 살아남아야 하면 원본은 URL이다.
- Zustand: 서버에도 URL에도 원본이 없는 값. 비로그인 장바구니와 위시리스트가 유일하다.
- useState: 한 컴포넌트 수명에 머무는 값. 제출 전 검색어 하나다.

## staleTime, gcTime 정책

- 전역 staleTime 20초. 새 쿼리가 도메인 정책 없이 추가돼도 한 화면 안의 중복 요청은 피한다.
  홈과 목록 팩토리는 아래의 더 구체적인 정책으로 전역 기본값을 덮어쓴다.
- 홈 staleTime 60초. 배너와 랭킹은 분 단위로 바뀌지 않는다. 탐색 중 홈 재방문에 재요청하지 않는다.
- 목록 staleTime 30초. 조건 이동과 뒤로가기가 잦아 캐시를 즉시 보여주되, 오래되면 백그라운드에서 갱신한다.
- gcTime은 둘 다 5분. 기본값이지만 조건을 바꿨다 되돌아오는 동선을 덮는다는 근거를 확인하고 명시했다.

## store에 저장한 것과 저장하지 않은 것

- 저장: cartIds, wishlistIds 문자열 배열 두 개와 toggle 액션 두 개. 이것이 전부다.
- 저장하지 않음: Product 전체(서버 캐시와 이중 원본이 된다), 개수(length 파생), 포함 여부(includes 파생).
- selector 경계: 헤더는 length만, 카드는 자기 상품의 boolean과 action만 구독한다.
  다른 상품을 토글해도 관련 없는 카드는 리렌더되지 않는다.
- store 자체는 파일 밖으로 공개하지 않는다. 화면은 `useCartCount`, `useIsInCart`,
  `useToggleCart`처럼 용도가 드러나는 selector 어댑터만 사용한다.

## 전역으로 올리지 않은 상태

- 제출 전 검색어: 제출 전에는 누구와도 공유되지 않는다. 폼 로컬 useState에 두고 제출 시 URL로 승격한다.
- 로딩, 에러, 빈 결과: 쿼리 상태에서 파생한다. 전역에 복사하는 순간 실제 상태와 어긋날 수 있다.

## 로그인이 생기면 소유권이 이동한다

위시리스트에 서버 API가 생기면 원본은 store에서 서버로 넘어가고 이 store는 폐기 대상이다.
그 시점에 익명 상태를 계정에 합칠지, 버릴지, 같은 상품 충돌을 어떻게 풀지 결정해야 한다.
지금 ID만 저장해 둔 것도 이 이관을 가볍게 만들기 위해서다.

## 검증 결과

자동 테스트로 고정한 계약 (`pnpm test`, 총 109건)

- 홈에서 담으면 목록의 같은 상품과 헤더 개수가 함께 바뀐다.
- 목록과 홈의 요청 실패 시 전용 에러 화면이 뜨고, 재시도로 목록에 복귀한다.
- URL의 category, sort, page가 화면의 select 값과 API 요청 쿼리에 그대로 나타난다.
- 카테고리를 바꾸면 page가 1로 돌아가고 검색어는 유지된다.
- 검색어는 제출 전에는 URL을 건드리지 않는다.
- page에 0, 음수, 소수, 문자가 와도 parser가 기본값 1로 되돌려 API 400을 차단한다.
- 잘못된 category, sort, page는 화면과 API 요청에서 같은 기본값으로 수렴한다.
- 조건 변경으로 쿼리가 취소되면 AbortSignal이 실제 fetch까지 전달된다.
- store 개수는 length 파생이며 별도 카운트 필드가 존재하지 않는다.
- 클라이언트 상태를 비우면 장바구니와 위시리스트가 함께 초기화된다.
  persist가 없어 새로고침으로도 같은 결과가 되며, 현재 이 어댑터의 용도는 테스트 격리다.

브라우저에서 확인할 항목 (테스트 대역으로는 부분 검증)

- 새로고침과 URL 공유 복원, 뒤로가기와 앞으로가기 복원. history push와 URL 원본 설계로 보장되지만 실기기 확인이 남아 있다.
- 클라이언트 페이지 이동 중 store 유지. Link 이동은 리마운트 없이 store가 살아 있다.
- 에러와 빈 화면은 fetch 대역 테스트로 고정했다. scenario는 사용자 URL 상태와 쿼리 조건에
  포함하지 않았으므로 주소창 입력으로는 재현되지 않는다. 브라우저에서 재현하려면
  개발자 도구의 네트워크 차단이나 API 직접 호출을 쓴다.

## 엣지케이스 점검과 트레이드오프 판단

적용한 것

- page parser를 isSafeInteger로 강화. isInteger는 1e20을 통과시키는데 API는 거절해서,
  재시도로 못 빠져나오는 에러 화면이 될 수 있었다.
- 빈 응답을 둘로 구분. 조건 불일치와 범위 밖 페이지는 다른 상태다.
  후자에는 개수 안내와 1페이지 이동 출구를 준다.
- React Query의 취소 신호를 fetch까지 전달. 조건 연타 시 낡은 요청을 끊는다.
- q parser에 trim 추가. 폼은 제출할 때 잘라내지만 주소창 입력과 뒤로가기는 폼을 거치지
  않아서, 같은 검색어가 공백 유무로 다른 캐시 엔트리를 만들었다. 정규화 관문을 page와
  같은 자리인 parser로 모았다.
- 조건 조립을 `useProductListCondition` 훅으로 이동. pageSize가 화면에서 붙고 있어서
  다른 호출자가 다른 값을 넣으면 같은 URL이 다른 query key가 될 수 있었다.
- 카테고리 표시 이름의 원본을 서버 응답으로 이동. 허용값 목록은 parser가 컴파일 타임
  유니온을 요구해 상수로 남기고, 이름만 응답에서 읽는다. 홈은 이미 응답으로 그리고
  있어서 서버가 이름을 바꾸면 홈과 목록 필터가 서로 다른 이름을 보여줬다.
  응답 전 첫 페인트에는 로컬 폴백을 쓴다.

보류한 것과 이유

- error.tsx(Error Boundary): 계약 밖 200 응답을 막는 안전망인데 mock API는 그런 응답을
  만들지 못하고, Error Boundary는 이후 라운드 주제라 그때 페이지 경계와 함께 설계한다.
- placeholderData로 페이지 전환 중 기존 목록 유지: Advanced C 범위라 Basic에서 제외.

장애영향 범위

- 목록 API 장애: 결과 영역만 에러. 필터와 헤더와 장바구니 상태는 생존한다.
- 홈 API 장애: 단일 endpoint라 홈 전체가 에러 화면이 되지만, 헤더가 layout에 있어
  다른 페이지로의 출구는 살아 있고 재시도 버튼을 둔다.
- 응답이 오지 않는 장애: 타임아웃으로 끊어 로딩에서 멈추지 않게 한다. 무한 로딩은
  에러보다 나쁘다. 사용자가 재시도할지 떠날지 고를 근거조차 주지 않는다.
- store는 순수 토글이라 예외 경로가 없고, persist가 없어 hydration 불일치도 없다.

## 발제 피드백 반영

### 수용한 것

- **HTTP 실패를 status와 서버 메시지를 가진 타입으로 승격.** 지적대로 status를 메시지
  문자열에 섞으면 쓰려는 쪽이 다시 파싱해야 한다. 확인해보니 손실이 하나 더 있었다.
  서버는 `{ message }`를 본문으로 내려주는데 클라이언트가 본문을 읽지 않아 400의
  "요청 조건을 확인해주세요."와 500의 안내가 구분 없이 버려지고 있었다. status와
  serverMessage를 함께 담고, 본문이 JSON이 아니면 status만 남긴다.
- **재시도 분기.** 이전 라운드에서 "우리 UI가 400을 만들 경로가 없어 도달 불가능하다"는
  이유로 보류했던 항목이다. 판단을 바꾼 근거는 두 가지다. 도달 경로가 없다는 것은
  우리 화면 기준이지 서버 기준이 아니고, 실제로 400을 만나면 전역 정책이 한 번 더
  보내고 화면은 재시도 버튼을 줘서 사용자를 같은 실패로 되돌린다. 지금은 400대를 즉시
  실패로 넘기고, 목록은 재시도 대신 검색 조건 초기화를 출구로 준다.
- **검증 규칙을 한 모듈로.** sort 허용값이 두 벌이었고 page 판정은 parser가 `Number`
  기반, route가 정규식 기반으로 달랐다. category는 parser가 리터럴을, route가 mock
  데이터를 봐서 데이터가 늘면 서로 다르게 판정할 수 있었다. 클라이언트 정규화와 서버
  검증은 책임이 다르다는 지적에 동의하고, 책임은 나누되 기준은 하나로 모았다.
- **검색 버튼.** 입력 하나짜리 폼이라 Enter로 제출은 됐지만 제출 수단이 보이지 않았다.
- **라이브러리 버전 명시.** 문서 앞에 표로 넣었다.

### 함께 넣은 것

- **요청 타임아웃.** 지적 목록에는 없었지만 같은 자리의 문제다. 실패는 구조로 남기면서
  응답이 오지 않는 경우는 그대로 두면, 화면이 로딩에서 멈춰 재시도 출구조차 나오지
  않는다. 취소 신호와 타임아웃을 함께 걸고 타임아웃은 재시도 가능한 실패로 분류한다.

### 보류한 것과 이유

- **쿼리 팩토리 도메인별 분리.** 방향에는 동의하지만 축이 다르다. 6주차 FSD 전환에서
  이 조회 계약의 소유자를 정하며 홈과 목록을 페이지 슬라이스로 나누기로 했다. 도메인
  축과 소비처 축은 지금 1:1이라 결과가 같고, 상품 상세가 생기는 시점에 갈린다. 구조
  이동과 기능 수정을 같은 커밋에 섞지 않기 위해 분리 자체는 6주차에서 한다.
- **Suspense 연계.** Error Boundary와 함께 6주차 실패 경계 결정에서 다룬다. 지금의
  `isPending` 인라인 분기와 Suspense는 배타적이라 한쪽만 먼저 넣으면 두 번 고치게 된다.
- **replace 전환.** 기준으로 주신 "공유되나, 북마크되나"를 적용하면 목록 조건 URL은
  공유 대상이므로 `push`를 유지한다. 우려하신 히스토리 오염은 검색 폼이 제출할 때만
  URL을 쓰기 때문에 이미 막혀 있다. 타이핑 한 글자마다 쌓이지 않는다.

## Advanced 선택과 근거

선택한 항목은 D 하나다.

### D. 테스트 (선택)

과제가 요구한 네 축을 전부 자동 테스트로 고정했다.

- Zustand action과 selector: `src/stores/shopping.test.ts`
- Header 개수 파생: `state-contract.test.tsx`의 담기 후 헤더 개수 검증
- nuqs URL 조건과 query key 일치: `searchParams.test.ts`, `queries.test.ts`,
  `state-contract.test.tsx`의 요청 URL 검증
- 홈과 목록의 store 상태 동기화: 같은 상품을 홈에서 담으면 목록 버튼과 헤더가 함께 바뀐다

선택한 이유는 이번 주의 결과물이 화면이 아니라 상태 경계라서다. 경계는 눈으로 확인해도
다음 변경에서 조용히 깨진다. 추가한 복잡도는 테스트 대역 두 개뿐이다. fetch 스텁과
nuqs 테스트 어댑터를 썼고, 새 DOM 환경이나 e2e 러너를 들이지 않았다.

### 선택하지 않은 항목과 이유

- A 상태 영속화: 과제가 새로고침 초기화를 허용한다. persist를 넣으면 hydration 불일치와
  version, migrate까지 따라오는데, 지금 저장할 값은 ID 배열 두 개뿐이라 얻는 것보다
  다룰 예외가 많다. 로그인이 생기면 원본이 서버로 넘어가 이 저장소 자체가 폐기 대상이다.
- B 서버 프리패치: 지금 구조가 두 군데서 막고 있다. `src/app/page.tsx`가 클라이언트
  컴포넌트라 prefetch를 놓을 서버 자리가 없고, `api.ts`가 상대 경로를 써서 서버에서
  부르면 base URL이 없다. 두 곳을 먼저 되돌려야 해서 이번 범위에서 제외했다.
- C 사용자 경험: 재시도 버튼은 기본 과제의 에러 분기로 이미 있다. placeholderData와
  다음 페이지 prefetch는 위의 보류 항목에 근거를 적었다.

## 경계 설계

- `src/lib/commerce/api.ts` — fetch 함수. HTTP 실패를 status와 서버 메시지를 가진
  `ApiError`로 승격해 쿼리가 에러 상태를 알게 한다. 취소 신호와 타임아웃을 함께 걸고,
  재시도 가능 여부와 표시 문구 판단도 여기서 공개한다.
- `src/lib/commerce/productListContract.ts` — 목록 조건의 허용값과 유효성 판정. URL parser와
  API route가 같은 기준을 쓰게 하는 단일 원본이다.
- `src/lib/commerce/queries.ts` — queryOptions 팩토리. key, queryFn, staleTime을 한 정의에
  묶고 `products → list → condition` 계층으로 무효화 범위를 조준한다.
- `src/lib/commerce/searchParams.ts` — nuqs parser. 계약 모듈의 판정 규칙으로 잘못된 URL
  값이 API 계약을 벗어나지 않게 막는 관문. 검색어 공백 제거도 여기서 한다.
- `src/lib/commerce/useProductListCondition.ts` — URL 조건에 pageSize를 붙여 요청 조건으로
  조립하는 유일한 자리. 화면은 조립된 조건만 받는다.
- `src/stores/shopping.ts` — 장바구니, 위시리스트 ID 목록과 toggle 액션만 가진 비공개
  store. 화면에는 용도별 selector 훅을 어댑터로 공개한다.
- 화면은 이 네 경계를 조합만 한다. scenario 제어값은 사용자 상태 어디에도 넣지 않는다.
