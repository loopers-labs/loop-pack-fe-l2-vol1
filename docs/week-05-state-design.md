# 5주차 상태 설계 — 코드보다 소유권을 먼저 정한다

도구를 먼저 고르지 않는다. 각 상태의 원본이 어디에 있고, 언제까지 살아야 하고,
누가 공유하는지를 정하면 도구는 따라온다.

## 상태 소유권 표

| 상태 | 원본(소유자) | 수명 | 공유 범위 | 선택 | 이유 |
| --- | --- | --- | --- | --- | --- |
| 홈 데이터(배너, 카테고리, 인기, 신상품) | 서버 | 캐시 수명(staleTime 60초) | 홈 페이지 | TanStack Query | 서버 원본의 스냅샷이다. 내가 소유한 값이 아니므로 로딩, 에러, 캐시 수명을 쿼리가 함께 관리한다 |
| 상품 목록과 totalCount | 서버 | 캐시 수명(staleTime 30초) | 목록 페이지 | TanStack Query | 검색 조건별로 다른 스냅샷이다. 조건을 query key에 넣어 조건별 캐시로 분리한다 |
| 검색어, 카테고리, 정렬, 페이지 | URL | URL이 살아있는 동안 | 새로고침, 공유, 뒤로가기 | nuqs | 다시 방문하고 공유해야 하는 조건이므로 원본은 URL이다. 컴포넌트 상태에 두면 복원이 불가능하다 |
| 장바구니, 위시리스트에 담긴 상품 ID | 클라이언트(store) | 앱 세션 | 홈, 목록, 헤더 | Zustand | 비로그인 익명 상태라 서버 원본이 없다. 여러 페이지가 공유하므로 컴포넌트보다 위에 둔다 |
| 헤더의 담김, 찜 개수 | 파생 | - | - | selector 파생 | ID 목록의 length로 계산 가능하다. 별도 상태로 저장하면 불일치의 씨앗이 된다 |
| 제출 전 검색어 입력값 | 컴포넌트 | 입력 중에만 | 검색 폼 하나 | React useState | 제출 전에는 나만 아는 임시 값이다. 제출 시점에 URL로 승격한다 |
| 로딩, 에러, 빈 결과 | 파생(쿼리 상태) | - | - | 쿼리 상태 분기 | isPending, isError, 빈 배열 여부에서 파생한다. 저장하는 순간 실제 상태와 어긋날 수 있다 |

## 중복 저장 금지 원칙

- 서버 응답을 Zustand에 복사하지 않는다. store에는 판별에 필요한 상품 ID만 남긴다.
- URL이 원본인 검색 조건을 컴포넌트 상태에 복제하지 않는다. 예외는 제출 전 입력값 하나다.
- 개수, 포함 여부, 화면 분기는 전부 파생값이다. useState로 동기화하지 않고 렌더 중에 계산한다.

## 경계 설계

- `src/lib/commerce/api.ts` — fetch 함수. HTTP 실패를 throw로 승격해 쿼리가 에러 상태를 알게 한다.
- `src/lib/commerce/queries.ts` — queryOptions 팩토리. key, queryFn, staleTime을 한 정의에 묶는다.
- `src/lib/commerce/searchParams.ts` — nuqs parser. 잘못된 URL 값이 API 계약을 벗어나지 않게 막는 관문.
- `src/stores/shopping.ts` — 장바구니, 위시리스트 ID 목록과 toggle 액션만 가진 store.
- 화면은 이 네 경계를 조합만 한다. scenario 제어값은 사용자 상태 어디에도 넣지 않는다.
