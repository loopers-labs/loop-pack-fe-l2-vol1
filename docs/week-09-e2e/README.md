# 비싼 E2E 테스트를 어디에 둘 것인가

이번 과제에서는 E2E 테스트를 많이 만드는 대신, 실제 브라우저에서만 확인하기 어려운 동작을 골라 남겼습니다. 사용자가 자주 거치는 화면인지뿐만 아니라, 기능이 망가졌을 때 사용자가 겪는 피해와 더 빠른 테스트로 같은 문제를 찾을 수 있는지도 함께 살폈습니다.

그 결과 9주차에는 인증, 주문 완료, 비회원 장바구니 병합을 E2E 대상으로 골랐습니다. 상품 목록과 상세는 훨씬 자주 쓰이지만, 대부분의 문제를 통합 테스트에서 더 빠르고 자세하게 찾을 수 있어 새 E2E를 추가하지 않았습니다.

| 살펴본 기능 | 선택한 테스트 | 판단한 이유 |
| --- | --- | --- |
| 로그인과 보호된 주문 화면 | E2E와 통합 테스트 | 쿠키, 서버 화면, 로그인 API, 화면 이동이 함께 이어지는지는 E2E로 확인하고 세부 조건은 통합 테스트로 확인합니다. |
| 주문 완료 | E2E와 통합 테스트 | 주문 생성부터 주문 내역 표시까지는 E2E로 확인하고 금액 계산과 오류 처리는 통합 테스트로 확인합니다. |
| 비회원 장바구니 병합 | E2E와 통합 테스트 | 로그인 전후로 쿠키와 브라우저 저장소가 함께 바뀌는 흐름은 E2E로 확인하고 수량 계산은 통합 테스트로 확인합니다. |
| 상품 탐색 | 통합 테스트 | 요청 조건, 목록 누적, 오류, 재시도를 실제 브라우저 없이도 충분히 확인할 수 있습니다. |

구체적인 이벤트 이름과 집계 기준, 테스트별 완료 조건은 [9주차 E2E 범위 문서](../rfc/week09-e2e-scope.md)에 먼저 정리했습니다. 이 글에서는 그 결정을 실제 테스트와 실험으로 확인하며 무엇을 배웠는지 설명합니다.

## 많이 쓰는 기능이 항상 E2E 대상은 아니었습니다

E2E 테스트는 사용자가 앱을 쓰는 모습과 가장 비슷합니다. 그러나 브라우저와 서버를 함께 띄워야 해서 오래 걸리고, 화면 문구나 이동 순서가 바뀌면 손볼 곳도 많습니다. 같은 문제를 단위 테스트나 통합 테스트에서 알아낼 수 있다면 굳이 E2E까지 늘릴 이유가 없습니다.

먼저 30일 동안 쌓인 8,000개 세션과 22,427개 이벤트를 살펴봤습니다. 세션은 한 사용자가 앱에 들어와 행동한 한 번의 방문을 뜻합니다. 한 사람이 같은 버튼을 여러 번 눌러도 한 세션으로 세어, 반복 행동 때문에 순위가 부풀지 않도록 했습니다.

분석을 흐리는 기록도 먼저 걷어냈습니다.

- 이벤트가 하나뿐이고, 그 이벤트가 `product_list_view`인 세션을 먼저 찾았습니다. 그중 `category=all`, `sort=latest`, `page=1`, `device=null`이며 시각의 밀리초가 `.000`, 시간이 UTC 01시인 486개 세션을 예약 실행으로 생긴 자동 방문 후보로 봤습니다. 이 조건을 모두 만족할 때만 제외했습니다.
- 세션 ID, 시각, 이벤트 이름, 상세 값, 사용자 ID, 기기가 모두 같은 77개 이벤트는 두 번째 기록부터 제외했습니다.
- 이미지 불러오기 실패만 담긴 `client_error` 103건은 행동 순위와 퍼널에서 제외했습니다. 다만 오류 코드와 오류가 있던 상세 세션의 전환을 확인할 수 있도록 별도 장애 분석에는 유지했습니다.

이 과정을 거친 뒤 행동 퍼널에서는 7,514개 세션과 21,761개 이벤트를 분석했습니다. 정리 전후의 12개 행동 이벤트 순위는 바뀌지 않았습니다. 자동 방문이 상품 목록 첫 화면에만 섞여 있었고, 중복 기록도 이미 해당 행동을 한 세션 안에서 생겼기 때문입니다. 다만 자동 방문을 그대로 두면 상품 상세 이후의 비율이 실제보다 낮아지므로 제외할 필요가 있었습니다.

| 사용자가 거친 단계 | 세션 수 | 전체 세션에서 차지한 비율 | E2E 판단 |
| --- | ---: | ---: | --- |
| 상품 목록 | 7,514 | 100.00% | 새 E2E를 추가하지 않음 |
| 상품 상세 | 4,656 | 61.96% | 새 E2E를 추가하지 않음 |
| 장바구니 담기 | 1,309 | 17.42% | 로그인 뒤 병합되는 흐름을 확인 |
| 로그인 시작 | 644 | 8.57% | 반드시 확인 |
| 주문 시작 | 419 | 5.58% | 주문 완료 흐름에 포함 |
| 주문 완료 | 277 | 3.69% | 반드시 확인 |

상품 목록은 모든 세션에서 사용됐지만, 목록 요청 조건과 화면 상태는 API 응답을 대신 만들어 주는 Mock Service Worker(MSW) 통합 테스트에서 빠르게 확인할 수 있습니다. 필터, 정렬, 다음 페이지, 오류, 재시도도 같은 방식으로 원인을 좁힐 수 있습니다. 실제 화면에서 다음 목록을 자동으로 불러오지 못해도 사용자가 `더 보기` 버튼으로 같은 동작을 할 수 있으므로, 새 E2E까지 만들 필요는 없다고 판단했습니다.

주문 완료는 277개 세션뿐이었지만 E2E에 남겼습니다. 주문이 중간에 끊기면 사용자는 주문 요청이 처리됐는지, 주문이 만들어졌는지 알기 어렵습니다. 사용 빈도가 낮더라도 사용자가 겪는 피해가 크고, 로그인 쿠키부터 주문 API와 화면 이동까지 모두 이어져야 끝나는 기능이기 때문입니다.

로그에 기록된 횟수는 결정을 돕는 자료였지만 결정 그 자체는 아니었습니다. 자주 쓰이는 상품 탐색은 통합 테스트에 맡기고, 비교적 적게 쓰이는 주문 완료는 E2E로 확인한 이유도 여기에 있습니다.

## E2E에는 브라우저가 이어 주는 동작만 남겼습니다

처음에는 한 주문 E2E 안에서 주문 생성, 장바구니 비우기, 주문 내역 이동, 새 주문 표시를 모두 확인하려고 했습니다. 비회원 장바구니 테스트에도 여러 탭 사이의 동기화와 로그아웃 뒤 정리까지 넣으려 했습니다.

이렇게 작성하면 하나가 실패했을 때 어디서 문제가 시작됐는지 찾기 어렵습니다. 통합 테스트에서 이미 확인한 계산과 저장 동작도 브라우저에서 다시 검사하게 됩니다. 그래서 E2E 하나가 사용자가 확인할 최종 결과 하나만 맡도록 줄였습니다.

### 인증은 네 가지 위험으로 나눴습니다

인증은 다음 네 가지를 각각 확인합니다.

- 로그인하지 않은 사용자가 주문서에 들어가면 로그인한 뒤 원래 주문서로 돌아옵니다.
- 만료된 로그인 정보로 주문 내역에 들어가면 다시 로그인하라는 화면으로 이동합니다.
- 잘못된 비밀번호를 입력하면 오류를 보여 주고 로그인 화면에 머뭅니다.
- 외부 주소를 복원 경로로 넣어도 로그인 뒤 애플리케이션 origin을 벗어나지 않습니다.

네 테스트는 모두 로그인을 다루지만 시작 상태와 실패 원인이 다릅니다. 하나의 긴 흐름으로 묶지 않고 독립된 테스트로 나눴습니다. 범위를 셀 때는 인증이라는 한 기능으로 보되, 실패 결과는 바로 구분할 수 있게 한 것입니다.

`proxy.ts`는 로그인 쿠키가 없는 요청을 빠르게 로그인 화면으로 보냅니다. 쿠키가 있다는 사실만으로 로그인했다고 확정하지는 않습니다. 서버 화면은 `getCurrentUser()`나 `requireCurrentUser()`를 호출하고, 두 함수는 내부에서 `readSessionToken()`으로 서명과 만료 시각을 확인합니다. 공통 레이아웃도 서버에서 현재 사용자를 먼저 읽으므로, 브라우저에서 자바스크립트가 시작되기 전부터 머리글에 로그인 상태가 드러납니다.

주문 API는 로그인 정보가 올바르지 않으면 401을 돌려줍니다. 클라이언트의 `handleSessionExpiry()`는 로그인이 필요한 요청에서 받은 401만 로그인 화면으로 연결합니다. 모든 401을 로그인 만료로 여기면 일반 로그인 실패까지 화면 이동으로 이어질 수 있어, 각 화면에서 따로 판단하지 않고 이 함수 한 곳에서 요청의 성격과 응답 값을 함께 확인합니다.

보호할 화면은 주문서(`/orders/new`)와 주문 내역(`/orders`)으로 한정했습니다. 상품과 장바구니(`/cart`)는 로그인하지 않아도 볼 수 있습니다. 로그인 뒤 돌아갈 주소는 `/`로 시작하는 앱 내부 주소만 허용합니다. `//example.com`처럼 외부 사이트로 이어질 수 있는 주소나 완전한 외부 주소는 `/`로 바꿉니다.

### 주문은 만들어진 결과만 확인했습니다

주문 E2E는 회원 장바구니에 상품 한 개를 준비합니다. 사용자가 주문 버튼을 누른 뒤 주문 생성 응답의 ID로 `/orders`에서 방금 만든 주문 카드 하나를 찾고, 그 카드에 상품과 수량이 나타나는지만 확인합니다.

금액과 수량 계산, 서버에 보내는 요청 내용, 주문 뒤 장바구니를 비우는 동작은 통합 테스트가 맡습니다. 실패 경로는 대표 오류 응답 하나로 오류 문구와 장바구니·현재 화면 유지를 확인하고, 400·500 상태 계약은 Route Handler 테스트에서 나눠 확인합니다. 같은 상품을 두 번 담거나 새로고침 뒤 수량을 복원하는 동작도 주문 E2E에서 되풀이하지 않습니다.

### 장바구니는 로그인 전후의 상품 보존만 확인했습니다

비회원 장바구니에는 `guest`, 회원 장바구니에는 `user:<userId>`라는 주인을 나타내는 값을 붙였습니다. 사용자가 로그인하면 비회원 장바구니의 상품 수량을 회원 장바구니에 합친 뒤 `guest` 장바구니를 비웁니다.

E2E에서는 비회원이 담아 둔 상품이 로그인 뒤 주문서에 같은 수량으로 남는지만 확인합니다. 수량을 더하는 계산, 저장소의 주인이 바뀌는 과정, `guest` 장바구니 정리, 여러 탭 사이의 변경 알림은 통합 테스트에 맡겼습니다.

로그아웃할 때는 회원 장바구니를 비회원 장바구니로 옮기지 않습니다. 회원별 저장소에 그대로 남겨 두어 다른 사용자나 비회원 화면에 보이지 않게 했습니다. 로그아웃 API가 성공하면 분석 도구에 남은 사용자 식별값과 주문 조회 결과를 지우고 서버 화면을 새로 불러옵니다.

## 테스트끼리 서로 영향을 주지 않게 나눴습니다

인증 자체를 확인하는 테스트와 비회원에서 회원으로 바뀌는 장바구니 테스트는 로그인 화면을 직접 거칩니다. 이미 로그인했다는 상태를 불러오면 정작 확인하려는 로그인 과정을 건너뛰기 때문입니다.

주문 테스트는 로그인 자체를 확인하지 않으므로 Playwright의 `storageState`를 사용합니다. `storageState`는 브라우저의 쿠키와 저장 상태를 파일에 담아 다음 테스트에서 다시 쓰는 기능입니다. 매번 로그인 화면을 채우지 않아도 주문 행동부터 바로 확인할 수 있습니다.

여러 테스트가 동시에 주문을 만들 때 같은 회원을 쓰면 주문 내역이 섞일 수 있습니다. 동시에 움직이는 각 작업 단위(worker)는 Playwright의 `parallelIndex`로 여덟 계정 중 하나를 고릅니다. 각 작업 단위는 자기 계정과 그 회원의 장바구니 저장소만 사용합니다. 주문 테스트는 기존 주문이 남아 있어도 방금 받은 주문 ID의 카드만 검증합니다. 실제로 첫 반복 검증에서는 같은 상품 링크가 누적되어 22/24만 통과했고, 이 단언을 보강한 뒤 워커 하나와 네 개에서 각각 세 번 반복해 24/24가 통과했습니다.

화면 요소는 사용자가 알아볼 수 있는 역할과 이름으로 찾았습니다. `getByTestId`는 사용하지 않았습니다. 시간을 정해 두고 기다리는 `sleep`도 쓰지 않고, URL이 바뀌거나 필요한 요소가 나타나는 조건을 기다렸습니다.

## 실행 기록에서 API와 화면을 함께 비교했습니다

Playwright의 실행 기록(trace)은 테스트가 실패하기 전후의 화면 이동, 요청과 응답, 사용자가 보던 화면을 같은 시간 순서로 보여 줍니다. 설정만 켜 두지 않고, 5단계에서 실제로 주입한 `proxy.ts` matcher 결함을 production build에 반영한 뒤 비회원 장바구니 E2E를 `--trace=on`으로 실행했습니다. 테스트 코드는 바꾸지 않았습니다.

실패 메시지는 장바구니 상품 링크를 5초 동안 찾지 못했다는 결과만 보여 줬습니다. trace의 URL·Network·마지막 DOM을 함께 보니 다음 순서가 드러났습니다.

```text
비로그인 홈에서 Next가 /cart?_rsc=... 를 prefetch
→ proxy가 307 Location: /login?returnTo=%2Fcart 응답
→ 테스트의 page.goto('/cart') document 요청도 307 응답
→ 최종 URL과 DOM은 상품이 있는 장바구니가 아니라 로그인 화면
→ 상품 링크 locator가 5초 뒤 실패
```

| 확인한 곳 | 실제로 확인한 값 | 알게 된 내용 |
| --- | --- | --- |
| 최초 RSC 요청 | `GET /cart?_rsc=…` → 307, `Location: /login?returnTo=%2Fcart` | `<Link href="/cart">`의 자동 prefetch부터 잘못된 matcher를 통과했습니다. |
| document 이동 | `GET /cart` → 307, 같은 로그인 주소 | 데이터나 hydration 전에 실제 route 경계가 요청을 차단했습니다. |
| 마지막 DOM | 로그인 heading·폼·로그인 링크 | 상품 조회나 장바구니 렌더 실패가 아니라 잘못된 인증 경계였습니다. |
| 기다리던 단언 | 카디건 상품 링크 | 실패 메시지만으로는 307의 원인을 알 수 없고 trace가 시작 지점을 좁혔습니다. |

분석 직후 matcher에서 `/cart/:path*`를 제거해 구현을 원복했습니다. trace 파일은 요청·응답과 쿠키를 포함할 수 있으므로 저장소에 올리지 않고, 확인한 사실만 문서에 남겼습니다.

## 구현을 일부러 망가뜨려 E2E의 필요성을 확인했습니다

통과하는 테스트가 정말 문제를 찾아내는지 확인하려고 테스트 코드는 그대로 두고 구현 한 곳씩만 바꿨습니다. 실험이 끝날 때마다 구현을 원래대로 되돌린 뒤 다음 실험을 시작했습니다.

| 일부러 만든 문제 | 단위·통합 테스트 결과 | E2E 결과 | 판단 |
| --- | --- | --- | --- |
| 로그인 뒤 원래 주문서 대신 첫 화면으로 이동 | 통합 테스트가 기대 주소와 실제 주소를 보여 주며 실패 | 원래 주문서로 돌아오는 테스트도 실패 | 통합 테스트가 직접 원인을 더 빨리 알려 줍니다. |
| 잘못된 비밀번호도 로그인 허용 | 데이터·API 테스트가 401 대신 200을 받아 실패 | 오류 문구 대신 주문 화면이 나타나 실패 | 비밀번호 확인은 데이터·API 테스트가 더 알맞습니다. |
| 공개 장바구니를 로그인 필수 화면으로 변경 | 실행한 proxy·장바구니 테스트 6개 통과 | 비회원 장바구니 테스트 실패 | Next.js가 `/cart` 요청에 proxy를 붙이는 과정까지 거친 E2E만 문제를 찾았습니다. |

세 변경은 모두 기존 테스트를 실패시켰습니다. 테스트 코드는 실험하는 동안 바꾸지 않았고, 테스트를 통과한 채 남은 문제도 없었습니다.

첫 번째와 두 번째 문제는 통합 테스트에서도 바로 찾을 수 있었습니다. E2E에서도 같은 문제가 드러났지만, 원래 주소를 계산하는 코드와 비밀번호를 확인하는 코드의 주된 검사는 더 빠른 테스트에 두는 편이 낫습니다.

세 번째 문제는 달랐습니다. `proxy()`를 직접 부르는 단위 테스트는 로그인 정보에 따라 무엇을 돌려주는지만 확인합니다. 장바구니 통합 테스트는 브라우저를 흉내 낸 jsdom에서 화면을 그리므로 실제 `/cart` 요청이 `proxy.ts`의 `config.matcher`와 연결되는 과정은 거치지 않습니다. 프로덕션 빌드를 띄운 E2E에서만 비회원이 장바구니 대신 로그인 화면으로 보내진다는 사실을 확인할 수 있었습니다.

처음에는 테스트와 구현이 같은 쿠키 이름 상수를 사용해서 통합 테스트가 놓친 문제를 E2E만의 사례로 생각했습니다. 하지만 통합 테스트가 실제 쿠키 이름을 직접 확인하도록 바꾸면 같은 문제를 찾을 수 있습니다. 이는 현재 테스트에 조건 하나가 빠진 문제이지, 반드시 실제 브라우저가 필요한 문제는 아니었습니다. E2E를 불필요하게 늘리는 근거로 쓰지 않기 위해 최종 사례에서 제외했습니다.

이 실험을 통해 E2E의 역할을 다시 정리했습니다. E2E는 단위·통합 테스트에서 빠진 조건을 대신 확인하는 마지막 안전망이 아닙니다. 실제 주소 요청, Next.js의 proxy 적용, 서버 화면, 쿠키, 브라우저 이동처럼 더 빠른 테스트에서 한꺼번에 실행하기 어려운 연결 과정을 확인하는 데 써야 합니다.

## 최종 E2E는 여덟 개로 정리했습니다

9주차에 고른 기능은 세 가지지만 실제 테스트 함수는 여섯 개입니다. 인증의 서로 다른 위험을 네 테스트로 나눴기 때문입니다. 여기에 8주차부터 유지한 상품 탐색 테스트 두 개를 더해 전체 E2E는 여덟 개가 됐습니다.

| 구분 | 확인하는 동작 | 테스트 수 |
| --- | --- | ---: |
| 인증 | 원래 주문서 복원, 만료된 로그인 처리, 잘못된 비밀번호 처리, 외부 복원 경로 차단 | 4 |
| 주문 | 주문 뒤 주문 내역에 새 주문 표시 | 1 |
| 비회원 장바구니 | 로그인 뒤 상품과 수량 유지 | 1 |
| 기존 상품 탐색 | 주소로 직접 들어가거나 새로고침했을 때 복원, 뒤로·앞으로 이동했을 때 복원 | 2 |

필터·정렬·장바구니 계산·오류 화면처럼 통합 테스트에서 더 잘 설명할 수 있는 동작은 E2E에 다시 넣지 않았습니다. 브라우저가 아니면 확인하기 어려운 이동과 저장소 연결만 남겼습니다.

## 로그인 초기 HTML의 성능 영향을 다시 확인했습니다

루트 레이아웃이 `getCurrentUser()`를 호출하고 그 안에서 `cookies()`를 읽기 때문에, production build에서 `/`, `/cart`, `/login`, `/orders`, `/orders/new`, `/products`, `/products/[id]`를 포함한 사용자 화면은 모두 동적 경로(`ƒ`)로 확인됐습니다. `robots.txt`와 `sitemap.xml`만 정적 경로로 남았습니다. 이 구조는 JavaScript 실행 전 초기 HTML에 로그인 상태를 넣기 위한 선택입니다.

구조만 보고 판단하지 않고 2026-09-04에 production server의 원본 document 응답도 확인했습니다. `Invoke-WebRequest`의 `WebRequestSession`으로 로그인 응답의 httpOnly 세션 쿠키를 보관한 뒤, 브라우저 DOM이나 hydration 결과가 아닌 `/` 응답의 `Content`를 직접 비교했습니다.

| 요청 상태 | HTTP | 원본 HTML에서 확인한 인증 UI |
| --- | ---: | --- |
| 쿠키 없는 `/` | 200 | `/login` 링크와 `로그인` 문구가 있고 `/orders` 링크와 `주문 내역`은 없음 |
| `POST /api/auth/login` 뒤 같은 세션의 `/` | 200 | `/orders` 링크, `주문 내역`, `루퍼1 로그인 중`, `로그아웃` 버튼이 있고 `/login` 링크는 없음 |

재현할 때는 `pnpm build` 뒤 `APP_ORIGIN=http://127.0.0.1:3209`로 `pnpm start -- -p 3209`를 실행했습니다. 비로그인 요청과 로그인 쿠키를 보관한 요청의 HTML 문자열에서 각 링크와 문구의 포함 여부를 검사했습니다. 따라서 로그인 상태가 클라이언트 JavaScript 실행 뒤에만 바뀌는 구조가 아니라 서버가 최초 HTML부터 서로 다른 헤더를 반환한다는 것을 확인했습니다.

7주차와 같은 모바일 412×823, DPR 1.75, Slow 4G 전송량, CPU 4배 제한, 캐시 비활성 조건으로 홈을 5회 다시 측정했습니다. 기존 Chrome 151과 Lighthouse 12.8.2 실행 파일은 현재 환경에 남아 있지 않아, Chrome 152에서 Playwright CDP와 `PerformanceObserver`로 같은 원시 지표를 수집했습니다. 따라서 작은 차이는 개선으로 해석하지 않고 회귀 여부만 판단했습니다.

| 지표 | 7주차 최종값 | 로그인 초기 HTML 적용 후 | 판단 |
| --- | ---: | ---: | --- |
| FCP 중앙값 | 2,198ms | 1,968ms | 기존 2,122–2,734ms 범위 안 |
| LCP 중앙값 | 2,262ms | 2,192ms | 기존 2,184–2,856ms 범위 안 |
| CLS 중앙값 | 0 | 0.0247 | 이동 원소를 별도 확인 |
| 응답 시작 | 대표 run 9.8ms | 중앙값 22.1ms | 첫 run 271.1ms, 나머지 20.1–23.6ms |

CLS는 다섯 번 모두 0.0247이었습니다. 추가 기록에서 가장 큰 이동은 홈 콘텐츠가 완성되며 초기 viewport의 footer가 밀려난 구간이었고, 작은 이동은 웹폰트 적용 전후의 Header navigation 폭 변화였습니다. 로그인 상태 영역은 layout shift source에 포함되지 않았습니다. FCP와 LCP는 기존 범위를 벗어나지 않았고 응답 시작 지연도 첫 서버 준비 요청을 제외하면 20.1–23.6ms였으므로, 인증이 필요한 영역만 별도 동적 레이아웃으로 분리하는 복잡도를 추가하지 않고 현재 구조를 유지합니다.

사용자별 HTML을 반환하므로 공개 캐시 헤더는 추가하지 않았습니다. 재현 스크립트는 [`scripts/measure-week09-performance.mjs`](../../scripts/measure-week09-performance.mjs), 5회 원시값과 route 판정은 [performance-regression.json](./performance-regression.json)에 남겼습니다.

7주차에 전송 병목을 확인하고 직접 만든 반응형 AVIF/WebP를 제공한 Hero `<picture>`는 그대로 유지했습니다. 6주차에 구조 변경과 섞지 않으려고 미뤘던 일반 상품 이미지는 별도 후속 작업으로 `next/image`에 옮겼습니다. 카드의 2·3·4열, 카테고리 최대 112px, 상세 최대 564px, 장바구니·주문 80px, 다이얼로그 64px 슬롯을 각각 `sizes`에 반영했습니다.

레이아웃이 달라지지 않았는지 production build의 390×844 viewport에서 전환 전후 렌더링 박스를 직접 비교했습니다. 카테고리 65.19px, 상품 카드 173px, 상세 358px, 장바구니·주문 80px, 다이얼로그 64px로 모두 같았고, 전환 후에는 여섯 위치 모두 `/_next/image` 최적화 경로를 사용했습니다. 375×812 소형 화면, 844×390 가로 화면, 768×1024 태블릿, 1440×900 데스크톱에서도 이미지와 기존 비율 wrapper의 너비·높이가 각각 일치했습니다. 이 비교는 기존 크기와 CLS 예약을 보존했다는 근거이며, 별도 전송량·LCP 측정 없이 추가 성능 개선 수치를 주장하지 않습니다.

일부러 망가뜨린 구현을 모두 되돌린 뒤 `pnpm check`를 실행했습니다.

| 확인한 항목 | 결과 |
| --- | --- |
| Vitest | 40개 파일, 182개 테스트 통과 |
| ESLint | Next.js 설정 기준 오류·경고 없음 |
| TypeScript | 타입 오류 없음 |
| 프로덕션 빌드 | 성공 |
| Playwright | 워커 4개에서 E2E 8개 통과 |

전체 E2E를 세 번씩 반복해 워커 하나에서 24/24, 네 워커에서도 24/24가 통과했습니다. Windows에서는 Playwright가 끝난 뒤 Next.js 서버가 자동으로 종료되지 않는 경우가 있어 프로세스를 직접 정리했습니다. 테스트 결과에는 영향을 주지 않았지만 실행 환경에서 따로 해결할 문제로 남겼습니다.

## 남은 판단과 배운 점

주문을 시작한 419개 세션 가운데 277개에 주문 완료 기록이 있었습니다. 나머지 142개는 사용자 중단, API 실패, 계측 누락을 구분할 수 없어 시스템 실패율로 해석하지 않았습니다. 주문 E2E는 이 비율이 아니라 주문 생성부터 내역 반영까지 검증할 기존 E2E가 없고, 흐름이 막혔을 때의 피해가 크다는 근거로 선택했습니다.

이번 과제에서 얻은 기준은 단순합니다.

- 사용 횟수만으로 E2E 대상을 고르지 않습니다.
- 더 빠른 테스트가 같은 문제를 자세히 알려 준다면 그 테스트에 맡깁니다.
- 실제 브라우저와 서버가 함께 이어져야 확인할 수 있는 결과만 E2E에 남깁니다.
- E2E 하나는 사용자가 확인할 중요한 결과 하나만 맡습니다.
- 통과 여부뿐만 아니라 실패 문구와 실행 기록으로 원인을 좁힐 수 있는지도 확인합니다.

E2E를 줄인다는 것은 덜 확인한다는 뜻이 아니었습니다. 각 문제를 가장 빨리, 가장 분명하게 알려 주는 자리에 테스트를 두는 일이었습니다.

## AI를 사용한 부분

AI와 함께 시드 로그 집계 결과를 표로 정리하고, 실행 기록에서 API 응답과 사용자 화면을 비교했습니다. 구현을 일부러 망가뜨릴 후보도 함께 검토했습니다.

어떤 동작을 E2E에 남길지, 테스트에서 무엇을 확인할지, 단위·통합·E2E 가운데 어디에 둘지는 실제 실행 결과를 확인한 뒤 직접 정했습니다. 통합 테스트로도 찾을 수 있는 쿠키 이름 문제를 E2E만의 사례에서 제외하고, Next.js가 `/cart` 요청에 proxy를 잘못 붙이는 문제로 다시 실험한 것도 같은 기준에 따른 결정입니다.
