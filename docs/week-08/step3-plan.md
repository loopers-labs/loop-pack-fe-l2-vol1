## 1. 남은 작업

### 1-1. 실험 3 — E2E (`partialize`)

| 항목        | 내용                                                                                                       |
| ----------- | ---------------------------------------------------------------------------------------------------------- |
| 망가뜨릴 곳 | `src/shared/lib/create-collection-store.ts`의 `partialize: (state) => ({ ids: state.ids })`                |
| 어떻게      | `partialize: () => ({ ids: [] })`                                                                          |
| 실행할 검증 | `pnpm build` 후 `pnpm exec playwright test e2e/state-restoration.spec.ts --grep "목록에서 찜·담기한 상태"` |
| 기대        | 클릭 직후 헤더 개수는 정상, `page.reload()` 뒤 복원이 실패                                                 |
| 함께 볼 것  | 같은 변형으로 12번 RTL(`Header.test.tsx`)은 **초록불로 남아야** 한다                                       |

마지막 줄이 이 실험의 진짜 목적이다. 통합과 E2E를 나눠둔 것이 값을 하는지가 여기서만 드러난다 — RTL이 잡아버리면 15번 E2E는 12번의 중복이라는 뜻이 된다.

E2E는 한 번 도는 데 오래 걸리므로(과제 197행) 빌드를 두 번 하지 않게 순서를 지킨다.

1. `partialize` 변형 적용
2. `pnpm build`
3. 대상 E2E만 `--grep`으로 실행
4. **같은 변형 상태에서** `pnpm exec vitest run src/widgets/header/Header.test.tsx` — 12번이 초록불인지 확인
5. 결과 기록
6. `git checkout src/shared/lib/create-collection-store.ts`
7. 대상 E2E 재실행해서 다시 통과하는지 확인

### 1-2. 실험 1·2를 한 번 더 볼지 결정 (작성자 판단 필요)

과제 195행과 계획서 「실험 순서」 5번이 이 시점에 요구하는 검토다.

> 세 실험이 전부 한 번에 잡혔다면, 쉬운 곳만 고른 게 아닌지 다시 보세요.

판단에 쓸 사실은 아래와 같다. **결론은 작성자가 정한다.**

- 실험 1: 4개 중 1개만 실패했다. `totalCount = 0`을 제외한 3개는 `Math.max`가 없어도 같은 값이라 원래 안 걸리는 자리다.
- 실험 2: 9개 중 1개만 실패했다. 실패한 것은 3페이지에서 카테고리를 바꾸는 경계 케이스이고, 나머지 8개는 1페이지에서 시작하므로 `page: 1`이 없어도 결과가 같다.
- 두 실험 모두 "전체가 우수수 빨개지는" 형태가 아니라 경계 하나만 빨개졌다. 이걸 "경계를 정확히 골랐다"로 읽을지 "나머지가 이 규칙을 안 보고 있다"로 읽을지가 갈림길이다.
- 후자로 읽는다면 추가 변형 후보가 있다: `setSort`의 `page: 1`(9번이 8번과 같은 구조로 보고 있는지), `getTotalPages`의 `Math.ceil` → `Math.floor`(딱 나누어떨어지지 않는 경우).

추가 변형을 하기로 정했다면 result 문서에 **왜 추가했는지**까지 적는다. 실험 개수는 과제 요구(계층당 1개 이상)를 이미 채웠으므로, 추가는 요구 충족이 아니라 판단의 결과다.

### 1-3. `step3-result.md` 작성

계획서에 정해둔 형식을 그대로 쓴다.


표 아래에 실험마다 문단으로 적는다.

1. 실패 메시지만 보고 원인을 추측할 수 있었는가 — 못 알아봤다면 테스트 이름이나 단언을 손볼 자리다(과제 191행)
2. 어떤 공개 동작을 그 테스트가 지키고 있었는가
3. 살아남았다면 왜 못 잡았는가
4. 살아남은 경우 어떤 단언을 보강했고, 같은 변형을 다시 적용했을 때 실패했는가

**살아남은 변경은 숨기지 않는다.** 과제 238행이 "그게 이번 주에 가장 값어치 있는 기록"이라고 적고 있다.

## 2. 지킬 규칙

과제 3단계 요구사항에서 온 것들이다. 어긴 코드를 지목할 수 있는 형태로 적는다.

- **한 번에 구현 한 곳만** 바꾼다. 두 변형을 동시에 적용하지 않는다.
- **테스트 코드는 건드리지 않는다.** 단, 1-2에서 "살아남았다"가 나와 보강하기로 정한 경우는 예외이며, 그 사실을 result 문서에 적는다.
- 실험 직후 구현을 원복하고 **대상 테스트를 다시 돌려 통과를 확인**한다. 원복했다는 말만 적지 않는다.
- 변형은 `git checkout <파일>`로 되돌린다. 손으로 다시 타이핑하지 않는다.
- 실험 대상 파일 외의 변경을 되돌리지 않는다.

## 3. 남아 있는 위험

- **E2E 실행 시간** — `pnpm test:e2e`가 빌드를 포함한다. 실험 3에서 빌드 → grep 실행 → 원복 → 재실행까지 빌드가 두 번 필요하다. 원복 후 재실행 시 구현이 바뀌었으므로 빌드를 다시 해야 한다.
- **실험 3이 살아남을 가능성** — `merge`가 복원 시 `readIds(persisted)`로 검증하므로, `partialize`가 빈 배열을 저장해도 저장 자체는 성공한다. 새로고침 후 `ids`가 빈 배열로 복원되는 것이 기대하는 결함인데, E2E가 헤더 개수를 **새로고침 이후에** 단언하지 않으면 살아남는다. 15번에 붙인 `page.reload()` 단언이 실제로 그 자리에 있는지가 이 실험의 성패를 가른다.
- **런타임 실행 권한** — 이 단계는 전부 실행이 필요하다. `AGENTS.md`상 런타임 검증은 사용자가 명시적으로 요청했을 때만 수행한다.
- **Advanced(Stryker)** — 선택 사항이다. 사용자가 요청하지 않으면 Basic 3단계까지만 한다.
