## 2. 왜 어긋났나 — 원인은 네 종류였다

### 유형 A. 계획서 단계에서는 알 수 없던 것 (1번)

표를 쓸 때 "기본값 생략"은 한 덩어리로 보였다. `?sort=latest`를 지우는 것과 `?page=3`을 지우는 것이 둘 다 "기본값이니까 지운다"로 읽혔다.

그 둘이 다르다는 건 **"이게 깨지면 사용자에게 뭐가 보이지?"를 실제로 따져봐야** 갈라진다. `page`가 남으면 공유한 링크를 받은 사람이 빈 화면을 보고, `sort`가 남으면 아무 일도 없다. 계획서 단계에서 이 해상도를 요구하는 건 무리다.

**이건 계획의 실패가 아니다.** "어디를 볼지"를 정해뒀기 때문에 "어떻게 볼지"가 구현 중에 드러난 것이다. 대응은 문서 갱신이지 재발 방지가 아니다.

### 유형 B. 의도만 쓰고 판정 조건을 안 쓴 문장 (4번)

「모킹 경계」에 이렇게 썼다.

> 잘못된 쿼리로 요청해도 순서만 맞아 통과하는 일을 막기 위해 MSW가 실제 URL의 요청 조건을 읽는다.

핸들러를 짜기 **전에** 쓴 문장이다. "조건을 읽는다"까지만 있고 "서버가 400을 주는 요청에는 핸들러도 400을 준다"가 빠졌다. 그래서 핸들러는 문장은 만족시키고(실제로 `category`·`sort`·`page`를 읽는다) 목적은 만족시키지 못했다 — 지원하지 않는 `sort`에도 정상 목록을 돌려줬다.

**의도를 적은 문장은 코드가 통과했는지 판정할 수 없다.** 판정 가능한 문장이었다면 짜는 순간 걸렸다.

### 유형 C. 계획을 초과한 것 (2번, 그리고 파일명)

`onUrlUpdate` 단언은 계획에 없는데 "어댑터가 이벤트를 주니 이것도 확인하자"로 들어갔다. 짜는 순간에는 **더 꼼꼼해 보이는 선택**이라 브레이크가 걸리지 않는다.

`HeaderCart.test.tsx`라는 파일명도 같은 종류다. 머릿속에서는 "헤더-장바구니 연결 테스트"라 자연스러운데, 그런 컴포넌트는 존재하지 않는다. 계획서 12번 항목명과도 파일 컨벤션과도 대조되지 않았다.

### 유형 D. 문서와 코드가 연결돼 있지 않다 (전부)

가장 큰 구조적 원인이다.

계획서에는 15개 항목에 **번호**가 있다. 그런데 테스트 코드 어디에도 그 번호가 없다. `ProductListContent.test.tsx`를 열어도 이 파일이 4·5·6·7·8·9·10번이라는 사실이 보이지 않는다. 코드를 고칠 때 문서를 열 계기가 생기지 않는다.

문서는 코드를 짜기 전에 한 번 읽히고 그 뒤로 아무도 열지 않는다. 그 상태로 코드가 며칠 움직이면 어긋나는 게 기본값이다.

## 3. 다음에 반복하지 않으려면

### ① 계획서 문장을 판정 가능한 형태로 쓴다

| 의도만 쓴 문장                        | 판정 가능한 문장                                     |
| ------------------------------------- | ---------------------------------------------------- |
| MSW가 실제 URL의 요청 조건을 읽는다   | 서버가 400을 주는 조건은 핸들러도 400을 준다         |
| 구현 세부사항 대신 사용자가 보는 결과 | `fetch` spy와 라이브러리 콜백 인자를 단언하지 않는다 |
| 접근 가능한 locator를 우선 사용한다   | `getByTestId`를 쓰면 이유를 주석으로 남긴다          |

기준은 "이 문장을 어긴 코드를 내가 지목할 수 있는가"다. 지목할 수 없으면 다짐이지 계획이 아니다.

### ② 항목 번호를 코드에 심는다

```ts
// 계획서 4·5·6·7·8·9·10번 — docs/rfc/week08-test-plan.md
describe('ProductListContent', () => {
```

파일 상단 주석 한 줄이면 된다. 코드를 고치는 사람에게 "이 단언에는 문서에 근거가 있다"가 보이고, 근거를 넘어서는 단언을 추가할 때 걸린다.

적용 결과 9개 파일에 붙었다. 항목 번호가 곧바로 붙는 6개(`search-params`·`get-total-pages`·`ProductListContent`·`useProductFilters`·`Header`·`state-restoration.spec.ts`) 외에 세 개가 더 나왔다 — 1번(`create-collection-store.test.ts`, "기존 테스트를 그대로 쓴다"도 결정이다), 2번과 6번에 걸친 `queries.test.ts`, 번호 대신 「기존 테스트와의 관계」 행을 가리키는 `api.test.ts`다. 번호를 심는 작업 자체가 문서와 코드의 대응을 다시 세게 만들었다.

### ③ 구현 중 바뀐 결정을 그때그때 계획서에 적는다

이번에는 구현을 다 끝낸 뒤에 대조해서 5개를 한꺼번에 찾았다. 유형 A는 어차피 구현 중에만 드러나므로, **그 자리에서 계획서에 한 줄 남기는 것**이 대조 비용을 없앤다. 계획서를 "코드보다 먼저 커밋하는 문서"로만 두면 갱신할 자리가 사라진다.

### ④ 대조를 언제 하는지 정해둔다

계획서가 있는 과제에서는 **커밋 전**에 한 번 대조한다. 이번처럼 커밋을 다 하고 나서 찾으면 문서 수정과 코드 수정이 뒤섞인 커밋이 나온다.

## 4. 어긋남이 나온 것 자체는

두루뭉술한 계획서는 절대 어긋나지 않는다. "테스트를 잘 작성한다"고 써두면 어떤 코드도 위반이 아니다.

`week08-test-plan.md`는 "URL 문자열은 단언하지 않는다", "요청 파라미터 대신 화면으로 확인한다"처럼 **위반 가능한 문장**으로 쓰여 있었다. 그래서 대조했을 때 5개가 걸렸다. 어긋남이 검출됐다는 건 계획서가 검증 가능한 수준으로 쓰여 있다는 뜻이기도 하다.

다음 단계는 "안 어긋나는 계획서"가 아니라 "어긋난 걸 빨리 아는 구조"다.

## 5. 2차 대조에서 더 나온 것

위 5개를 고친 뒤 한 번 더 대조했더니 네 개가 추가로 나왔다. 한 번의 대조로 끝나지 않는다는 게 이번의 결론이다.

| 자리                        | 무엇이 어긋났나                                                       | 어떻게 고쳤나                       |
| --------------------------- | --------------------------------------------------------------------- | ----------------------------------- |
| 「모킹 경계」 문장          | 코드에 400 검증을 넣고도 원문은 "조건을 읽는다"인 채였다              | 판정 가능한 문장으로 교체           |
| 7번 재시도 시나리오         | 계획서는 "첫 요청 실패 → 두 번째 성공", 코드는 두 번 실패 후 성공     | 코드가 더 낫다고 보고 계획서를 갱신 |
| 「3단계 예고」의 E2E 후보   | 1단계는 storage key, 2단계는 `partialize`로 뒤집혔는데 1단계가 그대로 | 1단계를 `partialize`로 갱신         |
| `step2-plan.md`의 커밋 상태 | "아직 커밋하지 않았다"가 사실과 달랐다                                | 현재 상태와 대조 결과를 반영        |

첫 번째가 특히 뼈아프다. **이 문서에서 그 문장을 "판정 불가 문장의 대표 예시"로 인용해놓고 원본은 안 고쳤다.** 방지책을 쓰는 것과 방지책을 자기 문서에 적용하는 것이 또 다른 일이었다.

`CLAUDE.md`(→`AGENTS.md`)가 "`pnpm check` 스크립트가 없다"고 쓰고 있는데 `package.json`에는 있다는 것도 이때 나왔다. 검증 정책 자체에 걸린 문제라 별도로 판단해, `AGENTS.md`와 `.claude/rules/verification.md`의 기본 검증 명령을 `pnpm verify`로, `pnpm check`를 빌드 포함 명령으로 갱신했다.

## 6. 3차 대조 — 8주차를 잘못된 베이스에서 시작했다

7주차 PR을 머지한 `origin/develop`을 8주차 브랜치에 뒤늦게 머지한 뒤 다시 대조했다. 원래는 **7주차가 머지된 상태에서 8주차를 시작했어야** 한다. 머지 시점을 늦춘 것이 이번 어긋남의 원인이고, 앞의 유형 A~D와는 종류가 다르다.

### 유형 E. 계획과 코드가 아니라 베이스가 틀렸다

앞의 네 유형은 전부 **내가 쓴 문서와 내가 쓴 코드 사이**의 어긋남이었다. 이건 다르다. 0단계 진단도, 1단계 설계도, 2단계 구현도 각자의 기준에서는 맞다. 틀린 것은 **그 판단들이 올려다본 코드**다.

0단계에서 "지금 레포는 이렇다"고 조사한 것이 실제로는 7주차 작업이 빠진 레포였다. 그 위에서 내린 결정이 이후 단계로 그대로 전파됐다.

| 자리                          | 잘못된 베이스에서 본 것                              | 정상 베이스였다면                                                |
| ----------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------- |
| 환경 예외 대상                | `src/examples/**` 경로로 `HeroSection.test.tsx` 하나 | 그 디렉터리가 없다. **경로 예외라는 선택지 자체가 안 나온다**    |
| include에서 빠진 `.tsx`       | 1개                                                  | 2개 (`ProductListResults.test.tsx`가 더 있다)                    |
| 테스트 파일 수                | 7개                                                  | 9개                                                              |
| HeroSection 예외의 근거       | "과제 레포에서 내려온 코드라 손대지 않는다"          | 이미 7주차가 이동·수정한 파일. 이 근거가 없다                    |
| `api.test.ts`의 MSW 분석 대상 | `fetch(\`/api/products${query}\`)`                   | `fetch(\`${getApiBaseUrl()}/api/products${query}\`, { signal })` |
| 목록 에러 분기                | `isError` 한 갈래                                    | 최초 실패 / 갱신 실패 **두 갈래**                                |

### 무엇이 실제로 뚫려 있었나

가장 큰 것은 마지막 줄이다. 7주차가 `ProductListResults`에 두 번째 에러 분기를 넣었다.

```
isError && !displayData  → 목록 자리에 실패 이유와 재시도        (최초 실패)
isError &&  displayData  → 직전 목록 유지 + 흐름 밖 알림 + 재시도 (갱신 실패)
```

1단계 표의 6번은 이걸 한 갈래로 보고 최초 실패만 다뤘고, 2단계 RTL 테스트 두 개도 캐시가 빈 상태에서만 시작해 갱신 실패 경로를 지나지 않았다. **커버리지 자체가 빈 것은 아니었다** — 7주차와 함께 들어온 `ProductListResults.test.tsx`가 그 분기를 덮고 있다. 뚫려 있던 것은 계획서 쪽이다. 계획서가 이 분기의 존재도, 그걸 덮는 테스트도 몰랐다.

이걸 확인한 방법도 적어둔다. 6·7번에 갱신 실패 케이스를 추가한 뒤, 통과하는 것만으로는 그 분기에 닿았는지 알 수 없어 3단계와 같은 방식으로 구현을 변형해봤다.

| 변형                                  | 결과                                                        |
| ------------------------------------- | ----------------------------------------------------------- |
| `isError && !displayData` → `isError` | 새 RTL 테스트와 `ProductListResults.test.tsx`가 함께 잡는다 |
| `refreshErrorAlert`를 항상 `null`로   | 새 RTL 테스트 2개가 잡는다                                  |

첫 줄이 말해주는 것이 하나 더 있다. 이 변형은 정상 베이스에서 3단계를 했더라도 **어차피 잡혔을** 것이다. 7주차 테스트가 이미 그 자리를 지키고 있었기 때문이다. 즉 이번 건은 "테스트가 없었다"가 아니라 "계획서가 코드의 절반을 못 봤다"는 문제다.

### 고친 것

| 무엇을                        | 어떻게                                                         |
| ----------------------------- | -------------------------------------------------------------- |
| `vitest.config.ts`            | 죽은 경로 예외 삭제, 예외를 파일 docblock으로 이동             |
| `HeroSection.test.tsx` 외 1개 | `@vitest-environment node` docblock 추가                       |
| 1단계 계획서 6·7번            | 최초 실패 / 갱신 실패 두 갈래로 범위 확장                      |
| `ProductListContent.test.tsx` | 갱신 실패의 화면과 복구를 보는 테스트 2개 추가                 |
| 1단계 계획서 분류표           | `ProductListResults.test.tsx`를 「7주차에서 유입」 행으로 명시 |
| 0단계 문서                    | 잘못된 베이스에서 내려진 진단 4곳에 정정 주석                  |

**경로 대신 docblock을 고른 이유.** 예외의 근거가 파일 밖에 있으면 파일이 움직일 때 깨지고, 깨져도 테스트는 다른 project가 주워서 통과시킨다. `pnpm check`로는 영영 안 드러난다. docblock은 파일과 함께 움직인다. 이건 새 규칙도 아니다 — 0단계 문서가 「환경 분리 방식」에서 이미 그렇게 정해뒀는데 정작 HeroSection 예외만 config 경로로 걸었다. 5장 첫 번째 항목("방지책을 자기 문서에 적용하지 않았다")과 같은 종류다.

### 대조 시점에 대해

4장에서 "커밋 전에 한 번 대조한다"고 정했는데 이번 건은 그걸로 안 잡힌다. 내 커밋이 만든 어긋남이 아니라 **시작 지점이 만든 어긋남**이라서다. 붙일 것은 두 가지다.

- 과제를 시작하기 전에 **베이스 브랜치가 최신 `develop`인지 확인한다**. 0단계의 "지금 레포는 이렇다"가 여기서 결정된다.
- 그럼에도 뒤늦게 머지하게 되면, 머지 직후에 **0단계 조사부터 다시 읽는다**. 코드만 합치고 그 위에서 내린 판단을 그대로 두면 이번처럼 된다.

_이 문서는 Claude가 작성했다. 계획서와 테스트 코드를 대조해 5개의 어긋남을 찾아내고 유형 A~D로 분류한 것, 재발 방지책 4개를 제시한 것이 Claude다._

_각 자리를 문서와 코드 중 어느 쪽에 맞출지는 작성자가 정했다 — 특히 2번(`onUrlUpdate` 단언 제거)은 "RTL의 가짜 URL 단언은 증명하는 게 적다"는 작성자의 판단으로 코드를 걷어낸 것이고, Claude는 처음에 반대로 문서를 고쳤다가 되돌렸다._

_6장(3차 대조)도 Claude가 작성했다. 머지 후 0단계부터 3단계까지를 과제 체크리스트와 대조하다가 죽은 include 패턴을 찾아낸 것, 그것이 앞의 유형 A·B·C·D와 다른 종류라고 정리한 것이 Claude다. 유형 E라는 이름과 "대조 시점에 머지 직후를 추가한다"는 결정은 작성자가 받아들인 것이다._
