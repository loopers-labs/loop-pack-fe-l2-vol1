## 실험 1 — 단위 · `getTotalPages`의 하한

```
AssertionError: expected +0 to be 1 // Object.is equality
❯ src/shared/lib/get-total-pages.test.ts:14:51
```

**실패 메시지만 보고 원인을 알 수 있었나.** 알 수 있었다. `expected +0 to be 1`은 "0페이지가 나왔는데 1페이지여야 한다"로 그대로 읽힌다. 테스트 이름(`상품 0개를 페이지당 12개로 나누면 1페이지다`)에 입력과 기대값이 다 있어서 스택을 따라가지 않아도 어느 경계인지 특정된다.

**어떤 공개 동작을 지키고 있었나.** "상품이 0개여도 페이지는 최소 1개"라는 규칙이다. 이게 깨지면 `totalPages = 0`이 되어 페이지네이션이 `1 / 0`을 그리거나, 다음 버튼 활성화 판단이 어긋난다.

**고른 자리가 쉬웠나.** 파일 내 4개 중 3개는 통과했다. `Math.max(1, …)`는 `totalCount = 0`일 때만 값을 바꾸므로, 상품이 있는 평소 화면에서는 이 변형이 드러나지 않는다. 반환값을 통째로 지우면 4개가 다 빨개졌을 텐데, 경계 하나만 빨개진 것이 자리를 제대로 골랐다는 신호다.

**복구.** `git checkout`으로 되돌린 뒤 같은 명령을 다시 돌려 4개 통과를 확인했다.

## 실험 2 — 통합 · 필터 변경 시 페이지 리셋

```
TestingLibraryElementError: Unable to find role="heading" and name "디지털 실속상품"
❯ src/_pages/product-list/ui/ProductListContent.test.tsx:144
```

**실패 메시지만 보고 원인을 알 수 있었나.** 메시지 첫 줄만으로는 부족했다. "디지털 실속상품 heading이 없다"까지만 알려주므로, 카테고리 전환이 아예 안 된 것인지 다른 페이지를 보고 있는 것인지 구분되지 않는다.

구분해준 것은 RTL이 함께 덤프한 DOM이었다. 거기에 `검색 결과가 없습니다`와 페이지네이션의 `3 / 1`이 같이 찍혀 있었다. 카테고리는 바뀌었는데 `page=3`이 남아 있고, 새 카테고리의 총 페이지는 1이라 빈 결과가 된 상태다. 원인이 "필터 변경 시 페이지가 1로 안 돌아감"이라는 게 여기서 확정된다.

테스트 이름이 `3페이지에서 카테고리를 바꾸면 1페이지의 해당 상품을 요청한다`라 이름과 DOM 덤프를 같이 보면 짚인다. 메시지 한 줄만으로 짚이지 않는 것은 `findByRole` 실패가 원래 "무엇이 없다"만 말하기 때문이고, 단언 방식의 문제로 보지는 않았다 — 여기서 확인해야 하는 건 화면에 보이는 결과이고, 요청 파라미터를 들여다보는 쪽은 1단계에서 의도적으로 뺀 방향이다(「모킹 경계」).

**어떤 공개 동작을 지키고 있었나.** "필터를 바꾸면 페이지가 1로 돌아간다"는 규칙이다. 이게 깨지면 뒤쪽 페이지를 보던 사용자가 카테고리를 바꿨을 때 빈 화면을 만난다.

**고른 자리가 쉬웠나.** 9개 중 8개가 통과했다. 나머지 8개는 1페이지에서 시작하므로 `page: 1`을 넣든 안 넣든 결과가 같다. 카테고리를 바꾸면 목록 자체는 실제로 바뀌기 때문에, 이 변형은 "절반은 정상으로 보이는" 종류다.

**복구.** 되돌린 뒤 9개 전부 통과를 확인했다.

## 실험 3 — E2E · `persist`의 저장 대상

```
Error: expect(locator).toBeVisible() failed
Locator: getByText('위시리스트 1', { exact: true })
Expected: visible
Timeout: 5000ms
Error: element(s) not found
❯ e2e/week-05-state.spec.ts:46
```

> 실험 당시 파일명이다. 이후 저장소 규칙(`e2e/<feature>.spec.ts`)에 맞춰 `e2e/state-restoration.spec.ts`로 바꿨다.

**실패 메시지만 보고 원인을 알 수 있었나.** 위치가 알려줬다. 실패한 46행이 `page.reload()` 바로 다음 줄이고, 그 앞 41행까지의 헤더 개수 단언은 전부 통과했다. "클릭 직후에는 맞는데 새로고침 후 사라진다"가 실패 지점만으로 드러나므로 저장·복원 경로를 의심하게 된다. Chromium과 WebKit이 같은 줄에서 같은 방식으로 실패한 것도 브라우저별 차이가 아니라는 근거가 됐다.

**어떤 공개 동작을 지키고 있었나.** "담은 상품이 새로고침 후에도 남아 있다"는 약속이다. `partialize`가 빈 배열을 저장하면 `localStorage`에는 `{ ids: [] }`가 들어가고, `merge`의 `readIds`는 그 값을 정상으로 판단해 빈 목록으로 복원한다. 저장도 복원도 에러 없이 성공하지만 사용자 데이터만 사라진다.

**계층을 나눠둔 것이 값을 했나.** 이 실험의 진짜 목적이 여기였다. 같은 변형을 그대로 둔 채 12번 RTL(`src/widgets/header/Header.test.tsx`)을 돌렸더니 3개 전부 통과했다.

| 계층                   | 같은 변형에서 결과 | 왜                                                                        |
| ---------------------- | ------------------ | ------------------------------------------------------------------------- |
| 12번 (RTL, 통합)       | 통과               | 테스트가 store를 직접 붙여 렌더하므로 `persist` 저장 경로를 지나지 않는다 |
| 15번 (Playwright, E2E) | 실패               | 실제 브라우저에서 새로고침해 `localStorage` 복원을 지난다                 |

1단계에서 12번과 15번이 "대상이 겹쳐 보이지만 보는 것이 다르다"고 적었는데, 그 구분이 실제로 성립한다는 게 이 실험으로 확인됐다. 둘 중 하나만 있었다면 이 결함은 통과했을 것이다.

**고른 자리가 쉬웠나.** 클릭 직후 화면은 완전히 정상이다. 헤더 개수도 버튼의 `aria-pressed`도 바뀐다. 새로고침이라는 한 단계를 더 밟아야만 드러난다.

**복구.** 되돌린 뒤 production build를 다시 만들고 같은 E2E를 돌려 Chromium·WebKit 모두 통과를 확인했다.

## 세 실험이 전부 잡힌 것에 대해

과제는 세 실험이 전부 한 번에 잡혔다면 쉬운 곳만 고른 게 아닌지 다시 보라고 한다(과제 195행). 판정 기준은 "살아남은 게 나왔나"가 아니라 "고른 자리가 눈에 잘 안 띄는 곳이었나"로 읽었다.

| #   | 전체 중 실패한 테스트  | 나머지가 통과한 이유                                       |
| --- | ---------------------- | ---------------------------------------------------------- |
| 1   | 4개 중 1개             | `totalCount = 0`이 아니면 `Math.max`가 값을 바꾸지 않는다  |
| 2   | 9개 중 1개             | 1페이지에서 시작하면 `page: 1`이 있으나 없으나 같다        |
| 3   | 대상 2개(브라우저 2종) | 같은 변형에 12번 RTL은 통과 — 새로고침을 지나야만 드러난다 |

세 줄 모두 "대부분 통과하고 경계 하나만 빨개졌다"는 형태다. 반환값을 통째로 지우는 쉬운 변형이었다면 해당 파일이 우수수 빨개졌을 텐데 그렇지 않았다. 이 근거로 추가 실험 없이 마감했다.

다만 이번에 확인하지 않은 자리는 남는다. `setSort`의 `page: 1`은 `setCategory`와 같은 구조라 실험 2가 대신 본 것으로 취급했고, 실제로 변형해보지는 않았다. `getTotalPages`도 `Math.max` 쪽만 봤고 `Math.ceil` → `Math.floor` 같은 다른 경계는 남겨뒀다. (이 자리는 이후 Advanced에서 확인했다 — [`docs/week-08/advanced-result.md`](./advanced-result.md) §3.) 계층당 하나라는 과제 요구를 넘어서는 범위라 이번에는 하지 않기로 정한 것이고, 못 한 것과 구분해 적어둔다.
